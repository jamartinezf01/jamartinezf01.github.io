1.3. Entidades JPA

En el apartado anterior hemos instalado MySQL en Windows y configurado la conexión desde Spring Boot. Ya tenemos una base de datos llamada mi_coleccion, pero todavía no hemos definido qué información queremos guardar ni cómo se organizará.

En Java trabajamos con clases y objetos. En MySQL, con tablas y registros. Ahora aprenderemos a relacionar ambos modelos mediante las entidades JPA, que permiten describir cómo debe almacenarse la información de nuestros objetos.

Idea principal

Una entidad JPA es una clase Java que representa información persistente. Mediante anotaciones indicamos, entre otras cosas, qué tabla le corresponde, cuál es su identificador y cómo se almacenan sus propiedades.

Definir una entidad no guarda automáticamente ningún objeto. Primero describiremos la estructura y, más adelante, utilizaremos repositorios para almacenar y recuperar registros.

1️⃣ De una clase Java a una entidad JPA​

Recordemos que un videojuego puede representarse mediante una clase Java con propiedades como el título, el género, la plataforma y el año de lanzamiento. Si creamos un objeto de esa clase, sus datos existirán en memoria mientras la aplicación los mantenga disponibles.

En esta primera versión representaremos la plataforma mediante un String, igual que el género o el título. Nos interesa aprender a persistir una entidad sencilla antes de introducir relaciones entre entidades.

Para que Hibernate pueda trabajar con esos objetos y una base de datos relacional, necesita conocer su correspondencia con las tablas. Por ejemplo, una clase Videojuego puede estar asociada a una tabla videojuegos, y la propiedad anioLanzamiento a una columna anio_lanzamiento.

🟩 ¿Qué información necesita JPA?​

Como mínimo, identificaremos la clase como entidad y definiremos un identificador para distinguir cada registro. Además, podemos concretar el nombre de la tabla, los nombres de sus columnas y algunas restricciones.

Elemento en JavaRepresentación en MySQL
Clase Videojuego.Tabla videojuegos.
Objeto Videojuego.Fila de la tabla, cuando se guarda.
Propiedad titulo.Columna titulo.
Propiedad anioLanzamiento.Columna anio_lanzamiento.
Propiedad id.Clave primaria.

La correspondencia no significa que ambos modelos sean idénticos. Java sigue trabajando con objetos y MySQL con registros. JPA y Hibernate facilitan la conversión y la gestión de la información entre ambos.

2️⃣ Creamos nuestra primera entidad​

Vamos a incorporar una clase Videojuego al proyecto Spring Boot que ya tenemos configurado.

🟩 Organizamos el código​

Dentro del paquete principal crearemos un subpaquete llamado modelo. En el proyecto que estamos utilizando, el paquete principal es com.dwes.mi_coleccion. La estructura queda así:

src/main/java/
└── com/dwes/mi_coleccion/
    ├── MiColeccionApplication.java
    └── modelo/
        └── Videojuego.java

Si en otro proyecto utilizamos un paquete diferente, adaptaremos la ruta y la declaración package. Lo importante es que modelo esté dentro del paquete principal, de forma que Spring Boot pueda encontrar la entidad al iniciar la aplicación.

🟨 Escribimos la clase Videojuego​

Creamos el siguiente archivo. El ejemplo incluye el código completo, con los constructores y los métodos de acceso que necesitamos:

src/main/java/com/dwes/mi_coleccion/modelo/Videojuego.java
package com.dwes.mi_coleccion.modelo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "videojuegos")
public class Videojuego {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String titulo;

    @Column(nullable = false, length = 60)
    private String genero;

    @Column(nullable = false, length = 60)
    private String plataforma;

    @Column(name = "anio_lanzamiento", nullable = false)
    private Integer anioLanzamiento;

    protected Videojuego() {
    }

    public Videojuego(String titulo, String genero,
                      String plataforma, Integer anioLanzamiento) {
        this.titulo = titulo;
        this.genero = genero;
        this.plataforma = plataforma;
        this.anioLanzamiento = anioLanzamiento;
    }

    // Getters y Setters
}
en este ejemplo

La anotación @Entity indica que la clase es una entidad JPA, y @Table(name = "videojuegos") establece el nombre de su tabla. Las anotaciones de los atributos indican el identificador, su generación y determinadas características de las columnas.

JPA necesita que la entidad disponga de un constructor sin argumentos, que puede ser public o protected. Aquí lo hemos declarado protected para reservarlo al funcionamiento de JPA. Hemos añadido otro constructor para crear videojuegos desde nuestro código sin indicar manualmente su identificador. Cuando preparemos el formulario de alta, adaptaremos el constructor sin argumentos para poder crear expresamente un objeto vacío desde el controlador.

Los métodos get y set permiten consultar y modificar las propiedades desde Java. No hemos creado un setId(): el identificador lo generará la base de datos al guardar un registro. Que exista esta clase no significa que ya se haya insertado ningún videojuego.

consejo

IntelliJ IDEA puede generar los métodos getter, setter y los constructores desde Code → Generate (habitualmente Alt + Insert en Windows). Aunque los genere el IDE, debemos comprender para qué sirven.

🟧 ¿Por qué utilizamos jakarta.persistence?​

Las anotaciones anteriores pertenecen a la API Jakarta Persistence, que define JPA en las versiones actuales de Spring Boot. Por eso los import comienzan por jakarta.persistence y no por javax.persistence, utilizado en proyectos más antiguos.

No necesitamos añadir estas anotaciones una por una como dependencias Maven: ya incorporamos Spring Data JPA cuando generamos el proyecto.

3️⃣ Entendemos el mapeo de la entidad​

Vamos a detenernos en las anotaciones más importantes, porque son las que utilizaremos repetidamente al definir otras entidades. Primero reuniremos las herramientas disponibles y después estudiaremos cómo tomar decisiones de mapeo sin depender de la clase Videojuego.

🟩 Anotaciones de mapeo: una referencia para otras entidades​

Cuando creamos una entidad, no tenemos que utilizar todas las anotaciones. Elegimos las que describen correctamente los datos que queremos guardar. Esta tabla recoge las que necesitamos conocer por ahora:

Anotación¿Para qué sirve?Opciones o uso habitual
@EntityMarca una clase como entidad persistente.name permite establecer su nombre como entidad JPA.
@TableConfigura la tabla asociada.name = "videojuegos".
@IdSeñala la propiedad que actúa como identificador.Se coloca sobre el atributo identificador.
@GeneratedValueIndica cómo se obtiene un identificador generado.strategy = GenerationType.IDENTITY.
@ColumnConfigura el mapeo de una columna.name, nullable, unique, length, precision, scale.
@TransientExcluye una propiedad del almacenamiento.Útil para información calculada que solo necesita la aplicación.
@EnumeratedIndica cómo representar una enumeración.EnumType.STRING o EnumType.ORDINAL.

Las anotaciones @Entity y @Id son las esenciales en una entidad sencilla. @Table y @Column son opcionales cuando las convenciones por defecto nos sirven. @GeneratedValue se utiliza cuando queremos que el identificador se genere automáticamente.

consejo

Esta tabla es una referencia para consultar al crear otras entidades. No significa que debamos copiar todas las anotaciones en cada clase: por ejemplo, una propiedad String sencilla puede guardarse sin @Column.

🟨 El identificador: @Id y @GeneratedValue​

Toda entidad necesita una forma de identificar sus registros. En nuestro caso hemos definido:

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@Id indica que la propiedad es el identificador de la entidad, correspondiente a la clave primaria de la tabla. @GeneratedValue señala que el valor se generará automáticamente. Con GenerationType.IDENTITY, utilizamos el mecanismo de identidad de MySQL, habitualmente una columna AUTO_INCREMENT.

Por eso, cuando creemos un nuevo videojuego, no necesitaremos decidir si su identificador es 1, 2 o 3. MySQL lo asignará cuando se inserte el registro.

Utilizamos Long en lugar de long para poder representar también un identificador todavía no asignado, cuyo valor inicial será null.

@GeneratedValue admite diferentes estrategias. Conviene reconocerlas aunque, para esta unidad y con MySQL, seguiremos utilizando IDENTITY:

Estrategia¿De dónde procede el identificador?En nuestro contexto
IDENTITYDe una columna con generación automática en la base de datos.Es la opción que utilizamos con AUTO_INCREMENT de MySQL.
SEQUENCEDe una secuencia de la base de datos.Habitual en otros gestores. MySQL no dispone de secuencias SQL independientes equivalentes.
TABLEDe una tabla auxiliar que almacena los valores necesarios para generar identificadores.No la necesitamos en este proyecto.
AUTOEl proveedor JPA elige una estrategia.Puede comportarse de manera distinta según la base de datos y el proveedor.

Esta elección no cambia el significado de @Id: la clave primaria sigue identificando de forma única cada fila. Lo que cambia es cómo se obtiene su valor.

aviso

No debemos asignar manualmente el identificador de los videojuegos nuevos cuando lo genera la base de datos. Tampoco debemos modificar la clave primaria de un registro ya persistente como si fuera una propiedad cualquiera.

🟧 Las columnas: @Column​

La anotación @Column nos permite indicar características de una columna. Por ejemplo:

@Column(nullable = false, length = 120)
private String titulo;

En una tabla creada a partir de este mapeo, length = 120 establece la longitud de referencia para la columna de texto y nullable = false indica que la columna no debe admitir NULL.

En el año de lanzamiento hemos definido expresamente otro nombre:

@Column(name = "anio_lanzamiento", nullable = false)
private Integer anioLanzamiento;

La propiedad se llama anioLanzamiento en Java, pero la columna se llamará anio_lanzamiento en MySQL. No es obligatorio anotar cada columna: JPA dispone de convenciones por defecto. Aquí lo hacemos para que el mapeo quede claro y las restricciones sean explícitas.

Para definir otra entidad es útil distinguir las opciones más habituales de @Column:

OpciónQué indicaEjemplo
nameNombre de la columna en MySQL.name = "fecha_alta".
nullableSi la columna admite NULL.nullable = false.
uniqueSi los valores de esa columna deben ser únicos.unique = true.
lengthLongitud de una columna de tipo texto o binario compatible.length = 150.
precisionNúmero máximo de cifras de un valor decimal exacto.precision = 10.
scaleNúmero de cifras que se reservan para la parte decimal.scale = 2.

No todas las opciones tienen sentido para todos los atributos. length no establece el máximo de un Integer, y precision y scale se utilizan principalmente con tipos decimales exactos, como BigDecimal. Más adelante comprobaremos las columnas reales que Hibernate genera en MySQL.

🟨 Tipos de datos Java y SQL​

Al definir una entidad utilizamos tipos Java, mientras que MySQL almacena los valores en columnas con tipos SQL. Hibernate interpreta el mapeo y elige tipos compatibles según el gestor de base de datos. No necesitamos escribir una instrucción CREATE TABLE para cada clase, pero sí comprender qué datos estamos definiendo.

Tipo JavaTipo habitual en MySQLEjemplo de uso
StringVARCHARTítulo, nombre o descripción corta.
ByteTINYINTValor entero pequeño.
ShortSMALLINTCantidad entera pequeña.
IntegerINTAño, cantidad o número de unidades.
LongBIGINTIdentificador de una entidad.
FloatFLOATValor decimal aproximado.
DoubleDOUBLEValor decimal aproximado de mayor precisión.
BigDecimalDECIMALPrecio o importe monetario.
BooleanBIT o TINYINT(1)Disponible, activo o completado.

Estos son ejemplos habituales, no una equivalencia que debamos memorizar como invariable. El tipo concreto depende del proveedor JPA, del dialecto de MySQL y de la configuración. Podemos comprobar el resultado real con DESCRIBE videojuegos.

En nuestra entidad, titulo está limitado a 120 caracteres y genero y plataforma a 60. Son decisiones explícitas del modelo que deben reflejarse en las columnas correspondientes al generar una tabla nueva. Que plataforma sea una columna de texto es una decisión inicial del proyecto, no la forma definitiva de representar las plataformas.

Dos decisiones frecuentes: importes y valores sin asignar​

Si en otra aplicación necesitamos almacenar un precio, utilizaremos preferentemente BigDecimal, porque Float y Double representan números en coma flotante y pueden introducir pequeñas diferencias de redondeo. Por ejemplo:

@Column(nullable = false, precision = 10, scale = 2)
private BigDecimal precio;
en este ejemplo

Con precision = 10 indicamos un máximo de diez cifras significativas y con scale = 2, dos cifras decimales. La base de datos puede generar una columna como DECIMAL(10,2). Para utilizar este tipo en Java necesitaríamos importar java.math.BigDecimal.

Este atributo es un ejemplo independiente: no debemos añadirlo a Videojuego.

También debemos elegir entre tipos primitivos (int, boolean, long) y sus clases envoltorio (Integer, Boolean, Long). Los envoltorios admiten null y permiten representar un dato aún no asignado. Eso no significa que la base de datos deba aceptar NULL: una columna puede declararse nullable = false aunque en Java utilicemos Integer.

🟧 Restricciones: valores obligatorios y únicos​

Conviene distinguir dos niveles que ya conocemos de las unidades anteriores:

  • Validación de entrada. Comprobamos, por ejemplo, que una persona no envíe un título vacío desde un formulario.
  • Restricciones de la base de datos. Impedimos que se almacenen determinados valores que no respetan la estructura de la tabla.

Con @Column(nullable = false) indicamos que la columna no debe aceptar NULL. Sin embargo, esto no impide almacenar una cadena vacía (""); para comprobar que una persona ha escrito un título válido seguiremos utilizando las técnicas de validación de UT3 cuando incorporemos formularios CRUD.

También podemos declarar una columna como única:

@Column(nullable = false, unique = true, length = 100)
private String codigo;
en este ejemplo

La opción unique = true indica que los valores de esa columna no deben repetirse en la tabla, mediante una restricción de unicidad en la base de datos. Este ejemplo es independiente de nuestra entidad Videojuego: no haremos único el título, porque distintos videojuegos podrían compartirlo.

Declarar una restricción en JPA ayuda a definir el esquema, pero no sustituye las comprobaciones que necesitemos realizar en la aplicación. Si el esquema ya existe, ddl-auto=update tampoco garantiza que cualquier cambio en una restricción se aplique correctamente.

🟥 Propiedades que no se guardan y enumeraciones​

No todas las propiedades de una clase tienen por qué almacenarse. La anotación @Transient, de jakarta.persistence, permite excluir un atributo del mapeo:

@Transient
private String textoResumen;

En este ejemplo, textoResumen puede utilizarse en Java, pero no se creará una columna para él. No debemos confundir esta anotación JPA con la palabra clave transient del lenguaje Java.

Otra posibilidad habitual es guardar el valor de una enumeración. Imaginemos que, en otra aplicación, definimos estos estados:

public enum Estado {
    PENDIENTE,
    COMPLETADO
}

Podríamos mapear una propiedad de ese tipo de la siguiente forma:

@Enumerated(EnumType.STRING)
private Estado estado;
en este ejemplo

Con @Enumerated(EnumType.STRING) indicamos que JPA debe representar el valor por el nombre de la constante, como PENDIENTE, en lugar de por su posición numérica. Así evitamos depender del orden en que aparecen las constantes del enum. Hibernate puede utilizar el tipo ENUM nativo de MySQL para este mapeo.

La alternativa EnumType.ORDINAL almacena una posición numérica (0, 1, etc.). Resulta más frágil: si reordenamos las constantes, los valores existentes pueden interpretarse de otro modo. Por eso, salvo una necesidad justificada, preferiremos STRING.

Estos dos ejemplos muestran posibilidades del mapeo, pero todavía no debemos añadirlos a Videojuego. Mantendremos nuestra entidad sencilla hasta que necesitemos esas propiedades en una funcionalidad real.

🟪 ¿Dónde colocamos las anotaciones JPA?​

En Videojuego hemos escrito @Id, @Column y las demás anotaciones directamente sobre los atributos. Esto se denomina acceso por campos (field access): JPA realiza el mapeo a partir de los campos, sin necesitar llamar a los getters y setters para leerlos o escribirlos.

También existe el acceso mediante propiedades, colocando las anotaciones en métodos getter. En esta unidad utilizaremos el acceso por campos de forma coherente en nuestras entidades, para no mezclar ambas estrategias sin necesidad.

🟩 Cómo diseñar el mapeo de otra entidad​

Hasta ahora hemos observado qué hace cada anotación. Pero, cuando debamos crear una entidad nueva, el punto de partida no será copiar el código de Videojuego, sino decidir qué datos necesita nuestra aplicación.

Imaginemos una biblioteca que guarda libros con un identificador automático, un ISBN que no puede repetirse, un título obligatorio, un número de ejemplares y una fecha de publicación opcional. Antes de escribir la clase, podemos tomar estas decisiones:

Información que queremos guardarTipo Java adecuadoDecisión de mapeo
Identificador del libro.Long.@Id y @GeneratedValue(strategy = GenerationType.IDENTITY).
ISBN.String.@Column(nullable = false, unique = true, length = 17).
Título.String.@Column(nullable = false, length = 150).
Número de ejemplares.Integer.@Column(nullable = false).
Fecha de publicación.LocalDate.Puede admitir NULL si es un dato opcional.

Por ejemplo, solo los atributos de esa entidad podrían declararse así:

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@Column(nullable = false, unique = true, length = 17)
private String isbn;

@Column(nullable = false, length = 150)
private String titulo;

@Column(nullable = false)
private Integer ejemplares;

private LocalDate fechaPublicacion;
en este ejemplo

Este fragmento no es una clase completa ni debemos incorporarlo a MiColección. En una entidad real añadiríamos @Entity, el constructor sin argumentos y los métodos o constructores necesarios, además de importar java.time.LocalDate y las anotaciones utilizadas. La idea es aprender a justificar cada atributo y cada restricción, no reproducir de memoria los campos de Videojuego.

Que ejemplares sea obligatorio en la base de datos no impide introducir un número negativo: si necesitáramos prohibirlo, añadiríamos validación o una restricción adecuada. Del mismo modo, una cadena vacía no se convierte en válida solo por tener nullable = false.

Cuando diseñemos una entidad propia, podemos seguir este orden: identificar los datos, elegir sus tipos Java, decidir qué datos son obligatorios o únicos y, por último, añadir las anotaciones necesarias. Después comprobaremos el esquema real en MySQL.

4️⃣ Comprobamos la tabla en MySQL​

Ya podemos observar una primera consecuencia práctica de haber definido la entidad. Como tenemos configurado spring.jpa.hibernate.ddl-auto=update, Hibernate intentará crear o adaptar la tabla correspondiente cuando iniciemos Spring Boot.

aviso

ddl-auto=update resulta útil para practicar con un esquema sencillo, pero no garantiza todas las modificaciones de una tabla existente ni protege frente a cualquier cambio de estructura. Cuando lleguemos a la migración de MiColección, haremos una copia de seguridad y comprobaremos los datos antes de modificar sus columnas y relaciones. No cambiaremos ahora la estructura de la tabla manualmente.

🟩 Arrancamos la aplicación​

Primero comprobamos que el servicio de MySQL esté en funcionamiento. Desde PowerShell ejecutamos (utilizaremos el nombre real del servicio si no es MySQL84):

Get-Service -Name MySQL84

Debe aparecer en estado Running.

Después iniciamos Spring Boot desde IntelliJ IDEA con la variable de entorno DB_PASSWORD configurada. La aplicación debería arrancar sin errores relacionados con la conexión o el mapeo.

🟨 Inspeccionamos la estructura creada​

Abrimos PowerShell y entramos en MySQL con el usuario de la aplicación:

mysql -u coleccion_app -p mi_coleccion

Introducimos la contraseña de coleccion_app que establecimos al configurar la conexión con MySQL. A continuación ejecutamos:

SHOW TABLES;
DESCRIBE videojuegos;
SELECT COUNT(*) FROM videojuegos;
en este ejemplo

SHOW TABLES nos permite comprobar que existe la tabla videojuegos. DESCRIBE videojuegos muestra sus columnas, tipos de datos, posibilidad de admitir NULL y clave primaria. Por último, SELECT COUNT(*) cuenta los registros.

Si todavía no hemos insertado ninguno, el resultado de COUNT(*) será 0. Esto es perfectamente normal: Hibernate puede crear la estructura de la tabla, pero no inventa los videojuegos que queremos guardar.

Si queremos examinar con más detalle la definición SQL de la tabla, podemos ejecutar SHOW CREATE TABLE videojuegos;. Comprobaremos cómo MySQL representa el identificador autogenerado y las restricciones.

consejo

La estructura real que muestre MySQL puede incluir detalles técnicos adicionales y tipos concretos elegidos por Hibernate. Debemos reconocer la tabla, su clave primaria y las columnas que hemos definido. Si ya existía una tabla de pruebas con otra estructura, ddl-auto=update no garantiza que todas sus restricciones o longitudes se modifiquen exactamente como esperamos; no borraremos datos para intentar corregirla sin revisarlos antes.

🟧 ¿Qué hemos conseguido realmente?​

Ahora tenemos una clase Java mapeada y una tabla preparada para almacenar registros. Todavía no tenemos un catálogo persistente con datos ni hemos creado operaciones para añadir videojuegos desde la aplicación. Esta primera tabla contiene una sola entidad.

Para guardar objetos y recuperar las filas de MySQL como entidades Java utilizaremos repositorios Spring Data JPA. La definición de la entidad, por sí sola, no realiza esas operaciones.

5️⃣ Una primera idea sobre el contexto de persistencia​

En el código anterior hemos definido un constructor que nos permite crear un objeto:

Videojuego juego = new Videojuego("Celeste", "Plataformas", "PC", 2018);

Este código solo crea un objeto Java en memoria. Aunque su clase esté anotada con @Entity, todavía no se ha realizado ningún INSERT en MySQL. El identificador id sigue siendo null.

JPA utiliza un componente llamado contexto de persistencia para gestionar las entidades con las que está trabajando. De forma introductoria, conviene distinguir estas situaciones:

SituaciónQué significa
Nueva (transitoria)Hemos creado el objeto Java, pero JPA todavía no lo gestiona.
GestionadaEl objeto está asociado a un contexto de persistencia, que puede seguir sus cambios.
Separada (detached)El objeto representa datos de una entidad, pero ya no está asociado a ese contexto.
EliminadaSe ha marcado para su eliminación dentro del contexto.

No necesitamos manipular todavía estos estados. Nos servirán después para entender por qué algunas operaciones se sincronizan con MySQL dentro de una transacción y por qué otras no.

aviso

@Entity no convierte cada cambio de una propiedad en una operación inmediata sobre MySQL. Para interpretar cuándo se guardan y sincronizan los cambios necesitaremos aprender a utilizar repositorios y, más adelante, transacciones.

6️⃣ Errores frecuentes y comprobación final​

🟩 Si no aparece la tabla​

Lo primero es comprobar que Spring Boot haya arrancado correctamente y que estemos consultando la base de datos mi_coleccion. Después revisaremos si la entidad tiene @Entity, si se encuentra dentro del paquete principal del proyecto y si ddl-auto=update sigue configurado.

Si la aplicación muestra un error SQL, consultaremos el mensaje real de la consola antes de modificar propiedades al azar.

🟨 Si el código no reconoce las anotaciones​

Comprobaremos que los import son de jakarta.persistence y que el proyecto tiene la dependencia Spring Data JPA. Después dejaremos que IntelliJ y Maven terminen de cargar las dependencias.

🟧 Si esperamos encontrar videojuegos y la tabla está vacía​

No es un error. Definir la estructura no introduce registros. Para hacerlo necesitaremos ejecutar una operación de persistencia, que aprenderemos en los apartados siguientes.

  7. ¿Por qué crear un objeto con new Videojuego(...) no lo guarda automáticamente en MySQL?
  8. Si necesitamos almacenar el precio de una entrada, ¿qué tipo Java utilizaríamos y cómo indicaríamos dos decimales?
  9. ¿Qué opciones de @Column utilizaríamos para un código obligatorio y que no pueda repetirse? ¿Qué no garantiza nullable = false?
  10. En una entidad nueva con un identificador autogenerado, ¿por qué elegiríamos Long y GenerationType.IDENTITY?

Debemos tener la clase Videojuego creada, Spring Boot arrancando sin errores de JPA y la tabla videojuegos visible en MySQL. No necesitamos introducir datos todavía.
