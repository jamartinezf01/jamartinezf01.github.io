1.4. Repositorios JPA

En el apartado anterior definimos la entidad Videojuego y comprobamos que Hibernate había creado su tabla en MySQL. Si partimos de una base de datos nueva, la tabla estará vacía: describir cómo se almacenan los objetos no significa que hayamos guardado ninguno.

Ahora vamos a dar ese paso. Crearemos nuestro primer repositorio Spring Data JPA, guardaremos un videojuego y recuperaremos los registros almacenados. También entenderemos por qué podemos utilizar ese repositorio sin programar sus operaciones SQL y cómo Spring se lo proporciona a las clases que lo necesitan.

Idea principal

Un repositorio es el componente que utilizaremos para acceder a los datos persistentes. Con Spring Data JPA declaramos una interfaz y el framework proporciona una implementación de las operaciones habituales, como guardar, buscar y recuperar registros.

Nosotros seguiremos trabajando con objetos Videojuego; el repositorio, junto con JPA e Hibernate, se encargará del acceso a MySQL.

1️⃣ Del objeto Java a la base de datos​

Recordemos el objeto que podíamos crear al estudiar las entidades:

Videojuego juego = new Videojuego("Celeste", "Plataformas", "PC", 2018);

Ese código construye un objeto en memoria. Aunque la clase lleve @Entity, no se ejecuta automáticamente ningún INSERT. Para conservar sus datos necesitamos realizar una operación de persistencia.

Podríamos escribir instrucciones SQL y ejecutarlas mediante JDBC, pero estaríamos encargándonos manualmente de operaciones repetitivas: abrir conexiones, preparar consultas, obtener resultados y convertir filas en objetos.

Spring Data JPA simplifica ese trabajo. Nos ofrece repositorios que permiten realizar operaciones comunes con métodos Java, sin tener que redactar el SQL de cada una.

🟩 ¿Qué responsabilidad tiene un repositorio?​

Un repositorio se ocupa del acceso a los datos, no de decidir cómo se presenta una página web ni de aplicar todas las reglas de negocio. Más adelante incorporaremos servicios y controladores para separar esas responsabilidades.

Comenzaremos comprobando tres operaciones fundamentales: guardar, recuperar todos los registros y buscar uno por su identificador. Después ampliaremos la perspectiva con una guía de los métodos que ya hereda cualquier repositorio JPA. No implementaremos todavía un CRUD web: ahora nos interesa conocer las operaciones disponibles y comprobar su efecto en MySQL.

2️⃣ Creamos VideojuegoRepository​

🟩 Una interfaz con muy poco código​

En com.dwes.mi_coleccion crearemos un paquete llamado repositorios. Dentro añadimos esta interfaz:

src/main/java/com/dwes/mi_coleccion/repositorios/VideojuegoRepository.java
package com.dwes.mi_coleccion.repositorios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import org.springframework.data.jpa.repository.JpaRepository;

public interface VideojuegoRepository extends JpaRepository<Videojuego, Long> {
}
en este ejemplo

JpaRepository es una interfaz de Spring Data JPA que reúne operaciones habituales de persistencia. Nuestra interfaz VideojuegoRepository la extiende y hereda sus métodos.

Los dos tipos entre los símbolos <> tienen significados distintos:

  • Videojuego es el tipo de entidad con el que trabajará el repositorio.
  • Long es el tipo de su identificador, definido mediante @Id en la entidad.

No hemos escrito ningún método ni implementado la interfaz. En esta primera versión no lo necesitamos: Spring Data JPA proporciona la implementación en tiempo de ejecución.

aviso

El segundo tipo debe coincidir con el del identificador de la entidad. Si Videojuego utiliza private Long id, declararemos JpaRepository<Videojuego, Long>, no JpaRepository<Videojuego, Integer>.

🟨 ¿Cómo crearíamos el repositorio de otra entidad?​

La estructura de la interfaz no es exclusiva de los videojuegos. Para definir un repositorio seguimos siempre el mismo procedimiento:

  1. Identificamos la clase anotada con @Entity cuyos datos queremos gestionar.
  2. Comprobamos el tipo Java del atributo marcado con @Id.
  3. Declaramos una interfaz que extienda JpaRepository<Entidad, TipoId>.
  4. Colocamos la interfaz en un paquete que Spring Boot pueda detectar.

Por ejemplo, si en otra aplicación tuviéramos una entidad Libro con un identificador Long, la declaración sería:

public interface LibroRepository extends JpaRepository<Libro, Long> {
}

Este fragmento es solo una referencia para otro proyecto: no crearemos Libro ni LibroRepository en MiColección. Lo importante es comprender que la estructura es reutilizable y que cambia el tipo de entidad y, si corresponde, el del identificador.

consejo

En IntelliJ IDEA, después de escribir repositorio., podemos usar el autocompletado (Ctrl + Espacio) para explorar los métodos disponibles. No son métodos que tengamos que declarar uno por uno en nuestra interfaz: los heredamos de JpaRepository.

🟧 ¿Quién crea el repositorio? Introducción a IoC y beans​

Una duda razonable es cómo podremos utilizar VideojuegoRepository si solo hemos declarado una interfaz.

Al arrancar, Spring Data JPA detecta las interfaces de repositorio y prepara los objetos que implementan sus operaciones. Spring los registra y gestiona dentro de su contenedor de inversión de control (IoC).

Un objeto gestionado por ese contenedor se denomina bean de Spring. Cuando otra clase necesite el repositorio, podremos pedirlo en su constructor y Spring le proporcionará la instancia correspondiente. A este mecanismo lo llamamos inyección de dependencias (DI).

No necesitamos utilizar new VideojuegoRepository(): además de que una interfaz no se puede instanciar directamente, no debemos construir manualmente el repositorio. Tampoco necesitamos añadir @Repository a esta interfaz: Spring Data JPA ya sabe reconocerla y registrarla.

consejo

No debemos confundir los objetos que intervienen aquí. VideojuegoRepository será un componente gestionado por Spring. En cambio, cada Videojuego representa datos de nuestro dominio: @Entity no lo convierte en un bean de Spring.

3️⃣ Utilizamos el repositorio por primera vez​

Antes de construir páginas web, vamos a comprobar el repositorio de la forma más sencilla: ejecutaremos unas operaciones al arrancar la aplicación y observaremos el resultado en la consola y en MySQL.

Para ello utilizaremos temporalmente CommandLineRunner. Se trata de una interfaz de Spring Boot cuyo método run(...) se ejecuta después de que la aplicación haya iniciado su contexto.

🟩 Una clase de comprobación temporal​

Crearemos un paquete pruebas dentro de com.dwes.mi_coleccion y añadiremos la siguiente clase. Se trata de una comprobación manual durante el arranque, no de una prueba automatizada de JUnit:

src/main/java/com/dwes/mi_coleccion/pruebas/PruebaVideojuegoRepositorio.java
package com.dwes.mi_coleccion.pruebas;

import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.repositorios.VideojuegoRepository;
import org.springframework.boot.CommandLineRunner;
import org.springframework.stereotype.Component;

import java.util.List;
import java.util.Optional;

@Component
public class PruebaVideojuegoRepositorio implements CommandLineRunner {

    private final VideojuegoRepository repositorio;

    public PruebaVideojuegoRepositorio(VideojuegoRepository repositorio) {
        this.repositorio = repositorio;
    }

    @Override
    public void run(String... args) {
        // Solo insertamos un videojuego si la tabla está vacía.
        if (repositorio.count() == 0) {
            Videojuego nuevo = new Videojuego(
                    "Celeste", "Plataformas", "PC", 2018);

            Videojuego guardado = repositorio.save(nuevo);
            System.out.println("Guardado con ID: " + guardado.getId());
        }

        // Recuperamos todos los videojuegos almacenados.
        List<Videojuego> videojuegos = repositorio.findAll();
        System.out.println("Videojuegos encontrados: " + videojuegos.size());

        for (Videojuego videojuego : videojuegos) {
            System.out.println(videojuego.getId() + " - "
                    + videojuego.getTitulo());
        }

        // Buscamos por el ID de un registro que sí existe.
        if (!videojuegos.isEmpty()) {
            Long idBuscado = videojuegos.get(0).getId();
            Optional<Videojuego> resultado = repositorio.findById(idBuscado);

            if (resultado.isPresent()) {
                System.out.println("Recuperado: "
                        + resultado.get().getTitulo());
            } else {
                System.out.println("No existe un videojuego con ese ID.");
            }
        }
    }
}
en este ejemplo

La anotación @Component indica que queremos que Spring registre esta clase como uno de sus componentes. Al implementar CommandLineRunner, Spring Boot ejecutará su método run(...) durante el arranque.

Observa el constructor:

public PruebaVideojuegoRepositorio(VideojuegoRepository repositorio) {
    this.repositorio = repositorio;
}

La clase declara que necesita un repositorio, pero no lo construye. Spring encuentra el bean correspondiente y se lo proporciona al crear el componente. Esto es inyección de dependencias por constructor, una aplicación práctica de la inversión de control.

No necesitamos escribir @Autowired porque la clase tiene un único constructor. Utilizamos final para indicar que la referencia al repositorio quedará asignada al construir el objeto.

aviso

Esta clase es una herramienta temporal para aprender, no la organización definitiva de nuestra aplicación. Los métodos de persistencia se ejecutarán cada vez que iniciemos Spring Boot. Hemos incluido la comprobación count() == 0 para que solo inserte el ejemplo si toda la tabla está vacía. Esta comprobación no busca si ya existe «Celeste»: no serviría como regla general para evitar duplicados en una aplicación real.

A continuación organizaremos el acceso a los datos mediante un servicio y lo utilizaremos desde controladores y vistas Thymeleaf.

🟨 Ejecutamos el proyecto​

Con el servicio MySQL de Windows en funcionamiento, arrancamos Spring Boot desde IntelliJ IDEA. Recordemos que debe estar configurada la variable de entorno DB_PASSWORD, utilizada para conectar la aplicación con MySQL.

Si la tabla estaba vacía, en la consola veremos mensajes semejantes a estos:

Guardado con ID: 1
Videojuegos encontrados: 1
1 - Celeste
Recuperado: Celeste

El identificador puede ser diferente: MySQL asigna el ID y no debemos suponer que siempre comienza en 1. Si ya teníamos registros, la aplicación los recuperará, pero no insertará otro videojuego.

También podemos observar una diferencia respecto al apartado anterior: en el registro de arranque, Spring Data JPA ya debería detectar una interfaz de repositorio, en lugar de mostrar Found 0 JPA repository interfaces.

4️⃣ Entendemos las operaciones que hemos utilizado​

🟩 Guardar con save()​

En la primera parte del ejemplo hemos utilizado:

Videojuego nuevo = new Videojuego("Celeste", "Plataformas", "PC", 2018);
Videojuego guardado = repositorio.save(nuevo);

Antes de llamar a save(), nuevo es un objeto que acabamos de crear en Java. Con save() solicitamos al repositorio que lo almacene. Como su identificador lo genera MySQL mediante IDENTITY, después de guardar podremos consultar el identificador asignado en el objeto devuelto.

Conviene utilizar el valor devuelto por save(): en general, no debemos asumir que el objeto que pasamos como argumento y el que obtenemos como resultado son necesariamente la misma instancia Java.

Más adelante veremos que save() también participa en las actualizaciones y estudiaremos cómo influye el estado de la entidad. No necesitamos resolver todavía todos los detalles del contexto de persistencia.

🟨 Recuperar registros con findAll()​

El método findAll() permite obtener los videojuegos almacenados:

List<Videojuego> videojuegos = repositorio.findAll();

En nuestro caso devuelve una List<Videojuego>. Podemos recorrer sus elementos con un for y acceder a las propiedades mediante los getters de la entidad.

Si la tabla está vacía, obtendremos una lista vacía, no null. Por tanto, podemos comprobarlo con videojuegos.isEmpty().

En términos de los resultados de aprendizaje de la unidad, List<Videojuego> es un conjunto de resultados que podemos recorrer, consultar y procesar en Java. No es la tabla permanente: la información sigue almacenada en MySQL y la lista contiene los objetos recuperados en esta consulta.

consejo

findAll() es muy útil para empezar, pero recupera el conjunto completo de registros. Para colecciones más grandes podremos filtrar, ordenar y paginar los resultados. Además, el orden de findAll() no está garantizado si no lo indicamos expresamente.

🟧 Buscar por identificador con findById() y Optional​

No siempre conocemos todos los registros: a veces queremos encontrar uno solo, a partir de su identificador.

Optional<Videojuego> resultado = repositorio.findById(idBuscado);

El resultado es un Optional<Videojuego>, porque puede existir o no un registro con ese ID. Optional nos permite representar explícitamente ambas situaciones.

if (resultado.isPresent()) {
    Videojuego videojuego = resultado.get();
    System.out.println(videojuego.getTitulo());
} else {
    System.out.println("Videojuego no encontrado.");
}
en este ejemplo

isPresent() indica si se ha encontrado un valor. Solo después de comprobarlo utilizamos get() para obtener la entidad. Llamar a get() sobre un Optional vacío provoca una excepción.

Más adelante, al recuperar un videojuego desde un controlador, aprenderemos a responder adecuadamente cuando el identificador no exista.

🟥 Los métodos heredados de JpaRepository: guía de consulta​

Hasta ahora hemos utilizado tres métodos, pero un repositorio ofrece bastantes más sin escribir código adicional. Conviene conocer qué operaciones tenemos disponibles, qué parámetros esperan y qué devuelven. No necesitamos aprenderlas de memoria: esta tabla nos servirá como referencia cuando desarrollemos nuestros propios proyectos.

Operaciones de guardado

MétodoQué recibeQué devuelvePara qué lo utilizamos
save(entidad)Una entidad.La entidad guardada (S).Guardar una entidad nueva o solicitar la actualización de una existente.
saveAll(entidades)Un conjunto de entidades (Iterable<S>).Una lista de entidades guardadas (List<S>).Guardar varias entidades en una llamada al repositorio.

Operaciones de consulta

MétodoQué recibeQué devuelvePara qué lo utilizamos
findById(id)Un identificador.Optional<T>.Buscar una entidad por su clave primaria.
findAll()Nada.List<T>.Recuperar todas las entidades.
findAllById(ids)Varios identificadores (Iterable<ID>).List<T>.Recuperar los registros existentes con esos identificadores.
count()Nada.long.Saber cuántos registros existen.
existsById(id)Un identificador.boolean.Comprobar si existe un registro con ese ID.

Operaciones de eliminación

MétodoQué recibeQué devuelvePara qué lo utilizamos
delete(entidad)Una entidad.void.Solicitar la eliminación de esa entidad.
deleteById(id)Un identificador.void.Solicitar la eliminación del registro identificado.
deleteAll()Nada.void.Eliminar todas las entidades. Debemos utilizarlo con especial cuidado.
en este ejemplo

En las firmas generales, T representa el tipo de entidad (Videojuego) y ID su identificador (Long). La letra S representa un tipo de entidad compatible con T; en nuestros ejemplos será también Videojuego.

Iterable indica que podemos pasar varios elementos, por ejemplo una lista. List representa una colección de resultados. En cambio, void significa que el método no devuelve un valor y Optional<T> que la búsqueda puede no encontrar ningún registro.

La tabla recoge los métodos más útiles en esta unidad, no toda la API de JpaRepository. También existen métodos para ordenación, paginación y operaciones más específicas de JPA, que veremos cuando realmente los necesitemos.

🟪 Elegimos el método según lo que necesitamos​

Supongamos que nuestra aplicación debe responder a distintas preguntas:

NecesidadMétodo apropiadoMotivo
Mostrar todos los videojuegos.findAll()Necesitamos una lista de entidades.
Mostrar la ficha del videojuego con ID 8.findById(8L)Buscamos una entidad concreta, que podría no existir.
Mostrar el número total de videojuegos.count()Solo necesitamos una cantidad, no recuperar todos los registros.
Comprobar si existe el ID 8.existsById(8L)Necesitamos una respuesta verdadera o falsa.
Registrar varios videojuegos.saveAll(...)Tenemos varias entidades para guardar.
Eliminar un videojuego identificado.deleteById(id)Conocemos su clave primaria.

Por ejemplo, para mostrar una cantidad no tiene sentido recuperar todos los registros y después contar los elementos de la lista. Podemos preguntar directamente al repositorio:

long total = repositorio.count();
System.out.println("Total de videojuegos: " + total);

Si queremos saber si existe un identificador, podemos comprobarlo sin recuperar previamente toda la tabla:

Long id = 8L;
boolean existe = repositorio.existsById(id);

if (existe) {
    System.out.println("Existe un videojuego con ese ID.");
} else {
    System.out.println("No existe un videojuego con ese ID.");
}
en este ejemplo

Observa que count() devuelve un long, mientras que existsById() devuelve un boolean. No todos los métodos de un repositorio devuelven entidades: debemos elegir el adecuado según la información que necesita nuestra aplicación.

Utilizamos 8L porque el identificador de Videojuego es de tipo Long. No importa si ese registro existe o no; precisamente estamos comprobándolo.

🟩 Guardamos varios objetos con saveAll()​

Si necesitamos registrar varios videojuegos, podemos preparar una lista y pasarla al repositorio. Este ejemplo es independiente de la clase temporal de arranque; no lo añadiremos a run(...), ya que crearía nuevos registros cada vez que iniciáramos la aplicación.

List<Videojuego> nuevos = List.of(
        new Videojuego("Hollow Knight", "Metroidvania", "PC", 2017),
        new Videojuego("Stardew Valley", "Simulación", "PC", 2016)
);

List<Videojuego> guardados = repositorio.saveAll(nuevos);
System.out.println("Entidades guardadas: " + guardados.size());
en este ejemplo

List.of(...) construye una lista con los dos objetos Java. saveAll(...) solicita guardar las entidades y devuelve una lista con los resultados, que podemos utilizar para consultar sus identificadores.

No debemos confundir saveAll() con una garantía de ejecución mediante un único INSERT SQL: la cantidad de instrucciones SQL depende del mapeo y de la configuración de JPA e Hibernate.

🟨 ¿save() sirve para insertar y también para actualizar?​

Sí. Spring Data JPA utiliza el mismo método para guardar una entidad nueva o una existente, pero no debemos pensar que save() equivale siempre a un INSERT.

En nuestro modelo, cuando creamos un Videojuego con new, su identificador todavía es null. Spring Data JPA puede reconocerlo como nuevo y solicitar que se persista. Si trabajamos con una entidad ya existente, save() puede intervenir en su actualización.

Esto no significa que debamos asignar un ID inventado para actualizar. En una aplicación web, lo habitual será recuperar primero la entidad por su identificador, comprobar que existe y modificar las propiedades permitidas. Esa será la estrategia que utilizaremos al implementar las operaciones CRUD del servicio y sus formularios Thymeleaf.

aviso

save() no busca duplicados por título. Dos videojuegos distintos pueden compartir título y, si creamos dos entidades nuevas, podríamos guardar dos registros. La comprobación de duplicados corresponde a las reglas y restricciones que decidamos para nuestra aplicación.

🟧 ¿Qué ocurre si buscamos o eliminamos un registro inexistente?​

Conviene distinguir el comportamiento de los métodos:

  • findById(id) devuelve Optional.empty() si no encuentra el registro.
  • findAllById(ids) devuelve una lista que contiene los registros encontrados; los identificadores inexistentes no aparecen. No debemos suponer que los resultados mantienen el orden de los identificadores solicitados.
  • existsById(id) devuelve false cuando ese identificador no existe.
  • deleteById(id) no devuelve un valor que indique si se ha eliminado algo. Si necesitamos informar de que el registro no existe, debemos comprobarlo y gestionar el caso desde nuestra aplicación.

También debemos tener en cuenta que una eliminación puede fallar por restricciones de integridad de la base de datos. No asumiremos que un delete tiene éxito en cualquier situación: abordaremos estos casos al desarrollar el CRUD y las relaciones entre entidades.

🟥 ¿Hay otros métodos distintos de los heredados?​

Sí. Hasta ahora utilizamos métodos que ya existen en JpaRepository, por lo que nuestra interfaz sigue vacía. Cuando queramos buscar, por ejemplo, por el género de un videojuego, necesitaremos indicar una consulta que no esté incluida entre las operaciones generales.

Spring Data JPA permite declarar métodos de consulta dentro de nuestra interfaz, siguiendo convenciones de nombres como findByGenero(...). También podemos utilizar @Query para describir una consulta. Aprenderemos a construir estas consultas cuando necesitemos filtrar los videojuegos.

La distinción importante es esta: los métodos heredados se pueden utilizar directamente; los métodos de consulta específicos de nuestra aplicación debemos declararlos en el repositorio.

nota

Una operación más avanzada: flush(). JpaRepository ofrece este método para solicitar la sincronización de cambios pendientes con la base de datos. Sincronizar no equivale a confirmar una transacción. No necesitamos llamarlo en esta comprobación; conviene conservar esa diferencia para comprender la gestión de transacciones.

5️⃣ Comprobamos que los videojuegos están realmente en MySQL​

🟩 Consultamos la tabla desde MySQL​

Vamos a comprobar que el videojuego no existe solamente en la memoria de Java. Abrimos PowerShell y ejecutamos:

mysql -u coleccion_app -p mi_coleccion

Después de introducir la contraseña correspondiente, consultamos la tabla:

SELECT id, titulo, genero, plataforma, anio_lanzamiento
FROM videojuegos;

Deberíamos encontrar el videojuego que acabamos de guardar, si la tabla estaba inicialmente vacía. Si ya contenía datos, veremos los registros existentes.

Ahora podemos detener y volver a iniciar Spring Boot. El videojuego seguirá almacenado y el repositorio podrá recuperarlo de nuevo. Esto confirma que la información se conserva en MySQL, no en una lista temporal de Java.

🟨 Observamos el SQL generado (opcional)​

Si queremos ver qué operaciones realiza Hibernate, podemos añadir temporalmente esta propiedad al archivo de configuración que ya tenemos:

src/main/resources/application.properties (propiedad adicional)
spring.jpa.show-sql=true

Reiniciamos Spring Boot y observamos la consola. Veremos instrucciones SQL correspondientes a las operaciones que realiza el repositorio, como consultas y, si se inserta un registro nuevo, un INSERT.

consejo

Como el ejemplo solo inserta si la tabla está vacía, al reiniciar normalmente observaremos consultas de lectura y no otro INSERT. La salida concreta depende de las operaciones ejecutadas. Podemos eliminar spring.jpa.show-sql=true cuando ya no necesitemos examinar el SQL.

🟧 Retiramos la clase de prueba al terminar​

PruebaVideojuegoRepositorio nos ha servido para experimentar, pero no debe quedar ejecutando operaciones en cada arranque durante el resto del proyecto.

Una vez realizadas las comprobaciones, retiraremos esta clase temporal del proyecto. No borraremos el repositorio ni la entidad: los necesitaremos al incorporar la capa de servicios. Tampoco se perderán los registros guardados en MySQL por eliminar esta clase Java.

Retiramos la clase temporal de comprobación

Cuando terminemos las pruebas del repositorio, eliminaremos la clase temporal src/main/java/com/dwes/mi_coleccion/pruebas/PruebaVideojuegoRepositorio.java (o retiraremos su anotación @Component). Mantendremos intactos Videojuego.java, VideojuegoRepository.java y los registros de MySQL.

Esta retirada evita también futuros problemas de compatibilidad si cambia el constructor de Videojuego: por ejemplo, si la plataforma deja de ser un texto y pasa a ser una entidad relacionada. Las pruebas automatizadas tendrán su propio lugar en src/test/java.

6️⃣ Errores frecuentes y comprobación final​

🟩 Spring no encuentra el repositorio​

Comprobaremos que VideojuegoRepository extiende JpaRepository<Videojuego, Long>, que los imports son correctos y que el paquete repositorios está dentro de com.dwes.mi_coleccion, donde Spring Boot puede detectarlo. Si aparece un mensaje indicando que falta un bean de tipo VideojuegoRepository, revisaremos estos puntos antes de modificar la configuración.

🟨 La clase de prueba no se ejecuta​

Revisaremos que tiene @Component, implementa CommandLineRunner y se encuentra dentro de un paquete detectado por Spring. También comprobaremos que hemos arrancado la aplicación correctamente y no se ha detenido por otro error.

🟧 Aparecen varios registros repetidos​

Si quitamos la condición repositorio.count() == 0, cada arranque puede insertar un nuevo Celeste. Guardar una entidad no significa comprobar automáticamente si otro videojuego con los mismos datos ya existe. Más adelante introduciremos reglas de negocio cuando necesitemos evitar duplicados.

🟥 La búsqueda devuelve Optional.empty​

Significa que no se encontró ningún registro con ese identificador. No es un fallo de conexión: debemos comprobar el ID utilizado y tratar el caso de ausencia antes de acceder al valor.

🟪 Comprobamos lo aprendido​

Estas comprobaciones son de práctica y no son evaluables. No requieren entrega.

  1. Explica por qué podemos utilizar los métodos de VideojuegoRepository aunque la interfaz esté vacía.
  2. Identifica quién proporciona el repositorio a PruebaVideojuegoRepositorio y dónde se solicita esa dependencia.
  3. Comprueba en MySQL el identificador generado para el videojuego insertado. ¿Por qué no debemos escribir ese ID manualmente en Java?
  4. Reinicia Spring Boot. ¿Sigue existiendo el registro? ¿Por qué no se crea otro igual con nuestro código actual?
  5. ¿Qué diferencia existe entre una lista vacía devuelta por findAll() y un Optional.empty() devuelto por findById()?
  6. Si únicamente queremos mostrar el número de videojuegos, ¿por qué resulta más adecuado count() que findAll().size()?
  7. En una aplicación de biblioteca, la entidad Libro tiene @Id private Integer id. ¿Qué tipos escribiríamos entre los signos <> al declarar LibroRepository?
  8. Tenemos una lista con cinco identificadores, pero solo existen tres registros. ¿Qué podemos esperar de findAllById(ids)?
  9. ¿Por qué save() no sirve por sí solo para evitar videojuegos duplicados?
Antes de continuar

Debemos tener VideojuegoRepository funcionando, haber comprobado el almacenamiento y la recuperación de registros desde Java, y poder consultar los mismos datos en MySQL. También debemos saber elegir entre los métodos heredados cuando necesitemos obtener un registro, una lista, un recuento o una comprobación de existencia.

A continuación introduciremos @Service y la capa de servicios. Así dejaremos de realizar comprobaciones al arrancar y organizaremos las operaciones de persistencia para utilizarlas desde controladores y vistas Thymeleaf.
