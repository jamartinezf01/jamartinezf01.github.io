1.1. Introducción a la persistencia

En las unidades anteriores hemos aprendido a recibir peticiones, procesar formularios y mostrar información con Spring Boot y Thymeleaf. Para representar esos datos hemos utilizado objetos y colecciones de Java. Sin embargo, disponer de información mientras se ejecuta una aplicación no significa que podamos recuperarla cuando volvamos a iniciarla.

En este apartado vamos a comprender qué significa conservar datos, qué alternativas de almacenamiento existen y por qué necesitamos tecnologías específicas para acceder a una base de datos desde una aplicación Java. No se trata todavía de memorizar anotaciones ni de configurar un proyecto, sino de entender qué problema resuelve cada herramienta.

Para aprender estos conceptos utilizaremos MiColección, una aplicación de gestión de videojuegos. Empezaremos con una sola entidad y una tabla para comprender la persistencia sin añadir complejidad innecesaria.

1️⃣ De los datos en memoria a la persistencia​

Cuando creamos un objeto o añadimos elementos a una colección, la aplicación puede consultar y modificar esa información mientras está funcionando. Si los cambios solo existen en memoria, se perderán cuando finalice el proceso.

Pensemos en un catálogo de videojuegos. Durante una sesión podemos añadir un título, corregir su año de lanzamiento y eliminar un registro duplicado. Si al reiniciar el servidor volvemos a encontrar el catálogo tal como estaba al principio, esos cambios no se habían guardado de forma persistente.

Para evitarlo, necesitamos almacenar la información fuera de la memoria de trabajo de la aplicación, por ejemplo, en un archivo o en una base de datos. De ese modo podremos recuperarla en una ejecución posterior.

Idea principal

Persistir datos significa conservar información para recuperarla posteriormente, incluso cuando la aplicación haya terminado de ejecutarse.

Esto no impide que sigamos utilizando objetos y colecciones: los datos pueden almacenarse de forma persistente y, al recuperarlos, volver a estar disponibles como objetos Java en memoria.

2️⃣ Dónde podemos almacenar la información​

No todas las aplicaciones necesitan el mismo sistema de almacenamiento. Dependerá de qué información queremos conservar, cómo la consultaremos, con qué frecuencia cambia y cuántos usuarios pueden trabajar con ella.

🟩 Almacenamiento en archivos​

Una aplicación puede escribir información en un archivo y leerla cuando vuelva a necesitarla. Los formatos más conocidos son TXT, CSV y JSON. Cada uno resulta útil para necesidades diferentes: un TXT puede contener líneas de texto, un CSV permite intercambiar datos tabulares y JSON representa información estructurada mediante objetos y listas.

Por ejemplo, un archivo JSON podría contener parte de un catálogo:

videojuegos.json
[
  {
    "titulo": "Celeste",
    "plataforma": "PC",
    "anioLanzamiento": 2018
  },
  {
    "titulo": "Hollow Knight",
    "plataforma": "Nintendo Switch",
    "anioLanzamiento": 2017
  }
]
en este ejemplo

El archivo contiene una lista con dos objetos JSON. Cada uno representa un videojuego mediante varias propiedades. El formato facilita que otros programas puedan interpretar la información sin conocer nuestras clases Java.

Este bloque muestra el contenido del archivo, no una operación que lo guarde automáticamente. Para crear o actualizar ese archivo, nuestra aplicación tendría que escribir los datos en él. Para recuperarlos, tendría que leerlo e interpretarlo.

Guardar en archivos puede ser una solución suficiente para exportaciones, configuraciones o conjuntos pequeños de datos. No obstante, si necesitamos buscar videojuegos según varios criterios, modificar un registro concreto o admitir actualizaciones simultáneas, tendremos que desarrollar mecanismos adicionales.

Por ejemplo, modificar un videojuego dentro de un JSON puede implicar leer el archivo, localizar el elemento, cambiar sus propiedades y volver a escribir su contenido. También debemos pensar qué ocurriría si dos usuarios intentaran guardar cambios al mismo tiempo o si una escritura se interrumpiera.

aviso

JSON es un formato de representación de datos, no un sistema gestor de bases de datos. Un contenido JSON que solo existe en una variable también se perderá al finalizar la ejecución. La persistencia depende de que se almacene realmente en un medio adecuado.

🟨 Bases de datos relacionales​

Una base de datos relacional organiza la información en tablas. Cada fila representa un registro y cada columna describe una característica de ese registro. Los datos se identifican y relacionan mediante claves, conceptos que ya conocemos del modelo relacional.

Por ejemplo, podríamos almacenar el catálogo anterior en una tabla videojuegos:

idtituloplataformaanio_lanzamiento
1CelestePC2018
2Hollow KnightNintendo Switch2017

Un sistema gestor de bases de datos como MySQL permite realizar consultas, insertar y modificar registros, controlar accesos y aplicar restricciones para mantener la integridad. También proporciona mecanismos para gestionar operaciones concurrentes, algo especialmente importante en las aplicaciones web.

Esto no significa que una base de datos resuelva automáticamente cualquier problema. Seguimos siendo responsables de definir bien nuestras tablas, formular consultas adecuadas y establecer reglas que eviten datos incorrectos.

🟧 Elegir según las necesidades​

Imaginemos que queremos enviar una copia del catálogo a otra aplicación: exportarlo a JSON o CSV puede ser apropiado. Si, en cambio, necesitamos mantener un catálogo consultable desde la web, actualizar registros y relacionar videojuegos con plataformas, una base de datos relacional suele ofrecer una solución más adecuada.

Los archivos y las bases de datos no son alternativas excluyentes. Una aplicación puede utilizar una base de datos para gestionar su información habitual y archivos para importarla, exportarla o intercambiarla.

3️⃣ De los objetos Java a las tablas​

En Java representamos la información mediante clases y objetos. Un videojuego, por ejemplo, puede tener propiedades como id, titulo, plataforma y anioLanzamiento. En una base de datos relacional podemos representar esos mismos datos mediante las columnas de una tabla.

Sin embargo, un objeto Java no es una fila de MySQL. En Java trabajamos con objetos, tipos y referencias. En la base de datos trabajamos con tablas, registros y claves. Debemos establecer una correspondencia entre ambas formas de representar la información.

En un ejemplo tan sencillo, asociar una propiedad a una columna parece fácil. La dificultad aumenta cuando introducimos relaciones. En Java, un videojuego podría tener una propiedad que contenga un objeto Plataforma; en MySQL, esa relación normalmente se representaría mediante una clave ajena.

Esta diferencia entre las formas de organizar y relacionar la información contribuye al llamado desfase objeto-relacional: los modelos de objetos y de tablas no encajan siempre de manera directa. Existen tecnologías que facilitan esa correspondencia.

consejo

En esta primera versión, plataforma será un texto dentro de la entidad Videojuego. Así podremos centrarnos en cómo se guarda y recupera una entidad sencilla.

4️⃣ De JDBC al mapeo objeto-relacional​

🟩 JDBC: trabajar con SQL desde Java​

JDBC (Java Database Connectivity) es la API estándar de Java para interactuar con bases de datos mediante los controladores adecuados. Nos permite abrir conexiones, ejecutar instrucciones SQL y procesar los resultados.

Por ejemplo, para recuperar los videojuegos de PC necesitamos una consulta como esta:

SELECT id, titulo, plataforma, anio_lanzamiento
FROM videojuegos
WHERE plataforma = 'PC';
en este ejemplo

La sentencia consulta la tabla videojuegos y recupera determinadas columnas de los registros cuya plataforma sea PC.

No estamos ejecutando todavía la consulta: sirve para recordar que, en una base de datos relacional, recuperar información implica realizar operaciones sobre tablas.

Si utilizáramos JDBC directamente desde Java, además de ejecutar el SQL tendríamos que recorrer los resultados y construir los objetos correspondientes. También gestionaríamos los parámetros de las consultas y los recursos asociados a la conexión.

JDBC es una tecnología válida y sigue desempeñando un papel esencial. Sin embargo, cuando nuestra aplicación contiene muchas entidades y operaciones, repetir continuamente este trabajo puede dificultar el mantenimiento del código.

🟨 ORM: facilitar la correspondencia​

El mapeo objeto-relacional, conocido por sus siglas ORM (Object-Relational Mapping), permite describir cómo se corresponden nuestras clases Java con las tablas, y sus propiedades con las columnas.

En lugar de convertir manualmente cada resultado SQL en un objeto, un proveedor ORM puede encargarse de gran parte de esa conversión y de generar las operaciones necesarias para recuperar o almacenar entidades.

Esto simplifica muchas tareas, pero no nos permite olvidarnos del modelo relacional. Seguiremos necesitando comprender claves primarias, claves ajenas, consultas, restricciones y relaciones entre tablas. Además, las operaciones ORM terminan ejecutándose sobre una base de datos real.

consejo

JDBC y ORM no son rivales. En el entorno que vamos a utilizar, Hibernate puede apoyarse en JDBC para comunicarse con MySQL. ORM nos proporciona un nivel de abstracción mayor, pero las operaciones sobre la base de datos siguen existiendo.

5️⃣ JPA, Hibernate y Spring Data JPA: funciones diferentes​

Cuando trabajamos con persistencia en Spring Boot aparecen varios nombres que conviene distinguir desde el principio.

🟩 JPA: las reglas comunes​

JPA, actualmente parte de Jakarta Persistence, es una especificación. Define un modelo para representar entidades persistentes y trabajar con ellas: identificadores, relaciones, consultas y operaciones de persistencia, entre otros aspectos.

Una especificación establece cómo debe funcionar una tecnología, pero no constituye por sí sola un programa que almacene los datos. Para utilizar JPA necesitamos una implementación.

🟨 Hibernate: la implementación​

Hibernate es un proveedor de persistencia que implementa JPA. Se encarga de interpretar el mapeo de las entidades, gestionar su persistencia y ejecutar las operaciones necesarias en la base de datos.

Por ejemplo, cuando solicitamos recuperar una entidad, Hibernate puede generar y ejecutar el SQL apropiado y utilizar los resultados para construir o gestionar los objetos Java correspondientes.

No debemos confundir Hibernate con MySQL. Hibernate trabaja desde la aplicación Java; MySQL es el gestor que almacena la información.

🟧 Spring Data JPA: acceso mediante repositorios​

Spring Data JPA facilita la creación de la capa de acceso a datos. Nos permite definir interfaces de repositorio con operaciones comunes, como consultar todos los registros, buscar por identificador, guardar o eliminar.

La ventaja es que no necesitamos escribir una implementación completa de esas operaciones para cada entidad. Spring Data JPA proporciona la infraestructura necesaria y se apoya en JPA y en su proveedor de persistencia.

Los repositorios también permiten crear consultas a partir de nombres de métodos, ordenar y paginar resultados. Lo importante es comprender que Spring Data JPA simplifica el uso de JPA; no la sustituye.

🟥 Spring Boot y MySQL​

Spring Boot facilita la configuración y la integración de estas tecnologías dentro de una aplicación Spring. MySQL es el sistema gestor relacional en el que se almacenan los registros.

Podemos resumir sus responsabilidades:

TecnologíaPapel principal
Spring BootConfigura e integra los componentes de la aplicación.
Spring Data JPAProporciona repositorios y simplifica las operaciones de acceso a datos.
JPA (Jakarta Persistence)Define el modelo y las operaciones estándar de persistencia de entidades.
HibernateImplementa JPA y realiza el trabajo de persistencia.
JDBCFacilita la comunicación desde Java con el gestor mediante un controlador.
MySQLAlmacena y gestiona los datos relacionales.

El esquema representa una simplificación conceptual, no todas las llamadas internas que realiza Spring Boot. Nos ayuda a situar cada tecnología y comprender que las operaciones de los repositorios terminan apoyándose en componentes que se comunican con MySQL.

aviso

No son nombres intercambiables. JPA es una especificación, Hibernate la implementa, Spring Data JPA facilita los repositorios y MySQL conserva los registros. Tampoco desaparece SQL: Hibernate lo genera y ejecuta cuando es necesario.

6️⃣ Comprobamos lo aprendido​

Antes de empezar a configurar la conexión con MySQL, conviene comprobar que distinguimos las ideas principales:

  1. Si añadimos un elemento a una List y reiniciamos el servidor, ¿por qué no se conserva necesariamente ese cambio?
  2. ¿En qué situaciones utilizaríamos un archivo JSON y en cuáles una base de datos relacional?
  3. ¿Por qué una propiedad de un objeto Java no es exactamente lo mismo que una columna de una tabla?
  4. ¿Qué trabajo tendríamos que realizar si utilizáramos JDBC directamente? ¿Qué aporta un ORM?
  5. Explica con tus palabras la diferencia entre JPA, Hibernate y Spring Data JPA.
Para recordar

Una aplicación web puede seguir trabajando con objetos Java y, al mismo tiempo, conservar la información en MySQL. JPA y Hibernate facilitan la correspondencia entre ambos modelos, mientras que Spring Data JPA simplifica las operaciones habituales de acceso a los datos.
