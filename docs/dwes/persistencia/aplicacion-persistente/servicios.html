2.1. Servicios e integración con Thymeleaf

En el apartado anterior creamos VideojuegoRepository y comprobamos que podíamos guardar y recuperar videojuegos de MySQL utilizando Spring Data JPA. Para realizar las primeras pruebas empleamos una clase CommandLineRunner, que ejecutaba operaciones durante el arranque de Spring Boot.

Ahora vamos a dar un paso más: queremos que una persona pueda abrir el navegador y consultar los videojuegos almacenados. Para hacerlo, recuperaremos lo aprendido sobre controladores MVC, Model y vistas Thymeleaf, pero incorporaremos una pieza que hasta ahora no necesitábamos: la capa de servicios.

Idea principal

Un servicio reúne o coordina operaciones de la aplicación y es el lugar adecuado para incorporar sus reglas de negocio. El controlador atiende las peticiones web, mientras que el repositorio se ocupa del acceso a los datos.

En Spring Boot podemos conectar estos componentes mediante inyección de dependencias por constructor, sin tener que crearlos manualmente con new.

1️⃣ ¿Por qué necesitamos una capa de servicios?​

Imaginemos que queremos mostrar la lista de videojuegos de nuestra colección. El controlador podría recibir directamente el repositorio y llamar a findAll(). Técnicamente funcionaría, pero entonces el controlador empezaría a ocuparse también del acceso a datos.

A medida que la aplicación crezca, necesitaremos comprobar información antes de guardarla, consultar varios registros para realizar una operación o aplicar decisiones que no dependen de cómo se presenta la página. Si colocamos todo ese código en los controladores, acabaremos mezclando responsabilidades y repitiendo operaciones.

🟩 Tres componentes con responsabilidades diferentes​

En nuestra aplicación distinguiremos tres tipos de componentes:

ComponenteSu responsabilidad principal
ControladorRecibir una petición HTTP, solicitar la información necesaria y preparar la vista o la respuesta.
ServicioCoordinar las operaciones de la aplicación y aplicar las reglas de negocio.
RepositorioAcceder a la información persistente mediante Spring Data JPA.

Por ejemplo, cuando alguien visite /videojuegos, el controlador pedirá al servicio la lista de videojuegos. El servicio utilizará el repositorio y devolverá los objetos recuperados. El controlador añadirá esa lista al modelo para que Thymeleaf pueda mostrarla.

🟨 Cómo decidimos dónde colocar cada operación​

Conocer los nombres de las capas no es suficiente: cuando programemos una funcionalidad nueva tendremos que decidir dónde escribir cada parte del código. Podemos orientarnos pensando en la responsabilidad de cada operación, no en la clase en la que resulte más rápido escribirla.

Necesidad de la aplicaciónComponente más adecuadoMotivo
Atender una petición GET /videojuegos.Controlador.La ruta y el método HTTP pertenecen a la comunicación web.
Añadir una lista al Model y elegir una plantilla.Controlador.Prepara los datos necesarios para presentar la página.
Decidir si se puede registrar un videojuego según las reglas de la aplicación.Servicio.Es una decisión de negocio que no depende de la página HTML.
Coordinar varias consultas y operaciones para completar una acción.Servicio.Organiza los pasos necesarios de una funcionalidad.
Recuperar los videojuegos almacenados.Repositorio.Ejecuta operaciones de acceso a datos.
Comprobar mediante una consulta si existe un identificador.Repositorio, utilizado cuando corresponda desde el servicio.Es una operación sobre la información persistente.
Recorrer la lista para generar filas de una tabla HTML.Vista Thymeleaf.Es una tarea de presentación.

Por ejemplo, mostrar un mensaje de error junto a un campo es una tarea de presentación, mientras que comprobar una regla propia de la aplicación antes de aceptar una operación corresponde al servicio. Las validaciones de formularios que ya conocemos de UT3 pueden intervenir antes de llamar al servicio; no tenemos que trasladarlas sin criterio de una capa a otra.

Regla práctica

Antes de escribir una operación, preguntémonos: ¿depende de HTTP o de la vista? Probablemente irá en el controlador o la plantilla. ¿Es una decisión sobre cómo debe funcionar la aplicación? Probablemente corresponde al servicio. ¿Consiste en consultar o modificar registros? Utilizaremos el repositorio desde la capa que corresponda.

consejo

No toda aplicación necesita una capa de servicios extensa desde el primer día. En este ejemplo empezaremos con métodos sencillos, que delegan en el repositorio. Su utilidad se hará más evidente cuando añadamos reglas de negocio, formularios y operaciones que impliquen varios pasos.

2️⃣ Creamos nuestro primer servicio​

Vamos a mantener la entidad Videojuego y la interfaz VideojuegoRepository tal como quedaron en el apartado anterior. En el paquete principal com.dwes.mi_coleccion crearemos un nuevo paquete llamado servicios.

🟩 La anotación @Service​

Creamos la clase VideojuegoService:

src/main/java/com/dwes/mi_coleccion/servicios/VideojuegoService.java
package com.dwes.mi_coleccion.servicios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.repositorios.VideojuegoRepository;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Optional;

@Service
public class VideojuegoService {

    private final VideojuegoRepository repositorio;

    public VideojuegoService(VideojuegoRepository repositorio) {
        this.repositorio = repositorio;
    }

    public List<Videojuego> listarVideojuegos() {
        return repositorio.findAll();
    }

    public Optional<Videojuego> buscarPorId(Long id) {
        return repositorio.findById(id);
    }

    public long contarVideojuegos() {
        return repositorio.count();
    }
}
en este ejemplo
  • @Service identifica esta clase como un componente de servicio. Spring la detectará y registrará como un bean: un objeto gestionado por su contenedor.
  • private final VideojuegoRepository repositorio declara la dependencia necesaria para acceder a los datos. final indica que la referencia se asigna en la construcción del objeto.
  • El constructor recibe un VideojuegoRepository. Spring Data JPA proporciona su implementación y Spring la entrega al crear VideojuegoService. No escribimos new VideojuegoRepository().
  • listarVideojuegos() recupera una lista de entidades. buscarPorId() mantiene el tipo Optional<Videojuego> para indicar que podría no existir el registro. contarVideojuegos() obtiene el número de registros.

De momento, estos métodos son sencillos. Más adelante ampliaremos el servicio con operaciones de creación, modificación, eliminación y reglas de negocio.

🟨 Cómo diseñamos los métodos de un servicio​

A diferencia de JpaRepository, un servicio no hereda una lista de operaciones de negocio con nombres obligatorios. Somos nosotros quienes decidimos qué métodos ofrece. Su nombre debe expresar una acción comprensible de nuestra aplicación y sus parámetros deben recoger los datos que necesita para realizarla.

En el servicio anterior hemos tomado estas decisiones:

Método del servicioParámetrosTipo devueltoQué permite hacer
listarVideojuegos()Ninguno.List<Videojuego>Obtener los videojuegos para mostrarlos.
buscarPorId(Long id)Identificador.Optional<Videojuego>Buscar uno y contemplar que no exista.
contarVideojuegos()Ninguno.longObtener el total almacenado.

El controlador utiliza estos métodos sin conocer si detrás hay un findAll(), una consulta personalizada o varias operaciones. Es una ventaja de la separación en capas: podemos cambiar el modo de obtener los datos sin obligar a modificar todas las clases que los utilizan.

Para diseñar un método nuevo seguiremos tres pasos:

  1. Identificamos la operación que necesita la aplicación: por ejemplo, listar los videojuegos de un género.
  2. Decidimos qué debe recibir y devolver: un String genero y una List<Videojuego>, respectivamente.
  3. Elegimos cómo resolverla: el servicio podría utilizar una consulta del repositorio para recuperar solo los registros de ese género. Para ello aprenderemos a declarar métodos de búsqueda en Spring Data JPA.

No es obligatorio que el nombre del método del servicio sea idéntico al del repositorio. Por ejemplo, listarVideojuegos() utiliza internamente findAll(): el primero expresa una operación de nuestra aplicación y el segundo es una operación de acceso a datos.

aviso

En general, no colocaremos Model, HttpServletRequest ni nombres de plantillas Thymeleaf en los métodos de un servicio de negocio. Esos elementos vincularían la capa de servicios a la presentación web. Nuestros servicios trabajarán principalmente con parámetros, entidades y resultados propios de la aplicación.

🟧 Qué tiene que ver con IoC y la inyección de dependencias​

Hasta ahora habíamos creado objetos Java mediante new. En cambio, no creamos manualmente VideojuegoService ni el repositorio. Spring gestiona esos componentes y resuelve sus dependencias.

La inversión de control (IoC) significa, en este contexto, que delegamos en Spring la creación y gestión de los componentes de la aplicación. La inyección de dependencias (DI) es el mecanismo por el que Spring proporciona a un componente los colaboradores que necesita.

En este caso, Spring crea el servicio y le proporciona el repositorio cuando invoca su constructor. Utilizaremos esta misma técnica dentro de un momento para entregar el servicio al controlador.

No necesitamos añadir @Autowired sobre el constructor porque la clase tiene un único constructor. Tampoco es necesario añadir @Component además de @Service: @Service ya identifica la clase como componente gestionado por Spring.

Para distinguir los componentes que hemos utilizado hasta ahora, podemos consultar esta referencia:

Anotación o elementoDónde lo utilizamosPara qué sirve
@ComponentEn la clase temporal PruebaVideojuegoRepositorio.Indica de forma general que Spring debe gestionar esa clase como un bean.
@ServiceEn VideojuegoService.Identifica un componente de la capa de servicios.
@ControllerEn VideojuegoController.Identifica un controlador web MVC.
@RepositoryEn clases de acceso a datos implementadas manualmente, cuando corresponda.Identifica un componente de persistencia. No hace falta añadirla a nuestra interfaz que extiende JpaRepository.
@EntityEn Videojuego.Identifica una entidad JPA, no un bean de servicio gestionado mediante estas anotaciones.

Las anotaciones @Service y @Controller son especializaciones de @Component. En nuestro proyecto Spring Boot las descubre automáticamente cuando sus clases están dentro del paquete principal y sus subpaquetes.

en este ejemplo

Podemos seguir la cadena de dependencias de nuestra aplicación: Spring Data JPA proporciona el repositorio; Spring crea VideojuegoService e inyecta ese repositorio; finalmente, Spring crea VideojuegoController e inyecta el servicio. Cada clase declara lo que necesita en su constructor, pero no se encarga de fabricar esos componentes.

aviso

No debemos confundir inyectar un repositorio con crear o recuperar un videojuego. VideojuegoRepository y VideojuegoService son componentes gestionados por Spring. Las instancias de Videojuego representan los datos persistentes y su gestión corresponde a JPA.

3️⃣ Utilizamos el servicio desde un controlador MVC​

Ahora sí, vamos a recuperar datos cuando alguien abra una página web. Ya conocemos @Controller, @GetMapping y Model de las unidades anteriores; lo nuevo es que el controlador no utilizará directamente el repositorio.

🟩 Creamos el controlador​

En el paquete controladores creamos esta clase:

src/main/java/com/dwes/mi_coleccion/controladores/VideojuegoController.java
package com.dwes.mi_coleccion.controladores;

import com.dwes.mi_coleccion.servicios.VideojuegoService;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class VideojuegoController {

    private final VideojuegoService servicio;

    public VideojuegoController(VideojuegoService servicio) {
        this.servicio = servicio;
    }

    @GetMapping("/videojuegos")
    public String listar(Model model) {
        model.addAttribute("videojuegos", servicio.listarVideojuegos());
        model.addAttribute("total", servicio.contarVideojuegos());
        return "videojuegos/lista";
    }
}
en este ejemplo

@Controller indica que esta clase atiende peticiones web utilizando el modelo MVC. @GetMapping("/videojuegos") relaciona las peticiones GET a esa dirección con el método listar().

El constructor recibe VideojuegoService. Spring nos proporciona la instancia del servicio, igual que hizo con el repositorio. El controlador ya no necesita conocer cómo se recuperan los registros de MySQL: solo solicita los datos al servicio.

Model permite enviar información a la plantilla. Aquí añadimos dos atributos: videojuegos, con la lista recuperada, y total, con el número de registros. Finalmente, devolvemos "videojuegos/lista", que es el nombre lógico de la vista Thymeleaf.

aviso

Esta es la primera versión del controlador. Cuando incorporemos las operaciones CRUD y el buscador, modificaremos la misma clase, sin crear otro VideojuegoController ni repetir la ruta GET /videojuegos, porque se produciría un conflicto de rutas.

Fíjate en que no hemos utilizado @ResponseBody ni @RestController. Queremos devolver una página HTML generada con Thymeleaf, no escribir directamente la lista de objetos en la respuesta HTTP.

🟨 ¿Por qué esta organización resulta más útil?​

El método del controlador es breve porque cada componente se ocupa de lo que le corresponde. Cuando más adelante necesitemos impedir duplicados o comprobar determinadas condiciones antes de guardar un videojuego, esas decisiones podrán incorporarse al servicio sin trasladar la lógica de persistencia a la vista.

Del mismo modo, el repositorio seguirá ocupándose de las consultas y operaciones sobre MySQL. El servicio coordinará esas operaciones y expondrá métodos con sentido para nuestra aplicación, en lugar de obligar a los controladores a conocer los detalles de JPA.

🟧 Aplicamos la misma organización a otro proyecto​

Imaginemos ahora una aplicación para gestionar una biblioteca. Ya no trabajamos con videojuegos, pero las reglas de organización siguen siendo las mismas. Podríamos tener una entidad Libro, un LibroRepository, un LibroService y un LibroController.

Si necesitamos mostrar todos los libros, el controlador atenderá la ruta, el servicio ofrecerá una operación como listarLibros() y el repositorio recuperará los registros. Si necesitamos prestar un libro, aparecerá además una regla de negocio: comprobar que el libro está disponible antes de registrar el préstamo.

Pregunta que debemos resolverDecisión de diseño
¿Qué URL mostrará los libros?La definimos en el controlador.
¿Cómo llamaremos a la operación de listado?Podemos definir listarLibros() en el servicio.
¿Quién consulta los libros almacenados?LibroRepository.
¿Quién decide si se permite un préstamo?El servicio que coordine esa operación.
¿Quién muestra el mensaje «No disponible»?El controlador prepara el resultado y Thymeleaf lo presenta.

Observa que no hemos necesitado copiar una clase de videojuegos y sustituir palabras. Hemos tomado decisiones a partir de las responsabilidades de cada capa. En una aplicación real, el préstamo podría necesitar más de un repositorio; por eso la capa de servicios resulta útil para coordinar el conjunto.

4️⃣ Mostramos los videojuegos con Thymeleaf​

Vamos a crear la vista que utilizará el controlador. Dentro de src/main/resources/templates/ creamos la carpeta videojuegos y, dentro de ella, el archivo lista.html.

src/main/resources/templates/videojuegos/lista.html
<!DOCTYPE html>
<html lang="es" xmlns:th="http://www.thymeleaf.org">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>MiColección - Videojuegos</title>
    <link rel="stylesheet" th:href="@{/css/mi-coleccion.css}">
</head>
<body>
    <h1>Mi colección de videojuegos</h1>

    <p>
        Total de videojuegos:
        <strong th:text="${total}">0</strong>
    </p>

    <p class="sin-resultados" th:if="${#lists.isEmpty(videojuegos)}">
        Todavía no hay videojuegos registrados.
    </p>

    <div class="tabla-responsive" th:unless="${#lists.isEmpty(videojuegos)}">
        <table class="tabla-videojuegos">
            <thead>
            <tr>
                <th>ID</th>
                <th>Título</th>
                <th>Género</th>
                <th>Plataforma</th>
                <th>Año</th>
            </tr>
            </thead>
            <tbody>
            <tr th:each="juego : ${videojuegos}">
                <td th:text="${juego.id}">1</td>
                <td th:text="${juego.titulo}">Celeste</td>
                <td th:text="${juego.genero}">Plataformas</td>
                <td th:text="${juego.plataforma}">PC</td>
                <td th:text="${juego.anioLanzamiento}">2018</td>
            </tr>
            </tbody>
        </table>
    </div>
</body>
</html>
en este ejemplo

La plantilla recibe los atributos que el controlador ha añadido al modelo. ${total} muestra cuántos videojuegos hay registrados.

Con th:if mostramos un mensaje cuando la lista está vacía; con th:unless mostramos la tabla en caso contrario. th:each recorre los objetos Videojuego, y th:text inserta sus propiedades en las celdas.

Este uso de Thymeleaf ya lo conocemos de la UT2. Aquí cambia el origen de los datos: los objetos de la lista se han recuperado de MySQL a través del servicio y del repositorio.

La clase tabla-videojuegos aplica el estilo común a la tabla, mientras que tabla-responsive permite desplazarnos horizontalmente cuando no haya espacio suficiente. sin-resultados mejora la presentación del mensaje de catálogo vacío. Las clases CSS afectan a la apariencia, no a las consultas JPA ni a las expresiones Thymeleaf.

La tabla sigue siendo sencilla desde el punto de vista funcional: por ahora queremos comprobar que la información llega desde MySQL hasta el navegador.

aplicamos estilo al HTML

Desde esta primera página utilizaremos una hoja de estilos común para que el listado, los formularios y el buscador mantengan una presentación coherente.

5️⃣ Comprobamos el funcionamiento de extremo a extremo​

🟩 Ejecutamos y abrimos el listado​

Antes de arrancar, comprobamos que el servicio MySQL de Windows sigue en funcionamiento. También debemos mantener configurada la variable de entorno DB_PASSWORD en IntelliJ IDEA.

Ya guardamos al menos un videojuego mediante el repositorio. Podemos utilizar ese registro para comprobar el listado sin introducir nuevos datos. Al retirar la clase temporal PruebaVideojuegoRepositorio, el videojuego sigue almacenado en MySQL: eliminar código Java no borra los registros.

Arrancamos Spring Boot y abrimos esta dirección:

http://localhost:8080/videojuegos

Deberíamos ver el título de la página, el número de registros y una fila por cada videojuego existente. Si la tabla estuviera vacía, aparecería el mensaje correspondiente, pero no debería producirse un error.

🟨 Seguimos el recorrido de una petición​

Cuando solicitamos /videojuegos, ocurre lo siguiente:

  1. Spring MVC invoca el método listar() de VideojuegoController.
  2. El controlador solicita la lista y el total a VideojuegoService.
  3. El servicio utiliza VideojuegoRepository para acceder a los datos de MySQL.
  4. El controlador incorpora los resultados al Model y devuelve el nombre de la vista.
  5. Thymeleaf genera el HTML y el navegador muestra la página.

Si detenemos Spring Boot, volvemos a iniciarlo y abrimos la misma dirección, recuperaremos los registros conservados en MySQL. No estamos leyendo una colección fija creada dentro del controlador.

consejo

En este primer listado ejecutamos una consulta para obtener la lista y otra para contar los registros. Lo hacemos para mantener el ejemplo claro. Más adelante aprenderemos a trabajar con consultas específicas y paginación, donde también tendremos que considerar el coste de cada consulta.

🟧 Procedimiento para incorporar una funcionalidad nueva​

Cuando añadamos una operación a cualquier aplicación organizada por capas, podemos utilizar esta pequeña guía. No implica que siempre tengamos que crear clases nuevas: comenzaremos por identificar qué componentes existentes debemos ampliar.

  1. Definimos la necesidad. Por ejemplo, mostrar la ficha de un videojuego a partir de su identificador.
  2. Determinamos qué datos requiere. En este caso, el identificador id y la posibilidad de que no exista ningún registro.
  3. Diseñamos la operación del servicio. Podemos reutilizar buscarPorId(Long id), que devuelve un Optional<Videojuego>.
  4. Comprobamos si el repositorio ya ofrece lo necesario. findById(id) ya existe; no hace falta crear una consulta nueva.
  5. Adaptamos el controlador y la vista. El controlador recibe el identificador, consulta al servicio y decide qué respuesta web ofrecer. Thymeleaf se encarga de presentar los datos.

Esta forma de trabajar evita dos errores habituales: escribir toda la funcionalidad dentro del controlador y crear métodos personalizados en el repositorio cuando ya existe una operación adecuada.

🟪 Errores frecuentes​

El controlador no encuentra VideojuegoService​

Si aparece un error indicando que no existe un bean de ese tipo, revisamos que la clase tenga @Service y se encuentre dentro de com.dwes.mi_coleccion o alguno de sus subpaquetes. También comprobamos que el repositorio esté correctamente definido.

Thymeleaf indica que no encuentra la vista​

Si devuelve un error de plantilla, comprobamos la ruta exacta src/main/resources/templates/videojuegos/lista.html y que el controlador devuelva "videojuegos/lista", sin añadir .html al nombre lógico.

La página se abre, pero no aparecen videojuegos​

Esto no implica necesariamente un fallo. Si MySQL no tiene registros, la lista estará vacía. Podemos comprobarlo con la consulta SQL que utilizamos en el apartado anterior. También verificaremos que Spring Boot se conecta a la base de datos mi_coleccion.

Se devuelven datos en lugar de una página HTML​

El controlador destinado a Thymeleaf debe utilizar @Controller y devolver el nombre de la vista, sin @ResponseBody. No utilizaremos @RestController para esta funcionalidad.

Mezclamos responsabilidades entre capas​

Si un controlador contiene muchas llamadas al repositorio, comprobaciones de reglas de negocio y modificaciones de entidades, conviene revisar su diseño: probablemente estamos colocando en él trabajo que debería coordinar un servicio.

A la inversa, un servicio que recibe un Model o devuelve directamente el nombre de una plantilla está asumiendo responsabilidades de presentación. La separación en capas no depende del nombre que demos a las clases, sino de lo que hacemos dentro de ellas.

6️⃣ Comprobamos lo aprendido​

Estas comprobaciones son no evaluables y no requieren entrega.

  1. Identifica dónde se utiliza cada anotación: @Service, @Controller y @GetMapping.
  2. Explica qué componente proporciona VideojuegoRepository al servicio y quién proporciona el servicio al controlador.
  3. Indica qué modificarías si necesitáramos cambiar la consulta a MySQL, pero mantener la misma página HTML.
  4. Comprueba qué ocurre al mostrar el listado con la tabla vacía y con un videojuego almacenado.
  5. ¿Por qué no es necesario crear VideojuegoService mediante new dentro del controlador?
  6. En una aplicación de biblioteca, ¿qué capa decidiría si un libro puede prestarse? ¿Cuál comprobaría su existencia en la base de datos y cuál mostraría el resultado en HTML?
  7. Si necesitas mostrar la ficha de un videojuego por su ID, ¿qué método del servicio reutilizarías y cómo tratarías la posibilidad de que el registro no exista?
  8. ¿Por qué no deberíamos pasar un Model de Spring MVC como parámetro de un método de servicio?
Antes de continuar

Ya tenemos un recorrido completo: petición HTTP → controlador → servicio → repositorio JPA → MySQL → vista Thymeleaf.

Al finalizar deben existir Videojuego.java, VideojuegoRepository.java, VideojuegoService.java, VideojuegoController.java y la plantilla templates/videojuegos/lista.html y static/css/mi-coleccion.css. La página debe cargar los estilos y mostrar los registros persistentes de mi_coleccion, incluso después de reiniciar la aplicación. La clase temporal PruebaVideojuegoRepositorio ya debe estar retirada.

El siguiente paso será ampliar VideojuegoService con operaciones para crear, modificar y eliminar videojuegos. Después las conectaremos con controladores y formularios Thymeleaf, reutilizando lo aprendido sobre formularios en la UT3.
