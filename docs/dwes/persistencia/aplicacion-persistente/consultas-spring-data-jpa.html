2.4. Consultas con Spring Data JPA

Ya hemos completado el CRUD de MiColección: podemos dar de alta, modificar y eliminar videojuegos desde el navegador. Sin embargo, el listado sigue mostrando todos los registros almacenados, independientemente de lo que estemos buscando.

En este apartado aprenderemos a escribir consultas que seleccionen los videojuegos adecuados. Primero estudiaremos cómo Spring Data JPA interpreta los nombres de los métodos; después conoceremos @Query, JPQL y las consultas SQL nativas. Por último, aplicaremos lo aprendido para añadir búsqueda por título y filtro por género al listado de MiColección.

Idea principal

Una consulta permite recuperar solo los registros que cumplen determinadas condiciones. En Spring Data JPA podemos definir esas condiciones mediante métodos derivados o escribirlas con @Query. El repositorio accede a MySQL, el servicio organiza la búsqueda y el controlador prepara los resultados para Thymeleaf.

1️⃣ ¿Por qué necesitamos consultas más concretas?​

🟩 Filtrar en MySQL, no después de recuperar todo​

Hasta ahora VideojuegoService utilizaba findAll() para recuperar los registros. Si tenemos cinco videojuegos, resulta suficiente; si tenemos varios centenares, no tiene sentido mostrar toda la colección cada vez que alguien quiere localizar un título.

Podríamos recuperar todos los videojuegos en una lista de Java y buscar manualmente dentro de ella. Pero estaríamos trasladando a la aplicación un trabajo que el gestor de bases de datos puede realizar directamente. En SQL escribiríamos, por ejemplo:

Filtramos registros desde MySQL
SELECT id, titulo, genero, plataforma, anio_lanzamiento
FROM videojuegos
WHERE genero = 'Plataformas';
en este ejemplo

WHERE limita las filas que devuelve MySQL. La consulta no modifica la tabla: únicamente selecciona los videojuegos que cumplen la condición. Más adelante haremos búsquedas equivalentes desde Java, sin construir manualmente un SELECT para cada operación.

🟨 La búsqueda sigue la organización por capas​

En nuestra aplicación, cada componente tiene su función:

ComponenteResponsabilidad durante una búsqueda
RepositorioDeclarar y ejecutar la consulta a través de JPA.
ServicioRecibir los criterios y coordinar la consulta.
ControladorObtener parámetros GET y preparar el Model.
ThymeleafMostrar el formulario y los resultados.

Buscar no modifica registros, por lo que utilizaremos GET /videojuegos con parámetros de consulta. Las rutas POST del CRUD seguirán reservadas para crear, actualizar y eliminar.

2️⃣ Consultas derivadas del nombre del método​

Los métodos findAll() y findById() ya están disponibles al extender JpaRepository. Para buscar por otros atributos, Spring Data JPA nos permite declarar métodos nuevos dentro de la interfaz. Cuando reconoce la estructura de su nombre, genera la consulta correspondiente.

🟩 Construimos una búsqueda por género​

Supongamos que queremos buscar los videojuegos de un género, sin distinguir mayúsculas y minúsculas. Necesitamos una propiedad (genero), una comparación (igualdad sin diferenciar mayúsculas) y un resultado capaz de contener varios registros (List<Videojuego>).

Método derivado en VideojuegoRepository.java
List<Videojuego> findByGeneroIgnoreCase(String genero);
en este ejemplo
  • findBy indica que queremos recuperar entidades que cumplen una condición.
  • Genero se refiere a la propiedad Java genero, no al nombre de una columna SQL.
  • IgnoreCase solicita ignorar las diferencias entre mayúsculas y minúsculas.

La firma termina en ;, sin cuerpo de método. Spring Data JPA proporciona su implementación. Por ejemplo, al buscar "PLATAFORMAS" podremos recuperar registros cuyo género sea Plataformas.

En nuestro proyecto abrimos VideojuegoRepository.java, que hasta ahora estaba vacío por dentro, y añadimos temporalmente esa declaración:

src/main/java/com/dwes/mi_coleccion/repositorios/VideojuegoRepository.java
package com.dwes.mi_coleccion.repositorios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.List;

public interface VideojuegoRepository extends JpaRepository<Videojuego, Long> {

    List<Videojuego> findByGeneroIgnoreCase(String genero);
}

No crearemos otra interfaz. Estamos ampliando la que utilizamos en toda la unidad. Más adelante en este mismo apartado mostraremos su versión completa para el buscador.

🟨 Cómo elegimos un nombre derivado​

La estructura habitual de estas consultas es findBy seguido de la propiedad, el operador y, si procede, otras condiciones. No debemos inventar palabras: Spring Data reconoce un conjunto de operadores.

OperadorEjemploQué consulta
IgualdadfindByGenero(String genero)Coincidencia exacta de género.
IgnoreCasefindByGeneroIgnoreCase(String genero)Género sin diferenciar mayúsculas.
ContainingfindByTituloContainingIgnoreCase(String texto)Una palabra o fragmento dentro del título.
StartingWithfindByTituloStartingWith(String inicio)Títulos que empiezan por un texto.
GreaterThanEqualfindByAnioLanzamientoGreaterThanEqual(Integer anio)Año igual o posterior al indicado.
BetweenfindByAnioLanzamientoBetween(Integer desde, Integer hasta)Años dentro de un intervalo.
AndfindByGeneroAndAnioLanzamiento(String genero, Integer anio)Ambas condiciones.
OrfindByGeneroOrPlataforma(String genero, String plataforma)Al menos una condición.
OrderBy...AscfindByGeneroOrderByTituloAsc(String genero)Filtrar y ordenar de forma fija.
Top / FirstfindTop3ByOrderByAnioLanzamientoDesc()Como máximo tres resultados.

La búsqueda por intervalo de años, por ejemplo, podría declararse así:

Ejemplo de otra consulta derivada (no es necesario conservarla)
List<Videojuego> findByAnioLanzamientoBetween(Integer desde, Integer hasta);

Desde el servicio podríamos invocarla con repositorio.findByAnioLanzamientoBetween(2015, 2020). Los argumentos deben seguir el mismo orden que las propiedades y condiciones indicadas en el método.

🟧 También podemos contar o comprobar existencias​

No todas las consultas tienen que devolver una lista. Spring Data JPA reconoce otros prefijos:

PrefijoEjemploResultado habitual
findByfindByGeneroIgnoreCase(...)Una lista u otro tipo de resultado de búsqueda.
countBycountByGenero(String genero)long con el número de coincidencias.
existsByexistsByTituloIgnoreCase(String titulo)boolean.
deleteBydeleteByGenero(String genero)Una operación de eliminación, no de lectura.

Las eliminaciones derivadas existen, pero no las utilizaremos aquí. Nuestro CRUD ya gestiona las eliminaciones desde el servicio, donde comprobamos qué registro se quiere borrar. Las operaciones masivas requieren prestar atención a la integridad y a las transacciones.

consejo

No existe un updateBy genérico que permita modificar campos solo mediante el nombre de un método. Para nuestras actualizaciones habituales seguiremos recuperando la entidad y utilizando save(); las consultas que modifican varios registros se estudiarán con mayor detalle junto a las transacciones.

🟥 Qué devuelve una consulta​

Un método que puede encontrar varios videojuegos suele devolver List<Videojuego>. Para un resultado único que puede no existir, Optional<Videojuego> expresa mejor esa posibilidad. Si la búsqueda no garantiza unicidad, no debemos declararla como si solo pudiera recuperar un registro.

Los nombres de las consultas se construyen con propiedades Java. Por eso escribimos AnioLanzamiento y no anio_lanzamiento, aunque esa sea la columna de MySQL. Si Spring Data no reconoce una propiedad, normalmente dará un error durante el arranque.

3️⃣ Consultas escritas con @Query​

🟩 Cuándo necesitamos algo más que un nombre​

Los métodos derivados son cómodos para las condiciones sencillas, pero un método con varios filtros opcionales puede resultar largo y difícil de leer. En ese caso podemos escribir la consulta con @Query. Seguimos declarando un método del repositorio; lo que cambia es cómo describimos la búsqueda.

AlternativaCómo expresamos la operaciónUso habitual
Método heredadoYa viene en JpaRepository.Buscar por ID, listar todos, contar.
Método derivadoSpring Data interpreta el nombre.Búsquedas sencillas.
@Query con JPQLEscribimos una consulta sobre entidades y propiedades Java.Consultas con condiciones más elaboradas.
@Query con SQL nativoEscribimos SQL con tablas y columnas reales.Operaciones ligadas al gestor de base de datos.

🟨 JPQL trabaja con entidades y propiedades Java​

JPQL (Jakarta Persistence Query Language) utiliza los nombres de las entidades y sus propiedades. Una consulta sencilla puede escribirse así:

Consulta JPQL de ejemplo en VideojuegoRepository.java
@Query("SELECT v FROM Videojuego v WHERE v.anioLanzamiento >= :anio")
List<Videojuego> buscarDesdeAnio(@Param("anio") Integer anio);
en este ejemplo

FROM Videojuego v señala la clase entidad Videojuego y le asigna el alias v. Escribimos v.anioLanzamiento, porque JPQL emplea nombres Java, no videojuegos ni anio_lanzamiento.

:anio es un parámetro con nombre. La anotación @Param("anio") enlaza ese marcador con el argumento Java del método. Los valores se proporcionan como parámetros: no creamos la consulta concatenando texto recibido del navegador.

JPQL utiliza expresiones familiares del lenguaje SQL: SELECT, FROM, WHERE, AND, OR, LIKE y ORDER BY, pero su modelo de referencia son las entidades y sus propiedades. Por ejemplo, para buscar por género y año:

Ejemplo independiente de JPQL con dos filtros
@Query("""
       SELECT v FROM Videojuego v
       WHERE v.genero = :genero
         AND v.anioLanzamiento >= :anio
       """)
List<Videojuego> buscarGeneroDesdeAnio(
        @Param("genero") String genero,
        @Param("anio") Integer anio);
en este ejemplo

AND obliga a cumplir las dos condiciones. El método puede devolver varios videojuegos y por eso usamos una lista. No es obligatorio copiar este segundo ejemplo: la idea es reconocer cómo construir una consulta y asociar cada parámetro a un argumento.

🟧 SQL nativo utiliza tablas y columnas reales​

Si necesitamos emplear instrucciones específicas de MySQL, podemos escribir SQL nativo:

Ejemplo alternativo con SQL nativo
@Query(value = "SELECT * FROM videojuegos WHERE genero = :genero",
       nativeQuery = true)
List<Videojuego> buscarGeneroSql(@Param("genero") String genero);

La diferencia de nombres es importante:

JPQLSQL nativo
FROM Videojuego vFROM videojuegos
v.anioLanzamientoanio_lanzamiento
v.genero = :generogenero = :genero

No incorporaremos esta variante a MiColección porque la búsqueda puede resolverse con JPQL. Las consultas nativas siguen siendo útiles, pero nos vinculan de forma más directa al esquema de MySQL.

Valores parametrizados

Usaremos siempre parámetros para los valores de búsqueda, tanto con JPQL como con SQL nativo. No construiremos SQL concatenando la entrada de una persona con +. La parametrización evita que los datos recibidos se interpreten como fragmentos de una instrucción SQL.

🟥 Una nota sobre @Modifying​

@Query también admite sentencias de modificación, pero no las confundiremos con las búsquedas de lectura. Para realizar un UPDATE o un DELETE masivo se utiliza @Modifying y es necesario prestar atención a la transacción. No añadiremos ahora una operación masiva al repositorio: estas operaciones se explicarán al trabajar la integridad y las transacciones.

4️⃣ Añadimos búsquedas a MiColección​

Vamos a aplicar lo aprendido sin cambiar las rutas de alta, edición y eliminación. Modificaremos cuatro piezas existentes: el repositorio, el servicio, el método de listado del controlador y la vista lista.html.

Nuestro objetivo es que /videojuegos permita buscar por una parte del título, filtrar por género y combinar ambas condiciones. Todavía no añadiremos ordenación seleccionable ni paginación.

🟩 Paso 1. Ampliamos el repositorio​

Sustituimos VideojuegoRepository.java por esta versión completa. Incluye dos métodos derivados como ejemplos y una consulta JPQL para el buscador web:

src/main/java/com/dwes/mi_coleccion/repositorios/VideojuegoRepository.java
package com.dwes.mi_coleccion.repositorios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.List;

public interface VideojuegoRepository extends JpaRepository<Videojuego, Long> {

    List<Videojuego> findByGeneroIgnoreCase(String genero);

    List<Videojuego> findByTituloContainingIgnoreCase(String texto);

    @Query("""
            SELECT v FROM Videojuego v
            WHERE (:titulo = '' OR LOWER(v.titulo) LIKE LOWER(CONCAT('%', :titulo, '%')))
              AND (:genero = '' OR LOWER(v.genero) = LOWER(:genero))
            """)
    List<Videojuego> buscarConFiltros(
            @Param("titulo") String titulo,
            @Param("genero") String genero);
}
en este ejemplo

La consulta buscarConFiltros() admite dos parámetros. Cuando titulo está vacío, la primera condición no limita los resultados; si contiene texto, LIKE busca la secuencia dentro del título. El género sigue una regla parecida, pero exige coincidencia exacta sin diferenciar mayúsculas.

Los métodos derivados son ejemplos de otras búsquedas disponibles. El listado web utilizará buscarConFiltros(), que combina las condiciones en una sola consulta JPQL. Ambos parámetros llegarán normalizados desde el servicio.

consejo

En LIKE, los caracteres % y _ tienen significado especial como comodines. Una búsqueda de 100% puede encontrar más títulos de los previstos; no es una inyección SQL, pues los valores viajan parametrizados. En esta primera versión aceptaremos ese comportamiento y lo distinguiremos de un problema de seguridad.

🟨 Paso 2. Incorporamos el método de búsqueda al servicio​

No sustituimos VideojuegoService.java completo: debe conservar listarVideojuegos(), buscarPorId(), contarVideojuegos() y todos los métodos CRUD que ya implementamos. Solo añadimos dentro de la clase:

Método que añadimos a VideojuegoService.java
public List<Videojuego> buscarConFiltros(String titulo, String genero) {
    String tituloBuscado = titulo == null ? "" : titulo.trim();
    String generoBuscado = genero == null ? "" : genero.trim();

    return repositorio.buscarConFiltros(tituloBuscado, generoBuscado);
}
en este ejemplo

El servicio elimina los espacios al principio y al final de los filtros mediante trim() y sustituye un posible valor null por una cadena vacía. La consulta no se ejecuta dentro del controlador: el servicio delega en el repositorio, como en el resto de MiColección.

🟧 Paso 3. Sustituimos solo la ruta GET del listado​

Conservamos en VideojuegoController los métodos POST y las rutas de edición que ya funcionan. Añadimos dos importaciones que todavía no aparecían en el controlador:

Importaciones adicionales en VideojuegoController.java
import org.springframework.web.bind.annotation.RequestParam;
import java.util.List;

Después sustituimos exclusivamente el método listar(); no dejamos dos métodos para la misma ruta:

Nuevo listar() de VideojuegoController.java
@GetMapping
public String listar(
        @RequestParam(defaultValue = "") String titulo,
        @RequestParam(defaultValue = "") String genero,
        Model model) {

    List<Videojuego> encontrados = servicio.buscarConFiltros(titulo, genero);
    model.addAttribute("videojuegos", encontrados);
    model.addAttribute("total", encontrados.size());
    model.addAttribute("titulo", titulo);
    model.addAttribute("genero", genero);
    return "videojuegos/lista";
}
en este ejemplo

@RequestParam recoge los filtros enviados en la URL. El valor predeterminado "" permite seguir abriendo /videojuegos sin parámetros, igual que antes. En este momento total es el tamaño de la lista recuperada. Cuando incorporemos paginación distinguiremos entre registros de una página y número total de coincidencias.

La clase es un controlador MVC con @Controller, por lo que devuelve la vista Thymeleaf; no debemos añadir @ResponseBody ni sustituirla por @RestController.

🟥 Paso 4. Adaptamos el listado Thymeleaf​

El archivo formulario.html del CRUD no cambia. Sustituimos solo src/main/resources/templates/videojuegos/lista.html por esta versión completa, que conserva los mensajes, las acciones y el CSS de MiColección y añade un formulario GET de búsqueda:

El formulario usa method="get": los filtros se incorporan a la URL, por ejemplo /videojuegos?titulo=zelda&genero=Aventura. th:value conserva lo que se había escrito y la tabla se rellena con los resultados obtenidos de MySQL.

No hemos eliminado el CRUD: se mantienen el enlace de alta, la edición, la eliminación por POST y los mensajes flash. Las clases .filtros y .campo ya están previstas en mi-coleccion.css; no es necesario añadir otro CSS.

5️⃣ Comprobamos las consultas y evitamos errores comunes​

🟩 Probamos desde el navegador​

Con MySQL iniciado y la variable DB_PASSWORD configurada, arrancamos la aplicación y abrimos:

http://localhost:8080/videojuegos

Haremos las siguientes comprobaciones: mostrar el listado sin filtros, buscar parte de un título, filtrar por un género existente, combinar ambos criterios y escribir un título que no tenga coincidencias. También verificaremos que los botones de añadir, editar y eliminar siguen funcionando.

Podemos comprobar en MySQL que filtrar no modifica registros:

Comprobamos cuántos registros tenemos en MySQL
SELECT COUNT(*) FROM videojuegos;

🟨 Errores frecuentes​

🟩 Spring no reconoce la consulta derivada​

Revisamos que el nombre utilice propiedades Java, como titulo, genero y anioLanzamiento, y que no hayamos añadido nombres de columnas SQL dentro de un findBy....

🟨 JPQL produce un error al arrancar​

Comprobamos que la consulta use FROM Videojuego v, no FROM videojuegos, y que los nombres de los parámetros (:titulo y :genero) coincidan con @Param.

🟧 El listado deja de mostrar los mensajes de guardado​

La plantilla debe seguir incluyendo los elementos con th:if="${mensaje}" y th:if="${error}". También debemos conservar las rutas POST del controlador, que no hemos modificado.

🟥 El buscador no muestra valores en los campos​

Comprobamos que el controlador añada titulo y genero al modelo y que los name y th:value del formulario GET coincidan con los parámetros de la URL.

aviso

La búsqueda es una lectura, no una operación de escritura. No debemos modificar la base de datos ni convertir el formulario de filtros en un POST. Tampoco filtraremos una lista completa en Java cuando podemos expresar la condición desde el repositorio.

🟧 Comprobación no evaluable: diseñamos una búsqueda distinta​

En una biblioteca, queremos buscar libros por una parte de su título y por el nombre del autor. ¿Qué propiedades necesitaría la entidad Libro? ¿Qué método derivado serviría para buscar únicamente por título? ¿Cómo escribiríamos una consulta JPQL con dos parámetros opcionales?

No necesitamos programar la biblioteca. Esta comprobación es no evaluable y no requiere entrega; nos interesa razonar la consulta antes de escribirla.

6️⃣ Qué debemos haber comprendido​

Al finalizar, deberíamos distinguir cuándo basta un método heredado, cuándo interesa una consulta derivada y cuándo resulta más legible utilizar @Query con JPQL. También debemos reconocer en qué se diferencia JPQL del SQL nativo y por qué enviamos los valores de búsqueda como parámetros.

Estado de MiColección: podemos dar de alta, editar y eliminar videojuegos; también buscar por título y género desde el listado. Esta búsqueda podrá ampliarse con ordenación y paginación sin perder las funcionalidades existentes.
