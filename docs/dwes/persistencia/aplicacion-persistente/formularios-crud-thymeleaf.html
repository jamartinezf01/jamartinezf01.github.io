2.3. Formularios CRUD con Thymeleaf

En el apartado anterior hemos ampliado VideojuegoService con operaciones para crear, actualizar y eliminar registros. Los métodos están preparados, pero todavía no existe una forma de utilizarlos desde el navegador: por ahora solo tenemos el listado de videojuegos.

En este apartado construiremos esa interfaz. Recuperaremos los conceptos de formularios, validación, @ModelAttribute, BindingResult y redirecciones estudiados en UT3, pero ahora los aplicaremos a datos que se conservarán en MySQL.

Idea principal

Un formulario recoge datos, pero no guarda por sí mismo ningún registro. El controlador recibe la petición, comprueba la validación, utiliza el servicio y decide si debe mostrar de nuevo el formulario o redirigir al listado.

1️⃣ Preparamos las rutas de gestión​

🟩 Las operaciones que ofrecerá el navegador​

Anteriormente creamos GET /videojuegos para mostrar todos los registros. Ahora ampliaremos ese mismo controlador, sin duplicar la ruta de listado, con las acciones siguientes:

AcciónMétodo HTTPRutaQué ocurre
ListarGET/videojuegosMuestra los registros almacenados.
Abrir el altaGET/videojuegos/nuevoMuestra un formulario vacío.
Guardar el altaPOST/videojuegos/nuevoValida e inserta un videojuego nuevo.
Abrir la ediciónGET/videojuegos/{id}/editarRecupera el registro y rellena el formulario.
Guardar la ediciónPOST/videojuegos/{id}/editarValida y actualiza el registro identificado.
EliminarPOST/videojuegos/{id}/eliminarElimina el registro solicitado.

Utilizamos GET para solicitar páginas y POST para las operaciones que modifican datos. En particular, eliminar nunca se hará mediante un enlace GET: cargar una página no debería borrar información.

🟨 Qué archivos modificaremos​

Partiremos del estado alcanzado en los puntos anteriores. A partir de aquí realizaremos exactamente estos cambios:

  1. Videojuego.java: añadiremos reglas de validación y un constructor público vacío.
  2. VideojuegoController.java: sustituiremos la clase por una versión completa que conserva el listado y añade las rutas CRUD.
  3. formulario.html: crearemos una plantilla para altas y ediciones.
  4. lista.html: actualizaremos la tabla para incluir acciones y mensajes.
  5. Estilos de MiColección: mantendremos el enlace a mi-coleccion.css en lista.html y lo añadiremos a formulario.html. No es necesario volver a descargar el archivo.

No modificaremos VideojuegoRepository ni volveremos a sustituir VideojuegoService. Ambos ya están preparados para estas operaciones.

2️⃣ Preparamos la entidad para recibir datos del formulario​

Al definir la entidad Videojuego creamos las propiedades titulo, genero, plataforma y anioLanzamiento. Mantendremos sus columnas y sus métodos de acceso. Solo necesitamos un pequeño ajuste para trabajar cómodamente con formularios MVC y añadir las reglas de validación que ya aprendimos en UT3.

🟩 Constructor sin argumentos y validación​

En Videojuego.java cambiaremos el constructor sin argumentos de protected a public. Ambas opciones son válidas para JPA, pero con el constructor público podremos escribir new Videojuego() al preparar un formulario vacío.

A continuación incorporaremos las anotaciones de Jakarta Validation a los cuatro atributos editables. No es necesario volver a escribir toda la clase: sustituimos las declaraciones correspondientes por estas, conservando el resto del código de Videojuego.java.

Atención: el siguiente bloque no es un archivo Java completo. Conservaremos la entidad Videojuego que ya tenemos y cambiaremos únicamente las propiedades indicadas, sus anotaciones y el constructor sin argumentos; los import van al principio de la clase.

Cambios en src/main/java/com/dwes/mi_coleccion/modelo/Videojuego.java
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

// Dentro de la clase Videojuego:

@Column(nullable = false, length = 120)
@NotBlank(message = "El título es obligatorio")
@Size(max = 120, message = "Máximo 120 caracteres")
private String titulo;

@Column(nullable = false, length = 60)
@NotBlank(message = "El género es obligatorio")
@Size(max = 60, message = "Máximo 60 caracteres")
private String genero;

@Column(nullable = false, length = 60)
@NotBlank(message = "La plataforma es obligatoria")
@Size(max = 60, message = "Máximo 60 caracteres")
private String plataforma;

@Column(name = "anio_lanzamiento", nullable = false)
@NotNull(message = "El año es obligatorio")
@Min(value = 1950, message = "El año debe ser 1950 o posterior")
private Integer anioLanzamiento;

public Videojuego() {
}
en este ejemplo

@Column describe cómo se almacena la propiedad en la base de datos: longitud de la columna y posibilidad de admitir NULL, entre otras características. En cambio, @NotBlank, @Size, @NotNull y @Min son reglas de validación de los datos recibidos por la aplicación. Aunque puedan estar relacionadas, no tienen exactamente la misma función.

@NotBlank impide enviar cadenas vacías o compuestas únicamente por espacios. @NotNull exige un valor y @Min establece el mínimo admitido. Añadimos también @Size para validar las longitudes antes de llegar a MySQL.

Estas anotaciones requieren la dependencia Validation, que ya añadimos al crear nuestro proyecto. El constructor público sin argumentos permite crear un Videojuego vacío para mostrar el formulario.

aviso

El fragmento anterior contiene únicamente los cambios, no una clase Java completa que haya que copiar sobre Videojuego.java. Conservaremos @Entity, @Table, @Id, @GeneratedValue, el constructor con argumentos y todos los getters y setters existentes. Los cuatro import de validación deben ir al principio del archivo, junto con los demás.

No añadiremos un setId() ni un campo de formulario editable para el identificador. MySQL genera el ID de los registros nuevos y, para editar, identificaremos el registro mediante la URL.

consejo

Vincular el formulario directamente con la entidad es una simplificación adecuada mientras sus propiedades sean sencillas. Cuando necesitemos recibir identificadores de otras entidades relacionadas, una clase específica para el formulario permitirá separar los datos enviados desde la web del modelo persistente.

🟨 Dos comprobaciones distintas: formulario y base de datos​

Cuando diseñamos un alta o una edición debemos pensar en dos preguntas: ¿son correctos los datos introducidos? y ¿puede MySQL almacenarlos sin incumplir sus restricciones? No son exactamente la misma comprobación.

SituaciónDónde la tratamos principalmenteEjemplo
Campo obligatorio vacío.Validación del objeto con @NotBlank.Título formado solo por espacios.
Número fuera del intervalo permitido.Validación con @Min, @Max u otra regla.Año anterior a 1950.
Columna que no puede almacenar NULL.Restricción del esquema con @Column(nullable = false).titulo no admite NULL.
Valor que debe ser único en la tabla.Restricción de unicidad de MySQL y, si conviene, comprobación previa en la aplicación.Código de inventario que no puede repetirse.

@Valid comprueba las restricciones de validación que hayamos declarado, pero no significa que todas las operaciones vayan a completarse en MySQL. Si una restricción de la base de datos rechaza la escritura, necesitaremos gestionar ese fallo. En este primer CRUD nos concentraremos en los casos de validación y de registros inexistentes; volveremos sobre la integridad al estudiar las relaciones y las transacciones.

3️⃣ Añadimos las rutas CRUD al controlador​

Nuestro controlador ya mostraba la lista de videojuegos. Sustituiremos la clase anterior por esta versión completa, que mantiene @GetMapping para el listado y añade las rutas de alta, edición y eliminación. No crearemos un segundo controlador ni conservaremos el anterior en paralelo: eso produciría rutas duplicadas.

🟩 Controlador completo​

src/main/java/com/dwes/mi_coleccion/controladores/VideojuegoController.java
package com.dwes.mi_coleccion.controladores;

import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.servicios.VideojuegoService;
import jakarta.validation.Valid;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

import java.util.Optional;

@Controller
@RequestMapping("/videojuegos")
public class VideojuegoController {

    private final VideojuegoService servicio;

    public VideojuegoController(VideojuegoService servicio) {
        this.servicio = servicio;
    }

    @GetMapping
    public String listar(Model model) {
        model.addAttribute("videojuegos", servicio.listarVideojuegos());
        model.addAttribute("total", servicio.contarVideojuegos());
        return "videojuegos/lista";
    }

    @GetMapping("/nuevo")
    public String mostrarNuevo(Model model) {
        model.addAttribute("videojuego", new Videojuego());
        model.addAttribute("modoEdicion", false);
        return "videojuegos/formulario";
    }

    @PostMapping("/nuevo")
    public String crear(
            @Valid @ModelAttribute("videojuego") Videojuego videojuego,
            BindingResult errores,
            Model model,
            RedirectAttributes redirect) {

        if (errores.hasErrors()) {
            model.addAttribute("modoEdicion", false);
            return "videojuegos/formulario";
        }

        servicio.crear(videojuego);
        redirect.addFlashAttribute("mensaje", "Videojuego añadido correctamente.");
        return "redirect:/videojuegos";
    }

    @GetMapping("/{id}/editar")
    public String mostrarEditar(
            @PathVariable Long id,
            Model model,
            RedirectAttributes redirect) {

        Optional<Videojuego> encontrado = servicio.buscarPorId(id);
        if (encontrado.isEmpty()) {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
            return "redirect:/videojuegos";
        }

        model.addAttribute("videojuego", encontrado.get());
        model.addAttribute("modoEdicion", true);
        model.addAttribute("idEdicion", id);
        return "videojuegos/formulario";
    }

    @PostMapping("/{id}/editar")
    public String actualizar(
            @PathVariable Long id,
            @Valid @ModelAttribute("videojuego") Videojuego videojuego,
            BindingResult errores,
            Model model,
            RedirectAttributes redirect) {

        if (errores.hasErrors()) {
            model.addAttribute("modoEdicion", true);
            model.addAttribute("idEdicion", id);
            return "videojuegos/formulario";
        }

        if (!servicio.actualizar(id, videojuego)) {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
            return "redirect:/videojuegos";
        }

        redirect.addFlashAttribute("mensaje", "Videojuego actualizado correctamente.");
        return "redirect:/videojuegos";
    }

    @PostMapping("/{id}/eliminar")
    public String eliminar(@PathVariable Long id, RedirectAttributes redirect) {
        if (servicio.eliminar(id)) {
            redirect.addFlashAttribute("mensaje", "Videojuego eliminado.");
        } else {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
        }
        return "redirect:/videojuegos";
    }
}
en este ejemplo

@RequestMapping("/videojuegos") establece una ruta común para todos los métodos. Por eso @GetMapping("/nuevo") responde a /videojuegos/nuevo y @GetMapping sin ruta adicional responde a /videojuegos.

@ModelAttribute("videojuego") recoge los campos enviados y los vincula a un objeto Java. @Valid activa la validación y BindingResult, colocado inmediatamente después del objeto validado, permite detectar errores sin perder los datos introducidos.

@PathVariable obtiene el ID incluido en la ruta de edición o eliminación. Los métodos del controlador no llaman al repositorio: delegan en VideojuegoService.

Con RedirectAttributes.addFlashAttribute() enviamos un mensaje que estará disponible después de la redirección. Recordemos que el prefijo redirect: indica una nueva petición, en lugar de renderizar directamente una plantilla.

🟨 ¿Qué ocurre cuando los datos no son válidos?​

Si se deja el título vacío o se introduce un año inferior al mínimo, errores.hasErrors() será true. El controlador devuelve el formulario, que conserva los valores introducidos y muestra los mensajes de validación. No se llama a servicio.crear() ni a servicio.actualizar().

En la edición, la URL contiene el ID original y se conserva en idEdicion para que el formulario vuelva a enviarse a la ruta correcta. El identificador no se modifica con los campos del formulario.

🟧 El patrón GET → POST → redirección​

En aplicaciones MVC con formularios es habitual separar la petición que abre el formulario de la que procesa sus datos. Nuestro controlador sigue este esquema:

MomentoQué realiza el controladorResultado
GET de altaCrea un objeto vacío y prepara la plantilla.Muestra el formulario.
GET de ediciónSolicita al servicio el registro por su ID.Muestra sus datos o informa de que no existe.
POST con errores de validaciónConsulta BindingResult y prepara los atributos que necesita la vista.Devuelve el mismo formulario, sin guardar.
POST válidoLlama al servicio y añade un mensaje flash cuando procede.Redirige al listado.

La última parte se conoce como Post/Redirect/Get (PRG): después de procesar un formulario correctamente, respondemos con una redirección y el navegador realiza una nueva petición GET. De este modo, al recargar el listado no reenviamos directamente el POST anterior.

En cambio, si hay errores de validación no redirigimos: devolvemos el formulario para conservar el objeto recibido y su BindingResult, que Thymeleaf utiliza al presentar los errores. Ya trabajamos este mecanismo en la UT3 y ahora lo aplicamos a datos persistentes.

consejo

Un método @PostMapping no significa automáticamente «insertar en la base de datos». Lo que hace depende de la operación del servicio que invoque: puede crear, actualizar o eliminar. Por eso distinguimos claramente las rutas y los nombres de los métodos.

4️⃣ Creamos y adaptamos las vistas Thymeleaf​

Necesitamos dos páginas: el formulario, que utilizaremos tanto para crear como para editar, y el listado que ya conocemos, al que añadiremos las acciones. Ambas reutilizarán mi-coleccion.css, que ya incorporamos al primer listado. Por eso conservamos su enlace en <head> al sustituir lista.html y lo añadimos también en formulario.html.

🟩 Un mismo formulario para el alta y la edición​

Creamos el archivo formulario.html en la carpeta templates/videojuegos/:

src/main/resources/templates/videojuegos/formulario.html
<!DOCTYPE html>
<html lang="es" xmlns:th="http://www.thymeleaf.org">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Formulario de videojuego</title>
    <link rel="stylesheet" th:href="@{/css/mi-coleccion.css}">
</head>
<body>
    <h1 th:text="${modoEdicion} ? 'Editar videojuego' : 'Nuevo videojuego'">
        Formulario de videojuego
    </h1>

    <form class="formulario" th:object="${videojuego}"
          th:action="${modoEdicion} ? @{/videojuegos/{id}/editar(id=${idEdicion})} : @{/videojuegos/nuevo}"
          method="post">

        <p>
            <label for="titulo">Título:</label>
            <input type="text" th:field="*{titulo}" maxlength="120">
            <span class="error-campo" th:if="${#fields.hasErrors('titulo')}"
                  th:errors="*{titulo}">Error de título</span>
        </p>

        <p>
            <label for="genero">Género:</label>
            <input type="text" th:field="*{genero}" maxlength="60">
            <span class="error-campo" th:if="${#fields.hasErrors('genero')}"
                  th:errors="*{genero}">Error de género</span>
        </p>

        <p>
            <label for="plataforma">Plataforma:</label>
            <input type="text" th:field="*{plataforma}" maxlength="60">
            <span class="error-campo" th:if="${#fields.hasErrors('plataforma')}"
                  th:errors="*{plataforma}">Error de plataforma</span>
        </p>

        <p>
            <label for="anioLanzamiento">Año de lanzamiento:</label>
            <input type="number" th:field="*{anioLanzamiento}" min="1950">
            <span class="error-campo" th:if="${#fields.hasErrors('anioLanzamiento')}"
                  th:errors="*{anioLanzamiento}">Error de año</span>
        </p>

        <button type="submit"
                th:text="${modoEdicion} ? 'Guardar cambios' : 'Añadir videojuego'">
            Guardar
        </button>
        <a class="boton boton-secundario" th:href="@{/videojuegos}">Cancelar</a>
    </form>
</body>
</html>
en este ejemplo

th:object establece el objeto al que se vincula el formulario, y th:field vincula los controles con sus propiedades. Cuando abrimos la edición, los campos aparecen rellenos con los valores del videojuego existente.

La expresión condicional de th:action elige la ruta de destino: /videojuegos/nuevo para el alta o /videojuegos/{id}/editar para modificar un registro. th:errors presenta los mensajes de validación.

No incluimos un campo id: en las altas lo genera MySQL y en las modificaciones lo obtenemos de la URL. Los atributos HTML maxlength y min ayudan en el navegador, pero la validación del servidor continúa siendo imprescindible.

Sustituimos el contenido de lista.html por esta versión completa:

en este ejemplo

th:href construye el enlace GET que abre el formulario de edición, incluyendo el ID del videojuego. Para eliminar, utilizamos un formulario con method="post" y th:action apuntando a la ruta de eliminación.

La función JavaScript confirm(...) solicita una confirmación antes de enviar el formulario. Es una ayuda para evitar pulsaciones accidentales, no una medida de seguridad del servidor. Cuando abordemos la seguridad web estudiaremos otras protecciones necesarias para las operaciones que modifican datos.

Los mensajes mensaje y error llegan mediante atributos flash después de guardar, editar o eliminar. Las clases CSS .mensaje, .error y .boton les dan un estilo coherente con el resto de la página.

5️⃣ Comprobamos las operaciones y los casos problemáticos​

🟩 Probamos desde el navegador​

Comprobamos que el servicio MySQL de Windows está iniciado y que DB_PASSWORD está configurada en IntelliJ IDEA. Arrancamos Spring Boot y accedemos a:

http://localhost:8080/videojuegos

Primero añadimos un videojuego desde Añadir videojuego. Cuando se guarde, regresaremos al listado y veremos una nueva fila con el identificador generado. Después abrimos Editar, cambiamos su plataforma o su año y comprobamos que el registro conserva el mismo ID. Finalmente, podemos eliminar un videojuego de prueba.

También debemos comprobar los errores: enviar un título vacío, introducir un año inferior a 1950 e intentar abrir una ruta de edición con un ID inexistente. Los dos primeros casos deben mostrar mensajes en el formulario, sin guardar cambios; el último debe redirigir al listado y mostrar un aviso.

🟨 Comprobamos los cambios en MySQL​

No basta con ver los datos en la página. Queremos comprobar que las operaciones han afectado a los registros persistentes. Abrimos PowerShell y entramos en el cliente MySQL, como hicimos al configurar la conexión:

mysql -u coleccion_app -p mi_coleccion

Una vez introducida la contraseña, ejecutamos:

SELECT id, titulo, genero, plataforma, anio_lanzamiento
FROM videojuegos
ORDER BY id;

La consulta debe reflejar los registros que hemos creado, actualizado y eliminado. También podemos detener y volver a arrancar Spring Boot: los datos deben seguir almacenados en MySQL porque no dependen de la memoria de la aplicación.

🟧 Probamos resultados, no solo botones​

Para comprobar que entendemos el funcionamiento del CRUD no basta con pulsar cada opción una vez. Podemos utilizar una pequeña matriz de pruebas que también servirá para futuras aplicaciones:

PruebaResultado esperado en la aplicaciónComprobación en MySQL
Alta con datos válidos.Mensaje de éxito y nueva fila en el listado.Aparece un nuevo ID.
Alta con título vacío.Mensaje de validación en el formulario.No aparece una fila nueva.

🟥 Errores frecuentes​

🟩 El formulario genera un error al crear un videojuego​

Comprobamos que Videojuego tiene un constructor público sin argumentos, que conserva los setters y que @ModelAttribute utiliza el mismo nombre (videojuego) que th:object.

🟨 Los errores de validación no aparecen​

Revisamos que las restricciones de Jakarta Validation estén en la entidad y que BindingResult figure inmediatamente después del parámetro anotado con @Valid. También comprobamos que los nombres de th:field coincidan con las propiedades Java.

🟧 Editar crea otra fila en lugar de modificar la existente​

La operación de edición debe buscar el registro por su ID y modificar ese registro, como hace actualizar() en nuestro servicio. No debemos crear una entidad nueva con ID nulo y guardarla esperando que Hibernate sepa cuál queremos modificar.

🟥 El registro ya no existe cuando intentamos editarlo o borrarlo​

El ID puede no corresponder a ningún videojuego. Por eso buscarPorId(), actualizar() y eliminar() contemplan ese caso. También puede ocurrir que otra persona modifique el mismo videojuego mientras tenemos abierto el formulario: es una situación que tendremos en cuenta al estudiar las transacciones y la concurrencia.

aviso

Estas comprobaciones cubren el funcionamiento básico de nuestra aplicación de aula. Validar formularios no sustituye las restricciones de MySQL ni la gestión de transacciones. Cuando incorporemos relaciones y operaciones compuestas, estudiaremos cómo mantener la integridad ante situaciones más complejas.

6️⃣ Qué debemos haber comprendido​

Al finalizar este apartado deberíamos ser capaces de seguir el recorrido completo de una operación: formulario → controlador → servicio → repositorio → MySQL. También deberíamos distinguir la inserción de una actualización, justificar por qué la edición conserva el ID del registro y explicar qué ocurre cuando un formulario contiene datos inválidos.

🟩 Aplicamos el patrón a otra aplicación​

Imaginemos una pequeña biblioteca con una entidad Libro, que tiene id, titulo, autor y ejemplaresDisponibles. Sin copiar los nombres de MiColección, razonaremos las siguientes decisiones:

  1. ¿Qué rutas GET y POST ofreceríamos para añadir y editar libros? ¿Qué responsabilidad tendría el controlador?
  2. ¿Cómo prepararíamos un formulario de edición que conserve la identidad del libro?
  3. Si una persona envía un número negativo de ejemplares, ¿en qué momento detectaríamos el error y qué debería mostrar Thymeleaf?
  4. ¿Cómo comprobaríamos en MySQL que una eliminación se ha realizado realmente?

Estas comprobaciones son no evaluables y no requieren entrega.

🟨 Estado del proyecto antes de las consultas​

En este momento MiColección tiene una única entidad, Videojuego, cuyos atributos son id, titulo, genero, plataforma (todavía String) y anioLanzamiento. Dispone de un repositorio, un servicio con operaciones CRUD, un controlador MVC, un listado y un formulario de alta y edición con validación. Los registros se guardan en la tabla videojuegos de MySQL.

Por ahora mantenemos plataforma como un texto y conservamos las rutas actuales. El siguiente objetivo será incorporar filtros al listado y ampliar posteriormente la búsqueda con ordenación y paginación.

Antes de continuar

Debemos poder crear, consultar, editar y eliminar videojuegos desde el navegador, ver los mensajes de validación cuando corresponda y comprobar en MySQL que los cambios se conservan. A partir de esta base podremos realizar consultas más específicas sin alterar el CRUD que acabamos de construir.
