2.7. DTO y proyecciones

En MiColección ya sabemos guardar videojuegos en MySQL, consultarlos con diferentes filtros y mostrarlos de cinco en cinco mediante Pageable y Page. En todas esas operaciones hemos trabajado principalmente con objetos de la entidad Videojuego. Es una forma adecuada de empezar, pero no siempre necesitamos utilizar todos los datos de una entidad.

Pensemos en una nueva pantalla que solo muestra el identificador, el título y el género de cada videojuego. Para construirla no necesitamos la plataforma ni el año de lanzamiento. Además, es posible que en otros proyectos una entidad contenga datos internos que no queramos trasladar a todas las pantallas.

En este apartado conoceremos dos herramientas relacionadas: los DTO, que nos permiten preparar objetos con los datos que necesita otra parte de la aplicación, y las proyecciones, que permiten obtener resultados con una estructura distinta de la entidad completa. Partiremos de un DTO muy sencillo y avanzaremos hasta utilizar proyecciones con Spring Data JPA, servicios, paginación y Thymeleaf.

Idea principal

Una entidad JPA representa información persistente que podemos guardar y modificar. Un DTO es un objeto que utilizamos para transportar o presentar ciertos datos. Una proyección es una forma de obtener desde una consulta únicamente una representación de la información que necesitamos.

DTO y proyección no son conceptos opuestos: una consulta puede devolver directamente un DTO. Lo importante es distinguir qué objeto queremos utilizar de cómo lo obtenemos.

1️⃣ ¿Por qué no utilizar siempre las entidades completas?​

🟩 La entidad contiene más información de la que pide una pantalla​

Recordemos una versión simplificada de nuestra entidad:

Fragmento de Videojuego.java
@Entity
public class Videojuego {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String titulo;
    private String genero;
    private String plataforma;
    private int anioLanzamiento;

    // Constructores, getters y setters.
}

En la pantalla de edición sí necesitamos un objeto Videojuego, porque vamos a recuperar y modificar sus propiedades. En cambio, un listado reducido podría limitarse a tres columnas:

IDTítuloGénero
1CelestePlataformas
2Hollow KnightMetroidvania
3HadesAcción

Hasta ahora habríamos llamado a findAll() o a nuestra consulta paginada y después habríamos mostrado solamente algunas propiedades de cada entidad. El resultado es correcto, pero conviene conocer otras posibilidades.

🟨 Tres conceptos que no debemos confundir​

ConceptoQué representaEjemplo en MiColección
Entidad JPAUn objeto del modelo persistente, asociado a una tabla mediante JPA.Videojuego.
DTO (Data Transfer Object)Una clase o record que agrupa datos para otro uso; no tiene por qué ser una entidad.VideojuegoResumenDTO.
ProyecciónEl resultado de consultar determinados datos, sin necesitar necesariamente la entidad completa.VideojuegoResumenView o una consulta que construye un DTO.

No debemos pensar que toda aplicación necesita un DTO para cada entidad o para cada operación. En proyectos pequeños, utilizar la entidad directamente puede ser suficiente. El objetivo es saber elegir, no añadir clases por costumbre.

consejo

Podemos encontrar DTO tanto en aplicaciones MVC con Thymeleaf como en APIs REST. En este apartado los usaremos en una vista HTML. Más adelante, al desarrollar APIs, veremos otra razón importante para utilizarlos: controlar qué datos enviamos al cliente.

2️⃣ Creamos un DTO con un record de Java​

🟩 Un objeto que solo contiene los datos necesarios​

Java permite declarar un DTO mediante una clase convencional con atributos, constructor y métodos de acceso. Para evitar repetir ese código utilizaremos un record, una característica de Java que ya podemos emplear con el JDK del módulo.

Creamos el paquete dto y, dentro de él, el archivo VideojuegoResumenDTO.java:

src/main/java/com/dwes/mi_coleccion/dto/VideojuegoResumenDTO.java
package com.dwes.mi_coleccion.dto;

public record VideojuegoResumenDTO(
        Long id,
        String titulo,
        String genero
) {
}

El record declara tres componentes. Java proporciona automáticamente un constructor, los métodos de acceso id(), titulo() y genero(), y otros métodos habituales. No necesitamos Lombok ni escribir getters y setters.

Por ejemplo, podemos crear un DTO de forma explícita:

Creamos un objeto de resumen
VideojuegoResumenDTO resumen = new VideojuegoResumenDTO(
        3L, "Hades", "Acción"
);

System.out.println(resumen.titulo()); // Hades
en este ejemplo

VideojuegoResumenDTO no tiene @Entity, @Id ni una tabla propia. No se guarda directamente mediante videojuegoRepository.save(resumen), porque el repositorio está preparado para trabajar con entidades Videojuego.

Además, el record es adecuado para representar datos que no necesitamos modificar después de construir el objeto. Si la aplicación necesita cambiar un videojuego, seguimos utilizando la entidad correspondiente y los métodos del servicio.

🟨 Convertimos una entidad en un DTO​

La forma más fácil de entender un DTO es construirlo a partir de una entidad que ya hemos recuperado:

Transformación manual de una entidad
Videojuego juego = repositorio.findById(3L)
        .orElseThrow();

VideojuegoResumenDTO resumen = new VideojuegoResumenDTO(
        juego.getId(),
        juego.getTitulo(),
        juego.getGenero()
);

Esta transformación puede realizarse en la capa de servicios, porque el controlador no debería encargarse de decidir cómo se obtiene la información ni de repetir conversiones.

La ventaja es que el resultado contiene solo lo que queremos utilizar en la vista. Pero hay un detalle importante: en este ejemplo ya hemos recuperado antes la entidad completa. Convertirla después en DTO no hace que MySQL haya leído menos columnas.

🟧 Transformamos una página completa mediante Page.map()​

Con la paginación sucede algo parecido. Podemos recorrer los objetos de una Page<Videojuego> y convertirlos en DTO sin perder los datos necesarios para construir los botones de navegación.

Dentro de VideojuegoService, podemos incorporar este método como ejemplo independiente de nuestro buscador habitual:

Método de VideojuegoService.java: conversión después de consultar
public Page<VideojuegoResumenDTO> obtenerResumenesDesdeEntidades(int numeroPagina) {
    Pageable paginacion = PageRequest.of(
            Math.max(0, numeroPagina),
            5,
            Sort.by("titulo").ascending()
                    .and(Sort.by("id").ascending())
    );

    Page<Videojuego> paginaEntidades = repositorio.findAll(paginacion);

    return paginaEntidades.map(juego -> new VideojuegoResumenDTO(
            juego.getId(),
            juego.getTitulo(),
            juego.getGenero()
    ));
}

Este fragmento utiliza las importaciones Page, PageRequest, Pageable y Sort que ya conocemos, y añade com.dwes.mi_coleccion.dto.VideojuegoResumenDTO. No necesitamos modificar los métodos CRUD ni el buscador actual.

en este ejemplo

Page.map() aplica una transformación a cada elemento de la página, manteniendo el número de página, el tamaño y la información sobre el total de resultados. El tipo cambia de Page<Videojuego> a Page<VideojuegoResumenDTO>.

No es una nueva consulta a MySQL. En este caso hemos consultado entidades completas y las hemos transformado después. Esta distinción nos ayudará a comprender la utilidad de las proyecciones.

3️⃣ Utilizamos proyecciones de interfaz en Spring Data JPA​

🟩 Pedimos directamente una representación parcial​

Hasta ahora, la conversión la realiza nuestro servicio una vez recuperados los videojuegos. Con Spring Data JPA podemos dar otro paso: declarar un método de repositorio cuyo resultado no sea Videojuego, sino una proyección.

Una forma sencilla de hacerlo es mediante una interfaz. Creamos el paquete proyecciones y el archivo siguiente:

src/main/java/com/dwes/mi_coleccion/proyecciones/VideojuegoResumenView.java
package com.dwes.mi_coleccion.proyecciones;

public interface VideojuegoResumenView {

    Long getId();
    String getTitulo();
    String getGenero();
}

La interfaz no implementa ninguno de los métodos y tampoco lleva @Entity. Los nombres de sus métodos deben corresponder con propiedades de Videojuego: getTitulo() se refiere a titulo, y no al nombre de una columna de MySQL.

🟨 Declaramos la consulta en el repositorio existente​

Abrimos VideojuegoRepository.java y añadimos este método a los que ya contiene:

Nuevo método en VideojuegoRepository.java
Page<VideojuegoResumenView> findProjectedByGeneroIgnoreCase(
        String genero,
        Pageable pageable
);

Necesitamos importar VideojuegoResumenView, Page y Pageable, si todavía no lo estaban. El repositorio sigue extendiendo JpaRepository<Videojuego, Long> y conserva el método buscarConFiltros(...) utilizado por el listado principal.

en este ejemplo
  • find...ByGeneroIgnoreCase expresa una búsqueda por la propiedad genero sin distinguir mayúsculas.
  • Projected es una palabra descriptiva antes de By. Nos permite distinguir este método de otro que ya pudiera llamarse findByGeneroIgnoreCase(...).
  • Pageable indica qué página queremos recuperar y con qué ordenación.
  • Page<VideojuegoResumenView> indica que cada resultado tendrá los métodos de la interfaz de proyección.

Spring Data JPA crea la implementación necesaria. Nosotros no programamos una clase que implemente VideojuegoResumenView.

En un servicio podríamos utilizar el método de esta manera:

Consultamos una página de proyecciones
Pageable paginacion = PageRequest.of(
        0, 5, Sort.by("titulo").ascending()
);

Page<VideojuegoResumenView> resultados =
        repositorio.findProjectedByGeneroIgnoreCase("Plataformas", paginacion);

for (VideojuegoResumenView juego : resultados.getContent()) {
    System.out.println(juego.getTitulo() + " - " + juego.getGenero());
}

En una proyección sencilla como esta, Spring Data JPA puede preparar una consulta que seleccione las propiedades que hemos declarado, en lugar de recuperar necesariamente todas las columnas de Videojuego.

aviso

La proyección no es una entidad editable. No podemos cambiar su título y esperar que JPA lo guarde, ni enviarla a save() como si fuera un Videojuego.

Tampoco debemos interpretar que todas las proyecciones garantizan consultar menos datos: si incorporamos relaciones anidadas o expresiones más complejas, las consultas generadas pueden necesitar información adicional. Aquí trabajamos solo con propiedades directas de Videojuego.

🟧 Un resultado de proyección también puede transformarse​

Las proyecciones y los DTO pueden trabajar juntos. Por ejemplo, el servicio puede recuperar una página de proyecciones y transformarla después en una página de VideojuegoResumenDTO:

De una proyección de interfaz a un DTO
Page<VideojuegoResumenDTO> paginaDTO = resultados.map(v ->
        new VideojuegoResumenDTO(
                v.getId(),
                v.getTitulo(),
                v.getGenero()
        )
);

La consulta sigue devolviendo solo las propiedades de la proyección sencilla y el servicio prepara el tipo de objeto que necesita la vista. Esta combinación será especialmente útil en la actividad de seguimiento de incidencias, donde un DTO incorporará un dato calculado que no existe como columna de MySQL.

4️⃣ Devolvemos un DTO directamente desde una consulta JPQL​

🟩 Otra posibilidad: proyección basada en record​

No siempre queremos utilizar una interfaz. También podemos indicar a JPA que construya directamente objetos VideojuegoResumenDTO con los valores seleccionados por una consulta.

Para ello utilizamos una expresión constructora SELECT new ... de JPQL. Aprovechamos el mismo record que ya habíamos definido; no es necesario crear un segundo DTO.

Añadimos otro método a VideojuegoRepository, sin eliminar los anteriores:

Nuevo método de VideojuegoRepository.java: proyección a DTO
@Query("""
    SELECT new com.dwes.mi_coleccion.dto.VideojuegoResumenDTO(
        v.id, v.titulo, v.genero
    )
    FROM Videojuego v
    WHERE (:genero = '' OR LOWER(v.genero) = LOWER(:genero))
    """)
Page<VideojuegoResumenDTO> buscarResumenes(
        @Param("genero") String genero,
        Pageable pageable
);

Este método necesita importar VideojuegoResumenDTO, @Query y @Param, además de Page y Pageable. Si usamos exactamente la organización de paquetes de estos apuntes, el nombre completo del DTO será com.dwes.mi_coleccion.dto.VideojuegoResumenDTO. Si el paquete de nuestro proyecto es diferente, hay que adaptar esa ruta.

en este ejemplo

SELECT new ...VideojuegoResumenDTO(v.id, v.titulo, v.genero) construye un objeto mediante el constructor de nuestro record. El orden y los tipos de los valores seleccionados deben coincidir con los componentes declarados en el DTO.

FROM Videojuego v utiliza el nombre de la entidad Java, no el de la tabla SQL. La condición permite filtrar por género o, si el parámetro está vacío, mostrar todos los géneros.

Como el método devuelve un Page<VideojuegoResumenDTO>, Spring Data JPA necesita conocer el total de resultados para calcular las páginas disponibles. En consultas sencillas como esta, normalmente genera automáticamente el recuento, por lo que no necesitamos escribir otra consulta.

🟨 ¿En qué se diferencia de transformar entidades manualmente?​

Tenemos ahora dos recorridos distintos:

  • Primero entidades y después DTO: findAll(pageable) devuelve Page<Videojuego>; el servicio utiliza map() para crear los resúmenes. La consulta ya ha recuperado los datos de la entidad.
  • Proyección directa al DTO: buscarResumenes(genero, pageable) ejecuta una consulta JPQL que selecciona id, titulo y genero y construye directamente Page<VideojuegoResumenDTO>.

Ambas soluciones son válidas. No siempre necesitamos optimizar las consultas de una aplicación pequeña, pero sí es importante entender que el lugar donde construimos el DTO afecta a los datos que recupera la consulta.

5️⃣ Integramos un listado de DTO en MiColección​

🟩 El servicio prepara la consulta y la paginación​

Vamos a añadir una pantalla de resumen independiente para probar esta última consulta, sin sustituir el listado principal /videojuegos ni alterar el CRUD que ya tenemos.

En VideojuegoService añadimos este método:

Método nuevo en VideojuegoService.java
public Page<VideojuegoResumenDTO> buscarResumenes(String genero, int numeroPagina) {
    String generoBuscado = genero == null ? "" : genero.trim();

    Sort ordenacion = Sort.by("titulo").ascending()
            .and(Sort.by("id").ascending());

    Pageable paginacion = PageRequest.of(
            Math.max(0, numeroPagina),
            5,
            ordenacion
    );

    return repositorio.buscarResumenes(generoBuscado, paginacion);
}

Es la misma organización que ya conocemos: el servicio interpreta el filtro, fija las opciones de ordenación y crea el Pageable. El repositorio ejecuta la consulta y devuelve una página de DTO.

🟨 El controlador prepara el Model​

En nuestro VideojuegoController, que ya tiene @RequestMapping("/videojuegos"), añadimos este método:

Método adicional de VideojuegoController.java
@GetMapping("/resumen")
public String resumen(
        @RequestParam(defaultValue = "") String genero,
        @RequestParam(defaultValue = "0") int pagina,
        Model model) {

    Page<VideojuegoResumenDTO> resultado =
            servicio.buscarResumenes(genero, pagina);

    model.addAttribute("videojuegos", resultado.getContent());
    model.addAttribute("pagina", resultado);
    model.addAttribute("genero", genero);

    return "videojuegos/resumen";
}

La ruta resultante es GET /videojuegos/resumen. El controlador no realiza consultas a MySQL ni necesita conocer la expresión JPQL: se limita a recibir parámetros y proporcionar datos a la vista.

🟧 Thymeleaf muestra los resúmenes y conserva los filtros​

Creamos src/main/resources/templates/videojuegos/resumen.html. Para no repetir todo el diseño de MiColección, aquí mostramos el contenido esencial de la página:

templates/videojuegos/resumen.html

en este ejemplo

La tabla recorre objetos VideojuegoResumenDTO, no entidades Videojuego. Por eso muestra sus componentes mediante los métodos del record: id(), titulo() y genero().

El formulario no envía ningún número de página y, por tanto, una nueva búsqueda comienza en la página 0. Los enlaces Anterior y Siguiente conservan el parámetro genero, igual que hicimos en el buscador principal de MiColección.

Podemos abrir http://localhost:8080/videojuegos/resumen, comprobar el resultado, aplicar un género y cambiar de página. La ruta /videojuegos continúa utilizando su consulta original y los formularios CRUD permanecen intactos.

6️⃣ ¿Cuándo conviene utilizar cada solución?​

🟩 Elegimos según la necesidad, no por costumbre​

NecesidadSolución razonableMotivo
Dar de alta o editar un videojuego.Entidad JPA.Queremos guardar cambios persistentes.
Mostrar tres propiedades después de haber recuperado una entidad.DTO construido en el servicio.Permite preparar datos para una pantalla.
Consultar una lista con unas pocas propiedades.Proyección de interfaz.Define de forma sencilla los datos que necesitamos.
Obtener directamente un tipo record desde una consulta.Proyección a DTO mediante JPQL.La consulta construye el resultado sin recuperar antes la entidad completa.
Presentar datos calculados, por ejemplo la antigüedad de una incidencia.Proyección y transformación posterior a DTO.La consulta recupera lo necesario y el servicio prepara el dato derivado.

En proyectos reales pueden utilizarse distintas soluciones simultáneamente. Es habitual conservar entidades para las operaciones de persistencia y disponer de DTO específicos para ciertos listados, informes o respuestas. No hace falta crear un DTO para cada entidad ni una proyección para cada método del repositorio.

🟨 Errores frecuentes​

🟩 Confundir un DTO con una entidad​

Un record VideojuegoResumenDTO no representa una nueva tabla y no se puede guardar mediante JpaRepository<Videojuego, Long> como si fuera un Videojuego.

🟨 Pensar que Page.map() consulta menos columnas​

map() transforma los elementos después de ejecutar la consulta. Si el repositorio recuperó entidades completas, crear DTO a continuación no reduce las columnas consultadas.

🟧 Escribir nombres de columnas SQL en los métodos derivados​

Para métodos como findProjectedByGeneroIgnoreCase(...), Spring Data JPA utiliza propiedades Java. En nuestro modelo escribimos genero y anioLanzamiento, no los nombres de las columnas físicas.

🟥 Olvidar el nombre completo del DTO en SELECT new​

La expresión constructora JPQL utiliza el nombre completo de la clase o record y debe recibir los argumentos en el orden y con los tipos adecuados.

🟪 Creer que una proyección siempre optimiza cualquier consulta​

Las proyecciones sencillas sobre propiedades directas pueden reducir la selección de datos. Sin embargo, las asociaciones entre entidades y las consultas complejas requieren valorar qué SQL se ejecuta realmente. Lo estudiaremos con más detalle al trabajar las relaciones JPA.

  1. Tenemos una entidad Videojuego completa y queremos mostrar únicamente su título y género. ¿Cómo construiríamos un DTO?
  2. Si convertimos una Page<Videojuego> en Page<VideojuegoResumenDTO> mediante Page.map(), ¿qué sucede con los datos de paginación? ¿Y con los datos que ya había consultado MySQL?
  3. ¿Qué debemos añadir a VideojuegoRepository para obtener resultados de una proyección de interfaz?
