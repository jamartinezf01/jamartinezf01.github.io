2.4. Persistencia de imágenes en aplicaciones web

En MiColección ya podemos crear y editar videojuegos. Ahora queremos que cada videojuego tenga una portada, elegida en el mismo formulario donde escribimos su título, género, plataforma y año, y que siga disponible cuando reiniciemos la aplicación.

Idea principal

La imagen no se guarda en MySQL. El archivo se guarda en una carpeta del servidor y en MySQL solo guardamos su nombre, como un texto más de la entidad Videojuego.

DóndeQué se guardaEjemplo
Carpeta del servidorEl archivo de la imagen.C:/datos/mi-coleccion/portadas/79dff143-....jpg
Columna imagen_nombre de MySQLSolo el nombre del archivo.79dff143-....jpg

Si se pierde una de las dos piezas, la portada deja de mostrarse.

1️⃣ El recorrido completo en tres pasos​

Antes de escribir código, veamos qué tiene que ocurrir:

  1. Enviar: el formulario del videojuego envía los datos de texto y, si se ha elegido, el archivo de la imagen.
  2. Guardar: el servidor comprueba la imagen, la escribe en la carpeta y guarda el videojuego en MySQL con el nombre del archivo.
  3. Mostrar: las páginas incluyen una etiqueta <img> que apunta a ese archivo.

Partimos del CRUD del apartado anterior. Estas son las piezas que crearemos o modificaremos:

PiezaCambio
application.propertiesIndicamos en qué carpeta se guardan las portadas.
Videojuego.javaAñadimos la propiedad imagenNombre.
formulario.htmlAñadimos el campo de archivo al formulario existente.
PortadaService.javaNuevo. Comprueba la imagen, la guarda en la carpeta y la borra.
VideojuegoService.javacrear(), actualizar() y eliminar() también gestionan la portada.

Cómo leer el código de este apartado

En los archivos que ya existen mostramos solo las modificaciones, indicando qué hay que sustituir o añadir. Debajo de cada uno hay un desplegable con el archivo completo, por si queremos comparar o sustituirlo entero.

En los fragmentos no aparecen los import: IntelliJ IDEA los propone con Alt + Enter. Las clases nuevas sí se muestran completas.

¿Y guardar la imagen dentro de MySQL?

También es posible, con una columna de tipo BLOB. Evita tener una carpeta aparte, pero hace crecer mucho la base de datos. En esta unidad utilizaremos la carpeta, que es la opción más habitual.

2️⃣ Preparamos la carpeta y la columna​

🟩 La carpeta de las portadas​

En application.properties conservamos la configuración de MySQL y añadimos:

src/main/resources/application.properties
app.portadas.directorio=C:/datos/mi-coleccion/portadas
spring.servlet.multipart.max-file-size=1MB
spring.servlet.multipart.max-request-size=2MB
  • app.portadas.directorio es una propiedad inventada por nosotros: la leeremos desde Java con @Value.
  • Las dos últimas limitan el tamaño de los archivos que Spring acepta.
¿Por qué no en static/?

No guardaremos las portadas en src/main/resources/static/. Esa carpeta contiene los archivos del proyecto (como mi-coleccion.css), no los que suben las personas usuarias mientras la aplicación funciona. Además, al desplegar la aplicación esa carpeta queda empaquetada y no se puede escribir en ella.

🟨 La columna en la entidad​

En Videojuego.java añadimos esta propiedad con su getter y su setter, sin tocar el resto de la clase:

Añadir en modelo/Videojuego.java
@Column(name = "imagen_nombre", length = 50)
private String imagenNombre;

public String getImagenNombre() {
    return imagenNombre;
}

public void setImagenNombre(String imagenNombre) {
    this.imagenNombre = imagenNombre;
}

Es un String, no una imagen. Si el videojuego no tiene portada, valdrá null. Como tenemos ddl-auto=update, Hibernate añadirá la columna al arrancar.

No añadimos ninguna anotación de validación: la portada es opcional.

en este ejemplo

enctype="multipart/form-data" hace que el navegador envíe el contenido del archivo junto con los campos de texto. Sin él, solo llegaría el nombre del archivo. Los campos de texto siguen funcionando exactamente igual.

<input type="file" name="portada"> muestra el botón para elegir la imagen. No utilizamos th:field, porque el archivo no es una propiedad de Videojuego: lo recibiremos en el controlador como un parámetro aparte, llamado portada. Lo que sí es propiedad de la entidad es imagenNombre, y ese dato no lo escribe la persona usuaria, lo genera el servidor.

errorPortada es un atributo que añadirá el controlador cuando el archivo no sea una imagen válida, igual que th:errors muestra los errores de los demás campos.

El atributo accept solo filtra los archivos que ofrece el navegador; no impide enviar otro tipo de archivo. Por eso el servidor volverá a comprobarlo.

La etiqueta <img> apunta a /portadas/nombre-del-archivo. En el paso 3 veremos cómo hacer que esa dirección funcione.

Si hay errores de validación, hay que volver a elegir la imagen

Cuando el formulario se muestra de nuevo con errores (por ejemplo, título vacío), los campos de texto conservan lo que se escribió, pero el campo de archivo aparece vacío. Por seguridad, los navegadores no permiten que una página rellene un <input type="file">. Es un comportamiento normal en cualquier aplicación web.

4️⃣ Paso 2: guardar el archivo y el videojuego​

Repartimos el trabajo en dos servicios:

  • PortadaService solo sabe de archivos: comprobar que es una imagen, guardarla en la carpeta y borrarla. No sabe nada de videojuegos.
  • VideojuegoService coordina la operación completa: utiliza PortadaService para el archivo y el repositorio para MySQL.

🟩 Nuevo servicio: PortadaService​

src/main/java/com/dwes/mi_coleccion/servicios/PortadaService.java
package com.dwes.mi_coleccion.servicios;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;
import org.springframework.web.multipart.MultipartFile;

import javax.imageio.ImageIO;
import java.io.IOException;
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.UUID;

@Service
public class PortadaService {

    private final Path carpeta;

    public PortadaService(@Value("${app.portadas.directorio}") String directorio) {
        this.carpeta = Path.of(directorio).toAbsolutePath();
    }

    /** Comprueba la imagen, la guarda en la carpeta y devuelve el nombre generado. */
    public String guardar(MultipartFile archivo) {
        String extension = comprobarImagen(archivo);
        String nombre = UUID.randomUUID() + "." + extension;

        try {
            Files.createDirectories(carpeta);
            archivo.transferTo(carpeta.resolve(nombre));
        } catch (IOException e) {
            throw new IllegalStateException("No se pudo guardar la imagen en el servidor.", e);
        }
        return nombre;
    }

    /** Borra el archivo de una portada que ya no se utiliza. */
    public void borrar(String nombre) {
        try {
            Files.deleteIfExists(carpeta.resolve(nombre));
        } catch (IOException e) {
            // El videojuego ya está guardado: un archivo sin borrar no impide la operación.
            System.err.println("No se pudo borrar la portada " + nombre);
        }
    }

    private String comprobarImagen(MultipartFile archivo) {
        String tipo = archivo.getContentType();
        if (!"image/jpeg".equals(tipo) && !"image/png".equals(tipo)) {
            throw new IllegalArgumentException("Solo se admiten imágenes JPG o PNG.");
        }

        try (InputStream entrada = archivo.getInputStream()) {
            if (ImageIO.read(entrada) == null) {
                throw new IllegalArgumentException("El archivo no es una imagen válida.");
            }
        } catch (IOException e) {
            throw new IllegalArgumentException("El archivo no es una imagen válida.");
        }

        return "image/png".equals(tipo) ? "png" : "jpg";
    }
}

Al pulsar Alt + Enter, IntelliJ IDEA puede ofrecer varias clases con el mismo nombre, porque nuestro proyecto incluye Spring, JPA e Hibernate. Si elegimos la equivocada, aparecen errores que despistan, como que no encuentra el método Path.of(...). En este apartado, las correctas son:

en este ejemplo

MultipartFile es el tipo con el que Spring nos entrega un archivo recibido desde un formulario.

Comprobar la imagen (comprobarImagen). Hacemos dos comprobaciones:

  • getContentType() indica qué tipo de archivo dice el navegador que envía (image/jpeg, image/png...).
  • ImageIO.read(...) intenta abrir el archivo como imagen. Si devuelve null, no es una imagen, aunque su nombre termine en .jpg.

Guardar el archivo (guardar):

  • UUID.randomUUID() genera un nombre único, como 79dff143-49b6-43db-8237-5a610f0fca1d. Así dos portadas llamadas portada.jpg no se sobrescriben, y nadie puede elegir el nombre con que se guarda un archivo en nuestro servidor.
  • Files.createDirectories() crea la carpeta si todavía no existe.
  • transferTo() copia el archivo recibido a la ruta indicada.
  • El método devuelve el nombre generado, que es lo que guardaremos en MySQL.

Los errores. Si el archivo no es válido lanzamos IllegalArgumentException; si falla el disco, IllegalStateException. Las dos llevan un mensaje que el controlador podrá mostrar en el formulario.

Para una validación más completa: la cabecera del archivo

El tipo que devuelve getContentType() lo declara el navegador y se puede falsificar. La forma más fiable de saber qué es un archivo es examinar su cabecera: los primeros bytes, conocidos como firma o número mágico, que identifican cada formato. Por ejemplo, todo archivo JPEG empieza por los bytes FF D8 FF y todo PNG por 89 50 4E 47 0D 0A 1A 0A.

ImageIO.read() ya lee esa cabecera para decidir cómo abrir la imagen, por lo que rechaza los archivos que no son imágenes. Pero no comprueba que el formato real coincida con el declarado: un GIF enviado como image/png pasaría nuestra validación. Para simplificar no lo hemos incluido; en una aplicación real conviene comprobar la firma del archivo, además de su tamaño y extensión.

Más información: OWASP: recomendaciones para la subida de archivos y lista de firmas de archivo.

2. Los métodos de escritura gestionan la portada. Sustituimos crear(), actualizar() y eliminar() por estos, y añadimos el método privado hayArchivo(). Las líneas nuevas van marcadas con // NUEVO:

VideojuegoService.java: sustituir crear(), actualizar() y eliminar(), y añadir hayArchivo()
public Videojuego crear(Videojuego datos, MultipartFile portada) {
    Videojuego nuevo = new Videojuego(
            datos.getTitulo(),
            datos.getGenero(),
            datos.getPlataforma(),
            datos.getAnioLanzamiento()
    );

    // NUEVO: si se ha elegido una imagen, la guardamos y anotamos su nombre
    if (hayArchivo(portada)) {
        nuevo.setImagenNombre(portadas.guardar(portada));
    }

    return repositorio.save(nuevo);
}

public boolean actualizar(Long id, Videojuego datos, MultipartFile portada) {
    Optional<Videojuego> encontrado = repositorio.findById(id);
    if (encontrado.isEmpty()) {
        return false;
    }

    Videojuego existente = encontrado.get();
    existente.setTitulo(datos.getTitulo());
    existente.setGenero(datos.getGenero());
    existente.setPlataforma(datos.getPlataforma());
    existente.setAnioLanzamiento(datos.getAnioLanzamiento());

    // NUEVO: si se ha elegido otra imagen, sustituye a la anterior
    String portadaAnterior = null;
    if (hayArchivo(portada)) {
        portadaAnterior = existente.getImagenNombre();
        existente.setImagenNombre(portadas.guardar(portada));
    }

    repositorio.save(existente);

    // NUEVO: cuando MySQL ya tiene el nombre nuevo, borramos el archivo antiguo
    if (portadaAnterior != null) {
        portadas.borrar(portadaAnterior);
    }
    return true;
}

public boolean eliminar(Long id) {
    Optional<Videojuego> encontrado = repositorio.findById(id);
    if (encontrado.isEmpty()) {
        return false;
    }

    Videojuego juego = encontrado.get();
    repositorio.delete(juego);

    // NUEVO: si tenía portada, borramos también su archivo
    if (juego.getImagenNombre() != null) {
        portadas.borrar(juego.getImagenNombre());
    }
    return true;
}

en este ejemplo

VideojuegoService recibe PortadaService en su constructor, igual que recibe el repositorio. Es la misma inyección de dependencias que ya conocemos: un servicio puede utilizar otros servicios.

El orden importa. En crear() y actualizar():

  1. Primero guardamos la imagen. Si no es válida, portadas.guardar() lanza una excepción y no llegamos a repositorio.save(): el videojuego no se crea ni se modifica.
  2. Después guardamos en MySQL el videojuego con el nombre del archivo.
  3. Por último, en la edición, borramos el archivo antiguo. Lo hacemos al final para no quedarnos sin ninguna portada si algo falla antes.

La portada es opcional. hayArchivo() comprueba si se ha elegido un archivo. Si no, en el alta el videojuego queda sin portada y en la edición conserva la que tenía.

¿Por qué no se puede modificar imagenNombre desde el formulario? Porque, igual que en el apartado anterior, copiamos solo los campos permitidos (título, género, plataforma y año). Aunque alguien añadiera a mano un campo imagenNombre al formulario, nuestro servicio lo ignoraría. El nombre del archivo solo lo asigna PortadaService.

🟧 Adaptamos VideojuegoController​

Las rutas de alta y edición reciben ahora un parámetro más: el archivo. En VideojuegoController.java sustituimos los métodos crear() y actualizar() (los de @PostMapping) y añadimos al final el método privado volverAEdicion(). El resto de métodos no cambia.

VideojuegoController.java: sustituir crear() y actualizar(), y añadir volverAEdicion()
@PostMapping("/nuevo")
public String crear(
        @Valid @ModelAttribute("videojuego") Videojuego videojuego,
        BindingResult errores,
        @RequestParam(value = "portada", required = false) MultipartFile portada, // NUEVO
        Model model,
        RedirectAttributes redirect) {

    if (errores.hasErrors()) {
        model.addAttribute("modoEdicion", false);
        return "videojuegos/formulario";
    }

    // NUEVO: si la imagen no es válida, volvemos al formulario con el error
    try {
        servicio.crear(videojuego, portada);
    } catch (IllegalArgumentException | IllegalStateException e) {
        model.addAttribute("errorPortada", e.getMessage());
        model.addAttribute("modoEdicion", false);
        return "videojuegos/formulario";
    }

    redirect.addFlashAttribute("mensaje", "Videojuego añadido correctamente.");
    return "redirect:/videojuegos";
}

@PostMapping("/{id}/editar")
public String actualizar(
        @PathVariable Long id,
        @Valid @ModelAttribute("videojuego") Videojuego videojuego,
        BindingResult errores,
        @RequestParam(value = "portada", required = false) MultipartFile portada, // NUEVO
        Model model,
        RedirectAttributes redirect) {

    if (errores.hasErrors()) {
        return volverAEdicion(id, videojuego, model);
    }

    // NUEVO: si la imagen no es válida, volvemos al formulario con el error
    try {
        if (!servicio.actualizar(id, videojuego, portada)) {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
            return "redirect:/videojuegos";
        }
    } catch (IllegalArgumentException | IllegalStateException e) {
        model.addAttribute("errorPortada", e.getMessage());
        return volverAEdicion(id, videojuego, model);
    }

    redirect.addFlashAttribute("mensaje", "Videojuego actualizado correctamente.");
    return "redirect:/videojuegos";
}

// NUEVO: vuelve a mostrar el formulario de edición, conservando la portada actual
private String volverAEdicion(Long id, Videojuego videojuego, Model model) {
    servicio.buscarPorId(id)
            .ifPresent(guardado -> videojuego.setImagenNombre(guardado.getImagenNombre()));
    model.addAttribute("modoEdicion", true);
    model.addAttribute("idEdicion", id);
    return "videojuegos/formulario";
}

src/main/java/com/dwes/mi_coleccion/controladores/VideojuegoController.java
package com.dwes.mi_coleccion.controladores;

import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.servicios.VideojuegoService;
import jakarta.validation.Valid;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.multipart.MultipartFile;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

import java.util.Optional;

@Controller
@RequestMapping("/videojuegos")
public class VideojuegoController {

    private final VideojuegoService servicio;

    public VideojuegoController(VideojuegoService servicio) {
        this.servicio = servicio;
    }

    @GetMapping
    public String listar(Model model) {
        model.addAttribute("videojuegos", servicio.listarVideojuegos());
        model.addAttribute("total", servicio.contarVideojuegos());
        return "videojuegos/lista";
    }

    @GetMapping("/nuevo")
    public String mostrarNuevo(Model model) {
        model.addAttribute("videojuego", new Videojuego());
        model.addAttribute("modoEdicion", false);
        return "videojuegos/formulario";
    }

    @PostMapping("/nuevo")
    public String crear(
            @Valid @ModelAttribute("videojuego") Videojuego videojuego,
            BindingResult errores,
            @RequestParam(value = "portada", required = false) MultipartFile portada,
            Model model,
            RedirectAttributes redirect) {

        if (errores.hasErrors()) {
            model.addAttribute("modoEdicion", false);
            return "videojuegos/formulario";
        }

        try {
            servicio.crear(videojuego, portada);
        } catch (IllegalArgumentException | IllegalStateException e) {
            model.addAttribute("errorPortada", e.getMessage());
            model.addAttribute("modoEdicion", false);
            return "videojuegos/formulario";
        }

        redirect.addFlashAttribute("mensaje", "Videojuego añadido correctamente.");
        return "redirect:/videojuegos";
    }

    @GetMapping("/{id}/editar")
    public String mostrarEditar(
            @PathVariable Long id,
            Model model,
            RedirectAttributes redirect) {

        Optional<Videojuego> encontrado = servicio.buscarPorId(id);
        if (encontrado.isEmpty()) {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
            return "redirect:/videojuegos";
        }

        model.addAttribute("videojuego", encontrado.get());
        model.addAttribute("modoEdicion", true);
        model.addAttribute("idEdicion", id);
        return "videojuegos/formulario";
    }

    @PostMapping("/{id}/editar")
    public String actualizar(
            @PathVariable Long id,
            @Valid @ModelAttribute("videojuego") Videojuego videojuego,
            BindingResult errores,
            @RequestParam(value = "portada", required = false) MultipartFile portada,
            Model model,
            RedirectAttributes redirect) {

        if (errores.hasErrors()) {
            return volverAEdicion(id, videojuego, model);
        }

        try {
            if (!servicio.actualizar(id, videojuego, portada)) {
                redirect.addFlashAttribute("error", "El videojuego no existe.");
                return "redirect:/videojuegos";
            }
        } catch (IllegalArgumentException | IllegalStateException e) {
            model.addAttribute("errorPortada", e.getMessage());
            return volverAEdicion(id, videojuego, model);
        }

        redirect.addFlashAttribute("mensaje", "Videojuego actualizado correctamente.");
        return "redirect:/videojuegos";
    }

    @PostMapping("/{id}/eliminar")
    public String eliminar(@PathVariable Long id, RedirectAttributes redirect) {
        if (servicio.eliminar(id)) {
            redirect.addFlashAttribute("mensaje", "Videojuego eliminado.");
        } else {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
        }
        return "redirect:/videojuegos";
    }

    private String volverAEdicion(Long id, Videojuego videojuego, Model model) {
        servicio.buscarPorId(id)
                .ifPresent(guardado -> videojuego.setImagenNombre(guardado.getImagenNombre()));
        model.addAttribute("modoEdicion", true);
        model.addAttribute("idEdicion", id);
        return "videojuegos/formulario";
    }
}
en este ejemplo

@RequestParam("portada") MultipartFile portada recoge el archivo del campo <input type="file" name="portada">. El nombre debe coincidir. Con required = false indicamos que puede no llegar ningún archivo.

BindingResult sigue inmediatamente después del objeto con @Valid. El parámetro del archivo va detrás; si lo pusiéramos entre ambos, la validación dejaría de funcionar como esperamos.

Dos tipos de error, dos respuestas:

  • Errores de los campos de texto: BindingResult los detecta y volvemos al formulario, como ya hacíamos.
  • Errores de la imagen: el servicio lanza una excepción con un mensaje; lo guardamos en errorPortada y volvemos al formulario. El videojuego no se ha guardado y los datos escritos se conservan.

volverAEdicion() evita repetir código y resuelve un detalle: el objeto videojuego que llega del formulario no trae imagenNombre, porque ese dato no se envía. Lo recuperamos de MySQL para que, al volver a mostrar el formulario, siga viéndose la portada actual.

La eliminación no cambia en el controlador: es el servicio quien ahora borra también el archivo.

Si el archivo supera 1 MB

Spring lo rechaza antes de llegar a nuestro código, por la propiedad max-file-size, y muestra una página de error. Es el comportamiento esperado en esta práctica.

5️⃣ Paso 3: mostrar la imagen en el navegador​

🟩 Publicamos la carpeta como si fuera static/​

Ya conocemos un caso parecido: el archivo static/css/mi-coleccion.css del proyecto está disponible en la dirección /css/mi-coleccion.css. Spring sirve automáticamente los archivos de static/.

Queremos lo mismo con nuestra carpeta: que el archivo C:/datos/mi-coleccion/portadas/abc.jpg esté disponible en la dirección /portadas/abc.jpg. Para ello creamos un paquete config y esta clase:

src/main/java/com/dwes/mi_coleccion/config/PortadasConfig.java
package com.dwes.mi_coleccion.config;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.ResourceHandlerRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class PortadasConfig implements WebMvcConfigurer {

    private final String directorio;

    public PortadasConfig(@Value("${app.portadas.directorio}") String directorio) {
        this.directorio = directorio;
    }

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/portadas/**")
                .addResourceLocations("file:" + directorio + "/");
    }
}
en este ejemplo
  • @Configuration indica que la clase contiene configuración de Spring.
  • addResourceHandler("/portadas/**") representa las direcciones que empiezan por /portadas/.
  • addResourceLocations("file:...") indica en qué carpeta del disco buscar esos archivos. El prefijo file: significa «carpeta del sistema de archivos».

Es decir: cuando el navegador pida /portadas/abc.jpg, Spring devolverá el archivo abc.jpg de nuestra carpeta. No necesitamos programar ningún método en un controlador para mostrar las imágenes.

Con esto, la etiqueta <img> del formulario ya funciona:

<img th:src="@{/portadas/{nombre}(nombre=${videojuego.imagenNombre})}" ...>

Thymeleaf genera, por ejemplo, <img src="/portadas/79dff143-....jpg">, y el navegador pide ese archivo a Spring.

Utilizamos la misma expresión que en el formulario: @{/portadas/{nombre}(...)} construye la dirección del archivo a partir del nombre guardado en MySQL.

Con width, height y object-fit: cover todas las miniaturas tienen el mismo tamaño aunque las imágenes originales sean de proporciones distintas: la imagen se recorta para llenar el recuadro sin deformarse. Si el videojuego no tiene portada, mostramos un guion.

La miniatura es la imagen original reducida por el navegador, no un archivo más pequeño. Para una práctica es suficiente; en una aplicación con muchas imágenes convendría generar miniaturas reales al subirlas.

6️⃣ Comprobamos que la portada persiste​

Además de ver el resultado en el navegador, comprobaremos la carpeta C:/datos/mi-coleccion/portadas y la tabla en MySQL:

SELECT id, titulo, imagen_nombre
FROM videojuegos;

En imagen_nombre veremos el nombre del archivo, no la imagen. Si reiniciamos Spring Boot, las portadas siguen apareciendo.

Limitaciones de este ejemplo
  • La base de datos y la carpeta van juntas. Si movemos la aplicación a otro servidor o hacemos una copia de seguridad, hay que copiar las dos.
  • MySQL y el disco no forman una transacción. Si fallara repositorio.save() después de escribir el archivo, quedaría en la carpeta un archivo sin usar. En una aplicación real se gestionaría ese caso; en nuestra práctica, no afecta al funcionamiento.

7️⃣ Para saber más​

🟩 Otra forma de mostrar la imagen: ResponseEntity​

En lugar de publicar la carpeta con PortadasConfig, un controlador puede leer el archivo y devolver sus bytes con ResponseEntity<byte[]>, indicando el tipo de contenido (image/png, image/jpeg). Es útil cuando hay que comprobar permisos antes de entregar la imagen (por ejemplo, fotos privadas de cada usuario). Documentación de ResponseEntity.

🟨 Guardar las imágenes en la nube​

En lugar de una carpeta del servidor, las imágenes pueden guardarse en un servicio de almacenamiento como Supabase Storage o Amazon S3. Gracias a cómo hemos repartido el trabajo, solo habría que cambiar PortadaService: en lugar de transferTo(), enviaría el archivo por HTTP a la API del proveedor. VideojuegoService, el controlador, el formulario y la columna imagen_nombre seguirían igual.

Documentación oficial: guía de Spring sobre subida de archivos y recursos estáticos en Spring MVC.
