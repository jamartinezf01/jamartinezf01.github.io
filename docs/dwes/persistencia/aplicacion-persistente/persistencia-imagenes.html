2.4. Persistencia de imágenes en aplicaciones web

En MiColección ya podemos crear, consultar, modificar y eliminar videojuegos desde formularios Thymeleaf. Hasta ahora sus datos son textos y números: título, género, plataforma y año de lanzamiento. Pero ¿qué sucede si queremos que cada videojuego tenga también una portada?

Podríamos colocar algunas imágenes dentro de src/main/resources/static/img/ y mostrarlas en la página. Eso funciona para los recursos que distribuimos con la aplicación, pero no resuelve otro problema: que una persona seleccione una imagen desde su ordenador, la suba desde un formulario y pueda volver a verla después de reiniciar Spring Boot.

En este apartado resolveremos ese problema de dos maneras: guardando los bytes de la imagen en MySQL y guardando el archivo en una carpeta del servidor mientras conservamos su referencia mediante JPA. Las dos soluciones conseguirán lo mismo desde el punto de vista del usuario, pero su funcionamiento y sus consecuencias serán distintos.

Idea principal

Persistir una imagen significa conservarla para poder recuperarla posteriormente. Podemos guardar su contenido binario directamente en la base de datos o almacenar el archivo aparte y guardar en la base de datos una referencia que permita localizarlo.

1️⃣ Dos maneras de conservar las imágenes​

🟩 Imágenes incluidas en el proyecto e imágenes subidas​

Una imagen que acompaña a los archivos HTML y CSS del proyecto es un recurso estático. Por ejemplo, una portada predeterminada incluida en static/img/ se empaqueta con el archivo JAR y forma parte del despliegue. No necesitamos JPA para mostrarla.

En cambio, las imágenes que llegan mediante un formulario pueden cambiar durante la ejecución: hoy añadimos una portada, mañana la sustituimos y otro día eliminamos el videojuego. Por eso necesitamos decidir dónde quedará almacenado el archivo y cómo lo recuperará nuestra aplicación.

🟨 Comparación visual de las dos alternativas​

En la alternativa A, MySQL contiene los propios bytes de la portada. En la alternativa B, MySQL solo contiene un nombre como a62e9d4b-...jpg; el archivo se conserva en otra ubicación. Esta diferencia afecta a las copias de seguridad, al tamaño de la base de datos y a lo que sucede cuando trasladamos la aplicación a otro equipo.

Para no mezclar implementaciones, trabajaremos con dos variantes de MiColección. La primera será la práctica guiada principal; después reutilizaremos el mismo formulario y las mismas rutas para sustituir únicamente la forma de almacenamiento.

aviso

Si vamos a probar ambas variantes de forma independiente, conviene duplicar el proyecto y utilizar bases de datos de prácticas separadas (con los permisos correspondientes). No debemos alternar cambios de esquema sobre una base de datos con datos importantes ni pensar que ddl-auto=update es una herramienta de migración.

2️⃣ Preparamos la subida: lo que comparten ambas soluciones​

🟩 El formulario envía un archivo​

Recuperamos lo aprendido sobre formularios HTML. Un archivo no se envía como si fuera una cadena de texto: el navegador necesita utilizar el formato multipart/form-data.

En nuestra plantilla src/main/resources/templates/videojuegos/formulario.html, después del cierre del formulario CRUD que ya existe, añadimos un segundo formulario dedicado a la portada. Solo aparecerá cuando estemos editando un videojuego que ya tiene identificador.

Fragmento para añadir después de </form> en videojuegos/formulario.html
<section th:if="${modoEdicion}">
    <h2>Portada del videojuego</h2>

    <form th:action="@{/videojuegos/{id}/portada(id=${idEdicion})}"
          method="post"
          enctype="multipart/form-data">

        <label for="portada">Selecciona una imagen JPG o PNG:</label>
        <input type="file" id="portada" name="portada"
               accept="image/jpeg,image/png" required>

        <button type="submit">Guardar portada</button>
    </form>
</section>
en este ejemplo

type="file" abre el selector de archivos del navegador. enctype="multipart/form-data" permite enviar el contenido del archivo. El atributo accept orienta al navegador sobre los formatos admitidos, pero no garantiza que el archivo realmente sea una imagen válida.

Usamos un formulario separado porque ya existe otro formulario para editar los datos del videojuego. No debemos introducir un formulario dentro de otro. La variable ${idEdicion} ya se prepara en el controlador CRUD cuando abrimos la edición.

🟨 La clase MultipartFile y los límites de tamaño​

Spring MVC representa el archivo recibido mediante MultipartFile. Podemos consultar su tamaño y leer sus bytes, por ejemplo, con getSize() y getBytes().

En application.properties establecemos límites apropiados para portadas pequeñas:

src/main/resources/application.properties
spring.servlet.multipart.max-file-size=1MB
spring.servlet.multipart.max-request-size=2MB

Estas propiedades establecen límites de recepción en el servidor. Si se superan, la petición puede rechazarse antes de llegar al método del controlador.

🟧 Dependencias necesarias​

No necesitaremos instalar librerías nuevas para esta práctica. MultipartFile forma parte de Spring Web MVC, @Lob y el repositorio pertenecen a JPA/Spring Data JPA, y Path, Files, UUID e ImageIO están disponibles con Java 21. Continuaremos utilizando las dependencias Maven que ya tiene MiColección.

🟥 Comprobamos que realmente hemos recibido una imagen​

Antes de guardar archivos enviados por un usuario hay que controlar, como mínimo, que no estén vacíos, que no superen el tamaño admitido y que correspondan a un formato permitido. No debemos confiar exclusivamente en el nombre del archivo ni en getContentType(), porque ambos proceden de información que puede manipularse.

Para las dos variantes crearemos dos tipos auxiliares muy sencillos. El primero reúne los datos de una imagen que ya hemos comprobado; el segundo servirá para devolverla al navegador.

servicios/ImagenValidada.java
package com.dwes.mi_coleccion.servicios;

public record ImagenValidada(byte[] datos, String tipo, String extension) {
}
servicios/PortadaRecuperada.java
package com.dwes.mi_coleccion.servicios;

public record PortadaRecuperada(byte[] datos, String tipo) {
}

Con Java 21 podemos utilizar record para objetos que solo agrupan información. No son entidades JPA y no crean tablas.

Ahora implementamos una comprobación básica y reutilizable:

src/main/java/com/dwes/mi_coleccion/servicios/ValidadorImagenes.java
package com.dwes.mi_coleccion.servicios;

import org.springframework.web.multipart.MultipartFile;
import javax.imageio.ImageIO;
import java.awt.image.BufferedImage;
import java.io.ByteArrayInputStream;
import java.io.IOException;

public class ValidadorImagenes {

    private static final long TAMANIO_MAXIMO = 1024 * 1024;

    public static ImagenValidada validar(MultipartFile archivo)
            throws IOException {

        if (archivo.isEmpty() || archivo.getSize() > TAMANIO_MAXIMO) {
            throw new IllegalArgumentException(
                    "Selecciona una imagen de 1 MB como máximo.");
        }

        byte[] bytes = archivo.getBytes();

        boolean esJpg = bytes.length >= 3
                && (bytes[0] & 0xFF) == 0xFF
                && (bytes[1] & 0xFF) == 0xD8
                && (bytes[2] & 0xFF) == 0xFF;

        boolean esPng = bytes.length >= 8
                && (bytes[0] & 0xFF) == 0x89
                && bytes[1] == 0x50
                && bytes[2] == 0x4E
                && bytes[3] == 0x47
                && bytes[4] == 0x0D
                && bytes[5] == 0x0A
                && bytes[6] == 0x1A
                && bytes[7] == 0x0A;

        if (!esJpg && !esPng) {
            throw new IllegalArgumentException("Solo se permiten JPG y PNG.");
        }

        BufferedImage imagen;
        try {
            imagen = ImageIO.read(new ByteArrayInputStream(bytes));
        } catch (IOException e) {
            throw new IllegalArgumentException("La imagen está dañada.");
        }

        if (imagen == null || imagen.getWidth() > 4000
                || imagen.getHeight() > 4000) {
            throw new IllegalArgumentException("Imagen no válida.");
        }

        return new ImagenValidada(bytes,
                esJpg ? "image/jpeg" : "image/png",
                esJpg ? "jpg" : "png");
    }
}
en este ejemplo

Comprobamos la firma inicial de los archivos JPEG y PNG y tratamos de decodificar su contenido con ImageIO. Si se supera el límite de tamaño o el archivo no puede interpretarse como una imagen admitida, lanzamos una excepción y evitamos guardarlo.

Este código es una validación básica para una práctica educativa. En un servicio expuesto a Internet pueden ser necesarias medidas adicionales, como limitar recursos de decodificación, procesar la imagen en un entorno controlado o volver a codificarla antes de publicarla.

3️⃣ Alternativa A: guardamos la portada en MySQL​

🟩 Añadimos un campo binario a Videojuego​

MySQL dispone de tipos de datos de la familia BLOB (Binary Large Object), destinados al almacenamiento binario. Como nuestras portadas serán pequeñas, utilizaremos una columna MEDIUMBLOB, que admite mucho más que el límite de 1 MB definido para la práctica.

En la entidad Videojuego conservamos todos los atributos, constructores y métodos que ya teníamos y añadimos únicamente estas propiedades y sus métodos de acceso:

Cambios en modelo/Videojuego.java (alternativa A)
@Lob
@Column(name = "portada", columnDefinition = "MEDIUMBLOB")
private byte[] portada;

@Column(name = "portada_tipo", length = 20)
private String portadaTipo;

public byte[] getPortada() {
    return portada;
}

public void setPortada(byte[] portada) {
    this.portada = portada;
}

public String getPortadaTipo() {
    return portadaTipo;
}

public void setPortadaTipo(String portadaTipo) {
    this.portadaTipo = portadaTipo;
}

Importamos jakarta.persistence.Lob y jakarta.persistence.Column si todavía no lo hemos hecho.

@Lob indica que el campo contiene datos binarios de gran tamaño. columnDefinition = "MEDIUMBLOB" fuerza un tipo concreto de MySQL: es una decisión específica de este gestor, no una configuración portable a cualquier base de datos.

La tabla conservará sus columnas anteriores y añadirá otras dos: una con los bytes y otra con el tipo MIME, como image/png. Si utilizamos ddl-auto=update en una base de pruebas, Hibernate intentará añadirlas; si gestionamos el esquema mediante SQL, podemos incorporarlas de forma controlada:

Alternativa A: columnas que añadimos a videojuegos
ALTER TABLE videojuegos
    ADD COLUMN portada MEDIUMBLOB NULL,
    ADD COLUMN portada_tipo VARCHAR(20) NULL;
aviso

El SQL anterior es una alternativa a dejar que Hibernate añada las columnas; no debemos aplicar las dos opciones sin comprobar primero el esquema real. Si las columnas ya existen, la instrucción fallará. Antes de modificar una tabla con datos, realizaremos una copia de seguridad.

🟨 Creamos el servicio que guarda y recupera la portada​

Nuestra aplicación ya tiene VideojuegoService para gestionar el CRUD. Añadiremos otro servicio, PortadaService, especializado en el tratamiento de imágenes. Así evitamos mezclar detalles de archivos con las operaciones habituales sobre títulos, géneros o plataformas.

src/main/java/com/dwes/mi_coleccion/servicios/PortadaService.java (alternativa A)
package com.dwes.mi_coleccion.servicios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.repositorios.VideojuegoRepository;
import org.springframework.stereotype.Service;
import org.springframework.web.multipart.MultipartFile;

import java.io.IOException;
import java.util.NoSuchElementException;
import java.util.Optional;

@Service
public class PortadaService {

    private final VideojuegoRepository repositorio;

    public PortadaService(VideojuegoRepository repositorio) {
        this.repositorio = repositorio;
    }

    public void guardarPortada(Long id, MultipartFile archivo)
            throws IOException {

        Videojuego videojuego = repositorio.findById(id)
                .orElseThrow(() -> new NoSuchElementException(
                        "El videojuego no existe."));

        ImagenValidada imagen = ValidadorImagenes.validar(archivo);

        videojuego.setPortada(imagen.datos());
        videojuego.setPortadaTipo(imagen.tipo());
        repositorio.save(videojuego);
    }

    public Optional<PortadaRecuperada> obtenerPortada(Long id)
            throws IOException {

        return repositorio.findById(id)
                .filter(v -> v.getPortada() != null
                        && v.getPortadaTipo() != null)
                .map(v -> new PortadaRecuperada(
                        v.getPortada(), v.getPortadaTipo()));
    }
}
en este ejemplo

guardarPortada() localiza primero el videojuego. Después utiliza el validador para obtener un byte[] y el tipo MIME comprobado, incorpora ambos datos a la entidad y llama a save().

obtenerPortada() recupera los bytes guardados. Devuelve un Optional: puede no existir el videojuego o puede que todavía no tenga portada.

Observa que no hemos modificado el contrato de VideojuegoRepository: seguimos utilizando los métodos que ya proporciona JpaRepository.

🟧 Publicamos una ruta para subir y mostrar la imagen​

Una portada guardada en MySQL no tiene una URL propia. Necesitamos que Spring Boot recupere sus bytes y los entregue al navegador cuando este solicite la imagen.

Creamos un controlador adicional, específico para las portadas. No sustituimos VideojuegoController ni duplicamos sus rutas CRUD.

src/main/java/com/dwes/mi_coleccion/controladores/PortadaController.java
package com.dwes.mi_coleccion.controladores;

import com.dwes.mi_coleccion.servicios.PortadaRecuperada;
import com.dwes.mi_coleccion.servicios.PortadaService;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.multipart.MultipartFile;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

import java.io.IOException;
import java.util.NoSuchElementException;
import java.util.Optional;

@Controller
@RequestMapping("/videojuegos")
public class PortadaController {

    private final PortadaService servicio;

    public PortadaController(PortadaService servicio) {
        this.servicio = servicio;
    }

    @PostMapping("/{id}/portada")
    public String subir(@PathVariable Long id,
                        @RequestParam("portada") MultipartFile archivo,
                        RedirectAttributes redirect) {
        try {
            servicio.guardarPortada(id, archivo);
            redirect.addFlashAttribute("mensaje", "Portada guardada.");
        } catch (IllegalArgumentException | IllegalStateException
                 | NoSuchElementException e) {
            redirect.addFlashAttribute("error", e.getMessage());
        } catch (IOException e) {
            redirect.addFlashAttribute("error", "No se pudo guardar la imagen.");
        }
        return "redirect:/videojuegos";
    }

    @GetMapping("/{id}/portada")
    public ResponseEntity<byte[]> mostrar(@PathVariable Long id) {
        try {
            Optional<PortadaRecuperada> imagen = servicio.obtenerPortada(id);
            if (imagen.isEmpty()) {
                return ResponseEntity.notFound().build();
            }

            return ResponseEntity.ok()
                    .contentType(MediaType.parseMediaType(imagen.get().tipo()))
                    .header(HttpHeaders.CACHE_CONTROL, "no-store")
                    .body(imagen.get().datos());
        } catch (IOException e) {
            return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                    .build();
        }
    }
}
en este ejemplo

El método subir() recibe el archivo mediante MultipartFile y delega en el servicio. Después redirige al listado y muestra un mensaje flash, siguiendo el patrón que ya utilizamos en el CRUD.

El método mostrar() devuelve el contenido binario mediante ResponseEntity<byte[]>, indicando si se trata de JPEG o PNG con Content-Type. No devuelve una plantilla porque el navegador está solicitando la imagen, no una página HTML. Seguimos en una aplicación MVC; no estamos desarrollando una API REST completa.

Si no existe la portada, responde con HTTP 404. El controlador no accede directamente al repositorio ni al sistema de archivos.

🟥 Mostramos la portada en Thymeleaf​

Dentro de la sección dedicada a la portada que añadimos tras el formulario CRUD, colocamos antes del formulario de subida este fragmento:

Vista de edición: mostrar la portada guardada en MySQL
<div th:if="${videojuego.portada != null}">
    <img th:src="@{/videojuegos/{id}/portada(id=${idEdicion})}"
         alt="Portada del videojuego" style="max-width: 180px; height: auto;">
</div>

    Este videojuego todavía no tiene portada.

El atributo th:src construye la URL de la imagen. El navegador solicitará esa dirección y PortadaController devolverá los bytes recuperados de MySQL.

🟪 Comprobamos la persistencia de los bytes​

Subimos una imagen pequeña a un videojuego existente. Después, en MySQL, ejecutamos:

Comprobar una portada almacenada en MySQL
SELECT id, titulo, portada_tipo,
       OCTET_LENGTH(portada) AS tamanio_bytes
FROM videojuegos;

OCTET_LENGTH() permite comprobar que MySQL conserva información binaria. No necesitamos visualizar los bytes directamente en Workbench. Detenemos Spring Boot, volvemos a arrancarlo y comprobamos que la portada sigue disponible.

aviso

Esta solución es cómoda para imágenes pequeñas, pero tiene un coste: al recuperar entidades Videojuego podemos estar recuperando también los bytes de sus portadas. Si la colección creciera mucho, convendría estudiar un mapeo o consulta que evitara cargar imágenes al construir los listados, o utilizar otra estrategia de almacenamiento.

4️⃣ Alternativa B: guardamos el archivo fuera de MySQL​

🟩 Cambiamos qué guarda la entidad​

Ahora vamos a resolver el mismo problema de otra manera. Trabajaremos sobre una copia de MiColección destinada a esta variante. Los formularios y las rutas serán los mismos, pero el contenido binario ya no se almacenará en la tabla.

En la entidad Videojuego de esta segunda variante no añadimos portada ni portadaTipo. En su lugar incorporamos una única propiedad:

Cambios en modelo/Videojuego.java (alternativa B)
@Column(name = "imagen_nombre", length = 50)
private String imagenNombre;

public String getImagenNombre() {
    return imagenNombre;
}

public void setImagenNombre(String imagenNombre) {
    this.imagenNombre = imagenNombre;
}

De este modo, MySQL conservará un nombre como d9fa6d33-8917-4ae2-bf07-349a8bfcd219.png. El archivo real estará en una carpeta del servidor.

Podemos configurar la carpeta mediante application.properties:

application.properties (alternativa B)
app.portadas.directorio=C:/datos/mi-coleccion/portadas
spring.servlet.multipart.max-file-size=1MB
spring.servlet.multipart.max-request-size=2MB

Esta ubicación está fuera del directorio src, porque no debemos escribir archivos de usuarios dentro de src/main/resources/static/: ese directorio forma parte de los recursos que empaquetamos, no de un almacenamiento persistente de archivos nuevos.

🟨 Sustituimos solo la implementación de PortadaService​

Mantenemos las clases ValidadorImagenes, ImagenValidada, PortadaRecuperada y PortadaController. Solo sustituimos PortadaService por una versión que guarda y lee archivos.

src/main/java/com/dwes/mi_coleccion/servicios/PortadaService.java (alternativa B)
package com.dwes.mi_coleccion.servicios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.repositorios.VideojuegoRepository;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;
import org.springframework.web.multipart.MultipartFile;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.util.NoSuchElementException;
import java.util.Optional;
import java.util.UUID;

@Service
public class PortadaService {

    private final VideojuegoRepository repositorio;
    private final Path carpeta;

    public PortadaService(VideojuegoRepository repositorio,
                         @Value("${app.portadas.directorio}") String directorio) {
        this.repositorio = repositorio;
        this.carpeta = Path.of(directorio).toAbsolutePath().normalize();
    }

    public void guardarPortada(Long id, MultipartFile archivo)
            throws IOException {

        Videojuego videojuego = repositorio.findById(id)
                .orElseThrow(() -> new NoSuchElementException(
                        "El videojuego no existe."));

        // Primera versión: una portada por videojuego, sin sustitución.
        if (videojuego.getImagenNombre() != null) {
            throw new IllegalStateException(
                    "Ya existe una portada; la sustitución se estudiará aparte.");
        }

        ImagenValidada imagen = ValidadorImagenes.validar(archivo);
        String nombre = UUID.randomUUID() + "." + imagen.extension();
        Files.createDirectories(carpeta);
        Path destino = carpeta.resolve(nombre);

        Files.write(destino, imagen.datos(),
                StandardOpenOption.CREATE_NEW, StandardOpenOption.WRITE);

        try {
            videojuego.setImagenNombre(nombre);
            repositorio.saveAndFlush(videojuego);
        } catch (RuntimeException e) {
            // Si MySQL rechaza el cambio, retiramos el archivo nuevo.
            try {
                Files.deleteIfExists(destino);
            } catch (IOException errorLimpieza) {
                e.addSuppressed(errorLimpieza);
            }
            throw e;
        }
    }

    public Optional<PortadaRecuperada> obtenerPortada(Long id)
            throws IOException {

        Optional<Videojuego> encontrado = repositorio.findById(id);
        if (encontrado.isEmpty() || encontrado.get().getImagenNombre() == null) {
            return Optional.empty();
        }

        String nombre = encontrado.get().getImagenNombre();
        if (!nombre.matches("[a-f0-9-]{36}\\.(jpg|png)")) {
            return Optional.empty();
        }

        Path ruta = carpeta.resolve(nombre).normalize();
        if (!ruta.startsWith(carpeta) || !Files.isRegularFile(ruta)) {
            return Optional.empty();
        }

        String tipo = nombre.endsWith(".jpg") ? "image/jpeg" : "image/png";
        return Optional.of(new PortadaRecuperada(
                Files.readAllBytes(ruta), tipo));
    }
}
en este ejemplo

Path representa la ruta del archivo y Files.write() escribe sus bytes. UUID.randomUUID() crea nombres difíciles de repetir; así no dependemos del nombre que envió el navegador y evitamos sobrescribir archivos por coincidencia.

repositorio.saveAndFlush() guarda la referencia del archivo y solicita sincronizarla con la base de datos dentro de la operación del repositorio. Si MySQL rechaza esa escritura, el código intenta retirar el archivo que acabamos de crear. Esto reduce el riesgo de dejar archivos huérfanos, pero no constituye una transacción única entre MySQL y el sistema de archivos.

Para mantener el primer ejemplo comprensible, esta variante solo permite añadir la primera portada. No intentamos sustituirla automáticamente: borrar el archivo antiguo antes de confirmar que la nueva referencia funciona podría provocar pérdidas de información.

🟧 Recuperamos el archivo con la misma ruta web​

No es necesario modificar PortadaController. Su método GET /videojuegos/{id}/portada invoca obtenerPortada(id) y devuelve los bytes recibidos, sin necesitar saber si proceden de MySQL o del sistema de archivos.

En formulario.html mantenemos el formulario de subida y sustituimos únicamente la comprobación visual de existencia:

Vista de edición: mostrar la portada almacenada como archivo

    <img th:src="@{/videojuegos/{id}/portada(id=${idEdicion})}"
         alt="Portada del videojuego" style="max-width: 180px; height: auto;">
</div>
<p th:unless="${videojuego.imagenNombre != null}">
    Este videojuego todavía no tiene portada.
</p>

En esta alternativa, la consulta de MySQL nos mostrará el nombre, no los bytes:

Comprobar el nombre de archivo almacenado en MySQL
SELECT id, titulo, imagen_nombre
FROM videojuegos;

Podemos abrir la carpeta C:/datos/mi-coleccion/portadas/ y comprobar que contiene el archivo correspondiente. Si borramos manualmente el archivo, MySQL seguirá conservando el nombre, pero el navegador recibirá un 404: hemos perdido la correspondencia entre ambos almacenes.

5️⃣ Elegimos una estrategia y cuidamos la integridad​

🟩 No hay una solución que sea siempre mejor​

Guardar imágenes pequeñas en MySQL facilita que los bytes y los demás datos estén incluidos en una misma copia de seguridad de la base de datos. Sin embargo, aumenta su tamaño y puede encarecer las consultas cuando cargamos entidades con imágenes. Si utilizamos una instancia gratuita remota, como Aiven, las portadas también consumirán su almacenamiento disponible.

Guardar los archivos fuera de MySQL separa los datos estructurados del contenido multimedia, pero exige gestionar rutas, copias de seguridad de carpetas y la coherencia entre la referencia de MySQL y el archivo real. Si la aplicación se despliega en otro servidor, no basta con trasladar la base de datos: las imágenes deben estar disponibles en la nueva ubicación.

🟨 Sustitución, eliminación y fallos​

Hay operaciones que nuestra primera práctica no resuelve por completo, pero que debemos entender:

SituaciónAlmacenamiento en MySQLAlmacenamiento en carpeta
Sustituir una portada.Actualizar bytes y tipo MIME de la entidad.Guardar archivo nuevo, confirmar nueva referencia y retirar el anterior cuando sea seguro.
Eliminar un videojuego.Los bytes asociados desaparecen al borrar su fila.Hay que decidir cuándo eliminar también el archivo físico.
Falla el guardado.La base de datos puede deshacer la operación en una transacción.Puede quedar un archivo sin referencia o una referencia sin archivo.
Hacer una copia.Copiar la base de datos incluye la imagen.Copiar la base de datos y la carpeta de imágenes.
aviso

@Transactional no convierte los archivos de disco en parte de una transacción MySQL. No debemos prometer que un rollback de JPA deshace también una operación de Files.write() o Files.delete().

En aplicaciones reales se diseñan estrategias de recuperación o limpieza para evitar referencias rotas y archivos huérfanos.

🟧 Buenas prácticas mínimas​

Además de limitar el tamaño y comprobar el formato, procuraremos que los nombres de archivo los genere el servidor y que las rutas públicas no permitan leer archivos arbitrarios. Para una aplicación expuesta a Internet también deberíamos controlar quién puede subir, sustituir o eliminar portadas; esa cuestión corresponde al bloque de seguridad y no la resolveremos aquí.

No debemos almacenar contraseñas ni rutas sensibles dentro del código Java. Para las rutas de archivos utilizamos propiedades de configuración; para las credenciales de MySQL mantenemos las variables de entorno trabajadas en la unidad.

6️⃣ Errores frecuentes​

🟩 El formulario se muestra, pero MultipartFile llega vacío​

Comprueba el atributo enctype="multipart/form-data", el método POST y que el name del <input> sea portada, igual que en @RequestParam("portada").

🟨 La imagen se guarda, pero no se muestra​

Comprueba que la dirección generada con th:src corresponde a GET /videojuegos/{id}/portada. Recuerda que el navegador realiza una segunda petición para solicitar la imagen, después de cargar el HTML.

🟧 En MySQL aparece el nombre del archivo, pero no la imagen​

Eso es normal en la alternativa B: MySQL no contiene los bytes. La imagen debe encontrarse en la carpeta configurada. Si falta, la referencia ya no es válida.

🟥 Las imágenes desaparecen al mover la aplicación a otro ordenador​

En la alternativa B, además del proyecto y la base de datos, hay que conservar los archivos y adaptar la ruta app.portadas.directorio al nuevo entorno.

consejo

La pregunta principal no es «¿qué opción funciona?», porque ambas funcionan. La pregunta es qué sistema resulta más adecuado para el tamaño de los archivos, el modo de despliegue, las copias de seguridad y los requisitos de la aplicación.
