2.2. Operaciones CRUD con JPA

En el apartado anterior organizamos MiColección mediante un controlador, un servicio y un repositorio. Ya podemos recuperar videojuegos de MySQL y mostrarlos en una vista Thymeleaf. Ahora aprenderemos a modificar esos datos de forma persistente, sin introducir todavía nuevos formularios o rutas web.

Comenzaremos por entender las cuatro operaciones CRUD y cómo las coordinamos desde VideojuegoService. Los formularios y las rutas web se incorporarán después, para distinguir la gestión de datos de la presentación de la aplicación.

Idea principal

CRUD son las operaciones crear (Create), consultar (Read), actualizar (Update) y eliminar (Delete). JpaRepository ya dispone de métodos para realizarlas; la capa de servicios los utilizará para ofrecer operaciones con sentido en nuestra aplicación.

1️⃣ Comprendemos las operaciones CRUD​

🟩 Cuatro operaciones, una responsabilidad​

Cuando gestionamos una colección de videojuegos, necesitamos dar de alta nuevos títulos, consultar los existentes, corregir sus datos y eliminar los que ya no queremos conservar. Estas acciones tienen equivalentes en la base de datos: INSERT, SELECT, UPDATE y DELETE.

OperaciónQué necesitamosQué hace el servicioMétodo del repositorio
CrearDatos de un videojuego nuevo.Construye una entidad sin identificador y solicita guardarla.save(entidad).
ConsultarNingún ID o uno concreto.Recupera registros y contempla que no existan.findAll(), findById(id).
ActualizarID existente y nuevos valores.Recupera la entidad, modifica los campos permitidos y la guarda.findById(id), save(entidad).
EliminarID del registro.Comprueba que existe y solicita eliminarlo.findById(id), delete(entidad).

Las operaciones de consulta ya las hemos utilizado para mostrar el listado. En este apartado ampliaremos el servicio con las tres operaciones de escritura. No es necesario crear otra interfaz de repositorio: los métodos indicados ya se heredan de JpaRepository<Videojuego, Long>.

🟨 El repositorio no decide cómo responde la web​

save() y delete() trabajan con entidades; no saben si la operación se solicita desde un formulario Thymeleaf, una aplicación de escritorio u otro tipo de interfaz. Tampoco deciden qué mensaje debe aparecer en una página.

Por ejemplo, el servicio puede devolver false cuando no encuentra el ID solicitado para actualizar. Será el controlador web quien convierta ese resultado en una respuesta adecuada para la persona usuaria.

consejo

Los nombres crear(), actualizar() y eliminar() son métodos que definiremos nosotros en el servicio. No son nombres obligatorios de Spring Data JPA. En cambio, save(), findById() y delete() sí son métodos heredados del repositorio.

2️⃣ Ampliamos el servicio con operaciones de escritura​

La interfaz VideojuegoRepository no necesita cambios: JpaRepository ya proporciona save(), findById() y delete(). Nuestro servicio, en cambio, debe ofrecer operaciones que expresen qué queremos hacer en la aplicación.

🟩 Crear, modificar y eliminar​

Sustituimos el contenido de VideojuegoService.java por esta versión completa:

src/main/java/com/dwes/mi_coleccion/servicios/VideojuegoService.java
package com.dwes.mi_coleccion.servicios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.repositorios.VideojuegoRepository;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Optional;

@Service
public class VideojuegoService {

    private final VideojuegoRepository repositorio;

    public VideojuegoService(VideojuegoRepository repositorio) {
        this.repositorio = repositorio;
    }

    public List<Videojuego> listarVideojuegos() {
        return repositorio.findAll();
    }

    public Optional<Videojuego> buscarPorId(Long id) {
        return repositorio.findById(id);
    }

    public long contarVideojuegos() {
        return repositorio.count();
    }

    public Videojuego crear(Videojuego datos) {
        Videojuego nuevo = new Videojuego(
                datos.getTitulo(),
                datos.getGenero(),
                datos.getPlataforma(),
                datos.getAnioLanzamiento()
        );
        return repositorio.save(nuevo);
    }

    public boolean actualizar(Long id, Videojuego datos) {
        Optional<Videojuego> encontrado = repositorio.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }

        Videojuego existente = encontrado.get();
        existente.setTitulo(datos.getTitulo());
        existente.setGenero(datos.getGenero());
        existente.setPlataforma(datos.getPlataforma());
        existente.setAnioLanzamiento(datos.getAnioLanzamiento());
        repositorio.save(existente);
        return true;
    }

    public boolean eliminar(Long id) {
        Optional<Videojuego> encontrado = repositorio.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }

        repositorio.delete(encontrado.get());
        return true;
    }
}
en este ejemplo

En crear() construimos una entidad nueva, sin ID asignado, y llamamos a save(). Con nuestra estrategia GenerationType.IDENTITY, MySQL genera el identificador cuando se inserta el registro.

En actualizar() buscamos primero el videojuego por el ID que identificará el registro solicitado. Si existe, modificamos sus propiedades y guardamos la entidad recuperada. Si no existe, devolvemos false para que el controlador pueda informar del problema.

En eliminar() también comprobamos la existencia del registro antes de borrarlo. Utilizamos delete(entidad), otra operación heredada de JpaRepository.

Seguimos utilizando inyección por constructor: Spring proporciona el repositorio al servicio. No tenemos que crear el repositorio manualmente.

🟨 Cómo diseñamos los métodos del servicio​

Los métodos crear(), actualizar() y eliminar() no pertenecen a JpaRepository: son operaciones que hemos definido en VideojuegoService. Por eso sus nombres, parámetros y tipos de retorno responden a las necesidades de nuestra aplicación.

Antes de escribir un método de servicio conviene decidir cuatro cosas:

  1. Qué operación representa. Es preferible actualizar() o eliminar() a un nombre genérico que no exprese lo que hace.
  2. Qué datos necesita. Crear requiere datos de la entidad; actualizar y eliminar necesitan identificar un registro existente.
  3. Qué debe devolver. Una entidad guardada, una lista, un Optional o un resultado que indique si la operación se ha podido realizar.
  4. Qué sucede si la operación no puede completarse. Por ejemplo, porque el identificador no existe o porque la información no cumple una regla.

En MiColección hemos elegido estas firmas:

Método propio del servicioParámetrosRetornoQué expresa el resultado
crear(Videojuego datos)Datos del videojuego.VideojuegoEntidad guardada, con el ID asignado.
actualizar(Long id, Videojuego datos)ID y nuevos valores.booleantrue si encontramos el registro y solicitamos guardar sus cambios.
eliminar(Long id)ID del registro.booleantrue si encontramos el registro y solicitamos eliminarlo.

El uso de boolean es una decisión didáctica para este ejemplo, no una norma de Spring. En aplicaciones más complejas también podemos representar los resultados mediante objetos específicos o excepciones. Aquí no añadiremos esas alternativas hasta que nos hagan falta.

🟧 ¿Por qué no usamos directamente el objeto recibido para actualizar?​

Cuando nuestra aplicación reciba datos para modificar un videojuego, esos datos pueden llegar en un objeto Videojuego que no esté gestionado por JPA y que no tenga asignado un identificador. Esto ocurrirá, por ejemplo, cuando Spring MVC construya el objeto a partir de un formulario.

Por eso recuperamos la entidad existente y copiamos las propiedades que permitimos modificar. Así no dependemos de un identificador introducido por el usuario ni sobrescribimos otras propiedades que no están presentes en el formulario.

consejo

Aunque utilizamos save() tanto para insertar como para actualizar, no es correcto afirmar que siempre ejecuta un INSERT o siempre un UPDATE. El comportamiento depende de si la entidad es nueva o existente y de cómo JPA la gestione. Más adelante profundizaremos en los estados de las entidades y las transacciones.

🟥 ¿Por qué actualizar no es lo mismo que crear?​

Fijémonos en la diferencia que podremos trasladar a cualquier otra entidad:

  • Alta: partimos de datos que todavía no corresponden a un registro de la tabla. Creamos una entidad nueva y dejamos que se genere su identificador.
  • Edición: partimos de un identificador existente. Primero recuperamos el registro, conservamos su identidad y modificamos únicamente los campos autorizados.
  • Eliminación: identificamos qué registro queremos borrar. Antes de hacerlo, el servicio puede necesitar comprobar si existe o si alguna regla de negocio impide eliminarlo.

Una confusión habitual consiste en crear un objeto nuevo con los datos de edición y llamar a save() sin buscar la entidad original. Si ese objeto no tiene identificador, JPA puede tratarlo como una nueva entidad y crear otra fila. Por eso nuestro método actualizar() empieza con findById(id).

aviso

Que un registro exista cuando lo consultamos no garantiza por sí solo que ninguna otra operación pueda modificarlo antes de terminar. Nuestro ejemplo cubre un CRUD sencillo; la gestión de transacciones y concurrencia permitirá estudiar después estas situaciones.

3️⃣ Comprobamos qué ha cambiado en MiColección​

Al terminar este apartado, el proyecto conserva la entidad Videojuego, el repositorio y el controlador del primer listado. El único archivo Java que hemos sustituido es VideojuegoService.java. Los tres métodos nuevos compilan y están disponibles, pero el navegador todavía no presenta botones de alta, edición y eliminación: esas rutas y vistas se incorporarán al crear los formularios CRUD.

🟩 Revisamos el código sin modificar la base de datos​

Comprobamos en IntelliJ IDEA que el proyecto compila y que VideojuegoService contiene tanto las operaciones de lectura anteriores como crear(), actualizar() y eliminar(). Si arrancamos Spring Boot y abrimos /videojuegos, el listado seguirá funcionando exactamente como antes.

aviso

No ejecutaremos altas o eliminaciones de prueba desde métodos de arranque. La clase temporal PruebaVideojuegoRepositorio ya debía estar retirada. Comprobaremos las operaciones desde los formularios y verificaremos los cambios en MySQL.

🟨 ¿Qué ocurriría ante estas situaciones?​

La lógica del servicio merece una comprobación antes de construir la interfaz. Pensemos, por ejemplo, qué devolvería cada método si el identificador no existiera o si intentáramos guardar dos videojuegos nuevos con el mismo título.

SituaciónResultado esperado de nuestro servicio
Creamos un videojuego sin ID.crear() solicita guardarlo y devuelve la entidad resultante.
Actualizamos un ID inexistente.actualizar() devuelve false; no crea otro videojuego.
Actualizamos un ID existente.Cambian los campos permitidos y se conserva la identidad del registro.
Eliminamos un ID inexistente.eliminar() devuelve false.
Creamos dos juegos con el mismo título.El título no es único en nuestro modelo; el repositorio no impide por sí solo ambos registros.

Esta tabla representa el comportamiento de nuestro ejemplo didáctico, no una garantía general de ausencia de errores. Una operación podría fallar por restricciones o problemas de conexión; estudiaremos mejor la integridad y las transacciones más adelante.

4️⃣ Errores frecuentes y comprobación final​

🟩 Confundir crear y actualizar​

Si intentamos actualizar un videojuego construyendo otro objeto nuevo sin identificador, JPA puede tratarlo como una inserción. Por eso actualizar() recupera primero la entidad existente con findById(id) y modifica sus propiedades.

🟨 Modificar el identificador manualmente​

No añadiremos un setId() para asignar números a los videojuegos. La clave primaria la genera MySQL y debe conservarse al actualizar un registro.

🟧 Suponer que save() detecta duplicados​

save() no busca por título ni decide qué videojuegos son equivalentes. Si nuestra aplicación necesitara prohibir duplicados, tendríamos que establecer una regla concreta y las restricciones apropiadas.

  3. ¿Por qué actualizar() recupera primero una entidad existente?
  4. ¿Por qué el servicio devuelve boolean en dos operaciones, en lugar de devolver una URL o el nombre de una plantilla?
  5. ¿Qué componente debería decidir si se muestra un mensaje de éxito o un mensaje de error?
  6. En una biblioteca, ¿qué métodos del repositorio utilizaríamos para modificar el número de ejemplares de un libro existente sin cambiar su identificador?
Antes de continuar

Tenemos la capa de servicios preparada para realizar CRUD, pero aún no hemos habilitado esas operaciones en la interfaz web. Para hacerlo, adaptaremos la entidad para validarla, ampliaremos el mismo controlador y crearemos los formularios Thymeleaf necesarios para gestionar videojuegos desde el navegador.
