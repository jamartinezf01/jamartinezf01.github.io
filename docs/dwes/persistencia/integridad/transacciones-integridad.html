4.1. Transacciones e integridad de los datos

En los apartados anteriores hemos aprendido a guardar información con repositorios JPA y a relacionar entidades. Sin embargo, una aplicación no siempre modifica un único registro cada vez: al devolver un préstamo en una biblioteca, por ejemplo, podemos necesitar finalizar el préstamo y volver a marcar el ejemplar como disponible.

Ambos cambios forman parte de una misma operación. Si guardamos uno y el otro falla, los datos pueden quedar en un estado que no representa lo que realmente ha sucedido. Para evitarlo utilizamos transacciones, un mecanismo de las bases de datos que Spring Boot nos permite gestionar desde nuestros servicios.

Vamos a aprender cómo identificar una unidad de trabajo, delimitarla con @Transactional y comprender las opciones más habituales de la anotación. Trabajaremos con ejemplos independientes para centrarnos en las transacciones sin modificar MiColección.

Idea principal

Una transacción permite tratar varios cambios como una unidad. Si termina correctamente, se confirman mediante un commit. Si se produce un fallo que debe deshacerlos, se revierten mediante un rollback.

La decisión importante no es dónde escribir la anotación, sino qué operaciones deben confirmarse o deshacerse juntas.

1️⃣ Por qué necesitamos transacciones​

🟩 Una operación de negocio puede tener varios pasos​

Imaginemos una biblioteca que registra préstamos de ejemplares. Cuando se devuelve un libro, la aplicación debe modificar, al menos, dos datos: el préstamo deja de estar activo y el ejemplar vuelve a estar disponible.

Si actualizamos primero el préstamo y después falla la actualización del ejemplar, el sistema podría indicar que el libro se ha devuelto, pero mantenerlo como no disponible. El problema no está en una tabla aislada: los dos cambios deben ser coherentes entre sí.

Podemos describir los resultados posibles así:

ResultadoEstado del préstamoEstado del ejemplar¿Es coherente?
Devolución completa.Finalizado.Disponible.Sí.
Operación sin realizar.Activo.No disponible.Sí, si hubo un fallo y se revirtió.
Cambio incompleto.Finalizado.No disponible.No, según las reglas de este ejemplo.

Una transacción impide que confirmemos parcialmente los cambios cuando todos se ejecutan dentro de la misma transacción de base de datos y el fallo provoca su reversión.

🟨 Atomicidad y propiedades ACID​

La atomicidad es la propiedad que acabamos de observar: una transacción no debe quedar confirmada a medias. En los sistemas de bases de datos relacionales también hablamos de otras tres propiedades; juntas forman el acrónimo ACID.

PropiedadQué significaEjemplo orientativo
AtomicidadLos cambios de la transacción se aceptan o se descartan como una unidad.Se actualizan conjuntamente el préstamo y el ejemplar.
ConsistenciaLos cambios respetan las restricciones y las reglas de integridad definidas.No se guarda una clave ajena que apunte a un registro inexistente.
AislamientoLas operaciones simultáneas se coordinan según el nivel de aislamiento del gestor.Dos peticiones no deben interferir entre sí de cualquier manera.
DurabilidadUna vez confirmado un cambio, el gestor se encarga de conservarlo.Una devolución confirmada debe permanecer registrada.

ACID no sustituye las reglas de negocio. Si programamos una operación que actualiza el ejemplar equivocado, una transacción puede confirmar esos cambios incorrectos. Debemos combinar transacciones, validaciones y restricciones de MySQL.

🟧 La base de datos también importa​

En esta unidad utilizamos MySQL con tablas InnoDB, un motor que admite transacciones y claves ajenas. No todas las operaciones sobre un gestor ni todos los motores tienen necesariamente el mismo comportamiento transaccional.

Podemos comprobar el motor de nuestras tablas con una consulta como la siguiente:

Consulta de MySQL para comprobar el motor de una tabla
SHOW TABLE STATUS FROM mi_coleccion LIKE 'videojuegos';

Si la tabla existe, la columna Engine debería indicar InnoDB. Esta consulta es únicamente de comprobación: no modificaremos las tablas ni los registros habituales de MiColección.

2️⃣ Qué significan commit y rollback​

🟩 El ciclo de una transacción​

Una transacción sigue, de forma simplificada, este recorrido: comienza, realiza operaciones, comprueba si puede completarse y termina confirmando o revirtiendo los cambios.

ConceptoFunciónConsecuencia
InicioDefine el comienzo de la unidad transaccional.Las operaciones posteriores pertenecen a esa transacción.
commitConfirma los cambios de la transacción.Se hacen definitivos según las garantías del gestor.
rollbackRevierte los cambios que pertenecen a la transacción.Se recupera el estado anterior a esos cambios.

Podemos entenderlo con SQL, aunque en nuestros servicios Spring no tendremos que escribir estas instrucciones manualmente:

Ejemplo conceptual: operaciones SQL dentro de una transacción
START TRANSACTION;

UPDATE prestamos
SET devuelto = TRUE
WHERE id = 25;

UPDATE ejemplares
SET disponible = TRUE
WHERE id = 4;

COMMIT;
en este ejemplo

Es un ejemplo conceptual de una biblioteca, no un bloque para ejecutar sobre mi_coleccion: presupone que existen las tablas prestamos y ejemplares, que los identificadores son correctos y que se han comprobado las reglas del préstamo.

Las dos sentencias UPDATE pertenecen a la misma transacción. En lugar de COMMIT, si detectáramos un problema antes de confirmar, utilizaríamos ROLLBACK y las modificaciones transaccionales se desharían.

🟨 Ejecutar SQL no significa que esté confirmado​

Durante una transacción, el gestor puede ejecutar un INSERT, UPDATE o DELETE antes del commit. Si después se realiza un rollback, esas modificaciones no quedan confirmadas.

Esta diferencia será importante cuando estudiemos flush y las consultas @Modifying. Una operación puede haber enviado SQL a MySQL y, aun así, terminar sin cambios permanentes.

🟧 Qué no se revierte con una transacción JPA​

Una transacción gestionada sobre una base de datos no deshace por sí sola operaciones ajenas a ella. Por ejemplo, enviar un correo, escribir un archivo o realizar una petición a un servicio externo son acciones que no podemos recuperar automáticamente mediante el rollback de MySQL.

Tampoco debemos confundir cambios en los registros con cambios en la estructura. En MySQL, instrucciones como ALTER TABLE pueden provocar confirmaciones implícitas y no se revierten como un UPDATE ordinario.

aviso

Transacción no significa copia de seguridad. Una transacción protege la coherencia de una operación, mientras que una copia de seguridad sirve para recuperar datos ante otros problemas, como una eliminación ya confirmada o una avería.

3️⃣ Cómo gestionamos transacciones con Spring Boot​

🟩 @Transactional: declaramos los límites​

Spring proporciona la anotación @Transactional, que utilizaremos desde org.springframework.transaction.annotation.Transactional. Con ella declaramos que un método debe ejecutarse dentro de una transacción gestionada por Spring.

Estructura básica de una operación de servicio transaccional
import org.springframework.transaction.annotation.Transactional;

@Transactional
public void realizarOperacion() {
    // Las operaciones de base de datos forman una unidad.
}
en este ejemplo

En el caso habitual, Spring crea una transacción si todavía no existe una. Si el método termina correctamente, intenta confirmarla. Si se propaga un error que exige reversión, la transacción se deshace.

No necesitamos llamar a commit() ni rollback() desde el método. Spring establece el límite transaccional y el gestor de base de datos realiza las operaciones correspondientes.

🟨 Un ejemplo guiado de unidad de trabajo: devolver un préstamo​

Supongamos que en una aplicación de biblioteca ya existen las entidades Prestamo y Ejemplar, con sus repositorios correspondientes. Prestamo tiene una propiedad booleana devuelto y una referencia ejemplar; Ejemplar tiene una propiedad disponible. El servicio siguiente muestra cómo coordinaríamos la operación:

Ejemplo didáctico: PrestamoService.java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PrestamoService {

    private final PrestamoRepository prestamos;
    private final EjemplarRepository ejemplares;

    public PrestamoService(PrestamoRepository prestamos,
                           EjemplarRepository ejemplares) {
        this.prestamos = prestamos;
        this.ejemplares = ejemplares;
    }

    @Transactional
    public void devolverPrestamo(Long prestamoId) {
        Prestamo prestamo = prestamos.findById(prestamoId)
                .orElseThrow(() -> new IllegalArgumentException(
                        "El préstamo no existe"));

        if (prestamo.isDevuelto()) {
            throw new IllegalStateException("El préstamo ya está devuelto");
        }

        Ejemplar ejemplar = prestamo.getEjemplar();

        prestamo.setDevuelto(true);
        ejemplar.setDisponible(true);

        prestamos.save(prestamo);
        ejemplares.save(ejemplar);
    }
}
en este ejemplo

El servicio utiliza dos repositorios, pero sus llamadas pertenecen a la misma transacción porque se realizan dentro de devolverPrestamo(), anotado con @Transactional.

Si no existe el préstamo o ya estaba devuelto, la operación se interrumpe. Si se produjera un fallo que provocara rollback después de realizar parte de los cambios, ninguno de ellos quedaría confirmado.

Este código es un ejemplo independiente, no una clase para añadir a MiColección. Para compilarlo necesitaríamos crear previamente las entidades y repositorios mencionados con esas propiedades y métodos. Hemos mostrado save() en ambas entidades para expresar con claridad las dos escrituras. Al estudiar el contexto de persistencia veremos por qué una entidad gestionada también puede actualizarse sin llamarlo explícitamente.

🟧 ¿Por qué situamos la anotación en el servicio?​

El controlador web atiende una petición y decide qué respuesta devolver. El repositorio ejecuta operaciones de acceso a datos. El servicio conoce la unidad de trabajo que solicita la aplicación: sabe que devolver un préstamo incluye comprobar su estado, modificarlo y actualizar el ejemplar.

ResponsabilidadEjemploComponente
Recibir POST /prestamos/25/devolver.Interpretar el identificador de la URL.Controlador MVC.
Decidir si el préstamo puede devolverse.Comprobar que sigue activo.Servicio.
Garantizar que los cambios formen una unidad.Declarar @Transactional en devolverPrestamo().Servicio.
Recuperar o guardar entidades.findById() y save().Repositorios.
Mostrar un mensaje de éxito o error.Redirigir a una vista Thymeleaf.Controlador y vista.

Los métodos heredados de JpaRepository, como save() y delete(), ya disponen de una configuración transaccional habitual. Pero si una operación de negocio necesita varias llamadas, no debemos confiar en que cada una se confirme por separado: situamos el límite en el servicio que las coordina.

consejo

No añadiremos @Transactional a todos los métodos por rutina. Primero identificaremos qué operaciones deben confirmarse conjuntamente. Una consulta aislada o una simple validación de formulario puede no necesitar un nuevo límite transaccional en el servicio.

4️⃣ Parámetros de @Transactional: qué podemos configurar​

🟩 Las opciones más importantes​

La anotación permite ajustar distintos comportamientos. No necesitamos utilizar todos los parámetros: empezaremos con los valores por defecto y modificaremos solo los que respondan a una necesidad concreta.

ParámetroValor habitual por defectoPara qué sirve
propagationPropagation.REQUIREDDetermina cómo se incorpora el método a una transacción existente o cómo inicia una nueva.
isolationIsolation.DEFAULTIndica el nivel de aislamiento, normalmente el establecido en la base de datos.
readOnlyfalseIdentifica operaciones de consulta para posibles optimizaciones.
timeoutTiempo predeterminado del gestor transaccional.Limita, cuando es compatible, el tiempo permitido para la operación. Se expresa en segundos.
rollbackForSin tipos adicionales definidos.Añade excepciones que deben provocar rollback.
noRollbackForSin excepciones excluidas expresamente.Indica excepciones que no deben provocar rollback por esa regla.
transactionManagerGestor transaccional seleccionado por Spring.Permite elegir uno cuando la aplicación dispone de varios.

La configuración habitual de Spring provoca rollback por RuntimeException y Error, pero no por una excepción comprobada (checked exception), salvo que se indiquen otras reglas o se haya personalizado la política global. Conviene tener presente esta diferencia al diseñar el tratamiento de errores.

🟨 Propagación: REQUIRED y otras posibilidades​

La propagación responde a una pregunta: ¿qué sucede si llamamos a un método transaccional cuando ya hay otra transacción en curso?

ValorComportamiento resumidoUso en esta unidad
REQUIREDSe une a una transacción existente o inicia una si no la hay.El valor por defecto. Adecuado para nuestros servicios habituales.
REQUIRES_NEWInicia una transacción independiente y suspende la existente mientras se ejecuta.Conocer su significado; no lo necesitamos para el ejemplo básico.
SUPPORTSParticipa si existe una transacción; si no, puede ejecutarse sin ella.Ampliación.
MANDATORYExige una transacción ya existente; si no la hay, falla.Ampliación.
NOT_SUPPORTEDEjecuta el método sin transacción, suspendiendo una existente cuando corresponde.Ampliación.
NEVERExige que no haya transacción activa.Ampliación.
NESTEDPuede crear un ámbito con punto de retorno (savepoint) dentro de una transacción compatible.Requiere soporte específico del gestor; no lo utilizaremos.

Por ejemplo, estas dos declaraciones expresan el mismo comportamiento básico:

La propagación REQUIRED ya es el valor por defecto
@Transactional
public void devolverPrestamo(Long id) {
    // ...
}

@Transactional(propagation = Propagation.REQUIRED)
public void registrarDevolucion(Long id) {
    // ...
}
en este ejemplo

Propagation.REQUIRED, de org.springframework.transaction.annotation.Propagation, es el valor por defecto. Por eso, normalmente bastará con escribir @Transactional.

REQUIRES_NEW no significa «más seguro». Una operación independiente puede confirmarse incluso aunque otra transacción exterior se revierta, lo que puede ser justo lo contrario de lo que necesita una unidad de trabajo. Además, suele requerir recursos de conexión adicionales.

🟧 Transacciones de solo lectura: readOnly​

Cuando un método está dedicado a recuperar información podemos expresar esa intención mediante readOnly = true:

Ejemplo de consulta dentro de una transacción de lectura
@Transactional(readOnly = true)
public List<Prestamo> listarPrestamos() {
    return prestamos.findAll();
}
en este ejemplo

Es una pista de optimización para la infraestructura de persistencia. No significa que podamos usarla como un sistema de permisos ni garantiza que todas las bases de datos rechacen cualquier escritura.

Los métodos de consulta heredados de Spring Data JPA ya disponen de configuración transaccional de lectura. Definir un límite en el servicio puede ser útil cuando necesitamos coordinar varias consultas o acceder a relaciones dentro de una misma operación.

🟥 Aislamiento y tiempo máximo​

El aislamiento se refiere a cómo pueden influirse dos transacciones que se ejecutan al mismo tiempo. Por defecto, Isolation.DEFAULT conserva el comportamiento definido por el gestor, por lo que no debemos confundir el valor configurado en Spring con un nivel fijo universal de MySQL.

Por ahora basta con saber que isolation permite solicitar un comportamiento específico si el gestor lo soporta:

Ejemplo de configuración avanzada, no necesaria para las prácticas
@Transactional(isolation = Isolation.READ_COMMITTED, timeout = 10)
public void operacionConRequisitosEspecificos() {
    // ...
}

Isolation pertenece a org.springframework.transaction.annotation.Isolation. El valor timeout = 10 expresa diez segundos, pero su aplicación efectiva depende del gestor y de cómo se inicia la transacción. No utilizaremos estos ajustes para solucionar errores por ensayo y error.

🟪 Reglas particulares de reversión​

Podemos modificar el comportamiento ante excepciones mediante rollbackFor o noRollbackFor:

Ejemplo conceptual: rollback también ante una excepción comprobada
@Transactional(rollbackFor = java.io.IOException.class)
public void operacionConArchivo() throws java.io.IOException {
    // ...
}
aviso

Este ejemplo solo muestra la sintaxis de rollbackFor. Que una IOException provoque la reversión de las operaciones de MySQL no deshace lo que ya se haya escrito en un archivo. Las acciones externas no pasan a formar parte de la misma transacción por añadir un parámetro.

5️⃣ Qué sucede cuando aparece un error​

🟩 Excepciones y comportamiento de rollback​

En el comportamiento predeterminado habitual de Spring, el tipo de excepción que sale del método transaccional es importante.

SituaciónComportamiento esperado por defecto
El método finaliza sin errores.Se intenta confirmar la transacción.
Sale una RuntimeException, como IllegalStateException.Se revierte la transacción.
Sale un Error.Se revierte la transacción.
Sale una excepción comprobada, como IOException.No provoca reversión automáticamente, salvo configuración adicional.
Se captura el fallo y se termina normalmente.No podemos suponer que Spring vaya a revertir por ese motivo.

La regla no sustituye el análisis del resultado de la operación: por ejemplo, una restricción SQL puede impedir el commit y dejar la transacción marcada para reversión. Lo correcto es definir explícitamente qué fallos deben cancelar la unidad de trabajo.

🟨 La diferencia entre gestionar y ocultar una excepción​

Consideremos una operación que tiene dos pasos. Si capturamos una excepción después del primero, escribimos un mensaje en consola y dejamos que el método termine normalmente, podríamos estar permitiendo que se confirme un cambio incompleto.

Ejemplo conceptual de un error de diseño
@Transactional
public void operacionIncompleta() {
    actualizarPrimerRegistro();

    try {
        actualizarSegundoRegistro();
    } catch (IllegalStateException ex) {
        System.out.println("El segundo paso ha fallado");
    }
}
en este ejemplo

Los métodos actualizarPrimerRegistro() y actualizarSegundoRegistro() representan operaciones imaginarias de un servicio, no funciones que ya existan en MiColección. El problema es el catch que oculta el fallo: si la infraestructura no ha marcado previamente la transacción para reversión, Spring puede intentar confirmarla al terminar el método.

Una solución habitual consiste en dejar propagar una excepción que deba provocar rollback. El controlador puede decidir después qué mensaje mostrar, una vez terminada la llamada al servicio.

🟧 Una excepción puede aparecer al confirmar​

No todos los errores ocurren exactamente en la línea de save(). Hibernate puede posponer operaciones de escritura hasta sincronizar el contexto, y MySQL puede rechazar algún cambio cuando se envía el SQL o al finalizar la transacción.

Por eso, no debemos afirmar que la ausencia de una excepción durante save() demuestra que todo se ha confirmado. Para tratar correctamente una operación, importa el resultado completo del método transaccional, incluido su cierre.

6️⃣ Entidades gestionadas, save(), flush() y commit​

🟩 JPA puede detectar los cambios de una entidad​

Cuando recuperamos una entidad dentro de una transacción, JPA puede mantenerla gestionada en su contexto de persistencia. Si modificamos una de sus propiedades, Hibernate puede detectar el cambio y sincronizarlo con la base de datos. Este mecanismo se denomina dirty checking.

Fragmento de servicio: actualización de una entidad gestionada
@Transactional
public void cambiarTitulo(Long libroId, String nuevoTitulo) {
    Libro libro = libros.findById(libroId)
            .orElseThrow(() -> new IllegalArgumentException(
                    "El libro no existe"));

    libro.setTitulo(nuevoTitulo);
}
en este ejemplo

Este fragmento presupone una clase Libro y un repositorio libros; no es una modificación del proyecto MiColección. La entidad recuperada permanece gestionada durante la transacción, por lo que sus cambios pueden persistirse al sincronizar el contexto sin escribir otro save().

Eso no significa que cualquier objeto Java se guarde automáticamente. El comportamiento depende de que la entidad esté gestionada y de que la transacción complete correctamente sus cambios.

🟨 Cuatro operaciones que no significan lo mismo​

OperaciónQué hace¿Confirma por sí sola la transacción exterior?
setTitulo(...)Modifica una propiedad del objeto Java.No.
repositorio.save(entidad)Solicita guardar una entidad nueva o combinar los cambios de una existente según su estado.No, si participa en una transacción del servicio que todavía sigue abierta.
flush() o saveAndFlush()Sincroniza cambios pendientes con la base de datos.No. Todavía puede haber rollback.
commitConfirma la transacción.Sí, es el paso que confirma los cambios.

Un save() aislado de un repositorio tiene su propia gestión transaccional habitual; en ese caso, la confirmación se produce al finalizar esa llamada si ella misma abrió la transacción. La tabla compara operaciones realizadas dentro de un método de servicio transaccional más amplio.

🟧 Actualizaciones en bloque: @Modifying​

Si queremos aplicar el mismo cambio a muchos registros, Spring Data JPA permite declarar consultas UPDATE o DELETE mediante @Query y @Modifying. Por ejemplo, podríamos marcar varios ejemplares como no disponibles:

Fragmento de EjemplarRepository.java: actualización en bloque
@Modifying
@Query("UPDATE Ejemplar e SET e.disponible = false WHERE e.id IN :ids")
int marcarNoDisponibles(@Param("ids") Collection<Long> ids);
en este ejemplo

Este fragmento presupone la entidad Ejemplar y las importaciones de Spring Data JPA y java.util.Collection. @Modifying hace que la consulta declarada con @Query se ejecute como modificación; el valor int indica cuántas filas han sido afectadas.

La consulta debe ejecutarse dentro de una transacción de escritura, normalmente iniciada por un servicio con @Transactional. A diferencia de modificar una entidad gestionada, esta operación actúa directamente sobre los registros coincidentes y puede dejar desactualizados objetos que ya estaban cargados en el contexto de persistencia.

Podemos encontrar estos dos parámetros de @Modifying:

ParámetroValor por defectoEfecto
flushAutomaticallyfalseSi se activa, sincroniza cambios pendientes antes de ejecutar la consulta.
clearAutomaticallyfalseSi se activa, limpia el contexto de persistencia después de ejecutarla.

No conviene establecerlos siempre en true por costumbre. Limpiar el contexto separa las entidades gestionadas y, si no se han sincronizado los cambios pendientes, podemos perder modificaciones que todavía estaban solo en memoria.

7️⃣ Transacciones simultáneas: aislamiento y concurrencia​

🟩 Qué problema aparece cuando hay dos usuarios​

Supongamos que dos personas intentan reservar la última plaza libre de un taller. Cada una consulta si hay plazas disponibles y después intenta reservar. Aunque utilicemos una transacción por petición, necesitamos decidir cómo se coordinan las operaciones concurrentes para impedir que ambas consuman la misma plaza indebidamente.

El aislamiento es una parte de la solución. También pueden ser necesarios cambios en las consultas, condiciones de actualización, restricciones y mecanismos de bloqueo adecuados.

🟨 Niveles de aislamiento que debemos reconocer​

NivelIdea generalQué debemos recordar
READ_UNCOMMITTEDNivel muy débil de aislamiento.Puede permitir leer cambios todavía no confirmados, según el gestor.
READ_COMMITTEDLas lecturas no observan datos no confirmados de otras transacciones.Una consulta repetida puede encontrar un valor ya confirmado por otra transacción.
REPEATABLE_READOfrece mayor estabilidad de las lecturas dentro de la misma transacción.Es el nivel predeterminado habitual de InnoDB en MySQL, con matices según el tipo de consulta.
SERIALIZABLENivel más restrictivo.Reduce ciertas anomalías, a costa de mayor coordinación y posibles esperas.

Spring expresa estos valores mediante Isolation.READ_COMMITTED, Isolation.REPEATABLE_READ, etcétera. No cambiaremos el aislamiento por defecto de nuestro proyecto: primero debemos comprender el problema concreto y las garantías del gestor.

🟧 Bloqueo optimista con @Version​

Otro problema frecuente aparece cuando dos personas abren la edición del mismo registro, leen la misma información y la guardan en momentos diferentes. Una podría sobrescribir sin saberlo el cambio de la otra.

JPA permite incorporar un atributo de versión para detectar modificaciones concurrentes:

Atributo de control de versión en una entidad JPA
@Version
private Long version;
en este ejemplo

El proveedor JPA utiliza la versión para detectar si el estado del registro ha cambiado desde que se recuperó la entidad. Cuando la comprobación falla, se produce un error de bloqueo optimista en lugar de aceptar sin más una actualización sobre una versión obsoleta.

No basta con añadir @Version a una entidad para resolver todos los formularios de edición. Si queremos detectar que el usuario guardó una versión antigua, debemos conservar y comprobar la versión que estaba viendo al abrir el formulario. Es una posibilidad de ampliación que no implementaremos en el ejemplo principal.

aviso

@Transactional no impide automáticamente todas las pérdidas de actualización. Las transacciones establecen unidades de trabajo; para determinadas situaciones concurrentes necesitaremos además reglas de bloqueo, versiones o actualizaciones condicionadas.

8️⃣ Cómo decidimos y comprobamos una transacción​

🟩 Un procedimiento que podemos utilizar en otros proyectos​

Cuando aparezca una operación que modifica información persistente, nos plantearemos las siguientes cuestiones:

  1. ¿Qué acción completa desea realizar el usuario? Por ejemplo, devolver un préstamo, confirmar un pedido o matricular a una persona.
  2. ¿Qué consultas y modificaciones necesita? Identificamos las entidades y los repositorios implicados.
  3. ¿Qué cambios deben confirmarse juntos? Esa es la unidad de trabajo que normalmente expresaremos en un método de servicio.
  4. ¿Qué comprobaciones de negocio deben realizarse antes de escribir? Consideramos también que otra transacción puede modificar datos mientras trabajamos.
  5. ¿Qué fallos deben provocar un rollback? Revisamos los tipos de excepción y evitamos ocultar errores que deben cancelar la operación.
  6. ¿Cómo comprobaremos el resultado? Preparamos casos de éxito, error previo y error después de realizar alguna escritura.

Por ejemplo, imaginemos que una tienda confirma un pedido y descuenta las unidades disponibles de varios productos. Si no se puede completar el descuento de todas las unidades, debemos decidir si corresponde cancelar toda la confirmación. La respuesta no depende de cómo se llame el repositorio, sino de las reglas del negocio.

🟨 Qué probamos para saber si funciona​

No basta con comprobar que un método tiene @Transactional. Necesitamos evidencias de que el conjunto se comporta correctamente:

CasoAcción de pruebaResultado esperado
Operación correcta.Ejecutamos todos los pasos sin fallo.Todos los cambios quedan confirmados.
Error antes de modificar datos.Indicamos un préstamo que no existe.No se modifica ningún registro.
Error después de la primera modificación.Provocamos una RuntimeException antes del segundo paso.Tras terminar la llamada, los registros conservan el estado anterior.
Restricción incumplida.Intentamos guardar una clave ajena inexistente.La base de datos rechaza el cambio.
Dos peticiones simultáneas.Reproducimos una operación que compite por el mismo recurso.Analizamos si hacen falta medidas adicionales de concurrencia.

Estas comprobaciones deben realizarse sobre una base de pruebas separada, no sobre los registros que queremos conservar. En una aplicación Spring Boot podemos automatizarlas mediante pruebas de integración con JUnit.

🟧 Errores frecuentes al utilizar transacciones​

🟩 Anotar un método que Spring no intercepta​

La gestión declarativa habitual funciona mediante componentes gestionados por Spring. Una llamada desde un método a otro método de la misma instancia no pasa normalmente por el mecanismo que aplica @Transactional. Para empezar, declararemos métodos públicos de servicio y los invocaremos desde otro componente, como un controlador o un servicio diferente.

🟨 Pensar que cada save() confirma la operación completa​

Cuando existe una transacción exterior iniciada en el servicio, las llamadas a save() participan normalmente en ella. La confirmación del conjunto llega al finalizar esa unidad de trabajo, no después de cada escritura.

🟧 Ocultar excepciones con un catch​

Si el segundo paso falla, no basta con mostrar el error y terminar como si nada. Debemos asegurarnos de que el fallo cancela la operación que no puede quedar incompleta.

🟥 Confundir flush() con commit​

flush() sincroniza el contexto de persistencia con la base de datos, pero no confirma por sí mismo una transacción que todavía está activa. Todavía puede producirse un rollback.

🟪 Utilizar transacciones para corregir reglas que faltan​

Una transacción no sustituye la validación del formulario, las claves ajenas o la comprobación del estado de un pedido. Todos esos mecanismos se complementan.

Para recordar

Una transacción agrupa los cambios que deben confirmarse o deshacerse conjuntamente. En Spring Boot delimitamos normalmente esa operación con @Transactional en un método de servicio, pero debemos decidir también qué errores cancelan la operación y qué reglas garantizan la integridad de los datos.
