4.2. Pruebas y buenas prácticas de persistencia

Nuestra aplicación MiColección ya permite gestionar videojuegos, buscar y paginar resultados y relacionarlos con plataformas. También hemos aprendido a identificar operaciones que requieren transacciones. Hemos comprobado algunas de estas funciones desde el navegador y mediante consultas a MySQL, pero nos queda una cuestión importante: ¿cómo podemos detectar que una operación ha dejado de funcionar después de modificar nuestro código?

En este último apartado aprenderemos a comprobar la persistencia de forma más sistemática. Introduciremos pruebas automatizadas sencillas, revisaremos las consultas SQL generadas por Hibernate y recogeremos algunas precauciones que conviene aplicar antes de considerar terminada una aplicación.

Idea principal

Que una aplicación arranque no significa que funcione correctamente. Debemos comprobar tanto los resultados esperados como los casos problemáticos: búsquedas sin coincidencias, relaciones inexistentes, restricciones y operaciones que deben deshacerse ante un error.

1️⃣ ¿Qué necesitamos comprobar?​

Hasta ahora hemos trabajado con tres componentes: el controlador recibe peticiones, el servicio organiza las operaciones y aplica reglas de negocio, y el repositorio accede a MySQL mediante Spring Data JPA. Podemos comprobar cada uno de ellos de manera diferente.

🟩 Pruebas manuales y automatizadas​

Cuando añadimos un videojuego desde un formulario y comprobamos que aparece en el listado, estamos realizando una prueba funcional manual. Es útil porque permite verificar el recorrido completo, desde la petición HTTP hasta la base de datos.

Una prueba automatizada es un método Java que prepara una situación, ejecuta una operación y comprueba su resultado. Podemos repetirla después de modificar el proyecto, sin introducir los mismos datos manualmente cada vez.

Qué comprobamosEjemplo en MiColecciónCómo lo probaremos
RepositorioSe guarda un videojuego y podemos recuperarlo por su ID.Prueba JPA con MySQL.
ConsultaUna búsqueda por género devuelve los registros adecuados.Prueba JPA con MySQL.
RestriccionesNo se repite el nombre de una plataforma ni se elimina una plataforma con videojuegos.Prueba JPA con MySQL.
ServicioNo se intenta guardar un videojuego con una plataforma inexistente.Prueba de servicio con un repositorio simulado.
Aplicación webEl formulario guarda, redirige y muestra los datos.Comprobación desde el navegador.
IntegridadUna operación que modifica varios registros se deshace si falla uno de los pasos.Prueba transaccional en un caso preparado para ello.

No necesitamos probarlo todo mediante el mismo mecanismo. Por ejemplo, una prueba de repositorio necesita comprobar el acceso real a la base de datos, mientras que una regla del servicio puede comprobarse sin arrancar MySQL.

🟨 ¿Qué tipo de prueba conviene utilizar?​

En este apartado distinguiremos dos niveles de pruebas automatizadas. La elección depende de qué queremos demostrar, no de cuál sea más fácil de escribir.

Tipo de pruebaQué ejecuta realmenteQué permite comprobarQué no demuestra por sí sola
Unitaria de servicioUna clase Java real con colaboradores simulados mediante Mockito.Decisiones y reglas del servicio, como rechazar una plataforma inexistente.Que la consulta SQL funcione o que MySQL respete una restricción.
Integración de repositorioRepositorios, Hibernate y una base de datos MySQL real.Persistencia, consultas derivadas, mapeos y restricciones.Que el formulario o la vista Thymeleaf funcionen correctamente.

Las pruebas manuales desde el navegador siguen siendo necesarias para verificar las rutas, los formularios y la presentación. No sustituimos un tipo de prueba por otro: los combinamos según la responsabilidad que queremos comprobar.

🟧 Cómo diseñamos una prueba: preparar, actuar y comprobar​

Antes de escribir código, conviene formular una frase concreta: «Si guardamos un videojuego con una plataforma válida, al buscarlo por su ID recuperamos sus datos». A partir de ella organizamos la prueba en tres momentos, conocidos como AAA (Arrange, Act, Assert):

  1. Preparar (Arrange). Creamos los datos y las condiciones iniciales necesarias, sin depender de registros que dejó otra prueba.
  2. Actuar (Act). Ejecutamos el método o la operación que queremos comprobar.
  3. Comprobar (Assert). Verificamos el resultado esperado mediante una aserción, como assertEquals(); si no se cumple, la prueba falla.

Por ejemplo, para comprobar una búsqueda sin coincidencias prepararemos datos de otros géneros, ejecutaremos la búsqueda y verificaremos que devuelve una lista vacía. Una prueba no está completa simplemente porque el método se ejecute sin lanzar errores.

consejo

Los nombres de los métodos de prueba deberían explicar su comportamiento: noPermiteDosPlataformasConElMismoNombre() comunica mucho más que test3(). Así podemos entender qué ha fallado al leer los resultados de JUnit.

🟥 Qué comprobaremos primero​

Nos centraremos en pruebas sencillas: guardar y recuperar un Videojuego con su Plataforma, comprobar que MySQL hace respetar las restricciones de integridad y comprobar una regla del servicio. Después volveremos a las pruebas manuales para verificar el funcionamiento de las vistas Thymeleaf.

Una buena batería combina casos correctos, casos sin resultados y situaciones de error:

Situación preparadaOperaciónResultado que esperamos
Plataforma válida y videojuego nuevo.Guardar y buscar por ID.Se recuperan el título y la plataforma guardados.
Dos videojuegos de géneros distintos.Buscar por un género.Solo aparece el que cumple el filtro.
No existe ningún videojuego del género buscado.Buscar por ese género.Se devuelve una lista vacía, sin excepción.

En el código guiado implementaremos cuatro pruebas de repositorio y una de servicio. Los restantes casos nos servirán para diseñar comprobaciones autónomas después.

2️⃣ Preparamos un entorno de pruebas separado​

No ejecutaremos pruebas que creen o borren tablas sobre mi_coleccion, porque contiene los videojuegos de nuestras prácticas. Utilizaremos una segunda base de datos, mi_coleccion_test, dentro del mismo servidor MySQL instalado en Windows.

Esto no supone instalar otra versión de MySQL ni configurar otro servicio. Un mismo servidor puede alojar varias bases de datos independientes.

🟩 Creamos la base de datos de pruebas​

Con el servicio MySQL de Windows iniciado, abrimos PowerShell y entramos en MySQL con el usuario administrador:

mysql -u root -p

Introducimos la contraseña de root que establecimos durante la instalación con MySQL Configurator. Dentro de MySQL ejecutamos:

CREATE DATABASE IF NOT EXISTS mi_coleccion_test
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;

GRANT ALL PRIVILEGES ON mi_coleccion_test.*
TO 'coleccion_app'@'localhost';
en este ejemplo

Creamos una segunda base de datos y permitimos que el usuario coleccion_app, que ya utilizamos en Spring Boot, pueda preparar las tablas necesarias para nuestras pruebas.

Los permisos se conceden solo sobre mi_coleccion_test, no sobre todas las bases de datos del servidor. Esta configuración corresponde a nuestro entorno local de aprendizaje; en una aplicación real utilizaríamos cuentas y permisos específicos para cada entorno.

Podemos comprobar que existe mediante SHOW DATABASES; y salir del cliente escribiendo EXIT;.

Dos bases con finalidades distintas

mi_coleccion conserva los videojuegos del proyecto. mi_coleccion_test es un entorno desechable que puede recrearse para ejecutar pruebas. El perfil de pruebas debe apuntar siempre a la segunda, especialmente porque en él utilizaremos ddl-auto=create-drop.

La separación de bases nos protege ante errores de configuración, pero no convierte cualquier instrucción en inofensiva. Antes de ejecutar pruebas que alteran tablas, comprobaremos la URL de conexión.

🟨 Protegemos todas las ejecuciones de pruebas, no solo una clase​

Spring Initializr suele crear una clase MiColeccionApplicationTests con @SpringBootTest. Si existe y ejecutamos todas las pruebas con mvnw.cmd test, también se ejecutará. No debemos dar por hecho que usa el perfil test simplemente porque se encuentre en src/test/java. Por eso configuraremos también una conexión segura por defecto para las pruebas.

Primero revisamos ese archivo. Si no lo necesitamos para estas prácticas, podemos eliminarlo. Si queremos conservar la comprobación de arranque, lo dejamos así:

src/test/java/com/dwes/mi_coleccion/MiColeccionApplicationTests.java
package com.dwes.mi_coleccion;

import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.ActiveProfiles;

@SpringBootTest
@ActiveProfiles("test")
class MiColeccionApplicationTests {

    @Test
    void contextLoads() {
        // Comprueba que se inicia el contexto de Spring.
    }
}
Comprobación imprescindible antes de ejecutar

Revisaremos todas las clases que utilicen @SpringBootTest, @DataJpaTest u otras pruebas que arranquen Spring. Cada una debe apuntar a mi_coleccion_test mediante el perfil y las propiedades adecuados. No debe haber pruebas de integración conectándose a mi_coleccion.

Antes de ejecutar un test que cambie tablas, comprobaremos en su configuración que la URL termina en /mi_coleccion_test. Si no podemos asegurarlo, no ejecutaremos la prueba. El comando mvnw.cmd test no proporciona aislamiento por sí solo.

🟧 Añadimos las dependencias de pruebas​

En la sección <dependencies> del archivo pom.xml añadimos el siguiente starter si todavía no está presente:

pom.xml (dependencia adicional de pruebas)
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa-test</artifactId>
    <scope>test</scope>
</dependency>
en este ejemplo

En Spring Boot 4, spring-boot-starter-data-jpa-test aporta las herramientas de prueba para Spring Data JPA y las bibliotecas habituales de pruebas, entre ellas JUnit y Mockito. Maven seleccionará las versiones compatibles con nuestro proyecto.

El ámbito test indica que esta dependencia se utiliza para ejecutar las pruebas, no para el funcionamiento normal de la aplicación. Si el proyecto ya contiene otras dependencias de pruebas, podemos conservarlas; no necesitamos añadir H2.

Después de guardar pom.xml, recargamos el proyecto Maven desde IntelliJ IDEA.

🟥 Herramientas de prueba: ¿qué aporta cada una?​

HerramientaPara qué la utilizaremos
JUnit JupiterEjecutar métodos marcados con @Test y comprobar resultados con aserciones.

No tenemos que instalar estos componentes como aplicaciones independientes. Se incorporan como dependencias de pruebas y se ejecutan desde IntelliJ IDEA o Maven. En Spring Boot 4, el starter específico de JPA proporciona también el soporte general de pruebas.

🟪 Configuramos la conexión y el perfil de pruebas​

Vamos a utilizar dos archivos exclusivos de src/test/resources/. Esta organización nos permite añadir una protección: incluso si una clase de test olvida activar el perfil test, su configuración básica seguirá apuntando a mi_coleccion_test, nunca a la colección habitual.

Primero creamos la configuración general de los tests:

src/test/resources/application.properties
spring.datasource.url=jdbc:mysql://localhost:3306/mi_coleccion_test
spring.datasource.username=coleccion_app
spring.datasource.password=${DB_PASSWORD}

spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
en este ejemplo

No es el archivo principal de la aplicación. El application.properties de src/main/resources/ permanece intacto. El archivo de src/test/resources/ se utiliza al ejecutar las pruebas y establece otra base de datos. Hemos elegido validate como configuración de seguridad: si una prueba no activa el perfil previsto y el esquema no está preparado, preferimos que falle antes de intentar crearlo o borrarlo.

Ahora creamos el archivo específico del perfil test, que cambia únicamente la forma de preparar el esquema:

src/test/resources/application-test.properties
spring.jpa.hibernate.ddl-auto=create-drop
aviso

create-drop solo debe actuar sobre mi_coleccion_test. Permite crear las tablas de prueba y eliminarlas cuando se cierra el contexto. Nunca copiaremos esta configuración a src/main/resources/application.properties ni ejecutaremos pruebas destructivas si la URL apunta a mi_coleccion.

La configuración de prueba reduce el riesgo de errores, pero no impide que otra clase o una propiedad sobrescrita indique una conexión diferente. Antes de lanzar toda la batería comprobaremos también las anotaciones y las URL de conexión.

Añadiremos @ActiveProfiles("test") a las clases de integración para que se cargue el segundo archivo. La contraseña seguirá llegando desde DB_PASSWORD, igual que en la ejecución habitual de la aplicación.

en este ejemplo

Cuando activamos el perfil test, Spring utiliza la conexión definida en src/test/resources/application.properties y aplica encima el cambio ddl-auto=create-drop de application-test.properties. Así mantenemos separada la base de trabajo y no dependemos únicamente de que todas las clases lleven una anotación concreta.

create-drop gestiona las tablas durante la vida del contexto JPA. Por otra parte, cada método @DataJpaTest suele ejecutarse dentro de una transacción que se revierte al terminar. Son dos mecanismos distintos: uno prepara el esquema y el otro revierte las modificaciones hechas durante cada prueba.

3️⃣ Nuestra primera prueba de repositorio​

Vamos a comprobar que podemos guardar un videojuego asociado a una plataforma y recuperarlo posteriormente. También probaremos una consulta por género y dos restricciones de integridad: el nombre único de cada plataforma y la clave ajena que la relaciona con los videojuegos.

🟩 Creamos la clase de prueba​

En una prueba de repositorio distinguimos claramente los datos de partida, la operación del repositorio y la aserción. Para que la primera prueba compruebe mejor la lectura desde MySQL, después de guardar el registro limpiaremos el contexto de persistencia con TestEntityManager.clear(). Eso evita que la búsqueda recupere únicamente la entidad que ya estaba cargada en memoria.

Dentro de src/test/java/com/dwes/mi_coleccion/repositorios/ creamos VideojuegoRepositoryTest.java:

src/test/java/com/dwes/mi_coleccion/repositorios/VideojuegoRepositoryTest.java
package com.dwes.mi_coleccion.repositorios;

import com.dwes.mi_coleccion.modelo.Plataforma;
import com.dwes.mi_coleccion.modelo.Videojuego;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest;
import org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase;
import org.springframework.boot.jpa.test.autoconfigure.TestEntityManager;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.test.context.ActiveProfiles;

import java.util.List;

import static org.junit.jupiter.api.Assertions.*;

@DataJpaTest
@ActiveProfiles("test")
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
class VideojuegoRepositoryTest {

    private final VideojuegoRepository videojuegos;
    private final PlataformaRepository plataformas;
    private final TestEntityManager entityManager;

    @Autowired
    VideojuegoRepositoryTest(VideojuegoRepository videojuegos,
                             PlataformaRepository plataformas,
                             TestEntityManager entityManager) {
        this.videojuegos = videojuegos;
        this.plataformas = plataformas;
        this.entityManager = entityManager;
    }

    @Test
    void guardaYRecuperaUnVideojuego() {
        Plataforma pc = plataformas.save(new Plataforma("PC"));
        Videojuego nuevo = new Videojuego(
                "Celeste", "Plataformas", pc, 2018);

        Videojuego guardado = videojuegos.saveAndFlush(nuevo);
        Long idGuardado = guardado.getId();
        entityManager.clear();

        Videojuego recuperado = videojuegos.findById(idGuardado)
                .orElseThrow();

        assertNotNull(guardado.getId());
        assertEquals("Celeste", recuperado.getTitulo());
        assertEquals(pc.getId(), recuperado.getPlataforma().getId());
    }

    @Test
    void buscaPorGeneroSinDistinguirMayusculas() {
        Plataforma pc = plataformas.save(new Plataforma("PC"));
        videojuegos.save(new Videojuego("Celeste", "Plataformas", pc, 2018));
        videojuegos.save(new Videojuego("Hollow Knight", "Aventura", pc, 2017));

        List<Videojuego> resultado = videojuegos.findByGeneroIgnoreCase("AVENTURA");

        assertEquals(1, resultado.size());
        assertEquals("Hollow Knight", resultado.get(0).getTitulo());
    }

    @Test
    void noPermiteDosPlataformasConElMismoNombre() {
        plataformas.saveAndFlush(new Plataforma("PC"));

        assertThrows(DataIntegrityViolationException.class,
                () -> plataformas.saveAndFlush(new Plataforma("PC")));
    }

    @Test
    void noPermiteEliminarUnaPlataformaConVideojuegos() {
        Plataforma pc = plataformas.save(new Plataforma("PC"));
        videojuegos.saveAndFlush(new Videojuego("Celeste", "Plataformas", pc, 2018));

        assertThrows(DataIntegrityViolationException.class, () -> {
            plataformas.delete(pc);
            plataformas.flush();
        });
    }
}
en este ejemplo

@DataJpaTest prepara un contexto de prueba centrado en las entidades y los repositorios JPA, sin levantar nuestra aplicación web completa. En Spring Boot 4 esta anotación pertenece al paquete org.springframework.boot.data.jpa.test.autoconfigure.

@ActiveProfiles("test") activa la configuración de application-test.properties. Con @AutoConfigureTestDatabase(replace = ...NONE) indicamos que las pruebas deben utilizar nuestra conexión MySQL de prueba y que Spring no debe sustituirla por una base de datos incrustada.

@Autowired permite que Spring suministre los repositorios y TestEntityManager al constructor de la clase de prueba, igual que inyectamos dependencias en nuestros componentes. TestEntityManager es una utilidad específica de pruebas JPA que nos permite, entre otras cosas, limpiar el contexto de persistencia.

@Test señala cada método que JUnit debe ejecutar. Las comprobaciones assertNotNull() y assertEquals() hacen que la prueba falle si el resultado no es el esperado. No basta con ejecutar un método: debemos comprobar su comportamiento.

Las dos últimas pruebas comprueban lo contrario: que una operación falla cuando debe fallar. assertThrows() ejecuta el código indicado y solo se supera si se produce la excepción esperada. DataIntegrityViolationException es la excepción con la que Spring representa que MySQL ha rechazado una operación por incumplir una restricción: aquí, la unicidad del nombre y la clave ajena plataforma_id.

Al utilizar saveAndFlush() o flush() forzamos la sincronización con MySQL durante la prueba. Sin ellos, algunas operaciones no llegarían a enviarse a la base de datos antes de que la prueba revierta sus cambios, y la restricción no se comprobaría nunca. Recordemos que flush no equivale a commit.

🟨 Leemos las pruebas con un criterio común​

PruebaPreparaciónAcciónComprobación
guardaYRecuperaUnVideojuego()Creamos una plataforma y un videojuego.Guardamos, limpiamos el contexto y buscamos por ID.El identificador, título y plataforma coinciden.
buscaPorGeneroSinDistinguirMayusculas()Guardamos videojuegos de dos géneros.Buscamos con "AVENTURA".Se obtiene un único resultado con el título esperado.
noPermiteDosPlataformasConElMismoNombre()Existe una plataforma "PC".Intentamos insertar otra "PC".La restricción de unicidad provoca una excepción.
noPermiteEliminarUnaPlataformaConVideojuegos()Hay un videojuego relacionado.Intentamos eliminar su plataforma y sincronizamos.La clave ajena impide el borrado.

En las dos primeras esperamos un resultado correcto. En las dos últimas, el comportamiento correcto es que MySQL rechace la operación: una prueba puede estar superada aunque su código haya provocado deliberadamente una excepción.

🟧 Aserciones de JUnit que conviene conocer​

Las aserciones se utilizan para expresar qué debe cumplirse. Podemos elegir entre estas opciones habituales:

MétodoQué compruebaEjemplo
assertEquals(esperado, real)Dos valores son iguales.assertEquals(2, lista.size()).
assertNotNull(valor)Existe un valor distinto de null.assertNotNull(juego.getId()).
assertTrue(condicion)Una condición se cumple.assertTrue(resultado.isEmpty()).
assertFalse(condicion)Una condición no se cumple.assertFalse(lista.isEmpty()).
assertThrows(Tipo.class, accion)Una operación lanza la excepción indicada.assertThrows(IllegalArgumentException.class, () -> servicio.crear(form)).
aviso

Una aserción debe comprobar algo relevante. Por ejemplo, verificar que findById() devuelve un objeto con el mismo título y la misma plataforma es más útil que comprobar únicamente que no ha lanzado una excepción.

Las pruebas que provocan errores de integridad fuerzan un flush() para que MySQL compruebe realmente las restricciones. Esos errores dejan sin utilidad la transacción de prueba afectada; no seguiremos intentando guardar más entidades dentro de ese mismo método después de provocar la excepción.

¿Quedan guardados los videojuegos de prueba?

Las pruebas con @DataJpaTest son transaccionales y, por defecto, revierten sus cambios al finalizar cada método de prueba. Por tanto, los videojuegos que creamos en un test no deberían aparecer como registros permanentes en la base de pruebas.

Además, al utilizar mi_coleccion_test mantenemos la base de datos habitual al margen de estas comprobaciones. Son dos medidas distintas de protección.

Ejecución segura de Maven

Si queremos activar expresamente el perfil de pruebas al ejecutar Maven desde PowerShell, podemos utilizar:

.\mvnw.cmd -Dspring.profiles.active=test test

Esta opción no sustituye la revisión de todas las clases de prueba ni la comprobación de la URL de MySQL: evita un descuido frecuente, pero debemos seguir verificando los perfiles y la configuración de las conexiones.

🟨 Ejecutamos las pruebas​

Primero comprobamos que el servicio MySQL de Windows está iniciado. Después ejecutamos la prueba desde el icono situado junto a la clase o sus métodos en IntelliJ IDEA.

Si IntelliJ no encuentra DB_PASSWORD, debemos incorporarla también a la configuración de ejecución de JUnit, porque no todas las configuraciones de ejecución comparten automáticamente las mismas variables de entorno.

Como alternativa, desde PowerShell podemos ejecutar las pruebas mediante Maven. En la carpeta del proyecto mi-coleccion, escribimos:

$env:DB_PASSWORD = "TU_CONTRASENA_LOCAL"
.\mvnw.cmd test

Sustituimos el texto por la contraseña de coleccion_app. Esta asignación afecta a la sesión actual de PowerShell: no la escribiremos en el código ni la subiremos a Git.

Si todo funciona, veremos cuatro pruebas superadas en VideojuegoRepositoryTest. Si alguna falla, IntelliJ o Maven mostrará qué método ha fallado y la causa. No debemos corregir una prueba cambiando el resultado esperado simplemente para que aparezca en verde.

🟥 Cómo interpretar una prueba que falla​

Antes de cambiar código, distinguiremos tres situaciones:

ResultadoQué revisamos primero
Error de conexiónServicio MySQL de Windows (con el nombre que tenga en nuestro equipo), URL de mi_coleccion_test, usuario, permisos y DB_PASSWORD.
Error al iniciar el contexto JPAPaquetes e imports de Spring Boot 4, mapeo de entidades, dependencia de pruebas y esquema de test.
Aserción no satisfechaDatos preparados, resultado esperado y comportamiento del método; no cambiaremos la aserción para ocultar un defecto.

La prueba de servicio del apartado siguiente se ejecuta sin conectarse a MySQL. Si esa prueba funciona y las de repositorio no, podemos orientar la investigación hacia la configuración o el acceso real a datos, aunque todavía tendremos que comprobar cuál es la causa concreta.

4️⃣ Comprobamos una regla del servicio sin utilizar MySQL​

No todas las pruebas necesitan conectarse a una base de datos. Si queremos comprobar una decisión del servicio, podemos sustituir temporalmente sus repositorios por objetos simulados (mocks).

Al incorporar la relación con Plataforma establecimos que, para crear un videojuego, el servicio debe localizar primero la plataforma indicada. Si no existe, el servicio debe impedir que se guarde el videojuego.

🟩 Probamos ese comportamiento​

Creamos esta segunda clase:

src/test/java/com/dwes/mi_coleccion/servicios/VideojuegoServiceTest.java
package com.dwes.mi_coleccion.servicios;

import com.dwes.mi_coleccion.formularios.VideojuegoForm;
import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.repositorios.PlataformaRepository;
import com.dwes.mi_coleccion.repositorios.VideojuegoRepository;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.util.Optional;

import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
class VideojuegoServiceTest {

    @Mock
    private VideojuegoRepository videojuegos;

    @Mock
    private PlataformaRepository plataformas;

    @InjectMocks
    private VideojuegoService servicio;

    @Test
    void noGuardaUnVideojuegoSiLaPlataformaNoExiste() {
        VideojuegoForm form = new VideojuegoForm();
        form.setTitulo("Celeste");
        form.setGenero("Plataformas");
        form.setPlataformaId(999L);
        form.setAnioLanzamiento(2018);

        when(plataformas.findById(999L)).thenReturn(Optional.empty());

        assertThrows(IllegalArgumentException.class,
                () -> servicio.crear(form));

        verify(videojuegos, never()).save(any(Videojuego.class));
    }
}
en este ejemplo

Mockito permite simular colaboradores de una clase. @Mock crea repositorios simulados y @InjectMocks los proporciona al constructor de VideojuegoService.

Preparamos un VideojuegoForm con datos válidos salvo la plataforma, que no existe. Mediante when(...).thenReturn(...) indicamos que su búsqueda no debe encontrar resultados. Con assertThrows() comprobamos que el servicio rechaza la operación y con verify(..., never()) confirmamos que no se ha intentado guardar ningún videojuego.

Esta prueba es rápida porque no necesita arrancar Spring Boot ni conectarse a MySQL. Sin embargo, no comprueba las consultas SQL ni las transacciones reales. Por eso es complementaria a las pruebas del repositorio, no un sustituto.

🟨 Cómo se construye una prueba de servicio con Mockito​

A diferencia del repositorio, VideojuegoService sí es código escrito por nosotros: tiene reglas que podemos comprobar de forma aislada. Estas son las piezas del ejemplo:

ElementoFunción dentro de la prueba
@ExtendWith(MockitoExtension.class)Activa la integración de Mockito con JUnit.
@MockCrea una dependencia simulada, como PlataformaRepository.
@InjectMocksConstruye el servicio e incorpora sus colaboradores simulados.
when(...).thenReturn(...)Define qué debe responder el repositorio simulado.
verify(...)Comprueba que se haya realizado una llamada esperada.
never()Expresa que una operación no debía ejecutarse.

No debemos confundir when(...) con una consulta a MySQL: la respuesta la hemos preparado nosotros. Un mock puede responder Optional.empty() aunque exista una plataforma con ese ID en la base real, porque aquí no consultamos ninguna tabla.

🟧 Otro caso que podríamos probar​

Sin escribir una segunda clase de prueba completa, podemos plantear una situación opuesta: si la plataforma sí existe, crear(form) debería construir el videojuego y llamar a videojuegos.save(...) con una entidad cuya plataforma sea la elegida.

En ese caso prepararíamos when(plataformas.findById(...)) para que devuelva una Plataforma y verificaríamos la llamada a save(). Este diseño comprueba nuestra decisión de negocio, mientras que la integración real con MySQL ya se comprueba en el apartado 3.

5️⃣ Observamos las consultas SQL que ejecuta Hibernate​

Cuando utilizamos findAll(), una consulta paginada o una relación entre entidades, Spring Data JPA y Hibernate se encargan de preparar las operaciones necesarias. Pero podemos observar el SQL que llega a MySQL para comprender mejor su funcionamiento.

🟩 Activamos el registro SQL durante el desarrollo​

Podemos añadir temporalmente estas propiedades al archivo principal de configuración:

src/main/resources/application.properties (propiedades temporales para depuración)
logging.level.org.hibernate.SQL=DEBUG
# Solo si necesitamos ver los valores de los parámetros:
logging.level.org.hibernate.orm.jdbc.bind=TRACE
en este ejemplo

El primer nivel muestra las sentencias SQL generadas por Hibernate. El segundo permite observar los valores que se asignan a sus parámetros JDBC.

Por ejemplo, podemos comprobar si una búsqueda por género produce un SELECT con condiciones o si actualizar un videojuego provoca un UPDATE. También podremos observar si acceder a las plataformas relacionadas provoca consultas adicionales.

aviso

El registro de parámetros puede mostrar datos sensibles introducidos en formularios o consultados desde la base de datos. Lo activaremos únicamente para depurar nuestra aplicación local y lo desactivaremos después.

No debemos confundir observar el SQL con escribirlo nosotros: Spring Data JPA y Hibernate siguen gestionando el acceso a los datos.

🟨 ¿Qué debemos observar?​

Podemos revisar tres situaciones conocidas:

  • Una búsqueda paginada debe recuperar un conjunto limitado de registros, en lugar de cargar todo el catálogo para dividirlo después en Java.
  • Al editar un videojuego debemos observar una operación de actualización, no una inserción accidental de una nueva fila.
  • Al mostrar títulos junto con sus plataformas, conviene comprobar si se realizan consultas adicionales innecesarias. Para ello utilizamos @EntityGraph en las consultas que necesitan cargar esa relación.

No tenemos que estudiar planes de ejecución avanzados. Por ahora basta con relacionar una acción de nuestra aplicación con las operaciones SQL que realmente produce.

🟧 Una pauta para investigar consultas innecesarias​

Cuando una operación tarda demasiado o genera más consultas de las esperadas, seguiremos esta secuencia:

  1. Reproducir la acción. Por ejemplo, abrir la lista de videojuegos con diez registros.
  2. Observar el SQL. Comprobar cuántos SELECT aparecen y a qué tablas se dirigen.
  3. Identificar el motivo. Si aparece un SELECT adicional por cada plataforma consultada, puede existir un problema de carga de relaciones de tipo N+1.
  4. Revisar la consulta JPA. En nuestro listado utilizamos @EntityGraph(attributePaths = "plataforma") porque sabemos que Thymeleaf necesita mostrar ese dato.
  5. Repetir la comprobación. Verificar que el listado sigue mostrando las plataformas y que ya no se generan consultas adicionales innecesarias.

Esta pauta no significa que cada SELECT adicional sea un error. Debemos analizar qué información necesita la vista y si la consulta es apropiada para esa necesidad.

6️⃣ Seguridad y buenas prácticas en el acceso a datos​

Una aplicación puede superar varias pruebas y seguir teniendo problemas si no tratamos adecuadamente las credenciales, las consultas, las restricciones o la evolución del esquema. La seguridad y la integridad de la información son parte de una persistencia bien diseñada. Reunimos aquí las medidas que hemos ido aplicando a lo largo de la unidad.

🟩 ¿Qué riesgo evita cada medida?​

Estas medidas responden a problemas diferentes. No basta con aplicar una sola de ellas:

MedidaProblema que ayuda a evitarEjemplo en MiColección
Validación de entradaDatos incompletos o con formato incorrecto.@NotBlank en VideojuegoForm.
Restricciones MySQLDatos que incumplen la estructura o las relaciones.UNIQUE en plataformas.nombre y clave ajena plataforma_id.
Consultas parametrizadasInyección SQL mediante valores del usuario.Parámetros :genero de @Query.
TransaccionesCambios parciales ante un fallo.Una devolución de préstamo con varias modificaciones coordinadas.
Credenciales con permisos limitadosAcceso innecesario a otras bases.Usuario coleccion_app para la aplicación.
Copias y separación de pruebasPérdida de datos durante cambios y pruebas.Respaldo previo a la migración y mi_coleccion_test.

Seguridad e integridad no son sinónimos. Proteger una contraseña no garantiza que dos registros mantengan una relación válida, y una clave ajena no evita que escribamos una consulta SQL vulnerable.

🟨 Diferenciamos responsabilidades​

El controlador recibe la petición, valida los datos del formulario y prepara una respuesta. El servicio expresa las operaciones y reglas del negocio. El repositorio proporciona acceso a la base de datos. Mantener esta separación hace más sencillo modificar el código y probar cada comportamiento.

La validación del formulario no sustituye las restricciones de la base de datos. Por ejemplo, un campo obligatorio puede necesitar una anotación de validación en Java y una columna NOT NULL en MySQL. Una relación entre entidades debe respetar, además, su clave ajena.

🟧 Protegemos la configuración y los datos​

  • Contraseñas: mantenemos DB_PASSWORD fuera de application.properties, no escribimos contraseñas en el código ni las subimos a Git.
  • Esquema: utilizamos ddl-auto=update únicamente para facilitar el desarrollo. No es una estrategia de migraciones fiable cuando existen datos importantes.
  • Copias de seguridad: antes de modificar tablas o relaciones, guardamos la información que necesitemos conservar, como hicimos antes de migrar las plataformas.
  • Servicio de Windows: MySQL puede iniciarse automáticamente con Windows. Detener el servicio no borra los registros, pero tampoco sustituye una copia de seguridad.
  • Datos de prueba: utilizamos la base mi_coleccion_test y nunca ejecutamos configuraciones destructivas sobre mi_coleccion.

🟥 Evitamos la inyección SQL​

La inyección SQL se produce cuando un valor introducido por el usuario se incorpora al texto de una consulta y acaba interpretándose como parte de la sentencia. Observa este ejemplo, que nunca debemos escribir:

❌ Ejemplo vulnerable: NO debemos hacer esto
String sql = "SELECT * FROM videojuegos WHERE genero = '" + genero + "'";
List<Videojuego> resultado = entityManager
        .createNativeQuery(sql, Videojuego.class)
        .getResultList();

Si alguien escribe en el buscador el texto x' OR '1'='1, la consulta resultante es:

SELECT * FROM videojuegos WHERE genero = 'x' OR '1'='1';

La condición '1'='1' siempre es verdadera, así que la consulta devuelve todos los registros. Con otras cadenas, un atacante podría intentar leer otras tablas o modificar datos.

en este ejemplo

En MiColección no hemos escrito nunca una consulta así. Todas nuestras consultas envían los valores del usuario como parámetros:

  • Los métodos derivados (findByGeneroIgnoreCase(genero)) y los métodos heredados de JpaRepository parametrizan los valores automáticamente.
  • En @Query, tanto JPQL como SQL nativo, utilizamos parámetros con nombre (:genero) vinculados con @Param.
  • En la ordenación, no aceptamos el nombre de una propiedad enviado por el navegador: el servicio solo admite las opciones titulo y anio.

Con parámetros, el gestor recibe por separado la sentencia y los valores. Aunque el valor contenga comillas o palabras SQL, se trata siempre como un dato, nunca como parte de la consulta.

🟪 Aplicamos el principio de mínimo privilegio​

Cada componente debe tener solo los permisos que necesita. En nuestro entorno lo hemos aplicado al configurar la conexión a MySQL:

MedidaCómo la aplicamos
Usuario propio para la aplicaciónSpring Boot se conecta como coleccion_app, no como root.
Permisos limitadoscoleccion_app solo tiene permisos sobre mi_coleccion y mi_coleccion_test, no sobre todo el servidor.
Acceso desde la aplicación localLa cuenta coleccion_app se creó para localhost. No necesitamos configurar accesos remotos; verificaremos la configuración del servidor y el cortafuegos si la red del equipo es compartida.
Credenciales fuera del códigoLa contraseña llega mediante DB_PASSWORD y no se sube a Git.

Si un atacante consiguiera aprovechar un fallo de la aplicación, sus posibilidades quedarían limitadas a lo que puede hacer coleccion_app. En un entorno de producción iríamos más allá: con las migraciones gestionadas por una herramienta como Flyway, el usuario de la aplicación ni siquiera necesitaría permisos para crear o eliminar tablas.

🟩 Tratamos los errores sin ocultarlos​

Debemos distinguir entre un dato que el usuario puede corregir y un fallo técnico. Por ejemplo, si se intenta editar un videojuego inexistente, la aplicación puede mostrar un mensaje comprensible y regresar al listado. En cambio, un fallo de conexión con MySQL debe quedar registrado para poder investigarlo, sin mostrar al usuario contraseñas ni detalles internos.

Al trabajar con transacciones, no debemos ocultar dentro del servicio una excepción que exige deshacer los cambios, para que Spring pueda revertir la operación.

Los errores de integridad merecen una atención especial. Si en otra aplicación incorporásemos una pantalla para eliminar plataformas, intentar borrar una plataforma con videojuegos asociados podría provocar una DataIntegrityViolationException, como hemos comprobado en las pruebas. El controlador podría capturarla y mostrar un mensaje comprensible:

Ejemplo conceptual: mostrar un error al eliminar una plataforma
try {
    plataformaService.eliminar(id);
    redirect.addFlashAttribute("mensaje", "Plataforma eliminada.");
} catch (DataIntegrityViolationException ex) {
    redirect.addFlashAttribute("error",
            "No se puede eliminar una plataforma que tiene videojuegos.");
}
return "redirect:/plataformas";
en este ejemplo

Capturamos la excepción en el controlador, fuera del método transaccional del servicio: así la transacción ya se ha revertido cuando decidimos qué mostrar.

No mostramos ex.getMessage(): el mensaje técnico de una excepción de integridad contiene nombres de tablas, columnas y restricciones que el usuario no necesita conocer. Sí podemos mostrar los mensajes de las IllegalArgumentException que lanza nuestro servicio, porque los hemos redactado nosotros para el usuario.

Para ofrecer una respuesta más precisa, el servicio puede comprobar antes la situación (por ejemplo, si ya existe una plataforma con ese nombre). Aun así, la restricción de MySQL sigue siendo la garantía final: dos peticiones simultáneas podrían superar la comprobación previa a la vez.

De los resultados de una consulta a una comprobación

Cuando un repositorio devuelve una List<Videojuego> o una Page<Videojuego>, podemos verificar que el conjunto de datos obtenido contiene precisamente los registros esperados. Por ejemplo, una prueba de búsqueda por género comprueba resultado.size() y el título del videojuego devuelto. La tabla MySQL sigue conservando los datos; la colección Java es el resultado que manipulamos en memoria.

7️⃣ Comprobación final de MiColección​

Antes de considerar terminada la aplicación, comprobaremos que sus funciones siguen operativas tras incorporar las relaciones. Las operaciones transaccionales que hemos estudiado con ejemplos independientes se comprobarán cuando formen parte de una aplicación concreta.

ComprobaciónQué debemos verificar
InicioSpring Boot conecta con el servicio MySQL de Windows sin errores.
PersistenciaLos videojuegos siguen disponibles después de reiniciar la aplicación.
CRUDPodemos crear, modificar y eliminar registros con los resultados esperados.
ValidaciónLos formularios muestran errores sin perder los datos introducidos.
ConsultasLos filtros, la ordenación y la paginación devuelven resultados correctos.
RelacionesCada videojuego muestra su plataforma y se respetan las claves ajenas.
TransaccionesEn una operación que modifica varios registros, comprobaríamos que los cambios se revierten si falla un paso.
SeguridadLas consultas usan parámetros, la aplicación usa coleccion_app y no hay contraseñas en el código ni en Git.
PruebasLos tests de repositorio y servicio finalizan correctamente.

La documentación de una aplicación no tiene por qué consistir en un documento extenso. Para nuestras prácticas bastará con dejar claro cómo se prepara el entorno, qué funciones ofrece la aplicación y cómo hemos comprobado que funcionan. Las pruebas automatizadas y las consultas SQL realizadas son evidencias que podemos describir de forma breve y precisa.

🟩 Cómo documentamos una comprobación​

Para que otra persona pueda repetir una prueba, es suficiente con describir qué se quería comprobar, cómo se preparó el caso, qué operación se ejecutó y qué resultado se obtuvo. Por ejemplo:

ElementoEjemplo de registro de prueba
ObjetivoImpedir dos plataformas con el mismo nombre.
Situación inicialExiste la plataforma PC.
AcciónIntentamos insertar otra PC.
Resultado esperadoMySQL rechaza la segunda inserción.
Resultado observadoLa prueba noPermiteDosPlataformasConElMismoNombre() supera assertThrows().

No es necesario incluir capturas de cada línea de código. En un proyecto bien documentado, los propios métodos de prueba son evidencias reproducibles, siempre que expresen claramente qué están comprobando.

🟨 Transferimos lo aprendido a otra aplicación​

Imaginemos un sistema de préstamos de una biblioteca. Antes de programar las pruebas, deberíamos ser capaces de diseñar al menos estos casos: recuperar un préstamo existente, obtener una lista vacía cuando no hay préstamos de una persona, impedir un préstamo asociado a un libro inexistente y comprobar que una operación de devolución no queda completada a medias si falla uno de sus pasos.

La comprobación es no evaluable y no requiere entrega. Se trata de decidir qué tipo de prueba utilizaríamos para cada caso, qué datos necesitaríamos preparar y qué aserción expresaría el resultado esperado. No tenemos que implementar ahora otra aplicación completa.

Para terminar la unidad

Hemos completado el recorrido desde los primeros objetos Java hasta una aplicación web con datos persistentes, repositorios, servicios, CRUD, consultas y relaciones. También hemos aprendido a planificar migraciones seguras, reconocer operaciones transaccionales y preparar pruebas reproducibles.

La idea final es sencilla: persistir datos no consiste únicamente en guardarlos. También debemos conservar su integridad, comprobar el comportamiento de la aplicación y proteger la información que ya existe.
