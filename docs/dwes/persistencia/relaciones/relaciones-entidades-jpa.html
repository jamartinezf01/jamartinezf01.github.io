3.1. Relaciones entre entidades JPA

En MiColección hemos aprendido a almacenar videojuegos en MySQL y a trabajar con ellos desde una aplicación Spring Boot: operaciones CRUD, consultas, filtros y paginación. Hasta ahora, cada registro se ha gestionado principalmente como una entidad independiente.

Sin embargo, las aplicaciones suelen trabajar con información relacionada. Una editorial publica varios libros, un pedido pertenece a un cliente y un libro puede clasificarse en varias categorías. En una base de datos relacional, estas asociaciones se representan mediante claves ajenas o tablas intermedias. En Java, nos interesa trabajar directamente con objetos relacionados.

En este apartado aprenderemos a interpretar y definir esas relaciones con JPA. Utilizaremos fragmentos pequeños de código para comprender las anotaciones, sin construir todavía una aplicación completa.

Idea principal

Antes de escribir una anotación JPA debemos conocer la cardinalidad de la relación, cómo se almacena en MySQL y en qué sentido necesitamos acceder a los objetos desde Java.

JPA relaciona objetos Java, pero la base de datos sigue almacenando identificadores y aplicando restricciones de integridad.

1️⃣ De las relaciones entre tablas a las relaciones entre objetos​

🟩 Una misma relación, tres representaciones​

Imaginemos que una editorial puede publicar muchos libros y que cada libro pertenece a una sola editorial.

En el modelo entidad-relación hablamos de una asociación 1:N desde Editorial hacia Libro. Al pasar al modelo relacional, la clave ajena se coloca en la tabla del lado N: libros.editorial_id hace referencia a editoriales.id.

En Java no necesitamos guardar esa referencia como un número aislado. Podemos declarar una propiedad cuyo tipo sea otra entidad:

Fragmento conceptual de Libro.java
private Editorial editorial;

De esta forma podremos escribir libro.getEditorial().getNombre() para acceder al nombre de la editorial. Cuando JPA guarde el libro, utilizará el identificador del objeto Editorial para mantener la asociación en MySQL.

ModeloCómo representa la relación
Entidad-relaciónUna editorial publica muchos libros (1:N).
Relacionallibros.editorial_id es clave ajena de editoriales.id.
JPALa propiedad Libro.editorial hace referencia a un objeto Editorial.
aviso

Una propiedad de relación no es una clave ajena escrita como atributo Java. En la entidad utilizamos Editorial editorial, no Long editorialId. Los identificadores sí serán útiles más adelante para recibir datos de los formularios.

🟨 Identificamos la cardinalidad​

Para reconocer una relación conviene formular dos preguntas: ¿con cuántos registros del otro tipo puede relacionarse uno de este tipo? ¿Y qué ocurre si miramos desde el extremo contrario?

CardinalidadEjemploRepresentación habitual en MySQL
1:1Un usuario tiene, como máximo, un perfil y cada perfil corresponde a un usuario.Una clave ajena con restricción UNIQUE.
1:N / N:1Una editorial publica muchos libros; cada libro pertenece a una editorial.Una clave ajena en la tabla del lado N.
N:MUn libro puede tener varias categorías y una categoría puede corresponder a muchos libros.Una tabla intermedia con dos claves ajenas.
RecursivaUna categoría puede tener una categoría superior.Una clave ajena que referencia la misma tabla.

1:N y N:1 son dos maneras de mirar la misma relación, no dos asociaciones independientes. Lo que cambia es desde qué entidad la estamos describiendo.

🟧 Cómo tomaremos las decisiones​

En cada caso seguiremos un procedimiento sencillo: identificaremos las entidades, estableceremos la cardinalidad, localizaremos la clave ajena o la tabla intermedia y, finalmente, elegiremos las propiedades y anotaciones Java. Después comprobaremos si la relación es obligatoria y qué debe ocurrir al eliminar registros relacionados.

No conviene comenzar escribiendo anotaciones al azar: JPA puede generar tablas, pero no puede decidir por nosotros las reglas del problema.

2️⃣ Relaciones muchos a uno y uno a muchos​

🟩 Empezamos por @ManyToOne: el lado que contiene la clave ajena​

Una relación entre una plataforma y sus videojuegos se puede representar de tres formas: modelo E/R, tablas MySQL y clases JPA. Esta ilustración procede del ejemplo conceptual que ya conocíamos, pero no implica modificar MiColección.

Aplicaremos la misma idea a la biblioteca. Cada libro necesita una editorial; la asociación se define en la entidad Libro:

Fragmento de Libro.java
@ManyToOne(optional = false)
@JoinColumn(name = "editorial_id", nullable = false)
private Editorial editorial;
en este ejemplo
  • @ManyToOne indica que muchos libros pueden compartir una misma editorial.
  • @JoinColumn(name = "editorial_id") indica que la clave ajena se almacena en la tabla libros, en una columna llamada editorial_id.
  • optional = false expresa que el libro debe tener una editorial asignada.
  • nullable = false indica que esa columna no debe admitir NULL.

El objeto Java es de tipo Editorial, aunque en MySQL se guarde su identificador.

La parte relevante de las tablas podría verse así:

🟨 La navegación puede ser unidireccional​

Con el fragmento anterior podemos obtener la editorial de un libro:

Editorial editorial = libro.getEditorial();

Pero la entidad Editorial no tiene por qué contener una colección de libros. Para recuperar los libros de una editorial podemos realizar una consulta desde LibroRepository.

A esto se le llama relación unidireccional: desde Libro navegamos hacia Editorial, pero no hemos definido el camino inverso. Es una opción válida y suele ser la más sencilla para empezar.

🟧 Si necesitamos el camino inverso, añadimos @OneToMany​

Si también queremos escribir editorial.getLibros(), podemos declarar una colección en la clase Editorial:

Fragmento opcional de Editorial.java
@OneToMany(mappedBy = "editorial")
private List<Libro> libros = new ArrayList<>();

Ahora la relación es bidireccional. No hemos creado una segunda relación en MySQL: seguimos utilizando la misma columna libros.editorial_id.

La expresión mappedBy = "editorial" indica que el mapeo de la clave ajena ya está definido en la propiedad Java editorial de la clase Libro. No se escribe mappedBy = "editorial_id", porque ese es el nombre de la columna SQL.

¿Qué es el lado propietario?

En una relación bidireccional, JPA distingue el lado propietario, que determina cómo se guarda la asociación, y el lado inverso, que permite recorrerla desde el otro extremo.

En nuestro ejemplo, Libro.editorial es el lado propietario porque ahí se encuentra el mapeo de la clave ajena; Editorial.libros es el lado inverso y utiliza mappedBy.

Si queremos asignar una editorial a un libro, lo importante es actualizar el lado propietario:

Asignamos una editorial existente a un libro
libro.setEditorial(editorial);

Cuando mantenemos también una colección inversa, conviene actualizar ambos lados en memoria. Por ejemplo, un método auxiliar agregarLibro(Libro libro) podría añadir el libro a la colección y llamar a libro.setEditorial(this). No hace falta implementar ese método en todas las aplicaciones: depende de si necesitamos mantener ambas referencias sincronizadas.

3️⃣ Relaciones muchos a muchos: @ManyToMany​

🟩 Por qué necesitamos una tabla intermedia​

Supongamos que varios videojuegos pueden compartir etiquetas como «Indie» o «Aventura», y que cada videojuego puede tener varias etiquetas. Ninguna de las dos tablas puede representar por sí sola todas las asociaciones utilizando una única clave ajena.

En este caso aparece una tabla videojuego_etiquetas. Cada fila contiene videojuego_id y etiqueta_id, que identifican una asociación concreta. Es habitual impedir que se repita la misma pareja de identificadores.

Más adelante utilizaremos exactamente este diseño en la biblioteca, cambiando videojuegos y etiquetas por libros y categorías.

🟨 Definimos @ManyToMany y @JoinTable​

En la entidad Videojuego podríamos declarar:

Fragmento conceptual de Videojuego.java
@ManyToMany
@JoinTable(
    name = "videojuego_etiquetas",
    joinColumns = @JoinColumn(name = "videojuego_id"),
    inverseJoinColumns = @JoinColumn(name = "etiqueta_id")
)
private Set<Etiqueta> etiquetas = new HashSet<>();
en este ejemplo

@ManyToMany expresa la cardinalidad N:M. @JoinTable identifica la tabla intermedia: joinColumns señala la clave ajena que apunta a la entidad donde escribimos el mapeo (Videojuego) e inverseJoinColumns la que apunta a la entidad relacionada (Etiqueta).

Utilizamos Set<Etiqueta> porque representa un conjunto de elementos sin repeticiones. Para utilizarlo se importan Set y HashSet de java.util.

En este ejemplo, JPA puede gestionar las filas de videojuego_etiquetas sin crear una entidad Java específica para esa tabla.

🟧 Lado propietario e inverso en N:M​

Si solo necesitamos acceder a las etiquetas desde un videojuego, basta con la propiedad anterior. Si también queremos navegar desde una etiqueta hacia sus videojuegos, podemos añadir en Etiqueta:

Fragmento opcional de Etiqueta.java
@ManyToMany(mappedBy = "etiquetas")
private Set<Videojuego> videojuegos = new HashSet<>();

El lado que declara @JoinTable es el propietario. El otro utiliza mappedBy y no debe volver a declarar otra tabla intermedia.

aviso

No confundamos eliminar un registro de una tabla intermedia con eliminar una entidad compartida. Si borramos un videojuego, no queremos borrar las etiquetas que siguen utilizando otros videojuegos.

Si la tabla intermedia debe almacenar datos propios de la asociación —por ejemplo, la fecha de una matrícula—, suele ser preferible convertirla en una entidad independiente con sus correspondientes relaciones. No desarrollaremos ese caso en esta unidad.

4️⃣ Relaciones uno a uno y relaciones recursivas​

🟩 Reconocemos una relación 1:1 con @OneToOne​

Una relación 1:1 expresa que un registro solo puede asociarse, como máximo, con uno del otro tipo. Por ejemplo, cada usuario podría tener un perfil particular y cada perfil correspondería a un único usuario.

En el lado que contiene la clave ajena podríamos escribir:

Fragmento de Usuario.java
@OneToOne(optional = false)
@JoinColumn(name = "perfil_id", nullable = false, unique = true)
private Perfil perfil;

La diferencia importante respecto a una relación N:1 es unique = true: dos usuarios no pueden compartir el mismo perfil. Si quisiéramos navegar también desde Perfil a Usuario, podríamos añadir @OneToOne(mappedBy = "perfil") en el otro lado.

No necesitamos desarrollar ahora una aplicación 1:1. Lo importante es reconocerla y comprender por qué la base de datos debe garantizar la exclusividad.

🟨 Una entidad también puede relacionarse consigo misma​

En un catálogo de categorías, una categoría puede pertenecer a otra categoría superior. Por ejemplo, «Ordenadores» puede depender de «Electrónica». Ambas son filas de la misma tabla.

El mapeo básico utiliza una relación muchos a uno cuyo tipo es la propia entidad:

Fragmento de Categoria.java
@ManyToOne
@JoinColumn(name = "categoria_padre_id")
private Categoria categoriaPadre;

La columna categoria_padre_id referencia categorias.id. Puede ser NULL para las categorías que no tienen un padre. Si necesitáramos recorrer también las subcategorías, podríamos añadir @OneToMany(mappedBy = "categoriaPadre") y una colección en la misma clase.

consejo

Una relación recursiva no es una quinta anotación: utiliza las mismas anotaciones que ya conocemos. Lo especial es que los dos extremos de la relación pertenecen al mismo tipo de entidad.

5️⃣ Anotaciones y parámetros que debemos dominar​

🟩 Elegimos la anotación según la cardinalidad​

Esta tabla sirve como referencia al escribir los mapeos:

AnotaciónDónde se utilizaTipo de propiedad Java
@ManyToOneDel libro hacia su editorial.Un objeto Editorial.
@OneToManyDe la editorial hacia sus libros, si necesitamos ese recorrido.Una colección List<Libro> o Set<Libro>.
@OneToOneDel usuario hacia su perfil.Un objeto Perfil.
@ManyToManyDel videojuego hacia sus etiquetas.Una colección Set<Etiqueta>.

Las anotaciones explican qué relación existe. Otros elementos concretan cómo se guarda y en qué sentido se puede recorrer.

🟨 @JoinColumn, @JoinTable y mappedBy no significan lo mismo​

  • @JoinColumn(name = "editorial_id") señala una columna que guarda una clave ajena.
  • @JoinTable(name = "libro_categorias", ...) describe una tabla intermedia que almacena asociaciones.
  • mappedBy = "editorial" señala, desde el lado inverso, el nombre de la propiedad Java que mantiene el mapeo.

En @JoinColumn también nos interesan nullable para indicar si la clave ajena puede estar vacía y unique cuando necesitamos exclusividad. Por ahora no necesitamos parámetros más avanzados: los utilizaremos solo cuando un diseño concreto los justifique.

🟧 Cuándo una relación puede ser opcional​

Si todos los libros deben tener editorial, declaramos @ManyToOne(optional = false) y @JoinColumn(nullable = false). La primera opción expresa la obligatoriedad para JPA y la segunda describe la restricción de la columna.

Si permitimos que un libro todavía no tenga editorial asignada, podemos dejar la relación como opcional. En ese caso, la propiedad Java podrá valer null.

Declarar una relación obligatoria no sustituye a validar los datos enviados desde el navegador, ni a comprobar que la clave ajena existe realmente en MySQL.

6️⃣ Cuándo se cargan los objetos relacionados​

🟩 Diferenciamos LAZY y EAGER​

Al recuperar un libro de la base de datos, es posible que también necesitemos su editorial. Sin embargo, no siempre queremos recuperar todas las relaciones de una entidad en cada consulta.

JPA dispone de dos estrategias principales:

  • EAGER: indica que la relación debe estar disponible al recuperar la entidad.
  • LAZY: solicita que la relación se cargue cuando resulte necesaria; su aplicación efectiva depende del proveedor de persistencia.

Por defecto, las relaciones @ManyToOne y @OneToOne utilizan EAGER, mientras que @OneToMany y @ManyToMany utilizan LAZY.

En nuestros ejemplos podemos solicitar explícitamente carga diferida para una editorial:

Relación con carga diferida
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "editorial_id", nullable = false)
private Editorial editorial;

La carga diferida resulta útil, pero exige pensar en qué momento necesitaremos utilizar el objeto relacionado.

🟨 Planificamos las consultas que necesita Thymeleaf​

Supongamos que un listado muestra el título de cada libro y el nombre de su editorial. Si la relación no está cargada al preparar la vista, Hibernate puede necesitar consultas adicionales o incluso producir un error si ya no dispone del contexto de persistencia necesario.

Con Spring Data JPA podemos expresar que un método del repositorio necesita recuperar también la editorial:

Fragmento conceptual de LibroRepository.java
@EntityGraph(attributePaths = "editorial")
List<Libro> findByTituloContainingIgnoreCase(String texto);
en este ejemplo

@EntityGraph indica que la consulta debe incluir la relación editorial. El valor attributePaths = "editorial" es el nombre de la propiedad Java, no el de la columna editorial_id.

No estamos desarrollando aquí el repositorio completo. Este fragmento anticipa cómo prepararemos las consultas de la Biblioteca de aula.

aviso

No debemos cambiar todas las relaciones a EAGER para resolver un problema de carga. Eso podría recuperar datos innecesarios. También evitaremos, por ahora, combinar la carga de colecciones grandes con paginación: requiere decisiones que no hacen falta para aprender el mapeo básico.

7️⃣ Cascadas, eliminación e integridad​

🟩 Relacionar dos entidades no significa borrar las dos​

Una relación expresa una asociación, pero no implica que las operaciones de guardar o eliminar deban propagarse a las entidades relacionadas. Por defecto, JPA no aplica cascadas.

Por ejemplo, varios libros pueden compartir una editorial. Al eliminar un libro queremos borrar ese registro, no la editorial. Del mismo modo, al eliminar un libro asociado a varias categorías, no debemos borrar esas categorías, porque pueden seguir utilizándose en otros libros.

El parámetro cascade permite propagar determinadas operaciones JPA. Para nuestro nivel basta con distinguir dos casos:

  • CascadeType.REMOVE propaga una operación de eliminación a entidades relacionadas.
  • CascadeType.ALL incluye también la eliminación, además de otras operaciones de persistencia.

No son opciones que debamos añadir automáticamente. Solo tienen sentido si las reglas del problema indican que unas entidades dependen realmente de otras.

🟨 Qué protege la base de datos​

Aunque el código Java esté bien construido, MySQL continúa siendo responsable de garantizar la integridad de las tablas. Las claves ajenas impiden referencias a registros inexistentes, NOT NULL exige valores para las relaciones obligatorias y UNIQUE puede garantizar la exclusividad de una relación 1:1.

También existen orphanRemoval, que se utiliza en determinados casos de entidades dependientes, y ON DELETE CASCADE, que es una regla propia de MySQL. No los aplicaremos en las relaciones compartidas de la biblioteca. Por ahora nos interesa comprender la diferencia entre eliminar una asociación y eliminar el registro relacionado.

aviso

Si MySQL impide borrar una editorial porque todavía tiene libros asociados, no debemos desactivar las claves ajenas para forzar la eliminación. Primero hay que decidir si esa editorial debe conservarse, si es posible reasignar los libros o si la operación debe rechazarse.

8️⃣ De la teoría al formulario de una aplicación​

🟩 El formulario envía identificadores; el servicio utiliza entidades​

En la entidad Libro, la editorial es un objeto Java. En cambio, un formulario HTML normalmente tendrá un desplegable con nombres de editoriales que enviará un identificador, por ejemplo editorialId=2.

El servicio debe buscar la editorial existente y asignarla al libro antes de guardarlo:

Fragmento conceptual de un servicio
Editorial editorial = editorialRepository.findById(editorialId)
        .orElseThrow(() -> new IllegalArgumentException(
                "La editorial seleccionada no existe"));

Libro libro = new Libro();
libro.setTitulo(titulo);
libro.setEditorial(editorial);
libroRepository.save(libro);
en este ejemplo

Este fragmento no es una clase completa lista para copiar. Presupone que ya tenemos las entidades, los repositorios, sus métodos de acceso y los valores recibidos.

Lo que debemos entender es el recorrido: ID recibido → consulta a MySQL → entidad existente → asignación de la relación → guardado con JPA. No se crea una nueva editorial cada vez que registramos un libro.

Con una relación N:M se aplica una idea parecida: el formulario puede enviar varios identificadores y el servicio recuperará una colección de entidades existentes. Lo implementaremos de forma guiada en el documento 13.

🟨 Errores frecuentes al definir relaciones​

🟩 Confundir nombres Java y nombres SQL​

mappedBy = "editorial" utiliza el nombre de la propiedad Java. @JoinColumn(name = "editorial_id") utiliza el nombre de la columna de MySQL.

🟨 Crear los dos lados como propietarios​

En una relación bidireccional, un lado define la clave ajena o la tabla intermedia y el otro utiliza mappedBy. Si configuramos ambos lados como independientes, podemos generar un esquema distinto del que pretendíamos.

🟧 Añadir colecciones innecesarias​

No es obligatorio que cada @ManyToOne tenga su correspondiente @OneToMany. Añadiremos el recorrido inverso cuando una funcionalidad lo necesite.

🟥 Eliminar entidades compartidas mediante cascadas​

Una editorial o una categoría puede utilizarse desde varios libros. No debemos utilizar CascadeType.ALL o REMOVE para intentar arreglar problemas de guardado o de borrado.

🟪 Recorrer sin control una relación bidireccional​

Si una entidad referencia a otra y esta devuelve una colección que contiene a la primera, métodos como toString() pueden entrar en recorridos circulares. Evitaremos incluir automáticamente todas las relaciones en esos métodos.

🟧 Comprobamos lo aprendido​

Antes de avanzar, conviene responder con nuestras propias palabras a estas preguntas:

  1. Si cada libro pertenece a una editorial, ¿en qué tabla se guarda la clave ajena y qué anotación ponemos en Libro?
  2. ¿Qué añade @OneToMany(mappedBy = "editorial")? ¿Es imprescindible para que exista la relación en MySQL?
  3. ¿Por qué una relación N:M necesita una tabla intermedia?
  4. ¿Qué diferencia una relación 1:1 de una N:1 cuando utilizamos una clave ajena?
  5. Si el formulario envía editorialId=2, ¿por qué no asignamos directamente ese número al atributo Editorial editorial?
  6. ¿Por qué eliminar un libro no debería eliminar su editorial o sus categorías?

Esta comprobación es no evaluable y no requiere entrega.

Antes de continuar

Ya conocemos las principales relaciones JPA y sabemos relacionar cardinalidades, claves ajenas y propiedades Java. También distinguimos cuándo necesitamos navegación bidireccional, cómo indicar el lado propietario y por qué debemos proteger los datos compartidos.

Después añadiremos el recorrido inverso con @OneToMany. Más adelante incorporaremos las categorías N:M.
