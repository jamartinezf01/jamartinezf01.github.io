3.3. Implementación de relaciones muchos a muchos

En el apartado anterior construimos Biblioteca de aula. Cada libro pertenece a una editorial, y ya hemos comprobado cómo esa asociación se guarda mediante libros.editorial_id. También añadimos la navegación inversa con @OneToMany(mappedBy = "editorial"), sin crear otra clave ajena.

Ahora queremos clasificar los libros por categorías. Un mismo libro podrá pertenecer a varias categorías y, a su vez, una categoría podrá utilizarse en muchos libros. Es una relación N:M, que no se representa con una única clave ajena.

Continuaremos sobre el mismo proyecto biblioteca-relacional y la misma base de datos biblioteca_aula. No volveremos a crear el proyecto, las editoriales ni el CRUD de libros: únicamente incorporaremos la nueva entidad y adaptaremos los archivos que ya funcionan.

Idea principal

Una relación N:M se guarda en MySQL mediante una tabla intermedia. En Java, Libro tendrá una colección Set<Categoria>, y JPA utilizará @ManyToMany y @JoinTable para almacenar las asociaciones.

Al seleccionar categorías desde un formulario, no crearemos categorías nuevas. El navegador enviará sus identificadores y el servicio recuperará los objetos existentes antes de guardarlos como relaciones del libro.

1️⃣ Ampliamos el modelo de la biblioteca​

🟩 Por qué necesitamos una relación N:M​

Hasta ahora registramos el título de un libro, su año de publicación y una editorial. Imaginemos que queremos utilizar las categorías «Novela», «Misterio» y «Aventura» para facilitar su clasificación.

El faro podría pertenecer a «Novela» y «Misterio». La brújula podría pertenecer a «Novela» y «Aventura». La categoría «Novela» sería la misma para ambos libros: no tendría sentido crear una copia cada vez que se clasificara un título.

A diferencia de la relación con editoriales, aquí no basta con una columna categoria_id en libros. Una única columna no podría representar varias categorías para el mismo libro. Tampoco sería correcto almacenar los identificadores separados por comas dentro de un campo de texto.

🟨 Identificamos las cuatro tablas​

La biblioteca tendrá estas tablas:

TablaQué almacenaRelación
editorialesLos datos de las editoriales.Una editorial puede tener muchos libros.
librosLos libros, incluida su clave ajena editorial_id.Cada libro pertenece a una editorial.
categoriasLas categorías disponibles.Una categoría puede utilizarse en varios libros.
libro_categoriasLas parejas de identificadores de libro y categoría.Representa la relación N:M.

Observemos el caso concreto del siguiente esquema. Los identificadores son ilustrativos: en nuestra base pueden tener otros valores.

La tabla libro_categorias contiene una fila por cada asociación, no una fila por libro. Así, un libro con dos categorías aparece dos veces en esa tabla, aunque siga existiendo una sola fila para él en libros.

🟧 Decidimos cómo recorreremos la relación desde Java​

Para esta práctica necesitamos consultar y editar las categorías de cada libro. Por eso incorporaremos en Libro una colección:

Nueva propiedad que tendrá Libro
private Set<Categoria> categorias = new LinkedHashSet<>();

No añadiremos una colección de libros dentro de Categoria. La relación N:M será unidireccional desde Libro: resulta suficiente para las pantallas que vamos a construir y evita añadir código innecesario.

Conviene diferenciar las dos asociaciones que coexistirán en Libro:

  • Editorial editorial: un único objeto relacionado, mediante @ManyToOne.
  • Set<Categoria> categorias: un conjunto de objetos relacionados, mediante @ManyToMany.

No hay que modificar Editorial ni eliminar su colección libros: la navegación bidireccional del apartado anterior seguirá funcionando.

2️⃣ Creamos la entidad Categoria y el mapeo N:M​

🟩 Añadimos Categoria.java​

Creamos un archivo nuevo en el paquete modelo. Por ahora, cada categoría solo tendrá un identificador y un nombre.

src/main/java/com/dwes/biblioteca_relacional/modelo/Categoria.java
package com.dwes.biblioteca_relacional.modelo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "categorias")
public class Categoria {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 60)
    private String nombre;

    public Categoria() {
    }

    public Long getId() {
        return id;
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }
}
en este ejemplo

Categoria es una entidad independiente de Libro: tendrá sus propios registros en categorias. La restricción unique = true evita que guardemos varias veces el mismo nombre de categoría.

No incorporamos List<Libro> ni Set<Libro> a esta clase. Una relación N:M no tiene por qué ser bidireccional para funcionar: basta con que uno de los lados tenga el mapeo necesario.

🟨 Modificamos Libro.java sin perder la relación con Editorial​

Abrimos la entidad Libro del documento 12. Conservamos id, titulo, anioPublicacion, Editorial editorial, sus anotaciones y todos sus métodos de acceso.

Primero añadimos estos imports:

Imports nuevos de Libro.java
import com.dwes.biblioteca_relacional.modelo.Categoria;
import jakarta.persistence.JoinTable;
import jakarta.persistence.ManyToMany;
import java.util.LinkedHashSet;
import java.util.Set;

El import de Categoria no es obligatorio cuando ambas clases están en el mismo paquete, pero lo mostramos para identificar el tipo utilizado.

Después añadimos dentro de la clase Libro la nueva propiedad y sus métodos, sin sustituir la propiedad editorial:

Añadir dentro de Libro.java
@ManyToMany(fetch = FetchType.LAZY)
@JoinTable(
    name = "libro_categorias",
    joinColumns = @JoinColumn(name = "libro_id"),
    inverseJoinColumns = @JoinColumn(name = "categoria_id")
)
private Set<Categoria> categorias = new LinkedHashSet<>();

public Set<Categoria> getCategorias() {
    return categorias;
}

public void setCategorias(Set<Categoria> categorias) {
    this.categorias = categorias;
}
en este ejemplo

@ManyToMany expresa la cardinalidad. @JoinTable indica el nombre de la tabla intermedia y las columnas que conectarán con las dos entidades:

  • joinColumns = @JoinColumn(name = "libro_id") referencia el libro, que es la entidad donde declaramos esta propiedad.
  • inverseJoinColumns = @JoinColumn(name = "categoria_id") referencia la categoría relacionada.

El conjunto Set<Categoria> representa las categorías asociadas al libro. Elegimos un conjunto porque no queremos repetir una misma categoría en el modelo Java. Inicializarlo vacío nos permite crear un libro antes de asignarle sus categorías.

No hemos añadido cascade = CascadeType.ALL ni CascadeType.REMOVE: las categorías son registros compartidos y eliminar un libro no debe eliminarlas.

La clase Libro es ahora el lado propietario de la asociación N:M, porque contiene @JoinTable. No confundamos este concepto con el lado propietario de su otra relación: Libro.editorial sigue gestionando la clave ajena de las editoriales.

🟧 Comprobamos las nuevas tablas sin borrar libros anteriores​

En el apartado 12 habíamos propuesto cambiar spring.jpa.hibernate.ddl-auto a validate después de crear el esquema. Con validate, Hibernate no crea tablas nuevas.

Como en esta práctica únicamente incorporamos tablas nuevas, podemos utilizar de forma temporal y didáctica:

Cambio temporal en application.properties
spring.jpa.hibernate.ddl-auto=update

Arrancamos Spring Boot una vez con las dos entidades ya preparadas. No utilizamos create ni create-drop y no borramos biblioteca_aula: los libros del apartado 12 deben conservarse.

Desde el cliente MySQL comprobamos:

Comprobación del nuevo esquema
USE biblioteca_aula;
SHOW TABLES;
DESCRIBE categorias;
DESCRIBE libro_categorias;
SHOW CREATE TABLE libro_categorias;

Ahora deben existir cuatro tablas: editoriales, libros, categorias y libro_categorias.

En la tabla intermedia deben aparecer libro_id y categoria_id, con claves ajenas hacia las tablas correspondientes. También conviene revisar qué restricción impide duplicar una misma pareja de identificadores; las restricciones concretas se comprueban con SHOW CREATE TABLE, no se suponen solo por haber utilizado un Set en Java.

Una vez comprobadas las tablas, dejamos de nuevo:

Configuración después de crear las tablas
spring.jpa.hibernate.ddl-auto=validate
aviso

Los libros que ya teníamos siguen existiendo, pero todavía no tienen categorías asociadas. Eso es normal: acabamos de crear la relación. Más adelante podremos editar esos libros y seleccionar sus categorías.

ddl-auto=update es una ayuda para desarrollar esta práctica, no un sistema general de migración de bases con datos. No vamos a estudiar aquí migraciones ni a transformar la estructura de MiColección.

🟧 Adaptamos LibroRepository para consultar ambas relaciones​

El listado debe mostrar la editorial y las categorías de cada libro. Además, durante la edición necesitaremos recuperar las categorías que ya están seleccionadas.

Sustituimos solo el archivo LibroRepository.java por esta versión. El resto de repositorios se mantiene:

src/main/java/com/dwes/biblioteca_relacional/repositorios/LibroRepository.java
package com.dwes.biblioteca_relacional.repositorios;

import com.dwes.biblioteca_relacional.modelo.Libro;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;

import java.util.List;
import java.util.Optional;

public interface LibroRepository extends JpaRepository<Libro, Long> {

    @EntityGraph(attributePaths = {"editorial", "categorias"})
    @Query("SELECT DISTINCT l FROM Libro l ORDER BY l.titulo")
    List<Libro> listarCatalogo();

    @Override
    @EntityGraph(attributePaths = {"editorial", "categorias"})
    Optional<Libro> findById(Long id);
}
en este ejemplo

@EntityGraph señala que estas consultas deben recuperar las propiedades Java editorial y categorias, que después utilizarán las vistas Thymeleaf. Esto evita depender de cargar las categorías más tarde, cuando se genere la página.

listarCatalogo() utiliza una consulta JPQL. Escribimos Libro y titulo, que son nombres de la entidad y sus propiedades Java. DISTINCT expresa que queremos obtener cada libro una sola vez, aunque esté asociado a varias categorías.

El nombre listarCatalogo() sustituye al método derivado findAllByOrderByTituloAsc() que usábamos antes. Cuando modifiquemos el servicio cambiaremos también su llamada. No añadimos paginación: recuperar una colección junto con resultados paginados requiere otras consideraciones que no necesitamos en esta práctica.

🟨 Listamos y comprobamos las categorías seleccionadas​

Añadimos los siguientes métodos a LibroService:

Añadir dentro de LibroService.java
public List<Categoria> listarCategorias() {
    return categorias.findAll(Sort.by("nombre"));
}

public boolean existenCategorias(List<Long> ids) {
    if (ids == null || ids.isEmpty() || ids.contains(null)) {
        return false;
    }

    Set<Long> distintos = new LinkedHashSet<>(ids);
    return categorias.findAllById(distintos).size() == distintos.size();
}

private Set<Categoria> obtenerCategorias(List<Long> ids) {
    if (ids == null || ids.isEmpty() || ids.contains(null)) {
        throw new IllegalArgumentException("Selecciona categorías válidas");
    }

    Set<Long> distintos = new LinkedHashSet<>(ids);
    List<Categoria> encontradas = categorias.findAllById(distintos);

    if (encontradas.size() != distintos.size()) {
        throw new IllegalArgumentException(
                "Alguna categoría seleccionada no existe");
    }

    return new LinkedHashSet<>(encontradas);
}
en este ejemplo

listarCategorias() recupera el catálogo ordenado para mostrarlo en el formulario. existenCategorias() permite comprobar los IDs antes de guardar y mostrar un error si alguno no corresponde a una categoría de MySQL.

obtenerCategorias() realiza el paso esencial: transforma una lista de IDs en un conjunto de objetos Categoria existentes. findAllById() recupera sus registros y comprobamos que se han encontrado todos.

Utilizamos LinkedHashSet para eliminar posibles identificadores repetidos. No necesitamos inventar IDs, crear categorías nuevas ni escribir manualmente instrucciones INSERT en libro_categorias.

🟧 Guardamos las categorías junto con los datos del libro​

En LibroService ya teníamos los métodos crear(), actualizar() y eliminar(), además de un método privado copiarDatos().

No cambiamos las rutas ni repetimos las operaciones CRUD. Sustituimos únicamente copiarDatos() por esta versión:

Sustituir copiarDatos() en LibroService
private void copiarDatos(Libro libro, LibroForm form) {
    libro.setTitulo(form.getTitulo());
    libro.setAnioPublicacion(form.getAnioPublicacion());
    libro.setEditorial(obtenerEditorial(form.getEditorialId()));
    libro.setCategorias(obtenerCategorias(form.getCategoriaIds()));

La llamada a libro.setCategorias(...) asigna las entidades ya recuperadas. Después, cuando crear() o actualizar() ejecuten libros.save(libro), JPA se encargará de guardar las asociaciones en la tabla intermedia.

Si editamos un libro y cambiamos las categorías, su conjunto deberá reflejar la selección actual del formulario. Por ejemplo, pasar de «Novela y Misterio» a «Novela y Aventura» supone retirar una asociación y añadir otra; no significa eliminar o crear las propias categorías.

6️⃣ Actualizamos el controlador y las vistas Thymeleaf​

🟩 Comprobamos también las categorías en el controlador​

Seguimos utilizando LibroController y las mismas rutas CRUD del apartado anterior. No creamos un controlador nuevo para guardar categorías de un libro.

En la clase existente, cambiamos el método prepararFormulario() para añadir el catálogo de categorías. Sustituimos el método anterior por este:

Sustituir prepararFormulario() en LibroController
private void prepararFormulario(Model model, Long idEdicion) {
    model.addAttribute("modoEdicion", idEdicion != null);
    model.addAttribute("idEdicion", idEdicion);
    model.addAttribute("editoriales", servicio.listarEditoriales());
    model.addAttribute("categorias", servicio.listarCategorias());
}

El método debe seguir ejecutándose tanto al abrir el formulario como cuando una validación falla. De lo contrario, las casillas de categorías desaparecerían al regresar a la vista.

Sustituimos el método privado comprobarEditorial() por otro que comprueba ambas relaciones:

Sustituir comprobarEditorial() por comprobarRelaciones()
private void comprobarRelaciones(LibroForm form, BindingResult errores) {
    if (form.getEditorialId() != null
            && !servicio.existeEditorial(form.getEditorialId())) {
        errores.rejectValue("editorialId", "editorial.invalida",
                "Selecciona una editorial válida");
    }

    if (form.getCategoriaIds() != null
            && !form.getCategoriaIds().isEmpty()
            && !servicio.existenCategorias(form.getCategoriaIds())) {
        errores.rejectValue("categoriaIds", "categorias.invalidas",
                "Selecciona categorías válidas");
    }
}

Por último, en los dos métodos POST existentes, crear(...) y actualizar(...), reemplazamos la llamada:

Cambiar en los dos POST de LibroController
comprobarEditorial(form, errores);

por:

Nueva llamada en los dos POST
comprobarRelaciones(form, errores);
en este ejemplo

@Valid seguirá comprobando las restricciones de LibroForm, como @NotBlank, @NotNull y @NotEmpty. El método comprobarRelaciones() añade una comprobación diferente: que la editorial y las categorías seleccionadas existan realmente.

No cambiamos los métodos @GetMapping, los nombres de las vistas ni las redirecciones después de guardar correctamente. Solo ampliamos el tratamiento de los datos relacionados.

🟨 Añadimos las casillas de categorías al formulario​

Abrimos src/main/resources/templates/libros/formulario.html. Conservamos título, año, editorial, botón de guardar y enlace de cancelación.

<fieldset>

En cada fila th:each="libro : ${libros}", añadimos la celda siguiente, preferiblemente después de la columna de editorial y antes de «Acciones»:

Añadir a cada fila del listado
<td>
    <span th:if="${libro.categorias.isEmpty()}">Sin categorías</span>
    <span th:each="categoria, estado : ${libro.categorias}">
        <span th:text="${categoria.nombre}">Categoría</span><span th:unless="${estado.last}">, </span>
    </span>
</td>
en este ejemplo

La editorial sigue siendo una propiedad individual: ${libro.editorial.nombre}. Las categorías constituyen una colección, así que utilizamos th:each para recorrerlas.

El mensaje «Sin categorías» es útil para los libros que ya existían antes de incorporar esta relación. Su aparición inicial no es un error: todavía no hemos editado esos libros para asignarles categorías.

7️⃣ Comprobamos lo que se ha guardado realmente en MySQL​

🟩 Probamos altas y edición desde el navegador​

Arrancamos Spring Boot y accedemos a la dirección habitual:

http://localhost:8080/libros

Realizamos esta secuencia de comprobaciones:

  1. Primera alta. Creamos un libro y seleccionamos una editorial y dos categorías. Debe aparecer una sola fila para el libro en el listado, con los nombres de ambas categorías.
  2. Categoría compartida. Creamos otro libro y elegimos una de las mismas categorías. Comprobamos que esa categoría se reutiliza.
  3. Edición. Abrimos el primer libro, desmarcamos una categoría y marcamos otra. Después de guardar, el libro conserva su identificador y muestra las categorías actuales.
  4. Validación. Intentamos guardar sin seleccionar ninguna categoría. Debe aparecer un mensaje de error y no guardarse la operación.
  5. Libro anterior. Editamos uno de los libros creados en el documento 12 y le asignamos categorías. El título, la editorial y el identificador anteriores deben mantenerse.
  6. Eliminación. Borramos uno de los libros. Desaparecerán sus asociaciones, pero seguirán existiendo la editorial y las categorías compartidas.

🟨 Contrastamos el resultado con las cuatro tablas​

En MySQL consultamos las asociaciones tal como están almacenadas:

Comprobamos libros, editoriales y categorías
SELECT l.id, l.titulo, e.nombre AS editorial,
       c.nombre AS categoria
FROM libros l
JOIN editoriales e ON l.editorial_id = e.id
LEFT JOIN libro_categorias lc ON lc.libro_id = l.id
LEFT JOIN categorias c ON c.id = lc.categoria_id
ORDER BY l.id, c.nombre;
en este ejemplo

Esta consulta puede devolver varias filas con el mismo título porque cada fila del resultado corresponde a una asociación libro–categoría. Eso no significa que el libro esté duplicado en libros.

Utilizamos LEFT JOIN para que también aparezcan los libros antiguos que aún no tienen categorías: el valor de categoria será NULL hasta que les asignemos alguna.

Para comprobar cada tabla de manera independiente:

Consultas de comprobación
SELECT id, titulo, editorial_id FROM libros ORDER BY id;
SELECT id, nombre FROM categorias ORDER BY nombre;
SELECT libro_id, categoria_id
FROM libro_categorias
ORDER BY libro_id, categoria_id;

También podemos revisar si se ha repetido alguna pareja de identificadores:

Comprobamos asociaciones repetidas
SELECT libro_id, categoria_id, COUNT(*) AS repeticiones
FROM libro_categorias
GROUP BY libro_id, categoria_id
HAVING COUNT(*) > 1;

La última consulta debería devolver cero filas. Una misma categoría no debe quedar asociada dos veces al mismo libro. Comprobaremos igualmente con SHOW CREATE TABLE libro_categorias; qué restricciones de unicidad y claves ajenas hay definidas realmente.

🟧 Entendemos la diferencia entre cambiar y eliminar asociaciones​

Si desmarcamos «Misterio» en un formulario, no queremos eliminar la categoría «Misterio» de la base de datos. Solo se debe retirar la fila de libro_categorias que relacionaba ese libro con esa categoría.

Del mismo modo, si eliminamos un libro, JPA debe retirar sus asociaciones de la tabla intermedia y borrar el registro del libro. Las filas de categorias permanecerán porque pueden ser compartidas por otros libros. Por eso no hemos configurado una cascada de eliminación hacia Categoria.

aviso

No confundamos el lado propietario de una relación JPA con ser dueño de la existencia del otro registro. Libro controla las asociaciones de libro_categorias, pero no debe borrar las entidades Categoria.

Las claves ajenas de MySQL siguen siendo esenciales. No debemos desactivarlas para solucionar errores de borrado o de asociación.

8️⃣ Resolución de errores y comprobación final​

🟩 Errores frecuentes​

🟩 Hibernate no encuentra libro_categorias​

Si dejamos spring.jpa.hibernate.ddl-auto=validate antes de crear las nuevas tablas, Hibernate comprobará que faltan y no arrancará. Revisamos el paso de creación del esquema, utilizando update solo cuando incorporamos las nuevas tablas, y volvemos después a validate.

🟨 El proyecto deja de compilar después de cambiar el repositorio​

Al sustituir findAllByOrderByTituloAsc() por listarCatalogo(), también debemos cambiar la llamada dentro de LibroService.listarLibros(). No dejaremos ambos métodos con una llamada a uno que ya no existe.

🟧 El formulario muestra las categorías, pero no las guarda​

Comprobamos que las casillas utilizan th:field="*{categoriaIds}", que LibroForm incluye el campo List<Long> categoriaIds y que copiarDatos() ejecuta libro.setCategorias(obtenerCategorias(...)) antes de save().

🟥 Al editar, ninguna categoría aparece marcada​

Revisamos que LibroForm.desde(...) recupere los IDs asociados. También debemos comprobar que LibroRepository.findById() incluye @EntityGraph(attributePaths = {"editorial", "categorias"}).

🟪 Se produce un error al mostrar las categorías en Thymeleaf​

La vista recorre ${libro.categorias}, que es una colección. El listado utiliza listarCatalogo() para recuperar las asociaciones antes de renderizar la plantilla. No debemos cambiar todas las relaciones a EAGER por sistema.

🟩 Cuando hay un error de validación, desaparecen las casillas​

El controlador debe ejecutar prepararFormulario() también al devolver el formulario con errores. Ese método tiene que añadir tanto editoriales como categorias al Model.

  1. ¿Por qué una relación N:M necesita una tabla intermedia y qué almacena cada una de sus filas?
  2. ¿Qué significan joinColumns e inverseJoinColumns dentro de @JoinTable?
  3. ¿Por qué Libro contiene Set<Categoria> y LibroForm contiene List<Long> categoriaIds?
  4. ¿Qué función cumple findAllById() antes de guardar un libro?
  5. ¿Qué diferencia existe entre desmarcar una categoría, eliminar un libro y eliminar la categoría de la base de datos?
  6. ¿Por qué la nueva relación no obliga a eliminar @ManyToOne ni @OneToMany(mappedBy = "editorial")?

🟧 Qué debemos conservar al terminar​

La aplicación debe seguir permitiendo el CRUD de libros y la consulta de libros por editorial del apartado anterior. Además, ahora debe ser posible elegir varias categorías, modificar las asociaciones y visualizarlas sin crear categorías duplicadas ni eliminar registros compartidos.

Antes de continuar

La Biblioteca de aula ya combina dos relaciones distintas: 1:N entre editoriales y libros, y N:M entre libros y categorías. Hemos comprobado que las relaciones se representan como objetos y colecciones en Java, pero se guardan mediante claves ajenas y una tabla intermedia en MySQL.

No hemos migrado MiColección ni hemos repetido el proyecto. Hemos ampliado una aplicación conocida y hemos comprobado paso a paso que los registros relacionados se reutilizan correctamente.
