3.3. Aplicación con entidades relacionadas

Hasta ahora hemos trabajado con MiColección. Primero aprendimos a guardar videojuegos en MySQL, después construimos su interfaz web y finalmente sustituimos el texto de la plataforma por una relación con otra entidad. Hemos visto, por tanto, cómo hacer evolucionar una aplicación que ya contenía datos.

Ahora vamos a afrontar una situación diferente: diseñar desde el principio una aplicación con varias entidades relacionadas. El objetivo no es volver a copiar el código de MiColección cambiando los nombres, sino decidir qué relaciones necesitamos, cómo representarlas en JPA y cómo recoger sus datos desde formularios Thymeleaf.

Utilizaremos una pequeña biblioteca de aula. Cada libro pertenece a una editorial, pero también puede clasificarse en varias categorías. Esta diferencia nos permitirá trabajar con dos relaciones que se almacenan de forma distinta en MySQL.

Idea principal

En una aplicación con varias relaciones, no basta con guardar los atributos de una entidad. Debemos identificar los registros relacionados, comprobar que existen y decidir cómo se almacenan sus asociaciones.

En este proyecto utilizaremos @ManyToOne para la editorial y @ManyToMany para las categorías. Mantendremos los controladores MVC, los servicios, los repositorios JPA y las vistas Thymeleaf.

1️⃣ Diseñamos la biblioteca antes de programar​

🟩 El contexto y las necesidades​

Queremos registrar libros con su título, año de publicación, editorial y categorías. Por ejemplo, El nombre de la rosa podría pertenecer a una editorial y clasificarse en las categorías «Novela» y «Misterio». Otro libro podría utilizar esa misma editorial o compartir cualquiera de esas categorías.

La aplicación permitirá consultar los libros, añadirlos, modificar su información y eliminarlos. Las editoriales y categorías constituirán un catálogo inicial que prepararemos en MySQL. En esta práctica no crearemos formularios para administrarlas: nos concentraremos en las relaciones y en el CRUD de libros.

🟨 Identificamos las relaciones y sus cardinalidades​

Antes de seleccionar anotaciones, formulamos cada relación en ambos sentidos:

RelaciónDesde una entidadDesde la otraCardinalidad
Libro–EditorialCada libro pertenece a una editorial.Una editorial puede publicar muchos libros.N:1 / 1:N.
Libro–CategoríaUn libro puede tener varias categorías.Una categoría puede corresponder a muchos libros.N:M.

En la base de datos necesitaremos cuatro tablas. Solo tres corresponden a entidades Java: editoriales, categorias y libros. La cuarta, libro_categorias, representará las asociaciones entre libros y categorías.

El dibujo indica qué claves ajenas necesitamos, no el orden físico de las columnas. En libro_categorias la pareja (libro_id, categoria_id) identifica una asociación y evita asociar dos veces la misma categoría al mismo libro.

🟧 Elegimos qué asociaciones necesita Java​

Nuestro código trabajará desde Libro hacia sus relaciones. Por eso incluiremos una propiedad Editorial editorial y una colección Set<Categoria> categorias. No necesitamos añadir una lista de libros a Editorial ni a Categoria para resolver los requisitos de esta práctica.

Esta decisión simplifica el modelo sin perder las relaciones. Una relación unidireccional sigue siendo una relación real en MySQL: la base de datos conserva sus claves ajenas y JPA conoce cómo utilizarlas.

aviso

No debemos activar CascadeType.REMOVE ni CascadeType.ALL en la relación con las categorías o la editorial. Son registros compartidos: eliminar un libro no debe borrar la editorial ni las categorías que utilizan otros libros.

2️⃣ Preparamos un proyecto y una base de datos independientes​

🟩 Creamos biblioteca_aula en MySQL​

Utilizaremos el mismo servidor MySQL instalado en Windows, pero una base de datos distinta de mi_coleccion. Así podremos experimentar sin afectar a la aplicación anterior.

Abrimos PowerShell y accedemos como administrador del servidor:

mysql -u root -p

En el cliente MySQL ejecutamos, una sola vez y únicamente si todavía no existen la base de datos y el usuario:

Nueva base de datos y usuario de desarrollo

CREATE USER 'biblioteca_app'@'localhost'
IDENTIFIED BY 'SUSTITUIR_POR_UNA_CONTRASENA_PROPIA';

GRANT ALL PRIVILEGES ON biblioteca_aula.*
TO 'biblioteca_app'@'localhost';
en este ejemplo

Repetimos el procedimiento de configuración de MySQL, pero no reutilizamos la base de datos de MiColección. La cuenta biblioteca_app tiene permisos sobre biblioteca_aula para desarrollar y crear las tablas durante la práctica; en producción separaríamos los permisos de administración del esquema y de uso de la aplicación.

No incluiremos contraseñas reales en el repositorio. El texto SUSTITUIR_POR_UNA_CONTRASENA_PROPIA debe reemplazarse por una contraseña elegida para esta cuenta.

🟨 Generamos el proyecto Spring Boot​

Desde Spring Initializr generamos un proyecto Maven, Java 21, con una versión estable de Spring Boot compatible con el resto de la unidad. Utilizamos el grupo com.dwes y el artefacto biblioteca-relacional.

Seleccionamos Spring Web, Thymeleaf, Spring Data JPA, MySQL Driver y Validation. En Spring Boot 4, el iniciador web MVC puede aparecer en pom.xml como spring-boot-starter-webmvc.

Abrimos el proyecto desde IntelliJ IDEA gratuito. Para los ejemplos utilizaremos el paquete base com.dwes.biblioteca_relacional, que contiene los paquetes modelo, repositorios, servicios, formularios y controladores.

Creamos la configuración:

src/main/resources/application.properties
spring.application.name=biblioteca-relacional

spring.datasource.url=jdbc:mysql://localhost:3306/biblioteca_aula
spring.datasource.username=biblioteca_app
spring.datasource.password=${DB_PASSWORD}

spring.jpa.hibernate.ddl-auto=update
en este ejemplo

Configuramos DB_PASSWORD en Run → Edit Configurations → Environment variables con la contraseña de biblioteca_app. La variable pertenece a este proyecto; no debe contener la contraseña de coleccion_app ni la de root.

Usamos ddl-auto=update porque partimos de una base de datos nueva y vacía y queremos observar cómo JPA crea las tablas. Este uso didáctico no contradice la necesidad de migraciones controladas cuando evolucionamos bases que contienen datos. Una vez creado el esquema podemos pasar a validate para comprobarlo sin modificarlo.

No arrancamos todavía la aplicación: primero definiremos las tres entidades.

3️⃣ Creamos las entidades y mapeamos sus relaciones​

🟩 La entidad Editorial​

Una editorial tiene un identificador y un nombre. Para el funcionamiento de esta práctica no necesita contener una lista de libros.

src/main/java/com/dwes/biblioteca_relacional/modelo/Editorial.java
package com.dwes.biblioteca_relacional.modelo;

import jakarta.persistence.*;

@Entity
@Table(name = "editoriales")
public class Editorial {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 100)
    private String nombre;

    public Editorial() {
    }

    public Long getId() {
        return id;
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }
}
en este ejemplo

@Entity marca la clase como entidad JPA y @Table determina su nombre de tabla. El identificador utiliza GenerationType.IDENTITY, como en MiColección. Con unique = true declaramos que el nombre de la editorial no debe repetirse en esta aplicación de aula.

🟧 La entidad Libro: dos relaciones diferentes​

La clase Libro es el centro de nuestro proyecto. Sus dos propiedades relacionadas requieren anotaciones distintas:

src/main/java/com/dwes/biblioteca_relacional/modelo/Libro.java
package com.dwes.biblioteca_relacional.modelo;

import jakarta.persistence.*;
import java.util.LinkedHashSet;
import java.util.Set;

@Entity
@Table(name = "libros")
public class Libro {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String titulo;

    @Column(name = "anio_publicacion", nullable = false)
    private Integer anioPublicacion;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "editorial_id", nullable = false)
    private Editorial editorial;

    @ManyToMany(fetch = FetchType.LAZY)
    @JoinTable(
        name = "libro_categorias",
        joinColumns = @JoinColumn(name = "libro_id"),
        inverseJoinColumns = @JoinColumn(name = "categoria_id")
    )
    private Set<Categoria> categorias = new LinkedHashSet<>();

    public Libro() {
    }

    public Long getId() {
        return id;
    }

    public String getTitulo() {
        return titulo;
    }

    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }

    public Integer getAnioPublicacion() {
        return anioPublicacion;
    }

    public void setAnioPublicacion(Integer anioPublicacion) {
        this.anioPublicacion = anioPublicacion;
    }

    public Editorial getEditorial() {
        return editorial;
    }

    public void setEditorial(Editorial editorial) {
        this.editorial = editorial;
    }

    public Set<Categoria> getCategorias() {
        return categorias;
    }

    public void setCategorias(Set<Categoria> categorias) {
        this.categorias = categorias;
    }
}
en este ejemplo

@ManyToOne establece que varios libros pueden referirse a una misma editorial. El ID se guarda en la columna libros.editorial_id. En Java utilizamos un objeto Editorial, no un número suelto.

@ManyToMany expresa que un libro puede tener varias categorías y que una categoría puede asociarse a distintos libros. @JoinTable define la tabla intermedia libro_categorias y sus dos claves ajenas.

Utilizamos Set<Categoria> porque no queremos repetir una misma categoría dentro del conjunto de un libro. LinkedHashSet nos proporciona una colección inicialmente vacía. No hemos añadido cascade = CascadeType.ALL: las categorías ya existirán en MySQL y podrán ser compartidas.

Las asociaciones tienen carga LAZY. Recuperaremos explícitamente las relaciones que necesite la vista desde el repositorio, siguiendo el criterio de cargar los datos relacionados cuando se van a utilizar.

🟥 Comprobamos las tablas creadas​

Arrancamos Spring Boot una primera vez y comprobamos que no aparecen errores de conexión. Después entramos en MySQL con la cuenta del proyecto:

mysql -u biblioteca_app -p biblioteca_aula
Comprobación del esquema generado por JPA
SHOW TABLES;
DESCRIBE libros;
DESCRIBE libro_categorias;
SHOW CREATE TABLE libro_categorias;

Deben existir las tablas editoriales, categorias, libros y libro_categorias. En esta última, MySQL debe reflejar dos claves ajenas. Si no se han creado, revisamos el paquete de las entidades y los mensajes de arranque de Spring Boot.

consejo

Una vez verificado el esquema, podemos sustituir spring.jpa.hibernate.ddl-auto=update por validate. En adelante no vamos a cambiar la estructura de esta base: solo insertaremos, modificaremos y eliminaremos registros.

Como en MiColección, cada entidad que necesitemos consultar contará con un repositorio. Los dos catálogos utilizan operaciones ya heredadas de JpaRepository:

En el repositorio de libros necesitamos, además, recuperar la editorial y las categorías que mostraremos en las vistas:

src/main/java/com/dwes/biblioteca_relacional/repositorios/LibroRepository.java
package com.dwes.biblioteca_relacional.repositorios;

import com.dwes.biblioteca_relacional.modelo.Libro;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import java.util.List;
import java.util.Optional;

public interface LibroRepository extends JpaRepository<Libro, Long> {

    @EntityGraph(attributePaths = {"editorial", "categorias"})
    @Query("SELECT DISTINCT l FROM Libro l ORDER BY l.titulo")
    List<Libro> listarCatalogo();

    @Override
    @EntityGraph(attributePaths = {"editorial", "categorias"})
    Optional<Libro> findById(Long id);
}
en este ejemplo

En listarCatalogo() escribimos JPQL, por eso utilizamos Libro y titulo, que son los nombres de la entidad y su propiedad Java. DISTINCT expresa que queremos un libro por resultado, aunque tenga varias categorías relacionadas.

@EntityGraph indica que en estas consultas necesitamos también la editorial y las categorías. Así las vistas Thymeleaf podrán mostrarlas sin depender de acceder más tarde a asociaciones LAZY. No incorporaremos paginación en esta práctica: combinar una consulta paginada con la carga de una colección requiere otras consideraciones que no necesitamos aquí.

5️⃣ Recogemos las relaciones desde un formulario​

🟩 ¿Qué envía realmente el navegador?​

Un navegador no envía objetos Editorial ni Categoria: envía los valores de los controles HTML. Si seleccionamos una editorial y dos categorías, recibiremos algo parecido a esto:

Valores de ejemplo enviados por el formulario
titulo=Un libro de ejemplo
anioPublicacion=2022
editorialId=2
categoriaIds=1
categoriaIds=3

La editorial llega como un identificador y las categorías como varios identificadores. Nuestro servicio tendrá que buscar los registros correspondientes antes de crear el libro.

Ya utilizamos una clase específica para representar los datos de un formulario con una relación. Aquí aplicaremos la misma idea a una colección de IDs.

🟨 Definimos LibroForm​

src/main/java/com/dwes/biblioteca_relacional/formularios/LibroForm.java
package com.dwes.biblioteca_relacional.formularios;

import com.dwes.biblioteca_relacional.modelo.Categoria;
import com.dwes.biblioteca_relacional.modelo.Libro;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotEmpty;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;
import java.util.ArrayList;
import java.util.List;

public class LibroForm {

    @NotBlank(message = "El título es obligatorio")
    @Size(max = 150, message = "Máximo 150 caracteres")
    private String titulo;

    @NotNull(message = "El año es obligatorio")
    @Min(value = 1450, message = "Indica un año válido")
    private Integer anioPublicacion;

    @NotNull(message = "Selecciona una editorial")
    private Long editorialId;

    @NotEmpty(message = "Selecciona al menos una categoría")
    private List<Long> categoriaIds = new ArrayList<>();

    public static LibroForm desde(Libro libro) {
        LibroForm form = new LibroForm();
        form.setTitulo(libro.getTitulo());
        form.setAnioPublicacion(libro.getAnioPublicacion());
        form.setEditorialId(libro.getEditorial().getId());
        form.setCategoriaIds(libro.getCategorias().stream()
                .map(Categoria::getId).toList());
        return form;
    }

    public String getTitulo() {
        return titulo;
    }

    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }

    public Integer getAnioPublicacion() {
        return anioPublicacion;
    }

    public void setAnioPublicacion(Integer anioPublicacion) {
        this.anioPublicacion = anioPublicacion;
    }

    public Long getEditorialId() {
        return editorialId;
    }

    public void setEditorialId(Long editorialId) {
        this.editorialId = editorialId;
    }

    public List<Long> getCategoriaIds() {
        return categoriaIds;
    }

    public void setCategoriaIds(List<Long> categoriaIds) {
        this.categoriaIds = categoriaIds;
    }
}
en este ejemplo

@NotNull exige elegir una editorial. @NotEmpty exige seleccionar al menos una categoría. Validar que los valores recibidos existen realmente en MySQL es una comprobación diferente que incorporaremos al controlador mediante el servicio.

El método desde(Libro) prepara el formulario de edición: obtiene el ID de la editorial y los IDs de las categorías ya asociadas. Como recuperaremos el libro con @EntityGraph, podremos acceder a estas relaciones al preparar la vista.

6️⃣ Programamos el servicio: convertir IDs en entidades​

🟩 Recuperamos las relaciones y guardamos libros​

Nuestro servicio utilizará tres repositorios. Aunque tiene más dependencias que VideojuegoService, mantiene la misma separación de responsabilidades: no conoce Model, rutas HTTP ni plantillas.

src/main/java/com/dwes/biblioteca_relacional/servicios/LibroService.java
package com.dwes.biblioteca_relacional.servicios;

import com.dwes.biblioteca_relacional.formularios.LibroForm;
import com.dwes.biblioteca_relacional.modelo.Categoria;
import com.dwes.biblioteca_relacional.modelo.Editorial;
import com.dwes.biblioteca_relacional.modelo.Libro;
import com.dwes.biblioteca_relacional.repositorios.CategoriaRepository;
import com.dwes.biblioteca_relacional.repositorios.EditorialRepository;
import com.dwes.biblioteca_relacional.repositorios.LibroRepository;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Optional;
import java.util.Set;

@Service
public class LibroService {

    private final LibroRepository libros;
    private final EditorialRepository editoriales;
    private final CategoriaRepository categorias;

    public LibroService(LibroRepository libros,
                        EditorialRepository editoriales,
                        CategoriaRepository categorias) {
        this.libros = libros;
        this.editoriales = editoriales;
        this.categorias = categorias;
    }

    public List<Libro> listarLibros() {
        return libros.listarCatalogo();
    }

    public Optional<Libro> buscarPorId(Long id) {
        return libros.findById(id);
    }

    public List<Editorial> listarEditoriales() {
        return editoriales.findAll(Sort.by("nombre"));
    }

    public List<Categoria> listarCategorias() {
        return categorias.findAll(Sort.by("nombre"));
    }

    public boolean existeEditorial(Long id) {
        return id != null && editoriales.existsById(id);
    }

    public boolean existenCategorias(List<Long> ids) {
        if (ids == null || ids.isEmpty() || ids.contains(null)) {
            return false;
        }
        Set<Long> distintos = new LinkedHashSet<>(ids);
        return categorias.findAllById(distintos).size() == distintos.size();
    }

    private Editorial obtenerEditorial(Long id) {
        return editoriales.findById(id)
                .orElseThrow(() -> new IllegalArgumentException(
                        "La editorial indicada no existe"));
    }

    private Set<Categoria> obtenerCategorias(List<Long> ids) {
        Set<Long> distintos = new LinkedHashSet<>(ids);
        List<Categoria> encontradas = categorias.findAllById(distintos);
        if (encontradas.size() != distintos.size()) {
            throw new IllegalArgumentException(
                    "Alguna categoría indicada no existe");
        }
        return new LinkedHashSet<>(encontradas);
    }

    public Libro crear(LibroForm form) {
        Libro libro = new Libro();
        copiarDatos(libro, form);
        return libros.save(libro);
    }

    public boolean actualizar(Long id, LibroForm form) {
        Optional<Libro> encontrado = libros.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }
        Libro libro = encontrado.get();
        copiarDatos(libro, form);
        libros.save(libro);
        return true;
    }

    public boolean eliminar(Long id) {
        Optional<Libro> encontrado = libros.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }
        libros.delete(encontrado.get());
        return true;
    }

    private void copiarDatos(Libro libro, LibroForm form) {
        libro.setTitulo(form.getTitulo());
        libro.setAnioPublicacion(form.getAnioPublicacion());
        libro.setEditorial(obtenerEditorial(form.getEditorialId()));
        libro.setCategorias(obtenerCategorias(form.getCategoriaIds()));
    }
}
en este ejemplo

La operación clave es copiarDatos(). Recibe el objeto con los valores del formulario y resuelve sus relaciones: busca una editorial y una colección de categorías que ya existen en MySQL. JPA guardará después sus identificadores en editorial_id y en libro_categorias.

obtenerCategorias() elimina posibles IDs repetidos y comprueba que todos existan. No creamos una categoría nueva por cada libro: reutilizamos los registros compartidos. Tampoco cambiamos manualmente el ID de un libro al actualizarlo.

Los métodos existeEditorial() y existenCategorias() permiten mostrar mensajes de validación antes de guardar. En un entorno con operaciones concurrentes, esas comprobaciones no garantizan por sí solas que nadie modifique los registros entre la consulta y el guardado; las restricciones de MySQL siguen siendo necesarias.

🟨 Distinguimos dos consecuencias de eliminar un libro​

Si borramos un libro, debe desaparecer su registro de libros y también sus asociaciones en libro_categorias. Sin embargo, la editorial y las categorías deben permanecer porque pueden utilizarse en otros libros.

Es una diferencia fundamental entre eliminar una asociación y eliminar la entidad compartida. Por eso no hemos configurado cascadas de eliminación hacia Editorial o Categoria.

7️⃣ Creamos el controlador MVC y las vistas Thymeleaf​

🟩 Definimos las rutas de la aplicación​

AcciónMétodoRuta
Listar libros.GET./libros.
Abrir el formulario de alta.GET./libros/nuevo.
Guardar un libro nuevo.POST./libros/nuevo.
Abrir una edición.GET./libros/{id}/editar.
Guardar cambios.POST./libros/{id}/editar.
Eliminar un libro.POST./libros/{id}/eliminar.

Son rutas similares a las que ya conocemos, pero el tratamiento de las asociaciones es diferente. También repetiremos el patrón Post/Redirect/Get para no reenviar un formulario válido al recargar la página.

🟨 Implementamos LibroController​

src/main/java/com/dwes/biblioteca_relacional/controladores/LibroController.java
package com.dwes.biblioteca_relacional.controladores;

import com.dwes.biblioteca_relacional.formularios.LibroForm;
import com.dwes.biblioteca_relacional.modelo.Libro;
import com.dwes.biblioteca_relacional.servicios.LibroService;
import jakarta.validation.Valid;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;
import java.util.Optional;

@Controller
@RequestMapping("/libros")
public class LibroController {

    private final LibroService servicio;

    public LibroController(LibroService servicio) {
        this.servicio = servicio;
    }

    @GetMapping
    public String listar(Model model) {
        model.addAttribute("libros", servicio.listarLibros());
        return "libros/lista";
    }

    @GetMapping("/nuevo")
    public String mostrarNuevo(Model model) {
        model.addAttribute("libro", new LibroForm());
        prepararFormulario(model, null);
        return "libros/formulario";
    }

    @PostMapping("/nuevo")
    public String crear(@Valid @ModelAttribute("libro") LibroForm form,
                        BindingResult errores,
                        Model model,
                        RedirectAttributes redirect) {
        comprobarRelaciones(form, errores);
        if (errores.hasErrors()) {
            prepararFormulario(model, null);
            return "libros/formulario";
        }
        servicio.crear(form);
        redirect.addFlashAttribute("mensaje", "Libro añadido correctamente.");
        return "redirect:/libros";
    }

    @GetMapping("/{id}/editar")
    public String mostrarEditar(@PathVariable Long id, Model model,
                                RedirectAttributes redirect) {
        Optional<Libro> encontrado = servicio.buscarPorId(id);
        if (encontrado.isEmpty()) {
            redirect.addFlashAttribute("error", "El libro no existe.");
            return "redirect:/libros";
        }
        model.addAttribute("libro", LibroForm.desde(encontrado.get()));
        prepararFormulario(model, id);
        return "libros/formulario";
    }

    @PostMapping("/{id}/editar")
    public String actualizar(@PathVariable Long id,
                             @Valid @ModelAttribute("libro") LibroForm form,
                             BindingResult errores, Model model,
                             RedirectAttributes redirect) {
        comprobarRelaciones(form, errores);
        if (errores.hasErrors()) {
            prepararFormulario(model, id);
            return "libros/formulario";
        }
        if (!servicio.actualizar(id, form)) {
            redirect.addFlashAttribute("error", "El libro no existe.");
            return "redirect:/libros";
        }
        redirect.addFlashAttribute("mensaje", "Libro actualizado correctamente.");
        return "redirect:/libros";
    }

    @PostMapping("/{id}/eliminar")
    public String eliminar(@PathVariable Long id, RedirectAttributes redirect) {
        if (servicio.eliminar(id)) {
            redirect.addFlashAttribute("mensaje", "Libro eliminado.");
        } else {
            redirect.addFlashAttribute("error", "El libro no existe.");
        }
        return "redirect:/libros";
    }

    private void prepararFormulario(Model model, Long idEdicion) {
        model.addAttribute("modoEdicion", idEdicion != null);
        model.addAttribute("idEdicion", idEdicion);
        model.addAttribute("editoriales", servicio.listarEditoriales());
        model.addAttribute("categorias", servicio.listarCategorias());
    }

    private void comprobarRelaciones(LibroForm form, BindingResult errores) {
        if (form.getEditorialId() != null
                && !servicio.existeEditorial(form.getEditorialId())) {
            errores.rejectValue("editorialId", "editorial.invalida",
                    "Selecciona una editorial válida");
        }
        if (form.getCategoriaIds() != null
                && !form.getCategoriaIds().isEmpty()
                && !servicio.existenCategorias(form.getCategoriaIds())) {
            errores.rejectValue("categoriaIds", "categorias.invalidas",
                    "Selecciona categorías válidas");
        }
    }
}
en este ejemplo

@Controller devuelve nombres de vistas Thymeleaf; no utilizamos @ResponseBody porque queremos generar HTML. @ModelAttribute("libro") vincula los datos del navegador a LibroForm. @Valid activa las restricciones y BindingResult recoge sus errores.

prepararFormulario() añade los catálogos al Model. También lo invocamos cuando el POST contiene errores, para volver a mostrar las opciones del desplegable y las categorías marcadas.

comprobarRelaciones() comprueba que los IDs recibidos correspondan a registros existentes. No debemos confundir esta comprobación con @NotNull o @NotEmpty: esas anotaciones verifican la presencia de valores, no su existencia en la base de datos.

🟧 Construimos un formulario con una editorial y varias categorías​

Crearemos la plantilla formulario.html con un <select> para la editorial y casillas de verificación para las categorías. En ambos casos mostraremos nombres comprensibles, pero enviaremos identificadores.

en este ejemplo

El <select> envía un único editorialId. Las casillas de verificación comparten th:field="*{categoriaIds}", por lo que Spring MVC puede construir una lista de identificadores. Durante la edición, Thymeleaf marcará las categorías cuyos IDs ya estén en LibroForm.

Los mensajes th:errors aparecen junto a los controles cuando los datos son inválidos. El formulario no incluye un campo editable para el ID del libro: la ruta de edición indica qué registro queremos modificar.

🟥 Mostramos los libros y sus asociaciones​

La vista de listado debe mostrar la editorial y todas las categorías de cada libro. Podemos hacerlo con un bucle anidado de Thymeleaf, sin convertir antes las categorías en un texto dentro del controlador.

src/main/resources/templates/libros/lista.html

            <th>Categorías</th>
            <th>Acciones</th>
        </tr>
        </thead>

            <td th:text="${libro.titulo}">Libro</td>
            <td th:text="${libro.anioPublicacion}">2022</td>
            <td th:text="${libro.editorial.nombre}">Editorial</td>
            <td>
                <span th:each="categoria, estado : ${libro.categorias}">
                    <span th:text="${categoria.nombre}">Categoría</span><span th:unless="${estado.last}">, </span>
                </span>
            </td>
            <td>
                <a th:href="@{/libros/{id}/editar(id=${libro.id})}">Editar</a>
                <form th:action="@{/libros/{id}/eliminar(id=${libro.id})}"
                      method="post" style="display: inline"
                      onsubmit="return confirm('¿Eliminar este libro?');">
                    <button type="submit">Eliminar</button>
                </form>
            </td>
        </tr>
        </tbody>
    </table>
</body>
</html>
en este ejemplo

En una relación N:1, accedemos a una única propiedad: ${libro.editorial.nombre}. En una relación N:M, recorremos una colección: th:each="categoria : ${libro.categorias}". Es la diferencia que queremos comprender, no solo recordar el nombre de las anotaciones.

El formulario de eliminación utiliza POST, no un enlace GET. No usamos @RestController ni @ResponseBody: el resultado es una página HTML generada con Thymeleaf.

consejo

En esta aplicación hemos utilizado HTML básico para centrar la práctica en las relaciones. No es necesario volver a estudiar CSS. Si queremos darle una apariencia similar a MiColección, podemos adaptar su hoja de estilos, sin modificar los controladores ni los repositorios.

🟩 Realizamos una secuencia de pruebas​

Iniciamos MySQL, configuramos DB_PASSWORD en IntelliJ y arrancamos la aplicación. Abrimos:

http://localhost:8080/libros

El listado estará vacío hasta que registremos libros. A continuación probaremos el recorrido completo:

  1. Alta. Añadimos un libro seleccionando una editorial y dos categorías. Comprobamos que aparece una sola fila para ese libro en el listado web y que se muestran ambas categorías.
  2. Segunda alta. Añadimos otro libro con la misma editorial y una de las categorías anteriores. Así comprobamos que los registros compartidos se reutilizan.
  3. Edición. Abrimos el primer libro, cambiamos la editorial y sustituimos una categoría. Al guardar, el libro conserva su identificador.
  4. Validación. Enviamos un formulario sin editorial, sin categorías o con el título vacío. Deben aparecer los mensajes correspondientes, sin guardar nuevos registros.
  5. Eliminación. Borramos uno de los libros. Comprobamos que desaparece, pero su editorial y sus categorías continúan existiendo.

🟨 Contrastamos la pantalla con MySQL​

La vista HTML no basta para demostrar que las asociaciones se han guardado correctamente. En el cliente MySQL ejecutamos:

Libros, editoriales y categorías realmente almacenados
SELECT l.id, l.titulo, e.nombre AS editorial,
       c.nombre AS categoria
FROM libros l
JOIN editoriales e ON l.editorial_id = e.id
LEFT JOIN libro_categorias lc ON lc.libro_id = l.id
LEFT JOIN categorias c ON c.id = lc.categoria_id
ORDER BY l.id, c.nombre;
en este ejemplo

Esta consulta puede devolver varias filas para un mismo libro: una por cada categoría asociada. Eso no significa que existan varios libros duplicados. La tabla intermedia representa distintas asociaciones.

Para contar los libros reales podríamos utilizar SELECT COUNT(*) FROM libros;. Si contamos las filas de la consulta con JOIN, estaríamos contando asociaciones, no necesariamente libros distintos.

También verificamos que los registros compartidos siguen presentes después de eliminar un libro:

Comprobamos que los catálogos no se han eliminado
SELECT * FROM editoriales ORDER BY nombre;
SELECT * FROM categorias ORDER BY nombre;
SELECT * FROM libro_categorias ORDER BY libro_id, categoria_id;

🟧 Errores frecuentes​

🟩 Al guardar, JPA intenta insertar editoriales o categorías nuevas​

Los formularios envían IDs, no nombres para crear nuevos catálogos. Revisamos que el servicio utilice findById() y findAllById() y asigne entidades existentes, sin construir otras mediante new Editorial() o new Categoria() al guardar el libro.

🟨 Thymeleaf no muestra las categorías del libro​

Comprobamos que LibroRepository.listarCatalogo() y findById() incluyen @EntityGraph para cargar las relaciones que necesita la vista. También revisamos que la plantilla recorra libro.categorias, que es una colección, no un único objeto.

🟧 Se crea el libro, pero no aparecen filas en libro_categorias​

Revisamos el mapeo @ManyToMany y su @JoinTable, los IDs que envía el formulario y que copiarDatos() asigne el conjunto de categorías antes de save().

🟥 El formulario vuelve con errores y los catálogos desaparecen​

Cuando el POST no supera la validación, el controlador debe volver a ejecutar prepararFormulario() para añadir editoriales y categorias al Model. También debe conservarse BindingResult inmediatamente después del objeto anotado con @Valid.

🟪 Eliminar un libro también elimina una editorial o categoría​

Esto no debe ocurrir. Revisamos que no hayamos añadido cascadas de eliminación hacia las entidades compartidas. Una asociación no significa que un libro sea propietario de la existencia de su editorial o sus categorías.

aviso

Las comprobaciones anteriores cubren una aplicación de aula. En situaciones con usuarios concurrentes pueden aparecer fallos adicionales, aunque hayamos validado previamente los IDs. Las claves ajenas y la gestión de transacciones siguen siendo necesarias para proteger la integridad de los datos.

9️⃣ Aplicamos lo aprendido con autonomía​

En lugar de repetir MiColección, vamos a explicar por qué hemos tomado determinadas decisiones en esta biblioteca. La siguiente comprobación es no evaluable y no requiere entrega.

🟩 Comprobación del modelo​

  1. ¿Por qué Libro contiene una propiedad Editorial, mientras que Categoria se representa mediante una colección?
  2. ¿En qué tabla se guarda editorial_id y por qué no necesitamos una tabla intermedia para la editorial?
  3. ¿Por qué sí necesitamos libro_categorias? ¿Qué dos claves ajenas contiene?
  4. ¿Qué cambia en el código Java si una categoría puede pertenecer a muchos libros, pero un libro solo puede tener una categoría?

🟨 Pequeñas mejoras opcionales​

Podemos elegir una de estas ampliaciones, sin alterar las relaciones ya implementadas:

  • Añadir al listado un filtro por editorial. Debemos decidir qué método del repositorio necesitaremos y qué parámetro GET utilizará el controlador.
  • Mostrar el número de categorías de cada libro. Debemos decidir si esa información está ya disponible en la colección categorias.
  • Evitar que una categoría se elimine accidentalmente mientras está asociada a libros. Debemos explicar qué protección aporta la clave ajena y por qué no utilizaremos una cascada de eliminación.

Estas mejoras no forman parte de los requisitos mínimos de la práctica. Lo esencial es que podamos crear, modificar y eliminar libros sin destruir datos compartidos, y que sepamos justificar el mapeo de cada relación.

Antes de continuar

Hemos construido una aplicación nueva con tres entidades y dos tipos de relación. Libro se asocia a una editorial mediante una clave ajena y a varias categorías mediante una tabla intermedia. Los formularios envían identificadores; el servicio recupera los objetos asociados y el repositorio conserva las relaciones en MySQL.

Al estudiar las transacciones veremos cómo coordinar varias modificaciones para que una operación se complete correctamente o pueda deshacerse si falla.
