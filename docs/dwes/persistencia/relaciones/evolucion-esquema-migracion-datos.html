3.2. Evolución del esquema y migración de datos

Hasta ahora hemos construido MiColección de forma progresiva: empezamos con una entidad, incorporamos repositorios y servicios, desarrollamos los formularios CRUD y finalmente añadimos un buscador con filtros, ordenación y paginación. Los videojuegos no son datos de prueba que podamos borrar sin más: ya forman parte de una base de datos que queremos conservar.

Ya conocemos cómo representar relaciones entre entidades JPA. Ahora aparece una situación distinta de la que teníamos al crear las primeras tablas: necesitamos cambiar un modelo de datos que ya está en uso. Este problema es habitual en el desarrollo profesional. Los requisitos evolucionan, la aplicación incorpora nuevas funcionalidades y la estructura de sus tablas debe adaptarse sin perder la información almacenada.

Primero estudiaremos el procedimiento general para realizar una migración. Después lo aplicaremos a MiColección: convertiremos la plataforma, que actualmente se guarda como texto, en una entidad propia relacionada con cada videojuego. Conservaremos los registros y adaptaremos la aplicación web para que siga funcionando.

Idea principal

Una migración de base de datos es un cambio planificado de su estructura, sus datos o ambos. No consiste solo en modificar una clase @Entity: debemos comprobar el estado inicial, preparar los cambios, conservar la información existente y verificar que el nuevo esquema y el código de la aplicación son compatibles.

En esta práctica trabajaremos con MySQL instalado como servicio en Windows y con el proyecto Spring Boot de MiColección. No crearemos otro proyecto ni borraremos mi_coleccion.

1️⃣ ¿Por qué necesitamos migrar una base de datos?​

🟩 Los requisitos cambian, pero los datos permanecen​

Cuando desarrollamos la primera versión de un proyecto solemos elegir un modelo de datos suficiente para las necesidades del momento. En MiColección bastaba con guardar plataforma como un String. Era una solución sencilla para practicar JPA, CRUD y búsquedas.

Imaginemos ahora que queremos almacenar también el fabricante o el año de lanzamiento de cada plataforma. Si repetimos esos datos en todos los videojuegos, aparecerán duplicidades e inconsistencias. Tiene más sentido crear una tabla de plataformas y relacionarla con los videojuegos mediante una clave ajena.

La dificultad no está en crear la tabla nueva, sino en responder a una pregunta: ¿qué hacemos con los videojuegos que ya tienen escrita su plataforma como texto? No podemos sustituir el atributo Java sin preparar antes los registros de MySQL. Debemos transformar los valores antiguos para que sigan teniendo significado en el nuevo modelo.

🟨 Cuatro situaciones habituales de migración​

No todas las migraciones tienen el mismo alcance. Conviene distinguir algunos casos antes de estudiar los comandos:

Tipo de cambioEjemploQué debemos revisar
Ampliación del esquemaAñadir descripcion a una tabla.Valor inicial de los registros antiguos y si la columna admite NULL.
Cambio de tipo o formatoConvertir una fecha guardada como texto en una columna DATE.Que todos los valores se puedan transformar.
Reestructuración del modeloSustituir videojuegos.plataforma por plataforma_id y una tabla plataformas.Correspondencia de cada registro antiguo con el nuevo.
Traslado de datosImportar registros desde otra base de datos o desde un sistema anterior.Compatibilidad de formatos, identificadores y relaciones.

En esta unidad desarrollaremos el tercer caso, porque enlaza directamente con las relaciones JPA. No necesitamos practicar los cuatro tipos de migración para comprender el procedimiento común.

🟧 Cambiar el esquema no siempre equivale a migrar los datos​

Una instrucción como ALTER TABLE videojuegos ADD COLUMN ... modifica la estructura de la tabla. Sin embargo, no decide por sí sola qué valor debe tener esa columna en cada fila ya guardada.

Podemos verlo con un ejemplo independiente. Si una tabla clientes ya contiene registros, podríamos añadir una columna opcional:

Ejemplo conceptual: ampliar una tabla existente
ALTER TABLE clientes ADD COLUMN telefono VARCHAR(20) NULL;

Los clientes anteriores seguirían existiendo, pero su teléfono tendría el valor NULL hasta que se introdujera. No ejecutaríamos este SQL en MiColección: solo nos ayuda a distinguir la modificación estructural de la transformación de datos.

En nuestro proyecto sí tendremos que hacer ambas cosas: crear una nueva estructura y rellenarla utilizando los valores anteriores.

2️⃣ Planificamos una migración segura​

🟩 Primero conocemos el estado de partida​

Antes de escribir comandos debemos saber qué tablas y columnas existen, qué registros contienen y qué posibles anomalías impedirían el cambio. Una migración no debe partir de la suposición de que todos los datos son correctos.

Por ejemplo, si algunos videojuegos tienen plataforma vacía, no podremos asociarlos automáticamente a una plataforma válida. Y si existen valores como PC, Pc y pc, tendremos que decidir si representan la misma plataforma antes de crear registros nuevos.

Nuestro trabajo seguirá una secuencia que podremos reutilizar en otras aplicaciones:

  1. Inspeccionar. Revisamos la estructura y los datos que vamos a transformar.
  2. Preparar una copia. Guardamos un respaldo verificable antes de ejecutar cambios.
  3. Ampliar sin destruir. Creamos primero las estructuras nuevas y mantenemos temporalmente las antiguas.
  4. Transformar. Copiamos o relacionamos los datos existentes con el nuevo modelo.
  5. Comprobar. Verificamos correspondencias, cantidades y restricciones.
  6. Retirar lo antiguo. Solo cuando lo anterior funciona eliminamos columnas que ya no hacen falta.
  7. Adaptar y probar la aplicación. Actualizamos entidades, consultas y formularios; comprobamos el recorrido completo.
aviso

No debemos empezar por borrar la columna antigua. Si primero eliminamos videojuegos.plataforma, habremos perdido la información necesaria para relacionar los registros con las nuevas plataformas.

En MySQL muchas sentencias de modificación del esquema, como ALTER TABLE, realizan confirmaciones implícitas. No podemos confiar en un ROLLBACK para deshacer toda la migración. Por eso la copia de seguridad y las comprobaciones intermedias son imprescindibles.

🟨 Una representación visual del procedimiento​

🟧 ¿Qué hacemos si algo sale mal?​

La respuesta depende de en qué punto haya fallado el procedimiento. Si una consulta de comprobación devuelve resultados inesperados, nos detenemos sin ejecutar los siguientes cambios. Si ya hemos alterado el esquema, analizamos qué instrucciones se han aplicado antes de decidir cómo continuar.

Una copia de seguridad permite recuperar una versión anterior, pero restaurarla no es lo mismo que ejecutar ROLLBACK. En una aplicación real planificaríamos también la interrupción del servicio, la coordinación entre versiones del código y, si procede, la restauración en una base de datos independiente para comprobar la copia.

En nuestra práctica mantendremos Spring Boot detenido durante la migración, por lo que no habrá peticiones web modificando registros mientras trabajamos. MySQL permanecerá iniciado para poder ejecutar los comandos SQL.

3️⃣ Herramientas para evolucionar el esquema​

🟩 SQL controlado frente a cambios automáticos de Hibernate​

Para desarrollar MiColección habíamos configurado esta propiedad:

Configuración inicial de MiColección
spring.jpa.hibernate.ddl-auto=update

El valor update puede resultar cómodo al crear tablas durante las primeras prácticas: Hibernate compara el modelo JPA con la base y trata de adaptar algunas diferencias. Pero no conoce nuestras decisiones sobre qué hacer con los valores ya almacenados.

Si sustituimos una propiedad String plataforma por una relación Plataforma plataforma, Hibernate no puede deducir de forma fiable que debe leer los nombres anteriores, eliminar duplicados, generar filas en plataformas y asociar todos los videojuegos antes de retirar la columna antigua.

Por eso realizaremos el cambio mediante instrucciones SQL explícitas y verificables, con Spring Boot detenido. Cuando terminemos, podremos pedir a Hibernate que compruebe la correspondencia general entre entidades y tablas sin intentar transformarlas automáticamente:

Configuración recomendada tras la migración
spring.jpa.hibernate.ddl-auto=validate
en este ejemplo

validate comprueba al arrancar si el esquema existente es compatible con las entidades que hemos definido. No crea ni modifica tablas. Es útil para descubrir desacuerdos entre código y base de datos, pero no sustituye la comprobación de todos los registros y relaciones, que realizaremos con SQL y pruebas desde la web.

🟨 Migraciones versionadas: Flyway y Liquibase​

Cuando un proyecto evoluciona durante meses y trabajan varios desarrolladores, no es práctico depender de comandos que alguien ejecuta manualmente y luego olvida. Una alternativa es conservar las migraciones en archivos versionados que puedan aplicarse en un orden conocido.

Herramientas como Flyway o Liquibase permiten organizar y registrar cambios de esquema. De forma habitual, una migración incluirá sentencias CREATE TABLE, ALTER TABLE o transformaciones UPDATE, acompañadas de mecanismos para controlar qué versiones ya se han ejecutado.

En esta unidad no instalaremos ni configuraremos esas herramientas. Nos interesa reconocer su finalidad: hacer que la evolución de la base de datos sea reproducible y esté coordinada con las versiones del proyecto. Nuestro ejemplo manual nos permitirá comprender precisamente qué tareas tendría que contener una migración versionada.

consejo

Como buena práctica, en un proyecto que ya utiliza Flyway o Liquibase no conviene dejar que Hibernate y otra herramienta modifiquen el mismo esquema sin una estrategia clara. Utilizaremos un mecanismo responsable de los cambios y comprobaremos la compatibilidad con JPA.

4️⃣ Caso práctico: de texto a clave ajena en MiColección​

🟩 Qué cambia y qué debe conservarse​

Ahora aplicaremos el procedimiento anterior a la base mi_coleccion. Actualmente, cada fila de videojuegos contiene un texto en la columna plataforma. Queremos almacenar cada nombre una sola vez en plataformas y que cada videojuego conserve una referencia a ella.

Antes de migrarDespués de migrar
videojuegos.plataforma contiene PC o PlayStation.videojuegos.plataforma_id contiene un identificador numérico.
No existe una tabla de plataformas.Existe plataformas(id, nombre).
Videojuego.plataforma es String.Videojuego.plataforma es una referencia Plataforma.
Los formularios reciben el nombre como texto.El formulario envía el ID de la plataforma elegida.

El número de videojuegos y sus identificadores no deben cambiar. Tampoco perderemos las búsquedas por título y género, el CRUD, la paginación ni la hoja de estilos que ya incorporamos a MiColección.

🟨 Paso 1. Inspeccionamos los datos y hacemos una copia​

Detenemos primero Spring Boot en IntelliJ IDEA. Dejamos MySQL funcionando y abrimos PowerShell para entrar en el cliente:

Acceso a MySQL desde PowerShell
mysql -u coleccion_app -p mi_coleccion

Comprobamos la estructura de la tabla y anotamos el total de videojuegos almacenados:

Consulta previa en mi_coleccion
DESCRIBE videojuegos;
SELECT COUNT(*) AS total_antes FROM videojuegos;
SELECT id, titulo FROM videojuegos
WHERE plataforma IS NULL OR TRIM(plataforma) = '';
SELECT DISTINCT TRIM(plataforma) AS nombre FROM videojuegos ORDER BY nombre;

La columna plataforma debe seguir siendo de texto, y todavía no debe existir plataforma_id. Si la consulta de valores vacíos devuelve filas, corregimos esos registros antes de continuar. También revisamos los nombres distintos: PC y Pc pueden referirse a la misma plataforma y debemos decidir cómo unificarlos.

Si ya existen plataformas o plataforma_id por un intento anterior, no repetimos los comandos de esta práctica. Primero averiguamos hasta dónde llegó la migración. Estos pasos están preparados para la base de datos que tiene el buscador paginado y conserva plataforma como texto.

Salimos de MySQL con EXIT; y creamos una copia desde PowerShell:

Copia de seguridad de la base de datos
mysqldump --single-transaction --no-tablespaces -u coleccion_app -p --result-file=".\mi_coleccion_antes_relaciones.sql" mi_coleccion

El archivo incluirá estructura y datos. Antes de continuar comprobamos que el comando ha terminado sin errores y que el archivo realmente existe y no está vacío. Por ejemplo, desde PowerShell:

Comprobamos que se ha generado el archivo de respaldo
Get-Item .\mi_coleccion_antes_relaciones.sql | Select-Object Name, Length
aviso

La copia contiene información de la base de datos. No la subiremos a un repositorio público ni la confundiremos con un archivo que debamos incorporar a Docusaurus. Si la copia falla, no seguimos con la migración.

mysqldump --single-transaction está pensado para obtener una vista consistente de tablas transaccionales como InnoDB. Algunos entornos requieren permisos adicionales para la copia; si aparece un error, lo resolvemos antes de cambiar las tablas.

🟧 Paso 2. Creamos las plataformas a partir de los nombres existentes​

Volvemos a entrar en mi_coleccion. Crearemos la tabla plataformas y rellenaremos sus nombres utilizando los videojuegos actuales, sin inventar los ID:

Creamos plataformas y recogemos sus nombres
CREATE TABLE plataformas (
    id BIGINT NOT NULL AUTO_INCREMENT,
    nombre VARCHAR(60) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_plataformas_nombre UNIQUE (nombre)
) ENGINE=InnoDB;

INSERT INTO plataformas (nombre)
SELECT DISTINCT TRIM(plataforma)
FROM videojuegos
WHERE plataforma IS NOT NULL AND TRIM(plataforma) <> '';

SELECT * FROM plataformas;
en este ejemplo

La tabla plataformas tendrá una clave primaria id y un nombre que no debe repetirse. SELECT DISTINCT TRIM(plataforma) extrae los valores existentes, elimina espacios al principio y al final y evita repetir nombres según las reglas de comparación de la base de datos.

MySQL asigna automáticamente los identificadores. No supondremos que PC tendrá el ID 1: comprobaremos los valores reales con SELECT * FROM plataformas.

Si descubrimos nombres que representan la misma plataforma pero se han escrito de formas distintas, debemos unificarlos de manera consciente antes de continuar. No basta con dar por hecho que todas las variantes significan lo mismo.

🟥 Paso 3. Añadimos y rellenamos la clave ajena​

Todavía no borramos el texto antiguo. Primero añadimos una columna que pueda estar vacía mientras hacemos la transformación; luego la rellenamos relacionando el nombre antiguo con el registro correspondiente de plataformas:

Asociamos cada videojuego con una plataforma existente
ALTER TABLE videojuegos
ADD COLUMN plataforma_id BIGINT NULL;

UPDATE videojuegos v
JOIN plataformas p ON p.nombre = TRIM(v.plataforma)
SET v.plataforma_id = p.id;

SELECT id, titulo, plataforma
FROM videojuegos
WHERE plataforma_id IS NULL;
en este ejemplo

El UPDATE ... JOIN busca una plataforma cuyo nombre coincida con el texto de cada videojuego y escribe su id en plataforma_id. Mientras se ejecuta este paso conservamos ambas columnas: plataforma y plataforma_id.

La última consulta muestra los videojuegos sin asociación. Debe devolver cero filas. Si aparece algún registro, detenemos la migración y averiguamos qué valor no ha podido relacionarse. No debemos pasar al siguiente paso sin resolverlo.

Podemos revisar visualmente las correspondencias antes de activar la restricción:

Verificamos los nombres antes de retirar la columna antigua
SELECT v.id, v.titulo, v.plataforma AS nombre_antiguo,
       p.nombre AS nombre_nuevo
FROM videojuegos v
LEFT JOIN plataformas p ON v.plataforma_id = p.id
ORDER BY v.id;

🟪 Paso 4. Cerramos el cambio cuando las comprobaciones son correctas​

Solo si todos los videojuegos tienen plataforma asignada y las correspondencias son correctas, declaramos la columna obligatoria, añadimos la clave ajena y retiramos el texto duplicado:

Activamos la clave ajena y retiramos el texto antiguo
ALTER TABLE videojuegos
MODIFY COLUMN plataforma_id BIGINT NOT NULL;

ALTER TABLE videojuegos
ADD CONSTRAINT fk_videojuegos_plataformas
FOREIGN KEY (plataforma_id) REFERENCES plataformas(id);

ALTER TABLE videojuegos
DROP COLUMN plataforma;

Ahora videojuegos.plataforma_id debe referirse a una fila existente en plataformas. Una base de datos relacional no debería permitir que un videojuego apunte a una plataforma inexistente. La restricción FOREIGN KEY protege esa integridad referencial.

aviso

La eliminación de plataforma es el último paso del cambio estructural, porque implica dejar de conservar el texto antiguo. No lo ejecutaremos antes de comprobar los datos transformados.

🟩 Paso 5. Comprobamos la estructura resultante​

Ejecutamos las consultas siguientes y comparamos el resultado con el estado inicial:

Verificamos el resultado de la migración
SELECT v.id, v.titulo, p.nombre AS plataforma
FROM videojuegos v
JOIN plataformas p ON v.plataforma_id = p.id
ORDER BY v.id;

SELECT COUNT(*) AS total_despues FROM videojuegos;
SHOW CREATE TABLE videojuegos;

También comprobaremos las plataformas y la ausencia de asociaciones huérfanas:

Revisamos plataformas y referencias después de migrar
SELECT * FROM plataformas ORDER BY nombre;

SELECT COUNT(*) AS videojuegos_sin_plataforma
FROM videojuegos v
LEFT JOIN plataformas p ON v.plataforma_id = p.id
WHERE p.id IS NULL;

El valor de total_despues debe coincidir con total_antes, y videojuegos_sin_plataforma debe ser cero. La consulta con JOIN debe mostrar cada videojuego con la plataforma correcta.

Si la colección estaba vacía, la tabla plataformas también podría estarlo. Para poder utilizar el desplegable, introduciríamos algunas filas solo después de comprobar que todavía no existen:

Datos iniciales únicamente si no tenemos plataformas
INSERT INTO plataformas (nombre)
VALUES ('PC'), ('Nintendo Switch'), ('PlayStation');

No ejecutamos este bloque por costumbre si ya existen esas plataformas, porque nombre tiene una restricción de unicidad.

5️⃣ Adaptamos el modelo de entidades JPA​

La base de datos ya utiliza una clave ajena, pero nuestro código Java todavía espera un String. Por eso no habíamos arrancado Spring Boot después de los cambios SQL. Ahora pondremos de acuerdo las entidades con las tablas.

Este es el inventario de archivos que tendremos que revisar. No crearemos otro controlador ni otro servicio con nombres distintos: sustituiremos o modificaremos los archivos del proyecto actual.

🟩 Creamos Plataforma​

Una plataforma se convierte en una entidad independiente. No añadimos una colección List<Videojuego>: una relación N:1 unidireccional es suficiente para lo que necesitamos.

src/main/java/com/dwes/mi_coleccion/modelo/Plataforma.java
package com.dwes.mi_coleccion.modelo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;


@Entity
@Table(name = "plataformas", uniqueConstraints =
        @UniqueConstraint(name = "uk_plataformas_nombre", columnNames = "nombre"))
public class Plataforma {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 60)
    private String nombre;

    public Plataforma() {
    }

    public Plataforma(String nombre) {
        this.nombre = nombre;
    }

    public Long getId() {
        return id;
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }

}
en este ejemplo

@Entity y @Table vinculan la clase con plataformas. La restricción de unicidad indica que no queremos dos nombres iguales. El id se genera mediante GenerationType.IDENTITY, como en Videojuego.

El constructor sin argumentos es necesario para JPA. No hay ningún atributo List<Videojuego> porque, por ahora, consultaremos la plataforma desde cada videojuego.

🟨 Sustituimos la entidad Videojuego​

Este es el cambio más importante: la propiedad String plataforma desaparece de la entidad Java y pasa a ser Plataforma plataforma. Sustituimos el archivo completo, sin conservar el antiguo atributo ni sus métodos de acceso:

src/main/java/com/dwes/mi_coleccion/modelo/Videojuego.java
package com.dwes.mi_coleccion.modelo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.ForeignKey;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "videojuegos")
public class Videojuego {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String titulo;

    @Column(nullable = false, length = 60)
    private String genero;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "plataforma_id", nullable = false,
            foreignKey = @ForeignKey(name = "fk_videojuegos_plataformas"))
    private Plataforma plataforma;

    @Column(name = "anio_lanzamiento", nullable = false)
    private Integer anioLanzamiento;

    public Videojuego() {
    }

    public Videojuego(String titulo, String genero,
                      Plataforma plataforma, Integer anioLanzamiento) {
        this.titulo = titulo;
        this.genero = genero;
        this.plataforma = plataforma;
        this.anioLanzamiento = anioLanzamiento;
    }

    public Long getId() {
        return id;
    }

    public String getTitulo() {
        return titulo;
    }

    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }

    public String getGenero() {
        return genero;
    }

    public void setGenero(String genero) {
        this.genero = genero;
    }

    public Plataforma getPlataforma() {
        return plataforma;
    }

    public void setPlataforma(Plataforma plataforma) {
        this.plataforma = plataforma;
    }

    public Integer getAnioLanzamiento() {
        return anioLanzamiento;
    }

    public void setAnioLanzamiento(Integer anioLanzamiento) {
        this.anioLanzamiento = anioLanzamiento;
    }
}
en este ejemplo

@ManyToOne representa que varios videojuegos pueden compartir una plataforma. @JoinColumn(name = "plataforma_id") indica dónde se guarda el identificador asociado en MySQL. Hemos declarado una plataforma obligatoria con optional = false y nullable = false.

FetchType.LAZY indica que la plataforma puede cargarse cuando se necesite. Como el listado y la edición sí necesitan su nombre, prepararemos consultas que recuperen expresamente la relación. Así evitaremos depender de que Thymeleaf dispare lecturas adicionales.

Las restricciones de validación de los campos editables se trasladan al objeto de formulario VideojuegoForm, que crearemos al adaptar los formularios. La nueva entidad se concentra en representar la información persistente.

🟧 Creamos el repositorio de plataformas​

Necesitamos recuperar las plataformas para llenar el desplegable y comprobar que el ID elegido existe. Como ya sabemos, no tenemos que escribir una implementación del repositorio:

src/main/java/com/dwes/mi_coleccion/repositorios/PlataformaRepository.java
package com.dwes.mi_coleccion.repositorios;

import com.dwes.mi_coleccion.modelo.Plataforma;
import org.springframework.data.jpa.repository.JpaRepository;

public interface PlataformaRepository extends JpaRepository<Plataforma, Long> {

JpaRepository<Plataforma, Long> nos proporciona findAll(), findById() y existsById() entre otras operaciones. No vamos a crear un controlador CRUD para plataformas; en esta práctica serán valores que ya hemos incorporado a la base de datos.

🟥 Conservamos el buscador y planificamos la carga de la relación​

VideojuegoRepository ya permitía filtrar por título y género con paginación. Esa consulta no debe desaparecer al introducir plataformas. Sustituimos el repositorio por esta versión compatible con las nuevas entidades:

src/main/java/com/dwes/mi_coleccion/repositorios/VideojuegoRepository.java
package com.dwes.mi_coleccion.repositorios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.List;
import java.util.Optional;

public interface VideojuegoRepository extends JpaRepository<Videojuego, Long> {

    List<Videojuego> findByGeneroIgnoreCase(String genero);

    List<Videojuego> findByTituloContainingIgnoreCase(String texto);

    @Override
    @EntityGraph(attributePaths = "plataforma")
    Optional<Videojuego> findById(Long id);

    @EntityGraph(attributePaths = "plataforma")
    @Query("""
            SELECT v FROM Videojuego v
            WHERE (:titulo = '' OR LOWER(v.titulo) LIKE LOWER(CONCAT('%', :titulo, '%')))
              AND (:genero = '' OR LOWER(v.genero) = LOWER(:genero))
            """)
    Page<Videojuego> buscarConFiltros(
            @Param("titulo") String titulo,
            @Param("genero") String genero,
            Pageable pageable);
}
en este ejemplo

buscarConFiltros() sigue recibiendo el texto del título, el género y un Pageable. La búsqueda y la paginación continúan funcionando igual que antes. Los métodos derivados por título y género también se conservan.

La novedad es @EntityGraph(attributePaths = "plataforma"): indica que necesitamos disponer de la plataforma relacionada junto con los videojuegos recuperados. Lo aplicamos a findById() para la edición y a la búsqueda paginada que alimenta el listado. No hace falta convertir la relación en EAGER por sistema.

aviso

La expresión attributePaths = "plataforma" utiliza el nombre del atributo Java de Videojuego, no la columna plataforma_id. Si dejamos en el repositorio alguna consulta que compare v.plataforma con una cadena de texto, deberemos adaptarla: ahora plataforma es un objeto, no un String.

6️⃣ Adaptamos los formularios y la lógica de la aplicación​

Después de migrar MySQL ya no podemos pedir que la persona escriba libremente el nombre de la plataforma. Queremos que elija una plataforma existente. Un <select> HTML envía un identificador, mientras que la entidad JPA necesita un objeto Plataforma.

El recorrido será el siguiente: el formulario envía plataformaId=2, el controlador valida los campos y el servicio busca la plataforma con ID 2 antes de guardar el videojuego. Este procedimiento es aplicable a cualquier formulario que gestione relaciones entre entidades.

🟩 Creamos un objeto específico para el formulario​

Hasta ahora habíamos vinculado los formularios directamente con la entidad Videojuego. Ahora eso sería incómodo: necesitamos recibir un Long plataformaId, no construir una entidad Plataforma a partir de los parámetros HTTP.

Crearemos el paquete formularios y una clase que no es una entidad JPA:

src/main/java/com/dwes/mi_coleccion/formularios/VideojuegoForm.java
package com.dwes.mi_coleccion.formularios;

import com.dwes.mi_coleccion.modelo.Videojuego;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

public class VideojuegoForm {

    @NotBlank(message = "El título es obligatorio")
    @Size(max = 120, message = "Máximo 120 caracteres")
    private String titulo;

    @NotBlank(message = "El género es obligatorio")
    @Size(max = 60, message = "Máximo 60 caracteres")
    private String genero;

    @NotNull(message = "Selecciona una plataforma")
    private Long plataformaId;

    @NotNull(message = "El año es obligatorio")
    @Min(value = 1950, message = "El año debe ser 1950 o posterior")
    private Integer anioLanzamiento;

    public static VideojuegoForm desde(Videojuego videojuego) {
        VideojuegoForm form = new VideojuegoForm();
        form.setTitulo(videojuego.getTitulo());
        form.setGenero(videojuego.getGenero());
        form.setPlataformaId(videojuego.getPlataforma().getId());
        form.setAnioLanzamiento(videojuego.getAnioLanzamiento());
        return form;
    }

    public String getTitulo() {
        return titulo;
    }

    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }

    public String getGenero() {
        return genero;
    }

    public void setGenero(String genero) {
        this.genero = genero;
    }

    public Long getPlataformaId() {
        return plataformaId;
    }

    public void setPlataformaId(Long plataformaId) {
        this.plataformaId = plataformaId;
    }

    public Integer getAnioLanzamiento() {
        return anioLanzamiento;
    }

    public void setAnioLanzamiento(Integer anioLanzamiento) {
        this.anioLanzamiento = anioLanzamiento;
    }
}
en este ejemplo

plataformaId contiene el valor numérico del desplegable. @NotNull exige que se haya seleccionado alguna opción, pero no comprueba que el identificador exista en MySQL; esa comprobación se hará aparte.

El método estático desde(Videojuego) prepara los valores de un formulario de edición a partir de una entidad existente. En particular, obtiene el ID de su plataforma para que Thymeleaf marque la opción adecuada.

Con este cambio separamos las propiedades que llegan desde HTTP de las asociaciones entre entidades persistentes. No necesitamos introducir todavía una arquitectura compleja de DTO ni herramientas automáticas de mapeo.

🟨 Actualizamos el servicio sin perder las operaciones previas​

VideojuegoService necesita ahora dos repositorios: uno para los videojuegos y otro para las plataformas. La modificación afecta principalmente a crear() y actualizar(). Las consultas paginadas, los filtros por título y género y la eliminación deben conservarse.

Para evitar combinar fragmentos de versiones anteriores, mostramos la clase completa que sustituirá al servicio actual:

src/main/java/com/dwes/mi_coleccion/servicios/VideojuegoService.java
package com.dwes.mi_coleccion.servicios;

import com.dwes.mi_coleccion.formularios.VideojuegoForm;
import com.dwes.mi_coleccion.modelo.Plataforma;
import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.repositorios.PlataformaRepository;
import com.dwes.mi_coleccion.repositorios.VideojuegoRepository;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Optional;

@Service
public class VideojuegoService {

    private final VideojuegoRepository repositorio;
    private final PlataformaRepository plataformas;

    public VideojuegoService(VideojuegoRepository repositorio,
                             PlataformaRepository plataformas) {
        this.repositorio = repositorio;
        this.plataformas = plataformas;
    }

    // --- Consultas y búsqueda paginada ---

    public List<Videojuego> listarVideojuegos() {
        return repositorio.findAll();
    }

    public Optional<Videojuego> buscarPorId(Long id) {
        return repositorio.findById(id);
    }

    public long contarVideojuegos() {
        return repositorio.count();
    }

    public Page<Videojuego> buscarPaginados(
            String titulo, String genero, int numeroPagina, String orden) {

        Sort ordenacion = "anio".equals(orden)
                ? Sort.by("anioLanzamiento").descending()
                        .and(Sort.by("id").ascending())
                : Sort.by("titulo").ascending()
                        .and(Sort.by("id").ascending());

        Pageable paginacion = PageRequest.of(
                Math.max(0, numeroPagina),
                5,
                ordenacion
        );

        String tituloBuscado = titulo == null ? "" : titulo.trim();
        String generoBuscado = genero == null ? "" : genero.trim();

        return repositorio.buscarConFiltros(
                tituloBuscado, generoBuscado, paginacion
        );
    }

    // --- Consulta y comprobación de plataformas ---

    public List<Plataforma> listarPlataformas() {
        return plataformas.findAll(Sort.by("nombre").ascending());
    }

    public boolean existePlataforma(Long id) {
        return id != null && plataformas.existsById(id);
    }

    private Plataforma obtenerPlataforma(Long id) {
        if (id == null) {
            throw new IllegalArgumentException("Selecciona una plataforma");
        }
        return plataformas.findById(id)
                .orElseThrow(() -> new IllegalArgumentException(
                        "La plataforma indicada no existe"));
    }

    // --- Operaciones CRUD adaptadas a la relación ---

    public Videojuego crear(VideojuegoForm form) {
        Plataforma plataforma = obtenerPlataforma(form.getPlataformaId());

        Videojuego nuevo = new Videojuego(
                form.getTitulo(),
                form.getGenero(),
                plataforma,
                form.getAnioLanzamiento()
        );
        return repositorio.save(nuevo);
    }

    public boolean actualizar(Long id, VideojuegoForm form) {
        Optional<Videojuego> encontrado = repositorio.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }

        Videojuego existente = encontrado.get();
        existente.setTitulo(form.getTitulo());
        existente.setGenero(form.getGenero());
        existente.setPlataforma(obtenerPlataforma(form.getPlataformaId()));
        existente.setAnioLanzamiento(form.getAnioLanzamiento());
        repositorio.save(existente);
        return true;
    }

    public boolean eliminar(Long id) {
        Optional<Videojuego> encontrado = repositorio.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }

        repositorio.delete(encontrado.get());
        return true;
    }
}
en este ejemplo

El método privado obtenerPlataforma() recupera el objeto asociado a partir del ID enviado por el formulario. Si el ID no existe, no podremos asignar una plataforma válida. crear() utiliza ese objeto al construir el nuevo videojuego y actualizar() lo asigna a la entidad ya existente.

Conservamos buscarPaginados(), con el tamaño de cinco resultados, los dos órdenes permitidos y los filtros normalizados. Si elimináramos ese método al sustituir el servicio, dejaría de funcionar el listado paginado.

🟧 Adaptamos el controlador MVC existente​

Las URL no cambian: /videojuegos, /videojuegos/nuevo, /videojuegos/{id}/editar y /videojuegos/{id}/eliminar siguen siendo válidas. Lo que cambia es el objeto vinculado al formulario y la necesidad de enviar la lista de plataformas a Thymeleaf.

Sustituimos la clase VideojuegoController completa, sin conservar otro controlador ni duplicar listar():

src/main/java/com/dwes/mi_coleccion/controladores/VideojuegoController.java
package com.dwes.mi_coleccion.controladores;

import com.dwes.mi_coleccion.formularios.VideojuegoForm;
import com.dwes.mi_coleccion.modelo.Videojuego;
import com.dwes.mi_coleccion.servicios.VideojuegoService;
import jakarta.validation.Valid;
import org.springframework.data.domain.Page;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

import java.util.Optional;

@Controller
@RequestMapping("/videojuegos")
public class VideojuegoController {

    private final VideojuegoService servicio;

    public VideojuegoController(VideojuegoService servicio) {
        this.servicio = servicio;
    }

    @GetMapping
    public String listar(
            @RequestParam(defaultValue = "") String titulo,
            @RequestParam(defaultValue = "") String genero,
            @RequestParam(defaultValue = "0") int pagina,
            @RequestParam(defaultValue = "titulo") String orden,
            Model model) {

        Page<Videojuego> resultado = servicio.buscarPaginados(
                titulo, genero, pagina, orden
        );

        model.addAttribute("videojuegos", resultado.getContent());
        model.addAttribute("pagina", resultado);
        model.addAttribute("total", resultado.getTotalElements());
        model.addAttribute("titulo", titulo);
        model.addAttribute("genero", genero);
        model.addAttribute("orden", orden);

        return "videojuegos/lista";
    }

    @GetMapping("/nuevo")
    public String mostrarNuevo(Model model) {
        model.addAttribute("videojuego", new VideojuegoForm());
        prepararFormulario(model, null);
        return "videojuegos/formulario";
    }

    @PostMapping("/nuevo")
    public String crear(
            @Valid @ModelAttribute("videojuego") VideojuegoForm form,
            BindingResult errores,
            Model model,
            RedirectAttributes redirect) {

        comprobarPlataforma(form, errores);
        if (errores.hasErrors()) {
            prepararFormulario(model, null);
            return "videojuegos/formulario";
        }

        servicio.crear(form);
        redirect.addFlashAttribute("mensaje", "Videojuego añadido correctamente.");
        return "redirect:/videojuegos";
    }

    @GetMapping("/{id}/editar")
    public String mostrarEditar(
            @PathVariable Long id,
            Model model,
            RedirectAttributes redirect) {

        Optional<Videojuego> encontrado = servicio.buscarPorId(id);
        if (encontrado.isEmpty()) {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
            return "redirect:/videojuegos";
        }

        model.addAttribute("videojuego", VideojuegoForm.desde(encontrado.get()));
        prepararFormulario(model, id);
        return "videojuegos/formulario";
    }

    @PostMapping("/{id}/editar")
    public String actualizar(
            @PathVariable Long id,
            @Valid @ModelAttribute("videojuego") VideojuegoForm form,
            BindingResult errores,
            Model model,
            RedirectAttributes redirect) {

        comprobarPlataforma(form, errores);
        if (errores.hasErrors()) {
            prepararFormulario(model, id);
            return "videojuegos/formulario";
        }

        if (!servicio.actualizar(id, form)) {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
            return "redirect:/videojuegos";
        }

        redirect.addFlashAttribute("mensaje", "Videojuego actualizado correctamente.");
        return "redirect:/videojuegos";
    }

    @PostMapping("/{id}/eliminar")
    public String eliminar(@PathVariable Long id, RedirectAttributes redirect) {
        if (servicio.eliminar(id)) {
            redirect.addFlashAttribute("mensaje", "Videojuego eliminado.");
        } else {
            redirect.addFlashAttribute("error", "El videojuego no existe.");
        }
        return "redirect:/videojuegos";
    }

    private void prepararFormulario(Model model, Long idEdicion) {
        model.addAttribute("modoEdicion", idEdicion != null);
        model.addAttribute("idEdicion", idEdicion);
        model.addAttribute("plataformas", servicio.listarPlataformas());
    }

    private void comprobarPlataforma(VideojuegoForm form, BindingResult errores) {
        if (form.getPlataformaId() != null
                && !servicio.existePlataforma(form.getPlataformaId())) {
            errores.rejectValue("plataformaId", "plataforma.invalida",
                    "Selecciona una plataforma válida");
        }
    }
}
en este ejemplo

prepararFormulario() añade al Model las plataformas y la información necesaria para distinguir entre alta y edición. También se ejecuta cuando hay errores: de lo contrario, el desplegable aparecería vacío al volver a mostrar el formulario.

comprobarPlataforma() comprueba que un ID no nulo existe en MySQL. La anotación @NotNull solo comprueba si se recibió un valor; no puede validar que haya una fila correspondiente. Si el usuario envía un ID inventado, BindingResult recogerá un error junto al campo.

Los métodos del listado mantienen los filtros, la ordenación y la paginación que ya desarrollamos. Los métodos POST siguen redirigiendo al listado después de guardar correctamente.

aviso

Esta comprobación evita muchos errores habituales, pero no garantiza que una plataforma no pueda desaparecer después de comprobar su existencia y antes de guardar. La clave ajena de MySQL sigue siendo la protección definitiva de la integridad referencial. Profundizaremos en operaciones concurrentes y transacciones al estudiar su gestión.

🟥 ¿Qué hacemos ante los errores más frecuentes?​

🟩 El proyecto ya no compila​

Revisamos que el constructor de Videojuego recibe un objeto Plataforma y que hemos sustituido la clase antigua. No debe quedar ninguna clase temporal de comprobación que intente construir un videojuego con el texto de la plataforma. 🟨 Hibernate indica que falta una columna​

Comprobamos DESCRIBE videojuegos; y DESCRIBE plataformas;. La primera tabla debe tener plataforma_id y no debe conservar la antigua columna obligatoria plataforma. No repetimos ciegamente los ALTER TABLE si una parte de la migración ya se ejecutó.

🟧 El desplegable no muestra plataformas​

Consultamos SELECT * FROM plataformas;. Si la tabla está vacía, habrá que incorporar plataformas. Si sí contiene filas, comprobamos el método listarPlataformas() y que prepararFormulario() añada el atributo plataformas al modelo en todos los caminos, incluidos los errores de validación.

🟥 Thymeleaf falla al mostrar la plataforma​

La plantilla debe utilizar juego.plataforma.nombre. Confirmamos que Videojuego tiene la asociación @ManyToOne y que las consultas utilizadas en el listado y en la edición recuperan la relación con @EntityGraph.

🟪 Tras la migración funcionan los formularios, pero no el buscador​

Comprobamos que el servicio conserva buscarPaginados(), el repositorio ofrece buscarConFiltros(..., Pageable) y el método listar() sigue recibiendo titulo, genero, pagina y orden. El problema suele aparecer cuando copiamos una versión antigua completa del servicio o del controlador y perdemos métodos posteriores.

8️⃣ Qué debemos haber comprendido​

Una migración no termina al ejecutar correctamente las instrucciones SQL. Debemos entender por qué se modifica la estructura, de dónde proceden los datos transformados y cómo comprobamos que la aplicación sigue utilizando esos registros sin contradicciones.

🟩 Aplicamos el procedimiento a otro caso​

Imaginemos una biblioteca cuyo campo Libro.editorial se ha almacenado durante meses como texto. Ahora queremos convertir Editorial en una entidad propia, de forma que varios libros compartan el mismo registro. No vamos a programar esta segunda migración: utilizaremos lo aprendido para describir cómo la planificaríamos.

  1. ¿Qué información revisaríamos antes de crear una tabla editoriales?
  2. ¿Cómo conservaríamos los nombres originales hasta comprobar que cada libro tiene una editorial válida?
  3. ¿Qué consultas nos permitirían verificar que no se ha perdido ningún libro?
  4. ¿Por qué no bastaría con cambiar String editorial por Editorial editorial en la clase Java?
  5. ¿Qué archivos de una aplicación Spring Boot con Thymeleaf necesitaríamos revisar además de las entidades?

Esta comprobación es no evaluable y no requiere entrega.

🟨 Lista de comprobación antes de continuar​

  • Hemos guardado una copia de seguridad válida de mi_coleccion.
  • El total de videojuegos antes y después coincide.
  • Cada videojuego tiene una plataforma existente y la correspondencia es correcta.
  • Existe la restricción de clave ajena en MySQL.
  • El proyecto arranca con las entidades actualizadas.
  • El CRUD, los filtros y la paginación siguen funcionando.
  • El formulario utiliza un desplegable y mantiene el CSS de MiColección.
