3.2. Implementación de relaciones uno a muchos

En el apartado anterior hemos aprendido a reconocer las cardinalidades y a expresar relaciones entre entidades con JPA. Ahora vamos a aplicarlas a una situación concreta: una biblioteca de aula en la que cada libro pertenece a una editorial y una editorial puede publicar muchos libros.

No vamos a transformar MiColección ni a migrar sus datos. Crearemos una aplicación independiente para diseñar la relación correctamente desde el principio, observar cómo se almacena en MySQL y utilizarla en una aplicación web con Spring Boot y Thymeleaf.

El trabajo se dividirá en dos etapas. Primero construiremos una relación N:1 unidireccional, suficiente para registrar libros y consultar su editorial. Después añadiremos el recorrido inverso mediante @OneToMany(mappedBy = "editorial") y comprobaremos qué aporta una relación bidireccional. Las relaciones N:M con categorías llegarán en el apartado 3.3, como ampliación de esta misma biblioteca.

Idea principal

En Java, un libro tendrá una propiedad Editorial editorial. En MySQL, esa relación se guardará mediante libros.editorial_id, que apuntará a editoriales.id.

El formulario enviará un identificador, pero el servicio recuperará el objeto Editorial existente antes de asignarlo al libro. Así podremos guardar y editar libros sin duplicar editoriales.

1️⃣ Diseñamos la biblioteca y su primera relación​

🟩 Qué debe permitir la aplicación​

El centro dispone de un catálogo de editoriales conocidas. El alumnado podrá consultar los libros, añadir nuevos títulos, editar sus datos y eliminar aquellos que ya no formen parte de la biblioteca. Para cada libro guardaremos su título, año de publicación y editorial.

En esta primera etapa no crearemos pantallas para administrar editoriales. Introduciremos unos pocos registros directamente en MySQL y los utilizaremos como opciones de un desplegable. De esta forma podremos centrarnos en cómo se recupera y guarda una entidad relacionada, sin añadir otro CRUD que no necesitamos.

🟨 Interpretamos la relación 1:N​

Una editorial puede publicar muchos libros, mientras que cada libro de nuestra aplicación debe pertenecer a una sola editorial. La clave ajena se coloca en la tabla del lado N: libros.

En este ejemplo, los libros El faro y La brújula pertenecen a la misma editorial. No tenemos dos registros de «Ediciones Aurora»: los dos libros guardan el valor 1 en su clave ajena.

La correspondencia con Java será:

La relación que queremos representar
// En Libro:
private Editorial editorial;

La propiedad de Java es un objeto, no un Long editorialId. Ese identificador sí aparecerá en el formulario, porque el navegador no puede enviar directamente objetos JPA.

🟧 Organizamos el trabajo por etapas​

Seguiremos un orden que nos permita comprobar cada avance:

  1. Crear biblioteca_aula y el proyecto Spring Boot.
  2. Definir Editorial y Libro con @ManyToOne y @JoinColumn.
  3. Comprobar la columna editorial_id y la clave ajena en MySQL.
  4. Crear los repositorios, el servicio, el formulario y las vistas de libros.
  5. Probar altas, ediciones y eliminaciones sin perder editoriales.
  6. Incorporar @OneToMany(mappedBy = "editorial") y consultar los libros de una editorial.

No es necesario empezar por el sexto paso. Una relación N:1 unidireccional ya permite construir una aplicación completa y es la mejor forma de comprender dónde se almacena realmente la asociación.

2️⃣ Preparamos el proyecto y MySQL​

🟩 Creamos una base de datos independiente​

Utilizaremos el servidor MySQL que ya tenemos disponible para la unidad. Puede estar instalado como servicio o ejecutándose en un contenedor Docker, siempre que Spring Boot pueda conectarse a él en localhost:3306. La aplicación y la base de datos serán distintas de las de MiColección.

Entramos en el cliente MySQL con una cuenta que tenga permisos para crear bases de datos y usuarios:

Acceso al servidor MySQL
mysql -u root -p

Si estamos utilizando Docker y el cliente mysql no está instalado en Windows, podemos abrirlo dentro del contenedor, sustituyendo el nombre de ejemplo por el de nuestro contenedor:

Alternativa con MySQL en Docker
docker exec -it NOMBRE_CONTENEDOR_MYSQL mysql -u root -p

En ambos casos, los comandos SQL siguientes se ejecutan dentro del cliente MySQL, no en PowerShell.

Ejecutamos lo siguiente una sola vez. Sustituiremos la contraseña de ejemplo por una propia:

Base de datos y cuenta de desarrollo
CREATE DATABASE biblioteca_aula
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;

CREATE USER 'biblioteca_app'@'%'
IDENTIFIED BY 'SUSTITUIR_POR_UNA_CONTRASENA_PROPIA';

GRANT ALL PRIVILEGES ON biblioteca_aula.*
TO 'biblioteca_app'@'%';
en este ejemplo

La base biblioteca_aula comienza vacía. La cuenta biblioteca_app solo recibe privilegios sobre esta base y será la que utilice Spring Boot.

En esta práctica de desarrollo utilizamos % para admitir también la conexión cuando MySQL se ejecuta en Docker y la aplicación se inicia fuera del contenedor. No es una configuración recomendable para un servidor de producción expuesto a una red: allí restringiríamos el origen de las conexiones y los permisos de la cuenta.

Si ya existe alguna de estas estructuras, no repetiremos los comandos sin revisar primero su estado.

🟨 Generamos el proyecto desde Spring Initializr​

Desde Spring Initializr generamos un proyecto Maven, con Java 21 y una versión estable de Spring Boot compatible con el resto de la unidad. Configuramos el grupo com.dwes y el artefacto biblioteca-relacional.

Añadimos las dependencias Spring Web (MVC), Thymeleaf, Spring Data JPA, MySQL Driver y Validation. Según la versión de Spring Boot, el iniciador de Spring MVC puede aparecer como spring-boot-starter-webmvc.

Abrimos el proyecto en IntelliJ IDEA gratuito. Utilizaremos el paquete base com.dwes.biblioteca_relacional y, dentro de él, los paquetes modelo, repositorios, servicios, formularios y controladores.

Esta es la estructura que tendremos al terminar la primera etapa:

🟧 Configuramos la conexión​

En src/main/resources/application.properties escribimos:

src/main/resources/application.properties

spring.datasource.url=jdbc:mysql://localhost:3306/biblioteca_aula
spring.datasource.username=biblioteca_app

en este ejemplo

El valor de DB_PASSWORD se configura en IntelliJ desde Run → Edit Configurations → Environment variables, dentro de la configuración con la que arrancaremos este proyecto. No escribimos la contraseña real en el archivo ni la subimos a Git.

Usamos ddl-auto=update porque partimos de una base nueva y vacía y queremos comprobar cómo Hibernate genera las tablas a partir de las entidades. Una vez creado y comprobado el esquema, podremos cambiarlo a validate para evitar nuevas modificaciones automáticas.

Con spring.jpa.open-in-view=false evitamos depender de que Thymeleaf cargue relaciones adicionales mientras genera la página. Cuando una vista necesite una relación, la recuperaremos expresamente desde el repositorio.

aviso

No utilizaremos ddl-auto=create ni create-drop: podrían eliminar y recrear las tablas, perdiendo datos. Tampoco ejecutaremos ningún cambio sobre mi_coleccion.

3️⃣ Primera etapa: definimos una relación N:1 unidireccional​

🟩 Creamos la entidad Editorial​

Una editorial tiene un identificador y un nombre. Por ahora no contiene una colección de libros; todavía no necesitamos navegar desde la editorial hacia sus publicaciones.

src/main/java/com/dwes/biblioteca_relacional/modelo/Editorial.java
package com.dwes.biblioteca_relacional.modelo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "editoriales")
public class Editorial {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 100)
    private String nombre;

    public Editorial() {
    }

    public Long getId() {
        return id;
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }
}
en este ejemplo

@Entity indica que la clase representa una entidad persistente y @Table(name = "editoriales") fija el nombre de su tabla. El id utiliza el mismo sistema de generación que ya conocemos de MiColección.

Declaramos nombre obligatorio y único porque, en este pequeño catálogo, cada nombre de editorial se almacenará una sola vez. El constructor sin argumentos permite que JPA cree los objetos al consultar la base de datos.

🟨 Creamos Libro y su propiedad Editorial​

Ahora aparece la verdadera novedad. Además de sus atributos propios, cada Libro tendrá una referencia a un objeto Editorial.

src/main/java/com/dwes/biblioteca_relacional/modelo/Libro.java
package com.dwes.biblioteca_relacional.modelo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "libros")
public class Libro {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String titulo;

    @Column(name = "anio_publicacion", nullable = false)
    private Integer anioPublicacion;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "editorial_id", nullable = false)
    private Editorial editorial;

    public Libro() {
    }

    public Long getId() {
        return id;
    }

    public String getTitulo() {
        return titulo;
    }

    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }

    public Integer getAnioPublicacion() {
        return anioPublicacion;
    }

    public void setAnioPublicacion(Integer anioPublicacion) {
        this.anioPublicacion = anioPublicacion;
    }

    public Editorial getEditorial() {
        return editorial;
    }

    public void setEditorial(Editorial editorial) {
        this.editorial = editorial;
    }
}
en este ejemplo

La anotación @ManyToOne expresa que muchos libros pueden pertenecer a una misma editorial. La propiedad Java es Editorial editorial: no guardamos el identificador como un campo Long en la entidad.

@JoinColumn(name = "editorial_id") indica que el identificador de la editorial se almacena en la tabla libros. Con optional = false y nullable = false declaramos que un libro debe tener una editorial asignada y que la clave ajena no puede quedar vacía.

La opción fetch = FetchType.LAZY solicita una carga diferida de la editorial. Más adelante indicaremos expresamente al repositorio cuándo necesitamos recuperarla, por ejemplo para mostrar su nombre en el listado.

🟧 Comprobamos lo que ha creado JPA en MySQL​

Ahora sí arrancamos Spring Boot. Si la conexión y las entidades son correctas, Hibernate generará las tablas en la base vacía.

Entramos con la cuenta del proyecto:

Conectamos con la base de la biblioteca
mysql -u biblioteca_app -p biblioteca_aula

Si utilizamos el cliente dentro del contenedor Docker, accederemos de la misma forma que antes, pero indicando -u biblioteca_app -p biblioteca_aula.

Y ejecutamos:

Comprobamos el esquema generado
SHOW TABLES;
DESCRIBE editoriales;
DESCRIBE libros;
SHOW CREATE TABLE libros;

Debemos encontrar dos tablas: editoriales y libros. En la segunda aparecerá la columna editorial_id, y SHOW CREATE TABLE permitirá comprobar que existe una restricción de clave ajena hacia editoriales(id).

ElementoDónde debe aparecerQué significa
editoriales.idTabla editorialesClave primaria de cada editorial.
libros.editorial_idTabla librosIdentificador de la editorial asignada al libro.
FOREIGN KEYDefinición de librosImpide apuntar a una editorial inexistente.
NOT NULLColumna editorial_idImpide guardar un libro sin editorial.
consejo

Una vez confirmado que Hibernate ha creado las dos tablas y la clave ajena, podemos sustituir spring.jpa.hibernate.ddl-auto=update por validate y reiniciar la aplicación. validate comprueba la compatibilidad del esquema, pero no crea ni modifica tablas.

4️⃣ Preparamos editoriales y repositorios​

🟩 Introducimos las editoriales que utilizaremos​

Como todavía no existe una pantalla de administración de editoriales, crearemos tres registros en MySQL. Estos nombres estarán disponibles después en el formulario de libros.

Datos iniciales: ejecutar una sola vez
INSERT INTO editoriales (nombre) VALUES
('Ediciones Aurora'),
('Editorial Horizonte'),
('Letras del Norte');

SELECT id, nombre FROM editoriales ORDER BY nombre;

Anotamos que los identificadores los asigna MySQL. No supondremos que «Ediciones Aurora» siempre tenga el ID 1: nuestro código buscará los registros y el desplegable utilizará sus IDs reales.

aviso

No repetiremos el INSERT si esas editoriales ya existen. La restricción unique = true impide registrar dos editoriales con el mismo nombre.

🟨 Creamos EditorialRepository​

Necesitamos consultar las editoriales existentes para mostrarlas en el formulario y encontrar la seleccionada.

src/main/java/com/dwes/biblioteca_relacional/repositorios/EditorialRepository.java
package com.dwes.biblioteca_relacional.repositorios;

import com.dwes.biblioteca_relacional.modelo.Editorial;
import org.springframework.data.jpa.repository.JpaRepository;

public interface EditorialRepository extends JpaRepository<Editorial, Long> {
}

Los métodos heredados findAll(), findById() y existsById() son suficientes. No crearemos un CRUD de editoriales: el objetivo de este apartado es trabajar con la asociación de los libros.

🟧 Creamos LibroRepository y preparamos las consultas​

Además de guardar y eliminar libros, tendremos que recuperar su editorial para mostrarla en una plantilla Thymeleaf.

src/main/java/com/dwes/biblioteca_relacional/repositorios/LibroRepository.java
package com.dwes.biblioteca_relacional.repositorios;

import com.dwes.biblioteca_relacional.modelo.Libro;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.List;
import java.util.Optional;

public interface LibroRepository extends JpaRepository<Libro, Long> {

    @EntityGraph(attributePaths = "editorial")
    List<Libro> findAllByOrderByTituloAsc();

    @Override
    @EntityGraph(attributePaths = "editorial")
    Optional<Libro> findById(Long id);
}
en este ejemplo

findAllByOrderByTituloAsc() es un método derivado de Spring Data JPA: recupera los libros ordenados alfabéticamente por título. No necesitamos escribir una consulta JPQL para esta operación sencilla.

@EntityGraph(attributePaths = "editorial") indica que, en esas consultas, queremos disponer también de la editorial asociada. Así la vista podrá utilizar ${libro.editorial.nombre} sin depender de que Thymeleaf provoque consultas adicionales sobre una relación LAZY.

El valor "editorial" es el nombre de la propiedad Java de Libro, no la columna SQL editorial_id.

5️⃣ Recibimos la editorial seleccionada desde un formulario​

🟩 Entendemos qué envía el navegador​

Aunque la entidad Libro contiene un objeto Editorial, un formulario HTML no puede enviarlo directamente. El usuario verá una lista de nombres, pero el navegador enviará el identificador de la opción seleccionada.

Por ejemplo:

Datos de un formulario de libro
titulo=El faro
anioPublicacion=2022
editorialId=2

El servidor recibirá editorialId=2. A continuación, el servicio buscará la editorial con ese identificador y la asignará al libro.

Es importante diferenciar estos dos datos:

  • En el formulario: Long editorialId, porque recibimos un valor desde HTTP.
  • En la entidad JPA: Editorial editorial, porque representamos la asociación entre objetos.

🟨 Definimos LibroForm​

Para no mezclar ambas responsabilidades crearemos una clase que representa los valores del formulario, pero que no es una entidad JPA. Es el mismo planteamiento de validación de formularios que ya conocemos de la UT3.

src/main/java/com/dwes/biblioteca_relacional/formularios/LibroForm.java
package com.dwes.biblioteca_relacional.formularios;

import com.dwes.biblioteca_relacional.modelo.Libro;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

public class LibroForm {

    @NotBlank(message = "El título es obligatorio")
    @Size(max = 150, message = "Máximo 150 caracteres")
    private String titulo;

    @NotNull(message = "El año es obligatorio")
    @Min(value = 1450, message = "Indica un año válido")
    private Integer anioPublicacion;

    @NotNull(message = "Selecciona una editorial")
    private Long editorialId;

    public static LibroForm desde(Libro libro) {
        LibroForm form = new LibroForm();
        form.setTitulo(libro.getTitulo());
        form.setAnioPublicacion(libro.getAnioPublicacion());
        form.setEditorialId(libro.getEditorial().getId());
        return form;
    }

    public String getTitulo() {
        return titulo;
    }

    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }

    public Integer getAnioPublicacion() {
        return anioPublicacion;
    }

    public void setAnioPublicacion(Integer anioPublicacion) {
        this.anioPublicacion = anioPublicacion;
    }

    public Long getEditorialId() {
        return editorialId;
    }

    public void setEditorialId(Long editorialId) {
        this.editorialId = editorialId;
    }
}
en este ejemplo

La anotación @NotNull exige que el usuario seleccione una editorial, pero no comprueba que el ID exista en MySQL. Más adelante haremos esa comprobación utilizando el repositorio.

El método desde(Libro) prepara los valores cuando abrimos el formulario de edición. Obtiene el ID de la editorial actual para que Thymeleaf pueda mostrar la opción seleccionada. No convierte la clase LibroForm en una entidad ni modifica los datos almacenados.

6️⃣ Implementamos el servicio: del ID al objeto relacionado​

🟩 Recuperamos una editorial existente antes de guardar​

Nuestro servicio necesitará dos repositorios. Uno gestiona los libros y otro permite localizar las editoriales ya almacenadas.

La operación más importante seguirá esta secuencia: recibir editorialId → buscar Editorial → asignarla a Libro → guardar con JPA.

src/main/java/com/dwes/biblioteca_relacional/servicios/LibroService.java
package com.dwes.biblioteca_relacional.servicios;

import com.dwes.biblioteca_relacional.formularios.LibroForm;
import com.dwes.biblioteca_relacional.modelo.Editorial;
import com.dwes.biblioteca_relacional.modelo.Libro;
import com.dwes.biblioteca_relacional.repositorios.EditorialRepository;
import com.dwes.biblioteca_relacional.repositorios.LibroRepository;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Optional;

@Service
public class LibroService {

    private final LibroRepository libros;
    private final EditorialRepository editoriales;

    public LibroService(LibroRepository libros,
                        EditorialRepository editoriales) {
        this.libros = libros;
        this.editoriales = editoriales;
    }

    public List<Libro> listarLibros() {
        return libros.findAllByOrderByTituloAsc();
    }

    public Optional<Libro> buscarPorId(Long id) {
        return libros.findById(id);
    }

    public List<Editorial> listarEditoriales() {
        return editoriales.findAll(Sort.by("nombre"));
    }

    public boolean existeEditorial(Long id) {
        return id != null && editoriales.existsById(id);
    }

    private Editorial obtenerEditorial(Long id) {
        return editoriales.findById(id)
                .orElseThrow(() -> new IllegalArgumentException(
                        "La editorial seleccionada no existe"));
    }

    public Libro crear(LibroForm form) {
        Libro libro = new Libro();
        copiarDatos(libro, form);
        return libros.save(libro);
    }

    public boolean actualizar(Long id, LibroForm form) {
        Optional<Libro> encontrado = libros.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }

        Libro libro = encontrado.get();
        copiarDatos(libro, form);
        libros.save(libro);
        return true;
    }

    public boolean eliminar(Long id) {
        Optional<Libro> encontrado = libros.findById(id);
        if (encontrado.isEmpty()) {
            return false;
        }

        libros.delete(encontrado.get());
        return true;
    }

    private void copiarDatos(Libro libro, LibroForm form) {
        libro.setTitulo(form.getTitulo());
        libro.setAnioPublicacion(form.getAnioPublicacion());
        libro.setEditorial(obtenerEditorial(form.getEditorialId()));
    }
}
en este ejemplo

obtenerEditorial() busca el registro mediante findById(). Si no existe, se produce una excepción en lugar de asignar una editorial inventada. Antes de guardar, el controlador comprobará que el ID recibido es válido para poder mostrar un mensaje junto al campo.

En copiarDatos() se encuentra la operación esencial: libro.setEditorial(...). No creamos un objeto new Editorial() al guardar cada libro; recuperamos uno que ya existe. Cuando JPA guarde el libro, almacenará su identificador en la columna editorial_id.

El servicio no conoce Model, las rutas HTTP ni Thymeleaf. Mantiene las responsabilidades de la capa de servicios que ya hemos utilizado en MiColección.

🟨 ¿Qué debe ocurrir cuando eliminamos un libro?​

eliminar() borra el registro del libro. No debe borrar su editorial, porque esa editorial puede seguir asociada a otros libros.

No hemos utilizado CascadeType.REMOVE ni CascadeType.ALL en Libro.editorial. Su ausencia es intencionada: en este modelo las editoriales son registros compartidos y no dependen de la existencia de un libro concreto.

aviso

No confundamos eliminar una relación con eliminar la entidad relacionada. Si un libro deja de pertenecer a la biblioteca, puede desaparecer su fila de libros, pero el registro de editoriales debe continuar disponible.

🟩 Mantenemos las rutas CRUD habituales​

🟨 Implementamos LibroController​

El controlador mostrará los formularios, comprobará sus errores y delegará las operaciones de persistencia en el servicio. Cuando se devuelva una vista Thymeleaf utilizaremos @Controller, sin @ResponseBody.

src/main/java/com/dwes/biblioteca_relacional/controladores/LibroController.java
package com.dwes.biblioteca_relacional.controladores;

import com.dwes.biblioteca_relacional.formularios.LibroForm;
import com.dwes.biblioteca_relacional.servicios.LibroService;
import jakarta.validation.Valid;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

@Controller
@RequestMapping("/libros")
public class LibroController {

    private final LibroService servicio;

    public LibroController(LibroService servicio) {
        this.servicio = servicio;
    }

    @GetMapping
    public String listar(Model model) {
        model.addAttribute("libros", servicio.listarLibros());
        return "libros/lista";
    }

    @GetMapping("/nuevo")
    public String mostrarNuevo(Model model) {
        model.addAttribute("libro", new LibroForm());
        prepararFormulario(model, null);
        return "libros/formulario";
    }

    @PostMapping("/nuevo")
    public String crear(@Valid @ModelAttribute("libro") LibroForm form,
                        BindingResult errores, Model model,
                        RedirectAttributes redirect) {
        comprobarEditorial(form, errores);
        if (errores.hasErrors()) {
            prepararFormulario(model, null);
            return "libros/formulario";
        }

        servicio.crear(form);
        redirect.addFlashAttribute("mensaje", "Libro añadido correctamente.");
        return "redirect:/libros";
    }

    @GetMapping("/{id}/editar")
    public String mostrarEditar(@PathVariable Long id, Model model,
                                RedirectAttributes redirect) {
        var encontrado = servicio.buscarPorId(id);
        if (encontrado.isEmpty()) {
            redirect.addFlashAttribute("error", "El libro no existe.");
            return "redirect:/libros";
        }

        model.addAttribute("libro", LibroForm.desde(encontrado.get()));
        prepararFormulario(model, id);
        return "libros/formulario";
    }

    @PostMapping("/{id}/editar")
    public String actualizar(@PathVariable Long id,
                             @Valid @ModelAttribute("libro") LibroForm form,
                             BindingResult errores, Model model,
                             RedirectAttributes redirect) {
        comprobarEditorial(form, errores);
        if (errores.hasErrors()) {
            prepararFormulario(model, id);
            return "libros/formulario";
        }

        if (!servicio.actualizar(id, form)) {
            redirect.addFlashAttribute("error", "El libro no existe.");
            return "redirect:/libros";
        }

        redirect.addFlashAttribute("mensaje", "Libro actualizado correctamente.");
        return "redirect:/libros";
    }

    @PostMapping("/{id}/eliminar")
    public String eliminar(@PathVariable Long id, RedirectAttributes redirect) {
        if (servicio.eliminar(id)) {
            redirect.addFlashAttribute("mensaje", "Libro eliminado.");
        } else {
            redirect.addFlashAttribute("error", "El libro no existe.");
        }
        return "redirect:/libros";
    }

    private void prepararFormulario(Model model, Long idEdicion) {
        model.addAttribute("modoEdicion", idEdicion != null);
        model.addAttribute("idEdicion", idEdicion);
        model.addAttribute("editoriales", servicio.listarEditoriales());
    }

    private void comprobarEditorial(LibroForm form, BindingResult errores) {
        if (form.getEditorialId() != null
                && !servicio.existeEditorial(form.getEditorialId())) {
            errores.rejectValue("editorialId", "editorial.invalida",
                    "Selecciona una editorial válida");
        }
    }
}
en este ejemplo

@GetMapping muestra páginas o formularios y @PostMapping recoge los envíos. @ModelAttribute("libro") vincula los datos HTTP con LibroForm, mientras que @Valid y BindingResult permiten mostrar los errores de validación.

El método comprobarEditorial() distingue recibir un ID de comprobar que exista. Una opción vacía la detecta @NotNull; un ID que no corresponde a ninguna editorial se rechaza mediante errores.rejectValue(...).

prepararFormulario() añade la lista de editoriales al Model también cuando hay errores. Si olvidáramos esa llamada, el desplegable no tendría opciones al volver a mostrar el formulario.

Después de guardar correctamente devolvemos una redirección al listado (Post/Redirect/Get), como en las prácticas anteriores.

🟩 Probamos el recorrido completo desde el navegador​

Arrancamos la aplicación y abrimos:

http://localhost:8080/libros

Realizamos estas comprobaciones en orden, utilizando los nombres reales de las editoriales del desplegable:

  1. Alta. Creamos un libro y seleccionamos «Ediciones Aurora». Comprobamos que aparece en el listado con el nombre de la editorial.
  2. Editorial compartida. Creamos un segundo libro y seleccionamos la misma editorial. No debe aparecer una editorial nueva en la base de datos.
  3. Edición. Cambiamos la editorial de uno de los libros a «Letras del Norte» y guardamos. El libro debe conservar su ID.
  4. Validación. Intentamos guardar un libro sin seleccionar editorial. Debe mostrarse un error, sin insertar una fila nueva.
  5. Eliminación. Borramos uno de los libros. Su editorial debe seguir existiendo y debe poder seleccionarse al crear otro libro.

🟨 Verificamos las asociaciones en MySQL​

La pantalla es útil, pero también debemos comprobar qué identificadores se han guardado realmente en las tablas.

Relación entre los registros almacenados
SELECT l.id, l.titulo, l.editorial_id, e.nombre AS editorial
FROM libros l
JOIN editoriales e ON l.editorial_id = e.id
ORDER BY l.id;

SELECT id, nombre FROM editoriales ORDER BY nombre;

La primera consulta muestra una fila por libro, con su clave ajena y el nombre de la editorial correspondiente. La segunda permite comprobar que las editoriales siguen existiendo aunque hayamos borrado un libro.

Podemos comprobar también cuántos libros tiene cada editorial utilizando una consulta SQL que no requiere todavía navegación bidireccional en Java:

Número de libros por editorial
SELECT e.nombre, COUNT(l.id) AS total_libros
FROM editoriales e
LEFT JOIN libros l ON l.editorial_id = e.id
GROUP BY e.id, e.nombre
ORDER BY e.nombre;
en este ejemplo

Usamos LEFT JOIN para que también aparezcan las editoriales que todavía no tienen libros. COUNT(l.id) cuenta los libros asociados a cada editorial y devuelve cero para las que no tienen ninguno.

Esta consulta muestra algo importante: la relación ya está completa en MySQL, aunque en Java todavía no exista Editorial.libros. No necesitamos una colección inversa para que la clave ajena funcione.

🟧 ¿Podemos borrar una editorial que tiene libros?​

La base de datos tiene una clave ajena desde libros.editorial_id hacia editoriales.id. Por eso, si una editorial está siendo utilizada por libros, MySQL debe impedir su eliminación mientras esos libros sigan referenciándola, salvo que se hubiera definido expresamente otra política de borrado.

No hemos configurado cascadas para borrar editoriales o libros relacionados. En nuestra biblioteca, el comportamiento adecuado es conservar los registros compartidos y evitar que un libro quede apuntando a un registro inexistente.

aviso

No resolveremos un error de clave ajena eliminando la restricción ni desactivando las comprobaciones de integridad de MySQL. Primero debemos comprender qué registros están relacionados y qué operación permite realmente el problema.

9️⃣ Segunda etapa: añadimos la navegación inversa con @OneToMany​

Hasta ahora hemos podido gestionar libros y acceder desde cada libro a su editorial. Esto es una relación unidireccional. Ahora queremos añadir una pantalla que muestre todos los libros publicados por una editorial y comprobar cómo se utiliza una colección inversa en JPA.

🟩 Modificamos Editorial para incorporar sus libros​

Añadimos los imports OneToMany, ArrayList y List a la clase Editorial, y declaramos una colección de libros con su método de acceso. El resto de la clase se mantiene igual.

Nuevos imports de Editorial.java
import jakarta.persistence.OneToMany;
import java.util.ArrayList;
import java.util.List;
Añadir dentro de la clase Editorial
@OneToMany(mappedBy = "editorial")
private List<Libro> libros = new ArrayList<>();

public List<Libro> getLibros() {
    return libros;
}
en este ejemplo

@OneToMany indica que una editorial puede tener una colección de libros. mappedBy = "editorial" hace referencia a la propiedad Java editorial de Libro, donde ya definimos el @ManyToOne y el @JoinColumn.

La columna que guarda la relación sigue siendo libros.editorial_id. No creamos otra clave ajena ni una tabla intermedia. Tampoco es necesario modificar Libro para añadir esta navegación inversa.

🟨 Comprendemos el lado propietario​

En esta relación bidireccional hay dos propiedades que permiten navegar en sentidos diferentes:

PropiedadFunciónPapel en JPA
Libro.editorialObtener la editorial de un libro.Lado propietario: define la clave ajena mediante @JoinColumn.
Editorial.librosObtener los libros de una editorial.Lado inverso: utiliza mappedBy.

Aunque escribamos editorial.getLibros() para recorrer la colección, la asociación se guarda desde Libro.editorial. Si queremos cambiar de editorial un libro, debemos seguir asignando la editorial correcta con libro.setEditorial(...).

Cuando trabajamos con los dos objetos simultáneamente en memoria, conviene mantener ambos lados sincronizados. En esta práctica, el servicio modifica el lado propietario y cada petición de consulta recupera de nuevo los datos; por eso no necesitamos un método auxiliar de sincronización todavía.

aviso

No añadiremos @JoinColumn a la colección de Editorial ni configuraremos un segundo propietario. Tampoco incluiremos CascadeType.ALL u orphanRemoval = true: los libros son registros que gestionamos desde su propio CRUD y no deben eliminarse accidentalmente por manipular la colección de una editorial.

🟧 Recuperamos una editorial con sus libros​

La colección libros utiliza carga diferida. Para mostrarla en una vista sin depender de una carga posterior desde Thymeleaf, indicaremos que esta consulta debe recuperarla expresamente.

En EditorialRepository añadimos estos imports:

Nuevos imports de EditorialRepository.java
import org.springframework.data.jpa.repository.EntityGraph;
import java.util.Optional;

Y, dentro de la interfaz, añadimos el siguiente método:

Añadir dentro de EditorialRepository
@Override
@EntityGraph(attributePaths = "libros")
Optional<Editorial> findById(Long id);
en este ejemplo

@EntityGraph(attributePaths = "libros") indica que necesitamos la colección de libros al recuperar una editorial por ID. Igual que antes, "libros" es el nombre de una propiedad Java, no una tabla ni una clave ajena.

Esta ampliación es apropiada para mostrar una editorial concreta y sus libros. No estamos paginando una colección ni preparando un listado de cientos de editoriales con todas sus publicaciones.

🟥 Añadimos una consulta al servicio​

En LibroService ya existe el repositorio editoriales. Por eso podemos incorporar este método sin crear otra clase de servicio:

Añadir dentro de LibroService
public Optional<Editorial> buscarEditorialConLibros(Long id) {
    return editoriales.findById(id);
}

Ahora el servicio podrá devolver una editorial junto a la colección que necesita la nueva pantalla.

🟪 Creamos una página para consultar los libros de una editorial​

Añadimos un controlador pequeño e independiente, porque ahora la ruta parte de una editorial. No es un CRUD de editoriales: solo permite consultar sus libros.

src/main/java/com/dwes/biblioteca_relacional/controladores/EditorialController.java
package com.dwes.biblioteca_relacional.controladores;

import com.dwes.biblioteca_relacional.servicios.LibroService;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

@Controller
@RequestMapping("/editoriales")
public class EditorialController {

    private final LibroService servicio;

    public EditorialController(LibroService servicio) {
        this.servicio = servicio;
    }

    @GetMapping("/{id}/libros")
    public String verLibros(@PathVariable Long id, Model model,
                            RedirectAttributes redirect) {
        var encontrada = servicio.buscarEditorialConLibros(id);
        if (encontrada.isEmpty()) {
            redirect.addFlashAttribute("error", "La editorial no existe.");
            return "redirect:/libros";
        }

        model.addAttribute("editorial", encontrada.get());
        return "editoriales/libros";
    }
}

La ruta /editoriales/{id}/libros recupera una editorial y devuelve una vista Thymeleaf. En esta página recorreremos editorial.libros, lo que no era posible directamente desde el objeto Editorial antes de añadir @OneToMany.

Creamos la carpeta templates/editoriales y la siguiente plantilla:

En la lista de libros seguimos utilizando la relación N:1 para acceder a libro.editorial.id y libro.editorial.nombre. Al seguir el enlace, recuperamos una Editorial y recorremos su colección con th:each="libro : ${editorial.libros}": es el sentido 1:N de la misma asociación.

Esta es la ventaja concreta de la relación bidireccional. No obstante, si una aplicación solo necesita el camino Libro → Editorial, no está obligada a declarar Editorial.libros.

🟩 Verificamos que el esquema no ha cambiado​

La incorporación de @OneToMany(mappedBy = "editorial") no debería crear una tabla intermedia ni una segunda columna de relación. Comprobamos en MySQL:

Comprobamos que seguimos utilizando la misma clave ajena
SHOW TABLES;
DESCRIBE libros;
SHOW CREATE TABLE libros;

Deben seguir existiendo solo las tablas editoriales y libros. La relación se almacena en libros.editorial_id, exactamente igual que antes de añadir la colección inversa.

🟨 Probamos la pantalla de una editorial​

Volvemos al listado de /libros y seleccionamos el enlace de una editorial:

  • Si tiene varios libros, veremos sus títulos en la nueva pantalla.
  • Si tiene uno solo, aparecerá únicamente ese libro.
  • Si todavía no tiene ninguno, se mostrará el mensaje correspondiente.
  • Si cambiamos la editorial de un libro desde el formulario, dejará de aparecer en la colección de la editorial anterior y aparecerá en la nueva cuando recarguemos sus páginas.

Esta última comprobación es especialmente importante: demuestra que el cambio se realiza desde Libro.editorial, aunque después consultemos la relación en el sentido contrario.

🟧 Errores frecuentes y cómo identificarlos​

🟩 Aparece una columna o una tabla intermedia inesperada​

Revisamos que la colección de Editorial utilice exactamente @OneToMany(mappedBy = "editorial") y que no hayamos creado un segundo @JoinColumn sobre ella. mappedBy señala la propiedad Java, no editorial_id.

🟨 La editorial no aparece en el desplegable​

Comprobamos primero SELECT * FROM editoriales; y después que prepararFormulario() añada editoriales al Model, también cuando hay errores de validación.

🟧 Thymeleaf no puede acceder a la editorial o a sus libros​

Revisamos @EntityGraph(attributePaths = "editorial") en LibroRepository y @EntityGraph(attributePaths = "libros") en EditorialRepository. No resolveremos el problema cambiando indiscriminadamente todas las relaciones a EAGER.

🟥 Al editar un libro, la editorial no cambia​

Comprobamos que el formulario envía el campo editorialId, que el servicio recupera la editorial mediante findById() y que llama a libro.setEditorial(...) antes de guardar.

🟪 Eliminar un libro también intenta eliminar su editorial​

El diseño no requiere cascadas de borrado. Revisamos que no hayamos añadido CascadeType.REMOVE ni CascadeType.ALL sobre Libro.editorial.

🟥 ¿Qué debemos haber aprendido?​

Antes de pasar a las relaciones N:M, deberíamos poder responder a estas cuestiones:

  1. ¿Por qué la clave ajena editorial_id está en la tabla libros y no en editoriales?
  2. ¿Por qué el formulario recibe editorialId, pero la entidad Libro contiene un objeto Editorial?
  3. ¿Qué función cumple @ManyToOne y qué indica @JoinColumn?
  4. ¿Qué añade @OneToMany(mappedBy = "editorial") y por qué no crea otra relación en MySQL?
  5. ¿Qué lado es el propietario de la relación y cuál debemos actualizar al cambiar una editorial?
  6. ¿Por qué eliminar un libro no debe eliminar automáticamente su editorial?
