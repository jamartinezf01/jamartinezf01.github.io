Actividad 2. Un gestor que ya permite trabajar

En la primera actividad conseguimos que nuestro gestor de incidencias informáticas mostrara los registros almacenados en MySQL y permitiera dar de alta otros nuevos desde el navegador. Ya no dependemos de una colección temporal: la información permanece en la base de datos.

Sin embargo, al empezar a utilizar la aplicación aparecen nuevas necesidades. El personal del departamento informático quiere consultar una incidencia con todos sus datos, corregir información, actualizar su estado y eliminar registros que se hayan creado por error. También necesitamos evitar que los formularios guarden información incompleta o incorrecta.

En esta actividad continuaremos con el mismo proyecto gestor_incidencias. No volveremos a crear la base de datos ni las clases que ya funcionan: ampliaremos la aplicación y reorganizaremos su código para separar las responsabilidades del controlador y la capa de servicios.

nota

Esta actividad es de entrega obligatoria y forma parte del seguimiento de la unidad. No tiene una calificación numérica propia y se registrará como Entregada o NO entregada.

1️⃣ Punto de partida​

Continuad con el proyecto gestor_incidencias que terminasteis en la Actividad 1. Ya debe permitir consultar las incidencias almacenadas en MySQL y registrar otras nuevas desde el navegador.

Si no conseguisteis completar la actividad anterior, podéis utilizar el proyecto de recuperación, que incorpora las funcionalidades mínimas necesarias para continuar:

👉 Descargar Gestor de incidencias — recuperación de la Actividad 1 (ZIP)

Descomprimidlo y abrid la carpeta gestor_incidencias desde IntelliJ IDEA. El ZIP incluye las clases Java, las vistas Thymeleaf, el CSS, el pom.xml con las dependencias necesarias y un README-RECUPERACION.md con indicaciones para ponerlo en marcha. También contiene el script de preparación de MySQL, que solo debéis ejecutar si todavía no tenéis preparada la base de datos.

Antes de empezar, comprobad que:

  • GET /incidencias muestra el listado recuperado de MySQL.
  • GET /incidencias/nueva abre el formulario de alta con sus estilos CSS.
  • POST /incidencias/nueva permite registrar una incidencia y volver al listado.
  • La incidencia registrada sigue disponible después de detener y volver a iniciar la aplicación.
aviso

No volváis a crear el proyecto ni sustituyáis una base de datos que ya funciona.

Si terminasteis la actividad 1, debéis continuar con vuestro propio código. El proyecto de recuperación es una alternativa para quien necesite retomar el trabajo, no una solución de la actividad 2. Mantened la contraseña de MySQL fuera del proyecto mediante DB_PASSWORD.

consejo

El proyecto de recuperación está preparado con Java 21 y Spring Boot 4.1.2 e incluye las dependencias Maven de Web MVC, Thymeleaf, Spring Data JPA, MySQL Driver, Validation y pruebas. Antes de modificarlo, comprobad que arranca y funciona correctamente.

2️⃣ El reto: completar el gestor de incidencias​

🟩 Una aplicación que debe permitir gestionar los registros​

Hasta ahora, el gestor ofrece un listado y un formulario de alta. El departamento informático nos pide incorporar las siguientes funciones:

FuncionalidadQué debe poder hacer el usuario
Consultar una incidenciaAbrir una ficha con toda su información.
Editar una incidenciaCorregir título y descripción, cambiar su prioridad o actualizar su estado.
Eliminar una incidenciaBorrar un registro creado por error mediante una acción explícita.
Validar los datosRecibir mensajes claros cuando un formulario contenga información incorrecta.
Gestionar incidencias inexistentesObtener una respuesta comprensible si intenta acceder a un identificador que no existe.

Al terminar, el listado debe seguir funcionando y el formulario de alta debe continuar permitiendo registrar incidencias. Las funcionalidades nuevas no pueden romper lo que ya habíamos conseguido.

🟨 Reglas que debe respetar la aplicación​

La estructura de la entidad Incidencia se mantiene: id, titulo, descripcion, prioridad, estado y fechaRegistro. No necesitamos nuevas tablas ni relaciones JPA.

Una incidencia nueva debe comenzar con estado ABIERTA y con la fecha actual. Al editarla, podremos modificar su título, descripción, prioridad y estado, pero no su identificador ni su fecha original de registro.

Los valores permitidos seguirán siendo:

  • Prioridad: BAJA, MEDIA o ALTA.
  • Estado: ABIERTA, EN_PROCESO o RESUELTA.

La aplicación no debe aceptar otros valores aunque alguien modifique manualmente la petición enviada desde el navegador.

Idea principal

Ya sabemos utilizar controladores y formularios Thymeleaf. El reto ahora consiste en completar las operaciones CRUD sobre MySQL y organizar correctamente el código con una capa de servicios, sin repetir el ejemplo guiado de MiColección.

🟧 Qué archivos tendremos que revisar​

No es necesario que todos los proyectos tengan exactamente los mismos nombres de métodos, pero sí que separen las responsabilidades de forma clara.

ElementoTrabajo previsto
IncidenciaIncorporar las restricciones de validación necesarias.
IncidenciaRepositoryMantener las operaciones JPA que ya utilizamos.
IncidenciaServiceCrear la capa que gestione las operaciones sobre incidencias.
IncidenciaControllerAtender las peticiones web delegando las operaciones en el servicio.
incidencias.htmlAñadir enlaces o acciones para consultar, editar y eliminar.
Plantilla de detalleMostrar la información completa de una incidencia.
Plantilla de ediciónPermitir modificar los datos autorizados.
nueva-incidencia.htmlIncorporar los mensajes de validación.
gestor-incidencias.cssAmpliar los estilos únicamente si resulta necesario.

Podéis reutilizar una misma plantilla para el alta y la edición si conseguís que ambas operaciones funcionen correctamente. Lo importante es el comportamiento, no la cantidad de archivos HTML.

3️⃣ Primera etapa: incorporamos la capa de servicios​

🟩 Separamos las responsabilidades​

En la actividad anterior permitimos, de forma provisional, que el controlador utilizara directamente IncidenciaRepository. Ahora debemos reorganizarlo.

Cread una clase de servicio anotada con @Service que reciba el repositorio mediante inyección por constructor. Su responsabilidad será coordinar las operaciones necesarias para gestionar las incidencias y aplicar las reglas de negocio.

El controlador debe centrarse en recibir las peticiones, preparar los datos para Thymeleaf y elegir la vista o redirección adecuada. Una vez realizada la reorganización, no debe acceder directamente al repositorio.

Como mínimo, el servicio deberá permitir:

  • Obtener todas las incidencias para el listado.
  • Buscar una incidencia por su identificador.
  • Registrar una incidencia nueva con los valores iniciales correspondientes.
  • Actualizar una incidencia existente, conservando su identificador y fecha de registro.
  • Eliminar una incidencia por su identificador, si existe.

Elegid nombres adecuados para esos métodos. No es necesario crear interfaces de servicio adicionales ni añadir dependencias nuevas para esta separación.

🟨 Cuidamos la actualización de los datos​

Al recibir un formulario de edición, no basta con guardar directamente un objeto nuevo con el identificador recibido. Debemos recuperar la incidencia existente y actualizar únicamente los campos que se pueden modificar.

Por ejemplo, si una incidencia se registró el 10 de octubre, editar su descripción no debe sustituir esa fecha por la de hoy. Tampoco debe generar otro registro con un identificador distinto.

Comprobad igualmente qué ocurre si se intenta editar o eliminar un identificador que no existe. El servicio y el controlador deben tratar esa situación sin crear registros accidentales.

aviso

La capa de servicios no consiste en copiar al servicio todo el código del controlador. Revisad qué responsabilidades corresponden a cada clase. El controlador no debe contener las operaciones de acceso a datos y el servicio no debe devolver nombres de vistas Thymeleaf.

4️⃣ Segunda etapa: completamos la gestión desde el navegador​

🟩 Consultar el detalle de una incidencia​

Añadid al listado un enlace que permita abrir la ficha de una incidencia concreta. En ella deben aparecer todos sus datos: identificador, título, descripción, prioridad, estado y fecha de registro.

Proponemos la ruta GET /incidencias/{id}. Utilizad un parámetro de ruta para identificar el registro y recuperadlo desde el servicio. La página debe tener un enlace para volver al listado.

No utilicéis datos ficticios en la ficha: su contenido debe proceder de MySQL.

🟨 Editar una incidencia existente​

Añadid una acción Editar a cada fila del listado o a la ficha de detalle. El formulario deberá aparecer con los valores actuales de la incidencia para que el usuario no tenga que introducirlos de nuevo.

Debe permitir cambiar:

  • El título.
  • La descripción.
  • La prioridad.
  • El estado.

Ni el identificador ni la fecha de registro deben poder modificarse desde ese formulario.

Al guardar correctamente, actualizad el registro existente y redirigid a una página donde podamos comprobar el resultado. No debe aparecer una incidencia adicional.

🟧 Eliminar una incidencia​

Incorporad una acción Eliminar que permita borrar una incidencia de la base de datos.

La eliminación debe enviarse mediante una petición POST, no mediante un enlace GET. Antes de realizarla, el usuario debe disponer de una confirmación clara de que está eliminando ese registro.

Después de eliminarlo, volveremos al listado. La incidencia ya no deberá aparecer y tampoco podrá recuperarse directamente por su identificador.

aviso

No confundáis ocultar una fila de la página con eliminar un registro. Para comprobar la eliminación, consultad también los datos almacenados en MySQL.

🟥 Rutas mínimas del gestor​

Conservad las tres rutas que ya funcionaban y añadid las necesarias para completar la gestión:

PeticiónRutaResultado esperado
GET/incidenciasListado de incidencias.
GET/incidencias/nuevaFormulario de alta.
POST/incidencias/nuevaRegistro de una incidencia nueva.
GET/incidencias/{id}Ficha de detalle.
GET/incidencias/{id}/editarFormulario con los datos actuales.
POST/incidencias/{id}/editarActualización de la incidencia.
POST/incidencias/{id}/eliminarEliminación de la incidencia.

Las rutas propuestas permiten probar todos los proyectos con el mismo recorrido. La edición y la eliminación no deben depender de que el usuario escriba manualmente un identificador en la barra de direcciones.

5️⃣ Tercera etapa: evitamos datos incorrectos​

🟩 Definimos las restricciones de los formularios​

El departamento informático necesita que los registros sean útiles. Una incidencia sin título o con una descripción de una sola palabra no proporciona información suficiente.

Aplicad estas reglas, tanto al registrar como al editar incidencias:

CampoRestricción mínima
TítuloObligatorio, no formado solo por espacios, entre 5 y 100 caracteres.
DescripciónObligatoria, no formada solo por espacios, entre 10 y 500 caracteres.
PrioridadSolo BAJA, MEDIA o ALTA.
EstadoEn una incidencia nueva lo asigna el servidor. En edición solo admite ABIERTA, EN_PROCESO o RESUELTA.

Utilizad Jakarta Validation para las restricciones de los campos y comprobad la validación en el servidor antes de guardar los cambios. Si no añadisteis la dependencia Validation en la actividad 1, incorporadla ahora.

Podéis utilizar anotaciones como @NotBlank, @Size y @Pattern cuando correspondan, junto con @Valid y BindingResult en los métodos del controlador. Para las reglas sobre qué campos pueden actualizarse, aplicad también las comprobaciones necesarias en el servicio.

consejo

En el alta, el estado y la fecha siguen siendo responsabilidad del servidor. No es necesario añadirlos al formulario para que la validación funcione. Tened en cuenta el orden en que se vinculan y validan los datos antes de establecer los valores iniciales.

🟨 Mostramos los errores sin perder lo escrito​

Cuando un formulario contenga errores, la aplicación debe volver a mostrarlo con los valores introducidos y mensajes que expliquen qué debe corregirse.

Por ejemplo, si el título está vacío pero la descripción es válida, no debemos borrar la descripción ni guardar parcialmente la incidencia.

Mostrad los errores junto a sus campos utilizando Thymeleaf. Una vez corregidos, el usuario debe poder enviar el formulario correctamente.

🟧 Tratamos identificadores inexistentes​

Comprobad el comportamiento al solicitar una ficha o un formulario de edición con un identificador que no exista. También debéis contemplar el intento de enviar una edición o eliminación sobre un registro ausente.

En todos esos casos, mostrad una respuesta comprensible o redirigid de forma controlada con un aviso. No se debe mostrar un error técnico sin tratar ni crear una incidencia nueva por accidente.

6️⃣ Cuarta etapa: probamos la aplicación completa​

🟩 Casos de comprobación​

Partid de las incidencias que ya teníais en MySQL. Si vuestra base de datos está vacía, cread primero varias incidencias desde el formulario de alta.

Realizad estas comprobaciones en el navegador y contrastad los cambios importantes con MySQL:

CasoAcciónResultado que debemos observar
1Abrir el detalle de una incidencia.Se muestran los datos correctos del registro seleccionado.
2Editar su título y prioridad.Cambian esos datos en MySQL, sin crear otra fila.
3Cambiar el estado a EN_PROCESO.El listado y el detalle muestran el nuevo estado.
4Consultar la misma incidencia tras editarla.Conserva el mismo id y la misma fechaRegistro.
5Enviar un título vacío o demasiado corto.El formulario muestra un error y no guarda los cambios.
6Enviar una descripción demasiado corta.Se conservan los demás valores y se explica el error.
7Intentar utilizar una prioridad o estado no permitidos.La aplicación rechaza el valor, incluso si se manipula la petición.
8Eliminar una incidencia.Desaparece del listado y de MySQL.
9Abrir, editar o eliminar un identificador inexistente.Se gestiona el caso sin errores técnicos sin tratar ni registros nuevos.
10Registrar otra incidencia desde el formulario original.El alta sigue funcionando, con estado ABIERTA y fecha actual.

No basta con comprobar que aparecen botones de edición y eliminación: debemos verificar que cada operación produce el cambio esperado en la base de datos.

🟨 Qué hacer si algo no funciona​

🟩 La edición crea una incidencia nueva​

Revisad cómo recuperáis el registro existente antes de modificarlo y qué campos estáis copiando desde el formulario. Comprobad que no estáis sustituyendo su identificador.

🟨 La fecha de registro cambia después de editar​

La fecha pertenece al registro original. Debéis conservarla al actualizar los campos editables, en lugar de asignar la fecha actual en cada operación de guardado.

🟧 El formulario muestra errores, pero pierde los datos​

Comprobad qué objeto se devuelve a la vista cuando la validación falla y cómo se utilizan th:object, th:field y los mensajes de error.

🟥 El controlador sigue utilizando el repositorio​

Comprobad que todas las operaciones de acceso a incidencias se realizan desde IncidenciaService. El controlador debe delegar en él y ocuparse del flujo web.

7️⃣ Comprobación final y ampliación​

🟩 Lista de verificación​

  • He continuado mi proyecto de la actividad 1 o he utilizado la base de recuperación sin perder los datos existentes.
  • He incorporado IncidenciaService y utilizo inyección por constructor.
  • El controlador ya no accede directamente a IncidenciaRepository.
  • Puedo abrir la ficha de detalle de una incidencia.
  • Puedo editar título, descripción, prioridad y estado.
  • La edición conserva el identificador y la fecha de registro originales.
  • Puedo eliminar una incidencia mediante POST y comprobarlo en MySQL.
  • Los formularios aplican las restricciones indicadas en el servidor.
  • Los errores de validación se muestran sin perder los datos introducidos.
  • Los identificadores inexistentes se tratan de forma controlada.
  • El listado y el formulario de alta de la actividad 1 siguen funcionando.

🟨 Preguntas de repaso​

  1. ¿Por qué hemos dejado de utilizar el repositorio directamente desde el controlador?
  2. ¿Qué diferencia hay entre validar datos del formulario y comprobar que existe una incidencia en la base de datos?
  3. ¿Por qué debemos recuperar una incidencia existente antes de actualizar sus campos?
  4. ¿Qué consecuencias tendría utilizar una petición GET para eliminar un registro?
  5. ¿Por qué un formulario HTML con required no garantiza que los datos recibidos sean válidos?
  6. ¿Qué comprobación demuestra que una edición no ha creado accidentalmente una incidencia nueva?

🟧 Ampliación opcional​

Incorporad un mensaje de confirmación que se muestre después de crear, modificar o eliminar una incidencia, sin que vuelva a aparecer al actualizar la página. Podéis utilizar una redirección y atributos flash, ya trabajados al estudiar formularios.

La ampliación es opcional. No incorporaremos todavía filtros, búsquedas ni paginación: serán el objetivo de la siguiente etapa del gestor.

Conservamos el proyecto

Guardad el proyecto y sus datos. Seguiremos trabajando sobre esta misma aplicación, incorporando consultas, filtros, ordenación y paginación. No necesitaréis reconstruir el CRUD.

📦 Cómo preparar la entrega​

Comprobad que la aplicación arranca, que las operaciones funcionan desde el navegador y que los cambios se conservan en MySQL. Solo tenéis que entregar el proyecto Spring Boot: no es necesario incluir una exportación de la base de datos ni capturas adicionales.

Desde la terminal de IntelliJ IDEA, situada en la raíz del proyecto, ejecutad:

Limpiar y compilar el proyecto
.\mvnw.cmd clean package

Si la compilación finaliza correctamente, generad el ZIP:

Crear el ZIP de entrega
tar -a -c -f ..\apellido-nombre-UT4-2.zip pom.xml mvnw mvnw.cmd .mvn src

El comando incluye los archivos necesarios para reconstruir la aplicación sin añadir la carpeta target.

aviso

Antes de comprimir el proyecto, comprobad que no habéis incluido contraseñas reales ni otros datos sensibles en application.properties. La conexión debe seguir utilizando la variable de entorno DB_PASSWORD.

Entregad el archivo con este nombre, sustituyendo apellido-nombre por vuestros datos:
