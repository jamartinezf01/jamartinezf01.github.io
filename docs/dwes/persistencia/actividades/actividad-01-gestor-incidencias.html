Actividad 1. De los objetos a MySQL

En las unidades anteriores ya hemos trabajado con controladores, formularios y vistas Thymeleaf. Ahora vamos a dar un paso más: conseguir que la información introducida desde el navegador se almacene realmente en MySQL. En lugar de utilizar una lista de objetos que desaparece al detener la aplicación, recurriremos a una entidad JPA y a un repositorio Spring Data JPA.

Empezaremos un gestor de incidencias informáticas que ampliaremos en otras actividades. Al finalizar esta primera etapa tendremos una aplicación web sencilla: podremos consultar las incidencias registradas y dar de alta otras nuevas. La edición, la eliminación, los filtros y la paginación se incorporarán cuando avancemos en el proyecto.

nota

Esta actividad es de entrega obligatoria y forma parte del seguimiento de la unidad. No tiene una calificación numérica propia y se registrará como Entregada o NO entregada.

1️⃣ El encargo del departamento informático​

🟩 Un registro que debe conservarse​

El departamento informático de un centro educativo necesita registrar las incidencias que comunica el profesorado: equipos que no arrancan, fallos de impresión, problemas de red o aplicaciones que dejan de funcionar. No basta con mostrarlas temporalmente en pantalla; cada incidencia debe mantenerse en una base de datos para poder consultarla más adelante.

Nuestra aplicación debe almacenar estos datos:

Atributo JavaTipo orientativoCondición
idLongClave primaria, generada automáticamente.
tituloStringBreve descripción del problema. Obligatorio.
descripcionStringExplicación del problema. Obligatoria.
prioridadStringBAJA, MEDIA o ALTA.
estadoStringABIERTA, EN_PROCESO o RESUELTA.
fechaRegistroLocalDateFecha de registro, asignada por la aplicación.

En esta primera etapa, todas las incidencias nuevas tendrán el estado ABIERTA. Quien rellene el formulario elegirá la prioridad, pero no introducirá el identificador ni la fecha. Estos valores se establecerán desde el servidor.

aviso

Todavía no crearemos tablas relacionadas ni implementaremos un CRUD completo. El objetivo principal es conectar las dos operaciones web —listar y dar de alta— con la persistencia real en MySQL.

2️⃣ El material de partida​

🟩 Dos páginas HTML y una hoja CSS​

Todos los materiales de partida están reunidos en una única descarga:

👉 Descargar los recursos de la actividad 1 (ZIP)

Al descomprimir el archivo encontraréis dos páginas HTML estáticas, sin expresiones Thymeleaf, y la hoja de estilos gestor-incidencias.css. Los tres archivos están juntos para que las maquetas se vean correctamente al abrirlas desde el navegador.

Antes de programar, abrid los HTML en el navegador y observad su estructura. El listado muestra datos ficticios para ilustrar el resultado esperado, pero aún no consulta ninguna base de datos. El formulario tampoco guarda nada: solo define los campos y el aspecto de la página.

Aprovecharemos estas maquetas para concentrarnos en JPA y en la conexión entre las vistas y el servidor. No tenéis que diseñar una interfaz nueva, aunque sí convertir el HTML proporcionado en plantillas que funcionen con Thymeleaf.

🟨 Recursos para la base de datos​

En el mismo ZIP se incluyen preparacion-bd.sql, para preparar MySQL, y application.properties.ejemplo, como referencia para configurar Spring Boot.

El script crea la base de datos gestor_incidencias y un usuario local para esta aplicación, pero no crea la tabla de incidencias. Esa tabla deberá generarse a partir de vuestra entidad JPA.

aviso

Antes de ejecutar el script, sustituid CAMBIA_ESTA_CONTRASENA por una contraseña propia. Para ejecutar las instrucciones de creación de usuario necesitaréis una cuenta de MySQL con permisos suficientes. No guardéis contraseñas reales en el repositorio. La configuración de Spring Boot utiliza la variable de entorno DB_PASSWORD.

3️⃣ Primera etapa: proyecto y persistencia​

🟩 Preparar Spring Boot y MySQL​

Cread desde la web de Spring Initializr el proyecto gestor_incidencias, con Maven, Java 21 y empaquetado Jar, utilizando el paquete base com.dwes.gestor_incidencias.

Necesitaremos las dependencias Spring Web, Thymeleaf, Spring Data JPA y MySQL Driver. Podemos incorporar también Validation, que será útil al mejorar los formularios, aunque la validación completa no forma parte de esta primera actividad.

Después:

  1. Preparad la base de datos utilizando el script proporcionado.
  2. Copiad el contenido de application.properties.ejemplo a src/main/resources/application.properties.
  3. Configurad DB_PASSWORD en la ejecución de IntelliJ IDEA.
  4. Comprobad que la aplicación arranca sin errores de conexión.

Utilizaremos spring.jpa.hibernate.ddl-auto=update como apoyo durante el desarrollo. Recordad que no es una herramienta de migraciones y que no debemos utilizarla como sustituto de un procedimiento de evolución controlada de una base de datos.

🟨 Diseñar la entidad y el repositorio​

Implementad una entidad Incidencia con los atributos establecidos en el encargo. Decidid qué anotaciones JPA necesita la clase, cómo se generará el identificador y qué restricciones de columna son apropiadas.

Queremos que MySQL contenga una tabla denominada incidencias, con las columnas id, titulo, descripcion, prioridad, estado y fecha_registro. Cread también el repositorio Spring Data JPA correspondiente.

Arrancad la aplicación y comprobad mediante MySQL que la tabla se ha generado en la base de datos correcta. Revisad su clave primaria y los tipos de columna.

consejo

Si la tabla no aparece, comprobad primero la conexión, el paquete en el que habéis creado la entidad y las anotaciones JPA. Que el proyecto compile no significa necesariamente que la tabla se haya creado.

4️⃣ Segunda etapa: del HTML estático a una aplicación web​

🟩 Mostrar las incidencias guardadas​

Copiad las dos maquetas a src/main/resources/templates/ y la hoja CSS a src/main/resources/static/css/.

En las plantillas habrá que adaptar el enlace al CSS para que Spring Boot sirva el recurso correctamente. Por ejemplo, podéis utilizar th:href="@{/css/gestor-incidencias.css}".

Implementad una ruta GET /incidencias que consulte el repositorio y muestre la plantilla del listado. Sustituid las filas de ejemplo por un recorrido Thymeleaf sobre los registros recuperados de MySQL.

Si todavía no existe ninguna incidencia, la página debe mostrar un mensaje claro, sin conservar las filas ficticias de la maqueta.

Qué debemos comprobar

El navegador tiene que mostrar lo que hay en la tabla incidencias. Un dato escrito directamente en HTML no demuestra que la consulta JPA funcione.

🟨 Registrar una nueva incidencia​

Convertid la maqueta del formulario en una vista Thymeleaf accesible desde GET /incidencias/nueva. Debe permitir introducir:

  • El título de la incidencia.
  • La descripción del problema.
  • La prioridad: BAJA, MEDIA o ALTA.

Implementad también POST /incidencias/nueva, que recibirá los datos enviados, creará la nueva incidencia y la guardará mediante el repositorio. El servidor asignará automáticamente el estado ABIERTA y la fecha actual. El identificador lo generará JPA.

Cuando se complete el alta, redirigid al listado para comprobar que el nuevo registro aparece. Utilizad los conocimientos de Spring MVC y Thymeleaf que ya tenemos: @Controller, @GetMapping, @PostMapping, Model y vinculación de formularios. En esta actividad podemos utilizar temporalmente el repositorio desde el controlador; la capa de servicios se incorporará cuando ampliemos la aplicación.

Los atributos Thymeleaf y las rutas definitivas no están escritos en el HTML inicial: forman parte del trabajo. Los enlaces locales y la acción provisional del formulario de la maqueta deben sustituirse por los adecuados para Spring Boot.

aviso

El atributo HTML required ayuda a utilizar el formulario, pero no sustituye a la validación en el servidor. En esta etapa comprobamos las altas con datos válidos y la persistencia; el tratamiento completo de errores y validaciones se desarrollará al ampliar el gestor. No aceptéis valores arbitrarios de estado o prioridad simplemente porque lleguen en una petición.

🟧 Las rutas mínimas del gestor​

PeticiónRutaResultado esperado
GET/incidenciasMuestra las incidencias recuperadas de MySQL.
GET/incidencias/nuevaAbre el formulario de alta.
POST/incidencias/nuevaGuarda una incidencia y redirige al listado.

No incorporéis todavía botones de edición, eliminación, filtrado o paginación que aparenten funcionar sin estar implementados.

5️⃣ Tercera etapa: comprobar que los datos son reales​

🟩 Pruebas funcionales​

Registrad desde el navegador al menos cinco incidencias diferentes. Podéis utilizar estos casos, completando sus descripciones:

TítuloPrioridad
El ordenador del aula 2 no arrancaALTA
La impresora de secretaría no imprimeMEDIA
No funciona el proyector del aula 5ALTA
Actualizar navegador en bibliotecaBAJA
Fallos intermitentes de conexiónMEDIA

Después, realizad las siguientes comprobaciones:

  1. Consultad el listado y verificad que aparecen los cinco registros sin introducirlos manualmente en el HTML.
  2. Comprobad que todas las altas tienen estado ABIERTA, una fecha de registro y un identificador generado automáticamente.
  3. Consultad desde MySQL la tabla incidencias y comparad sus registros con los que muestra la página.
  4. Detened la aplicación Spring Boot y volved a arrancarla. Verificad que los registros siguen disponibles.
  5. Añadid otra incidencia desde el formulario y comprobad que aparece en MySQL sin reiniciar la aplicación.

Para contrastar los resultados podéis utilizar estas consultas:

Consultas para comprobar la persistencia
USE gestor_incidencias;

SELECT id, titulo, prioridad, estado, fecha_registro
FROM incidencias;

SELECT COUNT(*) AS total_incidencias
FROM incidencias;

🟨 Qué hacer si algo no funciona​

🟩 El navegador muestra siempre los mismos ejemplos​

Probablemente siguen presentes las filas estáticas de la maqueta. El listado debe generarse a partir de los datos enviados desde el controlador a Thymeleaf.

🟨 El formulario se ve, pero no guarda nada​

Comprobad el método HTTP y la URL del formulario, la ruta @PostMapping y la llamada al método de guardado del repositorio. El formulario HTML entregado es solamente una maqueta.

🟧 La aplicación arranca, pero no aparecen registros en MySQL​

Comprobad que estáis consultando la base de datos gestor_incidencias, que el controlador utiliza el repositorio y que el alta llega realmente a la operación de guardado.

🟥 El registro desaparece al reiniciar​

Revisad si estáis utilizando una colección Java temporal en lugar del repositorio JPA, y comprobad la configuración de la conexión y de Hibernate.

6️⃣ Comprobación final y ampliación​

🟩 Lista de verificación​

  • He configurado el proyecto Spring Boot y su conexión con gestor_incidencias.
  • He creado la entidad Incidencia y el repositorio JPA.
  • He comprobado la estructura real de la tabla en MySQL.
  • He adaptado las maquetas HTML a Thymeleaf y enlazado la hoja CSS.
  • El listado muestra registros recuperados de MySQL, no datos escritos en el HTML.
  • Puedo dar de alta incidencias desde el navegador.
  • El servidor asigna el estado ABIERTA y la fecha de registro.
  • Puedo consultar directamente en MySQL las incidencias creadas.
  • Los datos siguen existiendo después de reiniciar la aplicación.

🟨 Preguntas de repaso​

  1. ¿Qué diferencia hay entre representar una incidencia en una clase Java y guardarla mediante una entidad JPA?
  2. ¿Qué responsabilidad tiene JpaRepository en esta aplicación?
  3. ¿Por qué las filas de ejemplo del HTML no sirven para demostrar que existe persistencia?
  4. ¿Qué hace Thymeleaf que no pueda hacer por sí solo el HTML estático entregado?
  5. ¿Por qué debemos asignar el identificador y la fecha de registro desde el servidor?
  6. ¿Cómo comprobarías que la aplicación utiliza la base de datos prevista y no otra?

🟧 Ampliación opcional​

Si termináis las comprobaciones anteriores, añadid en el listado un pequeño resumen que indique el número total de incidencias registradas, calculado a partir de la información recuperada del repositorio. No debe ser un número escrito manualmente en HTML.

Esta ampliación es opcional y no introduce todavía consultas complejas, filtros ni paginación.

Conservamos el proyecto

Guardad el proyecto gestor_incidencias y su base de datos. Seguiremos ampliándolo con una capa de servicios, edición, eliminación y validación más completa. No tenéis que volver a empezar la aplicación.
