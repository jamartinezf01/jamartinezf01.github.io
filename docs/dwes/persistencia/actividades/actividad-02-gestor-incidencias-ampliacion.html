Actividad 2. Ampliación: una imagen también explica el problema

Nuestro gestor de incidencias informáticas ya permite registrar problemas, consultar sus detalles, modificar sus datos y eliminar registros. Además, hemos separado las responsabilidades del controlador y la capa de servicios y utilizamos MySQL para conservar la información.

Ahora el personal del departamento informático plantea una necesidad muy habitual: algunas incidencias se entienden mucho mejor cuando incluyen una fotografía. No es lo mismo leer «la pantalla muestra un error» que poder ver el mensaje que aparece en el equipo. Una imagen también puede ayudar a documentar un cable dañado, una impresora averiada o el estado de un dispositivo.

En esta actividad seguiremos ampliando el mismo proyecto gestor_incidencias, pero aprenderemos a conservar un tipo de información diferente. Las imágenes se guardarán como archivos en una carpeta externa al proyecto; MySQL almacenará únicamente el nombre que permite localizarlas. No utilizaremos columnas BLOB ni guardaremos los bytes de las fotografías en la base de datos.

nota

Esta actividad es de entrega obligatoria y forma parte del seguimiento de la unidad. No tiene una calificación numérica propia y se registrará como Entregada o NO entregada.

1️⃣ Punto de partida​

🟩 Continuamos desde la Actividad 2​

Utilizad el proyecto que terminasteis en la Actividad 2. Debe contar con Incidencia, IncidenciaRepository, IncidenciaService, los controladores MVC y las plantillas que permiten listar, registrar, consultar, editar y eliminar incidencias con validación.

Si no habéis conseguido terminar esa actividad, podéis comenzar desde el proyecto de recuperación correspondiente al final de la Actividad 2, que contiene el gestor completo, pero todavía no incorpora ninguna funcionalidad de imágenes.

👉 Descargar el proyecto de recuperación de la Actividad 2 (ZIP)

El ZIP contiene la carpeta gestor_incidencias/, con el proyecto Spring Boot, las instrucciones de recuperación y un archivo datos-prueba-actividad-03.sql que reservaremos para la Actividad 3. En esta ampliación solo necesitáis el proyecto. Mantiene Java 21, Spring Boot 4.1.2, Thymeleaf, Spring Data JPA, MySQL y Validation. No necesitáis crear otro proyecto desde Spring Initializr.

consejo

Este paquete se preparó originalmente para la Actividad 3, por eso sus instrucciones mencionan las búsquedas y la paginación. No debéis implementarlas ni ejecutar el script de datos todavía: en esta ampliación trabajaremos únicamente con las fotografías.

Antes de empezar, comprobad que podéis:

  1. Abrir GET /incidencias y ver los registros existentes.
  2. Registrar una incidencia nueva y consultar su detalle desde GET /incidencias/{id}.
  3. Editar y eliminar incidencias sin perder los datos de otras filas.
  4. Reiniciar la aplicación y recuperar los registros desde MySQL.
  5. Verificar que el controlador utiliza IncidenciaService y no accede directamente al repositorio.
aviso

Si vuestro gestor ya funciona, no lo sustituyáis por el de recuperación. Conservad las incidencias registradas y continuad con vuestro propio código. El ZIP es una alternativa para quien necesite recuperar el punto de partida.

Mantened la contraseña de MySQL fuera del proyecto mediante la variable DB_PASSWORD.

🟨 Preparamos una carpeta para las imágenes​

Elegid una carpeta externa a gestor_incidencias para almacenar las fotografías. En Windows podéis utilizar, por ejemplo:

Ejemplo de directorio de almacenamiento
C:/datos/gestor-incidencias/imagenes/

La ubicación debe poder configurarse sin modificar el código Java. Una posibilidad es añadir a application.properties una propiedad propia:

src/main/resources/application.properties (añadir)
app.imagenes.directorio=${IMAGENES_DIR}

Configurad IMAGENES_DIR en Run → Edit Configurations de IntelliJ IDEA, igual que ya hicisteis con DB_PASSWORD. Su valor será la ruta real elegida en vuestro equipo. El programa debe poder utilizar ese directorio y, si decidís que se cree automáticamente, hacerlo de forma controlada.

No utilicéis src/main/resources/static, templates ni target como destino de los archivos subidos. Esas carpetas pertenecen al proyecto o a su proceso de construcción y no son el almacenamiento persistente que necesitamos.

2️⃣ El reto: incorporar fotografías a las incidencias​

🟩 Qué debe poder hacer el usuario​

El departamento informático quiere asociar como máximo una imagen a cada incidencia. La fotografía es opcional: el gestor debe seguir admitiendo incidencias que solo tengan título, descripción, prioridad, estado y fecha.

FuncionalidadComportamiento esperado
Adjuntar fotografíaDesde la ficha de detalle de una incidencia existente se puede seleccionar y subir un archivo.
Formatos admitidosSolo imágenes JPEG (.jpg o .jpeg) y PNG (.png).
Tamaño máximoLa aplicación rechaza las imágenes que superen 1 MB.
AlmacenamientoEl archivo se guarda en la carpeta externa configurada, con un nombre generado por la aplicación.
Referencia en MySQLLa incidencia conserva el nombre del archivo, no sus bytes ni una ruta absoluta.
VisualizaciónLa ficha de detalle muestra la fotografía asociada cuando existe.
SustituciónSe puede subir otra fotografía para una incidencia que ya tiene una.
Retirada de imagenSe puede quitar la fotografía sin eliminar la incidencia.
Eliminación de incidenciaAl borrar una incidencia, se gestiona también el archivo que tenía asociado.
ErroresLos archivos inválidos y las incidencias inexistentes se tratan de manera comprensible.

🟨 Cómo se integrará con el gestor actual​

Para no rehacer los formularios CRUD, la subida se realizará desde detalle-incidencia.html, una vez creada la incidencia. No es necesario añadir un selector de archivos a los formularios de alta ni de edición general.

El funcionamiento esperado será el siguiente:

  1. Una persona abre la ficha de una incidencia.
  2. Si todavía no tiene fotografía, aparece un formulario para adjuntarla.
  3. Si ya tiene fotografía, se muestra la imagen y se ofrece la posibilidad de Sustituir o Quitar imagen.
  4. Después de una operación correcta, la aplicación vuelve a la ficha y muestra el resultado actualizado.
  5. Si la fotografía no es válida, se informa del motivo sin alterar la imagen anterior ni el resto de los datos.
Idea principal

En esta actividad hay dos elementos que deben mantenerse relacionados: el archivo físico y el registro de MySQL. Guardar un nombre en la base de datos no crea el archivo; copiar un archivo a una carpeta tampoco actualiza automáticamente la entidad JPA.

🟧 Rutas para comprobar el funcionamiento​

Utilizaremos estas rutas para que sea posible probar las aplicaciones de una forma común:

PeticiónRutaFinalidad
GET/incidencias/{id}Mostrar la ficha, con la fotografía si existe.
POST/incidencias/{id}/imagenRecibir una fotografía y asociarla a la incidencia, sustituyendo la anterior si procede.
GET/incidencias/{id}/imagenDevolver al navegador el contenido de la imagen almacenada.
POST/incidencias/{id}/imagen/eliminarQuitar la imagen asociada sin borrar la incidencia.
POST/incidencias/{id}/eliminarConservar la eliminación ya existente y gestionar su posible fotografía.

El uso de POST para subir, sustituir o quitar imágenes es intencionado: estas operaciones modifican información. La ruta GET de la imagen se utilizará exclusivamente para recuperar su contenido.

3️⃣ Primera etapa: ampliamos la persistencia​

🟩 La entidad conserva una referencia, no una imagen​

Ampliad Incidencia con una propiedad opcional llamada imagenNombre, que se persistirá en la columna imagen_nombre de la tabla incidencias.

Este atributo será una cadena de texto. No debéis añadir byte[], @Lob ni otra entidad relacionada: seguimos trabajando con una sola tabla y el almacenamiento de archivos se resolverá desde Java.

Comprobad que las incidencias anteriores siguen siendo válidas y que su nueva columna puede contener NULL. Una incidencia no debe dejar de poder registrarse porque no se adjunte una fotografía.

La configuración de prácticas utiliza spring.jpa.hibernate.ddl-auto=update; verificad desde MySQL que la columna se ha incorporado realmente. No eliminéis ni recreéis la tabla para empezar de cero.

Comprobación de la referencia persistente
USE gestor_incidencias;

SELECT id, titulo, imagen_nombre
FROM incidencias;

🟨 Elegimos dónde colocar la lógica​

Organizad la solución para que cada elemento tenga una responsabilidad clara:

ElementoResponsabilidad
Entidad IncidenciaConservar el nombre del archivo asociado.
Repositorio JPAPersistir y recuperar los datos de la incidencia.
ServicioValidar la fotografía y coordinar el guardado, la sustitución y la retirada de archivos y referencias.
Controlador MVCRecibir la petición, llamar al servicio y preparar la respuesta o la redirección.
ThymeleafMostrar la fotografía, el formulario de subida y las acciones disponibles.

Podéis ampliar IncidenciaService o crear un servicio específico para gestionar imágenes. No es necesario utilizar exactamente los mismos nombres de métodos, pero el controlador no debe encargarse de copiar y borrar directamente archivos del disco ni acceder a IncidenciaRepository para estas operaciones.

consejo

El nuevo campo imagenNombre no forma parte del formulario de alta o edición de texto. Revisad los métodos que ya recuperan una incidencia existente antes de actualizarla: cambiar su título o prioridad no debe hacer que pierda la imagen asociada.

4️⃣ Segunda etapa: subimos y conservamos las imágenes​

🟩 Recibir un archivo desde Thymeleaf​

Incorporad en detalle-incidencia.html un formulario de subida. Para enviar un archivo debe utilizar method="post", enctype="multipart/form-data" y un campo <input type="file">.

El controlador recibirá el archivo mediante MultipartFile. Podéis utilizar el nombre de parámetro imagen para que coincida con la ruta de subida que habéis definido. Después, delegará el trabajo de almacenamiento en el servicio.

No es necesario mezclar esta subida con @Valid @ModelAttribute("incidencia"): los datos de la incidencia ya están guardados y la fotografía se añade mediante una operación independiente.

🟨 Validar el archivo antes de guardarlo​

La aplicación debe comprobar desde el servidor que:

  • Se ha seleccionado un archivo y no está vacío.
  • Su tamaño no supera 1 MB (1 048 576 bytes).
  • El contenido corresponde realmente a una imagen JPEG o PNG; no basta con confiar en la extensión ni en getContentType().
  • La incidencia a la que se quiere asociar existe.

Podéis emplear las herramientas de lectura de imágenes de Java, como ImageIO, para comprobar que el contenido puede interpretarse como una imagen admitida. El nombre y el tipo que envía el navegador sirven como pistas, no como garantía.

Configurad también límites razonables para las peticiones multipart de Spring Boot. Tened en cuenta que un archivo rechazado por el límite global puede producir una excepción antes de llegar al servicio; gestionad ese caso para que el usuario reciba una respuesta comprensible.

aviso

Cambiar el nombre de documento.txt por documento.jpg no convierte el archivo en una imagen. La comprobación no debe depender únicamente de la extensión. Tampoco debe permitirse que el nombre original enviado por el navegador determine una ruta de escritura.

🟧 Guardar físicamente el archivo​

Para cada imagen válida, la aplicación debe generar un nombre único, por ejemplo mediante UUID, y conservar una extensión coherente con el formato validado.

La carpeta de destino debe ser la que se haya configurado mediante IMAGENES_DIR. Utilizad las clases Path y Files de Java para trabajar con rutas y archivos.

Una vez guardada la imagen, actualizad la propiedad imagenNombre de la incidencia existente utilizando la capa de servicios y el repositorio JPA. No se debe crear otra incidencia ni modificar su fecha, título, prioridad o estado.

En MySQL queremos encontrar un valor semejante a 5b8e...c7.png en imagen_nombre, no C:/datos/.../imagen.png, ni el contenido binario de la fotografía.

🟥 Mostrar un resultado útil al usuario​

Cuando la subida finalice correctamente, redirigid a la ficha de detalle y mostrad la fotografía. Si la validación falla, informad del problema y conservad los datos que ya existían.

Si una incidencia no tiene imagen, la ficha debe seguir viéndose correctamente: podéis indicar «Sin fotografía adjunta» en lugar de intentar mostrar una imagen inexistente.

5️⃣ Tercera etapa: recuperamos y gestionamos las fotografías​

🟩 Servir la imagen desde una ruta de Spring Boot​

Los archivos se encuentran fuera de static, por lo que no tendrán una URL pública automáticamente. Necesitáis implementar la ruta GET /incidencias/{id}/imagen.

Al recibir la petición, la aplicación deberá buscar la incidencia, obtener su referencia, localizar el archivo en la carpeta configurada y devolver su contenido con el tipo MIME correcto (image/jpeg o image/png). Podéis utilizar ResponseEntity y un recurso de Spring para construir esta respuesta.

No confundáis este funcionamiento con devolver una plantilla Thymeleaf: el navegador espera los bytes de una imagen, no una página HTML. La ficha de detalle sí seguirá devolviendo una vista Thymeleaf, que utilizará esa ruta como origen de la imagen.

Si el identificador no existe, la incidencia no tiene fotografía o el archivo ya no está disponible, la petición de imagen debe tratarse de forma controlada, por ejemplo con un 404, sin mostrar una excepción técnica sin gestionar.

🟨 Sustituir una fotografía​

Cuando una incidencia tenga una imagen, el usuario podrá seleccionar otra. En ese caso:

  1. Validaremos la nueva fotografía igual que en la primera subida.
  2. Guardaremos el nuevo archivo con un nombre diferente.
  3. Actualizaremos la referencia de esa misma incidencia en MySQL.
  4. Gestionaremos la retirada de la fotografía antigua para no acumular archivos innecesarios.

Si la nueva imagen es inválida, la fotografía anterior debe permanecer disponible. Pensad especialmente en el orden de las operaciones: eliminar primero el archivo antiguo sería una mala decisión si después falla la nueva subida.

🟧 Quitar la fotografía o eliminar la incidencia​

Añadid una acción Quitar imagen, enviada mediante POST, que elimine la asociación y gestione el archivo correspondiente. La incidencia debe seguir existiendo y conservar todos sus demás datos.

Adaptad también la operación de Eliminar incidencia que ya tenéis en IncidenciaService. Si el registro tiene una fotografía, el archivo no debe quedar olvidado en la carpeta después de una eliminación correcta.

Esta funcionalidad debe seguir funcionando cuando la incidencia no tenga fotografía o cuando se intente eliminar un identificador inexistente.

aviso

Una operación JPA sobre MySQL no deshace automáticamente los cambios que hayamos realizado con Files en el sistema de archivos. Si una escritura falla, hay que tratar el problema y evitar, en la medida de lo posible, que queden referencias a archivos inexistentes o archivos sin utilizar.

Por ahora buscamos una gestión coherente de los casos normales y de los errores más habituales. Las transacciones y sus límites se estudiarán con mayor profundidad al avanzar en la unidad.

6️⃣ Cuarta etapa: comprobamos que la persistencia es real​

🟩 Pruebas funcionales​

Trabajad con las incidencias que ya tenéis registradas. Si partís del proyecto de recuperación y la base de datos está vacía, cread primero dos o tres incidencias desde el formulario habitual. No importéis los 48 registros del script de la Actividad 3: los utilizaremos para practicar la paginación más adelante. Preparad imágenes pequeñas en JPEG y PNG, una superior a 1 MB y un archivo que no sea una imagen.

CasoAcciónResultado esperado
1Abrir una incidencia sin fotografía.La ficha se muestra normalmente y permite adjuntar una imagen.
2Subir un JPEG válido.Se guarda en la carpeta externa y aparece en la ficha.
3Consultar imagen_nombre en MySQL.Contiene el nombre generado del archivo, no su contenido ni la ruta absoluta.
4Detener y reiniciar Spring Boot.La fotografía sigue disponible.
5Subir un PNG válido a otra incidencia.Se conserva con su extensión correcta y se muestra en el navegador.
6Subir un archivo vacío, un fichero no válido renombrado a .jpg o una imagen superior a 1 MB.Se rechaza con un mensaje comprensible; no se guarda ni sustituye la imagen anterior.
7Sustituir una fotografía por otra válida.Se muestra la nueva, cambia la referencia y se gestiona el archivo antiguo.
8Quitar la fotografía desde su ficha.La incidencia permanece y deja de tener imagen asociada.
9Eliminar una incidencia que tenga fotografía.Desaparece el registro y se gestiona también el archivo.
10Pedir la imagen de un ID inexistente o sin archivo.La respuesta es controlada; no se produce un error 500 sin tratar.
11Editar el título o el estado de una incidencia que tenga imagen.Los cambios de texto se guardan y la fotografía sigue asociada.
12Crear, editar y eliminar una incidencia sin imagen.El CRUD anterior continúa funcionando.

La comprobación de persistencia requiere observar tres lugares diferentes: la ficha en el navegador, la columna imagen_nombre de MySQL y el archivo que existe físicamente en la carpeta configurada. Si solo verificáis uno, no habréis comprobado todo el recorrido.

consejo

Para preparar un archivo no válido, podéis crear un pequeño .txt y renombrarlo a .jpg. Para comprobar el tamaño, utilizad una imagen real de más de 1 MB. No necesitáis publicar ni entregar esas imágenes de prueba.

🟨 Errores frecuentes​

🟩 La imagen aparece antes de reiniciar, pero después desaparece​

Comprobad que el archivo se ha guardado en la carpeta externa configurada y no en un directorio temporal. Revisad también que IMAGENES_DIR tenga el mismo valor al volver a ejecutar la aplicación.

🟨 MySQL tiene un nombre de archivo, pero la ficha no muestra nada​

Revisad la ruta GET que devuelve el contenido, la ubicación física del archivo y el tipo MIME de la respuesta. Guardar la referencia en JPA no publica automáticamente el archivo.

🟧 Al editar una incidencia desaparece su fotografía​

Revisad el método de actualización de la actividad 2. Debe modificar los campos de texto autorizados sobre la entidad existente, sin borrar ni sustituir su referencia de imagen.

🟥 Al sustituir una imagen se acumulan archivos antiguos​

Revisad el orden de guardado, actualización de referencia y retirada de la fotografía anterior. El objetivo es no dejar archivos que ya no estén vinculados a ninguna incidencia.

7️⃣ Comprobación final y ampliación​

🟩 Lista de verificación​

  • He continuado el gestor de la actividad 2 o he partido del proyecto de recuperación.
  • El CRUD, las validaciones y la capa de servicios siguen funcionando.
  • He añadido imagenNombre como campo opcional y he comprobado su columna en MySQL.
  • La carpeta de imágenes es externa al proyecto y su ubicación es configurable.
  • Puedo adjuntar una imagen desde la ficha de una incidencia.
  • Valido el contenido y rechazo imágenes no admitidas o superiores a 1 MB.
  • Genero nombres únicos y no utilizo rutas proporcionadas por el navegador.
  • El archivo se guarda en disco y solo su nombre se almacena en MySQL.
  • La aplicación permite recuperar y mostrar la fotografía desde una ruta GET.
  • Puedo sustituir una imagen conservando la anterior si el nuevo archivo no es válido.
  • Puedo quitar una imagen sin borrar la incidencia.
  • La eliminación de una incidencia contempla también su fotografía.
  • Las incidencias sin imagen y los archivos ausentes se tratan de manera controlada.
  • He comprobado que la imagen permanece disponible después de reiniciar la aplicación.

🟨 Preguntas de repaso​

  1. ¿Por qué no guardamos el archivo subido dentro de src/main/resources/static?
  2. ¿Qué información conserva MySQL y cuál se guarda físicamente en el disco?
  3. ¿Para qué necesitamos multipart/form-data y MultipartFile?
  4. ¿Por qué no es seguro utilizar directamente el nombre original del archivo recibido?
  5. ¿Por qué el atributo accept de HTML no garantiza que una imagen sea válida?
  6. ¿Por qué necesitamos una ruta adicional para mostrar la fotografía en el navegador?
  7. ¿Qué puede ocurrir si eliminamos primero el archivo antiguo y después falla la sustitución?
  8. ¿Qué debe cambiar si trasladamos la aplicación a otro ordenador, aunque siga conectada a la misma base de datos MySQL?

🟧 Ampliación opcional​

Añadid al listado de incidencias un pequeño indicador visual que permita saber cuáles tienen fotografía. No debéis cargar ni mostrar todas las imágenes en la tabla; basta con indicar si la referencia existe.

La ampliación no es necesaria para completar la actividad. El listado seguirá sin búsquedas ni paginación: esas funcionalidades se incorporarán en la Actividad 3.

Conservamos el proyecto

Guardad el gestor con las nuevas funciones de imágenes. En la siguiente actividad ampliaremos las consultas, los filtros, la ordenación y la paginación. El proyecto de recuperación de la Actividad 3 incorporará estas funcionalidades, pero todavía no tendrá implementados los filtros ni la paginación.

📦 Cómo preparar la entrega​

Comprobad que la aplicación compila, que las imágenes se conservan al reiniciar y que las funciones CRUD siguen operativas. Entregad únicamente el proyecto Spring Boot, sin exportaciones de MySQL, capturas ni fotografías subidas durante las pruebas.

Desde la terminal de IntelliJ IDEA, situada en la raíz del proyecto, ejecutad:

Limpiar y compilar el proyecto
.\mvnw.cmd clean package

Cuando termine correctamente, cread el ZIP:

Crear el ZIP de entrega
tar -a -c -f ..\apellido-nombre-UT4-2-ampliacion.zip pom.xml mvnw mvnw.cmd .mvn src

El archivo contiene el código fuente y los recursos de la aplicación, pero no la carpeta de imágenes externa. No incorporéis contraseñas reales: DB_PASSWORD e IMAGENES_DIR deben configurarse como variables de entorno en el equipo donde se ejecute el proyecto.
