Actividad 3. Ampliación: un panel de seguimiento de incidencias

El gestor de incidencias informáticas ya permite registrar problemas, consultar sus detalles, editarlos, eliminarlos y buscar entre todos los registros. En la actividad anterior incorporamos tres filtros, distintas formas de ordenar y una paginación de ocho incidencias por página.

Pero el departamento informático nos plantea una necesidad nueva: cuando comienza la jornada, no quiere revisar el listado completo ni leer todas las descripciones. Necesita una pantalla de seguimiento en la que aparezcan únicamente las incidencias que todavía están pendientes, con la información imprescindible para decidir cuáles atender primero.

Para resolverlo aprovecharemos lo que hemos aprendido sobre DTO y proyecciones con Spring Data JPA. No vamos a desarrollar un nuevo CRUD ni a modificar la base de datos: construiremos una nueva forma de consultar y presentar la información que ya existe.

Objetivo de la actividad

Crear una página /incidencias/seguimiento que recupere solo los datos necesarios mediante una proyección de interfaz, los transforme en DTO con la antigüedad calculada y los muestre desde Thymeleaf, conservando la paginación con Page.map().

Esta es una actividad práctica no evaluable, destinada a aplicar los contenidos del apartado 2.7. No requiere entrega ni tiene calificación.

1️⃣ Punto de partida​

🟩 Continuamos con el gestor de incidencias​

La ampliación parte del proyecto finalizado de la Actividad 3. Debe conservar las siguientes funcionalidades:

  • Una entidad Incidencia, con las propiedades id, titulo, descripcion, prioridad, estado y fechaRegistro.
  • Un repositorio IncidenciaRepository, un servicio IncidenciaService y un controlador IncidenciaController.
  • El listado /incidencias, con búsqueda por título, prioridad y estado, cuatro opciones de ordenación y paginación de ocho registros.
  • Las operaciones de alta, detalle, edición y eliminación, junto con las validaciones correspondientes.

Si la Actividad 3 no está terminada o el proyecto no funciona correctamente, utilizad la siguiente versión de recuperación, que contiene el trabajo resuelto hasta ese punto:

Descargar proyecto de recuperación de la Actividad 3 (ZIP)

El ZIP incluye la carpeta gestor_incidencias/, un archivo de instrucciones y el script datos-prueba-actividad-03.sql con 48 registros para comprobar los resultados. No incluye la solución de esta ampliación.

aviso

Si vuestro proyecto ya funciona, continuad con él. La recuperación es una alternativa para quienes no hayan completado la actividad anterior, no un motivo para sustituir datos o código propios.

Para ejecutar el proyecto de recuperación necesitaréis Java 21, MySQL y la variable de entorno DB_PASSWORD. El archivo README-RECUPERACION.md explica cómo prepararlo. No escribáis contraseñas reales en application.properties.

🟨 Comprobamos el estado inicial​

Antes de comenzar, abrid /incidencias y comprobad que podéis buscar, ordenar, pasar de una página a otra y consultar el detalle de una incidencia. Si necesitáis datos de prueba, cargad el SQL incluido en el ZIP después de que la tabla exista.

No modificaremos las columnas de MySQL ni las rutas de gestión que ya funcionan. La nueva pantalla tendrá su propia ruta y plantilla.

2️⃣ El nuevo encargo: consultar lo que queda pendiente​

🟩 Qué debe mostrar el panel​

Una incidencia está pendiente si su estado es ABIERTA o EN_PROCESO. Las incidencias RESUELTA no deben aparecer en este panel, aunque seguirán estando disponibles en el listado general.

Para cada incidencia pendiente mostraremos:

Dato visibleProcedencia
Identificador.id, recuperado mediante la proyección.
Título.titulo, recuperado mediante la proyección.
Prioridad.prioridad, recuperada mediante la proyección.
Antigüedad en días.Calculada por el servicio a partir de fechaRegistro.
Enlace «Ver detalle».Ruta de detalle que ya existe en la aplicación.

Por ejemplo, una fila podría mostrar un título, la prioridad ALTA y una antigüedad de 12 días. Esa antigüedad es un dato calculado, no una columna adicional en MySQL: cambia según la fecha en que consultamos el panel.

El listado deberá mostrar como máximo ocho incidencias por página, empezando por las más antiguas. Si varias tienen la misma fecha de registro, utilizaremos id como segundo criterio de ordenación para mantener resultados estables.

🟨 Recorrido de los datos​

El recorrido que buscamos es el siguiente:

De MySQL hasta Thymeleaf
MySQL
  ↓
IncidenciaRepository
  ↓  Page<IncidenciaPendienteView>
IncidenciaService
  ↓  Page.map(...), con cálculo de días
  ↓  Page<IncidenciaSeguimientoDTO>
IncidenciaController
  ↓  Model
seguimiento-incidencias.html

En este recorrido el repositorio no devuelve entidades Incidencia completas para construir el panel. Obtiene una representación parcial; el servicio la transforma en los datos específicos que necesita la vista.

Diferencia importante

La proyección describe los datos que queremos obtener de la consulta. El DTO describe los datos que vamos a entregar a la vista. Por eso utilizamos ambos: recuperamos fechaRegistro para hacer el cálculo, pero en el resultado mostramos diasDesdeRegistro.

3️⃣ Primera etapa: una proyección para consultar menos datos​

🟩 Diseñamos la interfaz de proyección​

Dentro del proyecto, cread un paquete projection y una interfaz llamada IncidenciaPendienteView.

La interfaz debe permitir consultar exactamente estos cuatro datos:

  • id (Long).
  • titulo (String).
  • prioridad (String).
  • fechaRegistro (LocalDate).

Recordad que una proyección de interfaz utiliza métodos de acceso, no campos que tengamos que rellenar manualmente. No añadáis @Entity ni creéis una tabla para esta interfaz.

🟨 Incorporamos la consulta al repositorio​

En IncidenciaRepository, declarad un método que devuelva una Page<IncidenciaPendienteView> y reciba un Pageable.

El método debe recuperar exclusivamente las incidencias cuyo estado esté dentro del conjunto formado por ABIERTA y EN_PROCESO. Podéis utilizar un método derivado de Spring Data JPA con una condición In para indicar los estados permitidos. No hace falta crear una consulta SQL nativa ni cambiar las consultas de la Actividad 3.

Comprobad que el método devuelve el tipo de la proyección, no Page<Incidencia>. Para esta parte podéis consultar los ejemplos del apartado 2.7 sobre proyecciones de interfaz.

consejo

El estado sirve para filtrar la consulta, aunque no sea uno de los cuatro campos que necesitamos transportar en la proyección. No es necesario añadir todas las propiedades de la entidad a la interfaz.

4️⃣ Segunda etapa: un DTO con la antigüedad calculada​

🟩 Diseñamos los datos de salida​

En un paquete dto, cread un record llamado IncidenciaSeguimientoDTO con los siguientes componentes:

ComponenteTipo
idLong
tituloString
prioridadString
diasDesdeRegistrolong

A diferencia de la proyección, el DTO no necesita contener fechaRegistro, porque la pantalla mostrará su antigüedad en días. Tampoco necesita la descripción, ya que el usuario puede consultarla pulsando «Ver detalle».

🟨 Calculamos la antigüedad en el servicio​

Incorporad en IncidenciaService un método que reciba el número de página y devuelva una Page<IncidenciaSeguimientoDTO>.

El método deberá preparar una petición Pageable con ocho elementos por página, ordenar por fechaRegistro ascendente (y después por id) y solicitar al repositorio la página de incidencias pendientes.

Después, convertirá cada elemento obtenido en el DTO correspondiente. Para calcular los días desde el registro, podéis utilizar la clase ChronoUnit, del paquete java.time.temporal:

Operación que permite calcular los días transcurridos
long dias = ChronoUnit.DAYS.between(fechaRegistro, LocalDate.now());

El dato fechaRegistro debe proceder de la proyección de cada incidencia. No almacenaremos el resultado del cálculo en MySQL.

Utilizad Page.map() para transformar la página de proyecciones en una página de DTO. No convirtáis el resultado en una lista y construyáis manualmente otra paginación; la información sobre el total de páginas y registros debe conservarse.

aviso

No resolváis el encargo recuperando todas las incidencias con findAll() para después filtrar las pendientes o calcular la página en memoria. El filtrado y la paginación se realizan en la consulta del repositorio. El cálculo de la antigüedad sí corresponde al servicio.

5️⃣ Tercera etapa: el nuevo panel Thymeleaf​

🟩 Incorporamos una ruta de consulta​

En el controlador MVC añadid una ruta GET /incidencias/seguimiento.

Debe recibir opcionalmente el parámetro pagina, con valor predeterminado 0, y solicitar al servicio los DTO correspondientes. Después, incorporará al Model los resultados y los datos necesarios para la navegación.

Aseguraos de que esta nueva ruta no interfiere con /incidencias/{id}, que continúa mostrando el detalle de una incidencia existente.

🟨 Construimos la vista​

Cread la plantilla seguimiento-incidencias.html reutilizando los estilos generales del gestor. El panel mostrará una tabla con identificador, título, prioridad, antigüedad y enlace al detalle.

La vista debe mostrar también el total de incidencias pendientes, indicar en qué página estamos y disponer de controles Anterior y Siguiente cuando correspondan.

Un enlace de paginación podría generar una URL como esta:

Solicitamos la segunda página del panel
/incidencias/seguimiento?pagina=1

En el listado general /incidencias, añadid un enlace visible a «Panel de seguimiento». Desde el panel debe poderse regresar al listado general.

consejo

Para construir los enlaces de detalle, aprovechad las rutas de la actividad anterior, por ejemplo /incidencias/{id}. No necesitamos duplicar la ficha de cada incidencia.

🟧 Casos especiales​

Si no hay incidencias pendientes, la tabla debe sustituirse por un mensaje claro. Si el usuario solicita una página negativa o superior a las disponibles, el comportamiento debe ser controlado y no mostrar una excepción técnica.

El panel no permitirá editar ni eliminar registros directamente. El objetivo de esta ampliación es trabajar con datos de consulta y presentación, no repetir el CRUD.

6️⃣ Comprobamos el resultado​

🟩 Pruebas recomendadas​

Utilizad los datos de prueba y comprobad los siguientes casos:

PruebaResultado esperado
Abrir /incidencias/seguimiento.Se muestran incidencias abiertas o en proceso, nunca resueltas.
Revisar la tabla.Solo aparecen ID, título, prioridad, antigüedad y acceso al detalle.
Comprobar la consulta.El repositorio devuelve una proyección, no una entidad completa.
Abrir una segunda página.Se muestran hasta ocho registros y el orden se conserva.
Comprobar el total.Refleja las incidencias pendientes, no solo las filas de la página actual.
Comparar una fecha de registro y su antigüedad.Los días están calculados respecto de la fecha actual.
Pulsar «Ver detalle».Se abre la ficha existente de esa incidencia.
Volver al listado general.Siguen funcionando los filtros, la paginación y el CRUD.
Consultar sin incidencias pendientes.Aparece un mensaje de ausencia de resultados.

El script proporcionado contiene 33 incidencias pendientes (18 abiertas y 15 en proceso). Ese total solo será exacto si la base de datos contiene únicamente los 48 registros del script; los datos añadidos o modificados durante las prácticas pueden cambiarlo. Con ocho registros por página, los 33 registros ocuparían cinco páginas.

🟨 Errores frecuentes​

🟩 Se recuperan entidades completas para construir el panel​

Revisad el tipo devuelto por el repositorio. La finalidad de una proyección es obtener una representación parcial directamente desde la consulta, no crear un DTO después de findAll() cuando ese no es el enfoque solicitado.

🟨 La antigüedad siempre vale cero o es incorrecta​

Comprobad que el cálculo utiliza la fecha de registro almacenada y LocalDate.now(), no la fecha de creación de un DTO ni un valor fijo.

🟧 Se pierden los datos de paginación al transformar​

Si convertís una Page en una List, os quedáis solo con el contenido. Revisad cómo aplicar Page.map() para conservar los metadatos de paginación.

🟥 La aplicación intenta abrir un ID llamado «seguimiento»​

Revisad las rutas del controlador: la ruta literal /incidencias/seguimiento debe estar declarada correctamente y no tratarse como un identificador numérico.

🟧 Lista de verificación​

  • La Actividad 3 funciona antes de comenzar la ampliación.
  • He creado IncidenciaPendienteView con los cuatro datos necesarios.
  • He añadido al repositorio una consulta paginada que utiliza la proyección.
  • La consulta excluye las incidencias resueltas.
  • He creado IncidenciaSeguimientoDTO como record.
  • Calculo la antigüedad desde el servicio, sin añadir columnas nuevas en MySQL.
  • Utilizo Page.map() y conservo la paginación.
  • El panel muestra ocho registros como máximo por página y comienza por los más antiguos.
  • La vista permite navegar entre páginas y abrir el detalle.
  • El listado general y las operaciones CRUD siguen funcionando.

7️⃣ Para reflexionar​

Pensad en estas tres preguntas después de terminar:

  1. ¿Por qué la proyección necesita fechaRegistro si el DTO no la contiene?
  2. ¿Por qué el cálculo de antigüedad corresponde al servicio y no a Thymeleaf?
  3. ¿Qué diferencia hay entre utilizar Page.map() y consultar entidades completas para después recorrer una lista?

Como mejora opcional, podéis permitir que el panel se filtre por prioridad, conservando ese filtro al cambiar de página. Si lo hacéis, aplicad el filtro en el repositorio, antes de paginar, y no después de transformar los resultados.
