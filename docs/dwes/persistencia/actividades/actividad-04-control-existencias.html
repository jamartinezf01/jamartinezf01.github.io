Actividad 4. Control de existencias

En el apartado 3.2. Implementación de relaciones uno a muchos hemos construido una biblioteca en la que varios libros pueden compartir una editorial. Ahora vamos a utilizar esas relaciones en una situación diferente, en la que registrar una asociación también tiene consecuencias sobre los datos de la aplicación.

Un centro educativo dispone de un pequeño almacén de material informático: ratones, teclados, cables, memorias USB y otros artículos. Hasta ahora, su aplicación permite mantener el catálogo y consultar cuántas unidades hay disponibles. Sin embargo, cuando llegan nuevos materiales o se retiran unidades del almacén, el personal modifica las existencias sin dejar constancia de lo ocurrido.

El objetivo del reto es incorporar un historial de movimientos de entrada y salida. Cada movimiento pertenecerá a un artículo y, al registrarlo, las existencias de ese artículo deberán actualizarse correctamente. De esta forma practicaremos las relaciones N:1 y 1:N con Spring Data JPA, pero también tendremos que tomar decisiones sobre validación, consultas y conservación de los datos.

información

Esta actividad es de entrega obligatoria y forma parte del seguimiento de la unidad. No tiene una calificación numérica propia y se registrará como Entregada o NO entregada.

1️⃣ Partimos de una aplicación que ya funciona​

🟩 El proyecto de partida​

Se proporciona un proyecto Spring Boot con Maven, Java 21, Spring Data JPA, MySQL, Spring MVC y Thymeleaf. La aplicación ya contiene la entidad Articulo, su repositorio y un CRUD básico con listado, alta, edición y eliminación. También dispone de una hoja de estilos y de un script con diez artículos y sus existencias iniciales.

Descarga el proyecto de partida: Control de existencias · proyecto base (ZIP).

La entidad existente representa la información que ya conocemos de cada artículo:

Propiedad de ArticuloTipo JavaFinalidad
idLongIdentificador generado por MySQL.
codigoStringCódigo único del artículo.
nombreStringDenominación del material.
stockActualIntegerUnidades disponibles en el almacén.

En el formulario de artículos, el stock se establece al crear un artículo. Después no debe modificarse manualmente desde la edición: las entradas y salidas serán las responsables de cambiarlo. El proyecto base ya impide editar directamente ese valor; deberemos conservar esa decisión.

🟨 Preparamos el entorno y comprobamos el punto de partida​

El ZIP contiene un README.md con las instrucciones de arranque y dos scripts SQL. Utilizaremos una base nueva, control_existencias, sin modificar la base de la Biblioteca de aula ni la de MiColección.

  1. Abrimos el proyecto Maven en IntelliJ IDEA gratuito y comprobamos que utiliza Java 21.
  2. Preparamos la base de datos ejecutando sql/00-crear-base-datos.sql con una cuenta administradora. Sustituimos antes la contraseña de ejemplo por una propia.
  3. Configuramos DB_PASSWORD en Run → Edit Configurations → Environment variables. MySQL debe estar disponible en localhost:3306, directamente o mediante el puerto publicado de Docker.
  4. Arrancamos la aplicación para que Hibernate cree la tabla inicial articulos y comprobamos que no hay errores de conexión.
  5. Ejecutamos una sola vez sql/01-articulos-iniciales.sql y abrimos http://localhost:8080/articulos.

Comprobamos que aparecen los diez artículos y que podemos consultar y editar sus datos básicos. No debemos comenzar a programar los movimientos hasta confirmar que el proyecto de partida funciona.

aviso

Los scripts iniciales no están pensados para ejecutarse repetidamente sobre una base ya preparada. Si aparece un error porque la base, la cuenta o los artículos ya existen, revisaremos su estado antes de crear duplicados.

El proyecto utiliza spring.jpa.hibernate.ddl-auto=update para facilitar la creación de las tablas durante esta práctica. No utilizaremos create ni create-drop, porque podrían hacer perder los registros.

2️⃣ Diseñamos la relación entre artículos y movimientos​

🟩 Qué representa un movimiento​

Cada vez que entran o salen unidades del almacén se debe registrar un movimiento. Por ejemplo, si un artículo tiene 25 unidades y llegan otras 5, se registrará una entrada de 5 y el stock pasará a 30. Si posteriormente se retiran 8, se registrará una salida de 8 y el stock quedará en 22.

Diseñaremos una nueva entidad Movimiento con estos datos:

Propiedad de MovimientoTipo propuestoDescripción
idLongIdentificador del movimiento.
tipoStringENTRADA o SALIDA.
cantidadIntegerNúmero de unidades; siempre positivo.
fechaLocalDateTimeFecha y hora del registro, asignadas por el servidor.
articuloArticuloArtículo al que corresponde el movimiento.

La fecha no se elegirá en el formulario: se asignará cuando el servidor registre la operación. Para esta actividad podemos trabajar con las cadenas ENTRADA y SALIDA, comprobando expresamente que no se aceptan otros valores. No necesitamos incorporar todavía enumeraciones ni una arquitectura más compleja.

🟨 Identificamos la cardinalidad y su almacenamiento​

Las reglas de este almacén son sencillas: un artículo puede tener muchos movimientos, pero cada movimiento pertenece a un único artículo. Por tanto, la relación se interpreta como 1:N desde Articulo y N:1 desde Movimiento.

La base de datos tendrá dos tablas relacionadas. La nueva tabla movimientos almacenará una columna articulo_id que actuará como clave ajena hacia articulos.id.

En el código Java necesitamos poder recorrer la relación en ambos sentidos: desde un movimiento para conocer el artículo al que pertenece, y desde un artículo para consultar su historial.

consejo

Antes de programar, identifica qué entidad contiene la clave ajena, cuál será el lado propietario en JPA y qué nombre de propiedad debe utilizar mappedBy en el lado inverso. Estas tres decisiones deben ser coherentes con el modelo relacional.

3️⃣ Primer reto: registramos los movimientos​

🟩 Creamos la entidad y el repositorio​

Incorporamos Movimiento y MovimientoRepository. La nueva entidad debe utilizar @ManyToOne y @JoinColumn para establecer una relación obligatoria con un artículo existente. La clave ajena se llamará articulo_id.

No se trata de guardar únicamente Long articuloId dentro de Movimiento. Como vimos en la Biblioteca de aula, la propiedad relacionada de una entidad JPA debe representar un objeto Articulo. El identificador recibido por HTTP se resolverá más adelante desde el servicio.

Cuando el proyecto arranque, comprobaremos que Hibernate ha creado movimientos y que MySQL reconoce su clave ajena. La tabla articulos debe conservar los artículos iniciales.

🟨 Construimos el formulario de entrada y salida​

Desarrollamos una pantalla para registrar un movimiento. El formulario deberá permitir seleccionar un artículo existente, elegir ENTRADA o SALIDA e indicar la cantidad. Mostraremos los nombres de los artículos, pero el formulario enviará sus identificadores.

Conviene utilizar una clase específica, por ejemplo MovimientoForm, con los datos que llegan desde el navegador. Así podremos recibir un articuloId, comprobarlo y recuperar después la entidad correspondiente. El formulario no debe permitir introducir libremente un identificador de movimiento ni la fecha del registro.

Podemos utilizar estas rutas o una organización equivalente:

AcciónMétodoRuta propuesta
Mostrar el formulario de movimiento.GET/movimientos/nuevo
Registrar una entrada o salida.POST/movimientos/nuevo
Consultar el historial de un artículo.GET/articulos/{id}/movimientos

El diseño visual puede aprovechar la hoja CSS incluida en el proyecto base. Lo importante es que el formulario sea comprensible, conserve los datos cuando haya errores y muestre mensajes claros.

🟧 Implementamos las reglas del almacén en el servicio​

La operación principal debe resolverse en la capa de servicios, no dentro del controlador. Antes de guardar un movimiento tendremos que comprobar que el artículo existe, que el tipo es válido y que la cantidad es mayor que cero.

Si el movimiento es una entrada, el nuevo stock será el stock anterior más la cantidad recibida. Si es una salida, será el stock anterior menos la cantidad retirada. Pero una salida solo se admitirá cuando haya suficientes unidades disponibles: no podemos dejar el stock en negativo.

Al registrar una operación válida deben quedar almacenados dos cambios relacionados: el movimiento en su tabla y el nuevo stockActual del artículo. En cambio, si el formulario contiene datos inválidos, no se debe guardar ningún movimiento ni modificar el stock.

aviso

En esta actividad implementaremos la lógica con los servicios y repositorios que ya conocemos. No se exige todavía gestionar las dos escrituras como una operación transaccional completa: la atomicidad y los posibles fallos entre escrituras se estudiarán más adelante. Por ahora nos interesa representar correctamente la relación y las reglas del almacén.

4️⃣ Segundo reto: consultamos el historial de un artículo​

🟩 Añadimos la navegación inversa​

Hasta ahora, con @ManyToOne, cada movimiento conoce su artículo. Queremos también que desde un artículo pueda consultarse su colección de movimientos. Para ello, añadiremos a Articulo una propiedad List<Movimiento> con @OneToMany(mappedBy = "articulo").

No debemos crear una segunda clave ajena ni una tabla intermedia. La asociación seguirá almacenada únicamente en movimientos.articulo_id. Tampoco añadiremos cascadas de eliminación: los movimientos constituyen un historial que queremos conservar.

🟨 Mostramos los movimientos en orden cronológico​

Desde el listado de artículos añadiremos un enlace para consultar el historial de cada uno. La nueva pantalla debe mostrar el código y el nombre del artículo, su stock actual y los movimientos asociados, incluyendo tipo, cantidad y fecha.

Para que las pruebas sean sencillas, ordenaremos el historial del movimiento más reciente al más antiguo. Si el artículo no tiene movimientos, debe aparecer un mensaje informativo en lugar de una tabla vacía sin explicación.

Recuerda que el proyecto utiliza spring.jpa.open-in-view=false. Si una vista necesita recorrer la colección de movimientos, debes planificar su carga al realizar la consulta, por ejemplo con @EntityGraph en un método adecuado del repositorio. No cambies todas las asociaciones a EAGER para resolver el problema.

🟧 Protegemos la eliminación de artículos con historial​

El proyecto base incluye la opción de eliminar artículos. Cuando añadamos movimientos, debemos adaptar este comportamiento: un artículo que ya tenga movimientos registrados no podrá eliminarse desde la aplicación. En ese caso mostraremos un aviso comprensible al usuario y conservaremos tanto el artículo como su historial.

Un artículo sin movimientos puede seguir eliminándose. Esta comprobación debe realizarse consultando los datos que ya tenemos almacenados, no confiando únicamente en que falle la clave ajena de MySQL.

Una decisión importante

El historial no es el stock inicial. Los diez artículos del proyecto de partida ya tienen existencias antes de que empecemos a registrar movimientos. Por eso, aunque un artículo todavía no tenga movimientos, puede mostrar un stockActual mayor que cero.

A partir de ese momento, cada entrada o salida registrada modificará el stock y aparecerá en el historial.

5️⃣ Comprobamos que la aplicación funciona​

🟩 Pruebas desde el navegador​

No basta con comprobar que el formulario se envía. Debemos demostrar que las reglas se cumplen y que los datos siguen siendo coherentes. Podemos utilizar el artículo ART-001, que en el script inicial tiene 25 unidades:

AcciónStock esperadoQué debe ocurrir
Situación inicial.25Todavía no hay movimientos para ese artículo.
Registrar una entrada de 5 unidades.30Se guarda una ENTRADA y aumenta el stock.
Registrar una salida de 12 unidades.18Se guarda una SALIDA y disminuye el stock.
Intentar una salida de 19 unidades.18Se muestra un error y no se guarda el movimiento.
Intentar registrar 0 o -3 unidades.18La validación impide guardar el movimiento.
Consultar el historial.18Aparecen únicamente la entrada de 5 y la salida de 12.

Estas cantidades son un caso de comprobación, no datos que deban escribirse en el código. El resultado debe calcularse a partir de las existencias almacenadas para el artículo elegido.

Después repetiremos una entrada o salida sobre otro artículo y comprobaremos que el primero no cambia. También intentaremos borrar un artículo con movimientos para verificar que se conserva su historial.

🟨 Contrastamos la aplicación con MySQL​

Comprobamos los registros directamente en MySQL. El siguiente SQL supone que se han utilizado los nombres de tablas y columnas indicados en el enunciado:

Consulta de artículos y existencias
SELECT id, codigo, nombre, stock_actual
FROM articulos
ORDER BY codigo;
Consulta del historial y sus claves ajenas
SELECT m.id, a.codigo, m.tipo, m.cantidad, m.fecha
FROM movimientos m
JOIN articulos a ON m.articulo_id = a.id
ORDER BY m.fecha DESC, m.id DESC;

La segunda consulta debe permitir reconocer a qué artículo pertenece cada movimiento. No debe haber referencias a artículos inexistentes. También comprobaremos que un intento fallido de salida o una cantidad inválida no han creado nuevas filas en movimientos.

consejo

No hace falta anotar ni suponer los IDs generados por MySQL: comprobaremos los valores reales en la base de datos y utilizaremos los identificadores recuperados mediante los repositorios.

6️⃣ Si terminas antes: ampliaciones opcionales​

Una vez que funcione correctamente el mínimo solicitado, se pueden realizar pequeñas mejoras sin introducir todavía nuevas entidades ni relaciones N:M.

🟩 Avisos de existencias bajas​

Mostrar un aviso en el listado cuando el stock de un artículo sea inferior a cinco unidades. El aviso debe calcularse a partir de stockActual y no almacenarse en otra columna.

🟨 Filtrar el historial por tipo​

Permitir consultar únicamente las entradas o únicamente las salidas de un artículo. Decide qué parámetro GET necesitará la pantalla y cómo resolver la consulta con Spring Data JPA.

🟧 Resumen de movimientos​

Mostrar el número de entradas y salidas registradas para un artículo. Recuerda que el número de movimientos no equivale al número de unidades que han entrado o salido: un movimiento puede representar varias unidades.

Estas mejoras son voluntarias. No sustituyen a las comprobaciones de relación, stock e historial de los apartados anteriores.

7️⃣ Antes de dar la actividad por terminada​

🟩 Errores frecuentes que conviene revisar​

🟩 Confundir el identificador recibido con el objeto asociado​

El navegador envía un articuloId, pero Movimiento debe almacenar una referencia a Articulo. El servicio es el responsable de recuperar el artículo existente antes de guardar.

🟨 Actualizar el stock desde el controlador​

El controlador recibe y valida los datos del formulario. La decisión de sumar, restar o rechazar una salida debe estar en el servicio, para que la regla no dependa de una pantalla concreta.

🟧 Utilizar mappedBy = "articulo_id"​

mappedBy hace referencia al atributo Java de Movimiento, no a la columna SQL. Si la propiedad se llama articulo, el nombre correcto es mappedBy = "articulo".

🟥 Permitir que los movimientos eliminen artículos​

No utilizaremos CascadeType.REMOVE ni CascadeType.ALL para borrar artículos a través de una relación con movimientos. La eliminación de una entidad y la conservación de su historial son decisiones diferentes.

🟪 Cargar el historial desde Thymeleaf sin prepararlo​

Si la relación se declara LAZY, una vista que acceda a ella sin haberla recuperado correctamente puede producir un error. Debemos planificar la consulta en el repositorio o servicio.

🟨 Lista de comprobación personal​

  • El proyecto de partida funciona y contiene los diez artículos iniciales.
  • Existe Movimiento con @ManyToOne y una clave ajena articulo_id en MySQL.
  • Articulo permite recorrer sus movimientos mediante @OneToMany(mappedBy = "articulo").
  • El formulario permite elegir un artículo existente y registrar entradas o salidas.
  • El servicio rechaza cantidades no positivas, tipos inválidos y salidas que superen el stock.
  • Registrar un movimiento correcto actualiza el stock del artículo correspondiente.
  • El historial muestra los movimientos del artículo elegido y su fecha.
  • Un artículo con movimientos no puede eliminarse desde la aplicación.
  • Las consultas SQL confirman las asociaciones y las existencias resultantes.
Para continuar

En este reto hemos utilizado una relación 1:N / N:1 para resolver una necesidad real: relacionar movimientos con artículos y mantener un historial coherente. También hemos comprobado que representar correctamente una relación es solo una parte del trabajo: una aplicación debe respetar las reglas del problema al guardar y eliminar datos.

Más adelante retomaremos Control de existencias para estudiar las transacciones y comprobar qué ocurre cuando una operación necesita modificar varios registros. Por ahora no se exige resolver esas situaciones avanzadas.
