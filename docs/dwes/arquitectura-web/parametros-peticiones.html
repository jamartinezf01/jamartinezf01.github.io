Parámetros en las peticiones

Hasta ahora se ha visto que un controlador puede responder a una ruta fija, como /saludo. Sin embargo, en una aplicación web real no siempre basta con devolver la misma respuesta. Muy a menudo la aplicación necesita recibir algún dato en la petición para poder actuar de una forma u otra. En esta unidad veremos dos casos sencillos: datos que llegan como parámetros en la URL y datos que forman parte de la propia ruta.

Por ejemplo, no es lo mismo acceder a una página genérica que pedir un saludo personalizado, consultar el detalle de un producto o indicar una categoría concreta. En todos esos casos, el navegador envía una petición y, además, añade información que el servidor debe interpretar.

En Spring Boot, esta información puede recogerse de varias formas. En esta unidad nos centraremos en dos de las más habituales al empezar:

  • @RequestParam, para leer datos que llegan como parámetros en la URL.
  • @PathVariable, para leer datos que forman parte de la propia ruta.
Idea principal

En este punto no se trata todavía de construir formularios completos ni de trabajar con objetos complejos. Lo importante es entender que una petición puede llevar datos y que el controlador puede recuperarlos para generar una respuesta distinta.

1️⃣ Qué significa enviar parámetros en una petición​

Cuando se escribe una dirección en el navegador, no solo se puede indicar la ruta principal. También es posible añadir información extra. Esa información permite que el servidor sepa mejor qué se está solicitando.

Por ejemplo, estas dos direcciones no significan exactamente lo mismo:

http://localhost:8080/saludo
http://localhost:8080/saludo?nombre=Ana

En la primera, la ruta es simplemente /saludo. En la segunda, además de la ruta, se está enviando un parámetro llamado nombre con el valor Ana.

También puede ocurrir algo así:

http://localhost:8080/productos/7

En este caso, el valor 7 no aparece como parámetro con nombre, sino como parte de la propia ruta. Esa es justamente la situación en la que suele utilizarse @PathVariable.

🟩 Dos formas muy habituales de enviar datos​

Al empezar con Spring Boot conviene distinguir claramente estas dos formas:

FormaEjemploUso habitual
Parámetros en la URL/saludo?nombre=AnaFiltrar, buscar o enviar datos sencillos.
Datos dentro de la ruta/productos/7Identificar un elemento concreto.

No son exactamente lo mismo, aunque ambos mecanismos sirven para enviar información al servidor.

🟨 Cuándo usaremos cada una​

Una regla sencilla para empezar puede ser esta:

  • Si el dato funciona como una opción o un criterio de búsqueda, suele encajar bien con @RequestParam.
  • Si el dato identifica un recurso concreto dentro de la ruta, suele encajar mejor con @PathVariable.

No es necesario memorizar esto de forma rígida desde el primer día, pero sí ayuda a ir entendiendo por qué una URL puede tener distintas formas.

2️⃣ Uso de @RequestParam​

@RequestParam se utiliza para leer parámetros que llegan en la URL, normalmente detrás del signo ?.

Un ejemplo sencillo sería un saludo personalizado.

package com.ejemplo.demo.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.ResponseBody;

@Controller
public class SaludoController {

    @GetMapping("/saludo")
    @ResponseBody
    public String saludar(@RequestParam String nombre) {
        return "Hola, " + nombre;
    }
}
en este ejemplo

En este ejemplo, la ruta sigue siendo /saludo, pero el método necesita un dato adicional. La anotación @RequestParam indica a Spring Boot que debe buscar un parámetro llamado nombre en la petición. Si se accede a la dirección http://localhost:8080/saludo?nombre=Ana, el valor Ana se guardará en la variable nombre y se utilizará para construir la respuesta.

Si se accede correctamente, el navegador mostrará algo como esto:

Hola, Ana

🟩 Qué ocurre en la URL​

La dirección que utiliza este ejemplo sería:

http://localhost:8080/saludo?nombre=Ana

Aquí pueden distinguirse dos partes:

  • /saludo → la ruta principal.
  • nombre=Ana → el parámetro enviado.

Si hubiera más de un parámetro, se separarían con &.

http://localhost:8080/buscar?categoria=teclados&marca=logitech

🟨 Parámetros opcionales​

A veces interesa que el parámetro no sea obligatorio. Para ello puede indicarse un valor por defecto.

@GetMapping("/saludo")
@ResponseBody
public String saludar(@RequestParam(defaultValue = "invitado") String nombre) {
    return "Hola, " + nombre;
}
en este ejemplo

En esta versión, si la URL incluye ?nombre=Ana, la respuesta será Hola, Ana. Pero si se accede simplemente a /saludo, Spring usará el valor por defecto invitado y la respuesta será Hola, invitado.

Esta opción es muy útil al empezar, porque evita errores cuando un dato puede faltar.

🟧 Errores frecuentes con @RequestParam​

Uno de los fallos más habituales es confundir la ruta con el parámetro. Por ejemplo, si el método espera un @RequestParam llamado nombre, no basta con escribir:

http://localhost:8080/saludo/Ana

Eso sería otra estructura distinta. Si se ha programado @RequestParam, lo correcto sería:

http://localhost:8080/saludo?nombre=Ana

También es frecuente que el nombre del parámetro en la URL no coincida con el nombre esperado por el controlador.

3️⃣ Uso de @PathVariable​

@PathVariable se utiliza cuando el dato forma parte de la propia ruta.

Un ejemplo muy habitual sería mostrar el detalle de un producto según su identificador.

package com.ejemplo.demo.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.ResponseBody;

@Controller
public class ProductoController {

    @GetMapping("/productos/{id}")
    @ResponseBody
    public String verProducto(@PathVariable int id) {
        return "Mostrando el producto con id " + id;
    }
}
en este ejemplo

En este caso, la ruta ya indica que habrá una parte variable entre llaves: {id}. Cuando el navegador accede a http://localhost:8080/productos/7, Spring Boot toma el valor 7, lo guarda en la variable id y ejecuta el método con ese dato.

La respuesta podría ser:

Mostrando el producto con id 7

🟩 Qué significa la parte entre llaves​

En la anotación @GetMapping("/productos/{id}"), la parte {id} indica que la ruta no es completamente fija. Existe un hueco que se completará con el valor real enviado en la URL.

Por tanto:

  • /productos/1
  • /productos/2
  • /productos/25

pueden activar el mismo método, pero con valores distintos.

🟨 Cuándo tiene sentido usarlo​

@PathVariable encaja muy bien cuando se quiere acceder a un elemento concreto:

  • un producto,
  • una noticia,
  • un usuario,
  • una categoría,
  • una página identificada por un valor.

No hace falta que todavía haya base de datos. Aunque por ahora solo devolvamos un texto, la idea ya es la misma que se utilizará más adelante con datos reales.

🟧 Error frecuente con @PathVariable​

Si la ruta del @GetMapping y el valor esperado no coinciden, Spring no podrá enlazar correctamente el dato.

Por ejemplo, si se define:

@GetMapping("/productos/{id}")

pero luego se accede a:

http://localhost:8080/productos

faltará el valor variable y la ruta no coincidirá.

4️⃣ @RequestParam y @PathVariable: comparación sencilla​

Ambas anotaciones sirven para recibir datos en el controlador, pero no se usan exactamente igual.

AnotaciónDónde llega el datoEjemploIdea principal
@RequestParamEn la parte final de la URL, como parámetro/saludo?nombre=AnaAñadir opciones o datos sencillos.
@PathVariableDentro de la propia ruta/productos/7Identificar un recurso concreto.
tip

Si al leer la URL aparece un ?, probablemente se está trabajando con parámetros del tipo @RequestParam. Si el dato va incrustado en la ruta, probablemente encaje mejor con @PathVariable.

5️⃣ Cómo encaja esto en Spring Boot​

En los ejemplos anteriores se ha devuelto una cadena de texto directamente con @ResponseBody, porque eso permite centrarse en la idea principal: el controlador recibe la petición, extrae el dato y genera una respuesta.

Más adelante, estos mismos mecanismos se utilizarán también cuando el controlador devuelva una vista Thymeleaf. En ese caso, en lugar de responder con texto directo, se enviarán datos al modelo para que aparezcan en la plantilla.

aviso

Si un controlador devuelve una vista Thymeleaf, no debe usarse @ResponseBody, porque en ese caso Spring intentaría enviar texto literal en lugar de interpretar el nombre de la vista.

6️⃣ Actividad no evaluable: probando rutas con datos​

Esta actividad sirve para comprobar que se entienden las dos formas básicas de enviar datos al servidor. No es evaluable y no requiere entrega, pero conviene realizarla para afianzar los conceptos antes de seguir.

🟩 Objetivo​

Distinguir cuándo una petición utiliza un parámetro en la URL y cuándo utiliza un dato dentro de la ruta.

🟨 Desarrollo​

Observa estas direcciones y responde qué mecanismo parece más adecuado en cada caso:

http://localhost:8080/saludo?nombre=Lucía
http://localhost:8080/libros/12
http://localhost:8080/buscar?texto=java
http://localhost:8080/alumnos/4

Para cada una, indica:

  1. Si usarías @RequestParam o @PathVariable.
  2. Qué dato recibe el controlador.
  3. Qué podría devolver la aplicación como respuesta.

Después de clasificarlas, prueba a escribir dos rutas similares en un controlador sencillo y comprueba el resultado en el navegador.

🟧 Ejemplo orientativo​

Para esta dirección:

http://localhost:8080/saludo?nombre=Lucía

una respuesta razonable sería:

  • Se usaría @RequestParam.
  • El controlador recibiría el dato nombre = Lucía.
  • La respuesta podría ser Hola, Lucía.

🟥 Comprobación final​

Antes de terminar, comprueba si sabes responder a estas preguntas:

  • ¿En qué se diferencia /saludo?nombre=Ana de /saludo/Ana?
  • ¿Qué anotación usarías para /productos/8?
  • ¿Qué anotación usarías para /buscar?texto=raton?
  • ¿Cuándo tiene sentido definir un valor por defecto?
tip

Si todavía cuesta distinguir ambos casos, conviene fijarse solo en la forma de la URL. Ese suele ser el mejor punto de partida al empezar.

7️⃣ En resumen​

En Spring Boot, una petición puede llevar datos y el controlador puede recuperarlos de distintas maneras. En esta unidad se han trabajado dos de las más habituales.

Con @RequestParam, el dato llega como parámetro en la URL. Con @PathVariable, el dato forma parte de la propia ruta. Ambas opciones permiten que una misma aplicación responda de forma diferente según la información recibida.

No se trata todavía de memorizar todas las posibilidades, sino de reconocer la idea principal: una ruta puede ser fija o puede incluir datos variables que el controlador utiliza para generar la respuesta.
