Actividad. Simulador de peticiones HTTP

En esta unidad hemos estudiado cómo se comunican un cliente y un servidor mediante HTTP: el cliente envía una petición, el servidor la procesa y devuelve una respuesta con un código de estado, unas cabeceras y, cuando corresponde, un cuerpo.

En esta actividad vamos a representar ese funcionamiento mediante un programa Java.

No vamos a crear un servidor real ni a realizar conexiones a Internet. El objetivo es construir un simulador que nos obligue a modelar correctamente las piezas fundamentales de una comunicación HTTP y, al mismo tiempo, a utilizar los conocimientos de Java repasados previamente.

Objetivo

Desarrollar en Java un simulador de peticiones y respuestas HTTP capaz de procesar distintos tipos de peticiones sobre un pequeño conjunto de usuarios y devolver una respuesta coherente en cada caso.

1️⃣ Qué debe simular el programa​

El programa representará un intercambio como este:

CLIENTE
   │
   │  Petición HTTP
   ▼
SERVIDOR SIMULADO
   │
   │  Procesa método, ruta y datos
   ▼
RESPUESTA HTTP
   │
   ▼
CLIENTE

Por ejemplo:

========== PETICIÓN ==========

GET /usuarios/2 HTTP/1.1
Host: localhost
Accept: application/json

========== RESPUESTA =========

HTTP/1.1 200 OK
Content-Type: application/json

{"id":2,"nombre":"Ana"}

El formato no tiene que reproducir todos los detalles de HTTP real, pero sí debe permitir reconocer claramente:

  • el método utilizado.
  • la ruta solicitada.
  • las cabeceras.
  • el cuerpo, cuando exista.
  • el código de estado de la respuesta.

2️⃣ Representación de las peticiones​

Crea una clase abstracta:

HttpRequest

Esta clase representará los elementos comunes a cualquier petición HTTP.

Toda petición deberá almacenar, como mínimo:

  • la ruta solicitada.
  • las cabeceras HTTP.

Las cabeceras se almacenarán mediante:

Map<String, String>

La clase deberá permitir:

  • añadir una cabecera.
  • consultar una cabecera por su nombre.
  • mostrar las cabeceras de la petición.
  • conocer el método HTTP de la petición.
aviso

En el planteamiento original de la actividad se hacía referencia a una interfaz para determinar el método HTTP. En esta versión utilizaremos la propia jerarquía de HttpRequest: cada tipo concreto de petición deberá indicar qué método representa.

Una posible petición representada por el programa sería:

GET /usuarios HTTP/1.1
Host: localhost
Accept: application/json
User-Agent: JavaClient/1.0

🟩 Tipos de petición​

Crea tres clases que hereden de HttpRequest:

GetRequest
PostRequest
DeleteRequest

Cada clase representará su método HTTP correspondiente.

El programa deberá poder manejar objetos de estas clases de forma polimórfica como peticiones HTTP.

🟨 Peticiones con cuerpo​

Una petición POST deberá poder almacenar además un cuerpo.

Por ejemplo:

POST /usuarios HTTP/1.1
Host: localhost
Content-Type: application/json

{"nombre":"Lucía"}

No es necesario implementar un analizador JSON real. El cuerpo puede almacenarse como una cadena de texto.

3️⃣ Representación de las respuestas​

Crea un enum llamado:

HttpStatus

Debe incluir, al menos, estos estados:

CódigoEstadoUso en el simulador
200OKLa consulta se ha realizado correctamente.
201CreatedSe ha creado un nuevo usuario.
204No ContentSe ha eliminado correctamente un usuario.
400Bad RequestLa petición no es válida o no se reconoce.
404Not FoundEl recurso solicitado no existe.
500Internal Server ErrorSe ha producido un error durante el procesamiento.

Después crea una clase:

HttpResponse

La respuesta deberá almacenar:

  • el estado HTTP.
  • las cabeceras.
  • el cuerpo de la respuesta.

Las cabeceras pueden almacenarse también mediante:

Map<String, String>

Una respuesta podría tener este aspecto:

HTTP/1.1 200 OK
Content-Type: application/json

{"id":2,"nombre":"Ana"}
nota

Una respuesta 204 No Content no debe necesitar un cuerpo, porque precisamente indica que la operación se ha realizado correctamente pero no se devuelve contenido.

4️⃣ El servidor simulado​

Crea una clase:

HttpServer

Esta clase será la encargada de recibir objetos HttpRequest, analizar la petición y devolver un objeto HttpResponse.

El servidor mantendrá un pequeño conjunto de usuarios mediante:

Map<Integer, String>

Por ejemplo:

1 → Ana
2 → Marcos
3 → Lucía

No se pretende construir un sistema completo de gestión de usuarios. Este Map solo servirá para disponer de datos con los que comprobar el comportamiento del servidor.

🟩 Comportamiento obligatorio​

El servidor deberá responder como mínimo a estas situaciones:

PeticiónResultado esperado
GET /usuarios200 OK y listado de usuarios.
GET /usuarios/{id} con un identificador existente200 OK y datos del usuario.
GET /usuarios/{id} con un identificador inexistente404 Not Found.
POST /usuarios201 Created y creación del usuario.
DELETE /usuarios/{id} con un identificador existente204 No Content y eliminación del usuario.
DELETE /usuarios/{id} con un identificador inexistente404 Not Found.
Ruta o petición no reconocida400 Bad Request.

Para rutas como:

/usuarios/3

el programa deberá distinguir la parte fija:

/usuarios/

del identificador:

3

y utilizar ese valor para consultar el Map de usuarios.

aviso

No deben resolverse todos los casos devolviendo siempre 200 OK. El código de estado debe reflejar realmente el resultado de procesar la petición.

5️⃣ Procesamiento polimórfico​

El método principal del servidor encargado de procesar peticiones deberá poder recibir cualquier petición mediante una referencia del tipo:

HttpRequest

Por tanto, el servidor no deberá tener un método independiente para cada objeto creado desde Main.

La idea es que todas estas peticiones puedan procesarse mediante la misma operación:

GetRequest
PostRequest
DeleteRequest
     │
     └──────────────► HttpRequest ──────────────► HttpServer

El servidor deberá determinar qué tipo de petición ha recibido y actuar en consecuencia.

Este apartado es importante porque conecta el funcionamiento de HTTP con los conceptos de herencia y polimorfismo trabajados previamente en Java.

6️⃣ Programa principal y pruebas mínimas​

Crea una clase Main desde la que se construyan las peticiones y se envíen al servidor simulado.

El programa deberá ejecutar, como mínimo, estas pruebas:

  1. Obtener la lista completa de usuarios.
  2. Obtener un usuario existente.
  3. Solicitar un usuario que no existe.
  4. Crear un usuario mediante POST.
  5. Consultar después el usuario creado para comprobar que realmente se ha almacenado.
  6. Eliminar un usuario existente mediante DELETE.
  7. Consultar después el usuario eliminado para comprobar que ya no existe.
  8. Intentar eliminar un usuario inexistente.
  9. Realizar una petición con una ruta no reconocida.

Para cada caso deben mostrarse claramente por consola la petición enviada y la respuesta obtenida.

Por ejemplo:

========== PETICIÓN ==========

DELETE /usuarios/3 HTTP/1.1
Host: localhost

========== RESPUESTA =========

HTTP/1.1 204 No Content

Las pruebas no deben limitarse a imprimir respuestas preparadas directamente desde Main. Todas deben pasar por el método de procesamiento de HttpServer.

7️⃣ Requisitos técnicos​

La solución deberá cumplir todos estos requisitos:

  • Existirá una clase abstracta HttpRequest.
  • Se utilizará herencia para representar GET, POST y DELETE.
  • Se utilizará polimorfismo al procesar las peticiones.
  • Las cabeceras de las peticiones se almacenarán mediante Map<String, String>.
  • Los usuarios del servidor se almacenarán mediante Map<Integer, String>.
  • Los códigos HTTP se representarán mediante un enum.
  • Existirá una clase HttpResponse.
  • Existirá una clase HttpServer responsable del procesamiento.
  • POST permitirá almacenar un cuerpo.
  • Los códigos de estado deberán corresponder con el resultado real de cada operación.
  • La clase Main se utilizará para probar el sistema, no para implementar la lógica del servidor.
peligro

No se valorará como simulación HTTP una solución en la que toda la lógica esté concentrada en Main o en la que las clases se creen únicamente para cumplir formalmente los requisitos sin participar realmente en el funcionamiento del programa.

8️⃣ Comprobación antes de finalizar​

Antes de considerar terminada la actividad, comprueba que puedes responder afirmativamente a estas preguntas:

  • ¿Todas las peticiones comparten realmente una clase base?
  • ¿El servidor puede procesarlas utilizando referencias HttpRequest?
  • ¿Las cabeceras se almacenan en un Map?
  • ¿Los códigos de estado proceden del enum HttpStatus?
  • ¿Un GET sobre un usuario inexistente devuelve 404?
  • ¿Después de un POST el nuevo usuario puede consultarse?
  • ¿Después de un DELETE el usuario deja de existir?
  • ¿Una respuesta 204 se muestra sin cuerpo?
  • ¿Una ruta no reconocida produce 400 Bad Request?
  • ¿La salida por consola permite distinguir claramente petición y respuesta?

El objetivo final no es reproducir un servidor HTTP real, sino demostrar que se comprende cómo se relacionan método, ruta, cabeceras, cuerpo, procesamiento y código de estado dentro de una comunicación HTTP.

📦 Cómo preparar la entrega​

Antes de entregar, comprueba que el proyecto compila y se ejecuta correctamente.

Preparar la entrega

Comprime en un archivo .zip la carpeta src completa del proyecto.

Es importante conservar la estructura de paquetes y todos los archivos .java necesarios para ejecutar la aplicación.

El ZIP debe contener una estructura similar a:

Contenido de la entrega
src/
└── ...
Antes de entregar

No incluyas archivos o carpetas generados por IntelliJ IDEA o Git, como:

Archivos que no deben entregarse
.idea/
out/
.git/
*.iml

No copies los archivos .java sueltos: entrega siempre la carpeta src completa para conservar correctamente la estructura de paquetes.

Nombra el archivo siguiendo este formato:

Nombre del archivo
apellido-nombre-UT1.zip
