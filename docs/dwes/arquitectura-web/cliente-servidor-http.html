Cliente, servidor y HTTP

Cuando entramos en una página web parece que todo ocurre dentro del navegador. Escribimos una dirección, pulsamos Intro y aparece una página. Sin embargo, detrás de esa acción hay una comunicación entre varios elementos: un cliente, un servidor y un protocolo que permite que ambos se entiendan.

En esta primera parte de la unidad vamos a estudiar esa idea general. No se trata todavía de programar una aplicación completa, sino de comprender qué ocurre cuando una persona accede a una web y por qué en el desarrollo web en entorno servidor necesitamos distinguir muy bien qué se ejecuta en el navegador y qué se ejecuta en el servidor.

Idea principal

Una aplicación web funciona gracias a la comunicación entre un cliente, normalmente el navegador, y un servidor, que recibe peticiones, las procesa y devuelve respuestas.

1️⃣ El modelo cliente-servidor​

🟩 Qué es el cliente​

En una aplicación web, el cliente es el programa que utiliza la persona usuaria para acceder a la aplicación. En la mayoría de los casos será un navegador web como Chrome, Firefox, Edge o Safari.

El cliente se encarga de mostrar la interfaz, permitir que la persona interactúe con la página, enviar peticiones al servidor y representar la respuesta recibida. Cuando vemos un formulario, hacemos clic en un enlace o consultamos una página, estamos utilizando el cliente.

Por ejemplo, si una persona escribe esta dirección en el navegador:

http://localhost:8080/saludo

el navegador actúa como cliente y solicita al servidor el recurso asociado a la ruta /saludo.

tip

En desarrollo, localhost hace referencia al propio ordenador. Cuando ejecutemos una aplicación Spring Boot en clase, muchas veces accederemos a ella desde el navegador usando una dirección como http://localhost:8080.

🟨 Qué es el servidor​

El servidor es el sistema que recibe las peticiones del cliente, ejecuta la lógica necesaria y devuelve una respuesta. En una aplicación web en entorno servidor, esa lógica se ejecuta en el servidor, no en el navegador.

En nuestro caso, trabajaremos principalmente con Spring Boot, que nos permitirá crear aplicaciones web con Java. Cuando lancemos una aplicación Spring Boot, esta quedará escuchando peticiones en un puerto, normalmente el 8080, y responderá según las rutas que hayamos programado.

Dicho de forma sencilla: el navegador pregunta y el servidor responde.

Cliente:  Quiero ver la página /saludo
Servidor: Aquí tienes la respuesta para /saludo

Esta respuesta puede ser una página HTML, un texto sencillo, un error, una redirección o, más adelante, datos en formato JSON. En esta unidad nos centraremos en las respuestas más básicas para entender bien el funcionamiento inicial.

🟧 Comunicación entre cliente y servidor​

La comunicación entre cliente y servidor no se hace de cualquier manera. Ambos necesitan seguir unas reglas comunes. En la web, esas reglas las proporciona principalmente el protocolo HTTP.

HTTP permite que el cliente envíe una petición y que el servidor devuelva una respuesta. Cada vez que visitamos una página web, cargamos una imagen, enviamos un formulario o pulsamos sobre un enlace, se produce una comunicación de este tipo.

2️⃣ Frontend y backend​

Cuando hablamos de una aplicación web, es habitual distinguir entre frontend y backend. El frontend es la parte que se ejecuta en el navegador y con la que interactúa la persona usuaria. El backend es la parte que se ejecuta en el servidor y se encarga de procesar peticiones, aplicar lógica y generar respuestas.

🟩 El frontend: lo que se ejecuta en el cliente​

El término frontend se utiliza para referirse a la parte de la aplicación que se ejecuta en el cliente y con la que interactúa directamente la persona usuaria. En una página web tradicional, el frontend está formado principalmente por HTML, CSS y JavaScript.

HTML define la estructura de la página, CSS se encarga de la presentación visual y JavaScript permite añadir comportamiento en el navegador. Por ejemplo, validar un campo antes de enviar un formulario, mostrar u ocultar un menú o actualizar parte de una pantalla sin recargar toda la página.

<button onclick="alert('Hola desde el navegador')">
  Saludar
</button>
en este ejemplo

En este ejemplo, el código JavaScript se ejecuta en el navegador. El servidor no interviene cuando se muestra el mensaje de alerta. Por eso decimos que este comportamiento pertenece al lado del cliente.

Este tipo de código puede mejorar mucho la experiencia de uso, pero no sustituye a la lógica del servidor. Por ejemplo, aunque un formulario valide datos en el navegador, el servidor también deberá comprobarlos, porque el cliente puede ser manipulado por la persona usuaria.

🟨 El backend: lo que se ejecuta en el servidor​

El backend es la parte de la aplicación que se ejecuta en el servidor. Aquí se procesan las peticiones, se aplican reglas de negocio, se preparan respuestas y, más adelante, se accederá a bases de datos o servicios externos.

En este módulo vamos a trabajar el backend principalmente con Java y Spring Boot. Eso significa que escribiremos código Java que se ejecutará en el servidor y que responderá a las peticiones realizadas desde el navegador.

Un ejemplo muy básico de código de servidor en Spring Boot podría ser este:

@Controller
public class SaludoController {

    @GetMapping("/saludo")
    @ResponseBody
    public String saludar() {
        return "Hola desde el servidor";
    }
}
en este ejemplo

La anotación @Controller indica que esta clase puede atender peticiones web. Con @GetMapping("/saludo") asociamos el método saludar() a la ruta /saludo. La anotación @ResponseBody indica que el texto devuelto por el método será la respuesta enviada directamente al navegador, no el nombre de una vista Thymeleaf.

Si accedemos desde el navegador a http://localhost:8080/saludo, el cliente enviará una petición al servidor y Spring Boot ejecutará el método correspondiente. Después, el servidor devolverá el texto Hola desde el servidor como respuesta.

aviso

No debemos confundir el código que se ejecuta en el navegador con el código que se ejecuta en el servidor. Aunque ambos formen parte de la misma aplicación web, se ejecutan en lugares distintos y tienen responsabilidades diferentes.

3️⃣ Qué papel tiene HTTP​

🟩 HTTP como protocolo de comunicación​

HTTP significa HyperText Transfer Protocol. Es el protocolo que permite que un cliente y un servidor intercambien información en la web.

Cuando el navegador solicita una página, realmente está enviando una petición HTTP. Esa petición contiene información como la ruta solicitada, el método utilizado y algunas cabeceras. El servidor analiza esa petición, decide qué debe hacer y devuelve una respuesta HTTP.

De forma simplificada, el flujo sería este:

1. El usuario escribe una dirección en el navegador.
2. El navegador envía una petición HTTP al servidor.
3. El servidor recibe la petición y la procesa.
4. El servidor genera una respuesta HTTP.
5. El navegador recibe la respuesta y la muestra.

Aunque el proceso real puede incluir más pasos, esta secuencia es suficiente para empezar a entender cómo funciona la web desde el punto de vista del desarrollo en servidor.

🟨 Peticiones y respuestas​

Una petición HTTP es el mensaje que envía el cliente al servidor. Por ejemplo, cuando pedimos ver una página, descargar una imagen o enviar un formulario.

Una respuesta HTTP es el mensaje que devuelve el servidor al cliente. Puede contener una página HTML, un archivo, un mensaje de error o datos en otro formato.

GET /saludo HTTP/1.1
Host: localhost:8080
en este ejemplo

Este ejemplo representa, de forma simplificada, una petición HTTP. El método GET indica que el cliente quiere obtener un recurso. La ruta /saludo indica qué recurso se solicita. Host indica el servidor al que se está haciendo la petición.

En las próximas páginas de la unidad estudiaremos las peticiones y respuestas con más detalle, pero por ahora lo importante es quedarse con esta idea: cada interacción con una web suele implicar una petición y una respuesta.

🟧 HTTP no guarda estado por sí mismo​

Una característica importante de HTTP es que, por sí mismo, es un protocolo sin estado. Esto significa que cada petición se trata de forma independiente.

Por ejemplo, si una persona visita primero /saludo y después /perfil, el protocolo HTTP no recuerda automáticamente que ambas peticiones pertenecen a la misma persona. Más adelante veremos que existen mecanismos como las sesiones y las cookies para mantener cierta información entre peticiones, pero todavía no entraremos en ese nivel de detalle.

info

En esta unidad solo necesitamos entender que HTTP permite comunicar cliente y servidor. La gestión del estado, las sesiones y la seguridad se estudiarán más adelante.

4️⃣ Ejecución en cliente y ejecución en servidor​

🟩 Diferencia básica​

Uno de los objetivos principales de esta unidad es diferenciar claramente los modelos de ejecución de código en el cliente y en el servidor.

El código que se ejecuta en el cliente llega al navegador y se ejecuta en el ordenador o dispositivo de la persona usuaria. El ejemplo más claro es JavaScript ejecutado dentro del navegador.

El código que se ejecuta en el servidor permanece en el servidor. El navegador no recibe el código Java de nuestra aplicación Spring Boot, sino únicamente la respuesta que ese código genera.

Código JavaScript  → se ejecuta en el navegador
Código Java/Spring Boot → se ejecuta en el servidor

Esta diferencia es fundamental. El usuario puede ver el HTML, el CSS y parte del JavaScript que recibe su navegador, pero no puede ver directamente el código Java del servidor.

🟨 Ejemplo comparativo​

Imaginemos una página que muestra un saludo con el nombre de una persona.

En el cliente, podríamos tener JavaScript que cambia el contenido de una página ya cargada:

<p id="mensaje"></p>

<script>
  document.getElementById("mensaje").textContent = "Hola, Ana";
</script>
en este ejemplo

Este código se ejecuta en el navegador. La página ya ha llegado al cliente y JavaScript modifica el contenido del documento HTML desde el propio navegador.

En el servidor, podríamos tener código Java que genera la respuesta antes de enviarla:

@GetMapping("/saludo")
@ResponseBody
public String saludar() {
    return "Hola, Ana";
}
en este ejemplo

Este método se ejecuta en el servidor. El navegador solo recibe el resultado, es decir, el texto Hola, Ana. No recibe el código Java que ha producido esa respuesta.

Los dos enfoques pueden convivir en una misma aplicación web. De hecho, muchas aplicaciones modernas combinan lógica en el servidor y comportamiento en el cliente. Lo importante es saber distinguir qué responsabilidad corresponde a cada parte.

🟧 Error frecuente​

Un error habitual al empezar es pensar que todo el código de una aplicación web se ejecuta en el navegador porque el resultado se ve allí. Sin embargo, que el resultado se muestre en el navegador no significa que todo se haya ejecutado en el cliente.

Por ejemplo, si una aplicación consulta datos en el servidor, comprueba permisos o genera una página HTML con información personalizada, esa lógica pertenece al backend, aunque el resultado final se vea en el navegador.

aviso

Ver una página en el navegador no significa que la página se haya construido completamente en el navegador. Muchas veces el servidor ha generado parte o toda la respuesta antes de enviarla.

5️⃣ Comprobación rápida​

🟩 Preguntas para repasar​

Antes de continuar, conviene comprobar que las ideas principales están claras:

  1. ¿Qué programa suele actuar como cliente en una aplicación web?
  2. ¿Qué función cumple el servidor?
  3. ¿Qué protocolo permite la comunicación básica entre cliente y servidor?
  4. ¿Dónde se ejecuta normalmente JavaScript?
  5. ¿Dónde se ejecuta el código Java de una aplicación Spring Boot?
  6. ¿El navegador recibe el código Java del servidor o solo la respuesta generada?

🟨 Mini actividad no evaluable​

Esta actividad sirve para afianzar conceptos y no requiere entrega.

Abre el navegador y accede a varias páginas web que utilices normalmente. Para cada una, intenta identificar mentalmente estos elementos:

  • quién actúa como cliente.
  • qué servidor podría estar respondiendo.
  • qué parte ves como frontend.
  • qué acciones crees que requieren lógica de backend.
  • qué información viaja como petición y qué información vuelve como respuesta.

No hace falta conocer la implementación real de esas páginas. El objetivo es empezar a pensar como desarrolladores y no solo como usuarios.

tip

Cuando uses una aplicación web, pregúntate: “¿esto lo está resolviendo mi navegador o ha tenido que intervenir el servidor?”. Esa pregunta será muy útil durante todo el módulo.
