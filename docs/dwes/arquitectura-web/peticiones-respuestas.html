Peticiones y respuestas HTTP

En el apartado anterior vimos que una aplicación web funciona mediante una comunicación entre un cliente y un servidor. El cliente suele ser el navegador, y el servidor es el sistema que recibe la solicitud, la procesa y devuelve una respuesta.

Ahora vamos a fijarnos en el mecanismo que hace posible esa comunicación: HTTP.

HTTP es el protocolo que utilizan los navegadores y los servidores web para intercambiar información. Cada vez que abrimos una página, pulsamos un enlace, enviamos un formulario o cargamos una imagen desde una web, se produce una comunicación basada en peticiones y respuestas.

Idea principal

HTTP funciona como una conversación ordenada: el cliente realiza una petición y el servidor devuelve una respuesta.

1️⃣ Qué es HTTP​

HTTP significa HyperText Transfer Protocol, es decir, protocolo de transferencia de hipertexto. Aunque su nombre hace referencia al hipertexto, actualmente se utiliza para transferir muchos tipos de recursos: páginas HTML, imágenes, hojas de estilo CSS, archivos JavaScript, datos en JSON, documentos PDF y otros contenidos.

Cuando escribimos una dirección en el navegador, por ejemplo:

https://www.wikipedia.org/

el navegador prepara una petición HTTP y la envía al servidor correspondiente. El servidor recibe esa petición, decide qué debe hacer y devuelve una respuesta.

🟩 Una petición no es solo una URL​

Es habitual pensar que una petición consiste únicamente en escribir una dirección, pero internamente contiene más información. El navegador no solo indica qué recurso quiere, sino que también puede enviar datos adicionales, como el tipo de navegador, el idioma preferido o información relacionada con la sesión del usuario.

En esta unidad no vamos a analizar todos esos detalles, pero sí conviene quedarse con una idea clara: una petición HTTP es una solicitud estructurada que el cliente envía al servidor.

🟨 La respuesta tampoco es solo la página visible​

Cuando el servidor responde, el navegador puede mostrar una página, descargar un archivo o interpretar otros datos. La respuesta incluye el contenido solicitado, pero también información sobre si todo ha ido bien, si ha habido un error o si el recurso se encuentra en otra dirección.

Por eso, una página web puede parecer sencilla en pantalla, pero detrás puede haber muchas respuestas distintas: una para el HTML principal, otras para las imágenes, otras para los estilos CSS y otras para los scripts.

tip

Una buena forma de entender HTTP es imaginarlo como un diálogo breve: el navegador pregunta y el servidor responde.

2️⃣ La petición HTTP​

Una petición HTTP es el mensaje que envía el cliente al servidor para solicitar un recurso o enviar información.

Por ejemplo, cuando el navegador solicita la página principal de un sitio web, está diciendo algo parecido a esto:

Quiero obtener la página principal de este sitio web.

En una petición HTTP suelen aparecer varios elementos importantes.

🟩 Método HTTP​

El método indica qué quiere hacer el cliente. En una petición HTTP no solo importa la ruta solicitada, sino también la intención de la petición: obtener información, enviar datos, modificar un recurso o eliminarlo.

En esta unidad veremos los métodos de forma básica, sin entrar todavía en el diseño completo de APIs REST. Lo importante ahora es reconocer que el método forma parte de la petición y que ayuda al servidor a interpretar qué se quiere hacer.

MétodoUso habitualEjemplo sencillo
GETSolicitar información al servidor.Abrir una página web o consultar un listado.
POSTEnviar datos al servidor para que sean procesados.Enviar un formulario de contacto.
PUTSustituir o actualizar completamente un recurso.Reemplazar todos los datos de un producto.
PATCHActualizar parcialmente un recurso.Cambiar solo el precio de un producto.
DELETEEliminar un recurso.Borrar una noticia o un producto.
HEADSolicitar solo las cabeceras de la respuesta, sin el contenido.Comprobar si un recurso existe.
OPTIONSConsultar qué métodos admite un recurso.Saber si una ruta permite GET, POST o DELETE.

En una navegación web normal veremos sobre todo peticiones GET. Cuando enviemos formularios, será habitual encontrar peticiones POST. Otros métodos como PUT, PATCH o DELETE aparecerán con más sentido cuando trabajemos APIs REST más adelante.

aviso

No conviene memorizar los métodos HTTP como una lista aislada. Lo importante es entender su intención: no es lo mismo pedir información que enviar datos, actualizar un recurso o eliminarlo.

🟨 Ruta o recurso solicitado​

La ruta indica qué recurso se está solicitando dentro del servidor.

Por ejemplo, en esta dirección:

https://www.ejemplo.com/productos

la parte /productos indica la ruta solicitada. En una aplicación Spring Boot, más adelante podremos crear un controlador que atienda esa ruta.

Un ejemplo sencillo sería:

@GetMapping("/productos")
@ResponseBody
public String productos() {
    return "Listado de productos";
}
en este ejemplo

En este ejemplo, @GetMapping("/productos") indica que este método responderá a peticiones HTTP de tipo GET dirigidas a la ruta /productos. La anotación @ResponseBody indica que el texto devuelto se enviará directamente como respuesta al navegador, en lugar de buscar una plantilla o vista.

🟧 Cabeceras de la petición​

Las cabeceras aportan información adicional sobre la petición. Por ejemplo, pueden indicar el tipo de navegador, el idioma preferido, el formato de respuesta que se espera o datos relacionados con la autenticación.

No necesitamos dominarlas todavía, pero sí reconocer que existen y que forman parte del intercambio entre cliente y servidor.

Un ejemplo simplificado de petición podría verse así:

GET /productos HTTP/1.1
Host: www.ejemplo.com
Accept-Language: es
en este ejemplo

La primera línea indica que el cliente quiere hacer una petición GET a la ruta /productos. La cabecera Host indica el servidor al que se dirige la petición y Accept-Language informa de que el cliente prefiere contenido en español.

3️⃣ La respuesta HTTP​

La respuesta HTTP es el mensaje que devuelve el servidor después de recibir y procesar una petición.

Una respuesta puede contener una página HTML, una imagen, un archivo CSS, un documento o incluso un mensaje de error. Además del contenido, incluye información sobre el resultado de la petición.

🟩 Código de estado​

El código de estado indica si la petición se ha resuelto correctamente o si ha ocurrido algún problema.

Algunos códigos habituales son:

CódigoSignificado básico
200 OKLa petición se ha procesado correctamente.
301 / 302El recurso se ha redirigido a otra dirección.
400 Bad RequestLa petición enviada no es correcta.
403 ForbiddenEl acceso no está permitido.
404 Not FoundEl recurso solicitado no existe.
500 Internal Server ErrorSe ha producido un error en el servidor.

El código más conocido suele ser el 404, que aparece cuando intentamos acceder a una ruta que no existe.

🟨 Contenido de la respuesta​

El contenido de la respuesta depende del recurso solicitado. Si pedimos una página, lo normal es recibir HTML. Si pedimos una imagen, recibiremos los datos de esa imagen. Si pedimos una hoja de estilos, recibiremos CSS.

Un ejemplo simplificado de respuesta HTTP podría ser:

HTTP/1.1 200 OK
Content-Type: text/html

<html>
  <body>
    <h1>Listado de productos</h1>
  </body>
</html>
en este ejemplo

La primera línea indica que la petición se ha resuelto correctamente mediante el código 200 OK. La cabecera Content-Type indica que el contenido devuelto es HTML. Después aparece el cuerpo de la respuesta, que es lo que el navegador podrá interpretar para mostrar la página.

🟧 Tipo de contenido​

El servidor debe indicar qué tipo de contenido está enviando. Esto permite que el navegador sepa cómo interpretarlo.

Por ejemplo:

Tipo de contenidoUso
text/htmlPágina HTML.
text/cssHoja de estilos CSS.
application/javascriptCódigo JavaScript.
image/pngImagen PNG.
application/jsonDatos en formato JSON.

En esta unidad nos centraremos principalmente en respuestas HTML y texto sencillo. Más adelante, cuando trabajemos APIs REST, veremos con más detalle el formato JSON.

4️⃣ Una página web suele provocar varias peticiones​

Cuando escribimos una dirección en el navegador, puede parecer que solo se realiza una petición, pero no suele ser así.

Imagina que el navegador solicita una página HTML. Esa página puede hacer referencia a varios recursos adicionales:

<link rel="stylesheet" href="/css/estilos.css">
<script src="/js/app.js"></script>
<img src="/img/logo.png" alt="Logo de la aplicación">
en este ejemplo

El navegador primero solicita la página HTML. Al leer ese HTML, descubre que necesita una hoja de estilos, un archivo JavaScript y una imagen. Entonces realiza nuevas peticiones HTTP para obtener esos recursos adicionales.

Por eso, al abrir las herramientas de desarrollo del navegador y revisar la pestaña Red o Network, veremos varias filas. Cada fila representa una petición realizada por el navegador.

🟩 Ejemplo guiado​

Supongamos que visitamos una tienda online sencilla:

https://tienda.ejemplo.com/productos

El proceso podría ser el siguiente:

  1. El navegador solicita la ruta /productos.
  2. El servidor procesa la petición.
  3. El servidor devuelve una página HTML con el listado de productos.
  4. El navegador interpreta el HTML.
  5. El navegador solicita los archivos CSS, imágenes y JavaScript necesarios.
  6. La página termina de mostrarse en pantalla.

Aunque el usuario solo ha escrito una dirección, internamente se han realizado varias comunicaciones entre cliente y servidor.

Idea principal

Una página web no siempre llega al navegador como un único recurso. Normalmente se compone de HTML, CSS, JavaScript, imágenes y otros archivos que se solicitan mediante peticiones HTTP.

5️⃣ HTTP en una aplicación Spring Boot​

Cuando trabajamos con Spring Boot, nuestra aplicación actúa como parte del servidor. Su trabajo será recibir peticiones HTTP, decidir qué código debe ejecutarse y generar una respuesta.

Por ejemplo, si el navegador solicita esta ruta:

http://localhost:8080/saludo

podríamos tener un controlador como este:

@Controller
public class SaludoController {

    @GetMapping("/saludo")
    @ResponseBody
    public String saludo() {
        return "Hola desde Spring Boot";
    }
}
en este ejemplo

@Controller indica que esta clase contiene métodos capaces de responder a peticiones web. @GetMapping("/saludo") asocia el método saludo() con la ruta /saludo. Como usamos @ResponseBody, el texto Hola desde Spring Boot se envía directamente como respuesta HTTP al navegador.

En este caso, el flujo sería:

Navegador  --->  GET /saludo  --->  Spring Boot
Navegador  <---  Hola desde Spring Boot  <---  Spring Boot

Este ejemplo es muy simple, pero muestra la base de todo lo que haremos después. Más adelante, en lugar de devolver solo texto, devolveremos vistas HTML generadas con Thymeleaf.

aviso

Cuando queramos devolver una vista Thymeleaf, no debemos usar @ResponseBody, porque entonces Spring Boot enviaría el texto literalmente en vez de buscar una plantilla HTML.

6️⃣ Errores frecuentes al empezar​

Al principio es normal confundir algunos conceptos relacionados con HTTP. Conviene aclararlos desde el principio.

🟩 Confundir URL con petición​

La URL es la dirección que escribimos o visitamos. La petición HTTP es el mensaje completo que el navegador envía al servidor utilizando esa dirección y otros datos adicionales.

🟨 Pensar que una página es un único archivo​

Una página web puede necesitar muchos recursos. El HTML principal es solo una parte. Además, pueden cargarse imágenes, estilos, fuentes, scripts y otros elementos.

🟧 Creer que todos los errores son iguales​

No es lo mismo un error 404 que un error 500. El primero suele indicar que la ruta no existe. El segundo indica que el servidor ha tenido un problema al procesar la petición.

🟥 No distinguir entre cliente y servidor​

El navegador ejecuta el código del lado cliente, como HTML, CSS y JavaScript. La aplicación Spring Boot se ejecuta en el servidor y responde a las peticiones que recibe.

7️⃣ Actividad no evaluable: observa peticiones reales​

Esta actividad sirve para comprobar cómo se producen peticiones y respuestas HTTP al visitar una página web real. No es una actividad evaluable y no requiere entrega.

🟩 Objetivo​

Observar desde el navegador que una página web genera varias peticiones HTTP y que cada una recibe una respuesta del servidor.

🟨 Página de trabajo​

Abre el navegador y accede a una página sencilla, por ejemplo:

https://www.wikipedia.org/

También puedes usar otra página indicada por el profesor.

🟧 Desarrollo​

Abre las herramientas de desarrollo del navegador:

F12 → Red / Network

Después, recarga la página:

Ctrl + R

Observa las peticiones que aparecen. No hace falta entender todos los detalles todavía. En esta actividad solo interesa reconocer que el navegador ha solicitado varios recursos y que el servidor ha respondido.

🟥 Preguntas de comprobación​

Responde en tu cuaderno o coméntalo con un compañero:

  1. ¿Qué dirección has escrito en el navegador?
  2. ¿Cuál es la petición principal de la página?
  3. ¿Qué código de estado aparece en esa petición?
  4. ¿Qué otros recursos se cargan además del HTML?
  5. ¿Aparece alguna imagen, hoja de estilos o archivo JavaScript?
  6. ¿Por qué crees que una sola página puede generar varias peticiones?

🟪 Puesta en común​

Después de observar la pestaña de red, se comentarán las respuestas en clase. El objetivo es construir una explicación sencilla del proceso:

El navegador solicita la página principal. El servidor responde con HTML.
Después, el navegador realiza nuevas peticiones para cargar otros recursos
necesarios, como imágenes, estilos o scripts.
tip

No te preocupes si aparecen muchas filas en la pestaña de red. En este momento no buscamos analizarlo todo, sino empezar a reconocer el patrón petición-respuesta.

8️⃣ Resumen final​

HTTP es la base de la comunicación en la Web. Cada interacción entre un navegador y un servidor se organiza mediante una petición y una respuesta. El cliente solicita un recurso, el servidor lo procesa y devuelve una respuesta con un código de estado, cabeceras y, normalmente, un contenido.

En Spring Boot, los controladores serán los encargados de recibir esas peticiones y generar respuestas. Por ahora empezaremos con respuestas sencillas, pero esta misma idea nos servirá más adelante para trabajar con vistas Thymeleaf, formularios y APIs.
