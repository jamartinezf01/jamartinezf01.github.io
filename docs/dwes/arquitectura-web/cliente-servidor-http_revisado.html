Cliente, servidor y HTTP

Cuando entramos en una página web parece que todo ocurre dentro del navegador. Escribimos una dirección, pulsamos Intro y aparece una página. Sin embargo, detrás de esa acción existe una comunicación entre varios elementos: un cliente, un servidor y un protocolo que permite que ambos se entiendan.

En este primer apartado vamos a construir una visión general del funcionamiento de una aplicación web. Más adelante analizaremos con detalle cómo están formadas las peticiones y las respuestas HTTP.

Idea principal

Una aplicación web funciona gracias a la comunicación entre un cliente y un servidor. El cliente solicita un recurso y el servidor procesa esa petición y devuelve una respuesta.

1️⃣ El modelo cliente-servidor​

🟩 Qué es el cliente​

En una aplicación web, el cliente es el programa que utiliza la persona usuaria para acceder a la aplicación. En la mayoría de los casos será un navegador web como Chrome, Firefox, Edge o Safari.

El cliente se encarga, entre otras tareas, de:

  • solicitar recursos al servidor.
  • mostrar la información recibida.
  • permitir la interacción con la aplicación.
  • enviar datos cuando la persona usuaria realiza determinadas acciones.

Por ejemplo, cuando escribimos una dirección en el navegador, hacemos clic en un enlace o enviamos un formulario, el cliente inicia una comunicación con el servidor.

🟨 Qué es el servidor​

El servidor es el sistema que recibe las peticiones del cliente, las procesa y genera una respuesta.

Dependiendo de la aplicación, el servidor puede realizar tareas muy diferentes:

  • localizar y devolver un archivo.
  • ejecutar lógica de la aplicación.
  • consultar información almacenada.
  • comprobar determinados datos.
  • generar una respuesta diferente según la petición recibida.

Dicho de forma sencilla:

Cliente:  Quiero este recurso.
Servidor: Recibo la petición, la proceso y te devuelvo una respuesta.

El cliente y el servidor tienen, por tanto, responsabilidades distintas, aunque ambos formen parte de la misma aplicación web.

2️⃣ Frontend y backend​

Cuando hablamos de una aplicación web, es habitual distinguir entre frontend y backend.

El frontend corresponde a la parte con la que interactúa directamente la persona usuaria y que se ejecuta principalmente en el cliente. El backend corresponde a la parte que se ejecuta en el servidor y se encarga de procesar las peticiones y generar las respuestas.

🟩 El frontend​

En una página web tradicional, el frontend está formado principalmente por HTML, CSS y JavaScript.

Cada tecnología cumple una función diferente:

  • HTML define la estructura del contenido.
  • CSS controla su presentación.
  • JavaScript permite añadir comportamiento e interacción en el navegador.

Por ejemplo:

<button onclick="alert('Hola desde el navegador')">
  Saludar
</button>
en este ejemplo

El código JavaScript asociado al botón se ejecuta en el navegador. Al pulsarlo se muestra un mensaje sin necesidad de que el servidor intervenga en esa acción concreta.

🟨 El backend​

El backend es la parte de la aplicación que se ejecuta en el servidor.

Entre sus responsabilidades habituales se encuentran:

  • recibir y procesar peticiones.
  • aplicar la lógica de la aplicación.
  • acceder a datos o servicios.
  • comprobar información recibida.
  • generar la respuesta que se enviará al cliente.

El navegador no necesita conocer el código que se ejecuta en el servidor. Solo recibe el resultado generado por ese procesamiento.

aviso

Que el resultado de una operación aparezca en el navegador no significa que todo el trabajo se haya realizado en el cliente. Parte del procesamiento puede haberse realizado previamente en el servidor.

3️⃣ Qué papel tiene HTTP​

🟩 HTTP como protocolo de comunicación​

HTTP significa HyperText Transfer Protocol y es el protocolo que permite intercambiar información entre clientes y servidores en la Web.

Su funcionamiento se basa en dos mensajes fundamentales:

petición → respuesta

El cliente inicia la comunicación enviando una petición HTTP. El servidor recibe esa petición, la procesa y devuelve una respuesta HTTP.

Por ejemplo, una petición muy simplificada podría ser:

GET /saludo HTTP/1.1
Host: ejemplo.com
en este ejemplo

GET indica la acción que quiere realizar el cliente y /saludo identifica el recurso solicitado. La cabecera Host indica el servidor al que se dirige la petición.

En los siguientes apartados veremos con más detalle los métodos, las rutas, las cabeceras y el resto de elementos que pueden formar parte de una petición.

Una posible respuesta podría comenzar así:

HTTP/1.1 200 OK
Content-Type: text/html

El código 200 indica que la petición se ha procesado correctamente. Más adelante estudiaremos otros códigos de estado y veremos cómo interpretar las distintas respuestas que puede devolver un servidor.

🟨 El ciclo petición-respuesta​

De forma simplificada, cuando accedemos a un recurso web ocurre lo siguiente:

  1. La persona usuaria realiza una acción en el navegador.
  2. El navegador genera una petición HTTP.
  3. La petición llega al servidor.
  4. El servidor procesa la petición.
  5. El servidor genera una respuesta HTTP.
  6. El navegador recibe la respuesta y procesa su contenido.

Este proceso se repite continuamente mientras utilizamos una aplicación web.

tip

Una misma página puede provocar varias peticiones HTTP. Además del documento HTML, el navegador puede necesitar solicitar hojas de estilo, archivos JavaScript, imágenes u otros recursos.

🟧 HTTP no guarda estado por sí mismo​

HTTP es un protocolo sin estado. Esto significa que, por sí mismo, cada petición se trata de forma independiente.

Si un cliente realiza varias peticiones consecutivas, HTTP no mantiene automáticamente información sobre las anteriores.

Más adelante estudiaremos mecanismos que permiten conservar información entre distintas peticiones. Por ahora, basta con comprender que cada comunicación HTTP parte de una petición y genera una respuesta.

4️⃣ Cliente y servidor: responsabilidades diferentes​

Una aplicación web puede combinar trabajo realizado en el cliente y trabajo realizado en el servidor.

Por ejemplo:

CLIENTE                         SERVIDOR

Mostrar la interfaz            Procesar peticiones
Ejecutar JavaScript            Aplicar lógica
Recoger datos                  Consultar información
Enviar peticiones       →      Generar respuestas
Procesar respuestas     ←      Devolver resultados

Esta separación será importante durante todo el módulo. Antes de analizar una funcionalidad conviene preguntarse dónde se está ejecutando realmente cada parte del código.

Abre una página web que utilices habitualmente y piensa qué acciones pueden resolverse únicamente en el navegador y cuáles necesitan comunicarse con un servidor.

No es necesario conocer cómo está implementada realmente la aplicación. El objetivo es empezar a identificar las responsabilidades del cliente y del servidor.

tip

Cuando utilices una aplicación web, acostúmbrate a preguntarte: ¿esto puede resolverlo el navegador por sí solo o necesita pedir algo al servidor?
