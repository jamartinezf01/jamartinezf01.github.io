Servidores web y servidores de aplicaciones

Cuando visitamos una página web solemos pensar solo en el navegador y en la dirección que escribimos. Sin embargo, en el otro extremo de la comunicación hay una parte fundamental: el servidor.

En una aplicación web en entorno servidor, no basta con guardar archivos HTML, CSS o imágenes. Muchas veces necesitamos ejecutar código, tomar decisiones, generar contenido dinámico o coordinar distintas partes de una aplicación. Para entender esto, conviene diferenciar entre servidor web, servidor de aplicaciones y aplicación web.

Idea principal

Un servidor web se encarga principalmente de recibir peticiones HTTP y devolver recursos. Un servidor de aplicaciones permite ejecutar código de servidor y gestionar aplicaciones más complejas. En Spring Boot, muchas de estas piezas vienen integradas para facilitar el desarrollo.

1️⃣ Qué entendemos por servidor en una aplicación web​

La palabra servidor puede resultar un poco confusa porque se utiliza para referirse a varias cosas distintas. A veces hablamos de servidor para referirnos a una máquina física o virtual. Otras veces hablamos de servidor para referirnos al programa que atiende peticiones web.

Por ejemplo, cuando decimos que una página está “en un servidor”, podemos estar hablando de:

  • un ordenador conectado a Internet.
  • un servicio contratado en la nube.
  • un programa que escucha peticiones HTTP.
  • una aplicación web que se ejecuta dentro de ese entorno.

En esta unidad nos interesa sobre todo la idea funcional: el servidor es la parte que recibe peticiones del cliente, las procesa y devuelve respuestas.

🟩 Servidor como máquina​

Desde el punto de vista físico, un servidor puede ser un ordenador preparado para estar encendido y disponible durante mucho tiempo. En un entorno real, puede estar en un centro de datos, en una empresa o en una plataforma en la nube.

No necesitamos ver ahora cómo se administra una máquina de servidor, pero sí debemos entender que una aplicación web necesita ejecutarse en algún lugar para poder atender peticiones.

🟨 Servidor como programa​

Desde el punto de vista del software, un servidor es un programa que permanece a la espera de peticiones. Cuando recibe una petición, la procesa y devuelve una respuesta.

Un ejemplo sencillo sería:

Cliente: quiero acceder a /contacto
Servidor: recibo la petición, localizo el recurso y devuelvo una respuesta
en este ejemplo

El servidor no “adivina” lo que quiere el usuario. Recibe una petición concreta, normalmente asociada a una ruta, y decide qué respuesta debe generar. Esa respuesta puede ser un archivo HTML, una imagen, un error, una redirección o una página creada dinámicamente.

🟧 Servidor como entorno de ejecución​

En programación web en entorno servidor, además de servir archivos, necesitamos ejecutar código. Por ejemplo, una aplicación puede decidir qué mensaje mostrar, qué datos consultar o qué vista devolver.

Ahí aparece la diferencia entre limitarse a servir archivos estáticos y ejecutar una aplicación web con lógica propia.

2️⃣ El servidor web​

Un servidor web es el software encargado de atender peticiones HTTP y devolver respuestas. Su función principal es actuar como puerta de entrada a los recursos web.

Cuando el navegador pide una página, una imagen o una hoja de estilos, el servidor web recibe esa petición y responde con el recurso correspondiente, si existe y se puede entregar.

🟩 Recursos estáticos​

Un servidor web puede devolver recursos que ya existen como archivos. Estos recursos se llaman estáticos porque su contenido no cambia al ejecutarse una lógica de servidor.

Algunos ejemplos son:

/index.html
/estilos.css
/logo.png
/app.js

Si el navegador solicita /logo.png, el servidor puede buscar ese archivo y devolverlo directamente.

🟨 Peticiones y respuestas​

El servidor web trabaja con el modelo de petición y respuesta que vimos en el apartado anterior. El navegador solicita un recurso y el servidor responde.

GET /estilos.css HTTP/1.1

Una posible respuesta sería:

HTTP/1.1 200 OK
Content-Type: text/css
en este ejemplo

En este ejemplo, el navegador solicita una hoja de estilos. Si el recurso existe y se puede entregar, el servidor responde correctamente. El código 200 OK indica que la petición se ha resuelto con éxito.

🟧 Ejemplos de servidores web​

Existen distintos servidores web utilizados en entornos reales. Algunos de los más conocidos son Apache HTTP Server, Nginx o Microsoft IIS.

En esta unidad no vamos a configurarlos, pero conviene saber que existen porque en aplicaciones reales pueden colocarse delante de una aplicación de servidor para gestionar tráfico, seguridad, certificados o recursos estáticos.

aviso

No debemos confundir conocer el concepto con administrar un servidor real. En este punto solo necesitamos entender qué papel cumple un servidor web dentro de la arquitectura.

3️⃣ El servidor de aplicaciones​

Un servidor de aplicaciones va un paso más allá. No se limita a entregar archivos, sino que proporciona un entorno donde se puede ejecutar una aplicación web con lógica de servidor.

En el caso de Java, históricamente han existido servidores de aplicaciones como Tomcat, Jetty, WildFly o GlassFish. Estos entornos permiten ejecutar aplicaciones Java que responden a peticiones web.

🟩 Qué aporta un servidor de aplicaciones​

Un servidor de aplicaciones puede encargarse de tareas como:

  • ejecutar código en el servidor.
  • gestionar rutas y peticiones.
  • controlar sesiones de usuario.
  • integrar componentes de la aplicación.
  • conectar con otros servicios.
  • devolver respuestas generadas dinámicamente.

No todas estas funciones se estudiarán ahora en profundidad. Algunas, como las sesiones o la seguridad, aparecerán en unidades posteriores.

🟨 Diferencia principal con un servidor web​

La diferencia esencial es que el servidor web está muy orientado a recibir peticiones HTTP y devolver recursos, mientras que el servidor de aplicaciones está pensado para ejecutar lógica de aplicación.

Por ejemplo, un servidor web puede devolver directamente este archivo:

/contacto.html

Pero una aplicación de servidor podría recibir esta petición:

/productos

y generar una página distinta según los productos disponibles, el usuario que accede o los datos que maneje la aplicación.

🟧 Una comparación sencilla​

Podemos imaginar el servidor web como la recepción de un edificio. Recibe las solicitudes y las dirige al lugar adecuado. El servidor de aplicaciones sería la parte interna donde se realiza el trabajo: se consulta información, se aplican reglas y se prepara la respuesta.

tip

En proyectos pequeños o durante el aprendizaje, muchas piezas parecen estar juntas. Aun así, es importante distinguir los conceptos porque en proyectos reales pueden separarse en varios servicios o servidores.

4️⃣ Integración entre servidor web y servidor de aplicaciones​

En muchas arquitecturas reales, un servidor web y un servidor de aplicaciones trabajan juntos.

Una posibilidad habitual es que el servidor web reciba primero las peticiones del navegador. Si la petición es para un recurso estático, puede responder directamente. Si la petición requiere ejecutar código de la aplicación, la envía al servidor de aplicaciones.

🟩 Ejemplo conceptual​

Navegador
   |
   v
Servidor web
   |-- devuelve archivos estáticos: CSS, imágenes, JavaScript
   |
   v
Servidor de aplicaciones
   |-- ejecuta la aplicación y genera respuestas dinámicas
en este ejemplo

Este esquema separa dos responsabilidades. El servidor web puede encargarse de entregar recursos estáticos y recibir las peticiones externas. El servidor de aplicaciones ejecuta la lógica necesaria para construir respuestas dinámicas.

🟨 Por qué se separan en entornos reales​

Separar estas funciones puede aportar ventajas cuando una aplicación crece. Por ejemplo, permite optimizar la entrega de archivos estáticos, repartir carga, añadir certificados HTTPS, configurar reglas de seguridad o conectar varias aplicaciones.

En clase no empezaremos por esta arquitectura completa. Primero desarrollaremos aplicaciones sencillas con Spring Boot para entender bien las bases.

🟧 Qué ocurre durante el desarrollo​

Durante el desarrollo, lo normal es trabajar de forma más simple. Ejecutaremos la aplicación en nuestro equipo y accederemos a ella desde el navegador mediante una dirección como:

http://localhost:8080

En ese caso, nuestro propio ordenador hace de entorno de pruebas. El navegador será el cliente y la aplicación Spring Boot atenderá las peticiones.

5️⃣ Spring Boot y el servidor embebido​

Una de las ventajas de Spring Boot es que simplifica mucho el arranque de una aplicación web. En lugar de tener que instalar y configurar manualmente un servidor de aplicaciones externo desde el principio, Spring Boot puede incluir un servidor embebido.

Un servidor embebido es un servidor que va integrado dentro de la propia aplicación. Al ejecutar la aplicación, también se arranca el servidor que escuchará peticiones HTTP.

🟩 Qué significa servidor embebido​

Cuando creamos un proyecto Spring Boot web, normalmente se incluye un servidor como Tomcat embebido. Esto permite ejecutar la aplicación directamente desde IntelliJ IDEA Community o desde la terminal.

Por eso, al iniciar un proyecto Spring Boot, podemos ver mensajes parecidos a este:

Tomcat started on port 8080
Started AplicacionDw in ... seconds
en este ejemplo

El mensaje indica que Spring Boot ha arrancado la aplicación y que el servidor embebido está escuchando peticiones en el puerto 8080. A partir de ese momento, el navegador puede enviar peticiones a http://localhost:8080.

🟨 Ventajas para aprender​

Este enfoque es muy cómodo al empezar porque evita tener que instalar y configurar un servidor externo antes de escribir el primer controlador.

Nos permite centrarnos en lo importante:

  • entender las rutas.
  • crear controladores.
  • devolver respuestas.
  • conectar HTML con código Java.
  • observar qué ocurre en el navegador.

🟧 Cuidado con una confusión habitual​

Que Spring Boot incluya un servidor embebido no significa que el servidor “desaparezca”. Sigue existiendo un servidor que atiende peticiones HTTP. Lo que ocurre es que está integrado en la aplicación y se arranca automáticamente durante el desarrollo.

aviso

No debemos decir que Spring Boot sustituye a HTTP ni que elimina el servidor. Spring Boot nos facilita crear aplicaciones web en Java, pero sigue trabajando sobre el modelo cliente-servidor y sobre peticiones y respuestas HTTP.

http://localhost:8080/saludo

🟩 Relación con los controladores​

En los próximos apartados veremos que un controlador puede encargarse de responder a una ruta concreta. Por ahora, basta con entender que el servidor recibe la petición y que Spring Boot la dirige al código adecuado.

Un ejemplo muy básico sería:

@Controller
public class SaludoController {

    @GetMapping("/saludo")
    @ResponseBody
    public String saludo() {
        return "Hola desde Spring Boot";
    }
}
en este ejemplo

La anotación @Controller indica que esta clase puede atender peticiones web. @GetMapping("/saludo") asocia el método con la ruta /saludo cuando la petición usa el método GET. @ResponseBody hace que el texto devuelto se envíe directamente como respuesta al navegador, en lugar de buscar una vista HTML.

aviso

Cuando más adelante devolvamos una vista Thymeleaf, no usaremos @ResponseBody, porque en ese caso querremos que Spring Boot busque una plantilla HTML y genere una página como respuesta.

7️⃣ Errores frecuentes​

🟩 Pensar que el servidor es solo una máquina​

Un servidor puede ser una máquina, pero en desarrollo web muchas veces hablamos del programa o entorno que atiende peticiones. Es importante fijarse en el contexto.

🟨 Confundir servidor web y servidor de aplicaciones​

Un servidor web se asocia principalmente a HTTP y recursos web. Un servidor de aplicaciones ejecuta lógica de la aplicación. En proyectos reales pueden trabajar juntos.

🟧 Creer que Spring Boot no usa servidor​

Spring Boot sí usa servidor. La diferencia es que durante el desarrollo suele arrancar un servidor embebido automáticamente, lo que simplifica mucho el trabajo inicial.

🟥 Pensar que localhost es Internet​

Cuando usamos localhost, estamos accediendo a una aplicación que se está ejecutando en nuestro propio equipo. Es una forma de probar el proyecto antes de publicarlo en un entorno real.

8️⃣ Actividad no evaluable: identifica quién hace qué​

Esta actividad sirve para comprobar que has entendido las diferencias entre servidor web, servidor de aplicaciones y aplicación Spring Boot. No es evaluable y no requiere entrega.

🟩 Objetivo​

Relacionar cada elemento de una arquitectura web sencilla con su función principal.

🟨 Situación​

Imagina una aplicación web de una biblioteca. Una persona entra en el navegador y escribe:

http://localhost:8080/libros

La aplicación devuelve una página con un listado de libros.

🟧 Desarrollo​

Responde en tu cuaderno o coméntalo con un compañero:

  1. ¿Quién actúa como cliente?
  2. ¿Qué significa localhost:8080 en este ejemplo?
  3. ¿Qué papel tiene el servidor embebido de Spring Boot?
  4. ¿Qué parte de la aplicación decidirá qué respuesta se devuelve para /libros?
  5. Si la página incluye un archivo CSS y una imagen, ¿también se cargan mediante peticiones HTTP?
  6. ¿La respuesta de /libros sería necesariamente un archivo HTML fijo o podría generarse dinámicamente?

🟪 Comprobación final​

Antes de terminar, comprueba que sabes explicar estas ideas:

  • El servidor recibe peticiones HTTP.
  • Un servidor web puede entregar recursos estáticos.
  • Un servidor de aplicaciones permite ejecutar lógica de servidor.
  • Spring Boot suele utilizar un servidor embebido durante el desarrollo.
  • localhost:8080 permite probar la aplicación en nuestro propio equipo.
tip

La clave no es memorizar nombres de servidores, sino entender qué responsabilidad tiene cada parte dentro de la arquitectura.
