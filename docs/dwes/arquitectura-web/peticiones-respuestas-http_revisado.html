Peticiones y respuestas HTTP

En el apartado anterior vimos que una aplicación web funciona mediante una comunicación entre un cliente y un servidor.

Ahora vamos a observar esa comunicación con más detalle. Cuando un cliente necesita un recurso, envía una petición HTTP. El servidor la recibe, la procesa y devuelve una respuesta HTTP.

Idea principal

HTTP organiza la comunicación mediante dos mensajes: una petición, que viaja del cliente al servidor, y una respuesta, que viaja del servidor al cliente.

1️⃣ La petición HTTP​

Una petición HTTP es el mensaje que envía un cliente para solicitar un recurso o enviar información al servidor.

Aunque normalmente solo vemos una dirección en el navegador, internamente la petición contiene varios elementos.

🟩 Línea de petición​

La primera línea indica qué quiere hacer el cliente, qué recurso solicita y qué versión del protocolo utiliza.

Por ejemplo:

GET /productos HTTP/1.1

Podemos distinguir tres partes:

  • GET es el método HTTP.
  • /productos es la ruta o recurso solicitado.
  • HTTP/1.1 indica la versión del protocolo utilizada.
en este ejemplo

Esta línea puede leerse como: «quiero obtener el recurso /productos utilizando HTTP».

🟨 Cabeceras de la petición​

Las cabeceras añaden información sobre la petición. Se escriben después de la línea inicial y tienen normalmente la forma:

Nombre-Cabecera: valor

Por ejemplo:

GET /productos HTTP/1.1
Host: www.ejemplo.com
Accept: text/html
Accept-Language: es
User-Agent: Navegador

Algunas cabeceras habituales de una petición son:

CabeceraPara qué sirveEjemplo
HostIndica el servidor al que se dirige la petición.Host: www.ejemplo.com
AcceptIndica qué tipos de contenido puede recibir el cliente.Accept: text/html
Accept-LanguageIndica los idiomas preferidos.Accept-Language: es
User-AgentIdentifica el programa que realiza la petición.User-Agent: Mozilla/...
Content-TypeIndica el formato de los datos enviados en el cuerpo.Content-Type: application/json
AuthorizationPermite enviar credenciales o tokens de autenticación.Authorization: Bearer ...
CookieEnvía al servidor cookies almacenadas previamente por el cliente.Cookie: sesion=abc123
nota

No es necesario memorizar todas las cabeceras. Lo importante es saber interpretar las más habituales y entender que permiten enviar información adicional sobre la petición.

🟧 Cuerpo de la petición​

Algunas peticiones pueden incluir un cuerpo o body. En él se envían datos al servidor.

Por ejemplo:

POST /usuarios HTTP/1.1
Host: www.ejemplo.com
Content-Type: application/json

{"nombre":"Ana"}
en este ejemplo

La petición utiliza POST para enviar información a /usuarios.

La cabecera Content-Type indica que el cuerpo contiene datos en formato JSON. Después de las cabeceras aparece una línea en blanco y, a continuación, el cuerpo de la petición.

No todas las peticiones necesitan cuerpo. En una petición GET, por ejemplo, lo habitual es solicitar información sin enviar un cuerpo.

🟥 La ruta identifica el recurso​

La ruta indica sobre qué recurso queremos actuar.

En la URL:

https://www.ejemplo.com/usuarios/3

la ruta es:

/usuarios/3

Podemos interpretarla como una referencia al usuario identificado con el número 3.

Esta idea será útil en las actividades de la unidad, donde trabajaremos con rutas como:

/usuarios
/usuarios/1
/usuarios/2

2️⃣ URL, rutas y parámetros​

Cuando usamos una aplicación web, muchas veces trabajamos con direcciones como esta:

https://www.ejemplo.com/productos/3?idioma=es&orden=precio

Aunque solemos verla como una única dirección, podemos distinguir varias partes.

🟩 Partes principales de una URL​

ParteEjemploFunción
Esquema o protocolohttpsIndica cómo se realizará la comunicación.
Hostwww.ejemplo.comIdentifica el servidor al que queremos acceder.
Ruta/productos/3Identifica el recurso solicitado dentro del servidor.
Query string?idioma=es&orden=precioAñade información adicional a la petición.

Por ahora nos interesan especialmente la ruta y los parámetros de consulta.

🟨 La ruta puede tener varios segmentos​

La ruta indica qué recurso queremos solicitar o sobre qué recurso queremos actuar.

Por ejemplo:

/usuarios

puede representar una colección de usuarios, mientras que:

/usuarios/3

puede identificar un usuario concreto.

Una ruta puede estar formada por varios segmentos separados mediante /:

/categorias/tecnologia/productos/15

No necesitamos establecer todavía reglas estrictas sobre cómo deben diseñarse las rutas. Lo importante es comprender que forman parte de la petición HTTP y permiten identificar recursos diferentes.

🟧 Parámetros de consulta o query parameters​

A una ruta podemos añadir información adicional mediante la query string.

Por ejemplo:

/productos?categoria=teclados

El signo ? marca el comienzo de los parámetros.

En este caso:

categoria=teclados

es un parámetro formado por un nombre y un valor.

Si necesitamos enviar varios parámetros, normalmente se separan mediante &:

/productos?categoria=teclados&orden=precio

Aquí se están enviando dos parámetros:

categoria = teclados
orden = precio

Este tipo de información suele utilizarse para indicar opciones, búsquedas, filtros, ordenaciones o configuraciones de una consulta.

🟥 Ruta y parámetros no son lo mismo​

Estas dos direcciones pueden parecer parecidas, pero transmiten la información de forma diferente:

/usuarios/3
/usuarios?id=3

En la primera, el valor 3 forma parte de la ruta.

En la segunda, la ruta es /usuarios y id=3 es un parámetro de consulta.

Ambas formas permiten enviar información al servidor, pero no representan exactamente la misma estructura.

tip

Como orientación inicial:

  • la ruta suele utilizarse para identificar un recurso.
  • los parámetros de consulta suelen utilizarse para añadir opciones, filtros o criterios.

Más adelante veremos cómo puede recoger nuestra aplicación estos datos.

🟪 Cómo aparecen los parámetros en una petición HTTP​

Si el navegador accede a:

https://www.ejemplo.com/productos?categoria=teclados&orden=precio

la primera línea de la petición podría contener:

GET /productos?categoria=teclados&orden=precio HTTP/1.1
en este ejemplo

Los parámetros forman parte del recurso solicitado en la línea de petición.

El servidor recibirá la ruta /productos junto con los valores categoria=teclados y orden=precio, y podrá utilizarlos al procesar la solicitud.

3️⃣ Métodos HTTP​

El método HTTP indica qué acción quiere realizar el cliente sobre un recurso.

Los métodos más habituales son:

MétodoIntención habitualEjemplo¿Suele enviar datos en el cuerpo?
GETObtener un recurso o consultar información.Consultar /usuarios.No habitualmente.
POSTEnviar información para crear o procesar un recurso.Crear un nuevo usuario.Sí, con frecuencia.
PUTSustituir o actualizar completamente un recurso.Reemplazar los datos de /usuarios/3.Sí.
PATCHModificar parcialmente un recurso.Cambiar solo el correo de /usuarios/3.Sí.
DELETEEliminar un recurso.Eliminar /usuarios/3.No habitualmente.
HEADSolicitar únicamente las cabeceras de una respuesta.Comprobar información sobre un recurso.No.
OPTIONSConsultar qué operaciones admite un recurso o servidor.Consultar los métodos permitidos.No habitualmente.

En esta unidad trabajaremos especialmente con GET, POST y DELETE. Los demás métodos se incluyen como referencia y tendrán más importancia cuando estudiemos APIs REST.

aviso

No conviene memorizar los métodos HTTP como una lista aislada. Lo importante es relacionar cada método con la intención de la petición.

🟩 Propiedades de los métodos HTTP​

Además de indicar qué acción quiere realizar el cliente, los métodos HTTP tienen algunas propiedades que ayudan a describir su comportamiento.

Las tres más importantes son seguro, idempotente y cacheable.

Método seguro​

Un método es seguro cuando su finalidad es consultar información y no solicitar una modificación del recurso en el servidor.

Por ejemplo:

GET /usuarios/3

Una petición GET debería limitarse a obtener información sobre el usuario, no a modificarlo.

Esto no significa que el servidor no realice ninguna acción interna. Puede, por ejemplo, registrar la petición en un fichero de log. Lo importante es que el cliente no está solicitando un cambio en el recurso.

Método idempotente​

Un método es idempotente cuando realizar varias veces la misma petición tiene el mismo efecto final sobre el servidor que realizarla una sola vez.

Por ejemplo:

DELETE /usuarios/3

La primera petición puede eliminar al usuario. Si repetimos exactamente la misma petición, el usuario seguirá eliminado.

La respuesta podría no ser idéntica —por ejemplo, la primera vez podría devolver 204 No Content y una petición posterior 404 Not Found—, pero el estado final del recurso es el mismo.

En cambio, repetir varias veces:

POST /usuarios

podría crear varios recursos diferentes. Por eso POST no se considera idempotente de forma general.

Método cacheable​

Decimos que una respuesta es cacheable cuando puede almacenarse temporalmente y reutilizarse para responder a peticiones posteriores equivalentes.

Por ejemplo, si el navegador solicita:

GET /img/logo.png

puede guardar la respuesta durante un tiempo. Si vuelve a necesitar la misma imagen y la copia almacenada sigue siendo válida, puede reutilizarla sin descargarla otra vez.

Esto puede reducir el tráfico de red y mejorar el tiempo de carga.

nota

En la práctica, el uso de caché depende también de las cabeceras de la respuesta, como Cache-Control.

Por eso, la columna Cacheable de la siguiente tabla indica el comportamiento general del método, no que todas sus respuestas vayan a almacenarse siempre en caché.

MétodoSeguroIdempotenteCacheable habitualmente
GET✅✅✅
HEAD✅✅✅
POST❌❌⚠️ En condiciones concretas
PUT❌✅❌
PATCH❌❌⚠️ Depende
DELETE❌✅❌
OPTIONS✅✅❌
tip

Una relación útil para recordar estas propiedades es:

Todo método seguro es idempotente, pero no todo método idempotente es seguro.

Por ejemplo, GET es seguro e idempotente, mientras que DELETE es idempotente pero no es seguro porque modifica el estado del servidor.

🟨 Mismo recurso, distinta acción​

La ruta por sí sola no indica completamente qué quiere hacer el cliente.

Por ejemplo:

GET /usuarios

puede significar «quiero consultar los usuarios», mientras que:

POST /usuarios

puede significar «quiero enviar los datos de un nuevo usuario».

Y:

DELETE /usuarios/3

puede indicar que queremos eliminar el usuario identificado con el número 3.

La ruta identifica el recurso y el método indica qué queremos hacer con él.

4️⃣ La respuesta HTTP​

Después de procesar una petición, el servidor devuelve una respuesta HTTP.

Una respuesta contiene información sobre el resultado de la operación y, cuando es necesario, también el contenido solicitado.

🟩 Línea de estado​

La primera línea de una respuesta contiene la versión de HTTP y el resultado de la petición.

Por ejemplo:

HTTP/1.1 200 OK

Aquí:

  • HTTP/1.1 indica la versión del protocolo.
  • 200 es el código de estado.
  • OK es una descripción breve del resultado.

🟨 Cabeceras de la respuesta​

Las respuestas también incluyen cabeceras que describen el contenido o indican al cliente cómo debe tratarlo.

Por ejemplo:

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1280

Algunas cabeceras habituales de una respuesta son:

CabeceraPara qué sirveEjemplo
Content-TypeIndica el tipo de contenido enviado.Content-Type: text/html
Content-LengthIndica el tamaño del cuerpo de la respuesta.Content-Length: 1280
LocationIndica una nueva ubicación, normalmente en redirecciones.Location: /login
Set-CookiePermite al servidor enviar una cookie al cliente.Set-Cookie: sesion=abc123
Cache-ControlIndica cómo puede almacenarse la respuesta en caché.Cache-Control: no-cache
tip

Una misma cabecera puede aparecer en contextos diferentes, pero algunas son especialmente habituales en peticiones y otras en respuestas.

🟧 Tipo de contenido​

Una de las cabeceras más importantes es Content-Type, porque permite saber qué tipo de datos contiene el cuerpo.

Algunos valores habituales son:

Tipo de contenidoUso
text/htmlPágina HTML.
text/cssHoja de estilos CSS.
text/plainTexto sin formato.
application/javascriptCódigo JavaScript.
application/jsonDatos en formato JSON.
image/pngImagen PNG.
image/jpegImagen JPEG.
application/pdfDocumento PDF.

🟥 Cuerpo de la respuesta​

Cuando la respuesta necesita devolver contenido, este aparece después de las cabeceras.

Por ejemplo:

HTTP/1.1 200 OK
Content-Type: text/html

<h1>Listado de productos</h1>
en este ejemplo

El código 200 OK indica que la petición se ha procesado correctamente.

La cabecera Content-Type informa de que el contenido es HTML. Después de la línea en blanco aparece el cuerpo de la respuesta.

Una respuesta no tiene por qué incluir siempre un cuerpo. Por ejemplo, el código 204 No Content indica precisamente que la operación se ha realizado correctamente pero no se devuelve contenido.

5️⃣ Códigos de estado​

Los códigos de estado permiten al servidor comunicar qué ha ocurrido al procesar una petición.

No es necesario memorizar todos los códigos existentes, pero sí conocer cómo se organizan.

🟩 Familias de códigos​

La primera cifra permite identificar el tipo general de respuesta:

FamiliaSignificado general
1xxRespuestas informativas.
2xxLa petición se ha procesado correctamente.
3xxRedirecciones o acciones adicionales.
4xxExiste un problema relacionado con la petición del cliente.
5xxSe ha producido un problema en el servidor.

🟨 Códigos más habituales​

Estos son algunos de los códigos que encontraremos con mayor frecuencia:

CódigoSignificadoSituación habitual
200 OKLa operación se ha realizado correctamente.Consultar una página o recurso existente.
201 CreatedSe ha creado un nuevo recurso.Crear un usuario mediante POST.
204 No ContentLa operación ha sido correcta y no se devuelve contenido.Eliminar un recurso.
301 Moved PermanentlyEl recurso se encuentra permanentemente en otra ubicación.Cambio definitivo de URL.
302 FoundEl recurso se redirige temporalmente a otra ubicación.Redirección temporal.
400 Bad RequestLa petición no es válida o no puede interpretarse.Datos o formato de petición incorrectos.
401 UnauthorizedEs necesario autenticarse correctamente.Acceso sin credenciales válidas.
403 ForbiddenEl servidor entiende la petición, pero no permite el acceso.Usuario sin permisos suficientes.
404 Not FoundEl recurso solicitado no existe.Ruta o recurso inexistente.
405 Method Not AllowedEl recurso existe, pero no admite ese método HTTP.Enviar POST a una ruta que solo acepta GET.
500 Internal Server ErrorSe ha producido un error interno al procesar la petición.Error inesperado en la aplicación.
503 Service UnavailableEl servicio no está disponible temporalmente.Servidor saturado o en mantenimiento.
tip

No necesitamos aprender de memoria esta tabla. Debemos ser capaces de reconocer la familia del código y consultar su significado cuando sea necesario.

En la actividad práctica de la unidad trabajaremos especialmente con:

400 Bad Request
404 Not Found

Estos códigos permitirán representar distintos resultados al procesar las peticiones.

6️⃣ Petición y respuesta completas​

Veamos ahora un intercambio sencillo.

El cliente envía:

GET /usuarios/3 HTTP/1.1
Host: www.ejemplo.com
Accept: application/json

Si el usuario existe, el servidor podría responder:

HTTP/1.1 200 OK
Content-Type: application/json

{"id":3,"nombre":"Ana"}

Pero si el usuario no existe, podría devolver:

HTTP/1.1 404 Not Found
Content-Type: text/plain

Usuario no encontrado
en este ejemplo

La petición es la misma en ambos casos. Lo que cambia es la respuesta porque el resultado del procesamiento es diferente.

Esto muestra una idea importante: una petición no determina por sí sola el código de respuesta. El servidor debe procesarla antes de saber qué respuesta corresponde.

7️⃣ Una página web suele provocar varias peticiones​

Cuando escribimos una dirección en el navegador puede parecer que solo se realiza una petición, pero una página suele necesitar varios recursos.

Por ejemplo, un documento HTML puede contener:

<link rel="stylesheet" href="/css/estilos.css">
<script src="/js/app.js"></script>
<img src="/img/logo.png" alt="Logo de la aplicación">
en este ejemplo

El navegador solicita primero el documento HTML. Al interpretarlo descubre que necesita otros recursos y realiza nuevas peticiones para obtener la hoja de estilos, el archivo JavaScript y la imagen.

Por eso, una sola página puede producir numerosas comunicaciones HTTP.

GET /productos
GET /css/estilos.css
GET /js/app.js
GET /img/logo.png

Cada petición recibirá su propia respuesta.

8️⃣ Actividad no evaluable: observa peticiones reales​

Esta actividad sirve para comprobar cómo se producen peticiones y respuestas HTTP al visitar una página web real. No es evaluable y no requiere entrega.

🟩 Objetivo​

Observar que el navegador realiza varias peticiones HTTP y reconocer algunos de los elementos estudiados:

  • URL y ruta.
  • parámetros de consulta.
  • método HTTP.
  • código de estado.
  • tipo de contenido.
  • cabeceras de petición y respuesta.

🟨 Desarrollo​

Abre una página web sencilla y, a continuación, abre las herramientas de desarrollo del navegador:

F12 → Red / Network

Recarga la página para poder observar las peticiones que realiza el navegador.

Selecciona algunas peticiones y observa qué información puedes reconocer.

No es necesario comprender todavía todos los campos que muestran las herramientas del navegador.

🟧 Preguntas de comprobación​

  1. ¿Cuál es la petición correspondiente al documento principal?
  2. ¿Qué método HTTP utiliza?
  3. ¿Qué código de estado ha devuelto el servidor?
  4. ¿Qué otros recursos solicita el navegador?
  5. ¿Aparecen peticiones para imágenes, hojas de estilo o archivos JavaScript?
  6. ¿Todas las peticiones reciben necesariamente el mismo código de estado?
  7. ¿Puedes localizar la cabecera Content-Type en alguna respuesta?
  8. ¿Puedes localizar alguna cabecera enviada por el navegador?
  9. ¿Alguna de las peticiones contiene parámetros en la URL?
tip

El objetivo no es analizar todos los datos que aparecen en la pestaña Network, sino empezar a reconocer en una comunicación real los conceptos que acabamos de estudiar.

9️⃣ Errores frecuentes​

🟩 Confundir URL y petición​

La URL identifica una dirección o recurso. La petición HTTP es el mensaje completo que se envía al servidor e incluye, además de la ruta, un método, cabeceras y, en algunos casos, un cuerpo.

🟨 Confundir ruta y parámetros​

En:

/productos/3?idioma=es

la ruta es:

/productos/3

y el parámetro de consulta es:

idioma=es

No forman la misma parte de la URL.

🟧 Confundir petición y respuesta​

El método y la ruta pertenecen a la petición. El código de estado pertenece a la respuesta.

Por ejemplo:

GET /usuarios/3

es una petición, mientras que:

404 Not Found

forma parte de la respuesta.

🟥 Pensar que todas las respuestas tienen contenido​

Algunas respuestas pueden no incluir cuerpo. El ejemplo más claro que utilizaremos en esta unidad es 204 No Content.

🟪 Pensar que una página genera una única petición​

El navegador puede necesitar solicitar muchos recursos diferentes para construir una sola página: HTML, CSS, JavaScript, imágenes, fuentes y otros archivos.
