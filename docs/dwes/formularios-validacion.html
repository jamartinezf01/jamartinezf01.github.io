UT3. Formularios y validación

En la unidad anterior aprendimos a recibir peticiones en una aplicación Spring Boot, asociarlas con métodos de un controlador y generar páginas HTML dinámicas mediante Thymeleaf. Hasta ahora, sin embargo, la mayor parte de la información utilizada por la aplicación procedía del propio servidor o llegaba mediante parámetros sencillos incluidos en una petición.

En esta unidad daremos un paso importante: permitiremos que sea el usuario quien introduzca información mediante formularios web y aprenderemos a recibirla, comprobarla y procesarla correctamente en el servidor.

El recorrido será progresivo. Comenzaremos con formularios HTML sencillos y observaremos cómo se envían sus datos mediante peticiones GET y POST. Después veremos cómo Spring Boot puede agrupar automáticamente esos datos en objetos Java y, a partir de ahí, incorporaremos validación, mensajes de error y redirecciones.

Idea principal

Durante la unidad construiremos el recorrido completo de los datos introducidos por el usuario:

formulario → petición HTTP → controlador → objeto Java → validación → vista o redirección

1️⃣ Qué vamos a aprender​

Al finalizar la unidad, el alumnado deberá ser capaz de:

  • construir formularios HTML adecuados para enviar información a una aplicación web.
  • comprender la función de los atributos action, method y name de un formulario.
  • enviar datos mediante peticiones GET y POST y elegir el método adecuado según la operación realizada.
  • recibir datos enviados desde un formulario mediante un controlador de Spring Boot.
  • utilizar @RequestParam cuando sea apropiado recibir parámetros individuales.
  • comprender por qué, cuando aumenta el número de campos, resulta más conveniente trabajar con un objeto Java.
  • realizar binding entre los campos de un formulario y un objeto Java.
  • utilizar th:object y th:field para relacionar formularios Thymeleaf con objetos del servidor.
  • aplicar reglas básicas de validación a los datos recibidos.
  • utilizar @Valid para solicitar la validación de un objeto recibido por el controlador.
  • consultar los errores producidos durante el binding y la validación mediante BindingResult.
  • mostrar mensajes de error junto a los campos correspondientes y conservar los valores introducidos por el usuario.
  • redirigir después de procesar correctamente un formulario.
  • comprender el patrón POST → Redirect → GET y el problema que ayuda a evitar.
  • utilizar datos temporales asociados a una redirección para mostrar mensajes de confirmación.
  • relacionar correctamente formulario, controlador, objeto de datos y vista.
  • mantener una separación básica de responsabilidades durante el procesamiento de formularios.

En esta unidad seguiremos sin utilizar una base de datos. Los objetos creados a partir de los formularios podrán procesarse o mantenerse temporalmente en memoria, de forma que podamos concentrarnos en comprender bien el flujo de datos antes de introducir la persistencia.

aviso

No estudiaremos todavía persistencia con JPA, repositorios Spring Data, relaciones entre entidades, seguridad ni APIs REST completas.

El objetivo es dominar primero el recorrido de los datos desde el formulario hasta el servidor y de vuelta a la vista.

3️⃣ El cambio respecto a la unidad anterior​

En UT2 el recorrido habitual comenzaba cuando el navegador solicitaba una ruta y el controlador preparaba los datos que debía mostrar la vista.

Por ejemplo:

GET /productos

En esta unidad el navegador no solo solicitará información. El usuario podrá introducir datos en una página y enviarlos a nuestra aplicación.

Un formulario como este:

<form action="/registro" method="post">
    <input type="text" name="nombre">
    <input type="email" name="email">
    <button type="submit">Enviar</button>
</form>

provocará una petición al servidor que contendrá los valores introducidos. A partir de ese momento, nuestra aplicación tendrá que recibirlos, convertirlos al tipo adecuado, comprobar si son válidos y decidir qué respuesta debe devolver.

Este cambio parece pequeño, pero introduce varias responsabilidades nuevas. Ya no basta con saber qué ruta se ejecuta: tendremos que controlar qué datos llegan, cómo se transforman, qué ocurre si son incorrectos y qué debe ver el usuario después de enviar el formulario.

consejo

Un formulario no guarda información por sí mismo.

Su función es recoger datos en el navegador y enviarlos mediante una petición HTTP. Será el código ejecutado en el servidor el que decida qué hacer con esos datos.
