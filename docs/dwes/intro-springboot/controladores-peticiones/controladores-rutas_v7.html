Controladores y rutas

En el apartado anterior creamos nuestro primer proyecto Spring Boot, reconocimos su estructura y comprobamos que el servidor embebido podía arrancar correctamente.

Hasta ahora la aplicación podía mostrar una página estática desde src/main/resources/static. Sin embargo, una aplicación web necesita algo más que servir archivos: debe ser capaz de recibir una petición, ejecutar código Java y decidir qué respuesta devolver.

En este apartado vamos a dar ese primer paso utilizando Spring MVC, controladores y rutas.

Idea principal

A partir de ahora una petición ya no tiene por qué terminar directamente en un archivo.

Spring MVC puede recibirla, localizar el método Java que debe atenderla y utilizar el resultado de ese método para construir la respuesta.

1️⃣ De una página estática a una respuesta programada​

En el primer proyecto utilizamos un archivo index.html dentro de:

Ubicación de la página estática
src/main/resources/static/

Spring Boot podía servir directamente ese archivo al navegador. Ahora queremos introducir código Java entre la petición y la respuesta:

La diferencia importante es que ahora la aplicación puede ejecutar código Java antes de decidir qué respuesta devolver.

Esto nos permitirá más adelante:

  • decidir qué contenido mostrar.
  • utilizar datos.
  • responder de forma diferente según la petición recibida.
  • procesar formularios.
  • trabajar con bases de datos.
  • controlar la navegación de la aplicación.

2️⃣ Dónde encaja el controlador: Spring MVC​

Spring Web utiliza Spring MVC para organizar una parte importante del funcionamiento de las aplicaciones web tradicionales.

MVC corresponde a Model - View - Controller.

No significa que cada petición tenga que utilizar siempre las tres piezas de la misma forma, pero nos proporciona una separación clara de responsabilidades.

🟩 Model​

El modelo contiene los datos que necesita la aplicación o que queremos enviar a una vista.

Todavía no vamos a utilizar el objeto Model de Spring. Lo introduciremos cuando necesitemos enviar datos desde Java hacia Thymeleaf.

Por ahora basta con entender que el modelo representa la información con la que trabaja la aplicación.

🟨 View​

La vista se encarga de la presentación.

En nuestro proyecto utilizaremos Thymeleaf para generar HTML a partir de plantillas situadas en:

Carpeta de vistas Thymeleaf
src/main/resources/templates/

🟦 Controller​

El controlador recibe o atiende peticiones, ejecuta la lógica necesaria para esa petición y decide cuál debe ser el siguiente paso.

En los primeros ejemplos ese paso será simplemente devolver el nombre de una vista.

Podemos resumir las responsabilidades así:

ElementoResponsabilidad inicial en nuestro proyecto
ModelDatos que utilizará la aplicación o la vista.
ViewPresentación HTML generada con Thymeleaf.
ControllerAtiende la petición y decide qué respuesta debe prepararse.
aviso

MVC no significa que el controlador deba contener toda la lógica de la aplicación.

Más adelante distribuiremos responsabilidades entre controladores, servicios, repositorios y otras capas. El controlador debe centrarse principalmente en gestionar la interacción web.

3️⃣ Qué es un controlador y cómo lo encuentra Spring​

Un controlador es una clase Java que Spring registra para participar en la gestión de peticiones web.

En Spring MVC identificamos una clase como controlador mediante:

Anotación de un controlador Spring MVC
@Controller

Su import es:

Import de @Controller
import org.springframework.stereotype.Controller;

@Controller es una especialización de @Component. Esto significa que la clase puede ser detectada por el mecanismo de component scanning de Spring y registrada dentro del contexto de la aplicación.

No necesitamos estudiar todavía internamente el contenedor de Spring, pero sí entender por qué importa la ubicación de las clases.

🟩 El paquete principal marca el punto de partida​

Nuestra clase principal puede estar situada, por ejemplo, en:

Paquete principal de la aplicación
com.ejemplo.catalogo

y contener:

CatalogoApplication.java
package com.ejemplo.catalogo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class CatalogoApplication {

    public static void main(String[] args) {
        SpringApplication.run(CatalogoApplication.class, args);
    }
}

@SpringBootApplication incluye, entre otras funcionalidades, el escaneo de componentes.

Por defecto, Spring comienza a buscar componentes desde el paquete donde se encuentra la clase principal y continúa por sus subpaquetes.

Por eso esta organización es adecuada:

Organización de paquetes detectada por Spring
com.ejemplo.catalogo
├── CatalogoApplication.java
└── controller
    └── InicioController.java

En cambio, si colocamos el controlador fuera de ese árbol de paquetes, Spring podría no detectarlo con la configuración por defecto.

Para quedarnos con la idea

No colocamos controller debajo del paquete principal solo por orden.

Lo hacemos también porque esa estructura permite que el escaneo de componentes de Spring encuentre y registre nuestros controladores automáticamente.

🟨 Los objetos gestionados por Spring: beans​

Cuando Spring detecta una clase como InicioController, no se limita a “saber que existe”.
Lo habitual es que cree un objeto de esa clase y lo registre dentro de su contenedor.

A los objetos que gestiona Spring los llamamos beans.

Por ejemplo, a partir de una clase como esta:

Controlador que Spring puede gestionar
@Controller
public class InicioController {

    @GetMapping("/")
    public String inicio() {
        return "inicio";
    }
}

Spring puede seguir, de forma simplificada, este recorrido:

Qué es un bean

Un bean de Spring es un objeto cuya creación y gestión están controladas por el contenedor de Spring.

Nuestros controladores serán beans, pero más adelante también trabajaremos con beans que representarán servicios, repositorios y otros componentes de la aplicación.

🟦 El contexto de la aplicación​

El conjunto de beans gestionados por Spring se organiza dentro del ApplicationContext.

No necesitamos estudiar todavía toda su arquitectura interna, pero sí conviene quedarnos con esta idea:

Idea simplificada del ApplicationContext
ApplicationContext
   ├── InicioController
   ├── ProductosController
   └── otros beans de la aplicación

Cuando Spring necesita atender una petición, puede recurrir a los beans que ya ha registrado y gestionado dentro de ese contexto.

aviso

No debemos confundir un Spring Bean con un JavaBean.

En este tema, la palabra bean se refiere a un objeto gestionado por el contenedor de Spring.

4️⃣ Qué es una ruta​

Una ruta identifica un recurso o punto de acceso de nuestra aplicación al que puede dirigirse una petición.

Si nuestra aplicación se ejecuta en:

Dirección base de la aplicación
http://localhost:8080

la ruta:

Ruta raíz
/

corresponde a:

URL completa de la ruta raíz
http://localhost:8080/

Podemos definir otras rutas:

Ejemplos de rutas
/
/productos
/contacto
/acerca-de

Cada ruta puede quedar asociada a un método Java diferente.

nota

La ruta forma parte de la URL que solicita el cliente.

No debemos confundirla con el nombre del método Java ni con el nombre del archivo HTML que acabará utilizándose como vista.

5️⃣ @GetMapping: asociar una petición GET a un método​

Cuando escribimos una dirección en el navegador normalmente realizamos una petición HTTP de tipo GET.

En HTTP, GET está pensado para obtener o consultar un recurso. No deberíamos utilizarlo para operaciones cuya finalidad sea modificar el estado de la aplicación.

Spring permite asociar una petición GET con un método Java mediante:

Ejemplo básico de @GetMapping
@GetMapping("/productos")
public String productos() {
    return "productos";
}

Podemos leerlo así:

Cuando llegue una petición HTTP GET a /productos, este método puede encargarse de atenderla.

La URL sería:

URL de la ruta /productos
http://localhost:8080/productos

🟩 @GetMapping es una forma especializada de @RequestMapping​

@GetMapping no es un mecanismo completamente independiente.

Es una anotación compuesta equivalente, para este caso, a indicar un @RequestMapping limitado al método HTTP GET.

Podemos expresar una idea equivalente de forma más extensa:

Mapping GET expresado con @RequestMapping
@RequestMapping(value = "/productos", method = RequestMethod.GET)
public String productos() {
    return "productos";
}

Para ello necesitaríamos:

Imports de @RequestMapping y RequestMethod
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestMethod;

En nuestro código utilizaremos normalmente @GetMapping porque expresa de forma más directa la intención.

Semántica de GET

Además de utilizarse para consultar recursos, HTTP considera GET un método seguro e idempotente:

  • seguro: su finalidad no debe ser provocar cambios en el estado del servidor.
  • idempotente: repetir la misma petición debería tener el mismo efecto previsto que realizarla una sola vez.

Más adelante compararemos esta semántica con otros métodos HTTP, especialmente POST.

6️⃣ Nuestra primera ruta gestionada por un controlador​

Vamos a crear una página inicial que ya no será simplemente un archivo servido directamente desde static.

🟩 Crear el controlador​

Dentro de src/main/java crearemos el paquete:

Paquete para los controladores
com.ejemplo.catalogo.controller

Dentro crearemos InicioController.java:

src/main/java/com/ejemplo/catalogo/controller/InicioController.java
package com.ejemplo.catalogo.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class InicioController {

    @GetMapping("/")
    public String inicio() {
        return "inicio";
    }
}
en este ejemplo

@Controller permite que Spring identifique la clase como controlador.

@GetMapping("/") asocia el método inicio() con una petición GET a la ruta raíz /.

El método devuelve "inicio", pero esa cadena no contiene el HTML y tampoco representa directamente una URL. Es el nombre lógico de la vista que queremos utilizar.

🟨 Crear la vista​

Las plantillas Thymeleaf se guardan en:

Carpeta de plantillas Thymeleaf
src/main/resources/templates/

Crearemos:

Vista inicial
src/main/resources/templates/inicio.html

con un contenido sencillo:

src/main/resources/templates/inicio.html
<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <title>Catálogo</title>
</head>
<body>

    <h1>Catálogo</h1>

    <p>Esta página ha sido devuelta por un controlador de Spring.</p>

</body>
</html>

Ahora ejecutamos la aplicación y accedemos a:

Dirección para probar la primera ruta
http://localhost:8080/

El navegador mostrará el resultado generado a partir de inicio.html.

Para comprobar que la URL y la vista son conceptos distintos

Podemos cambiar temporalmente la ruta del controlador de / a /inicio.

La URL pasaría a ser:

URL temporal de la ruta /inicio
http://localhost:8080/inicio

pero el método seguiría devolviendo:

Nombre lógico de la vista
return "inicio";

y la plantilla seguiría siendo inicio.html.

7️⃣ Qué ocurre realmente cuando escribimos una URL​

Hasta ahora hemos dicho de forma simplificada que “Spring busca un método asociado a la ruta”.

Para trabajar con más rigor necesitamos introducir una pieza central de Spring MVC: DispatcherServlet.

DispatcherServlet actúa como Front Controller: recibe las peticiones web que entran en Spring MVC y coordina los componentes necesarios para procesarlas.

No realiza todo el trabajo por sí solo. Internamente colabora con otros componentes de Spring MVC.

Para nuestro nivel, podemos seguir este recorrido:

¿Qué ocurre en este recorrido?

El navegador envía una petición GET /.
DispatcherServlet recibe la petición y coordina su procesamiento dentro de Spring MVC.

Spring busca un mapping compatible y encuentra el método InicioController.inicio(). Ese método devuelve "inicio", que representa el nombre lógico de la vista.

A partir de ese nombre, Spring resuelve la plantilla correspondiente, Thymeleaf procesa inicio.html y genera el HTML final que se envía de vuelta al navegador.

🟩 Localizar el método adecuado​

Spring registra durante el arranque las rutas definidas mediante anotaciones como @GetMapping y @RequestMapping.

Cuando llega una petición, DispatcherServlet consulta los mappings disponibles para determinar qué método debe atenderla.

Internamente participan componentes como los HandlerMapping, encargados de relacionar una petición con su handler correspondiente.

No necesitamos configurarlos manualmente para estos ejemplos: Spring Boot prepara la infraestructura necesaria.

🟨 Ejecutar el método del controlador​

Para:

Método que atiende la ruta raíz
@GetMapping("/")
public String inicio() {
    return "inicio";
}

Spring ejecuta inicio() cuando recibe una petición GET / compatible con ese mapping.

🟪 Interpretar el valor devuelto​

Al utilizar @Controller, el valor:

Nombre lógico devuelto por el controlador
return "inicio";

se interpreta como un nombre lógico de vista.

No es todavía el archivo HTML final.

🟦 Resolver y procesar la vista​

Con Thymeleaf configurado mediante Spring Boot, la resolución se puede entender de forma simplificada así:

Resolución simplificada del nombre lógico de vista
"inicio"
   ↓
ViewResolver
   ↓
classpath:/templates/inicio.html
   ↓
Thymeleaf
   ↓
HTML

Un ViewResolver ayuda a transformar el nombre lógico devuelto por el controlador en una vista concreta.

Con la configuración habitual de Thymeleaf en Spring Boot se utilizan, entre otros valores por defecto:

Convenciones habituales de Thymeleaf
prefijo: classpath:/templates/
sufijo:  .html

Por eso podemos devolver simplemente:

Nombre lógico de vista
return "inicio";

sin escribir toda la ruta del archivo.

aviso

Estas convenciones pueden configurarse.

No debemos interpretar templates/ y .html como valores obligatorios e inmutables de Spring MVC, sino como la configuración habitual que Spring Boot proporciona para Thymeleaf.

8️⃣ Ruta, método y vista no son lo mismo​

Este punto es fundamental porque los tres conceptos aparecen juntos, pero cumplen funciones distintas.

ElementoEjemploQué representa
Ruta/catalogoDirección que solicita el cliente.
Método JavamostrarProductos()Código que atiende la petición.
Nombre lógico de vista"productos"Valor que devuelve el controlador para indicar la vista.
Plantillaproductos.htmlArchivo que procesará Thymeleaf.

Por ejemplo:

Ruta, método y nombre lógico de vista
@GetMapping("/catalogo")
public String mostrarProductos() {
    return "productos";
}

En este caso:

  • la ruta es /catalogo.
  • el método Java es mostrarProductos().
  • el nombre lógico de vista es "productos".
  • la plantilla será, con nuestra configuración, productos.html.

La URL sería:

URL del ejemplo
http://localhost:8080/catalogo

y la plantilla se encontrará en:

Plantilla que resolverá Thymeleaf
src/main/resources/templates/productos.html
aviso

Cuando devolvemos una vista Thymeleaf desde un @Controller, trabajamos con un nombre lógico de vista.

Utilizaremos:

Nombre lógico correcto de una vista
return "productos";

y dejaremos que el sistema de resolución de vistas aplique las convenciones configuradas.

9️⃣ Organizar varias rutas​

Un controlador puede atender varias rutas relacionadas.

Por ejemplo:

SitioController.java con varias rutas
package com.ejemplo.catalogo.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class SitioController {

    @GetMapping("/")
    public String inicio() {
        return "inicio";
    }

    @GetMapping("/productos")
    public String productos() {
        return "productos";
    }

    @GetMapping("/contacto")
    public String contacto() {
        return "contacto";
    }
}

Para que estas rutas funcionen necesitaremos las vistas correspondientes:

Plantillas utilizadas por el controlador
src/main/resources/templates/
├── inicio.html
├── productos.html
└── contacto.html

A medida que la aplicación crece, conviene agrupar rutas por responsabilidad.

🟩 @RequestMapping a nivel de clase​

Podemos establecer una ruta base para todo un controlador.

Por ejemplo:

ProductosController.java con ruta base
package com.ejemplo.catalogo.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;

@Controller
@RequestMapping("/productos")
public class ProductosController {

    @GetMapping
    public String listado() {
        return "productos";
    }

    @GetMapping("/destacados")
    public String destacados() {
        return "productos-destacados";
    }
}
en este ejemplo

@RequestMapping("/productos") establece una ruta base para los mappings definidos dentro de la clase.

El primer método tiene @GetMapping sin ruta adicional, por lo que atiende GET /productos.

El segundo añade /destacados, por lo que atiende GET /productos/destacados.

La composición de rutas queda así:

Composición de rutas a nivel de clase y método
@RequestMapping("/productos") + @GetMapping
→ GET /productos

@RequestMapping("/productos") + @GetMapping("/destacados")
→ GET /productos/destacados

Esta organización resulta especialmente útil cuando varias operaciones pertenecen al mismo recurso o área funcional.

🔟 static y templates cumplen funciones diferentes​

En el apartado anterior habíamos creado:

Página estática utilizada para comprobar el servidor
src/main/resources/static/index.html

Ahora también trabajamos con:

Ejemplo de plantilla Thymeleaf
src/main/resources/templates/inicio.html

No cumplen la misma función.

UbicaciónUso principal
static/Recursos que pueden servirse directamente, como CSS, JavaScript, imágenes o páginas estáticas.
templates/Plantillas que debe procesar un motor de vistas como Thymeleaf.

🟩 Utilizar un recurso estático común​

Una aplicación suele compartir determinados recursos entre varias páginas, por ejemplo una hoja de estilos CSS.

Podemos crear:

Ubicación de una hoja de estilos común
src/main/resources/static/css/estilos.css

con un contenido sencillo:

src/main/resources/static/css/estilos.css
body {
    font-family: Arial, sans-serif;
    max-width: 900px;
    margin: 0 auto;
    padding: 2rem;
}

nav {
    margin-bottom: 2rem;
}

nav a {
    margin-right: 1rem;
}

Desde una plantilla situada en templates podemos enlazar ese recurso dentro de <head>:

Enlace al CSS desde una plantilla
<link rel="stylesheet" href="/css/estilos.css">
en este ejemplo

Aunque el archivo se encuentra físicamente dentro de src/main/resources/static/css, en la URL no aparece la carpeta static.

Spring Boot sirve el contenido de static desde la raíz de la aplicación.

Por eso:

src/main/resources/static/css/estilos.css

se solicita desde el navegador como:

/css/estilos.css.

De esta forma varias vistas pueden utilizar la misma hoja de estilos sin duplicar CSS en cada archivo HTML.

🟨 Navegar entre rutas desde las vistas​

También podemos añadir enlaces HTML para movernos entre las distintas rutas de la aplicación.

Por ejemplo:

Navegación común entre varias rutas
<nav>
    <a href="/">Inicio</a>
    <a href="/productos">Productos</a>
    <a href="/contacto">Contacto</a>
</nav>

Al pulsar uno de estos enlaces, el navegador realiza una nueva petición GET a la ruta indicada.

Por ejemplo:

Recorrido al pulsar el enlace Productos
<a href="/productos">
        ↓
GET /productos
        ↓
Spring MVC localiza el mapping
        ↓
ProductosController o SitioController
        ↓
Vista correspondiente
nota

Por ahora utilizamos enlaces HTML normales con href.

Más adelante, cuando trabajemos con más funcionalidades de Thymeleaf, veremos otras formas de construir URLs desde las plantillas.

Podemos mantener temporalmente static/index.html para comprobar la diferencia.

Acceso directo al recurso estático:

Acceso directo al recurso estático
http://localhost:8080/index.html

Acceso a la ruta gestionada por el controlador:

Acceso mediante el controlador
http://localhost:8080/

En el primer caso solicitamos directamente un recurso estático.

En el segundo, la petición entra en Spring MVC, se ejecuta un controlador y finalmente se resuelve una vista.

Diferencia esencial

Recurso estático

navegador → recurso

Vista Thymeleaf desde un controlador

navegador → Spring MVC → controlador → nombre lógico → vista → navegador

🟧 Organizar las vistas en subcarpetas​

Cuando una aplicación empieza a tener varias vistas relacionadas, podemos organizarlas en subcarpetas dentro de templates.

Por ejemplo, en el apartado anterior habíamos creado un ProductosController con estas rutas:

Rutas del controlador de productos
/productos
/productos/destacados

En lugar de guardar todas las plantillas directamente en templates, podemos agrupar las relacionadas con productos:

Organización de las vistas de productos
src/main/resources/templates/
├── inicio.html
└── productos/
    ├── listado.html
    └── destacados.html

En ese caso, el controlador podría quedar así:

ProductosController.java con vistas organizadas en una subcarpeta
@Controller
@RequestMapping("/productos")
public class ProductosController {

    @GetMapping
    public String listado() {
        return "productos/listado";
    }

    @GetMapping("/destacados")
    public String destacados() {
        return "productos/destacados";
    }
}

La relación completa sería:

URL solicitadaNombre lógico devueltoPlantilla
/productos"productos/listado"templates/productos/listado.html
/productos/destacados"productos/destacados"templates/productos/destacados.html
Para quedarnos con la idea

Las subcarpetas de templates nos ayudan a organizar las vistas, pero no determinan por sí mismas las URL de la aplicación.

Seguimos distinguiendo tres elementos diferentes:

Ruta, nombre lógico y plantilla
URL
/productos/destacados
        ↓
nombre lógico
"productos/destacados"
        ↓
plantilla
templates/productos/destacados.html

1️⃣1️⃣ Errores frecuentes y qué significan​

No basta con saber que “algo falla”. Conviene aprender a relacionar el síntoma con la parte del recorrido que puede estar fallando.

🟩 No existe un mapping para la URL​

Si accedemos a una ruta que ningún controlador atiende y tampoco corresponde a un recurso estático, la aplicación no tendrá un recurso que devolver para esa dirección.

Por ejemplo, si no existe ningún mapping para:

Ejemplo de ruta no definida
http://localhost:8080/usuarios

la respuesta habitual será un 404 Not Found.

🟨 El controlador no ha sido detectado​

Si colocamos un controlador fuera del árbol de paquetes que Spring escanea por defecto, la clase puede no registrarse.

En ese caso, aunque el código contenga:

Mapping de un controlador no detectado
@GetMapping("/productos")
public String productos() {
    return "productos";
}

Spring no tendrá registrado ese mapping y la ruta se comportará como si no existiera.

🟧 La ruta existe, pero la vista no puede resolverse​

Supongamos que el controlador devuelve:

Nombre lógico de una vista inexistente
return "productos";

pero no existe una plantilla compatible en templates.

El mapping sí puede haberse encontrado y el método puede haberse ejecutado, pero el proceso falla posteriormente al intentar resolver o procesar la vista.

Esto suele terminar en un error del servidor y en la consola encontraremos información relacionada con la resolución de la plantilla.

🟥 Guardar una plantilla en la carpeta incorrecta​

No debemos confundir:

Ubicación de recursos estáticos y plantillas
static/      → recursos servidos directamente
templates/   → plantillas procesadas por Thymeleaf

Si esperamos que Thymeleaf procese una plantilla, deberá estar en la ubicación configurada para las vistas.

🟪 Repetir el mismo mapping​

Esto provoca un conflicto:

Dos métodos con el mismo mapping
@GetMapping("/productos")
public String productos() {
    return "productos";
}

@GetMapping("/productos")
public String catalogo() {
    return "catalogo";
}

Spring detectará que dos métodos pretenden atender la misma combinación de método HTTP y ruta.

El problema puede impedir que la aplicación arranque correctamente porque el mapping es ambiguo.

🟦 Confundir URL y vista​

Esta ruta:

Ruta y vista con nombres distintos
@GetMapping("/catalogo")
public String productos() {
    return "productos";
}

no implica que exista un archivo llamado catalogo.html.

La URL y la vista pertenecen a partes diferentes del proceso.
