2.2 Parámetros en las peticiones

Hasta ahora hemos trabajado con rutas fijas: una determinada URL activa un método concreto del controlador. Sin embargo, una aplicación real necesita recibir datos que cambian en cada petición.

No tendría sentido crear una ruta diferente para cada producto, usuario o búsqueda. Necesitamos definir rutas capaces de recibir valores y utilizarlos desde Java.

En Spring Boot, trabajando con Spring MVC, dos de los mecanismos más habituales para empezar son:

  • @RequestParam, para obtener parámetros enviados con la petición, normalmente en la query string de la URL.
  • @PathVariable, para obtener valores que forman parte de la propia ruta.
Idea principal

Una misma ruta puede atender muchas peticiones diferentes si el controlador es capaz de recoger los datos que cambian y utilizarlos al ejecutar el método Java.

1️⃣ De una ruta fija a una petición con datos​

Una ruta fija siempre representa exactamente la misma dirección:

Ruta fija
/productos

Pero podemos necesitar peticiones como estas:

Peticiones con datos
/productos/7
/productos/25
/buscar?texto=java
/buscar?texto=spring

En los dos primeros casos, el dato forma parte de la ruta. En los dos últimos, aparece después del signo ? como parámetro de consulta.

Spring MVC puede extraer esos valores y pasarlos como argumentos al método del controlador.

🟩 Dos formas distintas de transportar información​

Observa estas dos URL:

Valor dentro de la ruta
/productos/7
Valor como parámetro de consulta
/productos?id=7

Ambas contienen el valor 7, pero no están construidas de la misma forma.

En la primera, 7 identifica una parte variable de la ruta. En la segunda, la ruta sigue siendo /productos y se añade un parámetro llamado id.

Esta diferencia determinará qué anotación utilizaremos en el controlador.

🟨 Recordatorio: @ResponseBody​

En los ejemplos de este apartado todavía no vamos a devolver vistas HTML. Queremos centrarnos en comprobar qué valores recibe el controlador, por lo que devolveremos respuestas de texto directamente.

Para ello utilizaremos @ResponseBody.

Cuando una clase está anotada con @Controller, Spring MVC interpreta normalmente un String devuelto por un método como el nombre de una vista que debe localizar y renderizar. @ResponseBody cambia ese comportamiento: indica que el valor devuelto por el método debe escribirse directamente en el cuerpo de la respuesta HTTP.

Por ejemplo:

Respuesta de texto directa
@GetMapping("/saludo")
@ResponseBody
public String saludo() {
    return "Hola desde el servidor";
}
en este ejemplo

En este caso Spring no busca una plantilla llamada Hola desde el servidor. El texto se envía directamente como contenido de la respuesta HTTP.

Usaremos este mecanismo en los ejemplos de parámetros porque nos permite comprobar fácilmente qué datos ha recibido el método.

aviso

Cuando más adelante devolvamos una vista Thymeleaf desde un controlador, no utilizaremos @ResponseBody. En ese caso el String devuelto representará el nombre de la plantilla que Spring debe renderizar.

2️⃣ Parámetros de consulta con @RequestParam​

Los parámetros de consulta aparecen normalmente al final de una URL, después de ?.

Por ejemplo:

URL con un parámetro de consulta
/buscar?texto=java

Aquí podemos distinguir:

Partes de la URL
/buscar        → ruta
texto          → nombre del parámetro
java           → valor del parámetro

Para recoger ese valor desde un controlador utilizamos @RequestParam.

🟩 Primer ejemplo​

BusquedaController.java
@Controller
@RequestMapping("/buscar")
public class BusquedaController {

    @GetMapping
    @ResponseBody
    public String buscar(@RequestParam String texto) {
        return "Buscando: " + texto;
    }
}
en este ejemplo

@RequestParam indica a Spring MVC que el argumento texto debe obtenerse de un parámetro de la petición.

Si accedemos a /buscar?texto=java, Spring extrae el valor java y lo pasa al método buscar() como un String.

La petición:

Petición
GET /buscar?texto=java

produce una llamada equivalente a:

Valor recibido por el método
texto = "java"

🟨 Indicar explícitamente el nombre del parámetro​

Podemos indicar el nombre que Spring debe buscar en la petición:

Nombre explícito del parámetro
@GetMapping
@ResponseBody
public String buscar(@RequestParam("texto") String termino) {
    return "Buscando: " + termino;
}

En este caso:

  • el parámetro de la URL se llama texto.
  • la variable Java se llama termino.

Por tanto:

URL válida
/buscar?texto=java

seguirá funcionando.

tip

Escribir el nombre de forma explícita, por ejemplo @RequestParam("texto"), puede hacer el código más claro cuando el nombre de la variable Java y el de la petición no coinciden.

3️⃣ Parámetros obligatorios y opcionales​

Por defecto, un parámetro anotado con @RequestParam es obligatorio.

Si tenemos:

Parámetro obligatorio
@GetMapping
@ResponseBody
public String buscar(@RequestParam String texto) {
    return "Buscando: " + texto;
}

y hacemos una petición sin el parámetro:

Petición sin el parámetro requerido
/buscar

Spring no puede ejecutar correctamente el método porque falta un dato que se ha declarado como necesario.

🟩 required = false​

Si un dato puede faltar, podemos marcarlo como opcional:

Parámetro opcional
@GetMapping
@ResponseBody
public String buscar(@RequestParam(required = false) String texto) {
    if (texto == null) {
        return "No se ha indicado ningún texto de búsqueda";
    }

    return "Buscando: " + texto;
}
en este ejemplo

Con required = false, Spring permite que la petición llegue sin ese parámetro. En ese caso, la variable puede recibir null, por lo que nuestro código debe contemplar esa posibilidad.

🟨 Utilizar defaultValue​

Otra posibilidad es definir un valor que se utilizará cuando el parámetro no aparezca:

Parámetro con valor por defecto
@GetMapping
@ResponseBody
public String listar(
        @RequestParam(defaultValue = "nombre") String orden) {

    return "Ordenando por: " + orden;
}

Estas dos peticiones son válidas:

Peticiones posibles
/productos?orden=precio
/productos

En la segunda, Spring utilizará:

Valor utilizado por defecto
orden = "nombre"
nota

Cuando utilizamos defaultValue, el parámetro deja de comportarse como obligatorio: si no llega un valor, Spring utiliza el que hemos indicado.

4️⃣ Recibir varios parámetros​

Una petición puede incluir varios parámetros de consulta. Se separan mediante &.

Por ejemplo:

URL con varios parámetros
/productos?categoria=teclados&orden=precio

El controlador puede recibirlos por separado:

Controlador con varios @RequestParam
@GetMapping("/productos")
@ResponseBody
public String productos(
        @RequestParam String categoria,
        @RequestParam(defaultValue = "nombre") String orden) {

    return "Categoría: " + categoria + " | Orden: " + orden;
}
en este ejemplo

Spring analiza los parámetros de la petición y asigna cada valor al argumento correspondiente del método.

En este ejemplo, categoria es obligatorio mientras que orden dispone de un valor por defecto.

No importa el orden en el que aparezcan los parámetros en la URL:

Dos peticiones equivalentes respecto a sus parámetros
/productos?categoria=teclados&orden=precio
/productos?orden=precio&categoria=teclados

El nombre de cada parámetro es lo que permite identificar su valor.

5️⃣ Conversión automática de tipos​

Los datos de una URL llegan inicialmente como texto, pero el método Java no tiene por qué trabajar siempre con String.

Spring MVC dispone de mecanismos de conversión para tipos sencillos.

Por ejemplo:

Conversión automática a int
@GetMapping("/pagina")
@ResponseBody
public String pagina(@RequestParam int numero) {
    return "Página solicitada: " + numero;
}

Si hacemos:

Petición válida
/pagina?numero=3

Spring convierte el texto "3" en el entero 3 antes de ejecutar el método.

También podemos recibir otros tipos sencillos:

Conversión a varios tipos
@GetMapping("/filtro")
@ResponseBody
public String filtrar(
        @RequestParam int minimo,
        @RequestParam double maximo,
        @RequestParam boolean disponible) {

    return "Filtro recibido";
}

🟩 ¿Qué ocurre si el valor no puede convertirse?​

Esta petición no es válida para el método anterior:

Valor incompatible con int
/pagina?numero=tres

Spring intentará convertir "tres" a int, pero no podrá hacerlo.

Por tanto, no debemos pensar que @RequestParam int numero valida cualquier texto recibido. Estamos indicando que esperamos un valor convertible a entero.

aviso

La conversión automática evita que tengamos que utilizar manualmente Integer.parseInt() en estos casos, pero la petición debe contener un valor compatible con el tipo declarado.

6️⃣ Variables dentro de la ruta con @PathVariable​

En otras ocasiones, el dato no aparece después de ?, sino que forma parte de la propia ruta.

Por ejemplo:

Ruta con un identificador
/productos/7

No queremos crear manualmente:

Rutas que no deberíamos definir una a una
/productos/1
/productos/2
/productos/3
/productos/4
...

Podemos definir un patrón de ruta:

Patrón conceptual
/productos/{id}

La parte {id} representa un segmento variable.

🟩 Primer ejemplo con @PathVariable​

ProductoController.java
@Controller
@RequestMapping("/productos")
public class ProductoController {

    @GetMapping("/{id}")
    @ResponseBody
    public String detalle(@PathVariable int id) {
        return "Mostrando el producto " + id;
    }
}

La petición:

Petición
GET /productos/7

hace que Spring ejecute el método con:

Valor recibido
id = 7
en este ejemplo

@GetMapping("/{id}") define una parte variable de la ruta. @PathVariable indica que queremos recuperar ese valor y utilizarlo como argumento del método.

Además, Spring convierte automáticamente el segmento "7" al tipo int que hemos declarado.

🟨 Nombre explícito de la variable de ruta​

También podemos escribir:

Nombre explícito en @PathVariable
@GetMapping("/{id}")
@ResponseBody
public String detalle(@PathVariable("id") int productoId) {
    return "Mostrando el producto " + productoId;
}

Aquí el nombre utilizado en el patrón es id, mientras que la variable Java se llama productoId.

7️⃣ Varias variables en una misma ruta​

Una ruta puede contener más de una parte variable.

Por ejemplo:

Ruta con dos valores variables
/categorias/3/productos/12

Podríamos representarla así:

Dos @PathVariable en la misma ruta
@GetMapping("/categorias/{categoriaId}/productos/{productoId}")
@ResponseBody
public String detalle(
        @PathVariable int categoriaId,
        @PathVariable int productoId) {

    return "Categoría " + categoriaId
            + ", producto " + productoId;
}

Spring extraerá ambos valores de la ruta y los entregará al método.

Valores obtenidos
categoriaId = 3
productoId = 12
aviso

Una variable de ruta forma parte del patrón que debe coincidir con la petición. Si hemos definido /productos/{id}, la URL /productos es una ruta diferente y no proporciona el valor que necesita ese patrón.

8️⃣ @RequestParam y @PathVariable no significan lo mismo​

Aunque ambos permiten recibir datos, expresan ideas diferentes en la URL.

MecanismoEjemploQué representa normalmente
@PathVariable/productos/7Identifica un recurso o una parte concreta de la ruta.
@RequestParam/productos?categoria=tecladosAñade criterios, opciones, filtros o información adicional.

Por ejemplo, esta URL resulta bastante natural:

Recurso concreto con opciones adicionales
/productos/7?moneda=eur

Podemos interpretarla así:

Interpretación
/productos/7    → producto concreto
moneda=eur      → opción utilizada para mostrarlo

Un controlador podría combinar ambos mecanismos:

Combinación de @PathVariable y @RequestParam
@GetMapping("/productos/{id}")
@ResponseBody
public String detalle(
        @PathVariable int id,
        @RequestParam(defaultValue = "eur") String moneda) {

    return "Producto " + id + " | Moneda: " + moneda;
}
en este ejemplo

id procede de la ruta y permite identificar el producto. moneda procede de la query string y modifica la forma en que queremos trabajar con ese recurso.

9️⃣ Qué ocurre cuando una petición no encaja​

Trabajar con parámetros implica que no todas las URL serán válidas para todos los métodos del controlador.

Conviene distinguir varios casos.

🟩 Falta un @RequestParam obligatorio​

Si tenemos:

Parámetro obligatorio
@GetMapping("/buscar")
@ResponseBody
public String buscar(@RequestParam String texto) {
    return "Buscando " + texto;
}

y solicitamos:

Petición incompleta
/buscar

falta un parámetro necesario para ejecutar el método.

Spring considera que la petición no contiene los datos requeridos.

🟨 Falta una parte de una ruta con @PathVariable​

Si el controlador define:

Ruta con variable
@GetMapping("/productos/{id}")

esta URL coincide:

Ruta válida
/productos/7

pero esta otra no coincide con el mismo patrón:

Ruta diferente
/productos

No estamos simplemente dejando id vacío. Estamos solicitando otra ruta.

🟧 El valor no puede convertirse​

Si esperamos:

Argumento numérico
@PathVariable int id

pero la URL contiene:

Valor no convertible
/productos/abc

Spring no puede convertir abc al tipo int esperado por el método.

Una idea importante

Spring MVC realiza parte del trabajo entre la petición HTTP y nuestro método Java: localiza la ruta, extrae parámetros o segmentos variables y realiza conversiones sencillas antes de invocar el método.

Nuestro código comienza a ejecutarse cuando Spring ya ha conseguido construir correctamente los argumentos que necesita ese método.

🔟 Ejemplo: catálogo con filtros y detalle​

Vamos a reunir lo aprendido en un único controlador sencillo.

CatalogoController.java
package com.ejemplo.catalogo.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.ResponseBody;

@Controller
@RequestMapping("/catalogo")
public class CatalogoController {

    @GetMapping
    @ResponseBody
    public String listar(
            @RequestParam(required = false) String categoria,
            @RequestParam(defaultValue = "nombre") String orden) {

        if (categoria == null) {
            return "Todos los productos | Orden: " + orden;
        }

        return "Categoría: " + categoria + " | Orden: " + orden;
    }

    @GetMapping("/{id}")
    @ResponseBody
    public String detalle(
            @PathVariable int id,
            @RequestParam(defaultValue = "eur") String moneda) {

        return "Producto: " + id + " | Moneda: " + moneda;
    }
}
en este ejemplo

El primer método responde a /catalogo y permite añadir parámetros opcionales para filtrar y ordenar.

El segundo responde a rutas como /catalogo/7. El identificador procede de la ruta mediante @PathVariable, mientras que moneda es una opción adicional obtenida con @RequestParam.

Todavía devolvemos texto mediante @ResponseBody para concentrarnos en cómo llegan los datos al controlador. En el siguiente bloque utilizaremos estos valores para preparar información y enviarla a vistas HTML mediante Model.

Podemos probar, entre otras, estas peticiones:

Peticiones para probar el controlador
/catalogo
/catalogo?categoria=teclados
/catalogo?categoria=teclados&orden=precio
/catalogo/7
/catalogo/7?moneda=usd

Cada URL contiene información distinta, pero no necesitamos crear un método Java diferente para cada valor posible.

1️⃣1️⃣ Errores frecuentes​

🟩 Confundir una variable de ruta con un parámetro de consulta​

Dos estructuras diferentes
/productos/7
/productos?id=7

No son la misma estructura y no se reciben con la misma anotación.

🟨 Escribir ? o & dentro de @GetMapping​

El mapeo se define sobre la ruta, no sobre los valores concretos de la query string.

No escribiríamos:

Ejemplo incorrecto
@GetMapping("/buscar?texto=java")

Definimos la ruta y recibimos el parámetro por separado:

Forma correcta
@GetMapping("/buscar")
@ResponseBody
public String buscar(@RequestParam String texto) {
    return "Buscando: " + texto;
}

🟧 Suponer que un parámetro obligatorio puede faltar​

Si @RequestParam es obligatorio, nuestra aplicación espera que el cliente lo envíe. Si el dato realmente puede omitirse, debemos expresarlo mediante required = false o proporcionar un defaultValue.

🟥 No contemplar null en un parámetro opcional​

Con:

Parámetro que puede ser null
@RequestParam(required = false) String categoria

la variable puede no contener ningún valor. Nuestro código debe manejar esa situación antes de utilizarla como si siempre existiera.

🟪 Utilizar String para todo sin pensar en el dominio​

Spring puede convertir valores sencillos automáticamente. Si esperamos un identificador numérico, declarar:

Tipo adecuado para un identificador
@PathVariable int id

expresa mejor nuestra intención que recibir siempre un String y convertirlo manualmente después.

tip

Antes de escribir el controlador, conviene leer la URL y preguntarse:

¿este valor identifica una parte del recurso o es una opción que modifica la consulta?

La respuesta suele ayudar a decidir entre @PathVariable y @RequestParam.
