Actividad 2. Las URL empiezan a llevar información

En la actividad anterior construimos la estructura de Inventario Arcano: organizamos la aplicación en controladores, definimos sus rutas, conectamos las vistas y dejamos preparada una navegación funcional.

Ahora vamos a hacer que algunas URL puedan transportar información hasta el servidor.

La aplicación seguirá siendo la misma. No debes crear un proyecto nuevo. Partiremos del Inventario Arcano que ya funciona y ampliaremos el catálogo con distintas formas de consulta.

Objetivo

Ampliar Inventario Arcano para que un mismo controlador pueda recibir información desde segmentos de la ruta y parámetros de consulta, utilizando correctamente @PathVariable, @RequestParam, valores obligatorios, parámetros opcionales, valores por defecto y conversión automática a tipos Java.

nota

Esta actividad es de entrega obligatoria. Entra dentro de las actividades de seguimiento y será evaluada como Entregada o NO entregada.

La parte de ampliación es opcional y no será necesaria para poder continuar con la Actividad 2.

1️⃣ Punto de partida​

Debes comenzar con la aplicación resultante de la Actividad 1.

Proyecto de recuperación

Si tu proyecto de la Actividad 1 no funciona correctamente o necesitas incorporarte desde este punto, puedes utilizar el proyecto de recuperación preparado para esta actividad.

👉 Descargar proyecto de recuperación de la Actividad 1

El proyecto contiene únicamente el punto de partida mínimo necesario para comenzar esta actividad. No incluye la solución de los nuevos requisitos.

Si tu propio Inventario Arcano funciona correctamente, continúa trabajando sobre él.

Antes de continuar, comprueba que siguen funcionando al menos estas rutas:

Rutas que ya deben funcionar
/catalogo
/catalogo/pociones
/catalogo/pergaminos
/catalogo/artefactos
/catalogo/recomendados

También debe mantenerse la navegación existente y los recursos visuales del kit de Inventario Arcano.

En esta actividad añadiremos nuevas rutas al catálogo, pero las páginas que ya existen no deben dejar de funcionar.

aviso

Antes de modificar CatalogoController, arranca la aplicación y comprueba que el punto de partida funciona correctamente.

Si comienzas la actividad con errores de la fase anterior, será más difícil distinguir si un problema procede de las nuevas rutas o del código que ya existía.

2️⃣ La nueva necesidad de la tienda​

Hasta ahora, cada URL representa una página fija:

/catalogo/pociones
/catalogo/pergaminos
/catalogo/artefactos

Pero la tienda quiere empezar a realizar consultas más flexibles.

Por ejemplo:

Nuevas peticiones
/catalogo/objeto/7
/catalogo/objeto/7?moneda=gemas
/catalogo/objeto/7?moneda=gemas&cantidad=3
/catalogo/buscar?texto=cristal
/catalogo/buscar?texto=cristal&rareza=epica
/catalogo/rareza/legendaria?orden=precio

Ya no tendría sentido crear un método distinto para cada identificador, moneda, cantidad, texto o rareza.

Nuestro objetivo será que Spring MVC extraiga esos valores de la petición y los entregue al método Java correspondiente.

3️⃣ Antes de programar: interpreta las URL​

Antes de escribir código, analiza estas peticiones:

Peticiones para analizar
/catalogo/objeto/12
/catalogo/objeto/12?moneda=oro
/catalogo/objeto/12?moneda=gemas&cantidad=4&envolver=true
/catalogo/buscar?texto=pocion&rareza=rara
/catalogo/rareza/epica?orden=precio&limite=5

Para cada una debes ser capaz de identificar:

  • qué parte determina la ruta que debe coincidir con @GetMapping.
  • qué valores forman parte de la propia ruta.
  • qué valores pertenecen a la query string.
  • qué tipo Java sería adecuado para recibir cada dato.
Decisión previa

No empieces escribiendo anotaciones al azar.

Primero decide qué información identifica aquello que estamos consultando y qué información simplemente modifica u ofrece opciones sobre esa consulta.

4️⃣ Requisito 1: consultar un objeto por su identificador​

Añade al catálogo una operación que atienda este patrón:

Patrón de ruta
GET /catalogo/objeto/{id}

El identificador deberá recibirse como un:

int

Estas peticiones deben llegar al mismo método:

Ejemplos
/catalogo/objeto/1
/catalogo/objeto/7
/catalogo/objeto/42

Para poder comprobar el valor recibido, el método devolverá temporalmente una respuesta de texto.

Por ejemplo, para:

/catalogo/objeto/7

podríamos obtener:

Respuesta orientativa
Consulta de objeto arcano
Identificador: 7

No es obligatorio utilizar exactamente ese texto.

🟩 Una decisión importante​

No debes crear métodos como:

objeto1()
objeto2()
objeto3()

ni analizar manualmente la URL.

Queremos que un único método sea capaz de atender cualquier identificador numérico válido.

5️⃣ Requisito 2: añadir opciones a la consulta de un objeto​

Amplía la misma operación para que pueda recibir estas opciones:

ParámetroTipo JavaValor por defecto
monedaStringoro.
cantidadint1.
envolverbooleanfalse.

Por tanto, todas estas peticiones deberán ser válidas:

Consultas de un objeto
/catalogo/objeto/7
/catalogo/objeto/7?moneda=gemas
/catalogo/objeto/7?cantidad=3
/catalogo/objeto/7?moneda=gemas&cantidad=3
/catalogo/objeto/7?moneda=gemas&cantidad=3&envolver=true

El método deberá utilizar los valores finalmente recibidos o aplicados en su respuesta.

Para:

Petición
/catalogo/objeto/7?moneda=gemas&cantidad=3&envolver=true

la respuesta deberá permitir comprobar, como mínimo:

Datos interpretados por el controlador
id = 7
moneda = gemas
cantidad = 3
envolver = true
Punto importante

No queremos una ruta diferente para cada combinación de opciones.

La ruta sigue siendo /catalogo/objeto/{id}. Los parámetros de consulta permiten modificar la petición sin cambiar el patrón atendido por @GetMapping.

6️⃣ Requisito 3: construir una búsqueda flexible​

Añade ahora una operación para:

Ruta de búsqueda
GET /catalogo/buscar

La búsqueda recibirá los siguientes datos:

ParámetroTipo JavaComportamiento
textoStringObligatorio.
categoriaStringOpcional, puede no aparecer.
rarezaStringValor por defecto todas.
precioMaxdoubleValor por defecto 250.
ordenStringValor por defecto nombre.
soloDisponiblesbooleanValor por defecto false.

Estas peticiones deben funcionar:

Búsquedas válidas
/catalogo/buscar?texto=cristal
/catalogo/buscar?texto=pocion&categoria=pociones
/catalogo/buscar?texto=anillo&rareza=epica&precioMax=150
/catalogo/buscar?texto=libro&orden=precio&soloDisponibles=true

La respuesta deberá mostrar claramente los criterios que terminaría utilizando una búsqueda.

Por ejemplo:

Respuesta orientativa
Búsqueda en Inventario Arcano
Texto: cristal
Categoría: todas
Rareza: todas
Precio máximo: 250.0
Orden: nombre
Solo disponibles: false

🟩 Parámetro que puede no existir​

categoria es diferente del resto: no tiene valor por defecto y puede no aparecer.

Decide cómo declararás el parámetro para que esta petición siga siendo válida:

/catalogo/buscar?texto=cristal

y cómo construirás la respuesta sin provocar errores cuando no haya categoría.

🟨 Parámetro realmente obligatorio​

texto sí debe aparecer.

Esta petición está incompleta:

/catalogo/buscar

No conviertas texto en opcional únicamente para conseguir que la URL funcione.

El objetivo es comprobar también qué hace Spring MVC cuando falta un dato que el método ha declarado como obligatorio.

7️⃣ Requisito 4: consultar una rareza concreta​

Añade una tercera operación con este patrón:

Patrón de ruta
GET /catalogo/rareza/{rareza}

La rareza forma parte de la ruta.

Además, la consulta aceptará:

ParámetroTipo JavaValor por defecto
ordenStringnombre.
limiteint10.

Ejemplos:

Consultas por rareza
/catalogo/rareza/comun
/catalogo/rareza/rara?orden=precio
/catalogo/rareza/epica?orden=precio&limite=5
/catalogo/rareza/legendaria?limite=2

La respuesta deberá permitir comprobar:

  • la rareza obtenida desde la ruta.
  • el criterio de ordenación.
  • el límite solicitado.

🟩 Compara esta ruta con la búsqueda​

Observa estas dos peticiones:

/catalogo/rareza/epica
/catalogo/buscar?texto=anillo&rareza=epica

En ambas aparece el valor epica, pero no cumple la misma función dentro de la URL.

Debes poder explicar por qué en un caso corresponde recibirlo desde la ruta y en el otro desde la query string.

8️⃣ Requisito 5: integrar las nuevas consultas en Inventario Arcano​

Las nuevas operaciones no deben quedar completamente desconectadas de la aplicación visual que ya construiste.

En la vista catalogo.html, añade una sección sencilla llamada, por ejemplo:

Consultas del mercader

Incluye al menos cuatro enlaces de prueba hacia distintas peticiones de esta actividad.

Por ejemplo:

Enlaces posibles
/catalogo/objeto/7
/catalogo/objeto/7?moneda=gemas&cantidad=2
/catalogo/buscar?texto=cristal&rareza=rara
/catalogo/rareza=...

El último ejemplo anterior está deliberadamente incompleto: escribe tú correctamente la URL de una consulta por rareza.

aviso

En esta actividad los nuevos métodos devuelven texto para que podamos observar con claridad los datos recibidos.

El resto de Inventario Arcano debe seguir utilizando sus vistas habituales. No sustituyas las páginas existentes del catálogo por estas respuestas de comprobación.

9️⃣ Comprueba la conversión automática de tipos​

Hasta ahora los valores de una URL parecen texto, pero Spring MVC intenta convertirlos al tipo Java que has declarado en el método.

Prueba expresamente:

Valores válidos
/catalogo/objeto/8?cantidad=4
/catalogo/objeto/8?envolver=true
/catalogo/buscar?texto=cristal&precioMax=79.95
/catalogo/rareza/rara?limite=3

Después prueba:

Valores incompatibles
/catalogo/objeto/abc
/catalogo/objeto/8?cantidad=muchas
/catalogo/buscar?texto=cristal&precioMax=barato
/catalogo/rareza/rara?limite=varios

No conviertas manualmente estos valores con Integer.parseInt() o Double.parseDouble().

Observa qué ocurre antes de que el método pueda ejecutarse.

🟩 Registra tus observaciones​

Anota brevemente qué respuesta HTTP observas en estos tres casos:

  1. Falta el parámetro obligatorio texto.
  2. Un valor no puede convertirse a int.
  3. Escribes una ruta que no existe.

Relaciona cada situación con lo que espera el controlador.

🔟 Pruebas mínimas obligatorias​

Comprueba al menos estas peticiones:

Detalle de objetos
/catalogo/objeto/4
/catalogo/objeto/4?moneda=gemas
/catalogo/objeto/4?cantidad=3&envolver=true
/catalogo/objeto/18?moneda=oro&cantidad=2
Búsquedas
/catalogo/buscar?texto=cristal
/catalogo/buscar?texto=pocion&categoria=pociones
/catalogo/buscar?texto=libro&rareza=rara&precioMax=120
/catalogo/buscar?texto=anillo&orden=precio&soloDisponibles=true
Consultas por rareza
/catalogo/rareza/comun
/catalogo/rareza/epica?orden=precio
/catalogo/rareza/legendaria?limite=3

Y comprueba también:

Situaciones incorrectas
/catalogo/buscar
/catalogo/objeto/abc
/catalogo/objeto/4?cantidad=muchas
/catalogo/buscar?texto=cristal&precioMax=barato

Después de las pruebas, vuelve a comprobar que las páginas de la Actividad 1 continúan funcionando:

/catalogo
/catalogo/pociones
/catalogo/pergaminos
/catalogo/artefactos
/catalogo/recomendados

1️⃣1️⃣ Requisitos técnicos​

La solución deberá cumplir todos estos requisitos:

  • Continuar sobre el proyecto Inventario Arcano de la Actividad 1.
  • Mantener operativas las rutas y vistas que ya existían.
  • Utilizar @Controller.
  • Mantener la ruta base /catalogo mediante @RequestMapping.
  • Utilizar @GetMapping para las nuevas operaciones.
  • Utilizar @PathVariable para recibir información incluida en la ruta.
  • Utilizar @RequestParam para recibir parámetros de consulta.
  • Incluir al menos un parámetro obligatorio.
  • Incluir al menos un parámetro opcional sin valor por defecto.
  • Utilizar varios parámetros con defaultValue.
  • Recibir valores como String, int, double y boolean.
  • Combinar @PathVariable y varios @RequestParam en una misma operación.
  • Permitir que Spring MVC realice la conversión de tipos.
  • Utilizar @ResponseBody únicamente en los nuevos métodos que devuelven las respuestas de comprobación.
  • Añadir enlaces de prueba desde la vista del catálogo.
  • Mantener la navegación y el aspecto visual de la aplicación existente.
peligro

Una solución basada en muchos métodos casi idénticos para valores concretos no cumple el objetivo.

Queremos que unas pocas rutas sean capaces de atender numerosas peticiones diferentes gracias a las variables de ruta y a los parámetros de consulta.

1️⃣2️⃣ Comprobación final​

Antes de dar la actividad por terminada, comprueba:

  • He continuado trabajando sobre el proyecto de la Actividad 1.
  • Las rutas anteriores siguen funcionando.
  • /catalogo/objeto/{id} admite distintos identificadores.
  • El identificador se convierte automáticamente a int.
  • La consulta de un objeto admite moneda, cantidad y envolver.
  • Los valores por defecto se aplican cuando los parámetros no aparecen.
  • /catalogo/buscar recibe un parámetro texto obligatorio.
  • categoria puede omitirse sin provocar un error en el método.
  • La búsqueda recibe correctamente double y boolean.
  • /catalogo/rareza/{rareza} obtiene la rareza desde la ruta.
  • La consulta por rareza permite modificar orden y limite.
  • He combinado @PathVariable y @RequestParam en una misma operación.
  • He probado valores que Spring puede convertir correctamente.
  • He probado valores incompatibles y he observado el resultado.
  • La vista del catálogo contiene enlaces hacia algunas de las nuevas consultas.
  • La aplicación sigue pudiendo recorrerse mediante la navegación creada anteriormente.

1️⃣3️⃣ Ampliación opcional: el comparador arcano​

Si terminas la parte obligatoria, añade una herramienta para comparar dos objetos del catálogo.

La ampliación no será necesaria para comenzar la Actividad 3.

Diseña una ruta que permita representar consultas como:

Ejemplos
/catalogo/comparar/4/9
/catalogo/comparar/4/9?criterio=precio
/catalogo/comparar/7/12?criterio=rareza&mostrarDetalles=true

La operación deberá recibir:

  • dos identificadores numéricos incluidos en la ruta.
  • un parámetro criterio con valor por defecto precio.
  • un parámetro booleano mostrarDetalles con valor por defecto false.

La respuesta deberá mostrar claramente los valores recibidos.

🟩 Reto de ampliación​

No copies directamente la estructura de uno de los métodos anteriores.

Antes de escribir el código, identifica:

  • qué dos valores forman parte de la ruta.
  • qué valores son opciones de la consulta.
  • qué tipos Java utilizarás.
  • qué parte común seguirá aportando @RequestMapping("/catalogo").

Añade, si quieres, un enlace al comparador desde la sección de consultas del mercader.

Esta funcionalidad es independiente del trabajo obligatorio y podrá mantenerse o eliminarse en las siguientes actividades.

📦 Cómo preparar la entrega​

Antes de entregar, comprueba que el proyecto compila y se ejecuta correctamente.

Preparar la entrega

Abre la terminal de IntelliJ IDEA desde:

View → Tool Windows → Terminal

Sitúate en la carpeta raíz del proyecto, donde se encuentra pom.xml.

Primero elimina los archivos generados durante la compilación:

Limpiar el proyecto
.\mvnw.cmd clean

Después genera directamente el archivo ZIP de entrega:

Crear el ZIP
tar -a -c -f ..\apellido-nombre-UT2-2.zip pom.xml mvnw mvnw.cmd .mvn src

El archivo apellido-nombre-UT2-2.zip se creará en la carpeta inmediatamente superior a la del proyecto.

El ZIP debe contener una estructura similar a:

Contenido de la entrega
pom.xml
mvnw
mvnw.cmd
.mvn/
src/
Antes de entregar

No incluyas archivos o carpetas generados automáticamente por Maven, IntelliJ IDEA o Git, como:

Archivos que no deben entregarse
target/
.idea/
.git/
out/
*.iml

No entregues únicamente la carpeta src.

El archivo pom.xml y el wrapper de Maven (mvnw, mvnw.cmd y .mvn/) forman parte del proyecto y permiten reconstruirlo correctamente en otro equipo.

Antes de subir el archivo, abre el ZIP y comprueba que contiene todos los elementos indicados.

Nombra el archivo siguiendo este formato:

Nombre del archivo
apellido-nombre-UT2-2.zip
