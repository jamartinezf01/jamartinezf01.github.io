Actividad 1. Organizamos Inventario Arcano

En esta actividad vamos a comenzar Inventario Arcano, una aplicación web ambientada en una tienda de productos mágicos.

Esta será la primera actividad de un proyecto que iremos ampliando durante la unidad. Por ahora no trabajaremos con parámetros de petición, datos dinámicos, colecciones ni condiciones de Thymeleaf. Nuestro objetivo será construir una estructura web coherente, repartir correctamente las responsabilidades entre controladores y conseguir que todas las páginas estén conectadas mediante navegación.

Objetivo

Construir la primera versión de Inventario Arcano utilizando varios controladores, rutas organizadas con @RequestMapping y @GetMapping, vistas Thymeleaf y recursos estáticos compartidos.

nota

Esta actividad es de práctica y no es evaluable. No requiere entrega ni tiene calificación asociada.

La parte de ampliación es opcional y no será necesaria para poder continuar con la Actividad 2.

Kit de recursos de Inventario Arcano

Para realizar esta actividad debes utilizar el kit de recursos proporcionado. Incluye la hoja de estilos, recursos gráficos y varios HTML estáticos que servirán como punto de partida visual de la aplicación.

👉 Descargar kit de recursos de Inventario Arcano

Entre los archivos de referencia encontrarás:

HTML proporcionados
inicio.html
catalogo.html
gremio.html
plantilla-base.html
recursos.html

inicio.html, catalogo.html y gremio.html son prototipos que puedes integrar en templates. plantilla-base.html sirve como punto de partida para crear las vistas que faltan y recursos.html permite consultar los elementos visuales disponibles.

No debes rediseñar la aplicación desde cero. Tu trabajo consiste en integrar estos recursos en Spring Boot, completar las vistas necesarias y relacionarlas correctamente con las rutas y los controladores.

1️⃣ Contexto de la aplicación​

Inventario Arcano es una pequeña tienda especializada en objetos mágicos. La aplicación permitirá consultar distintas zonas de la tienda desde el navegador.

En esta primera versión todavía no existen productos almacenados como objetos Java. Las páginas mostrarán contenido escrito directamente en las plantillas, porque queremos centrarnos en la relación:

Flujo que vamos a practicar
URL → controlador → método → vista

La tienda tendrá, como mínimo, estas áreas:

  • portada de la tienda.
  • catálogo.
  • gremio de artesanos.
  • información de la tienda.

No queremos una colección de páginas aisladas. Al terminar la actividad, la aplicación debe poder recorrerse desde el navegador mediante una navegación coherente.

2️⃣ Punto de partida​

Crea un proyecto Spring Boot llamado, por ejemplo:

Nombre orientativo del proyecto
inventario-arcano

El proyecto deberá incluir las dependencias necesarias para trabajar con:

  • Spring Web.
  • Thymeleaf.

Organiza el código de manera que los controladores se encuentren dentro de un paquete específico, por ejemplo:

Organización orientativa
src/main/java/...
├── InventarioArcanoApplication.java
└── controller/

Las vistas deberán almacenarse en:

Ubicación de las vistas
src/main/resources/templates/

Y los recursos visuales en:

Ubicación de recursos estáticos
src/main/resources/static/
aviso

No empieces creando todas las páginas sin pensar primero cómo se van a agrupar las rutas y qué controlador debería atender cada zona de la aplicación.

3️⃣ Diseña primero el mapa de navegación​

Antes de escribir los controladores, decide cómo vas a organizar las páginas.

La aplicación deberá atender, como mínimo, estas rutas:

Rutas obligatorias
/
/tienda
/contacto

/catalogo
/catalogo/pociones
/catalogo/pergaminos
/catalogo/artefactos
/catalogo/recomendados

/gremio
/gremio/alquimistas
/gremio/encantadores

Cada grupo representa una zona distinta de la aplicación.

🟩 Primera decisión​

Antes de programar, responde en un comentario dentro de tu código o en una breve nota personal:

  • ¿Cuántos controladores necesitas?
  • ¿Qué rutas debería atender cada uno?
  • ¿Dónde tiene sentido utilizar una ruta base con @RequestMapping?

No existe una única distribución posible, pero no se admite concentrar todas las rutas en un único controlador.

4️⃣ Requisito 1: separar la aplicación en controladores​

La solución deberá utilizar al menos tres controladores.

Una posible organización sería:

Organización orientativa
GeneralController
CatalogoController
GremioController

No tienes que utilizar exactamente esos nombres, pero cada controlador debe tener una responsabilidad clara.

🟩 Zona general​

Debe atender:

Rutas generales
/
/tienda
/contacto

🟨 Zona de catálogo​

Las rutas del catálogo comparten la raíz:

/catalogo

Por tanto, debes utilizar @RequestMapping a nivel de clase para evitar repetir esa parte en todos los métodos.

El controlador deberá atender:

Rutas del catálogo
/catalogo
/catalogo/pociones
/catalogo/pergaminos
/catalogo/artefactos
/catalogo/recomendados

🟧 Zona del gremio​

Deberá utilizar como ruta base:

/gremio

Y atender:

Rutas del gremio
/gremio
/gremio/alquimistas
/gremio/encantadores
aviso

Si defines @RequestMapping("/catalogo") en la clase, los métodos no deben volver a repetir /catalogo dentro de cada @GetMapping.

5️⃣ Requisito 2: decidir los nombres lógicos de las vistas​

Cada ruta deberá devolver una vista Thymeleaf almacenada en templates.

No queremos que todas las URL, métodos y plantillas tengan necesariamente el mismo nombre.

En al menos tres rutas, utiliza un nombre lógico de vista diferente al último segmento de la URL.

Por ejemplo:

Ejemplo de nombre lógico diferente
@GetMapping("/recomendados")
public String recomendados() {
    return "seleccion-del-mercader";
}

La URL sería:

/catalogo/recomendados

pero la plantilla podría llamarse:

seleccion-del-mercader.html

🟩 Comprueba que entiendes la diferencia​

Antes de continuar, identifica en tu aplicación un ejemplo de cada elemento:

  • URL pública.
  • método Java.
  • nombre lógico de vista.
  • archivo .html utilizado.

Los cuatro elementos están relacionados, pero no son lo mismo.

6️⃣ Requisito 3: completar las vistas de la aplicación​

Parte de los HTML incluidos en el kit y reutiliza su estructura visual. No es necesario volver a construir desde cero la cabecera, la navegación, las tarjetas o la distribución general.

Integra en templates las vistas proporcionadas que correspondan y crea, a partir de plantilla-base.html, las que todavía falten.

Como mínimo deberás disponer de vistas para todas las rutas obligatorias:

Vistas que necesita la aplicación
/
 /tienda
 /contacto

 /catalogo
 /catalogo/pociones
 /catalogo/pergaminos
 /catalogo/artefactos
 /catalogo/recomendados

 /gremio
 /gremio/alquimistas
 /gremio/encantadores

🟩 Portada​

La vista asociada a / puede partir de inicio.html. Debe presentar Inventario Arcano y permitir acceder a las principales zonas de la aplicación.

🟨 Catálogo​

La vista de /catalogo puede partir de catalogo.html.

Las páginas de pociones, pergaminos y artefactos deberás crearlas a partir de la plantilla base. Cada una incluirá:

  • un título y una breve introducción propia.
  • al menos tres productos ficticios escritos directamente en HTML.
  • enlaces para continuar navegando por el catálogo.

Por ahora esos productos no son objetos Java. El objetivo sigue siendo trabajar la estructura de rutas, controladores y vistas.

🟧 Recomendados​

La ruta /catalogo/recomendados deberá devolver una vista propia. Puedes reutilizar los componentes del kit, pero organiza el contenido de forma que se distinga de una categoría normal.

🟥 Gremio​

La vista de /gremio puede partir de gremio.html.

Crea también las vistas de alquimistas y encantadores utilizando plantilla-base.html. Deben presentar información relacionada con cada especialidad y mantener la navegación propia del gremio.

🟪 Tienda y contacto​

Crea las vistas correspondientes a /tienda y /contacto partiendo también de la plantilla base.

No es necesario introducir funcionalidades nuevas: basta con que tengan contenido coherente con la aplicación y se integren correctamente en la navegación.

Qué estamos practicando

Los HTML proporcionados resuelven parte del diseño visual, pero no resuelven la aplicación Spring Boot.

Debes decidir qué controlador atiende cada ruta, qué método corresponde a cada petición, qué nombre lógico devuelve y qué plantilla termina renderizándose.

7️⃣ Requisito 4: navegación global y navegación contextual​

La aplicación deberá tener dos niveles de navegación.

🟩 Navegación global​

Todas las páginas deberán permitir acceder, como mínimo, a:

Navegación global
Inicio
Catálogo
Gremio
La tienda
Contacto

🟨 Navegación contextual​

Además, las páginas del catálogo deberán permitir moverse entre:

Navegación del catálogo
Pociones
Pergaminos
Artefactos
Recomendados

Y las páginas del gremio deberán enlazar al menos con:

Navegación del gremio
Gremio
Alquimistas
Encantadores
Punto importante

No queremos una página desde la que se pueda entrar en todas las demás y páginas secundarias sin salida.

La navegación debe permitir recorrer la aplicación de forma razonable sin escribir las URL manualmente.

🟩 Decisión que debes tomar​

Decide qué enlaces pertenecen a la navegación global y cuáles solo tienen sentido dentro de una sección concreta.

No copies automáticamente todos los enlaces en todas las páginas.

8️⃣ Requisito 5: utilizar el kit visual de Inventario Arcano​

La aplicación utilizará el kit visual proporcionado para mantener una apariencia coherente, cuidada y profesional entre todas las vistas.

Coloca los recursos dentro de:

Recursos estáticos
src/main/resources/static/

La estructura podrá ser similar a:

Estructura visual orientativa
static/
├── css/
│   └── inventario-arcano.css
└── img/
    ├── logo-inventario-arcano.png
    ├── portada-inventario-arcano.png
    ├── pocion.png
    ├── pergamino.png
    ├── artefacto.png
    ├── cristal.png
    └── gremio.png

Todas las páginas deberán utilizar la misma hoja de estilos.

El aspecto visual debe ser coherente entre las distintas vistas.

No es necesario modificar el CSS proporcionado para completar la actividad.

tip

Puedes personalizar textos, combinaciones de clases o distribución de los bloques, pero el objetivo principal sigue siendo practicar Spring MVC y la organización de la aplicación, no diseñar una interfaz desde cero.

9️⃣ Pruebas mínimas obligatorias​

Comprueba todas estas rutas desde el navegador:

Batería mínima de pruebas
/
/tienda
/contacto
/catalogo
/catalogo/pociones
/catalogo/pergaminos
/catalogo/artefactos
/catalogo/recomendados
/gremio
/gremio/alquimistas
/gremio/encantadores

Además, comprueba que:

  • todas las páginas cargan el CSS común.
  • las imágenes utilizadas se cargan correctamente.
  • la navegación global funciona desde cualquier zona.
  • la navegación contextual funciona dentro del catálogo y del gremio.
  • cambiar el nombre lógico de una vista no obliga a cambiar su URL.
  • las rutas agrupadas con @RequestMapping funcionan como antes.
  • ninguna página principal obliga a escribir una URL manualmente para continuar navegando.

🔟 Requisitos técnicos​

La solución deberá cumplir todos estos requisitos:

  • Utilizar Spring Boot con Spring Web y Thymeleaf.
  • Utilizar @Controller.
  • Utilizar @GetMapping para las rutas concretas.
  • Utilizar @RequestMapping a nivel de clase en las zonas que comparten una ruta base.
  • Incluir al menos tres controladores con responsabilidades diferenciadas.
  • Mantener separadas las zonas general, catálogo y gremio.
  • Devolver nombres lógicos de vistas.
  • Utilizar en al menos tres casos un nombre lógico diferente al último segmento de la URL.
  • Almacenar las plantillas en src/main/resources/templates.
  • Utilizar una hoja de estilos común desde src/main/resources/static/css.
  • Utilizar recursos gráficos desde src/main/resources/static/img.
  • Disponer de navegación global y navegación contextual.
  • Mantener todas las rutas obligatorias accesibles desde el navegador.
  • La navegación entre las páginas debe realizarse mediante enlaces HTML.
  • El contenido HTML debe mantenerse en las plantillas y no construirse desde los controladores.
peligro

La actividad no consiste en crear muchas páginas independientes.

El objetivo es construir una aplicación web organizada, en la que las rutas estén agrupadas con criterio, los controladores tengan responsabilidades claras y las vistas formen una navegación coherente.

1️⃣1️⃣ Comprobación final​

Antes de dar la actividad por terminada, comprueba:

  • El proyecto arranca sin errores.
  • Existen al menos tres controladores.
  • Las responsabilidades están repartidas entre ellos de forma coherente.
  • Catálogo y gremio utilizan una ruta base con @RequestMapping.
  • Todas las rutas obligatorias funcionan.
  • Los métodos devuelven nombres lógicos de vista.
  • Al menos tres vistas tienen un nombre lógico diferente al último segmento de su URL.
  • Las plantillas están dentro de templates.
  • Los HTML proporcionados se han integrado y las vistas que faltaban se han creado a partir de la plantilla base.
  • Todas las páginas utilizan el mismo CSS.
  • Los recursos gráficos se sirven desde static.
  • Existe navegación global.
  • Existen navegaciones específicas para catálogo y gremio.
  • La aplicación puede recorrerse sin escribir manualmente las URL.

1️⃣2️⃣ Ampliación opcional: la Cámara Sellada​

Si terminas la parte obligatoria, puedes añadir una nueva zona llamada Cámara Sellada.

Esta ampliación no será necesaria para comenzar la Actividad 2 y puede eliminarse o dejarse sin modificar en las siguientes fases del proyecto.

Añade:

Rutas opcionales
/camara
/camara/reliquias
/camara/maldiciones

La ampliación deberá cumplir estas condiciones:

  • tener su propio controlador.
  • utilizar @RequestMapping("/camara").
  • disponer de tres vistas propias.
  • integrarse en la navegación de forma coherente.
  • reutilizar el mismo CSS y recursos visuales de Inventario Arcano.
  • incluir al menos una página con una composición HTML diferente al catálogo.

🟩 Reto adicional de ampliación​

Sin cambiar ninguna URL pública, reorganiza después las plantillas de la Cámara Sellada dentro de una subcarpeta:

Organización opcional de plantillas
templates/
└── camara/
    ├── inicio.html
    ├── reliquias.html
    └── maldiciones.html

Ajusta únicamente los nombres lógicos devueltos por el controlador para que las rutas sigan funcionando exactamente igual.

Esta parte sirve para practicar que la estructura interna de las vistas puede cambiar sin modificar las URL públicas de la aplicación.
