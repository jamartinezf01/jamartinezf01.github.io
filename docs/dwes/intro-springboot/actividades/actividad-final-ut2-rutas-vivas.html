Actividad final UT2.

Durante esta unidad hemos pasado de atender una petición HTTP con un controlador a generar páginas completas cuyo contenido depende de los datos preparados por la aplicación.

En esta práctica vas a construir una pequeña aplicación llamada Rutas Vivas, un catálogo de rutas de senderismo. El punto de partida será un conjunto de páginas HTML ya maquetadas, una hoja de estilos y varias imágenes. Tu trabajo consistirá en convertir esa maqueta estática en una aplicación Spring Boot con vistas Thymeleaf realmente dinámicas.

El proyecto es independiente de Inventario Arcano. No debes reutilizar sus controladores, clases Java ni plantillas.

Duración orientativa

2 horas de trabajo.

La maquetación visual principal ya está preparada para que el tiempo se dedique a los contenidos de Desarrollo Web en Entorno Servidor.

nota

Esta actividad está planteada como actividad final evaluable de la UT2.

Se valorará especialmente que seas capaz de decidir cómo organizar la solución utilizando los mecanismos estudiados, no que reproduzcas literalmente los ejemplos de los apuntes.

1️⃣ Punto de partida​

Crea un proyecto Spring Boot desde Spring Initializr con Maven y Java 21. Añade, como mínimo, las dependencias Spring Web y Thymeleaf. Puedes añadir también Spring Boot DevTools para facilitar el trabajo durante el desarrollo.

Descarga después el paquete de recursos proporcionado para la práctica:

👉 Recursos base — Rutas Vivas

El ZIP contiene:

Recursos proporcionados
html-base/
├── index.html
├── rutas.html
└── detalle.html

css/
└── estilos.css

img/
├── portada-rutas.svg
├── bosque-niebla.svg
├── costa-acantilados.svg
├── montana-lagos.svg
├── ribera-verde.svg
└── volcan-negro.svg

Los HTML son maquetas estáticas de referencia. Puedes reorganizarlos y adaptarlos cuando los conviertas en plantillas Thymeleaf, pero debes conservar la identidad visual general proporcionada.

aviso

El paquete de recursos no contiene la solución Spring Boot.

Tendrás que crear la estructura de la aplicación, sus clases Java, controladores y plantillas dinámicas.

2️⃣ Qué debe hacer la aplicación​

La aplicación debe disponer de una portada, un catálogo de rutas y una página de detalle.

La imagen muestra únicamente la estructura funcional que debe conseguir la aplicación. La organización de controladores, clases Java, datos del Model y plantillas Thymeleaf forma parte del trabajo que debes resolver.

🟩 Portada​

La URL:

/

debe mostrar la portada de Rutas Vivas utilizando una vista Thymeleaf y los recursos estáticos proporcionados.

Desde ella debe poder accederse al catálogo.

🟨 Catálogo​

La URL:

/rutas

debe mostrar una colección de rutas preparada en Java y enviada a la vista.

La maqueta incluida contiene cinco rutas que puedes utilizar como referencia para preparar los datos de la aplicación. El catálogo final no debe contener cinco tarjetas escritas manualmente: el HTML debe generarse a partir de los objetos recibidos por la plantilla.

El catálogo debe permitir además consultar rutas por dificultad utilizando un parámetro de la petición. Deben funcionar, como mínimo, ejemplos equivalentes a:

Peticiones de catálogo
/rutas
/rutas?dificultad=facil
/rutas?dificultad=media
/rutas?dificultad=dificil

Cuando no se indique dificultad, deben mostrarse todas las rutas.

Si un filtro no produce resultados, la página debe seguir siendo comprensible y mostrar un mensaje apropiado.

🟧 Detalle de una ruta​

Cada tarjeta del catálogo debe permitir acceder a una URL del tipo:

/rutas/3

El identificador debe determinar qué ruta se muestra.

La página de detalle debe presentar la información del objeto correspondiente y permitir volver al catálogo mediante una URL generada por Thymeleaf.

Si lo consideras útil, puedes añadir a la URL de detalle algún parámetro de consulta sencillo que modifique una pequeña parte de la información mostrada, siempre que no convierta la práctica en algo innecesariamente complejo.

3️⃣ Requisitos de desarrollo​

No se proporciona una secuencia de pasos. Decide cómo organizar las clases y métodos necesarios para conseguir el comportamiento anterior.

Tu solución debe demostrar el uso correcto de los mecanismos trabajados durante la UT2.

🟩 Controladores y datos de la petición​

La aplicación debe utilizar controladores Spring MVC para atender las distintas URL.

En algún punto de la solución deben intervenir:

  • rutas mediante @GetMapping.
  • una variable recibida desde la propia ruta.
  • al menos un parámetro recibido desde la query string con un comportamiento por defecto.

No crees una operación distinta para cada ruta de senderismo.

🟨 Modelo y vistas​

Los controladores deben preparar los datos necesarios y enviarlos a las plantillas mediante Model.

La aplicación deberá trabajar, como mínimo, con:

  • una clase Java que represente una ruta.
  • un objeto individual para la página de detalle.
  • una colección de objetos para el catálogo.

Los métodos que muestran páginas Thymeleaf deben devolver nombres lógicos de vista y no deben utilizar @ResponseBody.

🟧 Thymeleaf​

Las plantillas deberán utilizar los datos recibidos para construir el HTML final.

A lo largo de la aplicación deben aparecer de forma justificada los mecanismos estudiados en la unidad:

  • expresiones de datos ${...}.
  • expresiones de URL @{...}.
  • th:text.
  • th:href y th:src.
  • iteración sobre la colección del catálogo.
  • información de estado de la iteración.
  • contenido condicionado a los datos de una ruta.
  • elección entre varias alternativas de presentación.
  • modificación condicional de alguna clase CSS.

No se valorará añadir instrucciones Thymeleaf sin una finalidad real. Deben responder a necesidades de la interfaz.

🟥 Reutilización de la interfaz​

Las páginas proporcionadas repiten la cabecera y el pie.

En la solución final esas partes comunes deben mantenerse desde un único lugar y reutilizarse en las distintas vistas mediante fragmentos Thymeleaf.

Como mínimo deberán reutilizarse:

  • la cabecera con la navegación.
  • el pie de página.

4️⃣ Datos y comportamiento mínimo​

Puedes obtener los datos iniciales a partir del contenido de las maquetas proporcionadas.

Cada ruta debería disponer, al menos, de información equivalente a:

Información de una ruta
id (entero)
nombre (cadena)
zona (cadena)
dificultad (cadena)
distancia (decimal)
duracion (entero)
disponible (booleano)
imagen (cadena)
descripcion (cadena)

No se utilizará base de datos en esta práctica. Los objetos pueden prepararse directamente en Java.

El resultado final debe permitir comprobar situaciones diferentes. Por ejemplo, no todas las rutas deberían tener necesariamente la misma dificultad o el mismo estado de disponibilidad.

aviso

No añadas JPA, repositorios, servicios, formularios ni seguridad.

El objetivo de esta práctica es integrar correctamente los contenidos de la UT2, no adelantar los de unidades posteriores.

5️⃣ Pruebas mínimas antes de entregar​

Tu aplicación debe permitir comprobar, al menos, estas situaciones:

Rutas que deben poder probarse
/
/rutas
/rutas?dificultad=facil
/rutas?dificultad=dificil
/rutas/1
/rutas/3

Además, verifica que:

  • cambiar el filtro modifica los datos mostrados sin necesitar otra plantilla.
  • cada enlace de detalle contiene el identificador correspondiente.
  • el catálogo se genera a partir de una colección y no mediante tarjetas duplicadas manualmente.
  • las decisiones de presentación cambian cuando cambian los datos.
  • las imágenes y el CSS se sirven desde static y sus URL se generan correctamente.
  • cabecera y pie se reutilizan mediante fragmentos.
  • al inspeccionar el HTML recibido por el navegador no aparecen instrucciones Thymeleaf pendientes de procesar.

6️⃣ Evidencias y evaluación​

Se revisará tanto el funcionamiento de la aplicación como la organización del código entregado.

🟩 Resultado de aprendizaje​

Esta práctica recoge contenidos asociados al RA2 de la unidad.

RA trabajado

RA2. Escribe sentencias ejecutables por un servidor web reconociendo y aplicando procedimientos de integración del código en lenguajes de marcas.

🟧 Qué se tendrá en cuenta​

La revisión se centrará en cuatro aspectos:

  1. Funcionamiento. Las URL solicitadas funcionan y producen páginas coherentes.
  2. Integración servidor-vista. Los datos llegan desde los controladores mediante Model y las plantillas los utilizan correctamente.
  3. Generación dinámica. Colecciones, condiciones, URL y fragmentos se utilizan con sentido y evitan duplicaciones innecesarias.
  4. Organización. El código es comprensible y mantiene separadas la preparación de los datos y su presentación.
peligro

Una solución basada principalmente en HTML estático, aunque visualmente se parezca a las maquetas proporcionadas, no demuestra los objetivos de la práctica.
