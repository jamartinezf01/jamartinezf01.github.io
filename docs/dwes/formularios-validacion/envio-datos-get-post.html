2. Envío de datos con GET y POST

En la UT2 ya aprendimos a trabajar con rutas y parámetros en Spring Boot mediante @GetMapping, @RequestParam y Model. Ahora partiremos un paso antes: veremos qué ocurre cuando esos parámetros proceden de un formulario que ha rellenado el usuario.

Además, introduciremos POST y @PostMapping, necesarios para procesar formularios que representan envíos o acciones sobre la aplicación.

Idea principal

El recorrido que nos interesa en este punto es:

formulario → petición HTTP → controlador Spring Boot

1️⃣ Del formulario a la petición HTTP​

Cuando el usuario pulsa un botón de tipo submit, el navegador prepara una petición HTTP. Dos atributos del elemento <form> determinan cómo se enviará:

  • action indica a qué URL se enviará la petición.
  • method indica qué método HTTP se utilizará.

En los formularios HTML tradicionales trabajaremos principalmente con GET y POST.

La diferencia importante no está en el aspecto del formulario, sino en cómo se construye la petición y qué intención expresa.

2️⃣ Enviar un formulario mediante GET​

GET se utiliza para solicitar o consultar información. Cuando un formulario utiliza este método, sus datos se incorporan normalmente a la URL como parámetros de consulta.

Formulario de búsqueda enviado mediante GET
<form action="/buscar" method="get">
  <label for="texto">Texto de búsqueda</label>
  <input type="text" id="texto" name="texto">

  <button type="submit">Buscar</button>
</form>

Si el usuario escribe spring boot, el navegador puede generar una URL equivalente a:

URL generada al enviar el formulario
/buscar?texto=spring+boot

La parte situada después de ? es la cadena de consulta o query string. Si hay varios campos con atributo name, los parámetros se separan con &:

URL con varios parámetros de consulta
/productos?categoria=libros&orden=precio

El navegador se encarga de codificar correctamente los valores, por lo que no necesitamos construir manualmente la cadena de consulta.

🟩 Cuándo tiene sentido utilizar GET​

GET encaja bien cuando el formulario sirve para buscar, consultar, filtrar u ordenar información sin pretender modificar el estado de la aplicación.

Por ejemplo:

  • Buscar libros por título.
  • Filtrar productos por categoría.
  • Ordenar un listado.
  • Consultar información por fecha o estado.

Además, como los parámetros forman parte de la URL, una búsqueda puede copiarse, compartirse o guardarse como marcador manteniendo sus criterios.

aviso

No debemos utilizar GET para acciones cuyo objetivo sea crear, modificar o eliminar información en el servidor.

Tampoco debemos enviar mediante la URL datos que no queremos que queden visibles en la barra de direcciones, el historial del navegador o determinados registros intermedios.

3️⃣ Enviar un formulario mediante POST​

POST se utiliza habitualmente cuando enviamos información para que el servidor la procese y la operación puede producir un cambio en la aplicación, por ejemplo registrar un usuario, enviar una inscripción, crear un comentario o guardar datos.

Formulario de registro enviado mediante POST
<form action="/registro" method="post">
  <label for="nombre">Nombre</label>
  <input type="text" id="nombre" name="nombre">

  <label for="email">Correo electrónico</label>
  <input type="email" id="email" name="email">

  <button type="submit">Registrar</button>
</form>

Si el usuario introduce Ana y ana@ejemplo.com, podemos representar de forma simplificada la petición así:

Representación simplificada de una petición POST
POST /registro
Content-Type: application/x-www-form-urlencoded

nombre=Ana&email=ana%40ejemplo.com
en este ejemplo

La ruta sigue siendo /registro, pero los valores del formulario no se añaden a la URL como ocurre normalmente con GET.

En un formulario HTML convencional, los datos se envían habitualmente en el cuerpo de la petición utilizando application/x-www-form-urlencoded, es decir, como pares nombre-valor codificados.

🟩 POST no significa que los datos estén cifrados​

Que los valores no aparezcan en la barra de direcciones no significa que POST los cifre. El método HTTP y el cifrado de la comunicación son cuestiones diferentes. Para proteger los datos durante el transporte utilizamos HTTPS.

peligro

No debemos decir que POST es «seguro» simplemente porque los datos no aparecen en la URL.

GET o POST determina cómo planteamos la petición. HTTPS protege la comunicación durante el transporte.

🟨 Otros tipos de envío​

En esta unidad trabajaremos con datos sencillos de formulario. Existen otras codificaciones, como multipart/form-data, utilizada entre otros casos para enviar archivos. La veremos en el punto 7, una vez completado el flujo principal de los formularios.

4️⃣ Recibir los datos en Spring Boot​

Aquí reutilizamos conocimientos de la UT2. Ya sabemos que @RequestParam permite obtener parámetros de una petición y que @GetMapping asocia una ruta con peticiones GET.

Ahora nos interesa conectar lo que envía el formulario con el controlador.

🟩 Un formulario GET llega a un @GetMapping​

El formulario anterior envía un parámetro llamado texto, por lo que podemos recibirlo como ya hicimos en la UT2:

Recepción de un dato enviado por un formulario GET
@GetMapping("/buscar")
public String buscar(@RequestParam String texto, Model model) {
    model.addAttribute("textoBuscado", texto);
    return "resultado-busqueda";
}

La novedad no está en @RequestParam, sino en de dónde ha salido ese parámetro:

Recorrido del parámetro desde el formulario
name="texto" → GET /buscar?texto=... → @RequestParam String texto
información

Spring no recibe un <input> HTML.

El navegador transforma el formulario en una petición HTTP y Spring trabaja con los datos de esa petición.

🟨 @PostMapping: recibir una petición POST​

Para atender una petición POST utilizamos @PostMapping:

Recepción de datos enviados mediante POST
@PostMapping("/registro")
public String registrar(
        @RequestParam String nombre,
        @RequestParam String email,
        Model model) {

    model.addAttribute("nombre", nombre);
    model.addAttribute("email", email);

    return "resultado-registro";
}
en este ejemplo

@PostMapping("/registro") indica que este método atenderá peticiones POST dirigidas a /registro.

Los @RequestParam recuperan los parámetros nombre y email que el navegador ha construido a partir de los atributos name del formulario.

Model ya se trabajó en la UT2. Aquí simplemente lo reutilizamos para mostrar los valores recibidos en una vista.

Como devolvemos una vista Thymeleaf, no utilizamos @ResponseBody.

🟧 Deben coincidir la ruta, el método y los nombres​

Para que el flujo funcione correctamente deben encajar tres elementos:

FormularioControlador
action="/registro"@PostMapping("/registro")
method="post"@PostMapping
name="nombre"@RequestParam String nombre
name="email"@RequestParam String email

Si una de estas relaciones no coincide, el formulario no será procesado como esperamos.

5️⃣ GET y POST expresan intenciones diferentes​

GET y POST no deberían elegirse simplemente por comodidad. Nos ayudan a expresar la intención de la petición.

AspectoGETPOST
Uso habitualConsultar información.Enviar información para procesarla o provocar un cambio.
Datos de un formulario sencilloEn la URL, como parámetros de consulta.Normalmente en el cuerpo de la petición.
Visibles en la barra de direccionesSí.No como datos del cuerpo.
Facilita compartir una consulta mediante su URLSí.No de la misma forma.
EjemplosBuscar, filtrar, ordenar.Registrar, crear, enviar una inscripción.
Anotación habitual en Spring Boot@GetMapping.@PostMapping.
nota

Una petición POST también puede tener parámetros en su URL. La tabla resume el funcionamiento habitual de los formularios sencillos que estamos utilizando, no una prohibición técnica absoluta.

🟩 Una regla práctica para comenzar​

Podemos preguntarnos:

¿El usuario está consultando información o está enviando datos para que la aplicación realice una operación?

Si está consultando, normalmente pensaremos en GET. Si está enviando datos para crear, registrar o procesar algo, normalmente pensaremos en POST.

6️⃣ Errores frecuentes al conectar formulario y controlador​

🟩 La ruta no coincide​

Formulario dirigido a una ruta
<form action="/registro" method="post">
Controlador asociado a una ruta diferente
@PostMapping("/registrar")

/registro y /registrar son rutas diferentes, por lo que ese método no atenderá la petición.

🟨 El método HTTP no coincide​

Formulario configurado para enviar mediante POST
<form action="/registro" method="post">

no corresponde con:

Controlador configurado para recibir GET
@GetMapping("/registro")
public String registrar() {
    return "resultado";
}

La ruta coincide, pero el método HTTP no.

🟧 El atributo name no coincide con el parámetro esperado​

Campo que envía un parámetro llamado correo
<input type="email" name="correo">

no coincide directamente con:

Parámetro que espera un nombre diferente
@RequestParam String email

Podemos cambiar el name o indicar expresamente qué parámetro esperamos:

Recepción explícita de un parámetro con otro nombre
@RequestParam("correo") String email

🟥 Confundir POST con validación​

Utilizar POST no comprueba que el correo sea correcto, que el nombre no esté vacío o que una edad esté dentro de un intervalo. La validación será otro paso de esta unidad.

7️⃣ Qué debemos haber entendido antes de continuar​

Antes de seguir debemos tener claras cinco ideas:

  • Un formulario genera una petición HTTP cuando se envía.
  • action determina la URL y method determina si utilizamos GET o POST.
  • GET incorpora normalmente los datos de un formulario sencillo a la URL; POST los envía normalmente en el cuerpo de la petición.
  • @RequestParam, @GetMapping y @PostMapping permiten recoger esos datos en Spring Boot.
  • Formulario y controlador deben coincidir en ruta, método HTTP y nombres de los parámetros.

También debemos recordar que POST no cifra los datos y que Spring recibe parámetros de una petición HTTP, no elementos HTML directamente.

Siguiente paso

Con uno o dos campos, utilizar varios @RequestParam resulta manejable.

Pero un formulario real puede tener nombre, apellidos, correo, fecha, opciones seleccionadas y muchos campos más.

En el siguiente punto veremos cómo Spring puede agrupar esos datos automáticamente en un objeto Java mediante binding.
