8. Validaciones personalizadas

Hasta ahora hemos trabajado con restricciones estándar de Jakarta Validation, como @NotBlank, @Email, @Min, @Max, @Pattern o @Past. Estas anotaciones cubren una parte importante de los formularios habituales.

Sin embargo, en una aplicación real puede aparecer una necesidad distinta: que la regla que queremos comprobar no exista ya hecha.

Por ejemplo:

  • Una persona debe ser mayor de edad.
  • El correo debe pertenecer a un dominio concreto.
  • El nombre de usuario no puede contener determinadas palabras.
  • Un archivo debe tener una extensión concreta.

En esos casos no basta con elegir una anotación estándar. Necesitamos crear una restricción personalizada.

Idea principal

Una validación personalizada nos permite seguir usando el mismo flujo que ya conocemos:

formulario → binding → @Valid → BindingResult → Thymeleaf.

La novedad está en que ahora la regla de validación la definimos nosotros.

1️⃣ Cuándo tiene sentido una validación personalizada​

No debemos crear restricciones personalizadas porque sí. Antes conviene comprobar si el problema ya se resuelve con una anotación estándar.

Por ejemplo, si un campo debe estar informado, usamos @NotBlank. Si debe seguir el formato de un correo, usamos @Email. Si queremos limitar una longitud, usamos @Size.

La validación personalizada aparece cuando la regla expresa una condición de negocio o una comprobación específica de nuestra aplicación.

Un ejemplo muy claro es este:

Propiedad con una regla que @Past no cubre del todo
private LocalDate fechaNacimiento;

Con una anotación estándar podríamos hacer esto:

Comprobar solo que la fecha pertenece al pasado
@Past(message = "La fecha debe ser anterior a hoy")
private LocalDate fechaNacimiento;

Esto comprueba que la fecha no sea futura, pero no garantiza que la persona tenga 18 años o más. Una fecha de hace diez años también está en el pasado.

Por tanto, la regla real que queremos expresar es otra:

La fecha de nacimiento debe corresponder a una persona que ya haya cumplido 18 años.

Ahí es donde tiene sentido crear nuestra propia anotación.

2️⃣ El ejemplo que vamos a construir​

Vamos a trabajar con un objeto de formulario que utiliza una fecha de nacimiento en lugar de una edad escrita a mano.

Objeto de formulario con fecha de nacimiento
public class RegistroForm {
    private LocalDate fechaNacimiento;
}

La idea es crear una nueva anotación:

Restricción personalizada que queremos usar
@MayorDeEdad

y aplicarla así:

Uso de la nueva restricción en el formulario
@NotNull(message = "La fecha de nacimiento es obligatoria")
@MayorDeEdad(message = "Debes tener al menos 18 años")
private LocalDate fechaNacimiento;

Con esto estamos separando dos responsabilidades:

  • @NotNull comprueba si el dato existe.
  • @MayorDeEdad comprueba si la fecha corresponde a una persona de 18 años o más.
consejo

Esta separación es importante.

Una validación personalizada no tiene por qué hacerlo todo. Lo normal es combinarla con restricciones estándar.

3️⃣ Primera pieza: la anotación personalizada​

La primera pieza es la anotación que colocaremos sobre la propiedad.

MayorDeEdad.java
import jakarta.validation.Constraint;
import jakarta.validation.Payload;

import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = MayorDeEdadValidator.class)
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface MayorDeEdad {

    String message() default "Debes ser mayor de edad";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};
}
en este ejemplo

@Constraint indica que estamos definiendo una restricción de Jakarta Validation.

Con validatedBy = MayorDeEdadValidator.class le decimos qué clase contendrá la lógica que comprobará si el valor es válido o no.

@Target(ElementType.FIELD) indica que la usaremos sobre propiedades del objeto.

@Retention(RetentionPolicy.RUNTIME) permite que esta anotación esté disponible en tiempo de ejecución, que es cuando se realiza la validación.

El método message() define el mensaje por defecto que se mostrará si la regla falla.

groups() y payload() forman parte de la estructura habitual de una restricción personalizada. En esta unidad no necesitamos profundizar en ellos, pero deben estar presentes.

Podemos resumir esta idea así:

Relación entre anotación y validador
@MayorDeEdad
      ↓
MayorDeEdadValidator
      ↓
contiene la lógica real de comprobación

4️⃣ Segunda pieza: la clase validadora​

La anotación por sí sola no valida nada. Solo identifica que existe una regla llamada @MayorDeEdad.

La lógica real se escribe en una clase que implemente ConstraintValidator.

MayorDeEdadValidator.java
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

import java.time.LocalDate;

public class MayorDeEdadValidator
        implements ConstraintValidator<MayorDeEdad, LocalDate> {

    @Override
    public boolean isValid(
            LocalDate fechaNacimiento,
            ConstraintValidatorContext context) {

        if (fechaNacimiento == null) {
            return true;
        }

        LocalDate fechaLimite = LocalDate.now().minusYears(18);

        return !fechaNacimiento.isAfter(fechaLimite);
    }
}
en este ejemplo

ConstraintValidator<MayorDeEdad, LocalDate> significa que esta clase implementa la validación de la anotación @MayorDeEdad y que se aplicará sobre valores de tipo LocalDate.

El método isValid() devuelve:

  • true cuando el valor cumple la regla.
  • false cuando no la cumple.

La lógica que hemos usado es sencilla:

  1. Calculamos la fecha correspondiente a hace 18 años.
  2. Comprobamos que la fecha introducida no sea posterior a esa fecha límite.

Si la fecha de nacimiento es posterior, entonces la persona todavía no ha cumplido 18 años.

🟩 Un ejemplo con fechas reales​

Supongamos que hoy es:

Fecha actual del ejemplo
21/10/2026

Entonces la fecha límite sería:

Fecha límite para tener ya 18 años
21/10/2008

A partir de ahí:

  • 20/10/2008 sería válida.
  • 21/10/2008 también sería válida.
  • 22/10/2008 ya no sería válida.

🟨 ¿Por qué devolvemos true si el valor es null?​

En muchas primeras implementaciones surge esta duda:

Tratamiento de valores nulos
if (fechaNacimiento == null) {
    return true;
}

Lo hacemos así porque la obligación de informar el dato no pertenece a @MayorDeEdad, sino a otra restricción, por ejemplo @NotNull.

Si no lo hiciéramos así, mezclaríamos dos responsabilidades distintas:

  • comprobar si el dato existe.
  • comprobar si el dato representa una persona mayor de edad.

5️⃣ Aplicar la restricción al objeto del formulario​

Una vez creadas la anotación y la clase validadora, podemos utilizarlas en nuestro formulario igual que usamos cualquier otra restricción.

Propiedad con varias restricciones combinadas
@NotNull(message = "La fecha de nacimiento es obligatoria")
@MayorDeEdad(message = "Debes tener al menos 18 años")
private LocalDate fechaNacimiento;

Esto encaja perfectamente con el resto del objeto:

Ejemplo de formulario con fecha de nacimiento
public class RegistroForm {

    @NotBlank(message = "El nombre es obligatorio")
    private String nombre;

    @NotNull(message = "La fecha de nacimiento es obligatoria")
    @MayorDeEdad(message = "Debes tener al menos 18 años")
    @DateTimeFormat(iso = DateTimeFormat.ISO.DATE)
    private LocalDate fechaNacimiento;

    @Email(message = "Introduce un correo válido")
    private String email;
}

@DateTimeFormat no valida nada: indica el formato de la fecha para que coincida con el de input type="date", como vimos en el punto 3.

Desde este momento, @Valid también ejecutará nuestra nueva regla.

6️⃣ Qué ocurre en el controlador​

Una de las ventajas de este enfoque es que el controlador prácticamente no cambia.

El controlador usa @Valid como siempre
@PostMapping("/registro")
public String procesarRegistro(
        @Valid @ModelAttribute("form") RegistroForm form,
        BindingResult resultado) {

    if (resultado.hasErrors()) {
        return "registro";
    }

    return "resultado";
}
en este ejemplo

El controlador no necesita conocer los detalles internos de @MayorDeEdad.

Su trabajo sigue siendo el mismo:

  • recibir el objeto.
  • comprobar si hay errores con BindingResult.
  • devolver la misma vista si existen errores.
  • continuar el procesamiento si todo es correcto.

Eso hace que la validación siga quedando bien organizada y no terminemos escribiendo comprobaciones manuales dentro del método del controlador.

7️⃣ Cómo se muestra el error en la vista​

Desde el punto de vista de Thymeleaf, una restricción personalizada se comporta igual que las restricciones estándar.

Mostrar el mensaje de error en Thymeleaf
<label for="fechaNacimiento">Fecha de nacimiento</label>

<input type="date"
       id="fechaNacimiento"
       th:field="*{fechaNacimiento}"
       th:errorclass="campo-error">

<p th:if="${#fields.hasErrors('fechaNacimiento')}"
   th:errors="*{fechaNacimiento}"
   class="mensaje-error">
</p>

Si el usuario introduce una fecha que no cumple la regla, el error se añadirá a BindingResult y Thymeleaf podrá mostrarlo junto al campo.

8️⃣ Errores frecuentes o ideas que conviene evitar​

Al introducir validaciones personalizadas aparecen varios errores típicos.

🟩 Pensar que siempre hay que crear una restricción propia​

No es así. Primero debemos comprobar si ya existe una anotación estándar adecuada.

Si la regla se resuelve con @NotBlank, @Size, @Pattern o @Email, no tiene sentido complicarlo más.

🟨 Mezclar demasiadas responsabilidades en la misma validación​

Una restricción como @MayorDeEdad no debería encargarse también de comprobar si el campo viene vacío.

Es mejor combinar varias anotaciones pequeñas y claras.

🟧 Hacer la comprobación en el controlador en vez de en la validación​

Podríamos escribir un if manual dentro del @PostMapping, pero perderíamos varias ventajas:

  • La regla dejaría de estar cerca del dato.
  • El objeto sería menos expresivo.
  • Thymeleaf no integraría el error de forma tan natural.
  • El código del controlador crecería innecesariamente.
nota

Esto se aplica a reglas que dependen solo del valor del campo. Las que dependen del estado de la aplicación, como un correo ya registrado, sí se comprueban en el controlador y se añaden con rejectValue(), como vimos en el punto 5.

9️⃣ Actividades voluntarias de ampliación​

Si quieres practicar un poco más, puedes probar alguna de estas propuestas.

🟩 Actividad voluntaria 1. Mayoría de edad con LocalDate​

Sustituye un campo edad de tipo Integer por un campo fechaNacimiento de tipo LocalDate.

Después:

  • crea @MayorDeEdad.
  • aplícala al formulario.
  • muestra el mensaje de error en la vista.

Prueba al menos tres casos:

  • una persona que ya haya cumplido 18 años.
  • una persona que cumpla 18 años hoy.
  • una persona que todavía tenga 17 años.

🟨 Actividad voluntaria 2. Correo de dominio educativo​

Crea una restricción personalizada como @CorreoEducativo que solo acepte direcciones terminadas, por ejemplo, en @educarex.es.

La idea no es sustituir a @Email, sino combinar ambas:

Combinación de validaciones en un correo
@Email(message = "Introduce un correo válido")
@CorreoEducativo(message = "Debes usar tu correo educativo")
private String email;

Así practicarás otra validación personalizada sobre un tipo String.

🟧 Actividad voluntaria 3. Archivo PDF obligatorio en una solicitud​

Partiendo del DocumentoForm del punto 7, crea una validación personalizada como @ArchivoPdf que compruebe que el archivo subido termina en .pdf. En este caso el validador implementará ConstraintValidator<ArchivoPdf, MultipartFile>.

No hace falta desarrollar una solución profesional completa. Basta con entender la idea: también podemos crear reglas propias para datos que no son solo texto o números.

🟥 Actividad voluntaria 4. Palabras no permitidas en un campo de texto​

Imagina un campo observaciones en el que no queremos aceptar ciertas palabras concretas.

Podrías crear una restricción como @SinPalabrasProhibidas y comprobar si el texto contiene alguna de ellas.

Esta propuesta ya es algo más abierta, pero resulta útil para entender que las validaciones personalizadas sirven para expresar reglas muy ligadas a la lógica de nuestra aplicación.

🔟 Qué debemos quedarnos de esta ampliación​

No necesitamos memorizar todos los detalles de la sintaxis, pero sí comprender bien la idea general.

Una validación personalizada se construye con dos piezas:

  • una anotación que aplicamos a la propiedad.
  • una clase validadora que implementa ConstraintValidator.

Después, todo encaja con el mismo sistema que ya conocemos:

  • el formulario se bindea a un objeto.
  • @Valid ejecuta las restricciones.
  • BindingResult recoge los errores.
  • Thymeleaf los muestra en la vista.
Resumen final

Usamos una validación personalizada cuando la aplicación necesita expresar una regla que las anotaciones estándar no cubren de forma directa.

En esta unidad no vamos a convertirlo en contenido central, pero sí conviene conocer la idea porque ayuda a entender hasta dónde puede llegar el sistema de validación de Spring Boot con Jakarta Validation.
