3. Binding de formularios con objetos Java

En el apartado anterior hemos visto cómo un formulario genera una petición HTTP y cómo Spring Boot puede recibir sus parámetros. Para formularios pequeños, @RequestParam sigue siendo una solución perfectamente válida.

Cuando varios datos pertenecen al mismo formulario, resulta más cómodo tratarlos como una unidad. En lugar de recibir nombre, correo, ciclo y otros valores por separado, podemos pedir a Spring que los reúna en un objeto Java.

Este proceso se denomina data binding o, simplemente, binding.

Idea principal

El binding permite convertir los parámetros recibidos en una petición en propiedades de un objeto Java.

parámetros de la petición → binding → objeto Java

En este punto reutilizaremos Model y th:each, ya trabajados en la UT2. Tampoco validaremos todavía los datos ni los guardaremos en una base de datos: primero necesitamos comprender cómo se construye y utiliza el objeto que representa el formulario.

1️⃣ Por qué pasar de parámetros sueltos a un objeto​

Imaginemos un formulario de inscripción con tres campos:

Formulario de inscripción con varios datos
<form action="/inscripcion" method="post">
  <label for="nombre">Nombre</label>
  <input type="text" id="nombre" name="nombre">

  <label for="email">Correo electrónico</label>
  <input type="email" id="email" name="email">

  <label for="ciclo">Ciclo</label>
  <input type="text" id="ciclo" name="ciclo">

  <button type="submit">Enviar</button>
</form>

Podríamos recibir los tres valores individualmente:

Recepción de los campos como parámetros independientes
@PostMapping("/inscripcion")
public String procesarInscripcion(
        @RequestParam String nombre,
        @RequestParam String email,
        @RequestParam String ciclo) {

    return "resultado";
}

Este código no es incorrecto. Para uno o dos parámetros puede ser la opción más sencilla. El problema aparece cuando el formulario crece: el método acumula parámetros y los datos que pertenecen a una misma operación quedan dispersos.

Podemos agruparlos en una clase Java:

Objeto Java que agrupa los datos de la inscripción
public class InscripcionForm {

    private String nombre;
    private String email;
    private String ciclo;

    public InscripcionForm() {
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }

    public String getCiclo() {
        return ciclo;
    }

    public void setCiclo(String ciclo) {
        this.ciclo = ciclo;
    }
}
en este ejemplo

InscripcionForm es una clase Java sencilla cuyas propiedades representan los datos del formulario.

Utilizamos propiedades privadas, un constructor sin argumentos y métodos get y set para que Spring pueda trabajar con esos datos.

Esta clase no representa una tabla de una base de datos ni una entidad JPA. En esta unidad su función es únicamente agrupar la información que entra y sale del formulario.

consejo

Una clase específica para el formulario también deja claro qué información esperamos recibir. No es necesario que un formulario pueda modificar todas las propiedades de otros objetos de la aplicación.

2️⃣ Cómo realiza Spring el binding​

El navegador no envía objetos Java. Envía parámetros de la petición, por ejemplo:

Datos enviados por el formulario
nombre=Ana
email=ana@ejemplo.com
ciclo=DAW

Spring puede vincular esos nombres con las propiedades de InscripcionForm:

Correspondencia entre parámetros y propiedades
nombre  →  InscripcionForm.nombre
email   →  InscripcionForm.email
ciclo   →  InscripcionForm.ciclo

La coincidencia de los nombres es fundamental. Spring trabaja con los parámetros de la petición, no con los elementos HTML directamente.

🟩 Recibir el objeto con @ModelAttribute​

Podemos pedir directamente a Spring que trabaje con un objeto InscripcionForm:

Recepción del formulario mediante @ModelAttribute
@PostMapping("/inscripcion")
public String procesarInscripcion(
        @ModelAttribute("inscripcion") InscripcionForm inscripcion) {

    System.out.println(inscripcion.getNombre());
    System.out.println(inscripcion.getEmail());
    System.out.println(inscripcion.getCiclo());

    return "resultado";
}
en este ejemplo

@ModelAttribute("inscripcion") indica que el parámetro del método es un objeto asociado al modelo con el nombre inscripcion.

Spring aplica el binding sobre ese objeto y el controlador lo recibe con sus propiedades ya rellenadas. Además, queda disponible en el modelo con ese mismo nombre, algo especialmente útil al trabajar con Thymeleaf.

En términos generales, Spring toma los parámetros recibidos, busca propiedades compatibles, realiza conversiones básicas cuando son necesarias y asigna los valores al objeto.

🟨 Binding y conversión de tipos​

El binding también puede realizar conversiones básicas cuando una propiedad no es String:

Objeto de formulario con una propiedad numérica
public class InscripcionForm {

    private String nombre;
    private Integer edad;

    // Constructor, getters y setters.
}

Si la petición contiene:

Valor textual que debe convertirse a Integer
nombre=Ana
edad=20

Spring intentará convertir el texto "20" a Integer antes de asignarlo a edad.

aviso

Binding y validación no son lo mismo.

Que Spring pueda convertir -5 a un Integer no significa que una edad de -5 sea válida. El binding traslada y convierte datos, la validación comprobará después si cumplen las reglas de la aplicación.

3️⃣ El objeto también participa al mostrar el formulario​

El objeto no solo sirve para recibir datos. Con Thymeleaf también podemos utilizarlo como respaldo del formulario cuando mostramos inicialmente la página.

Preparación del objeto que respaldará el formulario
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {
    model.addAttribute("inscripcion", new InscripcionForm());
    return "inscripcion";
}
en este ejemplo

Añadimos al Model un objeto InscripcionForm vacío con el nombre inscripcion. Thymeleaf podrá utilizarlo después como objeto asociado al formulario.

Así, el recorrido funciona en dos sentidos:

  • al mostrar la página, el controlador proporciona un objeto a la vista.
  • al enviar el formulario, los parámetros vuelven a poblar un objeto del mismo tipo.
Idea principal

El objeto del formulario tiene una doble utilidad:

  • sirve de respaldo a la vista cuando mostramos el formulario.
  • recibe los valores enviados cuando procesamos la petición.

4️⃣ Vincular Thymeleaf con el objeto: th:object y th:field​

Thymeleaf ofrece dos atributos especialmente importantes para trabajar con formularios respaldados por objetos: th:object y th:field.

🟩 Seleccionar el objeto con th:object​

Si el controlador ha añadido un atributo llamado inscripcion, podemos asociarlo al formulario:

Formulario asociado al objeto inscripcion
<form th:action="@{/inscripcion}"
      th:object="${inscripcion}"
      method="post">

  <!-- Campos del formulario. -->

</form>

th:object="${inscripcion}" selecciona el objeto sobre el que trabajarán los campos del formulario.

aviso

Para utilizar th:object="${inscripcion}", debe existir un atributo llamado inscripcion cuando Thymeleaf renderiza la vista.

🟨 Vincular cada campo con th:field​

Dentro del formulario podemos asociar cada control a una propiedad del objeto:

Campos vinculados a propiedades mediante th:field
<form th:action="@{/inscripcion}"
      th:object="${inscripcion}"
      method="post">

  <label for="nombre">Nombre</label>
  <input type="text" th:field="*{nombre}">

  <label for="email">Correo electrónico</label>
  <input type="email" th:field="*{email}">

  <label for="ciclo">Ciclo</label>
  <input type="text" th:field="*{ciclo}">

  <button type="submit">Enviar</button>
</form>
en este ejemplo

La expresión *{nombre} hace referencia a la propiedad nombre del objeto seleccionado mediante th:object.

Al procesar la plantilla, th:field genera la información necesaria para vincular el campo con esa propiedad, incluidos atributos como id, name y el valor correspondiente. Por eso no necesitamos escribirlos manualmente.

La correspondencia conceptual es:

Relación entre th:field y las propiedades del objeto
th:field="*{nombre}"  →  inscripcion.nombre
th:field="*{email}"   →  inscripcion.email
th:field="*{ciclo}"   →  inscripcion.ciclo
consejo

th:field será todavía más útil cuando incorporemos validación, porque permitirá volver a mostrar el formulario conservando los valores introducidos por el usuario.

5️⃣ Generar un desplegable con datos preparados por el servidor​

No todos los campos tienen que ser cajas de texto. Para el campo ciclo puede resultar más adecuado ofrecer opciones válidas que pedir al usuario que escriba DAW, DAM o ASIR.

Podríamos escribir las opciones directamente en el HTML, pero también podemos prepararlas desde Java y evitar duplicarlas en la plantilla.

🟩 Preparar las opciones en el controlador​

Preparación del formulario y de las opciones del desplegable
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {
    model.addAttribute("inscripcion", new InscripcionForm());
    model.addAttribute("ciclos", List.of("DAW", "DAM", "ASIR"));

    return "inscripcion";
}

La vista recibe dos datos diferentes:

  • inscripcion, que respalda los campos del formulario.
  • ciclos, que contiene las opciones disponibles.

🟨 Generar las opciones con Thymeleaf​

Podemos reutilizar th:each, ya conocido de la UT2, dentro de un <select>:

Desplegable cuyas opciones proceden del Model
<label for="ciclo">Ciclo</label>
<select th:field="*{ciclo}">
  <option value="">Selecciona un ciclo</option>
  <option th:each="c : ${ciclos}"
          th:value="${c}"
          th:text="${c}">
  </option>
</select>
en este ejemplo

th:each genera una opción por cada elemento de ciclos. th:value establece el valor que se enviará y th:text el texto visible.

th:field="*{ciclo}" vincula el <select> con la propiedad ciclo del objeto inscripcion.

Importante

Este desplegable es dinámico en el servidor: Spring prepara los datos y Thymeleaf genera las opciones antes de enviar el HTML al navegador.

No estamos haciendo todavía que un segundo desplegable cambie en tiempo real al seleccionar una opción del primero. Ese comportamiento necesita código ejecutado en el navegador y nuevas peticiones al servidor.

6️⃣ Reunir todas las piezas​

Sin añadir todavía validación, el recorrido completo es:

Flujo completo de un formulario respaldado por un objeto
GET /inscripcion
      ↓
Model
  ├── inscripcion
  └── ciclos
      ↓
formulario Thymeleaf
  ├── th:object
  ├── th:field
  └── th:each
      ↓
POST /inscripcion
      ↓
@ModelAttribute
      ↓
InscripcionForm con los datos recibidos

La idea que debemos conservar es:

objeto → Model → formulario Thymeleaf → petición POST → binding → objeto

No son mecanismos independientes. Es el mismo modelo de datos participando en los dos sentidos del formulario.

7️⃣ Errores frecuentes​

🟩 Los nombres no coinciden​

Si escribimos manualmente:

Campo cuyo nombre no coincide con la propiedad Java
<input type="text" name="correo">

pero el objeto contiene una propiedad email, no existe una correspondencia directa entre ambos nombres.

Utilizar th:field="*{email}" reduce este tipo de errores porque Thymeleaf genera el name a partir de la propiedad indicada.

🟨 El objeto no existe al renderizar la vista​

Si la plantilla contiene:

Formulario que espera un atributo del modelo
<form th:object="${inscripcion}">

el atributo inscripcion debe estar disponible cuando Thymeleaf procese la plantilla.

🟧 Confundir binding con validación​

El binding intenta trasladar y convertir datos desde la petición hacia un objeto. La validación comprobará si esos datos cumplen unas reglas. Son procesos relacionados, pero no equivalentes.

🟥 Utilizar @RequestBody para este formulario​

En un formulario HTML convencional como los de este punto no necesitamos @RequestBody.

@ModelAttribute es adecuado para vincular los parámetros de una petición con un objeto. @RequestBody aparecerá más adelante cuando trabajemos cuerpos de petición como JSON en APIs.

🟪 Pensar que th:field funciona en el navegador​

th:object, th:field y th:each son procesados por Thymeleaf en el servidor. El navegador recibe después HTML normal.

8️⃣ Qué debemos haber entendido antes de continuar​

Al finalizar este punto debemos tener claras estas ideas:

  • @RequestParam sigue siendo adecuado para datos sencillos, pero varios campos relacionados pueden agruparse en un objeto Java.
  • El binding relaciona parámetros de la petición con propiedades del objeto y puede realizar conversiones básicas de tipo.
  • @ModelAttribute permite recibir ese objeto y mantenerlo disponible en el modelo.
  • th:object y th:field vinculan el formulario Thymeleaf con sus propiedades.
  • Model y th:each permiten preparar desde el servidor datos auxiliares, como las opciones de un <select>.
