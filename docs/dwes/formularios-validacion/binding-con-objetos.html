3. Binding de formularios con objetos Java

En el apartado anterior hemos visto cómo un formulario genera una petición HTTP y cómo Spring Boot puede recibir sus parámetros mediante @RequestParam.

Para formularios pequeños, recibir los datos uno a uno sigue siendo una solución perfectamente válida. Sin embargo, cuando varios campos pertenecen a la misma operación, resulta más cómodo tratarlos como una unidad.

En lugar de trabajar por separado con nombre, correo, ciclo o edad, podemos representar todos esos datos mediante un objeto Java. A partir de ahí, Spring puede encargarse de relacionar automáticamente los parámetros recibidos con las propiedades de ese objeto. Este proceso se denomina data binding o, simplemente, binding.

Idea principal

En este punto seguiremos el recorrido real del formulario:

crear objeto → enviarlo a la vista → enlazarlo con el formulario → enviar datos → binding → objeto rellenado

1️⃣ Del formulario a un objeto Java​

Antes de estudiar el binding completo conviene entender por qué necesitamos un objeto.

🟩 Recibir parámetros sueltos funciona, pero tiene límites​

Imaginemos un formulario de inscripción con varios campos:

Formulario con varios datos
<form action="/inscripcion" method="post">

  <label for="nombre">Nombre</label>
  <input type="text" id="nombre" name="nombre">

  <label for="email">Correo electrónico</label>
  <input type="email" id="email" name="email">

  <label for="ciclo">Ciclo</label>
  <select id="ciclo" name="ciclo">
    <option value="">Selecciona un ciclo</option>
    <option value="DAW">DAW</option>
    <option value="DAM">DAM</option>
    <option value="ASIR">ASIR</option>
  </select>

  <button type="submit">Enviar</button>
</form>

Podríamos recibir sus valores individualmente:

Recepción mediante parámetros independientes
@PostMapping("/inscripcion")
public String procesarInscripcion(
        @RequestParam String nombre,
        @RequestParam String email,
        @RequestParam String ciclo) {

    return "resultado";
}

Este código no es incorrecto. Para uno o dos valores incluso puede ser la opción más sencilla.

El problema aparece cuando el formulario empieza a crecer. Los parámetros aumentan y los datos de una misma operación quedan repartidos dentro del método.

🟨 Crear una clase para agrupar los datos​

Podemos representar los datos del formulario mediante una clase Java:

Clase que representa los datos del formulario
public class InscripcionForm {

    private String nombre;
    private String email;
    private String ciclo;

    public InscripcionForm() {
    }

    public String getNombre() {
        return nombre;
    }

    public void setNombre(String nombre) {
        this.nombre = nombre;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }

    public String getCiclo() {
        return ciclo;
    }

    public void setCiclo(String ciclo) {
        this.ciclo = ciclo;
    }
}
en este ejemplo

InscripcionForm es una clase Java sencilla cuyas propiedades representan los datos que forman parte del formulario.

Utilizamos propiedades privadas, constructor sin argumentos y métodos get y set para que Spring pueda trabajar con esos valores.

aviso

InscripcionForm no es una entidad JPA y no representa una tabla de una base de datos.

En esta unidad su función es únicamente agrupar los datos que intervienen en el formulario.

2️⃣ Preparar el formulario desde el controlador​

Una vez creada la clase, el siguiente paso ocurre cuando el usuario solicita la página del formulario.

🟩 Crear el objeto en el GET​

Antes de recibir datos necesitamos mostrar el formulario. El controlador puede crear un objeto vacío y enviarlo a la vista mediante Model:

Preparación del objeto que respaldará el formulario
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {

    InscripcionForm inscripcion = new InscripcionForm();

    model.addAttribute("inscripcion", inscripcion);

    return "inscripcion";
}

La vista recibirá un atributo llamado inscripcion cuyo valor es un objeto InscripcionForm.

en este ejemplo

Model sigue cumpliendo la misma función que vimos en la UT2: transportar datos desde el controlador hasta la vista.

La novedad es que ahora enviamos un objeto que servirá como objeto de respaldo del formulario.

Podemos escribir lo mismo de forma más compacta:

Creación directa del objeto dentro del Model
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {

    model.addAttribute(
        "inscripcion",
        new InscripcionForm()
    );

    return "inscripcion";
}

Ambas versiones hacen lo mismo.

🟨 Asociar el formulario con th:object​

La plantilla necesita saber qué objeto debe utilizar. Para indicarlo usamos th:object:

Formulario asociado al objeto inscripcion
<form th:action="@{/inscripcion}"
      th:object="${inscripcion}"
      method="post">

  <!-- Campos del formulario. -->

</form>

La expresión ${inscripcion} hace referencia al atributo que el controlador añadió previamente al Model.

Podemos representar la relación así:

Relación entre controlador y formulario
new InscripcionForm()
        ↓
model.addAttribute("inscripcion", ...)
        ↓
th:object="${inscripcion}"
aviso

Si utilizamos th:object="${inscripcion}", debe existir un atributo llamado inscripcion cuando Thymeleaf procese la plantilla.

Si el controlador no lo añade al Model, Thymeleaf no podrá utilizarlo como objeto del formulario.

🟧 Vincular los controles con th:field​

Una vez seleccionado el objeto con th:object, podemos vincular cada control con una de sus propiedades:

Campos vinculados con las propiedades del objeto
<form th:action="@{/inscripcion}"
      th:object="${inscripcion}"
      method="post">

  <label for="nombre">Nombre</label>
  <input type="text" th:field="*{nombre}">

  <label for="email">Correo electrónico</label>
  <input type="email" th:field="*{email}">

  <label for="ciclo">Ciclo</label>
  <select th:field="*{ciclo}">
    <option value="">Selecciona un ciclo</option>
    <option value="DAW">DAW</option>
    <option value="DAM">DAM</option>
    <option value="ASIR">ASIR</option>
  </select>

  <button type="submit">Enviar</button>
</form>

La expresión *{nombre} significa “propiedad nombre del objeto seleccionado mediante th:object”.

Por tanto:

Correspondencia entre los controles y el objeto
th:field="*{nombre}"  →  inscripcion.nombre
th:field="*{email}"   →  inscripcion.email
th:field="*{ciclo}"   →  inscripcion.ciclo
en este ejemplo

th:field genera la información necesaria para vincular el control con la propiedad correspondiente.

Entre otras cosas, Thymeleaf genera atributos como id, name y el valor que deba mostrarse.

Por eso, cuando utilizamos th:field, normalmente no necesitamos escribir manualmente name.

🟥 Reutilizar un <select> cuyas opciones vienen del servidor​

En el primer documento de la unidad ya vimos que las opciones de un <select> pueden venir de una colección enviada mediante Model.

Ese mecanismo no cambia:

Select vinculado al objeto y generado desde una colección
<select th:field="*{ciclo}">

  <option value="">Selecciona un ciclo</option>

  <option th:each="ciclo : ${ciclos}"
          th:value="${ciclo}"
          th:text="${ciclo}">
  </option>

</select>

Aquí intervienen dos responsabilidades distintas:

  • th:each genera las opciones a partir de una colección.
  • th:field="*{ciclo}" vincula el <select> con la propiedad ciclo de InscripcionForm.
consejo

No debemos confundir ambos mecanismos.

Generar las opciones del desplegable y vincular el control con una propiedad del objeto son dos tareas diferentes.

3️⃣ Enviar el formulario y realizar el binding​

Hasta ahora hemos preparado el formulario. Ahora seguimos el recorrido cuando el usuario lo rellena y pulsa Enviar.

🟩 El navegador envía parámetros, no objetos Java​

Cuando Thymeleaf termina de procesar la plantilla, el navegador recibe HTML normal.

El usuario puede introducir, por ejemplo:

Valores introducidos por el usuario
Nombre: Ana
Correo: ana@ejemplo.com
Ciclo: DAW

Al enviar el formulario, el navegador prepara una petición cuyos datos pueden representarse así:

Parámetros enviados en la petición
nombre=Ana
email=ana@ejemplo.com
ciclo=DAW
Idea importante

El navegador no envía un objeto InscripcionForm.

El navegador envía parámetros HTTP.

El objeto Java existe únicamente en la aplicación del servidor.

🟨 Spring relaciona los parámetros con las propiedades​

Cuando llega el POST, Spring puede relacionar los nombres recibidos con las propiedades del objeto:

Correspondencia utilizada durante el binding
nombre  →  InscripcionForm.nombre
email   →  InscripcionForm.email
ciclo   →  InscripcionForm.ciclo

La coincidencia entre los nombres es fundamental.

Spring trabaja con los parámetros de la petición, no con los elementos HTML directamente.

🟧 Recibir el objeto con @ModelAttribute​

Una vez realizado el binding, podemos pedir a Spring que entregue al controlador el objeto ya rellenado:

Recepción del formulario mediante @ModelAttribute
@PostMapping("/inscripcion")
public String procesarInscripcion(
        @ModelAttribute("inscripcion") InscripcionForm inscripcion) {

    System.out.println(inscripcion.getNombre());
    System.out.println(inscripcion.getEmail());
    System.out.println(inscripcion.getCiclo());

    return "resultado";
}
en este ejemplo

Cuando llega la petición POST, Spring:

  1. crea o prepara un objeto InscripcionForm.
  2. busca parámetros compatibles con sus propiedades.
  3. asigna los valores recibidos mediante binding.
  4. entrega al método el objeto ya rellenado.

@ModelAttribute("inscripcion") indica además el nombre con el que ese objeto queda asociado al modelo.

El recorrido de esta parte puede resumirse así:

Binding durante el POST
POST /inscripcion
        ↓
parámetros HTTP
        ↓
binding de Spring
        ↓
@ModelAttribute
        ↓
InscripcionForm rellenado

🟥 Binding y conversión de tipos​

Los datos de una petición HTTP llegan originalmente como información textual. Sin embargo, una propiedad Java puede tener otro tipo.

Por ejemplo:

Objeto de formulario con una propiedad numérica
public class InscripcionForm {

    private String nombre;
    private Integer edad;

    // Constructor, getters y setters.
}

Si la petición contiene:

Valor recibido en la petición
nombre=Ana
edad=20

Spring intentará convertir "20" a Integer antes de asignarlo a la propiedad.

Conversión realizada durante el binding
"20"
  ↓
Integer
  ↓
20

Si el usuario envía:

edad=abc

Spring no podrá transformar "abc" en un Integer.

Este tipo de problema aparecerá más adelante asociado a BindingResult, donde podremos detectar errores producidos durante el propio binding.

aviso

Binding y validación no son lo mismo.

Que Spring consiga convertir "20" en un Integer solo significa que el dato puede asignarse a la propiedad.

No significa que la edad sea válida según las reglas de nuestra aplicación.

La validación se estudiará en el siguiente apartado.

4️⃣ Errores frecuentes​

🟩 El objeto no existe al mostrar la vista​

Si la plantilla contiene:

<form th:object="${inscripcion}">

pero el controlador no ha añadido inscripcion al Model, Thymeleaf no podrá asociar el formulario con ese objeto.

🟨 Los nombres no coinciden​

Si un parámetro recibido se llama:

correo

pero el objeto tiene una propiedad:

private String email;

Spring no puede realizar una correspondencia directa entre ambos nombres.

El binding depende de que los nombres sean compatibles.

🟧 Escribir manualmente name y utilizar th:field​

Podemos escribir:

<input type="text"
       name="nombre"
       th:field="*{nombre}">

pero normalmente resulta redundante.

th:field ya genera el name adecuado a partir de la propiedad.

🟥 Confundir binding con validación​

El binding se ocupa de trasladar y convertir datos.

La validación comprobará después si esos valores cumplen las reglas que definamos.

Por ejemplo:

edad=-5

puede convertirse perfectamente a Integer, pero eso no significa que sea una edad válida.

🟪 Utilizar @RequestBody para un formulario HTML convencional​

En los formularios HTML que estamos utilizando no necesitamos:

@RequestBody

@ModelAttribute es adecuado para vincular los parámetros de la petición con un objeto Java.

@RequestBody aparecerá más adelante cuando trabajemos con cuerpos de petición como JSON en APIs REST.

🟩 Pensar que Thymeleaf funciona en el navegador​

Thymeleaf se ejecuta en el servidor.

El navegador no conoce:

th:object
th:field
th:each

Cuando recibe la respuesta, esas instrucciones ya han sido procesadas y se han convertido en HTML normal.

5️⃣ Qué debemos haber entendido antes de continuar​

Debemos tener claras estas ideas:

  • cuando varios datos pertenecen a un mismo formulario podemos agruparlos en una clase Java.
  • el controlador crea inicialmente un objeto y lo envía a la vista mediante Model.
  • th:object asocia el formulario con ese objeto.
  • th:field vincula cada control con una propiedad concreta.
  • el navegador no envía objetos Java, sino parámetros HTTP.
  • Spring utiliza esos parámetros para realizar el binding.
  • @ModelAttribute permite recibir el objeto ya rellenado en el método que procesa el POST.
  • el binding puede realizar conversiones básicas de tipos.
  • binding y validación son procesos diferentes.
  • un <select> puede seguir obteniendo sus opciones de una colección preparada por el controlador; th:field se limita a vincularlo con la propiedad correspondiente.
Siguiente paso

Ya sabemos construir un formulario respaldado por un objeto y recibir de nuevo sus datos mediante binding.

El siguiente problema es inevitable: ¿qué ocurre si el usuario deja un campo obligatorio vacío, introduce una edad incorrecta o escribe un correo con un formato no válido?
