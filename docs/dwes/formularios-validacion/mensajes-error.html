5. Mensajes y gestión de errores de validación

En el punto anterior hemos aprendido a definir reglas de validación y a aplicarlas sobre los datos recibidos.

Sin embargo, detectar que un dato no es válido no resuelve todavía el problema completo. Una aplicación web debe decidir qué hacer cuando encuentra errores, conservar los valores que el usuario ya había introducido y mostrar mensajes que le ayuden a corregirlos.

En los formularios completos trabajaremos principalmente con un objeto bindeado y BindingResult, porque este mecanismo está pensado precisamente para acompañar el flujo de un formulario en Spring MVC.

Idea principal

El recorrido habitual será:

POST → binding → validación → BindingResult → volver al formulario → mostrar errores

1️⃣ Recoger los errores con BindingResult​

Partimos del mismo objeto de formulario utilizado en el punto anterior:

Objeto de formulario con reglas de validación
public class InscripcionForm {

    @NotBlank(message = "El nombre es obligatorio")
    @Size(
        min = 2,
        max = 60,
        message = "El nombre debe tener entre 2 y 60 caracteres"
    )
    private String nombre;

    @NotBlank(message = "El correo electrónico es obligatorio")
    @Email(message = "Introduce un correo electrónico válido")
    private String email;

    @NotBlank(message = "Debes seleccionar un ciclo")
    private String ciclo;

    @NotNull(message = "La edad es obligatoria")
    @Min(value = 16, message = "La edad mínima es 16 años")
    @Max(value = 99, message = "La edad máxima es 99 años")
    private Integer edad;

    // Constructor, getters y setters.
}

Las restricciones describen qué valores consideramos correctos, pero necesitamos un lugar donde Spring pueda registrar los problemas que encuentre.

Ese lugar es BindingResult.

Recepción de los errores con BindingResult
@PostMapping("/inscripcion")
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado) {

    if (resultado.hasErrors()) {
        return "inscripcion";
    }

    return "resultado-inscripcion";
}
en este ejemplo

@Valid solicita la validación del objeto.

BindingResult recoge los problemas producidos durante el binding y la validación.

resultado.hasErrors() permite decidir si podemos continuar o debemos volver al formulario.

🟩 El orden de los parámetros importa​

Cuando queremos consultar los errores asociados a un objeto validado, BindingResult debe aparecer inmediatamente después de ese objeto:

Orden correcto entre el objeto validado y BindingResult
public String procesar(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado,
        Model model) {

    // ...
}

No debemos intercalar otro parámetro entre ambos.

aviso

Si BindingResult no aparece en la posición correcta, Spring no podrá asociarlo de la forma esperada con el objeto validado.

🟨 Errores de binding y errores de validación​

BindingResult puede contener problemas de dos tipos distintos.

Un error de validación aparece cuando el valor puede almacenarse en la propiedad Java, pero incumple una regla.

Por ejemplo:

Valor convertible pero no válido
edad=14

El valor 14 puede convertirse perfectamente a Integer, pero después @Min(16) detecta que no cumple la regla.

En cambio, un error de binding aparece cuando Spring no puede convertir el dato al tipo esperado:

Valor que no puede convertirse al tipo esperado
edad=abc

Si edad es un Integer, Spring no puede transformar "abc" en un número.

Idea importante

BindingResult no contiene únicamente errores de Jakarta Validation.

También puede contener errores producidos durante el binding y la conversión de tipos.

🟧 Consultar los errores​

La comprobación más habitual será:

Comprobar si existen errores
if (resultado.hasErrors()) {
    return "inscripcion";
}

También disponemos de otras consultas:

MétodoQué permite comprobar
hasErrors()Si existe cualquier error.
hasFieldErrors("email")Si una propiedad concreta contiene errores.
getFieldErrors()Obtener los errores asociados a campos.
getAllErrors()Obtener todos los errores registrados.

Normalmente el controlador se limitará a decidir el flujo y dejaremos que Thymeleaf se encargue de presentar los mensajes.

🟥 Añadir errores desde el controlador​

Algunas reglas no pueden expresarse con una anotación porque no dependen solo del valor del campo, sino del estado de la aplicación. Por ejemplo: no admitir dos inscripciones con el mismo correo.

En ese caso podemos comprobar la regla en el controlador y añadir nosotros el error a BindingResult mediante rejectValue():

Error añadido manualmente a BindingResult
@Controller
public class InscripcionController {

    private final List<InscripcionForm> inscripciones = new ArrayList<>();

    @PostMapping("/inscripcion")
    public String procesarInscripcion(
            @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
            BindingResult resultado) {

        if (!resultado.hasFieldErrors("email")
                && correoYaInscrito(inscripcion.getEmail())) {

            resultado.rejectValue(
                "email",
                "email.duplicado",
                "Ya existe una inscripción con ese correo"
            );
        }

        if (resultado.hasErrors()) {
            return "inscripcion";
        }

        inscripciones.add(inscripcion);
        return "resultado-inscripcion";
    }

    private boolean correoYaInscrito(String email) {
        return inscripciones.stream()
                .anyMatch(i -> i.getEmail().equalsIgnoreCase(email));
    }
}
en este ejemplo

rejectValue() recibe tres datos:

  • el nombre de la propiedad a la que asociamos el error ("email").
  • un código que identifica el tipo de error ("email.duplicado").
  • el mensaje que se mostrará.

El error queda asociado al campo email igual que uno producido por Jakarta Validation, así que th:errors lo mostrará sin cambiar nada en la vista.

Solo hacemos la comprobación si el correo no tiene ya otros errores (hasFieldErrors("email")). Así no buscamos duplicados de un correo vacío o mal escrito ni acumulamos mensajes en el mismo campo.

La comprobación debe hacerse antes de hasErrors(), para que el nuevo error se tenga en cuenta al decidir si volvemos al formulario.

¿Anotación o controlador?

Si la regla depende solo del valor del campo (formato, longitud, mayoría de edad…), la expresamos con una restricción, estándar o personalizada como veremos en el punto 8.

Si depende de datos de la aplicación (un correo ya registrado, plazas disponibles…), la comprobamos en el controlador y usamos rejectValue(). Más adelante, cuando incorporemos una capa de servicios, esta comprobación se trasladará allí.

2️⃣ Volver al formulario conservando los datos​

Cuando existen errores, normalmente devolvemos la misma vista:

Volver al formulario cuando existen errores
if (resultado.hasErrors()) {
    return "inscripcion";
}

Seguimos dentro de la misma petición POST y, por tanto, continúan disponibles:

  • el objeto inscripcion.
  • el BindingResult asociado.
  • los valores introducidos por el usuario.
  • los mensajes de error.

Eso permite que Thymeleaf reconstruya el formulario con su estado anterior.

🟩 th:field conserva el estado del formulario​

Si el usuario ha escrito correctamente su nombre pero se ha equivocado en el correo, no queremos obligarle a escribir de nuevo todo.

Al volver a la vista:

Campos vinculados al mismo objeto
<form th:action="@{/inscripcion}"
      th:object="${inscripcion}"
      method="post">

  <input type="text" th:field="*{nombre}">
  <input type="email" th:field="*{email}">

</form>

th:field vuelve a tomar los valores del objeto inscripcion que ya contiene lo introducido por el usuario.

peligro

No debemos crear un InscripcionForm nuevo antes de devolver la vista con errores.

Si sustituimos el objeto recibido por otro vacío, perderemos sus valores y la asociación con los errores detectados.

3️⃣ Mostrar los errores en Thymeleaf​

Una vez que el controlador vuelve a la vista, Thymeleaf puede consultar el BindingResult asociado al objeto.

🟩 Mostrar un mensaje junto al campo​

Mensaje de error asociado al campo nombre
<label for="nombre">Nombre</label>

<input type="text"
       th:field="*{nombre}"
       th:errorclass="campo-error">

<p th:if="${#fields.hasErrors('nombre')}"
   th:errors="*{nombre}"
   class="mensaje-error">
</p>
en este ejemplo

#fields.hasErrors('nombre') comprueba si la propiedad nombre contiene algún error.

th:errors="*{nombre}" muestra los mensajes asociados a esa propiedad.

th:errorclass="campo-error" añade una clase CSS al control cuando existe algún error.

Por ejemplo, si la restricción es:

Mensajes asociados a una propiedad
@NotBlank(message = "El nombre es obligatorio")
@Size(
    min = 2,
    max = 60,
    message = "El nombre debe tener entre 2 y 60 caracteres"
)
private String nombre;

th:errors podrá mostrar el mensaje de la regla que se haya incumplido.

🟨 Destacar visualmente el campo​

Podemos definir estilos para que el error sea más fácil de localizar:

Estilos básicos para los errores
.campo-error {
  border: 2px solid #c0392b;
}

.mensaje-error {
  font-size: 0.9rem;
  font-weight: 600;
}
consejo

El color ayuda a localizar el problema, pero no debe ser la única forma de comunicarlo.

El mensaje de texto sigue siendo necesario.

🟧 Mostrar un resumen general​

Además de mostrar cada error junto a su campo, podemos presentar un resumen:

Resumen de errores del formulario
<div th:if="${#fields.hasAnyErrors()}">

  <p>Revisa los siguientes datos:</p>

  <ul>
    <li th:each="error : ${#fields.allErrors()}"
        th:text="${error}">
    </li>
  </ul>

</div>

Este bloque debe colocarse dentro del elemento que tiene th:object, porque #fields trabaja sobre el objeto seleccionado.

En formularios pequeños suele ser suficiente mostrar los mensajes cerca de cada control. En formularios más largos puede resultar útil combinar ambas soluciones.

Errores asociados al formulario completo

Hasta ahora hemos trabajado con errores de campo, asociados a propiedades concretas como nombre, email o edad.

Spring también permite registrar errores globales asociados al objeto completo. Pueden resultar útiles cuando una regla depende de varios campos a la vez.

Se registran desde el controlador con resultado.reject(...), de forma parecida a rejectValue(). En esta unidad no los utilizaremos, aunque en el punto 8 veremos cómo crear restricciones personalizadas sobre un campo.

4️⃣ Mensajes de los errores de binding​

Los mensajes de las restricciones los escribimos nosotros mediante message. Pero los errores de binding no proceden de ninguna anotación.

Si edad es un Integer y el usuario escribe abc, th:errors mostrará un mensaje técnico parecido a este:

Mensaje por defecto de un error de conversión
Failed to convert property value of type 'java.lang.String' to required type 'java.lang.Integer' for property 'edad'; For input string: "abc"

Es un mensaje útil para quien programa, pero no para quien rellena el formulario.

🟩 Definir los mensajes en messages.properties​

Spring Boot carga automáticamente el archivo src/main/resources/messages.properties. En él podemos asociar mensajes a los errores de conversión, cuyo código es typeMismatch:

src/main/resources/messages.properties
typeMismatch.inscripcion.edad=La edad debe ser un número entero
typeMismatch.java.lang.Integer=Introduce un número entero
typeMismatch.java.time.LocalDate=Introduce una fecha válida
typeMismatch=El valor introducido no tiene un formato válido
en este ejemplo

Spring busca el mensaje de lo más concreto a lo más general y utiliza el primero que encuentra:

  1. typeMismatch.inscripcion.edad: el campo edad del objeto inscripcion.
  2. typeMismatch.edad: cualquier campo llamado edad.
  3. typeMismatch.java.lang.Integer: cualquier campo de tipo Integer.
  4. typeMismatch: cualquier error de conversión.

inscripcion es el nombre del atributo del modelo, el que indicamos en @ModelAttribute("inscripcion"), no el nombre de la clase.

aviso

Guarda messages.properties con codificación UTF-8, que es la que Spring Boot utiliza por defecto para leerlo. Si el editor lo guarda con otra codificación, las tildes y las eñes se mostrarán mal.

información

Además, al volver al formulario, th:field muestra el valor rechazado (abc). El usuario ve lo que escribió y el mensaje que le explica por qué no es correcto.

🟨 Ampliación: mensajes de validación en el mismo archivo​

Los mensajes de las restricciones también pueden trasladarse a messages.properties. En lugar del texto, indicamos su clave entre llaves:

Mensaje de validación tomado de messages.properties
@NotBlank(message = "{inscripcion.nombre.obligatorio}")
private String nombre;
src/main/resources/messages.properties
inscripcion.nombre.obligatorio=El nombre es obligatorio

Así todos los textos de la aplicación quedan reunidos en un solo lugar. En esta unidad es opcional: escribir el mensaje directamente en la anotación sigue siendo válido.

5️⃣ Volver a preparar los datos auxiliares​

Un formulario puede necesitar datos adicionales del Model.

Por ejemplo, un desplegable puede recibir sus opciones desde una colección:

Preparación inicial del formulario
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {

    model.addAttribute(
        "inscripcion",
        new InscripcionForm()
    );

    model.addAttribute(
        "ciclos",
        List.of("DAW", "DAM", "ASIR")
    );

    return "inscripcion";
}

Si el POST encuentra errores y devuelve la misma vista, el objeto inscripcion y su BindingResult siguen disponibles.

Sin embargo, la colección ciclos que añadimos durante el GET no se reconstruye automáticamente.

Debemos volver a prepararla:

Recarga de los datos auxiliares
if (resultado.hasErrors()) {

    model.addAttribute(
        "ciclos",
        List.of("DAW", "DAM", "ASIR")
    );

    return "inscripcion";
}
aviso

Volver a la misma vista no significa volver a ejecutar automáticamente el método @GetMapping.

🟩 Evitar duplicar la preparación​

Si el GET y el POST necesitan exactamente los mismos datos auxiliares, podemos extraerlos a un método privado:

Método auxiliar para preparar datos
private void prepararDatosFormulario(Model model) {

    model.addAttribute(
        "ciclos",
        List.of("DAW", "DAM", "ASIR")
    );
}

Y reutilizarlo:

Reutilización en GET y POST
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {

    model.addAttribute(
        "inscripcion",
        new InscripcionForm()
    );

    prepararDatosFormulario(model);

    return "inscripcion";
}

@PostMapping("/inscripcion")
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado,
        Model model) {

    if (resultado.hasErrors()) {
        prepararDatosFormulario(model);
        return "inscripcion";
    }

    return "resultado-inscripcion";
}

No estamos introduciendo todavía una capa de servicios.

Solo evitamos repetir una preparación sencilla que necesitan tanto el GET como el POST.

6️⃣ Y si validamos parámetros individuales​

En el punto anterior vimos, de forma complementaria, que también podemos aplicar restricciones directamente sobre parámetros como @RequestParam:

Validación directa de parámetros
@PostMapping("/reserva")
public String reservar(
        @RequestParam
        @NotBlank(message = "El nombre es obligatorio")
        String nombre,

        @RequestParam
        @Min(value = 1, message = "El mínimo es un día")
        @Max(value = 7, message = "El máximo son siete días")
        Integer dias) {

    return "resultado-reserva";
}

En este caso no tenemos un objeto de formulario con su BindingResult.

Si una restricción directa falla, Spring MVC aplica validación del método y puede producir una HandlerMethodValidationException.

nota

Este mecanismo está disponible desde Spring Framework 6.1 (Spring Boot 3.2). En materiales anteriores verás @Validated sobre la clase del controlador y ConstraintViolationException.

Podemos tratarla mediante @ExceptionHandler:

Gestión sencilla de la validación del método
@ExceptionHandler(HandlerMethodValidationException.class)
public String gestionarErroresParametros(
        HandlerMethodValidationException ex,
        Model model) {

    model.addAttribute(
        "errores",
        ex.getAllErrors()
    );

    return "error-validacion";
}

Y mostrar los mensajes en una vista sencilla:

Mostrar errores de validación del método
<ul>
  <li th:each="error : ${errores}"
      th:text="${error.defaultMessage}">
  </li>
</ul>
información

Este mecanismo lo veremos únicamente como posibilidad complementaria.

Para formularios completos seguiremos utilizando principalmente un objeto bindeado con @Valid y BindingResult, porque permite conservar y presentar los errores de cada campo de forma mucho más integrada.

aviso

No cualquier problema de un @RequestParam produce una HandlerMethodValidationException.

Un parámetro requerido que no llega o un valor que no puede convertirse al tipo esperado puede producir un error antes de aplicar las restricciones de Jakarta Validation.

consejo

8️⃣ Errores frecuentes​

🟩 Colocar BindingResult en una posición incorrecta​

Debe aparecer inmediatamente después del objeto validado al que corresponde.

🟨 Olvidar BindingResult​

Si utilizamos @Valid pero no declaramos BindingResult, Spring no tiene dónde dejar los errores.

En ese caso no llega a ejecutar nuestro método: lanza una excepción y el navegador muestra una página de error 400 en lugar de volver al formulario.

🟧 Crear un objeto nuevo antes de volver al formulario​

Sustituir inscripcion por un objeto vacío hace que perdamos el estado que necesitamos mostrar.

🟥 Olvidar los datos auxiliares​

Si la plantilla depende de ${ciclos}, esa colección debe estar disponible también cuando volvemos desde el POST.

🟪 Pensar que cualquier validación utiliza BindingResult​

BindingResult es el mecanismo principal para los objetos bindeados que estamos utilizando en nuestros formularios.

Las restricciones directas sobre parámetros siguen otro recorrido.

🟩 Confundir cualquier problema de @RequestParam con validación del método​

La ausencia de un parámetro obligatorio o un fallo de conversión puede producirse antes de que Jakarta Validation compruebe sus restricciones.

9️⃣ Qué debemos haber entendido antes de continuar​

Al finalizar este punto debemos conservar estas ideas:

  • BindingResult recoge errores de binding y de validación asociados a un objeto de formulario.
  • debe aparecer inmediatamente después del objeto validado.
  • cuando existen errores normalmente devolvemos la misma vista.
  • th:field permite conservar los valores introducidos.
  • #fields, th:errors y th:errorclass permiten presentar los errores en Thymeleaf.
  • rejectValue() permite añadir desde el controlador errores que dependen del estado de la aplicación.
  • los mensajes de los errores de binding (typeMismatch) pueden personalizarse en messages.properties.
  • no debemos sustituir el objeto recibido por uno nuevo cuando volvemos al formulario.
  • los datos auxiliares de la vista deben prepararse de nuevo desde el POST.
  • las restricciones directas sobre parámetros utilizan validación del método y siguen otro mecanismo de gestión.
  • para formularios completos, el objeto bindeado ofrece una integración mucho más cómoda.
