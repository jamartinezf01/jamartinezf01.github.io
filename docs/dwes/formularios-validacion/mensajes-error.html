5. Mensajes y gestión de errores de validación

En el punto anterior hemos aprendido a definir reglas de validación y a activarlas con @Valid. Sin embargo, detectar que un dato no es válido no resuelve todavía el problema completo.

Cuando existen errores, nuestra aplicación debe ser capaz de:

  • detectar que se han producido.
  • saber a qué campos afectan.
  • conservar los datos introducidos.
  • volver a mostrar el mismo formulario.
  • indicar qué debe corregirse.
  • evitar continuar como si los datos fueran válidos.
Idea principal

El flujo completo será:

recibir datos → binding → validar → detectar errores → volver al formulario → mostrar qué debe corregirse

1️⃣ De la validación a BindingResult​

Partimos del mismo objeto de formulario del punto anterior:

Objeto de formulario con reglas de validación
public class InscripcionForm {

    @NotBlank(message = "El nombre es obligatorio")
    @Size(min = 2, max = 60,
          message = "El nombre debe tener entre 2 y 60 caracteres")
    private String nombre;

    @NotBlank(message = "El correo electrónico es obligatorio")
    @Email(message = "Introduce un correo electrónico válido")
    private String email;

    @NotBlank(message = "Debes seleccionar un ciclo")
    private String ciclo;

    @NotNull(message = "La edad es obligatoria")
    @Min(value = 16, message = "La edad mínima es 16 años")
    @Max(value = 99, message = "La edad máxima es 99 años")
    private Integer edad;

    // Constructor, getters y setters.
}

Cuando enviamos el formulario, Spring realiza el binding y, si hemos utilizado @Valid, comprueba las restricciones. Para acceder a los problemas detectados utilizamos BindingResult.

Recepción de los errores con BindingResult
@PostMapping("/inscripcion")
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado) {

    if (resultado.hasErrors()) {
        return "inscripcion";
    }

    return "resultado-inscripcion";
}
en este ejemplo

@Valid activa la validación del objeto recibido.

BindingResult recoge los problemas producidos durante el binding y la validación.

resultado.hasErrors() permite decidir si podemos continuar o debemos volver al formulario.

🟩 El orden de los parámetros importa​

BindingResult debe aparecer inmediatamente después del objeto validado al que corresponde:

Orden correcto entre el objeto validado y BindingResult
public String procesar(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado,
        Model model) {
    // ...
}

No debemos intercalar otro parámetro entre ambos.

aviso

Si necesitamos consultar los errores de inscripcion, su BindingResult debe ir justo después de ese @ModelAttribute validado.

2️⃣ Errores de binding y errores de validación​

BindingResult puede recoger problemas de dos tipos.

🟩 Errores de validación​

Se producen cuando el valor puede almacenarse en la propiedad Java, pero incumple una regla.

Valor convertible pero no válido
edad=14

14 puede convertirse a Integer, pero @Min(16) detecta que no cumple la restricción.

🟨 Errores de binding​

Se producen cuando Spring no puede trasladar correctamente el valor recibido a la propiedad Java.

Valor que no puede convertirse al tipo esperado
edad=abc

Si edad es un Integer, Spring no puede convertir "abc" en un número y registra un error asociado a ese campo.

Idea importante

BindingResult no representa únicamente errores de Jakarta Validation.

También contiene problemas producidos durante el enlace y la conversión de los datos de la petición.

🟧 Consultar los errores desde el controlador​

El método que utilizaremos con más frecuencia será hasErrors():

Decisión del controlador según existan errores
if (resultado.hasErrors()) {
    return "inscripcion";
}

// Los datos han superado esta fase.

BindingResult permite también consultas más concretas:

MétodoQué permite comprobar
hasErrors()Si existe cualquier error.
hasFieldErrors("email")Si el campo email tiene algún error.
getFieldErrors()Obtener los errores asociados a campos.
getAllErrors()Obtener todos los errores registrados.

En formularios habituales, el controlador suele limitarse a decidir el flujo y deja que Thymeleaf consulte y muestre los errores.

consejo

El controlador no debe construir manualmente el HTML de los mensajes de error. La vista se encargará de presentarlos.

3️⃣ Volver al formulario conservando los datos​

Cuando existen errores, normalmente devolvemos la misma vista:

Regreso al formulario cuando existen errores
if (resultado.hasErrors()) {
    return "inscripcion";
}

No estamos realizando una redirección. En esa misma petición siguen disponibles:

  • el objeto inscripcion recibido mediante @ModelAttribute.
  • el BindingResult asociado.
  • los valores que introdujo el usuario.
  • los mensajes correspondientes a los errores.

Thymeleaf puede utilizar esa información para reconstruir el formulario.

aviso

Cuando devolvemos una vista Thymeleaf desde un @Controller, no utilizamos @ResponseBody.

🟩 th:field conserva el estado del formulario​

Si el formulario utiliza th:object y th:field, Thymeleaf puede volver a mostrar los valores asociados al objeto:

Formulario vinculado al mismo objeto después de un error
<form th:action="@{/inscripcion}"
      th:object="${inscripcion}"
      method="post">

  <label for="nombre">Nombre</label>
  <input type="text" th:field="*{nombre}">

  <label for="email">Correo electrónico</label>
  <input type="email" th:field="*{email}">

  <button type="submit">Enviar</button>
</form>

Si el usuario ha escrito correctamente su nombre pero se ha equivocado en el correo, no queremos obligarle a completar de nuevo todo el formulario.

peligro

No debemos crear un InscripcionForm nuevo antes de devolver la vista con errores.

Si sustituimos el objeto recibido por otro vacío, perderemos sus valores y la asociación con los errores detectados.

4️⃣ Mostrar los errores en Thymeleaf​

Thymeleaf dispone de utilidades específicas para consultar y mostrar los errores asociados al objeto del formulario.

🟩 Mostrar un mensaje junto al campo​

Mensaje de error asociado al campo nombre
<label for="nombre">Nombre</label>
<input type="text" th:field="*{nombre}">

<p th:if="${#fields.hasErrors('nombre')}"
   th:errors="*{nombre}">
  Error en el nombre
</p>
en este ejemplo

#fields.hasErrors('nombre') comprueba si la propiedad nombre tiene algún error.

th:errors="*{nombre}" muestra los mensajes asociados a esa propiedad.

El texto interior del <p> funciona como contenido de respaldo, pero será sustituido cuando Thymeleaf procese la plantilla.

Si la restricción contiene:

Regla con un mensaje destinado al usuario
@NotBlank(message = "El nombre es obligatorio")
@Size(min = 2, max = 60,
      message = "El nombre debe tener entre 2 y 60 caracteres")
private String nombre;

th:errors podrá mostrar el mensaje correspondiente cuando se incumpla una de esas reglas.

La misma estructura se aplica al resto de propiedades:

Mensajes de error en varios campos
<input type="email" th:field="*{email}">
<p th:if="${#fields.hasErrors('email')}"
   th:errors="*{email}"></p>

<input type="number" th:field="*{edad}">
<p th:if="${#fields.hasErrors('edad')}"
   th:errors="*{edad}"></p>

🟨 Destacar visualmente el campo con th:errorclass​

Además del mensaje, podemos resaltar el control que contiene el problema:

Aplicación automática de una clase CSS cuando existe un error
<label for="email">Correo electrónico</label>
<input
  type="email"
  th:field="*{email}"
  th:errorclass="campo-error"
>

<p th:if="${#fields.hasErrors('email')}"
   th:errors="*{email}"
   class="mensaje-error"></p>
Estilos para distinguir campos y mensajes con errores
.campo-error {
  border: 2px solid #c0392b;
}

.mensaje-error {
  font-size: 0.9rem;
  font-weight: 600;
}
en este ejemplo

th:errorclass="campo-error" añade esa clase cuando el campo tiene errores. No sustituye a las clases que ya pudiera tener el elemento.

consejo

El color puede ayudar a localizar el problema, pero el mensaje de texto sigue siendo necesario. No debemos transmitir el significado únicamente mediante color.

🟧 Mostrar un resumen de todos los errores​

También podemos presentar un resumen general:

Resumen de todos los errores del formulario
<div th:if="${#fields.hasAnyErrors()}">
  <p>Revisa los siguientes datos:</p>

  <ul>
    <li th:each="error : ${#fields.allErrors()}"
        th:text="${error}"></li>
  </ul>
</div>

En formularios pequeños suele ser suficiente mostrar cada mensaje junto a su campo. En formularios largos, un resumen inicial puede resultar útil.

Errores asociados al formulario completo

Hasta ahora hemos trabajado con errores de campo, asociados a propiedades como nombre, email, ciclo o edad.

Spring también puede registrar errores globales, vinculados al objeto completo. Pueden utilizarse cuando una regla depende de varios valores a la vez.

En esta unidad no crearemos validadores personalizados ni reglas globales; basta con saber que existen.

5️⃣ Recuperar los datos auxiliares que necesita la vista​

Un formulario puede depender de datos adicionales enviados mediante Model. Por ejemplo, el desplegable de ciclos:

Preparación inicial del formulario y de sus opciones
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {
    model.addAttribute("inscripcion", new InscripcionForm());
    model.addAttribute("ciclos", List.of("DAW", "DAM", "ASIR"));

    return "inscripcion";
}
Desplegable generado a partir de una colección del Model
<select th:field="*{ciclo}">
  <option value="">Selecciona un ciclo</option>
  <option th:each="c : ${ciclos}"
          th:value="${c}"
          th:text="${c}"></option>
</select>

Si el POST encuentra errores y devuelve simplemente:

Retorno insuficiente cuando la vista necesita datos adicionales
if (resultado.hasErrors()) {
    return "inscripcion";
}

el objeto inscripcion y sus errores siguen disponibles, pero la colección ciclos añadida durante el GET no aparece automáticamente en esta nueva petición.

Debemos volver a preparar los datos que la vista necesita:

Recarga de las opciones antes de volver al formulario con errores
if (resultado.hasErrors()) {
    model.addAttribute("ciclos", List.of("DAW", "DAM", "ASIR"));
    return "inscripcion";
}
aviso

Volver a la misma vista no significa volver a ejecutar automáticamente el método @GetMapping que mostró el formulario inicialmente.

🟩 Evitar repetir la preparación de datos​

Si GET y POST necesitan exactamente los mismos datos auxiliares, podemos extraerlos a un método privado:

Método auxiliar para preparar los datos comunes de la vista
private void prepararDatosFormulario(Model model) {
    model.addAttribute("ciclos", List.of("DAW", "DAM", "ASIR"));
}

Y reutilizarlo:

Reutilización de la preparación del formulario
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {
    model.addAttribute("inscripcion", new InscripcionForm());
    prepararDatosFormulario(model);
    return "inscripcion";
}

@PostMapping("/inscripcion")
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado,
        Model model) {

    if (resultado.hasErrors()) {
        prepararDatosFormulario(model);
        return "inscripcion";
    }

    return "resultado-inscripcion";
}

No estamos introduciendo todavía una capa de servicios. Solo evitamos duplicar una preparación sencilla dentro del mismo controlador.

6️⃣ El flujo completo​

A estas alturas el comportamiento del formulario puede resumirse así:

Flujo completo cuando existen errores
GET /inscripcion
      ↓
Model + datos auxiliares
      ↓
formulario Thymeleaf
      ↓
POST /inscripcion
      ↓
binding + validación
      ↓
BindingResult
   ↙       ↘
errores    sin errores
  ↓           ↓
misma vista   continuar

En la rama con errores:

  • no redirigimos.
  • no creamos un objeto nuevo.
  • conservamos el BindingResult y los valores introducidos.
  • reconstruimos únicamente los datos auxiliares que la vista necesita.
  • Thymeleaf muestra los mensajes junto a sus campos.

En la rama correcta, el controlador puede continuar con el procesamiento normal. En el siguiente punto mejoraremos esa parte mediante una redirección.

7️⃣ Errores frecuentes en esta fase​

🟩 Colocar BindingResult en una posición incorrecta​

Debe aparecer inmediatamente después del objeto validado al que corresponde.

🟨 Redirigir cuando existen errores​

Una redirección crea una nueva petición. Si queremos conservar fácilmente objeto, valores y errores, normalmente devolvemos directamente la vista.

🟧 Crear un objeto nuevo antes de volver al formulario​

Sustituir inscripcion por un objeto vacío hace que perdamos el estado que necesitamos mostrar.

🟥 Olvidar los datos auxiliares de la plantilla​

Si un <select> depende de ${ciclos}, esa colección debe estar disponible también al volver desde el POST.

🟪 Mostrar un mensaje genérico sin indicar el campo​

“Hay errores en el formulario” informa del problema, pero no ayuda a corregirlo. Siempre que sea posible, mostraremos el mensaje cerca del control correspondiente.

🟩 Confundir el mensaje con la presentación​

La restricción define qué mensaje corresponde al error. Thymeleaf decide dónde y cómo se muestra.

8️⃣ Qué debemos haber entendido antes de continuar​

Al finalizar este punto debemos tener claras estas ideas:

  • BindingResult recoge errores de binding y de validación.
  • debe aparecer inmediatamente después del objeto validado correspondiente.
  • con errores normalmente devolvemos la misma vista, sin redirigir ni sustituir el objeto recibido.
  • th:field, #fields.hasErrors(...), th:errors y th:errorclass permiten conservar el estado y mostrar los problemas en Thymeleaf.
  • los datos auxiliares de la vista deben volver a prepararse cuando devolvemos el formulario desde el POST.
  • el controlador decide el flujo y la vista se encarga de presentar los mensajes al usuario.
Siguiente paso

Ya sabemos resolver correctamente la rama en la que los datos contienen errores.
