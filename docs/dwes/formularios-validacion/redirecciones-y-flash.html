6. Redirecciones y datos temporales

En el punto anterior resolvimos la rama en la que el formulario contiene errores: si BindingResult detecta problemas, devolvemos directamente la misma vista, conservamos los valores introducidos y mostramos los mensajes correspondientes.

Nos queda completar la rama correcta: ¿qué hacemos cuando el formulario se procesa sin errores?

Una posibilidad sería devolver directamente una vista desde el método que atiende el POST, pero eso deja al navegador situado sobre la respuesta de esa petición. En aplicaciones web es habitual evitarlo mediante una redirección.

Idea principal

Cuando hay errores, normalmente volvemos directamente a la misma vista.

Cuando el procesamiento termina correctamente, es habitual redirigir a otra ruta para que el navegador termine en una nueva petición GET.

1️⃣ Devolver una vista y redirigir no son lo mismo​

Cuando devolvemos una vista Thymeleaf:

Devolución directa de una vista Thymeleaf
return "inscripcion";

Spring procesa esa plantilla dentro de la petición actual.

Si queremos redirigir, utilizamos el prefijo redirect::

Redirección hacia otra ruta de la aplicación
return "redirect:/inscripciones";

En este segundo caso el navegador recibe una respuesta de redirección y realiza una nueva petición hacia /inscripciones.

El controlador devuelve...Qué ocurre
"inscripcion"Spring procesa una vista Thymeleaf en la petición actual.
"redirect:/inscripciones"El navegador realiza una nueva petición a /inscripciones.
aviso

Una redirección no cambia simplemente de plantilla dentro de la misma petición. Implica otra petición HTTP.

2️⃣ Por qué evitar dejar al navegador sobre un POST​

Si un POST correcto termina devolviendo directamente una vista:

Respuesta directa después de un POST correcto
return "inscripcion-exito";

la página final sigue siendo la respuesta de ese POST.

Si el usuario pulsa Actualizar, el navegador puede intentar repetir la petición que originó esa página. Si el POST representa una operación con efecto, podríamos ejecutarla otra vez.

aviso

No es un problema exclusivo de las bases de datos. La idea importante es que un POST suele representar una operación que produce un efecto y conviene evitar que una actualización normal vuelva a ejecutarla.

3️⃣ El patrón Post/Redirect/Get​

La solución habitual es el patrón Post/Redirect/Get, abreviado como PRG:

  1. El usuario envía el formulario mediante POST.
  2. El servidor procesa los datos.
  3. Si existen errores, devuelve directamente el formulario.
  4. Si todo es correcto, responde con una redirección.
  5. El navegador realiza una nueva petición GET.
  6. El servidor muestra la página correspondiente a ese GET.

🟩 Aplicarlo en el controlador​

Aplicación del patrón Post/Redirect/Get
@PostMapping("/inscripcion")
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado,
        Model model) {

    if (resultado.hasErrors()) {
        prepararDatosFormulario(model);
        return "inscripcion";
    }

    // Procesamiento correcto de los datos.
    return "redirect:/inscripciones";
}

La ruta de destino debe atender la nueva petición:

Ruta GET que recibe la redirección
@GetMapping("/inscripciones")
public String mostrarInscripciones() {
    return "inscripciones";
}

El navegador termina así sobre GET /inscripciones, no sobre POST /inscripcion.

🟨 La rama con errores no utiliza PRG​

Nuestro criterio será:

Dos ramas del procesamiento del formulario
errores → misma vista
éxito   → redirección

Cuando hay errores necesitamos mantener el objeto del formulario y su BindingResult, por lo que devolvemos directamente la vista.

Cuando no existen errores, podemos cerrar el POST mediante una redirección.

4️⃣ Transportar información durante una redirección​

Una redirección crea una petición nueva. Por eso los atributos del Model de la petición anterior no pasan automáticamente a la siguiente.

Esto no es suficiente si queremos mostrar una confirmación después de redirigir:

El Model no se conserva automáticamente tras una redirección
model.addAttribute("mensaje", "La inscripción se ha realizado correctamente");
return "redirect:/inscripciones";

Para preparar datos destinados a la redirección utilizamos RedirectAttributes:

Recepción de RedirectAttributes en el método POST
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado,
        Model model,
        RedirectAttributes redirectAttributes) {

    // ...
}

Disponemos de dos mecanismos principales:

MétodoUso habitual¿Puede aparecer en la URL?
addAttribute(...)Datos que forman parte de la URL de destino.Sí.
addFlashAttribute(...)Datos temporales destinados a la siguiente petición.No.

5️⃣ Atributos normales de redirección​

addAttribute(...) se utiliza cuando el dato tiene sentido como parte de la URL.

Por ejemplo, para un filtro:

Parámetro añadido a la URL de redirección
redirectAttributes.addAttribute("ciclo", "DAW");
return "redirect:/inscripciones";

La URL resultante puede ser equivalente a:

URL con un parámetro de redirección
/inscripciones?ciclo=DAW

También puede utilizarse para completar una variable de ruta:

Redirección utilizando una variable incluida en la ruta
redirectAttributes.addAttribute("id", 25);
return "redirect:/inscripciones/{id}";

que produciría una URL equivalente a:

URL resultante con variable de ruta
/inscripciones/25
consejo

addAttribute(...) es apropiado cuando el dato pertenece a la URL, por ejemplo un identificador, un filtro o un número de página.

6️⃣ Flash attributes: datos para la siguiente petición​

Para un mensaje de confirmación normalmente no queremos añadir ?mensaje=... a la URL.

Los flash attributes permiten transportar información temporal desde una petición hasta la siguiente durante una redirección:

Mensaje temporal añadido antes de una redirección
redirectAttributes.addFlashAttribute(
    "mensaje",
    "La inscripción se ha realizado correctamente"
);

return "redirect:/inscripciones";

Spring conserva temporalmente ese valor para la petición que recibe la redirección.

🟩 Mostrar el mensaje en Thymeleaf​

La vista de destino puede utilizarlo directamente:

Mensaje temporal mostrado después de la redirección
<div th:if="${mensaje}" class="mensaje-exito">
  <p th:text="${mensaje}"></p>
</div>

No necesitamos recuperarlo manualmente en el método GET. Spring MVC lo pone a disposición del Model de la petición de destino.

Método GET que muestra la página después de la redirección
@GetMapping("/inscripciones")
public String mostrarInscripciones() {
    return "inscripciones";
}

🟨 Ciclo de vida de un flash attribute​

Podemos resumirlo así:

  1. El POST añade el flash attribute.
  2. Spring lo conserva temporalmente durante la redirección.
  3. El navegador realiza el nuevo GET.
  4. Spring hace disponible el atributo en esa petición.
  5. Thymeleaf puede mostrarlo.

Spring MVC gestiona este mecanismo normalmente mediante almacenamiento temporal asociado a la sesión HTTP. En esta unidad no necesitamos manipular la sesión directamente.

aviso

Los flash attributes están pensados para información pequeña y temporal, como mensajes de confirmación o avisos. No son un mecanismo de almacenamiento permanente.

7️⃣ El flujo completo del formulario​

Ya podemos reunir las dos ramas del formulario en un único controlador:

Procesamiento completo con errores y redirección tras el éxito
@Controller
public class InscripcionController {

    @GetMapping("/inscripcion")
    public String mostrarFormulario(Model model) {
        model.addAttribute("inscripcion", new InscripcionForm());
        prepararDatosFormulario(model);
        return "inscripcion";
    }

    @PostMapping("/inscripcion")
    public String procesarInscripcion(
            @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
            BindingResult resultado,
            Model model,
            RedirectAttributes redirectAttributes) {

        if (resultado.hasErrors()) {
            prepararDatosFormulario(model);
            return "inscripcion";
        }

        // Procesamiento correcto de los datos.

        redirectAttributes.addFlashAttribute(
            "mensaje",
            "La inscripción se ha realizado correctamente"
        );

        return "redirect:/inscripciones";
    }

    @GetMapping("/inscripciones")
    public String mostrarInscripciones() {
        return "inscripciones";
    }

    private void prepararDatosFormulario(Model model) {
        model.addAttribute("ciclos", List.of("DAW", "DAM", "ASIR"));
    }
}
en este ejemplo

El POST tiene dos salidas:

  • si hay errores, reconstruimos los datos auxiliares y volvemos directamente a inscripcion.
  • si todo es correcto, añadimos un mensaje flash y redirigimos a /inscripciones.

La nueva petición GET puede mostrar ese mensaje sin dejar al navegador situado sobre el POST.

La vista de destino puede contener simplemente:

Confirmación mostrada tras completar correctamente el formulario
<h1>Inscripciones</h1>

<div th:if="${mensaje}" class="mensaje-exito">
  <p th:text="${mensaje}"></p>
</div>

El flujo completo de la UT3 queda así:

Flujo final del formulario
formulario
   ↓
POST
   ↓
binding y validación
   ↓
¿hay errores?
   ├── sí → misma vista → valores conservados → mensajes de error
   └── no → procesamiento → flash attribute → redirect → GET → confirmación
Idea principal

No se trata de memorizar una sucesión de anotaciones y métodos, sino de comprender qué información existe en cada petición y por qué devolvemos una vista o realizamos una redirección en cada rama.

8️⃣ Errores frecuentes y qué debemos recordar​

🟩 Redirigir cuando hay errores de validación​

En nuestro flujo habitual no lo hacemos. Si hay errores, devolvemos directamente la misma vista para conservar el objeto y su BindingResult.

🟨 Devolver una vista después de un POST correcto​

Puede funcionar, pero deja al navegador sobre la respuesta del POST. PRG evita que una actualización normal pueda volver a ejecutarlo.

🟧 Utilizar Model como si sobreviviera a la redirección​

Una redirección inicia otra petición. Los datos que deban llegar a ella deben transportarse explícitamente.

🟥 Confundir addAttribute() y addFlashAttribute()​

addAttribute() se utiliza para valores que forman parte de la URL. addFlashAttribute() transporta información temporal hasta la siguiente petición.

🟪 Utilizar flash attributes como almacenamiento permanente​

No es su finalidad. Están pensados para datos temporales asociados al salto entre peticiones.

9️⃣ Qué debemos haber entendido​

Al terminar este punto debemos conservar estas ideas:

  • devolver una vista y realizar una redirección no son lo mismo.
  • después de un POST correcto suele ser conveniente aplicar Post/Redirect/Get.
  • cuando hay errores de validación normalmente devolvemos directamente la misma vista.
  • addAttribute(...) se utiliza para datos que deben formar parte de la URL de redirección.
  • addFlashAttribute(...) transporta datos temporales hasta la siguiente petición sin añadirlos a la URL.
  • los mensajes de confirmación son un uso habitual de los flash attributes.
