Actividad final. Formularios y validación

En las actividades anteriores hemos construido paso a paso el flujo de formularios de AulaHub. Ahora vamos a comprobar si podemos aplicar esas mismas ideas en una aplicación distinta y con mayor autonomía.

El proyecto se llamará MaterialLab y permitirá consultar material tecnológico disponible y solicitar su préstamo.

Objetivo

Construir el backend Spring Boot necesario para que una interfaz Thymeleaf ya preparada funcione correctamente, utilizando GET y POST, binding con objetos, distintos controles de formulario, validación, gestión de errores, subida de archivos y Post/Redirect/Get con mensajes flash.

1️⃣ Punto de partida​

Recibirás únicamente los recursos de interfaz:

Recursos proporcionados
templates/
├── materiales.html
└── prestamo.html

static/
├── css/
│   └── materialab.css
└── img/
    └── ...

👉 Descargar recursos de MaterialLab

Las plantillas ya contienen código Thymeleaf. No debes sustituirlas por páginas HTML nuevas: tendrás que estudiar qué datos esperan y construir el backend que necesitan.

El formulario de préstamo contiene distintos controles:

  • campos de texto.
  • un <select> para elegir material.
  • radio buttons para elegir la modalidad del préstamo.
  • checkboxes múltiples para seleccionar accesorios.
  • un checkbox individual para aceptar las condiciones.
  • un campo de tipo file para adjuntar opcionalmente un justificante.
aviso

No se proporciona código Java, pom.xml, controladores, modelos ni clases de formulario.

La parte visual ya está resuelta. El objetivo es trabajar con Spring Boot y hacer que el formulario funcione correctamente.

Crea un proyecto desde Spring Initializr con, al menos:

  • Spring Web.
  • Thymeleaf.
  • Validation.
  • Spring Boot DevTools.

2️⃣ El reto​

MaterialLab debe permitir dos operaciones distintas:

No utilizaremos base de datos. Los materiales y las opciones del formulario se mantendrán en memoria.

3️⃣ Datos de la aplicación​

🟩 Materiales disponibles​

Crea una clase Material con estas propiedades:

PropiedadTipo
idLong
nombreString
tipoString
disponibleboolean

La aplicación trabajará con estos datos:

idNombreTipoDisponible
1Portátil de desarrolloEquiposSí
2Kit de placa programableElectrónicaSí
3Router de prácticasRedesSí
4Cámara y micrófono USBMultimediaNo

Puedes crear esta colección directamente en Java. No utilices JPA ni repositorios.

🟨 Datos del préstamo​

Crea una clase PrestamoForm con:

PropiedadTipoControl asociado
nombreStringCampo de texto.
emailStringCampo de correo.
materialIdLong<select>.
diasIntegerCampo numérico.
modalidadStringRadio buttons.
accesoriosList<String>Checkboxes múltiples.
observacionesString<textarea>.
aceptaCondicionesbooleanCheckbox individual.

Añade constructor sin argumentos, getters y setters.

Observa los tipos

Los controles no representan siempre el mismo tipo de dato.

Los radio buttons permiten escoger un único valor, por lo que modalidad puede almacenarse en un String.

Los checkboxes de accesorios permiten seleccionar varios valores, por lo que utilizaremos una List<String>.

El checkbox de condiciones representa una decisión sí/no y se almacenará en un boolean.

El archivo adjunto no formará parte de PrestamoForm. Lo recibiremos de forma independiente como MultipartFile.

4️⃣ Construye la consulta del catálogo​

🟩 GET /materiales​

La plantilla materiales.html debe recibir:

Atributo del ModelContenido
materialesMateriales que deben mostrarse.
tiposTipos disponibles para el filtro.
tipoSeleccionadoFiltro aplicado actualmente.

La página contiene un formulario GET para filtrar el catálogo por tipo.

Debes conseguir que funcionen, por ejemplo:

Ejemplos de consulta
/materiales
/materiales?tipo=Redes
/materiales?tipo=Equipos

Sin filtro se muestran todos los materiales. Con filtro, únicamente los del tipo elegido.

consejo

Reutiliza @RequestParam para recibir el filtro. No necesitas crear un objeto de formulario para un único dato de consulta.

5️⃣ Construye el formulario de préstamo​

🟩 Mostrar el formulario​

Crea la ruta:

Ruta del formulario
GET /prestamos/nuevo

La plantilla prestamo.html espera:

  • prestamo: un PrestamoForm vacío.
  • materialesDisponibles: solo los materiales cuyo atributo disponible sea true.
  • accesoriosDisponibles: opciones que se mostrarán como checkboxes.

Utiliza, al menos, estos accesorios:

Accesorios disponibles
Cargador
Adaptador
Funda protectora

El <select> utiliza materialesDisponibles y los checkboxes se generan recorriendo accesoriosDisponibles.

🟨 Radio buttons y checkboxes​

La modalidad de préstamo se elegirá entre:

Modalidades
AULA
DOMICILIO

Los dos radio buttons deben estar vinculados a la misma propiedad:

prestamo.modalidad

Los accesorios deben estar vinculados a:

prestamo.accesorios

y permitir seleccionar ninguno, uno o varios.

El checkbox de aceptación se vinculará a:

prestamo.aceptaCondiciones
consejo

Observa cómo th:field permite trabajar con controles diferentes sin cambiar el mecanismo de binding:

valor único → String

varios valores → List<String>

marcado/no marcado → boolean

🟧 Preparar el envío de archivos​

El formulario ya está preparado con:

Codificación necesaria para enviar archivos
<form method="post"
      enctype="multipart/form-data">

y contiene un campo:

Archivo opcional
<input type="file"
       name="archivo"
       accept=".pdf,.png,.jpg,.jpeg">

El justificante será opcional.

aviso

multipart/form-data es necesario cuando un formulario envía archivos.

El archivo no llegará mediante el binding de PrestamoForm: lo recibiremos como un parámetro adicional del método.

🟥 Procesar el formulario​

Crea:

Ruta de procesamiento
POST /prestamos

El método debe recibir:

  • el formulario mediante @Valid y @ModelAttribute.
  • su BindingResult.
  • el archivo mediante @RequestParam("archivo") MultipartFile archivo.
  • el Model, cuando sea necesario reconstruir la vista.

No es necesario crear una clase diferente para representar el archivo.

6️⃣ Añade las reglas de validación​

PrestamoForm debe cumplir estas reglas:

CampoRegla
nombreObligatorio y entre 3 y 60 caracteres.
emailObligatorio y con formato de correo electrónico.
materialIdObligatorio.
diasObligatorio y entre 1 y 7.
modalidadDebe seleccionarse una modalidad.
accesoriosOpcional. Puede seleccionarse ninguno, uno o varios.
observacionesOpcional, máximo 200 caracteres.
aceptaCondicionesDebe estar marcado.

Utiliza restricciones de Jakarta Validation adecuadas y mensajes comprensibles para el usuario.

consejo

@AssertTrue resulta especialmente útil para la aceptación obligatoria de las condiciones.

No todas las propiedades necesitan una restricción. accesorios es opcional.

El archivo también será opcional, por lo que no necesitas añadir una regla de Jakarta Validation para él.

7️⃣ Gestiona correctamente los errores​

El método POST /prestamos debe recibir un BindingResult en la posición correcta.

Si existen errores:

  1. No redirijas.
  2. Vuelve directamente a prestamo.html.
  3. Conserva el mismo objeto PrestamoForm recibido.
  4. Vuelve a añadir materialesDisponibles al Model.
  5. Vuelve a añadir accesoriosDisponibles al Model.

La plantilla ya contiene los elementos Thymeleaf necesarios para mostrar los errores.

Comprueba, al menos:

  • nombre vacío.
  • email incorrecto.
  • material sin seleccionar.
  • dias vacío, menor que 1 y mayor que 7.
  • modalidad sin seleccionar.
  • condiciones sin aceptar.
  • ningún accesorio seleccionado.
  • uno o varios accesorios seleccionados.
aviso

Al volver al formulario después de un error deben conservarse las selecciones realizadas en el <select>, los radio buttons y los checkboxes.

El campo de archivo es una excepción: los navegadores no vuelven a rellenar automáticamente un <input type="file">. Si la validación falla, el usuario tendrá que seleccionar de nuevo el archivo.

8️⃣ Procesa el archivo opcional​

Si el usuario no ha seleccionado ningún archivo:

archivo.isEmpty()

la solicitud debe continuar normalmente.

Si existe un archivo, debes:

  1. Crear, si es necesario, una carpeta local llamada uploads.
  2. Consultar al menos su nombre original, tamaño y tipo de contenido.
  3. Generar un nombre propio para almacenarlo.
  4. Guardarlo en uploads.

Puedes utilizar UUID para generar el nombre.

aviso

No utilices directamente el nombre original proporcionado por el navegador como nombre definitivo del archivo.

En esta actividad no necesitamos desarrollar una validación avanzada de tipos MIME, límites de tamaño, antivirus ni almacenamiento en base de datos.

Alcance

La subida de archivos se incorpora para practicar el flujo básico:

multipart/form-data → MultipartFile → comprobar → guardar

No necesitamos implementar descarga de archivos ni asociarlos a una base de datos.

9️⃣ Completa la rama correcta con PRG​

Si el formulario no contiene errores:

  1. Procesa el archivo si se ha adjuntado.
  2. Añade un mensaje temporal mediante addFlashAttribute().
  3. Redirige a /materiales.
  4. El navegador debe terminar en una nueva petición GET /materiales.
  5. materiales.html debe mostrar el mensaje de confirmación.

El resultado debe seguir este criterio:

Decisión después del POST
hay errores  →  return "prestamo"

sin errores  →  procesar archivo opcional
             →  flash attribute
             →  redirect:/materiales
             →  GET /materiales

Después de una operación correcta, actualiza la página en el navegador y comprueba que no se vuelve a enviar el POST.

🔟 Comprobación final​

Antes de terminar, comprueba:

  • /materiales muestra el catálogo completo.
  • El filtro GET funciona.
  • /prestamos/nuevo muestra únicamente los materiales disponibles.
  • Los checkboxes de accesorios se generan desde accesoriosDisponibles.
  • El formulario realiza binding sobre un PrestamoForm.
  • La modalidad seleccionada llega correctamente a modalidad.
  • Los accesorios seleccionados llegan a List<String> accesorios.
  • El checkbox de condiciones se enlaza con aceptaCondiciones.
  • Las reglas de validación funcionan.
  • Los errores vuelven a la misma vista y conservan los datos introducidos.
  • El <select>, los radio buttons y los checkboxes conservan su estado tras un error.
  • Los datos auxiliares vuelven a prepararse cuando hay errores.
  • El formulario utiliza multipart/form-data.
  • El archivo se recibe mediante MultipartFile.
  • Una solicitud sin archivo sigue funcionando.
  • Si se adjunta un archivo, se guarda en uploads con un nombre generado por la aplicación.
  • La rama correcta utiliza PRG.
  • El mensaje de confirmación llega mediante flash attribute.
  • Actualizar la página final no repite el POST.
  • No has utilizado JPA, repositorios, servicios ni base de datos.

1️⃣1️⃣ Ampliación opcional​

Añade un segundo filtro GET que permita mostrar únicamente los materiales disponibles.

Debe poder combinarse con el filtro por tipo sin modificar el comportamiento del formulario de préstamo.

🟧 Qué se tendrá en cuenta​

La revisión se centrará en cinco aspectos:

  1. Funcionamiento. Las rutas GET y POST funcionan y producen el resultado esperado.
  2. Tratamiento de datos. Se utilizan correctamente decisiones, recorridos de colecciones y métodos para preparar y procesar la información.
  3. Recepción de datos. Los distintos controles se recuperan correctamente mediante @RequestParam, binding con @ModelAttribute y MultipartFile.
  4. Validación y flujo. Los errores vuelven al mismo formulario conservando su estado y la rama correcta utiliza Post/Redirect/Get.
  5. Código. La solución es comprensible, evita duplicaciones innecesarias y utiliza comentarios cuando aportan información.
peligro

Una solución que se limite a mostrar las plantillas, sin construir realmente el procesamiento de datos y el flujo de los formularios, no demuestra el RA3 completo.
