Actividad final. Formularios y validación

En las actividades anteriores hemos construido paso a paso el flujo de formularios de AulaHub. Ahora vamos a comprobar si podemos aplicar esas mismas ideas en una aplicación distinta y con mayor autonomía.

El proyecto se llamará MaterialLab y permitirá consultar material tecnológico disponible y solicitar su préstamo.

Objetivo

Construir el backend Spring Boot necesario para que una interfaz Thymeleaf ya preparada funcione correctamente, utilizando GET y POST, binding con objetos, validación, gestión de errores y Post/Redirect/Get con mensajes flash.

1️⃣ Punto de partida​

Recibirás únicamente los recursos de interfaz:

Recursos proporcionados
templates/
├── materiales.html
└── prestamo.html

static/
├── css/
│   └── materialab.css
└── img/
    └── ...

👉 Descargar recursos de MaterialLab

Las plantillas ya contienen código Thymeleaf. No debes sustituirlas por páginas HTML nuevas: tendrás que estudiar qué datos esperan y construir el backend que necesitan.

aviso

No se proporciona código Java, pom.xml, controladores, modelos ni clases de formulario.

La parte visual ya está resuelta. El objetivo es trabajar con Spring Boot.

Crea un proyecto desde Spring Initializr con, al menos:

  • Spring Web.
  • Thymeleaf.
  • Validation.
  • Spring Boot DevTools.

2️⃣ El reto​

MaterialLab debe permitir dos operaciones distintas:

No utilizaremos base de datos. Los materiales se mantendrán en memoria.

3️⃣ Datos de la aplicación​

🟩 Materiales disponibles​

Crea una clase Material con estas propiedades:

PropiedadTipo
idLong
nombreString
tipoString
disponibleboolean

La aplicación trabajará con estos datos:

idNombreTipoDisponible
1Portátil de desarrolloEquiposSí
2Kit de placa programableElectrónicaSí
3Router de prácticasRedesSí
4Cámara y micrófono USBMultimediaNo

Puedes crear esta colección directamente en Java. No utilices JPA ni repositorios.

🟨 Datos del préstamo​

Crea una clase PrestamoForm con:

PropiedadTipo
nombreString
emailString
materialIdLong
diasInteger
observacionesString
aceptaCondicionesboolean

Añade constructor sin argumentos, getters y setters.

4️⃣ Construye la consulta del catálogo​

🟩 GET /materiales​

La plantilla materiales.html debe recibir:

Atributo del ModelContenido
materialesMateriales que deben mostrarse.
tiposTipos disponibles para el filtro.
tipoSeleccionadoFiltro aplicado actualmente.

La página contiene un formulario GET para filtrar el catálogo por tipo.

Debes conseguir que funcionen, por ejemplo:

Ejemplos de consulta
/materiales
/materiales?tipo=Redes
/materiales?tipo=Equipos

Sin filtro se muestran todos los materiales. Con filtro, únicamente los del tipo elegido.

consejo

Reutiliza @RequestParam para recibir el filtro. No necesitas crear un objeto de formulario para un único dato de consulta.

5️⃣ Construye el formulario de préstamo​

🟩 Mostrar el formulario​

Crea la ruta:

Ruta del formulario
GET /prestamos/nuevo

La plantilla prestamo.html espera:

  • prestamo: un PrestamoForm vacío.
  • materialesDisponibles: solo los materiales cuyo atributo disponible sea true.

El <select> de la plantilla utiliza esa colección para generar sus opciones.

🟨 Procesar el formulario​

Crea:

Ruta de procesamiento
POST /prestamos

Recibe el formulario como un único objeto mediante @ModelAttribute y activa su validación con @Valid.

6️⃣ Añade las reglas de validación​

PrestamoForm debe cumplir estas reglas:

CampoRegla
nombreObligatorio y entre 3 y 60 caracteres.
emailObligatorio y con formato de correo electrónico.
materialIdObligatorio.
diasObligatorio y entre 1 y 7.
observacionesOpcional, máximo 200 caracteres.
aceptaCondicionesDebe estar marcado.

Utiliza restricciones de Jakarta Validation adecuadas y mensajes comprensibles para el usuario.

7️⃣ Gestiona correctamente los errores​

El método POST /prestamos debe recibir un BindingResult en la posición correcta.

Si existen errores:

  1. No redirijas.
  2. Vuelve directamente a prestamo.html.
  3. Conserva el mismo objeto PrestamoForm recibido.
  4. Vuelve a añadir materialesDisponibles al Model.

La plantilla ya contiene los elementos Thymeleaf necesarios para mostrar los errores. Tu backend debe proporcionar el estado correcto para que funcionen.

Comprueba, al menos:

  • nombre vacío.
  • email incorrecto.
  • material sin seleccionar.
  • dias vacío, menor que 1 y mayor que 7.
  • condiciones sin aceptar.

8️⃣ Completa la rama correcta con PRG​

Si el formulario no contiene errores:

  1. Añade un mensaje temporal mediante addFlashAttribute().
  2. Redirige a /materiales.
  3. El navegador debe terminar en una nueva petición GET /materiales.
  4. materiales.html debe mostrar el mensaje de confirmación.

El resultado debe seguir este criterio:

Decisión después del POST
hay errores  →  return "prestamo"

sin errores  →  flash attribute
             →  redirect:/materiales
             →  GET /materiales

Después de una operación correcta, actualiza la página en el navegador y comprueba que no se vuelve a enviar el POST.

9️⃣ Comprobación final​

Antes de terminar, comprueba:

  • /materiales muestra el catálogo completo.
  • El filtro GET funciona sin modificar el HTML proporcionado.
  • /prestamos/nuevo muestra el formulario con los materiales disponibles.
  • El formulario realiza binding sobre un PrestamoForm.
  • Las reglas de validación funcionan.
  • Los errores vuelven a la misma vista y conservan los datos introducidos.
  • El <select> sigue teniendo opciones después de un error.
  • La rama correcta utiliza PRG.
  • El mensaje de confirmación llega mediante flash attribute.
  • Actualizar la página final no repite el POST.
  • No has utilizado JPA, repositorios, servicios ni base de datos.

🔟 Ampliación opcional​

Añade un segundo filtro GET que permita mostrar únicamente los materiales disponibles.

Debe poder combinarse con el filtro por tipo sin modificar el comportamiento del formulario de préstamo.

🟧 Qué se tendrá en cuenta​

La revisión se centrará en cinco aspectos:

  1. Funcionamiento. Las rutas GET y POST funcionan y producen el resultado esperado.
  2. Tratamiento de datos. Se utilizan correctamente decisiones, recorridos de colecciones y métodos para preparar y procesar la información de la aplicación.
  3. Recepción de datos. Los datos enviados por los formularios se recuperan correctamente mediante @RequestParam y binding con @ModelAttribute.
  4. Validación y flujo. Las reglas se aplican, los errores regresan al mismo formulario conservando los datos necesarios y la rama correcta utiliza Post/Redirect/Get con un mensaje flash.
  5. Código. La solución es comprensible, evita duplicaciones innecesarias e incluye comentarios cuando realmente aportan información.
peligro

Una solución que se limite a mostrar las plantillas, sin construir realmente el procesamiento de datos y el flujo de los formularios, no demuestra el RA3 completo.
