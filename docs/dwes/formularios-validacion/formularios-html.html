1. Formularios HTML

En esta unidad no vamos a aprender los formularios HTML desde cero, porque ese contenido ya se ha trabajado previamente en el módulo de Lenguajes de Marcas. Este primer punto funciona únicamente como recordatorio de los aspectos que necesitamos para trabajar después en el servidor. Aun así, nos conviene recuperar algunas ideas antes de empezar a enviar datos a una aplicación hecha con Spring Boot.

En Desarrollo web en entorno servidor los formularios nos interesan sobre todo por una razón: son una de las formas más habituales de recoger datos del usuario y convertirlos en una petición HTTP que llega al servidor.

Idea principal

En esta unidad utilizaremos el formulario como punto de partida de este recorrido:

formulario HTML → datos enviados → petición HTTP → aplicación Spring Boot

1️⃣ Qué necesitamos recordar de los formularios​

Antes de continuar, conviene tener clara una idea general: un formulario no es solo una parte visual de una página. También es el mecanismo que permite reunir información, asociarla a unos nombres y prepararla para su envío.

En otras palabras, cuando el usuario escribe en varios campos y pulsa un botón, el navegador no envía “una pantalla” al servidor. Lo que envía son datos organizados a partir de los controles del formulario.

🟩 Un material previo que ya tenemos​

Los aspectos generales de los formularios HTML ya están explicados con más detalle en los apuntes del módulo de Lenguajes de Marcas. Si necesitas repasar tipos de controles, listas desplegables, botones o atributos de uso general, puedes consultar este material:

  • Apuntes de Lenguajes de Marcas · Formularios HTML.
consejo

En DWES no vamos a repetir toda esa teoría. Aquí nos centraremos en aquello que necesitamos para comprender cómo recibe el servidor los datos del formulario.

🟨 Los elementos que más nos importan en esta unidad​

De todos los elementos y atributos posibles, en este momento hay algunos especialmente importantes:

  • El elemento <form>, porque delimita el formulario.
  • El atributo action, porque indica a qué dirección se enviará la información.
  • El atributo method, porque indica cómo se enviarán los datos.
  • Los controles del formulario, como <input>, <select> o <textarea>.
  • El atributo name, porque identifica cada dato que se enviará al servidor.
  • El botón de envío, normalmente con type="submit", porque desencadena el envío del formulario.

La siguiente ilustración resume esta estructura básica.

🟧 Un ejemplo mínimo​

Observa este formulario sencillo:

Estructura básica de un formulario HTML
<form action="/registro" method="post">
  <label for="nombre">Nombre</label>
  <input type="text" id="nombre" name="nombre">

  <label for="email">Correo electrónico</label>
  <input type="email" id="email" name="email">

  <button type="submit">Enviar</button>
</form>
en este ejemplo

En este ejemplo ya aparecen casi todas las piezas que necesitaremos después.

  • action="/registro" indica la ruta a la que se enviará el formulario.
  • method="post" indica que los datos se enviarán mediante una petición POST.
  • Cada campo tiene un id, que sirve para identificarlo dentro de la página y asociarlo con su label.
  • Cada campo tiene también un name, que será la clave del dato enviado al servidor.
  • El botón con type="submit" provoca el envío del formulario.

2️⃣ Por qué el atributo name es tan importante​

Cuando trabajamos solo en el lado del navegador, a veces prestamos más atención al aspecto visual del formulario o a la asociación entre etiquetas y campos. Sin embargo, en el desarrollo en servidor hay un detalle decisivo: si un control no tiene atributo name, su valor no se enviará como dato del formulario.

Esta idea merece detenerse un momento en ella, porque será la base de todo lo que haremos después con Spring Boot.

🟩 id y name no son lo mismo​

Es bastante frecuente confundir estos dos atributos.

  • id identifica de forma única un elemento dentro de la página.
  • name identifica el dato que viajará al servidor.

Podemos decirlo de forma sencilla así:

  • id ayuda al navegador y al HTML de la página.
  • name ayuda a construir los datos de la petición.

Si un campo tiene id pero no tiene name, podrá seguir existiendo visualmente en la página, pero no formará parte del envío de datos del formulario.

🟨 Qué datos construye realmente el navegador​

La siguiente ilustración muestra muy bien esta idea.

En el ejemplo de la ilustración, el navegador prepararía unos datos equivalentes a estos:

Datos que el navegador prepara para enviar
nombre=Ana
email=ana@ejemplo.com

El campo Grupo no aparecería en el envío porque no tiene atributo name.

Idea importante

Tener atributo name es necesario para que un control pueda participar en el envío, pero no todos los controles visibles se envían siempre.

Por ejemplo:

  • Un control con disabled no se envía.
  • Un checkbox o un radio que no esté seleccionado no aporta ningún valor.
  • Un control sin name tampoco forma parte de los datos enviados.

En esta unidad no necesitamos estudiar todas las reglas de envío de los controles HTML, pero sí recordar que el navegador construye la petición a partir de los controles que realmente participan en el formulario.

aviso

Un error muy frecuente consiste en crear correctamente el formulario desde el punto de vista visual, pero olvidar el atributo name en uno o varios campos.

Cuando eso ocurre, el usuario puede escribir en ellos con normalidad, pero el servidor no recibirá esos valores.

3️⃣ Opciones de un formulario preparadas desde el servidor​

Un <select> puede contener sus opciones escritas directamente en el HTML, pero también puede generarlas a partir de datos preparados por el servidor.

Este segundo caso nos interesa especialmente en DWES porque permite que la aplicación decida qué opciones debe mostrar sin tener que escribirlas una a una en la plantilla.

🟩 Un <select> con opciones escritas en el HTML​

Podemos construir un desplegable de forma completamente estática:

Desplegable con opciones escritas directamente
<label for="ciclo">Ciclo</label>
<select id="ciclo" name="ciclo">
  <option value="">Selecciona un ciclo</option>
  <option value="DAW">DAW</option>
  <option value="DAM">DAM</option>
  <option value="ASIR">ASIR</option>
</select>

En este caso las opciones forman parte de la propia plantilla. Si queremos modificarlas, tendremos que cambiar el HTML.

🟨 Preparar las opciones en el controlador​

Como ya vimos en la UT2, un controlador puede enviar datos a una vista mediante Model.

Por ejemplo:

Colección de opciones enviada a la vista
@GetMapping("/inscripcion")
public String mostrarFormulario(Model model) {

    model.addAttribute(
        "ciclos",
        List.of("DAW", "DAM", "ASIR")
    );

    return "inscripcion";
}

La colección ciclos queda disponible para Thymeleaf cuando se procesa la plantilla.

información

Aquí no estamos introduciendo un mecanismo nuevo de Spring Boot.

Estamos reutilizando dos conceptos de la UT2 —Model y las colecciones— dentro de un formulario.

🟧 Generar las opciones con Thymeleaf​

Podemos recorrer la colección con th:each y generar una opción por cada elemento:

Desplegable generado a partir de datos del Model
<label for="ciclo">Ciclo</label>
<select id="ciclo" name="ciclo">
  <option value="">Selecciona un ciclo</option>

  <option th:each="ciclo : ${ciclos}"
          th:value="${ciclo}"
          th:text="${ciclo}">
  </option>
</select>
en este ejemplo

th:each recorre la colección ciclos.

En cada vuelta:

  • th:value establece el valor que se enviará al servidor si esa opción queda seleccionada.
  • th:text determina el texto que verá el usuario.

El navegador no recibe th:each. Thymeleaf lo procesa en el servidor y genera un <option> HTML por cada elemento de la colección.

consejo

Más adelante vincularemos este mismo <select> con una propiedad de un objeto Java mediante th:field.

De momento lo importante es distinguir dos responsabilidades:

el controlador prepara las opciones → Thymeleaf genera el HTML del desplegable.

4️⃣ El formulario como origen de una petición HTTP​

Una vez que el navegador reúne los datos del formulario, el siguiente paso es enviarlos al servidor mediante una petición HTTP. Ese paso es el que estudiaremos con más detalle en el siguiente documento.

De momento nos basta con comprender la secuencia básica:

  1. El usuario rellena los campos del formulario.
  2. El navegador identifica qué controles forman parte del envío.
  3. El navegador construye pares nombre=valor a partir de sus atributos name y de los valores introducidos.
  4. El navegador envía esa información a la URL indicada en action, usando el método indicado en method.

Ese proceso conecta directamente con lo que viene ahora en DWES: ya no nos limitaremos a mirar el formulario en el navegador, sino que aprenderemos a recibir esos datos desde Spring Boot.

🟩 Un ejemplo para enlazar con lo siguiente​

Si partimos de un formulario como este:

Formulario preparado para enviar datos al servidor
<form action="/registro" method="post">
  <label for="nombre">Nombre</label>
  <input type="text" id="nombre" name="nombre" value="Ana">

  <label for="email">Correo electrónico</label>
  <input type="email" id="email" name="email" value="ana@ejemplo.com">

  <button type="submit">Enviar</button>
</form>

el navegador enviará esos datos a la ruta /registro. En la siguiente parte de la unidad veremos cómo una aplicación Spring Boot puede recibir esa petición y acceder a sus valores.

Idea principal

En DWES no trabajamos con formularios solo para construir interfaces. Los trabajamos porque son una puerta de entrada de datos hacia nuestra aplicación en el servidor.

5️⃣ Qué debemos haber entendido antes de continuar​

Al terminar este recordatorio, conviene que tengamos claras estas ideas:

  • Un formulario recoge información del usuario y la prepara para su envío.
  • El elemento <form> marca el inicio del proceso de envío.
  • action indica el destino del envío.
  • method indica la forma de envío.
  • name identifica cada dato enviado al servidor.
  • id y name cumplen funciones distintas.
  • No todos los controles visibles se envían necesariamente.
  • Las opciones de un <select> pueden escribirse en el HTML o generarse a partir de una colección enviada por el controlador.
  • El siguiente paso será aprender a recibir esos datos en un controlador Spring Boot.
consejo
