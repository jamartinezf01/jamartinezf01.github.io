4. Validación de datos

En el apartado anterior hemos aprendido a utilizar binding para transformar los parámetros enviados por un formulario en las propiedades de un objeto Java. Gracias a @ModelAttribute, Spring puede entregarnos un InscripcionForm ya rellenado con los datos introducidos por el usuario.

Pero conseguir que los datos lleguen correctamente al objeto no significa que sean válidos. Un usuario podría dejar vacío un campo obligatorio, escribir un correo incorrecto, introducir una edad fuera del intervalo permitido o no seleccionar ninguna opción de un desplegable.

Necesitamos, por tanto, un segundo paso: comprobar que el objeto obtenido mediante binding cumple las reglas de nuestra aplicación.

Idea principal

Binding y validación son procesos distintos.

El binding responde a:

«¿Podemos trasladar los datos de la petición a un objeto Java?»

La validación responde después a:

«¿Los valores de ese objeto cumplen las reglas de nuestra aplicación?»

1️⃣ Por qué debemos validar en el servidor​

Los datos que llegan desde el navegador deben considerarse datos de entrada. Aunque el formulario esté bien diseñado, el servidor no debe asumir que siempre recibirá valores correctos.

HTML ya dispone de mecanismos que ayudan al usuario, como required, min, max, minlength, maxlength, pattern o tipos como email.

Validación inicial realizada por el navegador
<label for="email">Correo electrónico</label>
<input
  type="email"
  id="email"
  name="email"
  required
>

El navegador puede impedir un envío normal cuando el dato no cumple determinadas reglas. Esto mejora la experiencia de uso, pero no sustituye la validación en el servidor.

Una petición HTTP puede enviarse sin utilizar nuestro formulario o puede modificarse antes de llegar a la aplicación. Por eso las reglas importantes deben comprobarse nuevamente en Spring Boot.

peligro

La validación del navegador mejora la experiencia de uso, pero no debe ser nuestra única validación.

El servidor debe comprobar los datos que necesita considerar válidos antes de utilizarlos.

2️⃣ Añadir soporte de validación al proyecto​

Para utilizar Jakarta Validation necesitamos disponer de una implementación de esta especificación.

Spring Boot ofrece el starter spring-boot-starter-validation, que incorpora las dependencias necesarias y utiliza Hibernate Validator como implementación.

En un proyecto Maven añadimos:

Dependencia para habilitar Jakarta Validation
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

No necesitamos indicar manualmente una versión cuando utilizamos la gestión de dependencias habitual de Spring Boot.

aviso

Hibernate Validator no es Hibernate ORM.

Hibernate Validator aplica restricciones de validación. Hibernate ORM está relacionado con persistencia y JPA y aparecerá más adelante.

🟩 ¿De dónde salen las anotaciones?​

En proyectos actuales utilizaremos anotaciones del paquete jakarta.validation:

Importación de algunas restricciones de Jakarta Validation
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;
nota

En materiales antiguos puedes encontrar imports que comienzan por javax.validation.

En proyectos basados en Spring Boot 3 o posteriores utilizaremos jakarta.validation.

3️⃣ Definir las reglas en el objeto del formulario​

InscripcionForm representa los datos que esperamos recibir. Es un lugar adecuado para declarar las restricciones que deben cumplir sus propiedades.

Podemos evolucionar la clase anterior así:

Reglas de validación sobre los datos de inscripción
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

public class InscripcionForm {

    @NotBlank
    @Size(min = 2, max = 60)
    private String nombre;

    @NotBlank
    @Email
    private String email;

    @NotBlank
    private String ciclo;

    @NotNull
    @Min(16)
    @Max(99)
    private Integer edad;

    // Constructor, getters y setters.
}
en este ejemplo

Las anotaciones no cambian el binding. Spring seguirá intentando rellenar las propiedades del objeto con los parámetros recibidos.

Lo que añadimos ahora son restricciones que describen cuándo consideramos válidos esos valores. Por ejemplo, nombre debe contener texto real y tener entre 2 y 60 caracteres, mientras que edad debe existir y estar entre 16 y 99.

4️⃣ Restricciones habituales de Jakarta Validation​

Jakarta Validation incluye muchas restricciones estándar. No se trata de memorizarlas todas, sino de aprender a escoger la que expresa mejor cada regla.

Una idea importante es que restricciones como @Size, @Email, @Pattern, @Min o @Past no convierten por sí solas un dato en obligatorio. Cuando el valor además debe existir, las combinaremos con @NotNull, @NotBlank o @NotEmpty según corresponda.

🟩 @NotNull, @NotEmpty y @NotBlank​

No significan exactamente lo mismo:

RestricciónCompruebaUso habitual
@NotNullEl valor no puede ser null.Objetos, números, fechas y referencias.
@NotEmptyNo puede ser null ni estar vacío.Cadenas, colecciones, mapas y arrays.
@NotBlankNo puede ser null, estar vacío ni contener solo espacios.Campos de texto obligatorios.
Diferentes formas de expresar obligatoriedad
@NotBlank
private String nombre;

@NotEmpty
private List<String> intereses;

@NotNull
private LocalDate fechaNacimiento;
aviso

@NotNull sobre un String solo impide null. Una cadena vacía "" sigue cumpliendo esa restricción.

Para texto obligatorio suele ser más adecuado @NotBlank.

🟨 @Size: longitud o número de elementos​

@Size limita el tamaño de cadenas, colecciones, mapas o arrays.

Longitud permitida para el nombre
@NotBlank
@Size(min = 2, max = 60)
private String nombre;

En una colección, min y max indican el número de elementos.

aviso

@Size no comprueba intervalos numéricos. Para números utilizaremos restricciones como @Min, @Max, @DecimalMin o @DecimalMax.

🟧 @Email y @Pattern: formatos de texto​

@Email expresa que una cadena debe tener formato de correo electrónico:

Correo obligatorio con comprobación de formato
@NotBlank
@Email
private String email;

@NotBlank indica que el dato es obligatorio y @Email comprueba su formato. @Email no garantiza que la dirección exista realmente.

Cuando el formato es propio de nuestra aplicación podemos utilizar @Pattern:

Código que debe seguir un patrón concreto
@NotBlank
@Pattern(
    regexp = "^[A-Z]{2}[0-9]{4}$",
    message = "El código debe tener dos letras mayúsculas y cuatro cifras"
)
private String codigo;

En este patrón, ^ y $ marcan inicio y fin, [A-Z]{2} exige dos letras mayúsculas y [0-9]{4} cuatro cifras.

consejo

No necesitamos convertir esta unidad en un tema de expresiones regulares. Si existe una restricción específica como @Email, normalmente será más clara que una expresión regular equivalente.

🟥 Restricciones numéricas​

Para intervalos enteros podemos utilizar @Min y @Max:

Intervalo permitido para una edad
@NotNull
@Min(16)
@Max(99)
private Integer edad;

También disponemos de restricciones que expresan directamente el signo permitido:

  • @Positive.
  • @PositiveOrZero.
  • @Negative.
  • @NegativeOrZero.

Para cantidades decimales podemos utilizar @DecimalMin y @DecimalMax, y para limitar el número de cifras, @Digits:

Cantidad decimal con límites de valor y cifras
@NotNull
@DecimalMin("0.01")
@DecimalMax("9999.99")
@Digits(integer = 4, fraction = 2)
private BigDecimal precio;

Cada anotación expresa una regla diferente y pueden combinarse cuando sea necesario.

🟪 Restricciones para fechas y booleanos​

Para fechas son habituales:

  • @Past y @PastOrPresent.
  • @Future y @FutureOrPresent.
Fecha de nacimiento situada en el pasado
@NotNull
@Past
private LocalDate fechaNacimiento;

Para valores booleanos podemos utilizar @AssertTrue y @AssertFalse:

Casilla que debe estar marcada
@AssertTrue(message = "Debes aceptar las condiciones")
private boolean condicionesAceptadas;

La restricción adecuada depende siempre del significado del dato y de la regla que queramos expresar.

🟩 Resumen de restricciones útiles​

RestricciónPara qué la utilizamos principalmente
@NotNullExigir que exista un valor.
@NotEmptyImpedir valores null o vacíos en cadenas, colecciones, mapas y arrays.
@NotBlankExigir texto con algún carácter distinto de espacios.
@SizeLimitar longitud o número de elementos.
@EmailComprobar formato de correo electrónico.
@PatternExigir que un texto cumpla una expresión regular.
@Min / @MaxEstablecer límites para valores numéricos enteros.
@DecimalMin / @DecimalMaxEstablecer límites numéricos decimales.
@Positive / @PositiveOrZeroExigir valores positivos.
@Negative / @NegativeOrZeroExigir valores negativos.
@DigitsLimitar cifras enteras y decimales.
@Past / @PastOrPresentExigir fechas situadas en el pasado.
@Future / @FutureOrPresentExigir fechas situadas en el futuro.
@AssertTrue / @AssertFalseExigir un valor booleano concreto.
Idea principal

No elegimos una anotación porque sea “más fuerte” que otra. Elegimos la que describe con precisión la regla que debe cumplir el dato.

5️⃣ Combinar varias restricciones sobre una propiedad​

Una misma propiedad puede tener varias reglas:

Combinación de obligatoriedad, longitud y formato
@NotBlank
@Size(max = 100)
@Email
private String email;

Aquí comprobamos tres condiciones independientes: que exista texto real, que no supere 100 caracteres y que tenga formato de correo.

aviso

Validar no consiste en “poner muchas anotaciones”. Cada restricción debe corresponder a una regla real del formulario.

6️⃣ Activar la validación con @Valid​

Añadir anotaciones al objeto describe las reglas, pero necesitamos indicar a Spring que debe aplicarlas cuando procese el formulario.

Para ello utilizamos @Valid:

Activación de la validación sobre el objeto recibido
import jakarta.validation.Valid;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;

@PostMapping("/inscripcion")
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado) {

    if (resultado.hasErrors()) {
        return "inscripcion";
    }

    return "resultado";
}
en este ejemplo

@ModelAttribute sigue participando en el binding.

@Valid solicita que, después del binding, se comprueben las restricciones declaradas en InscripcionForm.

BindingResult permite consultar los problemas detectados durante binding y validación. Aquí solo lo introducimos para que el ejemplo sea funcional, lo estudiaremos con detalle en el siguiente punto.

aviso

Cuando queremos consultar los errores asociados a un @ModelAttribute validado, BindingResult debe aparecer inmediatamente después del objeto correspondiente en la firma del método.

El recorrido conceptual queda así:

petición POST → binding → InscripcionForm → @Valid → comprobación de restricciones

Si alguna regla no se cumple, se registran errores que podremos gestionar después.

7️⃣ Validar un desplegable dinámico​

En el apartado anterior generábamos el campo ciclo mediante un <select> vinculado con th:field.

Si su primera opción tiene valor vacío:

Opción inicial del desplegable
<option value="">Selecciona un ciclo</option>

podemos exigir que el usuario seleccione una opción mediante:

Selección obligatoria de un ciclo
@NotBlank
private String ciclo;

El recorrido es:

  • th:field="*{ciclo}" vincula el <select> con la propiedad.
  • el binding traslada el valor al objeto.
  • @NotBlank comprueba que no llegue vacío.
aviso

@NotBlank comprueba que llegue un texto no vacío, pero no demuestra por sí sola que ese texto pertenezca realmente a la colección de ciclos admitidos.

Esa comprobación adicional corresponde a una lógica que veremos más adelante.

8️⃣ Personalizar los mensajes de las restricciones​

Cada restricción dispone de un mensaje predeterminado, pero podemos proporcionar uno propio mediante message:

Restricciones con mensajes personalizados
@NotBlank(message = "El nombre es obligatorio")
@Size(
    min = 2,
    max = 60,
    message = "El nombre debe tener entre 2 y 60 caracteres"
)
private String nombre;

@NotBlank(message = "El correo electrónico es obligatorio")
@Email(message = "Introduce un correo electrónico válido")
private String email;

También podemos personalizar reglas con parámetros propios:

Patrón de texto con un mensaje comprensible
@Pattern(
    regexp = "^[A-Z]{2}[0-9]{4}$",
    message = "El código debe tener dos letras mayúsculas y cuatro cifras"
)
private String codigo;

El mensaje pertenece a la regla de validación. Todavía falta decidir dónde y cómo mostrarlo en la página; ese será el objetivo del siguiente punto.

consejo

En aplicaciones mayores es habitual externalizar los mensajes para facilitar su mantenimiento o internacionalización. En esta unidad podemos definir mensajes sencillos directamente en las restricciones.

9️⃣ Errores frecuentes al empezar a validar​

🟩 Pensar que binding y validación son lo mismo​

El binding puede asignar -5 a un Integer; la validación es la que debe decidir después que ese valor no cumple la regla establecida.

🟨 Confiar únicamente en required o en type="email"​

Las restricciones HTML ayudan al usuario, pero no sustituyen las reglas del servidor.

🟧 Pensar que @Email o @Pattern hacen obligatorio el campo​

Formato y obligatoriedad son reglas diferentes. Cuando un texto debe existir utilizaremos normalmente @NotBlank junto con la restricción de formato.

🟥 Utilizar @Size para limitar un número​

@Size se aplica a tamaños de cadenas, colecciones, mapas o arrays. Para números utilizaremos restricciones numéricas.

🟪 Confundir @NotNull, @NotEmpty y @NotBlank​

No son equivalentes. Elegiremos una u otra según el tipo de dato y los valores que queramos rechazar.

🟩 Utilizar tipos primitivos cuando necesitamos representar ausencia de valor​

Un int siempre tiene un valor. Si necesitamos distinguir entre “no se proporcionó edad” y “se proporcionó una edad”, suele resultar más adecuado utilizar Integer junto con @NotNull.

🟨 Confundir Hibernate Validator con Hibernate ORM​

Hibernate Validator aplica restricciones de validación. Hibernate ORM pertenece al ámbito de la persistencia y no interviene en este ejemplo.

🔟 Qué debemos haber entendido antes de continuar​

Al finalizar este punto debemos conservar estas ideas:

  • binding y validación son procesos distintos.
  • la validación del navegador no sustituye la validación del servidor.
  • spring-boot-starter-validation añade el soporte necesario para Jakarta Validation.
  • las restricciones se declaran sobre las propiedades del objeto que representa el formulario.
  • cada anotación expresa una regla concreta y varias pueden combinarse.
  • @Valid activa la comprobación de las restricciones al procesar el objeto.
  • los mensajes pueden asociarse a las restricciones, pero todavía debemos aprender a mostrarlos correctamente en la vista.
