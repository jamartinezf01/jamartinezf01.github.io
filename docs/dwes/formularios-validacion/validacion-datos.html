4. Validación de datos

En el apartado anterior hemos aprendido a utilizar binding para transformar los parámetros enviados por un formulario en las propiedades de un objeto Java. Gracias a @ModelAttribute, Spring puede entregarnos un InscripcionForm ya rellenado con los datos introducidos por el usuario.

Pero conseguir que los datos lleguen correctamente no significa que sean válidos. Un usuario podría dejar vacío un campo obligatorio, escribir un correo incorrecto, introducir una edad fuera del intervalo permitido o enviar un valor que nuestra aplicación no admite.

Necesitamos, por tanto, un segundo paso: validar los datos antes de utilizarlos.

En esta unidad trabajaremos principalmente con objetos de formulario bindeados, porque es la solución más cómoda para formularios con varios campos relacionados. Sin embargo, Jakarta Validation también puede aplicarse directamente sobre parámetros individuales de un método del controlador, como los recibidos mediante @RequestParam.

Idea principal

Binding y validación son procesos distintos.

El binding responde a:

«¿Podemos trasladar los datos de la petición al tipo que espera nuestra aplicación?»

La validación responde después a:

«¿Los valores recibidos cumplen las reglas de nuestra aplicación?»

1️⃣ Por qué debemos validar en el servidor​

Los datos que llegan desde el navegador deben considerarse datos de entrada. Aunque el formulario esté bien diseñado, el servidor no debe asumir que siempre recibirá valores correctos.

🟩 La validación del navegador ayuda, pero no es suficiente​

HTML dispone de mecanismos que facilitan una primera comprobación:

Validación inicial realizada por el navegador
<label for="email">Correo electrónico</label>
<input
  type="email"
  id="email"
  name="email"
  required
>

También podemos utilizar atributos como:

  • required.
  • min y max.
  • minlength y maxlength.
  • pattern.
  • tipos de control como email o number.

El navegador puede impedir un envío normal cuando el dato no cumple determinadas reglas. Esto mejora la experiencia de uso, pero no sustituye la validación en el servidor.

Una petición HTTP puede enviarse sin utilizar nuestro formulario o puede modificarse antes de llegar a la aplicación. Por eso las reglas importantes deben comprobarse nuevamente en Spring Boot.

peligro

La validación del navegador mejora la experiencia de uso, pero no debe ser nuestra única validación.

El servidor debe comprobar los datos que necesita considerar válidos antes de utilizarlos.

2️⃣ Preparar Jakarta Validation en el proyecto​

Para utilizar Jakarta Validation necesitamos disponer de una implementación de esta especificación.

Spring Boot ofrece el starter spring-boot-starter-validation, que incorpora las dependencias necesarias y utiliza Hibernate Validator como implementación.

🟩 Añadir la dependencia​

En un proyecto Maven añadimos:

Dependencia para habilitar Jakarta Validation
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

No necesitamos indicar manualmente una versión cuando utilizamos la gestión de dependencias habitual de Spring Boot.

aviso

Hibernate Validator no es Hibernate ORM.

Hibernate Validator aplica restricciones de validación. Hibernate ORM está relacionado con persistencia y JPA y aparecerá más adelante.

🟨 Utilizar las anotaciones de jakarta.validation​

En proyectos actuales utilizaremos anotaciones del paquete jakarta.validation:

Importación de algunas restricciones de Jakarta Validation
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;
nota

En materiales antiguos puedes encontrar imports que comienzan por javax.validation.

En proyectos basados en Spring Boot 3 o posteriores utilizaremos jakarta.validation.

3️⃣ Definir las reglas de validación​

Una restricción expresa una condición que debe cumplir un dato. No se trata de añadir anotaciones sin criterio, sino de escoger la que describa correctamente cada regla.

🟩 Declarar restricciones en un objeto de formulario​

InscripcionForm representa los datos que esperamos recibir en el formulario. Por eso es un lugar adecuado para declarar las reglas de sus propiedades:

Reglas de validación sobre los datos de inscripción

public class InscripcionForm {

    @NotBlank
    @Size(min = 2, max = 60)
    private String nombre;

    @NotBlank
    @Email
    private String email;

    @NotBlank
    private String ciclo;

    @NotNull
    @Min(16)
    @Max(99)
    private Integer edad;

    // Constructor, getters y setters.
}
en este ejemplo

Las anotaciones no cambian el binding. Spring seguirá intentando rellenar las propiedades del objeto con los parámetros recibidos.

Lo que añadimos son restricciones que describen cuándo consideramos válidos esos valores.

🟨 Obligatoriedad: @NotNull, @NotEmpty y @NotBlank​

Estas tres restricciones no significan exactamente lo mismo:

RestricciónCompruebaUso habitual
@NotNullEl valor no puede ser null.Objetos, números, fechas y referencias.
@NotEmptyNo puede ser null ni estar vacío.Cadenas, colecciones, mapas y arrays.
@NotBlankNo puede ser null, estar vacío ni contener solo espacios.Campos de texto obligatorios.
Diferentes formas de expresar obligatoriedad
@NotBlank
private String nombre;

@NotEmpty
private List<String> intereses;

@NotNull
private LocalDate fechaNacimiento;
aviso

@NotNull sobre un String solo impide null. Una cadena vacía "" sigue cumpliendo esa restricción.

Para texto obligatorio suele ser más adecuado @NotBlank.

🟧 Longitud y formato​

@Size limita la longitud de una cadena o el número de elementos de una colección, mapa o array:

Longitud permitida para el nombre
@NotBlank
@Size(min = 2, max = 60)
private String nombre;

Para correos electrónicos podemos utilizar @Email:

Correo obligatorio con comprobación de formato
@NotBlank
@Email
private String email;

@Email comprueba el formato, pero no demuestra que la dirección exista realmente.

Cuando necesitamos un formato propio podemos recurrir a @Pattern:

Código que debe seguir un patrón concreto
@NotBlank
@Pattern(
    regexp = "^[A-Z]{2}[0-9]{4}$",
    message = "El código debe tener dos letras mayúsculas y cuatro cifras"
)
private String codigo;
consejo

No necesitamos convertir esta unidad en un tema de expresiones regulares. Si existe una restricción específica como @Email, normalmente será más clara que una expresión regular equivalente.

🟥 Restricciones numéricas​

Para intervalos enteros podemos utilizar @Min y @Max:

Intervalo permitido para una edad
@NotNull
@Min(16)
@Max(99)
private Integer edad;

También disponemos de:

  • @Positive y @PositiveOrZero.
  • @Negative y @NegativeOrZero.
  • @DecimalMin y @DecimalMax.
  • @Digits.

Por ejemplo:

Cantidad decimal con límites de valor y cifras
@NotNull
@DecimalMin("0.01")
@DecimalMax("9999.99")
@Digits(integer = 4, fraction = 2)
private BigDecimal precio;
aviso

@Size no se utiliza para limitar un valor numérico.

Una cosa es el tamaño de una cadena o colección y otra el valor de un número.

🟪 Fechas y booleanos​

Para fechas son habituales:

  • @Past y @PastOrPresent.
  • @Future y @FutureOrPresent.
Fecha de nacimiento situada en el pasado
@NotNull
@Past
private LocalDate fechaNacimiento;

Para valores booleanos podemos utilizar @AssertTrue y @AssertFalse:

Casilla que debe estar marcada
@AssertTrue(message = "Debes aceptar las condiciones")
private boolean condicionesAceptadas;

🟩 Combinar restricciones y personalizar mensajes​

Una misma propiedad puede tener varias reglas:

Combinación de obligatoriedad, longitud y formato
@NotBlank(message = "El correo electrónico es obligatorio")
@Size(
    max = 100,
    message = "El correo no puede superar los 100 caracteres"
)
@Email(message = "Introduce un correo electrónico válido")
private String email;

Cada restricción expresa una condición distinta.

aviso

Validar no consiste en “poner muchas anotaciones”.

Cada restricción debe corresponder a una regla real del formulario.

4️⃣ Validar un objeto bindeado​

Este será el enfoque principal de la unidad cuando trabajemos con formularios que contienen varios campos relacionados.

🟩 Activar la validación con @Valid​

Añadir restricciones a InscripcionForm describe las reglas, pero todavía tenemos que pedir a Spring que las compruebe.

Para ello utilizamos @Valid:

Validación de un objeto recibido mediante binding
import jakarta.validation.Valid;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;

@PostMapping("/inscripcion")
public String procesarInscripcion(
        @Valid @ModelAttribute("inscripcion") InscripcionForm inscripcion,
        BindingResult resultado) {

    if (resultado.hasErrors()) {
        return "inscripcion";
    }

    return "resultado";
}
en este ejemplo

@ModelAttribute participa en el binding.

@Valid solicita que se comprueben las restricciones declaradas en InscripcionForm.

BindingResult permite consultar los problemas producidos durante el binding y la validación. Lo estudiaremos con detalle en el siguiente punto.

aviso

Cuando queremos consultar los errores asociados a un @ModelAttribute validado, BindingResult debe aparecer inmediatamente después de ese objeto en la firma del método.

🟨 Validar un desplegable​

Si un <select> utiliza una primera opción con valor vacío:

Opción inicial del desplegable
<option value="">Selecciona un ciclo</option>

podemos exigir que el usuario seleccione una opción mediante:

Selección obligatoria de un ciclo
@NotBlank(message = "Debes seleccionar un ciclo")
private String ciclo;
aviso

@NotBlank comprueba que llegue un texto no vacío, pero no demuestra por sí sola que ese texto pertenezca realmente a la colección de ciclos admitidos.

Esa comprobación adicional corresponde a la lógica de la aplicación y no la necesitamos todavía.

5️⃣ Validar parámetros individuales del controlador​

Jakarta Validation no está limitada a objetos bindeados. También podemos colocar restricciones directamente sobre parámetros individuales de un método del controlador.

Este caso lo veremos únicamente como posibilidad complementaria, porque para formularios completos seguiremos trabajando principalmente con objetos.

🟩 Restricciones sobre @RequestParam​

Imaginemos una operación sencilla que recibe un nombre y el número de días de una reserva:

Validación directa de parámetros individuales
@PostMapping("/reserva")
public String reservar(
        @RequestParam
        @NotBlank(message = "El nombre es obligatorio")
        String nombre,

        @RequestParam
        @Min(value = 1, message = "La reserva debe ser de al menos un día")
        @Max(value = 7, message = "La reserva no puede superar los 7 días")
        Integer dias) {

    return "resultado-reserva";
}

Aquí no existe una clase ReservaForm. Las restricciones se aplican directamente a los argumentos del método.

Idea principal

No necesitamos @Valid para este caso.

Las restricciones colocadas directamente sobre los parámetros hacen que Spring MVC aplique validación del método.

Si los valores cumplen las restricciones, el método continúa normalmente. Si alguna de ellas falla, Spring MVC puede producir una HandlerMethodValidationException.

La gestión de ese error se mostrará brevemente en el siguiente documento.

aviso

No debemos confundir la validación de un parámetro con los problemas que pueden ocurrir antes.

Por ejemplo, un parámetro obligatorio que no llega o un texto que no puede convertirse a Integer puede producir un error antes de comprobar @Min o @Max.

🟨 ¿Cuándo utilizar cada enfoque?​

SituaciónEnfoque habitual
Uno o pocos parámetros independientes.@RequestParam + restricciones directas.
Formulario con varios campos relacionados.@ModelAttribute + objeto + @Valid.
Necesitamos conservar los datos y mostrar errores junto a los campos.Objeto bindeado + BindingResult.
consejo

Para los formularios de esta unidad utilizaremos principalmente objetos bindeados.

La validación directa de parámetros nos interesa conocerla para entender que Jakarta Validation no depende exclusivamente de @ModelAttribute.

6️⃣ Errores frecuentes y qué debemos conservar​

🟩 Pensar que binding y validación son lo mismo​

El binding puede convertir y asignar un valor. La validación decide después si ese valor cumple las reglas.

Por ejemplo, -5 puede convertirse perfectamente a Integer, aunque después incumpla una restricción como @Min(0).

🟨 Confiar únicamente en required o type="email"​

Las restricciones HTML ayudan al usuario, pero no sustituyen las comprobaciones del servidor.

🟧 Pensar que @Email o @Pattern hacen obligatorio el campo​

Formato y obligatoriedad son reglas distintas. Cuando un texto debe existir utilizaremos normalmente @NotBlank junto con la restricción de formato.

🟥 Utilizar @Size para limitar un número​

@Size se aplica a tamaños de cadenas, colecciones, mapas o arrays. Para números utilizaremos restricciones numéricas.

🟪 Confundir @NotNull, @NotEmpty y @NotBlank​

No son equivalentes. Elegiremos una u otra según el tipo de dato y los valores que queramos rechazar.

🟩 Utilizar tipos primitivos cuando necesitamos representar ausencia de valor​

Un int siempre tiene un valor. Si necesitamos distinguir entre “no se proporcionó edad” y “se proporcionó una edad”, suele resultar más adecuado utilizar Integer junto con @NotNull.

7️⃣ Qué debemos haber entendido antes de continuar​

Al finalizar este punto debemos tener claras estas ideas:

  • binding y validación son procesos distintos.
  • la validación del navegador no sustituye la validación del servidor.
  • spring-boot-starter-validation añade el soporte necesario para Jakarta Validation.
  • las restricciones pueden declararse sobre propiedades de un objeto o directamente sobre parámetros de un método.
  • @Valid se utiliza para solicitar la validación del objeto bindeado.
  • las restricciones directas sobre @RequestParam permiten validar parámetros individuales mediante validación del método.
  • un objeto de formulario suele ser el enfoque más cómodo para formularios con varios campos.
  • en esta unidad utilizaremos como recorrido principal @ModelAttribute + @Valid + BindingResult.
