Actividades de repaso

Este bloque de repaso se completa con tres retos prácticos, uno por sesión.

Los ejemplos de los apuntes sirven para recordar cómo funcionan las herramientas de Java. Los retos, en cambio, plantean situaciones diferentes para comprobar si somos capaces de transferir lo aprendido sin reproducir exactamente el código visto en clase.

Carácter de los retos

Estos retos son no evaluables.

No existe entrega ni calificación asociada. Su finalidad es recuperar soltura con Java, detectar dudas y comprobar hasta qué punto podemos resolver pequeños problemas de programación antes de comenzar con Spring Boot.

1️⃣ Actividad 1 · Preparar un pedido​

🟩 Objetivo​

Aplicar variables, operadores, estructuras condicionales, bucles y métodos para resolver un problema sencillo.

🟨 Contexto​

Una tienda necesita calcular el importe final de un pedido.

De un pedido conocemos:

nombre del producto
precio por unidad
cantidad solicitada
stock disponible
cliente socio o no

La tienda aplica estas reglas:

  • el pedido solo puede realizarse si hay suficiente stock;
  • si el cliente es socio, recibe un 5 % de descuento;
  • los gastos de envío son de 4,95 €;
  • el envío es gratuito si el importe después de descuentos supera los 50 €.

El objetivo de este reto era recuperar la lógica básica de programación utilizando variables, condiciones, bucles y métodos.

2️⃣ Actividad 2 · Préstamo de material audiovisual​

🟩 Objetivo​

Aplicar clases, objetos, constructores, encapsulación, relaciones entre objetos, referencias, enum, interfaces y toString().

🟨 Contexto​

Un centro dispone de material audiovisual que puede prestar temporalmente: cámaras, trípodes, micrófonos o proyectores.

El sistema debe permitir representar el material disponible y registrar préstamos a distintas personas.

No utilices las clases de los ejemplos de los apuntes. Debes diseñar una solución nueva a partir de este contexto.

🟧 Nivel 1 · En marcha​

Diseña las clases necesarias para representar:

Material
Persona
Prestamo

Como mínimo:

Material

codigo
nombre
estado

Persona

nombre
email

Prestamo

persona
material
dias

Decide:

  • qué atributos deben ser private;
  • qué constructores necesitas;
  • qué getters son necesarios;
  • qué métodos tiene sentido añadir.

El programa debe permitir crear varios objetos y mostrar información semejante a:

Persona: Lucía
Material: Cámara Sony
Duración: 3 días
aviso

No copies la estructura de Producto de los apuntes.

Piensa qué información y comportamiento pertenecen realmente a cada clase.

🟥 Nivel 2 · Conseguido​

Añade un estado al material utilizando:

public enum EstadoMaterial {
    DISPONIBLE,
    PRESTADO,
    MANTENIMIENTO
}

El sistema debe cumplir estas reglas:

  • un material solo puede prestarse si está DISPONIBLE;
  • cuando se realiza un préstamo pasa a PRESTADO;
  • cuando se devuelve vuelve a DISPONIBLE;
  • un material en MANTENIMIENTO no puede prestarse.

Añade los métodos que consideres necesarios para representar correctamente este comportamiento.

Después crea varios objetos y prueba situaciones diferentes.

Ejemplo:

Cámara Sony - PRESTADO
Micrófono Rode - DISPONIBLE
Proyector Epson - MANTENIMIENTO

🟪 Nivel 3 · Ampliado​

Crea una interfaz:

public interface Prestable {
    boolean estaDisponible();
    void prestar();
    void devolver();
}

Haz que la clase adecuada implemente esa interfaz.

Añade también un toString() que permita mostrar un objeto de forma clara.

Por ejemplo:

CAM-01 - Cámara Sony - PRESTADO

Finalmente, analiza este fragmento:

Material m1 = new Material("CAM-01", "Cámara Sony");
Material m2 = m1;

m2.prestar();

Responde antes de ejecutar:

  1. ¿Cuántos objetos Material existen realmente?
  2. ¿Qué estado tendrá m1?
  3. ¿Por qué?
Piensa en las referencias

Este último apartado sirve para comprobar que se entiende que dos variables pueden hacer referencia al mismo objeto.

🟩 Comprobación del reto​

  • Las clases representan correctamente el problema.
  • Los atributos son private.
  • Se utilizan constructores.
  • Existen relaciones entre objetos.
  • El estado se representa mediante un enum.
  • El comportamiento está repartido entre las clases y no concentrado en main.
  • Se utiliza una interfaz en el nivel ampliado.
  • toString() proporciona una representación útil.
  • Se comprende qué ocurre cuando dos variables apuntan al mismo objeto.

3️⃣ Actividad 3 · Panel de incidencias técnicas​

🟩 Objetivo​

Aplicar List, ArrayList, Map, HashMap, recorridos, búsquedas, contadores, acumuladores, modificaciones y manejo básico de excepciones.

🟨 Contexto​

El equipo de soporte de una empresa registra incidencias técnicas.

Cada incidencia dispone de:

codigo
titulo
prioridad
minutosEstimados
resuelta

Puedes utilizar una clase similar a:

Incidencia

con los atributos anteriores.

Para este reto, parte de varias incidencias ya creadas.

Por ejemplo:

INC-101  "No arranca el equipo"      ALTA     45   false
INC-102  "Ratón no responde"         BAJA     10   true
INC-103  "Sin conexión a Internet"   ALTA     30   false
INC-104  "Impresora bloqueada"       MEDIA    20   false
INC-105  "Actualizar navegador"      BAJA     15   true

Puedes representar la prioridad mediante:

public enum Prioridad {
    BAJA,
    MEDIA,
    ALTA
}

🟧 Nivel 1 · En marcha​

Crea una:

List<Incidencia>

con al menos cinco incidencias.

Genera un pequeño resumen que indique:

número total de incidencias
número de incidencias resueltas
número de incidencias pendientes
número de incidencias de prioridad ALTA

Una posible salida:

=== RESUMEN DE INCIDENCIAS ===

Total: 5
Resueltas: 2
Pendientes: 3
Prioridad alta: 2

No se indica qué variables debes utilizar durante el recorrido.

Decide qué contadores necesitas.

🟥 Nivel 2 · Conseguido​

Amplía el análisis para obtener:

incidencia con mayor tiempo estimado
tiempo total estimado de las incidencias pendientes
tiempo medio estimado de las incidencias pendientes

Además, crea un:

Map<String, Incidencia>

donde:

  • la clave sea el código de la incidencia;
  • el valor sea el objeto Incidencia.

Utiliza el mapa para consultar directamente una incidencia mediante su código.

Por ejemplo:

Buscar código: INC-103

Sin conexión a Internet
Prioridad: ALTA
Pendiente
tip

La lista resulta útil para analizar el conjunto completo.

El mapa resulta útil cuando conocemos el código y queremos recuperar directamente una incidencia concreta.

🟪 Nivel 3 · Ampliado​

Realiza ahora estas operaciones:

Resolver una incidencia​

Localiza una incidencia mediante su código y márcala como resuelta.

Cambiar una prioridad​

Busca una incidencia concreta y modifica su prioridad.

Generar un informe actualizado​

Después de los cambios, vuelve a calcular:

incidencias pendientes
incidencias resueltas
incidencias de prioridad ALTA
tiempo total pendiente

Recorrer el mapa​

Muestra todas las entradas con:

entrySet()

con un formato semejante a:

INC-101 - No arranca el equipo
INC-102 - Ratón no responde
INC-103 - Sin conexión a Internet

🟥 Control de errores​

Parte del siguiente dato:

String minutosTexto = "treinta";

Intenta convertirlo a entero mediante:

Integer.parseInt(minutosTexto)

Controla el posible error con try y catch.

Después prueba con:

String minutosTexto = "30";

y comprueba la diferencia.

🟩 Preguntas de comprobación​

  1. ¿Por qué una List es adecuada para recorrer todas las incidencias?
  2. ¿Qué ventaja aporta un Map cuando conocemos el código?
  3. ¿Qué ocurre si hacemos get() con una clave que no existe?
  4. ¿Qué diferencia hay entre put() y add()?
  5. ¿Qué ocurre si utilizamos dos veces la misma clave en un Map?
  6. ¿Cuándo tiene sentido utilizar try/catch y cuándo basta con un if?

🟨 Comprobación del reto​

  • Se crea correctamente una List.
  • Se utilizan recorridos para analizar la colección.
  • Se utilizan contadores y acumuladores.
  • Se localiza correctamente la incidencia con mayor duración.
  • Se calcula correctamente el tiempo total y medio.
  • Se crea un Map<String, Incidencia>.
  • Se utilizan put(), get() y entrySet().
  • Se modifican objetos que ya están almacenados en las colecciones.
  • Se controla una conversión incorrecta con try/catch.
  • Se entiende cuándo utilizar List y cuándo Map.

4️⃣ Errores para investigar​

Estos fragmentos no forman parte de los retos anteriores.

Su objetivo es practicar otra habilidad importante: leer código y anticipar errores.

🟩 Caso 1​

List<Incidencia> incidencias = new ArrayList<>();

incidencias.add(new Incidencia("INC-101", "Error de red"));
incidencias.add(new Incidencia("INC-102", "Error de impresión"));

for (int i = 0; i <= incidencias.size(); i++) {
    System.out.println(incidencias.get(i));
}

¿Qué problema existe?

🟨 Caso 2​

Map<String, Incidencia> mapa = new HashMap<>();

mapa.put("INC-101", incidencia1);
mapa.put("INC-101", incidencia2);

¿Cuántas entradas tendrá finalmente el mapa?

¿Qué objeto quedará asociado a "INC-101"?

🟧 Caso 3​

Incidencia incidencia = mapa.get("INC-999");

System.out.println(incidencia.getTitulo());

¿Qué puede ocurrir?

¿Cómo lo evitarías?

🟥 Caso 4​

Incidencia i1 = new Incidencia("INC-101", "Error de red");
Incidencia i2 = i1;

i2.setResuelta(true);

¿Qué valor tendrá:

i1.isResuelta()

y por qué?

Leer código también es programar

Cuando empecemos con Spring Boot, muchas veces tendremos que entender código que no hemos escrito nosotros.

Saber predecir qué hace un fragmento y localizar un error será tan importante como escribir código desde cero.

5️⃣ Comprobación final del repaso​

Al terminar las tres sesiones deberíamos ser capaces, con una ayuda razonable de los apuntes, de:

  • utilizar variables y operadores;
  • tomar decisiones mediante if;
  • utilizar bucles;
  • crear métodos con parámetros y valores de retorno;
  • diseñar clases sencillas;
  • crear objetos mediante constructores;
  • utilizar this;
  • trabajar con atributos private;
  • relacionar objetos;
  • comprender referencias a objetos;
  • utilizar enum;
  • reconocer e implementar una interfaz sencilla;
  • utilizar toString();
  • crear y recorrer una List;
  • utilizar contadores y acumuladores;
  • crear y consultar un Map;
  • distinguir cuándo utilizar List y cuándo Map;
  • modificar objetos almacenados en colecciones;
  • comprobar correctamente un valor null;
  • controlar una excepción sencilla.
Preparados para Spring Boot

El objetivo de este repaso no es repetir Programación de primero.

Queremos recuperar la base suficiente para que, cuando aparezcan los conceptos nuevos de Spring Boot, podamos centrarnos en entender cómo funciona una aplicación web y no en recordar continuamente cómo se escribe Java.
