6. Responsive y accesibilidad

Una interfaz bien diseñada no debería funcionar únicamente en el monitor donde se creó. También debe poder utilizarse en pantallas más pequeñas, con teclado y con diferentes necesidades de lectura e interacción.

En este apartado se trabajarán dos ideas complementarias:

  • Diseño responsive: adaptar la presentación a las dimensiones disponibles sin perder información ni funcionalidad.
  • Accesibilidad: facilitar que más personas puedan percibir, comprender y utilizar la aplicación, también cuando interactúan de formas diferentes.

El objetivo no es memorizar todos los criterios WCAG ni desarrollar un sistema responsive desde cero. Se trata de aprender a identificar problemas y comprobar una interfaz real con herramientas profesionales.

1️⃣ Mobile first y puntos de ruptura (breakpoints)​

Diseñar con enfoque mobile first significa empezar por las necesidades y limitaciones de una pantalla estrecha y ampliar progresivamente la disposición cuando existe más espacio. Obliga a decidir qué contenido es esencial y qué elementos deben aparecer primero.

No consiste en ocultar funciones importantes en el móvil. La misma persona debe poder consultar una actividad, comprobar sus datos y completar la reserva independientemente del tamaño de pantalla.

Qué es un breakpoint​

Un breakpoint es un punto en el que una regla CSS cambia la disposición de la interfaz. Se elige cuando el contenido deja de funcionar bien con la distribución anterior, no porque exista un número mágico válido para todas las webs.

Como ejemplo, una cuadrícula puede empezar con una columna y pasar a dos cuando hay espacio suficiente:

/* Ejemplo orientativo: ajustar a las necesidades del contenido. */
.actividades {
  display: grid;
  grid-template-columns: 1fr;
  gap: 1rem;
}

@media (min-width: 48rem) {
  .actividades {
    grid-template-columns: repeat(2, minmax(0, 1fr));
  }
}

El valor 48rem no es una obligación ni define por sí solo qué dispositivo se está utilizando. Una aplicación puede necesitar otro punto de cambio dependiendo de sus tarjetas, navegación y contenido.

2️⃣ Qué cambia entre móvil, tableta y escritorio​

En un diseño responsive no se reduce toda la página como si fuera una fotografía. Se reorganizan los elementos y se ajusta su presentación para conservar la legibilidad y la facilidad de uso.

Cambios habituales que conviene observar​

  • Columnas: varias tarjetas pueden pasar de una cuadrícula a una sola columna.
  • Navegación: una cabecera extensa puede transformarse en un menú compacto con nombre accesible.
  • Espaciado: los márgenes y separaciones pueden ajustarse sin apretar los elementos.
  • Imágenes: deben conservar proporciones razonables y adaptarse al ancho disponible.
  • Formularios: varios campos en una fila pueden apilarse y mantener sus etiquetas visibles.
  • Acciones: un botón puede ocupar más ancho en móvil si facilita la interacción.

Lo importante es que el contenido siga disponible y que el orden de lectura tenga sentido. Al cambiar la posición de los bloques, debe comprobarse también el orden con el teclado y con tecnologías de apoyo.

Adaptación no equivale a accesibilidad

Una web puede verse bien en móvil y seguir siendo difícil de usar: texto con poco contraste, campos sin etiqueta, foco invisible o controles inaccesibles con teclado.

3️⃣ Foco visible y navegación con teclado​

No todas las personas interactúan utilizando el ratón. Algunas navegan con Tab para avanzar entre enlaces, botones y campos, y utilizan Shift + Tab para retroceder. En una aplicación funcional debe poderse reconocer qué control tiene el foco.

El indicador de foco puede ser un contorno, un borde reforzado u otra señal perceptible. Si se elimina el contorno que incorpora el navegador, hay que ofrecer una alternativa visible.

Un estilo posible utiliza :focus-visible:

button:focus-visible,
a:focus-visible,
input:focus-visible {
  outline: 3px solid #F59E0B;
  outline-offset: 3px;
}

El contorno es un ejemplo: deben comprobarse sus colores y visibilidad sobre los fondos reales. Es preferible no modificar outline salvo que exista una alternativa comprobada.

Prueba manual con el teclado​

  1. Abrir la página y comenzar a navegar con Tab, sin usar el ratón.
  2. Comprobar que se reconoce el elemento enfocado en cada paso.
  3. Verificar que el orden de navegación tiene sentido.
  4. Activar enlaces y botones mediante el teclado.
  5. Comprobar que los menús, formularios y diálogos pueden utilizarse y abandonarse sin quedar bloqueados.

4️⃣ HTML semántico y textos alternativos​

La accesibilidad no depende únicamente del aspecto visual. El HTML debe describir correctamente el significado y la función del contenido, para que las tecnologías de apoyo puedan interpretarlo.

Elegir elementos por su significado​

  • <header> y <nav>: identifican la cabecera y las zonas de navegación.
  • <main>: señala el contenido principal de la página.
  • <h1> a <h6>: organizan los encabezados en una jerarquía lógica.
  • <a>: permite navegar a otro recurso o ubicación.
  • <button>: permite realizar una acción dentro de la interfaz.
  • <label>: identifica un control de formulario y debe asociarse correctamente con él.

Un div con aspecto de botón no se convierte automáticamente en un botón accesible. Conviene utilizar elementos HTML nativos cuando corresponda.

Ejemplo: etiqueta asociada a un campo​

<label for="correo">Correo electrónico</label>
<input id="correo" name="correo" type="email" required>

Esta relación no solo mejora la accesibilidad: también permite seleccionar el campo al pulsar su etiqueta.

Las imágenes también necesitan una decisión​

El atributo alt debe comunicar la información útil que transmite la imagen. En una fotografía de actividad, puede describir su contenido. En una imagen puramente decorativa, puede utilizarse alt="" para evitar información redundante.

<!-- Imagen informativa -->
<img
  src="/img/actividades/senderismo.webp"
  alt="Ruta de senderismo junto a un lago de montaña"
>

<!-- Imagen decorativa -->
<img src="/img/decoracion.svg" alt="">

No es necesario comenzar todos los textos alternativos con «Imagen de…». Tampoco conviene repetir palabra por palabra una leyenda cercana si esa información ya resulta accesible.

5️⃣ Cómo comprobarlo: DevTools, Lighthouse y WAVE​

Las herramientas ayudan a detectar problemas, pero ninguna puede sustituir la revisión manual. Una auditoría automática con una puntuación alta no demuestra por sí sola que toda la página sea accesible.

Chrome DevTools: comprobar la adaptación de la página​

El modo de dispositivos de Chrome DevTools permite simular distintas anchuras y observar cómo se adapta la interfaz. Es una aproximación útil, pero conviene probar también en un dispositivo real.

  1. Abrir la web y pulsar F12 o Ctrl + Shift + I.
  2. Activar la barra de dispositivos (Toggle device toolbar).
  3. Seleccionar el modo Responsive y cambiar gradualmente el ancho.
  4. Revisar si aparecen desbordamientos, cortes de texto, controles inaccesibles o desplazamiento horizontal innecesario.
  5. Comprobar que menús, tarjetas y formularios continúan siendo utilizables.

Lighthouse: obtener una primera auditoría​

Lighthouse analiza diversos aspectos de la página, incluida la accesibilidad. En DevTools, abrir Lighthouse, seleccionar Accessibility y generar el informe. Conviene revisar cada problema señalado y comprobar manualmente los cambios que se realicen.

No hay que interpretar su puntuación como una certificación de accesibilidad. Es una herramienta de ayuda para localizar problemas detectables de manera automática.

WAVE: revisar elementos dentro de la propia página​

WAVE identifica potenciales problemas y los muestra relacionados con el contenido. Resulta especialmente útil para localizar etiquetas, contrastes, errores y alertas que conviene investigar.

Un aviso necesita interpretación: puede señalar una posible barrera, pero no sustituye la decisión de comprobar el contexto y el comportamiento del elemento.

Contraste: recuperar una comprobación del apartado 2​

Para textos y componentes se puede utilizar el laboratorio de color de esta guía o WebAIM Contrast Checker. Como referencia, las WCAG 2.2 de nivel AA establecen 4,5:1 para texto normal, 3:1 para texto grande y 3:1 para determinada información visual necesaria en componentes e indicadores. Son criterios diferentes que deben aplicarse al elemento correspondiente.

6️⃣ Aplicación al Proyecto Intermodular​

Para comprobar la web del proyecto no hace falta crear un informe complejo. Es preferible realizar una revisión breve, repetible y basada en evidencias.

Se propone seleccionar tres pantallas representativas: una portada o listado, una pantalla de detalle y un formulario. En cada una conviene comprobar:

  • Adaptación: no se pierde información ni funcionalidad al reducir el ancho.
  • Lectura: títulos, párrafos, etiquetas y botones se distinguen con claridad.
  • Teclado: se puede recorrer e interactuar con los controles y el foco es visible.
  • Formularios: las etiquetas y los mensajes permiten completar y corregir entradas.
  • Imágenes: los textos alternativos describen información útil cuando corresponde.
  • Herramientas: las incidencias encontradas mediante DevTools, Lighthouse o WAVE se revisan y se corrigen cuando procede.
Una comprobación útil

Una forma sencilla de documentar la revisión es conservar una captura del problema, anotar qué dificultaba el uso y mostrar la pantalla corregida. Esa evidencia explica mucho mejor una mejora que una puntuación aislada de auditoría.

  • WAI: comprobaciones básicas de accesibilidad, para realizar una primera revisión manual.
  • Chrome DevTools: modo de dispositivos, para comprobar distribuciones responsive.
  • WAVE, para identificar problemas potenciales en una página.
