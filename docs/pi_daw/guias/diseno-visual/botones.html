4. Botones y elementos interactivos

Un botón no es simplemente un rectángulo con texto. En una interfaz representa una acción y ayuda a decidir qué hacer después. Su color, tamaño, forma y posición deben responder a la función que cumple, no solo a las preferencias estéticas del equipo.

Al diseñar los botones de una aplicación se toman dos decisiones relacionadas, pero distintas: qué acción debe destacar y cómo se verá ese botón dentro del estilo visual elegido. En este apartado se aprenderá a tomar ambas decisiones con ejemplos de interfaces y un laboratorio interactivo.

1️⃣ Jerarquía de acciones: ¿qué debería llamar la atención?​

Imagina una pantalla de reservas con tres opciones: Confirmar reserva, Volver y Guardar para más tarde. No tienen la misma importancia. La primera permite completar el objetivo de la pantalla; las otras son alternativas.

Si las tres aparecen como botones grandes y rellenos de colores intensos, compiten por la atención. En cambio, una acción principal bien destacada y las restantes con un peso visual menor facilitan la elección.

UNA ACCIÓN PRINCIPAL
Confirmar reservaVolverGuardar

La acción principal se distingue sin ocultar las alternativas.

Estas muestras son representaciones visuales, no botones operativos. En una página real, cada acción debe tener el comportamiento adecuado. No significa que solo pueda existir un botón primario en toda la web: lo importante es que no haya varios compitiendo dentro del mismo contexto de decisión.

2️⃣ Tipos de botón y cuándo utilizarlos​

En muchos proyectos se necesita un sistema pequeño y coherente de botones. No hace falta inventar un estilo distinto para cada pantalla.

PRIMARIO
Confirmar reserva

La acción más relevante para completar el objetivo.

SECUNDARIO
Volver

Alternativa disponible sin competir con la principal.

TERCIARIO
Ver detalles

Acción complementaria que necesita poco protagonismo.

DESTRUCTIVO
Eliminar reserva

Borra datos o provoca consecuencias difíciles de revertir.

Una distinción importante: un botón Cancelar no es automáticamente destructivo. Cancelar la edición de un formulario suele ser una acción secundaria. Eliminar una cuenta, en cambio, sí merece una señal visual de peligro. La prioridad de una acción y su significado son dimensiones diferentes.

También conviene diferenciar enlaces y botones: un enlace lleva a otro recurso o página; un botón ejecuta una acción dentro de la interfaz. No debería convertirse cualquier enlace de navegación en un botón solo porque resulte más llamativo.

3️⃣ Forma, tamaño, color e iconos​

Una vez definida la jerarquía, se puede establecer el aspecto visual de los botones. Las decisiones deben ser consistentes con la paleta y la tipografía elegidas en los apartados anteriores.

El color no depende solo de la marca​

  • Color principal: suele identificar acciones prioritarias, siempre que el texto mantenga contraste suficiente.
  • Neutros o bordes: permiten mostrar acciones alternativas con menos peso visual.
  • Rojo u otro tratamiento de peligro: identifica acciones destructivas de manera consistente. No se utiliza como simple recurso para destacar cualquier botón.
  • Colores de éxito o advertencia: se reservan para comunicar estados cuando corresponda; no son sinónimos de «botón importante».
El contraste se comprueba, no se supone

El mismo azul puede funcionar con texto blanco y otro tono no. El texto de los botones debe cumplir los criterios de contraste que correspondan. Se puede utilizar el comprobador de WebAIM y el laboratorio de este apartado.

Esquinas, medidas y espacios​

Un botón rectangular con poco radio puede sugerir sobriedad; uno muy redondeado puede transmitir mayor cercanía. Ninguna forma es correcta por sí misma. Lo importante es mantener una misma familia de estilos dentro de la aplicación.

Como punto de partida práctico, se pueden utilizar botones de 40 a 48 px de altura, con una separación horizontal generosa entre texto y borde. Son orientaciones de diseño, no valores obligatorios. El área interactiva debe resultar cómoda para puntero y táctil.

Iconos: solo cuando aporten información​

Un icono de flecha puede reforzar el sentido de «Continuar». Un icono de papelera puede ayudar a reconocer «Eliminar». Pero no hace falta añadir iconos a todos los botones. Si un botón muestra solo un icono, debe disponer de un nombre accesible, por ejemplo aria-label="Eliminar reserva".

4️⃣ Estados: el botón cambia cuando interactuamos​

El botón no debería diseñarse únicamente en su apariencia normal. Las personas necesitan saber si un elemento se puede pulsar, si ha recibido el foco del teclado, si se está ejecutando una operación o si está temporalmente desactivado.

Las muestras anteriores son estáticas. En un proyecto real, hover depende del puntero, focus-visible permite identificar el foco del teclado, active se produce durante la activación y loading debe indicar que se está procesando la operación. Un cambio de color no sustituye a la funcionalidad.

No confundir disabled con loading

Un botón desactivado comunica que no está disponible. Un botón en carga comunica que una operación está en marcha. No basta con poner ambos en gris: durante la carga conviene mantener información visible sobre lo que está ocurriendo y prevenir envíos repetidos.

5️⃣ Errores frecuentes y buenas prácticas​

Cuando varios botones parecen igual de importantes​

La solución no es elegir colores más llamativos, sino reorganizar la jerarquía. Una acción principal, alternativas reconocibles y un orden espacial coherente suelen ser suficientes.

Cuando se utilizan iconos ambiguos​

Un icono sin texto puede resultar difícil de interpretar. Si el significado no es evidente, conviene añadir una etiqueta visible. Incluso cuando visualmente solo hay un icono, debe existir un nombre accesible.

Cuando la interfaz depende solo del color​

No basta con que «Eliminar» sea rojo para explicar qué hace. El texto de la acción y, si procede, un mensaje de confirmación, deben aclarar sus consecuencias. Las advertencias y errores tampoco deberían comunicarse exclusivamente mediante colores.

Cuando el foco desaparece​

Si se elimina el contorno del navegador, es necesario ofrecer otro indicador de foco visible. La navegación mediante teclado debe permitir identificar dónde se encuentra la persona usuaria.

Cuando los botones son demasiado pequeños​

WCAG 2.2 establece, en su criterio AA de tamaño mínimo de objetivos de puntero, 24 × 24 píxeles CSS, con determinadas excepciones. Esto no significa que 24 px sea un tamaño cómodo para todos los botones: para controles de uso habitual se recomiendan áreas más generosas y una separación adecuada.

Consultar: WCAG 2.2, criterio 2.5.8 y MDN: elemento button.

5. Lleva tus decisiones al proyecto

Copia estas reglas como punto de partida. Después ajusta los estilos según los requisitos y los estados reales de tu aplicación.

:root {
  --btn-primary: #1D4ED8;
  --btn-primary-hover: #1942B8;
  --btn-primary-active: #163BA2;
  --btn-on-primary: #FFFFFF;
  --btn-danger: #B91C1C;
  --btn-radius: 8px;
  --btn-min-height: 46px;
}

.mi-boton {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  gap: .5rem;
  min-height: var(--btn-min-height);
  padding: .6rem 1.1rem;
  border: 1px solid transparent;
  border-radius: var(--btn-radius);
  font: inherit;
  font-weight: 700;
  cursor: pointer;
}
.mi-boton--primario { background: var(--btn-primary); color: var(--btn-on-primary); }
.mi-boton--primario:hover { background: var(--btn-primary-hover); }
.mi-boton--primario:active { background: var(--btn-primary-active); }
.mi-boton--secundario { background: transparent; color: inherit; border-color: currentColor; }
.mi-boton--terciario { background: transparent; color: inherit; }
.mi-boton--destructivo { background: var(--btn-danger); color: white; }
.mi-boton:focus-visible { outline: 3px solid #F59E0B; outline-offset: 3px; }
.mi-boton:disabled { opacity: .56; cursor: not-allowed; }

7️⃣ Aplicación al Proyecto Intermodular​

Antes de maquetar todas las pantallas, cada equipo debería concretar un sistema de botones reutilizable:

  • Primario: qué tipo de acciones representa y qué estilo tendrá.
  • Secundario y terciario: cómo se distinguen de la acción principal.
  • Destructivo: cuándo se utiliza y qué confirmación necesita.
  • Estilos compartidos: altura, radio de borde, separación, texto e iconos.
  • Estados y accesibilidad: hover, foco, pulsación, carga y desactivación.

No se trata de multiplicar variantes. Un sistema pequeño, coherente y comprobable es más fácil de implementar y mantener que botones diseñados de forma independiente para cada pantalla.
