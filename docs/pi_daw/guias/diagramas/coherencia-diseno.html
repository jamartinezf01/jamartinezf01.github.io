Coherencia y revisión del diseño

1️⃣ Cómo se relacionan todos los diagramas​

Los diagramas y modelos que hemos utilizado no deben entenderse como representaciones aisladas.

Todos describen la misma solución desde perspectivas diferentes.

Los requisitos explican qué debe hacer el sistema. Los casos de uso muestran quién utiliza esas funcionalidades. El diseño de interfaz permite imaginar cómo interactuará el usuario con ellas. La arquitectura explica qué partes técnicas intervienen. El modelo de datos representa la información necesaria. Los componentes agrupan las funcionalidades en áreas de responsabilidad. Los diagramas de secuencia muestran cómo colaboran esas partes en procesos concretos. Finalmente, el MVP y la planificación convierten todo ese diseño en trabajo que tendremos que desarrollar.

Podemos resumir ese recorrido así:

requisitos → casos de uso → pantallas → arquitectura → datos → componentes → secuencias → MVP → planificación → tareas

A esta posibilidad de seguir una misma funcionalidad a través de las distintas decisiones del proyecto la llamamos trazabilidad.

La trazabilidad nos ayuda a comprobar que el diseño es coherente y que una misma funcionalidad puede seguirse desde su definición inicial hasta el trabajo de desarrollo.

🟩 Ejemplo con una reserva​

La siguiente ilustración muestra cómo una misma funcionalidad puede recorrerse desde su definición inicial hasta el trabajo de desarrollo:

en este ejemplo

El punto de partida es una necesidad funcional: permitir que un socio reserve un material.

Esa necesidad se convierte en un requisito y aparece después como caso de uso. Para hacerla posible tendremos que diseñar una pantalla, utilizar determinados componentes de la arquitectura, almacenar la información necesaria y organizarla dentro del componente de Reservas y disponibilidad.

Cuando estudiamos cómo funciona internamente podemos representarla mediante un diagrama de secuencia.

Finalmente, la funcionalidad debe formar parte del MVP y convertirse en trabajo planificado en el Gantt y en tareas concretas del tablero.

importante

Si una funcionalidad aparece en los requisitos pero después desaparece del diseño, o si encontramos elementos del diseño que no podemos relacionar con ninguna necesidad del proyecto, debemos revisar la solución.

La documentación debe contar una única historia coherente desde el problema inicial hasta el desarrollo.

2️⃣ Comprobación final​

Antes de cerrar el diseño técnico conviene revisar el conjunto del proyecto, no cada diagrama de forma aislada.

🟩 Funcionalidad​

Comprobación
¿Los actores coinciden con los tipos de usuario definidos?✅
¿Los casos de uso corresponden con requisitos reales?✅
¿Las funcionalidades principales aparecen representadas?✅

🟦 Arquitectura y componentes​

Comprobación
¿La arquitectura contiene solo las partes técnicas que realmente utilizaremos?✅
¿Sabemos qué responsabilidad tiene cada bloque técnico?✅
¿Los componentes funcionales agrupan requisitos relacionados?✅
¿Las dependencias entre componentes tienen sentido?✅

🟧 Datos y procesos​

Comprobación
¿El modelo de datos permite almacenar toda la información necesaria?✅
¿Las relaciones y cardinalidades representan correctamente las reglas del proyecto?✅
¿El modelo relacional es coherente con el modelo conceptual?✅
¿Los diagramas de secuencia representan procesos realmente importantes?✅
¿Las secuencias son coherentes con la arquitectura definida?✅

🟥 MVP y planificación​

Comprobación
¿El MVP contiene las funcionalidades necesarias para demostrar el funcionamiento del proyecto?✅
¿Podemos relacionar el MVP con requisitos y componentes?✅
¿El Gantt contiene el trabajo necesario para alcanzar el MVP?✅
¿Las dependencias y solapamientos de tareas son razonables?✅
¿El tablero permite convertir la planificación en trabajo concreto?✅

🟪 Coherencia global​

Comprobación
¿Podemos seguir una funcionalidad desde el requisito hasta las tareas de desarrollo?✅
¿Los distintos diagramas representan la misma solución sin contradicciones?✅
¿Podemos justificar las principales decisiones tomadas?✅

Si podemos responder afirmativamente a estas preguntas, nuestros diagramas y modelos están cumpliendo su función:

ayudarnos a construir una solución coherente antes de comenzar el desarrollo.
