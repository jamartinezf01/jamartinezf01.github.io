Diseño de datos

El diseño de datos responde a una pregunta fundamental:

¿Qué información necesita nuestra aplicación y cómo se relaciona?

En un proyecto que utiliza una base de datos relacional trabajaremos normalmente con dos representaciones complementarias:

  • Modelo conceptual E/R, para representar la información del problema y las relaciones entre sus elementos.
  • Modelo relacional, para concretar cómo se organizará esa información en tablas.

No son dos formas distintas de dibujar lo mismo.

El modelo E/R se centra en qué información existe y cómo se relaciona.

El modelo relacional se acerca más a la implementación y responde a cómo almacenaremos esa información en una base de datos relacional.

1️⃣ Modelo conceptual E/R​

🟩 Qué representa​

El modelo E/R representa las entidades sobre las que necesitamos almacenar información y las relaciones que existen entre ellas.

Tampoco aquí debemos empezar dibujando.

Primero debemos revisar los requisitos y preguntarnos:

¿Qué información necesita conservar el sistema para poder cumplirlos?

Supongamos que tenemos un requisito relacionado con las reservas:

RF04. El sistema permitirá a un socio solicitar la reserva de un material disponible para unas fechas determinadas.

De este requisito podemos empezar a identificar varios conceptos importantes:

  • Usuario, porque necesitamos saber quién realiza la reserva.
  • Material, porque necesitamos saber qué se reserva.
  • Reserva, porque necesitamos almacenar la propia operación y las fechas asociadas.

Estos conceptos pueden convertirse en entidades porque necesitamos guardar información propia sobre ellos.

Sin embargo, no todos los sustantivos que aparecen en los requisitos deben convertirse automáticamente en una entidad.

Por ejemplo, la disponibilidad de un material no tiene por qué almacenarse como una entidad independiente. Puede obtenerse a partir de las reservas y préstamos existentes.

consejo

Una posible entidad debe representar algo sobre lo que necesitamos guardar información propia durante la vida de la aplicación.

Encontrar un sustantivo en un requisito no es suficiente para convertirlo en entidad.

Una vez identificadas las entidades debemos estudiar cómo se relacionan entre ellas.

En nuestro ejemplo:

Un usuario realiza reservas.
Una reserva corresponde a un material.

Las relaciones deben representar reglas reales del problema, no conexiones arbitrarias entre entidades.

También necesitamos indicar las cardinalidades, es decir, cuántas ocurrencias de una entidad pueden relacionarse con otra.

Por ejemplo:

Un usuario puede realizar muchas reservas, pero cada reserva pertenece a un único usuario.

Por tanto, entre Usuario y Reserva existe una relación 1:N.

Las cardinalidades más habituales son:

  • 1:1, cuando una ocurrencia puede relacionarse como máximo con una del otro lado.
  • 1:N, cuando una ocurrencia puede relacionarse con varias del otro lado.
  • N:M, cuando varias ocurrencias pueden relacionarse con varias del otro lado.

Dependiendo de la notación utilizada también podremos indicar si la participación en una relación es obligatoria u opcional.

Este modelo reducido muestra únicamente las entidades necesarias para representar el flujo principal de una reserva.

Su objetivo es que podamos comprobar si hemos identificado correctamente entidades, relaciones y cardinalidades antes de ampliar el diseño.

🟦 Del modelo básico al modelo completo​

Cuando seguimos analizando los requisitos aparecen nuevas necesidades.

Por ejemplo, necesitamos una Categoría porque queremos clasificar los materiales.

También necesitamos un Préstamo, porque una reserva y una entrega real no representan la misma situación.

Reservar un material significa solicitarlo para unas fechas determinadas. El préstamo aparece cuando ese material se entrega realmente al usuario y permite registrar posteriormente su devolución.

Del mismo modo, necesitamos una Incidencia para almacenar problemas detectados durante el uso o la devolución del material.

El modelo crece porque el problema necesita representar nueva información, no porque queramos añadir más entidades.

en este ejemplo

Podemos comenzar siguiendo el proceso principal de Materialia Joven.

Un Usuario puede realizar varias Reservas, mientras que cada reserva pertenece a un único usuario. Cada reserva corresponde además a un Material.

La Categoría permite clasificar los materiales. Una categoría puede agrupar varios materiales, mientras que cada material pertenece a una categoría.

Cuando una reserva se convierte en una entrega real aparece el Préstamo, que permite registrar la entrega y posterior devolución del material.

Por último, una Incidencia permite registrar problemas relacionados con el uso o devolución de un material.

La separación entre Reserva y Préstamo es una decisión importante del modelo: reservar un material no significa que haya sido entregado.

Al revisar el modelo completo debemos comprobar que cada entidad tiene una finalidad clara, que las relaciones representan reglas reales del problema y que sus cardinalidades son coherentes.

2️⃣ Modelo relacional inicial​

🟩 Del modelo conceptual a las tablas​

El modelo relacional concreta cómo organizaremos la información en una base de datos relacional.

En este momento empezamos a transformar las decisiones del modelo E/R en tablas, claves y restricciones.

La transformación más sencilla puede entenderse mediante algunas reglas básicas:

  • Una entidad normalmente da lugar a una tabla.
  • El identificador de la entidad se convierte en su clave primaria (PK).
  • En una relación 1:N, la clave primaria del lado 1 aparece como clave ajena (FK) en la tabla del lado N.
  • Un dato que no puede repetirse puede incorporar una restricción UQ.
  • Cuando un dato puede no existir tendremos que decidir si el campo admite valores nulos.

No pretendemos todavía escribir el script SQL completo de creación de la base de datos.

Estamos definiendo suficientemente su estructura para poder comenzar posteriormente la implementación.

Cada entidad principal del modelo conceptual se ha convertido en una tabla con su correspondiente clave primaria.

Las relaciones se concretan mediante claves ajenas. Por ejemplo, usuario_id y material_id permiten relacionar cada reserva con el usuario que la realiza y con el material reservado.

También aparecen restricciones como UQ cuando un valor debe ser único y se indica qué campos pueden admitir valores nulos.

El resultado conserva las decisiones tomadas en el modelo E/R, pero las expresa de una forma mucho más cercana a la base de datos que posteriormente implementaremos.

Hay además decisiones que no consisten simplemente en transformar entidades en tablas.

Una decisión de diseño

En Materialia Joven el estado visible de un material —por ejemplo, Disponible, Reservado o Prestado— no se almacena directamente como un dato independiente.

Ese estado puede calcularse a partir de las reservas y préstamos existentes.

Al no almacenarlo evitamos que pueda quedar desincronizado con la situación real del material.

Diseñar los datos también consiste en decidir qué información debemos almacenar y qué información podemos calcular.

3️⃣ Errores frecuentes y qué esperamos​

Uno de los errores más habituales consiste en convertir cada concepto mencionado en los requisitos en una entidad o una tabla.

También debemos evitar duplicar información que puede obtenerse a partir de otros datos o crear relaciones sin haber comprobado antes qué regla del problema representan.

En el modelo relacional, otro error frecuente es añadir claves ajenas, restricciones o campos sin poder relacionarlos con las decisiones tomadas en el modelo conceptual.

Los dos modelos deben ser coherentes entre sí.

En vuestro proyecto

En los proyectos que utilicen una base de datos relacional, deberéis incluir:

  • un modelo conceptual E/R, o representación conceptual equivalente, con las entidades y relaciones principales.
  • cardinalidades coherentes con las reglas del proyecto.
  • un modelo relacional inicial con tablas, claves primarias y claves ajenas.
  • las restricciones principales cuando sean relevantes para el diseño.
  • coherencia entre el modelo conceptual y el modelo relacional.

No buscamos todavía el script SQL definitivo.

Buscamos un diseño suficientemente claro para comprender qué información necesita vuestra aplicación y cómo se almacenará antes de comenzar a implementarla.
