Diagrama de arquitectura

1️⃣ Qué representa​

El diagrama de arquitectura muestra las grandes partes técnicas de la solución y cómo se comunican entre ellas.

En la guía de casos de uso observábamos el sistema desde el punto de vista de sus usuarios:

¿Quién utiliza la aplicación y qué puede hacer?

Ahora cambiamos de perspectiva y nos preguntamos:

¿Cómo estará construida técnicamente nuestra aplicación?

Para responder no empezamos pensando en clases, controladores o tablas concretas. Primero necesitamos identificar los grandes bloques que forman la solución.

En una aplicación web como Materialia Joven podemos comenzar con tres grandes partes:

  • Frontend, encargado de la interfaz con la que interactúa el usuario.
  • Backend, encargado de recibir las peticiones, aplicar las reglas de negocio y coordinar el acceso a los datos.
  • Base de datos, encargada de almacenar de forma persistente la información de la aplicación.

En Materialia Joven estas responsabilidades se concretan inicialmente en:

Angular → Spring Boot → MySQL

consejo

Una arquitectura no consiste únicamente en escribir el nombre de las tecnologías.

Debemos ser capaces de explicar qué responsabilidad tiene cada parte y por qué necesitamos que exista.

2️⃣ Cómo construirla​

Tampoco en este caso debemos empezar dibujando.

La arquitectura se construye a partir de las decisiones que ya hemos tomado sobre la solución.

En la Fase 1 hemos definido qué problema queremos resolver y qué funcionalidades tendrá la aplicación. En la Fase 2 comenzamos además a decidir con qué tecnologías vamos a desarrollarla.

A partir de ahí podemos plantearnos tres preguntas:

¿Dónde interactúa el usuario con la aplicación?

En Materialia Joven, mediante una aplicación web desarrollada con Angular.

¿Dónde se ejecutan las reglas del sistema?

En un servidor desarrollado con Spring Boot.

¿Dónde se almacena la información?

En una base de datos MySQL.

Con estas decisiones ya podemos construir una primera arquitectura:

Este primer diagrama todavía no intenta mostrar cómo está organizada internamente cada tecnología.

Su función es permitirnos comprender el recorrido general de la información.

Cuando un usuario realiza una acción en Angular, el frontend envía una petición al backend. Spring Boot procesa esa petición y, cuando necesita consultar o modificar información, accede a MySQL. Finalmente, el resultado vuelve hacia el cliente.

Podemos resumir ese recorrido así:

navegador → Angular → Spring Boot → MySQL → Spring Boot → Angular → usuario

Esta representación ya nos permite comprobar una primera decisión importante: cada responsabilidad está situada en la parte adecuada del sistema.

3️⃣ De la arquitectura básica al diseño técnico​

Cuando tenemos clara la estructura general podemos añadir un segundo nivel de detalle.

No buscamos representar todas las clases que tendrá el proyecto. Queremos mostrar cómo se organiza internamente cada gran bloque cuando esa organización forma parte de las decisiones técnicas del equipo.

En el cliente Angular podemos distinguir:

  • Componentes y rutas, para organizar las pantallas y la navegación.
  • Servicios HTTP, para comunicarse con el backend.
  • Guardas de ruta, para controlar el acceso a determinadas zonas de la aplicación.
  • Interceptor, para aplicar comportamiento común a las peticiones, como incorporar el token de autenticación.
  • Estilos comunes, para mantener una presentación coherente en toda la aplicación.

En el servidor Spring Boot podemos distinguir:

  • Controladores REST, que reciben las peticiones procedentes del cliente.
  • Servicios, donde se aplican las reglas de negocio.
  • Repositorios, encargados del acceso a los datos.
  • Spring Security y JWT, para gestionar autenticación y autorización.
  • Gestión de errores, para devolver respuestas coherentes cuando una operación no puede completarse.

La base de datos continúa teniendo una función clara: almacenar de forma persistente la información de la aplicación.

También podemos indicar cómo se comunican estas partes cuando esa información ayuda a comprender la solución. En Materialia Joven, por ejemplo, Angular se comunica con Spring Boot mediante peticiones HTTP utilizando JSON, mientras que Spring Boot accede a MySQL mediante JPA.

Esta evolución nos lleva desde una arquitectura muy sencilla:

Angular → Spring Boot → MySQL

hasta una representación que explica también cómo se organiza internamente cada una de esas partes.

aviso

Añadir más bloques no significa mejorar la arquitectura.

Solo debemos representar aquellos elementos que ayuden a entender cómo se construirá realmente nuestra aplicación.

El diseño completo de Materialia Joven queda representado así:

en este ejemplo

Podemos leer la arquitectura de izquierda a derecha siguiendo el recorrido de una petición.

El usuario interactúa con la aplicación desde Angular. Cuando necesita información del servidor, el cliente envía una petición HTTP/HTTPS en formato JSON al backend desarrollado con Spring Boot.

La petición llega a los controladores REST, que delegan la operación en los servicios. Estos aplican las reglas de negocio y, cuando necesitan consultar o modificar datos, utilizan los repositorios de Spring Data JPA para acceder a MySQL.

La seguridad y la gestión de errores aparecen como responsabilidades transversales porque afectan a distintas partes del backend.

En la zona inferior se muestran herramientas de apoyo al desarrollo, como Git, GitHub, Docker Compose y Flyway. Son importantes para construir y mantener el proyecto, pero no forman parte del recorrido principal de una petición.

La arquitectura debe ser coherente con el resto del diseño.

Si hemos decidido que la aplicación tendrá un frontend Angular y una API REST desarrollada con Spring Boot, esa decisión deberá aparecer después en los componentes, en los diagramas de secuencia y finalmente en el código.

Del mismo modo, no tendría sentido representar una tecnología, una capa o un servicio que después no vayamos a utilizar.

La arquitectura debe describir la solución que realmente pretendemos construir.

4️⃣ Errores frecuentes y qué esperamos​

Uno de los errores más habituales es confundir una arquitectura con una lista de tecnologías.

Escribir simplemente:

Angular · Spring Boot · MySQL

no explica cómo está organizada la solución ni cómo se relacionan sus partes.

El error contrario consiste en añadir demasiada información. No necesitamos representar todas las clases, paquetes, endpoints o tablas del proyecto. Ese nivel de detalle corresponde a otras representaciones o directamente al código.

También debemos evitar incorporar tecnologías únicamente porque “parecen profesionales”. Añadir microservicios, colas, cachés o varios servidores sin una necesidad real hace el diseño más difícil de desarrollar y de justificar.

En vuestro proyecto

La arquitectura deberá permitir comprender con claridad:

  • cuáles son las grandes partes técnicas de la aplicación.
  • qué responsabilidad tiene cada una.
  • cómo se comunican.
  • qué tecnologías principales se utilizarán.
  • qué decisiones técnicas relevantes afectan al conjunto de la solución.

No buscamos una arquitectura compleja.

Buscamos una representación suficientemente clara para entender cómo estará construida vuestra aplicación antes de empezar a desarrollarla.
