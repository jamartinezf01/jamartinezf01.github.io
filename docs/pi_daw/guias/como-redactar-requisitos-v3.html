Cómo redactar requisitos

Cuando empezamos un proyecto, es fácil escribir frases como estas:

  • “La aplicación será intuitiva”.
  • “Habrá un sistema de reservas”.
  • “El usuario podrá hacer muchas cosas”.
  • “La aplicación será rápida y segura”.

El problema es que estas frases todavía no nos dicen con suficiente precisión qué debe hacer o cumplir la solución.

En esta guía vamos a aprender a pasar de una necesidad inicial a unos requisitos claros, concretos y comprobables.

tip

Un requisito bien redactado nos ayuda a entender qué debemos construir y, más adelante, a comprobar si realmente lo hemos conseguido.

1️⃣ De la necesidad al requisito​

Antes de escribir requisitos debemos tener claro qué problema queremos resolver y qué queremos conseguir.

El recorrido habitual es:

Necesidad → Objetivo → Funcionalidades → Requisitos

No estamos hablando de lo mismo en cada paso:

ConceptoQué describeEjemplo
NecesidadEl problema o situación que queremos mejorarNo sabemos con claridad qué material está disponible ni quién lo tiene.
ObjetivoQué queremos conseguir con el proyectoMejorar el control del material compartido y facilitar su préstamo.
FuncionalidadUna capacidad que ofrecerá la aplicaciónConsultar materiales, reservarlos o registrar devoluciones.
RequisitoQué debe hacer o cumplir exactamente la soluciónRF01. El sistema permitirá consultar el catálogo de materiales disponibles.

🟩 Un ejemplo completo​

Supongamos que una asociación gestiona el préstamo de material mediante mensajes y una hoja de cálculo.

Necesidad

La asociación no sabe con claridad qué material está disponible ni quién lo tiene en cada momento.

Objetivo

Mejorar el control del material compartido y facilitar su préstamo.

Funcionalidades posibles

  • Consultar materiales.
  • Reservar materiales.
  • Registrar entregas y devoluciones.
  • Consultar préstamos activos.

A partir de esas funcionalidades podemos concretar requisitos:

  • RF01. El sistema permitirá consultar el catálogo de materiales activos.
  • RF02. El sistema mostrará el estado de disponibilidad de cada material.
  • RF03. El responsable podrá registrar la entrega de un material reservado.
  • RF04. El responsable podrá registrar la devolución de un material prestado.
aviso

No debemos empezar a redactar requisitos si todavía no tenemos clara la necesidad.

Si no sabemos qué problema estamos resolviendo, es fácil acabar definiendo requisitos innecesarios, repetidos o incoherentes.

2️⃣ Requisitos funcionales y no funcionales​

Un requisito expresa algo que la solución debe hacer o una condición que debe cumplir.

Para nuestro proyecto distinguiremos dos grandes grupos:

  • requisitos funcionales (RF).
  • requisitos no funcionales (RNF).

🟩 Requisitos funcionales​

Los requisitos funcionales describen capacidades o comportamientos del sistema.

Pueden indicar:

  • acciones que realiza un usuario.
  • consultas o modificaciones de datos.
  • respuestas automáticas del sistema.
  • reglas de funcionamiento.
  • comportamientos ante determinadas situaciones.

Una estructura habitual es:

[Actor o sistema] + acción + objeto o condición

Por ejemplo:

RF01. El socio podrá consultar el catálogo de materiales activos.

RF02. El sistema permitirá reservar un material cuando esté disponible.

RF03. El responsable podrá registrar la devolución de un préstamo.

RF04. El sistema impedirá confirmar una reserva si el material ya está reservado para el mismo periodo.

En todos estos casos estamos indicando algo que el sistema debe hacer.

🟦 Requisitos no funcionales​

Los requisitos no funcionales describen condiciones de calidad, restricciones o características generales de la solución.

Suelen estar relacionados con aspectos como:

  • seguridad.
  • accesibilidad.
  • compatibilidad.
  • diseño adaptable.
  • privacidad.
  • usabilidad.
  • rendimiento.
  • disponibilidad.

Por ejemplo:

RNF01. Las funciones de administración solo estarán disponibles para usuarios autorizados.

RNF02. Los formularios deberán disponer de etiquetas asociadas a sus campos.

RNF03. Las pantallas principales deberán poder utilizarse desde ordenador y dispositivo móvil.

RNF04. Solo se almacenarán los datos personales necesarios para gestionar usuarios, reservas y préstamos.

La diferencia principal puede resumirse así:

Requisito funcionalRequisito no funcional
DescribeUna capacidad o comportamientoUna condición de calidad o restricción
Pregunta habitual¿Qué debe hacer el sistema?¿Qué condición debe cumplir?
EjemploEl usuario podrá cancelar una reserva futura.Solo los usuarios autorizados podrán acceder a la administración.
Cómo se compruebaMediante una operación o caso de pruebaMediante pruebas, medidas, inspecciones o revisiones
Ejemplo

Si escribimos:

RF05. El sistema permitirá cancelar una reserva antes de que comience el préstamo.

podremos comprobarlo creando una reserva futura, intentando cancelarla y verificando que queda cancelada.

Si no podemos imaginar cómo comprobar un requisito, probablemente todavía necesite una redacción más precisa.

3️⃣ Casos que pueden generar dudas​

No todos los requisitos encajan de forma evidente en una categoría. En estos casos nos interesa mantener un criterio coherente dentro del proyecto.

🟩 Permisos y roles​

RF10. El administrador podrá desactivar cuentas de usuario.

Lo consideramos funcional porque describe una acción disponible para un tipo de usuario.

En cambio:

RNF05. Las funciones administrativas solo estarán disponibles para usuarios autorizados.

Lo tratamos como no funcional porque establece una condición general de seguridad.

🟦 Validaciones​

RF11. El sistema impedirá realizar una reserva si la fecha de devolución es anterior a la fecha de inicio.

Es una regla de funcionamiento de una operación, por lo que podemos tratarla como requisito funcional.

En cambio:

RNF06. Todos los formularios validarán los campos obligatorios antes de procesar la información.

Es una condición general aplicable a la solución.

🟨 Reglas de negocio​

Las reglas de negocio suelen considerarse funcionales cuando determinan qué debe hacer el sistema ante una situación concreta.

RF12. Un usuario no podrá mantener más de tres préstamos activos simultáneamente.

Aunque contiene una restricción, está definiendo la lógica de una operación.

important

Cuando tengamos dudas, podemos hacernos tres preguntas:

  1. ¿Describe una operación, una acción de usuario o una respuesta concreta del sistema? → Probablemente es funcional.
  2. ¿Describe seguridad, rendimiento, accesibilidad, compatibilidad, privacidad, usabilidad u otra condición general? → Probablemente es no funcional.
  3. ¿Podemos comprobar objetivamente si se cumple? → Si no podemos, debemos mejorar su redacción.

4️⃣ Cómo redactamos un buen requisito​

Un buen requisito debe ser claro, concreto, comprobable, coherente con el proyecto y viable.

🟩 Claro y concreto​

Debe expresar una idea precisa y evitar formulaciones ambiguas.

Demasiado vagoMejor
El sistema tendrá cierta capacidad de gestión.El sistema permitirá registrar la devolución de un material prestado.
La aplicación gestionará usuarios.El administrador podrá crear, modificar y desactivar cuentas de usuario.
Habrá reservas.Una persona registrada podrá reservar un material disponible.

🟦 Comprobable​

Debemos poder decidir si el requisito se cumple o no.

Demasiado vago:

La aplicación será segura.

Más concreto:

RNF01. Las funciones de administración solo estarán disponibles para usuarios autorizados.

Demasiado vago:

La aplicación funcionará bien en móviles.

Más concreto:

RNF02. Las pantallas de catálogo, reserva y consulta de préstamos deberán poder utilizarse desde una anchura de pantalla móvil sin perder funcionalidades.

🟨 Coherente con el proyecto​

Un requisito debe responder a una necesidad u objetivo del proyecto.

Por ejemplo, si nuestro sistema no incluye pagos ni ventas, un requisito como este no tendría sentido:

El sistema generará facturas en PDF.

🟧 Viable​

También debemos tener en cuenta el tiempo, los recursos y el alcance del proyecto.

Un requisito técnicamente posible puede no ser razonable para nuestro proyecto si exige un desarrollo desproporcionado respecto a lo que queremos resolver.

tip

Antes de aceptar un requisito podemos preguntarnos:

¿Sabemos qué significa, por qué está en el proyecto y cómo comprobaremos que se cumple?

5️⃣ Errores frecuentes y cómo corregirlos​

Muchos problemas de redacción aparecen siempre de formas parecidas.

🟥 Confundir un objetivo con un requisito​

Objetivo:

Mejorar la gestión del material compartido.

Requisito:

RF03. El sistema permitirá registrar la entrega de un material reservado.

El objetivo expresa qué queremos conseguir. El requisito concreta qué debe hacer la solución para contribuir a ese objetivo.

🟨 Utilizar palabras vagas​

Expresiones como bonito, intuitivo, moderno, rápido, fácil, completo, eficiente o adecuado no bastan por sí solas como requisito.

Por ejemplo:

EvitamosLo concretamos
La aplicación será intuitiva.Los formularios mostrarán mensajes de error cuando contengan datos incorrectos.
La aplicación será segura.Las funciones administrativas solo estarán disponibles para usuarios autorizados.
La aplicación será fácil de usar.La aplicación mostrará mensajes de confirmación o error después de las operaciones principales.

🟧 Mezclar demasiadas cosas en un mismo requisito​

Mal:

RF10. El sistema permitirá consultar materiales, reservarlos, cancelarlos, pedir prórrogas, escribir mensajes, subir imágenes y generar informes.

Es mejor dividirlo en varios requisitos simples. Así podremos desarrollarlos, modificarlos y comprobarlos de forma independiente.

🟦 Confundir funcionalidad con interfaz​

Mal:

Habrá una pantalla bonita para usuarios.

Mejor:

RF06. El usuario podrá consultar sus préstamos activos.

La pantalla puede ser la forma de implementar la funcionalidad, pero el requisito debe centrarse en qué debe poder hacer el sistema.

🟪 Redactar requisitos que no responden a ninguna necesidad​

Si no sabemos por qué un requisito está incluido, debemos revisar si realmente forma parte del alcance del proyecto.

6️⃣ Cómo documentamos los requisitos​

Para poder referirnos a ellos con claridad utilizaremos una numeración sencilla:

  • RF01, RF02, RF03... para requisitos funcionales.
  • RNF01, RNF02, RNF03... para requisitos no funcionales.

La numeración nos permitirá relacionar después los requisitos con tareas, pruebas, incidencias o entregas.

🟩 Requisitos funcionales​

Podemos documentarlos con una tabla como esta:

CódigoRequisito funcionalUsuario principalPrioridad

RF02El usuario podrá......Alta
RF03El responsable podrá......Media

tip

La columna “Cómo podremos comprobarlo” nos obliga a revisar si el requisito está suficientemente concretado y nos prepara para la fase de pruebas.

7️⃣ Ejercicio guiado y lista de comprobación​

Vamos a aplicar el recorrido completo a una situación distinta.

🟩 Situación inicial​

En un club deportivo, las inscripciones a actividades se realizan por WhatsApp. Esto provoca errores, olvidos y dificultad para saber cuántas plazas quedan libres.

Objetivo

Mejorar la gestión de inscripciones y facilitar el control de plazas disponibles.

Funcionalidades posibles

  • Consultar actividades.
  • Ver plazas disponibles.
  • Inscribirse en una actividad.
  • Cancelar una inscripción.
  • Consultar participantes.

Requisitos funcionales posibles

  • RF01. El sistema mostrará la lista de actividades disponibles.
  • RF02. El sistema mostrará el número de plazas libres de cada actividad.
  • RF03. Una persona registrada podrá inscribirse en una actividad con plazas disponibles.
  • RF04. El sistema impedirá inscripciones cuando no queden plazas libres.
  • RF05. El responsable podrá consultar el listado de personas inscritas en cada actividad.

Requisitos no funcionales posibles

  • RNF01. La aplicación deberá poder utilizarse desde dispositivo móvil.
  • RNF02. Los formularios validarán los campos obligatorios antes del envío.
  • RNF03. Solo el personal autorizado podrá consultar el listado completo de participantes.

🟦 Lista de comprobación​

Antes de dar por cerrados nuestros requisitos comprobaremos que:

  • responden a una necesidad real del proyecto.
  • distinguen correctamente entre objetivo, funcionalidad y requisito.
  • están redactados de forma clara y concreta.
  • describen una única idea principal.
  • podemos comprobar si se cumplen.
  • mantienen un criterio coherente entre RF y RNF.
  • utilizan una numeración consistente.
  • son viables dentro del alcance del proyecto.
important

La pregunta final es sencilla:

¿Podríamos comprobar más adelante si este requisito se ha cumplido o no?

Si no sabemos cómo hacerlo, todavía debemos concretarlo mejor.
