Cómo redactar requisitos

Cuando empezamos un proyecto, es muy fácil decir cosas como:

  • “La aplicación tendrá que estar bien”.
  • “Queremos que sea intuitiva”.
  • “Habrá un sistema de reservas”.
  • “El usuario podrá hacer muchas cosas”.

El problema es que frases como estas no sirven todavía como requisitos.

En esta guía vamos a aprender a distinguir entre necesidad, objetivo, funcionalidad y requisito, y a redactar requisitos de forma clara, concreta y comprobable.

tip

Un requisito bien redactado nos ayuda a:

  • entender mejor qué debe hacer la aplicación.
  • organizarnos mejor durante el desarrollo.
  • comprobar después si el proyecto cumple lo que prometía.
  • evitar malentendidos dentro del equipo.

1️⃣ Antes de redactar requisitos: qué estamos describiendo​

Uno de los errores más habituales es mezclar conceptos.

No es lo mismo hablar de:

  • una necesidad.
  • un objetivo.
  • una funcionalidad.
  • un requisito.

🟩 Necesidad​

La necesidad describe el problema o situación que queremos mejorar.

Ejemplo:

Actualmente las reservas de material de una asociación juvenil se gestionan por mensajes y una hoja de cálculo. Esto provoca errores, retrasos y dificultad para saber qué material está disponible.

🟦 Objetivo​

El objetivo explica qué queremos conseguir al desarrollar el proyecto.

Ejemplo:

Mejorar la gestión del préstamo de material y facilitar que los socios conozcan la disponibilidad de los recursos compartidos.

🟨 Funcionalidad​

La funcionalidad expresa una capacidad o acción que ofrecerá la aplicación.

Ejemplo:

Consultar el catálogo de materiales.

Realizar una reserva.

Registrar una devolución.

🟧 Requisito​

El requisito concreta qué debe hacer la aplicación o qué condiciones debe cumplir, de forma que después podamos comprobarlo.

Ejemplo:

RF01. El sistema permitirá a una persona registrada consultar el catálogo de materiales disponibles.

RF02. El sistema permitirá reservar un material disponible indicando fecha de inicio y fecha prevista de devolución.

2️⃣ De la necesidad al requisito​

El proceso lógico suele ser este:

Necesidad → Objetivo → Funcionalidades → Requisitos

🟩 Ejemplo completo​

Necesidad​

La asociación no sabe con claridad qué material está disponible ni quién lo tiene en cada momento.

Objetivo​

Mejorar el control del material compartido y facilitar su préstamo.

Funcionalidades posibles​

  • Consultar materiales.
  • Reservar materiales.
  • Registrar entregas.
  • Registrar devoluciones.
  • Consultar préstamos activos.

Requisitos​

  • RF01. El sistema permitirá consultar el catálogo de materiales activos.
  • RF02. El sistema mostrará el estado de disponibilidad de cada material.
  • RF03. El responsable podrá registrar la entrega de un material reservado.
  • RF04. El responsable podrá registrar la devolución de un material prestado.
aviso

No debemos empezar por los requisitos si todavía no tenemos clara la necesidad.

Si no sabemos bien qué problema estamos resolviendo, es muy fácil redactar requisitos inútiles, repetidos o incoherentes.

3️⃣ Qué es exactamente un requisito​

Un requisito es una afirmación que expresa algo que la solución debe hacer o una condición que debe cumplir.

Los requisitos sirven como un acuerdo sobre lo que esperamos del sistema. Más adelante podremos utilizarlos para diseñar la aplicación, organizar el desarrollo y comprobar si el proyecto cumple lo que habíamos definido.

En esta guía distinguiremos dos grandes grupos:

  • requisitos funcionales (RF);
  • requisitos no funcionales (RNF).

La diferencia no consiste simplemente en que unos sean “funciones” y otros “cosas técnicas”. La clave está en qué aspecto del sistema describe cada uno.

🟩 Requisitos funcionales: describen capacidades o comportamientos​

Un requisito funcional indica qué debe poder hacer el sistema.

Normalmente describe:

  • una acción que puede realizar un usuario.
  • una respuesta del sistema.
  • una operación sobre los datos.
  • una regla de funcionamiento.
  • o un comportamiento que debe producirse ante una situación determinada.

Por ejemplo:

RF01. El sistema permitirá a una persona registrada reservar un material disponible.

Aquí estamos indicando una capacidad que la aplicación debe ofrecer.

🟦 Requisitos no funcionales: describen condiciones de calidad o restricciones​

Un requisito no funcional indica qué condiciones debe cumplir el sistema mientras ofrece sus funcionalidades.

Suelen afectar a aspectos como:

  • seguridad.
  • rendimiento.
  • accesibilidad.
  • usabilidad.
  • compatibilidad.
  • privacidad.
  • disponibilidad.
  • mantenibilidad.

Por ejemplo:

RNF01. La aplicación deberá poder utilizarse correctamente desde ordenador y dispositivo móvil.

La aplicación podría permitir realizar reservas aunque no cumpliera este requisito. Lo que estamos definiendo es una condición de calidad de la solución.

🟨 Una primera regla para distinguirlos​

Podemos hacernos estas dos preguntas:

¿Este requisito describe una acción o comportamiento que la aplicación debe ofrecer?
→ Probablemente es un requisito funcional.

¿Describe una condición de calidad, una restricción o una característica que debe cumplir la solución?
→ Probablemente es un requisito no funcional.

Pero esta regla no siempre es suficiente. Más adelante veremos algunos casos que pueden generar dudas.

4️⃣ Requisitos funcionales​

🟩 Qué describen​

Los requisitos funcionales expresan las capacidades del sistema.

Nos indican qué operaciones existirán y qué comportamiento esperamos de la aplicación.

Suelen responder a preguntas como:

  • ¿Qué podrá hacer cada tipo de usuario?
  • ¿Qué información podrá consultar?
  • ¿Qué datos podrá crear, modificar o eliminar?
  • ¿Qué debe hacer el sistema cuando ocurre algo?
  • ¿Qué reglas debe aplicar en una operación?

🟦 Estructura habitual​

Muchos requisitos funcionales pueden redactarse siguiendo una estructura parecida:

[Actor o sistema] + acción + objeto o condición

Por ejemplo:

RF01. El socio podrá consultar el catálogo de materiales activos.

RF02. El sistema permitirá reservar un material cuando esté disponible.

RF03. El responsable podrá registrar la devolución de un préstamo.

RF04. El sistema impedirá confirmar una reserva si el material ya está reservado para el mismo periodo.

En todos estos casos estamos describiendo algo que el sistema debe hacer.

🟩 Qué puede aparecer en un requisito funcional​

Acciones de usuario​

RF05. El usuario podrá cancelar una reserva futura.

Consultas​

RF06. El responsable podrá consultar los préstamos que hayan superado la fecha prevista de devolución.

Modificaciones de datos​

RF07. El administrador podrá desactivar una cuenta de usuario.

Respuestas automáticas del sistema​

RF08. El sistema actualizará el estado del material a “prestado” cuando se registre su entrega.

Reglas de negocio​

RF09. El sistema impedirá reservar un material durante un periodo en el que ya exista otra reserva confirmada.

Las reglas de negocio son importantes porque también describen cómo debe funcionar la lógica de la aplicación.

🟥 Qué NO es un buen requisito funcional​

RF01. La aplicación será muy útil.

No describe ninguna función.

RF02. Habrá un buen sistema de gestión.

No sabemos qué operaciones debe ofrecer.

RF03. El usuario podrá hacer todo lo necesario.

No es concreto ni comprobable.

RF04. La pantalla de reservas será bonita y moderna.

Esto no describe una funcionalidad.

🟨 Un requisito funcional debe poder probarse​

Si escribimos:

RF10. El sistema permitirá cancelar una reserva antes de que comience el préstamo.

Más adelante podremos crear una prueba:

  1. Creamos una reserva futura.
  2. Intentamos cancelarla.
  3. Comprobamos que la reserva queda cancelada.

Si no podemos imaginar cómo comprobar un requisito, probablemente necesite una redacción más precisa.

5️⃣ Requisitos no funcionales​

🟩 Qué describen​

Los requisitos no funcionales expresan condiciones de calidad, restricciones o características generales de la solución.

No suelen añadir una nueva función al sistema. Indican qué nivel o condición debe cumplir la aplicación mientras realiza sus funciones.

Por ejemplo:

La aplicación puede tener una funcionalidad de inicio de sesión.

Eso sería un requisito funcional:

RF01. El sistema permitirá iniciar sesión mediante una cuenta registrada.

Pero además podemos establecer condiciones relacionadas con esa funcionalidad:

RNF01. Las contraseñas no se almacenarán en texto plano.

RNF02. El acceso a funciones administrativas estará restringido a usuarios autorizados.

Estas condiciones están relacionadas con la seguridad.

🟦 Categorías habituales​

Seguridad​

RNF01. Las funciones de administración solo estarán disponibles para usuarios con permisos autorizados.

Accesibilidad​

RNF02. Los formularios deberán disponer de etiquetas asociadas a sus campos.

Compatibilidad​

RNF03. La aplicación deberá comprobarse en versiones actuales de Chrome, Firefox y Edge.

Diseño adaptable​

RNF04. Las pantallas principales deberán ser utilizables desde ordenador y dispositivo móvil.

Privacidad​

RNF05. Solo se almacenarán los datos personales necesarios para gestionar usuarios, reservas y préstamos.

Usabilidad​

RNF06. La aplicación mostrará mensajes claros de confirmación o error después de las operaciones principales.

Rendimiento​

RNF07. Las consultas habituales del catálogo deberán responder sin esperas perceptibles con el conjunto de datos previsto para el proyecto.

🟥 Qué NO es un buen requisito no funcional​

RNF01. La aplicación será segura.

¿En qué sentido?

RNF02. La aplicación será rápida.

¿En qué operaciones y en qué condiciones?

RNF03. La interfaz será intuitiva.

¿Cómo sabremos si se cumple?

RNF04. La aplicación tendrá buena accesibilidad.

Necesitamos concretar qué condiciones de accesibilidad esperamos.

🟨 De una idea vaga a un requisito comprobable​

Demasiado vago:

La aplicación será segura.

Más concreto:

Las funciones administrativas solo podrán utilizarse después de iniciar sesión con un usuario autorizado.

Demasiado vago:

La aplicación funcionará bien en móviles.

Más concreto:

Las pantallas de catálogo, reserva y consulta de préstamos deberán poder utilizarse desde una anchura de pantalla móvil sin perder funcionalidades.

Demasiado vago:

Los formularios serán fáciles de usar.

Más concreto:

Los campos obligatorios estarán identificados y el sistema mostrará un mensaje cuando un formulario contenga datos incorrectos.

6️⃣ Funcional o no funcional: cómo decidir​

La siguiente comparación puede ayudarnos.

PreguntaRequisito funcionalRequisito no funcional
¿Qué describe?Una capacidad o comportamiento del sistemaUna condición de calidad o restricción
¿Añade una acción o comportamiento?Normalmente síNormalmente no
¿Quién aparece con frecuencia?Usuario, administrador, responsable o el propio sistemaEl sistema o la aplicación en general
¿Qué verbos aparecen habitualmente?consultar, registrar, reservar, cancelar, mostrar, calcular, impedirgarantizar, restringir, soportar, responder, proteger, ser compatible
¿Cómo se verifica?Mediante una operación o caso de pruebaMediante pruebas, medidas, inspecciones o revisiones
EjemploEl usuario podrá reservar una actividadLa aplicación será utilizable desde móvil

🟩 El mismo caso visto desde los dos tipos​

Imaginemos una funcionalidad de reservas.

Requisitos funcionales:

RF01. El usuario podrá reservar una actividad con plazas disponibles.

RF02. El usuario podrá cancelar una reserva futura.

RF03. El sistema impedirá una reserva cuando no queden plazas.

Estos requisitos indican qué hace el sistema.

Requisitos no funcionales relacionados:

RNF01. El formulario de reserva podrá utilizarse desde dispositivo móvil.

RNF02. Solo los usuarios autenticados podrán realizar reservas.

RNF03. El sistema mostrará un mensaje comprensible cuando una reserva no pueda completarse.

Estos requisitos indican condiciones que debe cumplir la solución.

7️⃣ Casos que pueden generar dudas​

Hay requisitos que no siempre encajan de forma evidente en una categoría.

Lo importante es mantener un criterio coherente dentro del proyecto.

🟨 Permisos y roles​

Podemos escribir:

RF10. El administrador podrá desactivar cuentas de usuario.

Es funcional porque describe una acción disponible para un tipo de usuario.

En cambio:

RNF05. Las funciones administrativas solo estarán disponibles para usuarios autorizados.

Lo tratamos como no funcional porque establece una condición general de seguridad.

🟧 Validaciones​

RF11. El sistema impedirá realizar una reserva si la fecha de devolución es anterior a la fecha de inicio.

Esto es una regla de negocio, por lo que podemos tratarla como requisito funcional.

En cambio:

RNF06. Todos los formularios validarán los campos obligatorios antes de procesar la información.

Es una condición general aplicable a la solución y podemos tratarla como requisito no funcional.

🟦 Reglas de negocio​

Las reglas de negocio suelen considerarse funcionales cuando determinan qué debe hacer el sistema ante una situación concreta.

Por ejemplo:

RF12. Un usuario no podrá mantener más de tres préstamos activos simultáneamente.

Aunque contiene una restricción, está definiendo la lógica funcional de una operación.

important

No necesitamos discutir durante horas si un requisito concreto podría clasificarse de otra manera en otra metodología.

Para nuestro proyecto lo importante será:

  1. utilizar un criterio coherente.
  2. redactarlo con claridad.
  3. poder comprobarlo después.

8️⃣ Una prueba rápida para clasificarlos​

Cuando tengamos dudas podemos seguir este razonamiento:

Paso 1​

Preguntamos:

¿Describe una operación, una acción de usuario o una respuesta concreta del sistema?

Si la respuesta es sí, probablemente sea funcional.

Paso 2​

Si no, preguntamos:

¿Describe seguridad, rendimiento, accesibilidad, compatibilidad, privacidad, usabilidad u otra condición general?

Si la respuesta es sí, probablemente sea no funcional.

Paso 3​

Finalmente comprobamos:

¿Podemos verificar objetivamente si se cumple?

Si no podemos, debemos mejorar su redacción.

Ejemplo

“Los usuarios podrán reservar material” → funcional.

“La aplicación será usable desde móvil” → no funcional.

“El sistema impedirá reservar un material ya ocupado” → funcional, porque es una regla de negocio.

“Solo los usuarios autorizados podrán acceder a la administración” → no funcional, porque expresa una condición general de seguridad.

9️⃣ Cómo redactar un buen requisito​

Para que un requisito sea útil, conviene que cumpla estas características.

🟩 Claro​

Debe entenderse sin dar demasiadas vueltas.

Mal:

El sistema tendrá cierta capacidad de gestión.

Mejor:

El sistema permitirá registrar la devolución de un material prestado.

🟦 Concreto​

Debe decir algo preciso, no una idea general.

Mal:

La aplicación gestionará usuarios.

Mejor:

El administrador podrá crear, modificar y desactivar cuentas de usuario.

🟨 Comprobable​

Después debe poder comprobarse si se cumple o no.

Mal:

La aplicación será agradable de usar.

Mejor:

La aplicación mostrará mensajes de confirmación al completar una reserva o cancelar una operación.

🟧 Coherente con el proyecto​

Debe tener sentido con el problema, los objetivos y el alcance definidos.

Mal:

El sistema generará facturas en PDF.

Si el proyecto no incluye pagos ni ventas, este requisito no tiene sentido.

🟥 Viable​

Debe poder desarrollarse dentro del tiempo y el alcance del proyecto.

Mal:

El sistema incorporará reconocimiento por voz y análisis predictivo en tiempo real.

Si no está justificado y no es viable, no debería figurar como requisito del MVP.

🔟 Errores frecuentes al redactar requisitos​

❌ Confundir objetivo con requisito​

Objetivo:

Mejorar la gestión del material compartido.

Requisito:

RF03. El sistema permitirá registrar la entrega de un material reservado.

❌ Confundir funcionalidad con interfaz​

Mal:

Habrá una pantalla bonita para usuarios.

Mejor:

RF06. El usuario podrá consultar sus préstamos activos.

❌ Usar palabras vagas​

Evitemos expresiones como:

  • bonito.
  • intuitivo.
  • moderno.
  • rápido.
  • fácil.
  • completo.
  • eficiente.
  • adecuado.

No es que nunca puedan aparecer, sino que por sí solas no bastan como requisito.

❌ Meter demasiadas cosas en un solo requisito​

Mal:

RF10. El sistema permitirá consultar materiales, reservarlos, cancelarlos, pedir prórrogas, escribir mensajes, subir imágenes y generar informes.

Mejor dividirlo en varios requisitos más simples.

❌ Redactar requisitos que no responden a ninguna necesidad​

Si no sabemos por qué ese requisito está ahí, probablemente no debería estar.

1️⃣1️⃣ Cómo numerar los requisitos​

Conviene identificarlos con un código para poder referirnos a ellos con claridad.

🟩 Requisitos funcionales​

Usaremos un formato como este:

  • RF01
  • RF02
  • RF03

🟦 Requisitos no funcionales​

Usaremos un formato como este:

  • RNF01
  • RNF02
  • RNF03
info

La numeración no es un detalle estético.

Nos ayuda a:

  • referirnos a un requisito concreto.
  • modificarlo sin confundirnos.
  • relacionarlo después con pruebas, incidencias o entregas.

1️⃣2️⃣ Ejemplo comparado: mal y bien​

🟥 Versión mal planteada​

Supongamos un proyecto sobre reservas de material.

Los requisitos podrían aparecer así:

  • La aplicación será intuitiva.
  • El usuario podrá hacer muchas cosas.
  • Habrá reservas.
  • Será rápida.
  • La aplicación será moderna.
  • Habrá un sistema de control.

El problema es que, con esta redacción:

  • no está claro qué hace la aplicación.
  • no sabemos quién hace cada acción.
  • no podemos comprobar casi nada.
  • y varias frases son demasiado vagas.

🟩 Versión mejor redactada​

Ahora lo expresamos mejor:

  • RF01. El sistema permitirá consultar el catálogo de materiales disponibles.
  • RF02. El sistema permitirá reservar un material disponible indicando fecha de inicio y fecha prevista de devolución.
  • RF03. El socio podrá cancelar una reserva futura antes del inicio del préstamo.
  • RF04. El responsable podrá registrar la entrega de un material reservado.
  • RF05. El responsable podrá registrar la devolución de un material prestado.
  • RNF01. La aplicación deberá poder utilizarse correctamente desde ordenador y móvil.
  • RNF02. Solo los usuarios con rol de responsable podrán gestionar inventario y préstamos.
  • RNF03. Los formularios validarán los campos obligatorios antes de enviarse.

Esta segunda versión resulta mucho más útil.

1️⃣3️⃣ Del borrador al requisito final​

No siempre escribiremos el requisito perfecto a la primera.

A veces partimos de una frase inicial y la mejoramos.

🟩 Ejemplo 1​

Borrador:

La app debe dejar reservar cosas.

Versión mejorada:

RF01. El sistema permitirá a una persona registrada reservar un material disponible.

Versión todavía mejor:

RF01. El sistema permitirá a una persona registrada reservar un material disponible indicando fecha de inicio y fecha prevista de devolución.

🟦 Ejemplo 2​

Borrador:

La aplicación debe ser segura.

Versión mejorada:

RNF01. Las funciones de administración solo estarán disponibles para usuarios autorizados.

Versión ampliada:

RNF01. Las funciones de gestión de usuarios e inventario solo estarán disponibles para personas con rol de responsable o administrador.

🟨 Ejemplo 3​

Borrador:

La aplicación será fácil de usar.

Versión mejorada:

RNF02. La aplicación mostrará mensajes claros de confirmación o error al completar una operación.

1️⃣5️⃣ Ilustración recomendada​

1️⃣6️⃣ Ejercicio guiado​

Podemos practicar con este ejemplo.

🟩 Situación inicial​

En un club deportivo, las inscripciones a actividades se realizan por WhatsApp. Esto provoca errores, olvidos y dificultad para saber cuántas plazas quedan libres.

🟦 Objetivo​

Mejorar la gestión de inscripciones y facilitar el control de plazas disponibles.

🟨 Funcionalidades posibles​

  • Consultar actividades.
  • Ver plazas disponibles.
  • Inscribirse en una actividad.
  • Cancelar una inscripción.
  • Consultar participantes.

🟧 Requisitos funcionales posibles​

  • RF01. El sistema mostrará la lista de actividades disponibles.
  • RF02. El sistema mostrará el número de plazas libres de cada actividad.
  • RF03. Una persona registrada podrá inscribirse en una actividad con plazas disponibles.
  • RF04. El sistema impedirá inscripciones cuando no queden plazas libres.
  • RF05. El responsable podrá consultar el listado de personas inscritas en cada actividad.

🟥 Requisitos no funcionales posibles​

  • RNF01. La aplicación deberá ser utilizable desde dispositivo móvil.
  • RNF02. Los formularios validarán los campos obligatorios antes del envío.
  • RNF03. Solo el personal autorizado podrá consultar el listado completo de participantes.

1️⃣7️⃣ Lista de comprobación final​

Antes de cerrar nuestros requisitos, conviene revisar si:

  • distinguen correctamente entre objetivo y requisito.
  • responden a una necesidad real del proyecto.
  • están redactados de forma clara.
  • describen una acción o condición concreta.
  • pueden comprobarse después.
  • no mezclan demasiadas ideas en un mismo punto.
  • utilizan una numeración coherente.
  • son viables dentro del proyecto.
important

Si un requisito no se entiende bien o no sabemos cómo comprobarlo, probablemente todavía no está bien redactado.

1️⃣8️⃣ Idea final para recordar​

Un requisito no es una frase para “rellenar documentación”.

Es una herramienta para pensar mejor el proyecto.

🟩 Qué debemos recordar​

  • La necesidad explica el problema.
  • El objetivo explica qué queremos conseguir.
  • La funcionalidad expresa una capacidad de la aplicación.
  • El requisito concreta qué debe hacer o cumplir la solución.

🟦 La pregunta clave​

Cuando terminemos de redactar un requisito, podemos preguntarnos:

¿Podríamos comprobar más adelante si esto se ha cumplido o no?

Si la respuesta es sí, probablemente vamos por buen camino.
